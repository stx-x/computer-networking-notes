# 5.5　SDN 控制平面

本节深入 SDN 控制平面——控制网络中启用了 SDN 的设备之间分组转发的网络范围逻辑，以及这些设备及其服务的配置与管理。这里的学习建立在 4.4 节对广义 SDN 转发的讨论之上，所以继续之前你可能想先复习那一节以及本章 5.1 节。与 4.4 节一样，我们再次采用 SDN 文献中的术语，把网络中的转发设备称为"**分组交换机**"（或简称交换机，省略"分组"二字），因为转发决策可以基于网络层源／目的地址、链路层源／目的地址，以及运输层、网络层、链路层分组首部中许多其他字段的值。这里的讨论也将为后面讨论 5G 蜂窝网络中的控制平面（它采用了类似 SDN 的途径）打下良好基础。

可以识别出 SDN 体系结构的四个关键特征 [Kreutz 2015]：

- **基于流的转发**。SDN 控制的交换机的分组转发可以基于运输层、网络层或链路层首部中任意多个字段的值。我们在 4.4 节看到，OpenFlow 1.0 抽象允许基于 11 个不同首部字段值进行转发。这与我们在 5.2–5.4 节研究的传统基于路由器的转发形成鲜明对比——那里 IP 数据报的转发只基于数据报的目的 IP 地址。回忆图 5.2：分组转发规则规定在交换机的流表中；计算、管理并安装网络中所有交换机里的流表项，正是 SDN 控制平面的工作。
- **数据平面与控制平面分离**。图 5.2 与图 5.14 清楚地显示了这种分离。数据平面由网络中的交换机组成——这些相对简单（但快速）的设备执行其流表中的"匹配加动作"规则。控制平面由服务器与软件组成，它们确定并管理交换机的流表。
- **网络控制功能：位于数据平面交换机之外**。既然 SDN 中的"S"代表"软件"（software），SDN 控制平面用软件实现也就并不奇怪。不过，与传统路由器不同，这些软件运行在既独立于、又远程于网络交换机的服务器上。如图 5.14 所示，控制平面本身由两部分组成——一个 **SDN 控制器**（或称网络操作系统 [Gude 2008]）和一组**网络控制应用**。控制器维护准确的网络状态信息（例如远程链路、交换机与主机的状态），把这些信息提供给运行在控制平面中的网络控制应用，并提供这些应用据以监视、编程和控制底层网络设备的手段。图 5.14 中的控制器虽然画成一台中心服务器，但实践中控制器只是**逻辑上**集中的；它通常实现在多台服务器上，以提供协调的、可扩展的性能与高可用性。
- **可编程的网络控制平面**。网络控制平面通过运行在控制平面中的网络控制应用而变得可编程。这些应用代表 SDN 控制平面的"大脑"，使用 SDN 控制器提供的 API 来规定并控制网络设备中的数据平面。例如，一个选路网络控制应用可以确定源与目的之间的端到端路径（比如利用 SDN 控制器维护的节点状态与链路状态信息运行 Dijkstra 算法）；另一个网络应用可以执行访问控制，即确定哪些分组应在交换机处被阻断（如 4.4.3 节第三个例子）；还有一个应用可以让交换机以执行服务器负载均衡的方式转发分组（4.4.3 节第二个例子）。

<Figure src="ch05/fig5-14.webp" caption="图 5.14　SDN 体系结构的组成：SDN 控制的交换机、SDN 控制器、网络控制应用" />

从这段讨论可以看出，SDN 代表了网络功能的一次重大"**解绑**"（unbundling）——数据平面交换机、SDN 控制器与网络控制应用是彼此独立的实体，可以分别由不同厂商和组织提供。这与前 SDN 时代的模式形成对比：那时一台交换机／路由器（连同其内嵌的控制平面软件与协议实现）是一体化的、垂直整合的，由单一厂商出售。SDN 中这种网络功能的解绑，常被比作早先从大型机（硬件、系统软件与应用均由单一厂商提供）到个人计算机（硬件、操作系统与应用彼此分离）的演进。计算硬件、系统软件与应用的解绑，催生了一个由这三方面创新驱动的丰富开放生态；SDN 的一个希望，就是它将继续推动并促成同样丰富的创新。

理解了图 5.14 的 SDN 体系结构，自然会引出许多问题：流表究竟如何计算、在哪里计算？这些表如何响应 SDN 控制设备上的事件（例如某条相连链路通断）而更新？多台交换机上的流表项如何协调，从而产生编排好的、一致的网络范围功能（例如从源到目的的端到端转发路径，或协同的分布式防火墙）？提供这些以及许多其他能力，正是 SDN 控制平面的职责。

## 5.5.1　SDN 控制平面：SDN 控制器与 SDN 网络控制应用

先抽象地讨论 SDN 控制平面，考察控制平面必须提供的一般能力。我们将会看到，这种抽象的"第一性原理"途径会把我们引向一个整体架构，而它恰好反映了 SDN 控制平面在实践中是如何实现的。

如上所述，SDN 控制平面大致分为两部分——**SDN 控制器**与 **SDN 网络控制应用**。先探讨控制器。自最早的 SDN 控制器 [Gude 2008] 以来，已开发出许多不同的 SDN 控制器 [Kreutz 2015]，但它们的结构大体可以组织为三层。我们一反常态地自底向上来看这三层：

- **通信层**：在 SDN 控制器与被控网络设备之间通信。显然，如果 SDN 控制器要控制一台远程 SDN 交换机、主机或其他设备的运行，就需要一个协议在控制器与该设备之间传递信息。此外，设备必须能把本地观察到的事件告知控制器（例如某条相连链路通了或断了、某台设备刚加入网络，或表明设备在线运行的心跳）。这些事件为 SDN 控制器提供网络状态的最新视图。该协议构成控制器体系结构的最底层，如图 5.15 所示。控制器与被控设备之间的通信跨越所谓的控制器"**南向**"接口。5.5.2 节将研究 OpenFlow——提供这种通信功能的一个具体协议。绝大多数（如果不是全部）SDN 控制器都实现了 OpenFlow。
- **网络范围的状态管理层**。SDN 控制平面做出的最终控制决策——例如配置所有交换机中的流表以实现期望的端到端转发、实现负载均衡，或实现某种特定的防火墙能力——都要求控制器拥有关于网络中主机、链路、交换机及其他 SDN 控制设备状态的最新信息。交换机的流表含有计数器，其值也可能为网络控制应用所用，因此这些值应可供应用访问。由于控制平面的最终目标是为各被控设备确定流表，控制器还可能维护这些表的一份拷贝。这些信息共同构成 SDN 控制器所维护的网络范围"状态"的例子。
- **到网络控制应用层的接口**。控制器通过其"**北向**"接口与网络控制应用交互。这个 API 允许网络控制应用读写状态管理层中的网络状态与流表。应用可以注册为在状态变化事件发生时收到通知，从而能对 SDN 控制设备发来的网络事件通知做出响应。可以提供的 API 类型有多种；我们将会看到，两个流行的 SDN 控制器使用 REST [Fielding 2000] 请求-响应接口与其应用通信。

<Figure src="ch05/fig5-15.webp" caption="图 5.15　SDN 控制器的组成" />

我们已经多次指出，SDN 控制器可以被视为"逻辑上集中"的，即从外部（例如从 SDN 控制设备与外部网络控制应用的角度）看，控制器可以看作一个单一的一体化服务。然而实践中，这些服务以及用于保存状态信息的数据库，是出于容错、高可用或性能考虑而由一组分布式服务器实现的。当控制器功能由一组服务器实现时，就必须考虑控制器内部操作的语义（例如维护事件的逻辑时序、一致性、共识等）[Panda 2013; Ferguson 2021]。这类问题是许多不同分布式系统共有的；这些挑战的优雅解法见 [Lamport 1989, Lampson 1996]。ONOS [ONOS 2025] 与 ORION [Ferguson 2021] 等现代控制器（见专栏）都相当重视设计一个逻辑集中但物理分布的控制器平台，为被控设备与网络控制应用同样提供可扩展的服务与高可用性。

图 5.15 描绘的架构，与 2008 年最初提出的 NOX 控制器 [Gude 2008] 的架构以及当今控制器的架构（见专栏）非常相似。5.5.3 节将给出一个控制器运行的例子。不过先来看 OpenFlow 协议——它是最早的、如今也是若干可选协议之一的、可用于 SDN 控制器与被控设备之间通信的协议，位于控制器的通信层。

## 5.5.2　OpenFlow 协议

OpenFlow 协议 [OpenFlow 2025] 运行在 SDN 控制器与实现了我们前面在 4.4 节研究过的 OpenFlow API 的 SDN 交换机或其他设备之间。OpenFlow 协议运行在 TCP 之上，默认端口号为 6653。

从控制器流向被控交换机的重要报文包括：

- **Configuration**（配置）。该报文允许控制器查询和设置交换机的配置参数。
- **Modify-State**（修改状态）。控制器用该报文添加／删除或修改交换机流表中的表项，并设置交换机端口属性。
- **Read-State**（读取状态）。控制器用该报文从交换机的流表与端口收集统计信息与计数器值。
- **Send-Packet**（发送分组）。控制器用该报文让被控交换机从指定端口发出一个特定分组。报文本身在其载荷中包含要发送的分组。

从 SDN 控制的交换机流向控制器的报文包括：

- **Flow-Removed**（流删除）。该报文通知控制器某个流表项已被删除，例如因超时或由于收到修改状态报文。
- **Port-status**（端口状态）。交换机用该报文通知控制器端口状态的变化。
- **Packet-in**（分组入）。回忆 4.4 节：到达交换机端口但不匹配任何流表项的分组被送到控制器做进一步处理。匹配的分组也可能作为匹配时采取的一个动作被送到控制器。packet-in 报文就用于把这类分组送给控制器。

## 5.5.3　数据平面与控制平面的交互：一个例子

为巩固对 SDN 控制交换机与 SDN 控制器之间交互的理解，考虑图 5.16 中的例子，其中用 Dijkstra 算法（5.2 节学过）确定最短路径路由。图 5.16 的 SDN 场景与前面 5.2.1、5.3 节的逐路由器控制场景有两个重要区别——在后者中，Dijkstra 算法在每台路由器中实现，链路状态更新在所有网络路由器之间泛洪：

- Dijkstra 算法作为独立应用在分组交换机**之外**执行。
- 分组交换机把链路更新发送给 SDN 控制器，而不是彼此之间发送。

<Figure src="ch05/fig5-16.webp" caption="图 5.16　SDN 控制器场景：链路状态变化" />

在这个例子中，假设交换机 s1 与 s2 之间的链路断开；采用最短路径路由，因而 s1、s3、s4 的入向与出向流转发规则受到影响，而 s2 的运行不变。还假设使用 OpenFlow 作为通信层协议，并且控制平面除链路状态选路外不执行其他功能。

1. 交换机 s1 发现自己与 s2 之间的链路故障，用 OpenFlow 的 port-status 报文把链路状态变化通知 SDN 控制器。
1. SDN 控制器收到表明链路状态变化的 OpenFlow 报文，通知链路状态管理器，后者更新链路状态数据库。
1. 实现 Dijkstra 链路状态选路的网络控制应用此前已注册为在链路状态变化时收到通知。该应用收到链路状态变化通知。
1. 链路状态选路应用与链路状态管理器交互以获取更新后的链路状态；它也可能查询状态管理层中的其他组件。然后它计算新的最小代价路径。
1. 链路状态选路应用随后与流表管理器交互，由后者确定需要更新哪些流表。
1. 流表管理器随后用 OpenFlow 协议更新受影响交换机的流表项——s1（现在将经 s4 转发目的地为 s2 的分组）、s2（现在将开始经中间交换机 s4 接收来自 s1 的分组）、s4（现在必须转发来自 s1、目的地为 s2 的分组）。

这个例子很简单，却说明了 SDN 控制平面如何提供以前要在每台网络路由器中通过逐路由器控制来实现的控制平面服务（这里是网络层选路）。现在很容易体会：一个启用了 SDN 的 ISP 如何能轻松地从最小代价路径选路切换到更量身定制的选路方式。确实，既然控制器可以随意裁剪流表，它就能实现它想要的任何转发形式——只需改动其应用控制软件。这种易于变更应当与传统逐路由器控制平面的情形相对照：那里必须改动**所有**路由器中的软件（而这些软件可能由多个相互独立的厂商提供给该 ISP）。

<AsideCard title="原理与实践 · SDN 控制器案例：ONOS 与 Orion">

在 SDN 的早期，只有一种 SDN 协议（OpenFlow [McKeown 2008; OpenFlow 2025]）和一个 SDN 控制器（NOX [Gude 2008]）。此后，SDN 控制器的数量显著增长 [Kreutz 2015]。有些 SDN 控制器是公司专用、专有的，尤其是在用于控制内部专有网络（例如公司数据中心内部或之间）时。本专栏介绍两个 SDN 控制器，以说明逻辑集中这一原则在实践中是如何实现的。

**ONOS 控制器**　Open Network Operating System（ONOS®）[ONOS 2025] 是由开放网络基金会 [OpenNetworking 2025] 创建、分发和支持的开源 SDN 控制器。图 5.17 给出 ONOS 控制器的简化视图。与图 5.15 中的典型控制器类似，ONOS 控制器中可以识别出三层：

- **北向抽象与协议**。ONOS 的一个独特之处是它的 **intent**（意图）框架，允许应用请求一项高层服务（例如在主机 A 与主机 B 之间建立连接，或反之不允许 A 与 B 通信），而不必知道该服务如何执行的细节。状态信息通过北向 API 以同步（查询）或异步（监听器回调，例如网络状态变化时）方式提供给网络控制应用。
- **分布式核心**。网络中链路、主机与设备的状态保存在 ONOS 的分布式核心中。ONOS 作为服务部署在一组互联的服务器上，每台服务器运行一份相同的 ONOS 软件拷贝；服务器数量增加则服务容量增加。ONOS 核心提供服务复制与实例间协调的机制，为上层应用与下层网络设备提供逻辑集中核心服务的抽象。
- **南向抽象与协议**。南向抽象屏蔽了底层主机、链路、交换机与协议的异构性，使分布式核心既与设备无关、也与协议无关。由于这层抽象，分布式核心之下的南向接口在逻辑上高于图 5.14 中典型控制器的对应接口。

<Figure src="ch05/fig5-17.webp" caption="图 5.17　ONOS 控制器体系结构" />

**Orion**　Orion [Ferguson 2021] 是第二代 SDN 平台，用于控制 Google 的 Jupiter 数据中心网络 [Singh 2015]，以及把这些数据中心全球互联的内部 B4 广域网 [Jain 2013]。图 5.18 给出 Orion 的高层视图。Orion 的总体结构与语境与图 5.17 的 ONOS 惊人地相似。确实，Orion 的创建者指出 [Ferguson 2021]，"Orion 的架构……对应教科书式的 ONF 视图" [ONF 2013]。图 5.18 中央是 Orion SDN 核心，向北是到 Orion 应用的接口，向南是到 Orion 控制的路由器与交换机的接口。但在这个共同的高层视图之下，可以发现许多与 ONOS 的重要差别。

<Figure src="ch05/fig5-18.webp" caption="图 5.18　Google 的 Orion SDN" />

每个 Google 网络被划分为一个或多个**域**，一个 Orion SDN 控制器实例负责管理与控制其域内的设备。使用域有意限制了任何故障的影响范围与规模，也限制了单个 Orion 控制器必须完成的工作量。

Orion 核心的心脏是**网络信息库**（Network Information Base，NIB）。NIB 是一个逻辑集中的数据存储，配有一套数据驱动的发布／订阅（pub/sub）系统，使 Orion 应用与核心组件可以读写 NIB 数据，并在 NIB 数据变化时收到通知。逻辑集中的数据存储还有一个好处：可以全局地为网络事件定序，这对调试与排障大有帮助。[Ferguson 2021] 指出："基于多年经验，NIB 一直是我们最成功的设计要素之一。"一个 Orion NIB 每秒可处理约一百万次读／写事件。

Orion 核心中包含以下以微服务方式实现的组件：

- **拓扑管理器**（Topology Manager）维护 Orion 控制器域内链路、路由器与交换机的状态，还查询并接收运行时的端口统计。
- **配置管理器**（Config Manager）通过在 NIB 表中设置配置参数属性来配置 Orion 控制器域内的组件，还可以检查并校验配置的正确性。
- **流管理器**（Flow Manager）确保应用登记在 NIB 中的预期网络状态与行为，与被控设备报告的总体状态一致，并在需要时执行流状态的对账（reconciliation）。

Orion 应用位于 Orion 核心之上，通过 NIB 彼此交互并与其他 Orion 组件交互。**选路引擎**（Routing Engine）是域内选路应用，提供域间选路应用（如 Raven）与数据中心 spline 选路应用（如 IBR-C）所需的抽象拓扑与可达性信息。图 5.18 中的 **TE** 应用执行流量工程，**Path Exporter** 应用把数据平面状态导出给 Orion 之外的服务。

Orion 支持一种称为**基于意图的网络**（intent-based networking）的管理与控制途径。[Ferguson 2021] 指出："基于意图的网络通过描述网络新的预期**终态**（"做什么"）来规定管理或设计变更，而不是规定把网络带到该终态的一系列修改（"怎么做"）。"例如，预期的网络拓扑以抽象模型来规定 [Mogul 2020]。这是高层意图，且具有权威性：它要求较低层的网络应用（例如链路激活、选路应用）监视、设置并改变其配置，以满足这一高层意图。于是意图自上而下传播，并在较长时间尺度上保持稳定；网络状态以及为使网络状态与高层意图一致所需的变更则自下而上发生，并随网络条件变化而更快变化。意图、配置设置与被监视的设备状态都保存在 NIB 中，NIB 的 pub/sub 机制用于在应用需要响应 NIB 值变化而采取动作时通知它们。关于 Orion 基于意图的网络的讨论见 [Ferguson 2021]。

## 5.5.4　SDN：过去与未来

虽然对 SDN 的浓厚兴趣是相对晚近的现象，但 SDN 的若干技术根源——特别是数据平面与控制平面的分离——要早得多。今天的因特网的祖先 ARPAnet，有意强调基于协议的分散式网络控制途径。然而，20 世纪 70 年代初的另外两个数据网络完全拥抱了集中式控制以及数据平面与控制平面的清晰分离。TYMNET I [Tymes 1981] 是一个虚电路数据网络，它有一个集中式控制器，并用一个物理上分离的、基于树的控制网络，把 TYMNET 节点中的控制部分连接到树根的集中式控制器；而 TYMNET I 节点的数据平面则可以按任意网状拓扑连接。AT&T 的 Spider 网络 [Fraser 1993] 也有清晰的数据／控制平面分离，为在节点与集中式控制器之间收发控制报文保留了专用虚电路。

20 世纪 90 年代直到 2000 年代，数据／控制平面分离再次走到前台。[van der Merwe 1998] 描述了一个用于 ATM 网络 [Black 1995] 的控制框架，其中有多个控制器，每个控制若干台 ATM 交换机。2004 年，[Feamster 2004; Lakshman 2004; RFC 3746] 都主张把网络的数据平面与控制平面分离。除逻辑集中式控制与数据／控制平面分离之外，常与 SDN 联系在一起的其他属性还包括网络虚拟化、软件化与可编程性。[Feamster 2014; Anenousis 2021] 都深入探讨了 SDN 背后概念的历史。

Ethane 项目 [Casado 2007] 开创了这样一种构想：由简单的、基于流的以太网交换机组成网络，其流表采用匹配加动作；由一个集中式控制器管理流的准入与选路；未匹配的分组从交换机转发给控制器。2007 年，一个由 300 多台 Ethane 交换机组成的网络投入运行。Ethane 很快演化为 OpenFlow 项目，剩下的（正如俗话所说）就是历史了！

许多研究工作致力于发展未来的 SDN 体系结构与能力。如我们所见，SDN 革命正在导致专用的一体化交换机与路由器（同时含数据平面与控制平面）被简单的通用交换硬件加精巧的软件控制平面所颠覆性取代。SDN 的一种推广——**网络功能虚拟化**（NFV，4.5 节讨论过）——同样旨在用简单的通用服务器、交换与存储，颠覆性地取代复杂的中盒（例如为媒体缓存／服务而带有专用硬件与专有软件的中盒）。另一个重要挑战是让 SDN 控制器的结构对故障（例如路由器或计算机崩溃、连接丢失）具有健壮性，并能在故障确实发生时迅速恢复 [Ferguson 2021; Krentsel 2024]。
