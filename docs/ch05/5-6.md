# 5.6　ICMP：因特网控制报文协议

**因特网控制报文协议**（Internet Control Message Protocol，ICMP）规定在 [RFC 792] 中，被主机与路由器用来彼此通信网络层信息。ICMP 最典型的用途是**差错报告**。例如，在运行一次 HTTP 会话时，你可能遇到过"目的网络不可达"（Destination network unreachable）这样的差错消息，它就源自 ICMP：某个时刻，某台 IP 路由器无法找到通往你 HTTP 请求中指定主机的路径，那台路由器便生成一条 ICMP 报文发给你主机，指出该差错。

ICMP 常被视为 IP 的一部分，但从体系结构上看它位于 IP 之上，因为 ICMP 报文是在 IP 数据报内部承载的。也就是说，ICMP 报文作为 IP 载荷被承载，正如 TCP 或 UDP 报文段作为 IP 载荷被承载一样。类似地，当一台主机收到一个上层协议指定为 ICMP 的 IP 数据报（上层协议号为 1）时，它把数据报内容多路分用给 ICMP，就像把数据报内容多路分用给 TCP 或 UDP 一样。

ICMP 报文有一个**类型**字段和一个**代码**字段，并包含引起该 ICMP 报文生成的那个 IP 数据报的首部与前 8 个字节（以便发送方能确定是哪个数据报引起了差错）。部分 ICMP 报文类型见图 5.19。注意，ICMP 报文不只用于表示差错状态。

| 12 | 0 | IP 首部损坏 |

众所周知的 **ping** 程序向指定主机发送一条 ICMP 类型 8、代码 0 的报文。目的主机看到回显请求后，回送一条类型 0、代码 0 的 ICMP 回显应答。大多数 TCP/IP 实现直接在操作系统中支持 ping 服务器，也就是说该服务器不是一个进程。[Stevens 1990] 第 11 章给出了 ping 客户端程序的源代码。注意，客户端程序必须能够指示操作系统生成类型 8、代码 0 的 ICMP 报文。

第 1 章介绍了 **Traceroute** 程序，它让我们能追踪从一台主机到世界上任何其他主机的路由。有意思的是，Traceroute 正是用 ICMP 报文实现的。为确定源与目的之间各路由器的名字与地址，源端的 Traceroute 向目的地发送一系列普通 IP 数据报，每个数据报携带一个 UDP 报文段，其 UDP 端口号是一个不太可能被使用的号。这些数据报中第一个的 TTL 为 1，第二个为 2，第三个为 3，依此类推。源端还为每个数据报启动定时器。当第 $n$ 个数据报到达第 $n$ 台路由器时，第 $n$ 台路由器发现该数据报的 TTL 刚刚到期。按照 IP 协议的规则，路由器在数据报 TTL 到期时必须丢弃该数据报；此外，路由器通常向源端发送一条 ICMP 警告报文（类型 11、代码 0）。这条警告报文包含该路由器的名字及其 IP 地址。当这条 ICMP 报文回到源端时，源端从定时器得到往返时间，并从 ICMP 报文得到第 $n$ 台路由器的名字与 IP 地址。

Traceroute 源端如何知道何时停止发送 UDP 报文段？回忆源端每发送一个数据报就递增 TTL 字段。因此，其中某个数据报最终会一路到达目的主机。由于该数据报携带的 UDP 报文段的端口号不太可能被使用，目的主机便向源端回送一条"端口不可达"的 ICMP 报文（类型 3、代码 3）。当源主机收到这条特定的 ICMP 报文时，它就知道不必再发送探测分组了。（标准 Traceroute 程序实际上对同一 TTL 发送三个分组一组；因此 Traceroute 的输出对每个 TTL 给出三个结果。）

通过这种方式，源主机得知位于它与目的主机之间的路由器数目与身份，以及两台主机之间的往返时间。注意，Traceroute 客户端程序必须能够指示操作系统生成具有特定 TTL 值的 UDP 数据报，还必须能够在其操作系统收到 ICMP 报文时得到通知。既然你已经理解了 Traceroute 的工作原理，不妨回头再玩玩它。

RFC 4443 为 IPv6 定义了一个新版本的 ICMP。除了重新组织已有的 ICMP 类型与代码定义之外，ICMPv6 还增加了新 IPv6 功能所要求的新类型与新代码，其中包括"分组太大"（Packet Too Big）类型与"未识别的 IPv6 选项"差错代码。
