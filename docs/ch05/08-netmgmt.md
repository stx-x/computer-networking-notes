# 5.7　网络管理与 SNMP、NETCONF/YANG

至此我们对网络层的学习已接近尾声，前面只剩链路层。我们很清楚：一个网络由许多复杂、相互作用的硬件与软件部件组成——从构成网络物理组件的链路、交换机、路由器、主机及其他设备，到控制并协调这些设备的众多协议。当一个组织把成百上千个这样的部件汇集起来组成一个网络时，网络管理员要让网络"保持运行"的任务无疑是项挑战。我们在 5.5 节看到，在 SDN 语境下逻辑集中的控制器能对这项工作有所帮助。但网络管理的挑战早在 SDN 之前就已存在，伴随的是一整套丰富的网络管理工具与途径，帮助网络管理员监视、管理和控制网络。本节研究这些工具与技术，以及与 SDN 一同演化出来的新工具与新技术。

一个常被问的问题是"什么是网络管理？"[Saydam 1996] 给出了一个构思良好、一句话（虽然是个相当长的连写句）的定义：

网络管理包括硬件、软件与人这三类要素的部署、集成与协调，以对网络及网元资源进行监视、测试、轮询、配置、分析、评估与控制，从而以合理的成本满足实时性、运行性能与服务质量方面的要求。

鉴于这个宽泛的定义，本节只讲网络管理的基本内容——网络管理员执行任务时所使用的体系结构、协议与数据。我们不讨论管理员的决策过程，那里要考虑故障识别 [Labovitz 1997; Steinder 2002; Feamster 2005; Wu 2005; Teixeira 2006]、异常检测 [Lakhina 2005; Barford 2009]、为满足签约服务等级协议（SLA）而进行的网络设计／工程 [Huston 1999a] 等问题。因此我们的关注点是有意收窄的；有兴趣的读者应查阅这些文献、[Subramanian 2000; Schonwalder 2010; Claise 2019] 中出色的综述，以及本书网站上关于网络管理更详细的论述。

## 5.7.1　网络管理框架

图 5.20 展示了网络管理的关键组件：

- **管理服务器**（managing server）。管理服务器是一个应用，通常有网络管理员（人）参与其中，运行于网络运行中心（NOC）里的一台集中式网络管理站上。管理服务器是网络管理活动的中心：它控制网络管理信息与命令的收集、处理、分析与分发；正是在这里发起配置、监视与控制网络中被管设备的动作。实践中，一个网络可能有多台这样的管理服务器。
- **被管设备**（managed device）。被管设备是位于被管网络中的一件网络设备（包括其软件）。被管设备可以是一台主机、路由器、交换机、中盒、调制解调器、温度计或其他联网设备。设备本身会有许多可管理的组件（例如网络接口只是主机或路由器的一个组件），以及这些硬件与软件组件的配置参数（例如 OSPF 这样的 AS 内路由协议）。
- **数据**。每台被管设备都有与之关联的数据，也称为"状态"。数据有几种不同类型。**配置数据**是网络管理员显式配置的设备信息，例如管理员为某个设备接口指定／配置的 IP 地址或接口速率。**运行数据**是设备在运行过程中获取的信息，例如 OSPF 协议中的直接邻居列表。**设备统计**是随设备运行而更新的状态指示与计数（例如某接口上丢弃的分组数，或设备风扇转速）。网络管理员可以查询远程设备数据，在某些情况下还可以通过写入设备数据值来控制远程设备，如下文所述。如图 5.20 所示，管理服务器还维护着自己的一份拷贝，包含来自其被管设备的配置、运行与统计数据，以及网络范围的数据（例如网络拓扑）。
- **网络管理代理**（network management agent）。网络管理代理是运行在被管设备中的软件进程，它与管理服务器通信，在管理服务器的命令与控制下在被管设备上执行本地动作。网络管理代理类似于我们在图 5.2 中看到的选路代理。
- **网络管理协议**（network management protocol）。网络管理框架的最后一个组件是网络管理协议。该协议运行在管理服务器与被管设备之间，使管理服务器能查询被管设备的状态，并通过其代理在这些设备上采取动作。代理可以用网络管理协议把异常事件（例如组件故障或性能阈值被违反）告知管理服务器。需要强调的是：网络管理协议本身并不管理网络，而是提供能力，供网络管理员用来管理（"监视、测试、轮询、配置、分析、评估与控制"）网络。这个区分微妙但重要。

<Figure src="ch05/fig5-20.webp" caption="图 5.20　网络管理的要素" />

实践中，网络运营者用上述组件管理网络，常见方式有三种：

- **CLI**。网络运营者可以向设备发出直接的**命令行界面**（Command Line Interface）命令。这些命令可以直接在被管设备的控制台上输入（如果运营者就在设备旁），也可以通过管理服务器／控制器与被管设备之间的 Telnet 或安全外壳（SSH）连接（可能借助脚本）输入。CLI 命令因厂商和设备而异，可能相当晦涩。老练的网络高手也许能用 CLI 无差错地配置网络设备，但 CLI 使用容易出错，且难以自动化、难以在大型网络中高效扩展。面向消费者的网络设备（例如你家的无线路由器）可能提供一个管理菜单，你（就是网络管理员！）可以通过 HTTP 访问以配置该设备。这种方式对单个简单设备也许很好用，也比 CLI 更不易出错，但同样无法扩展到较大规模的网络。
- **SNMP/MIB**。在这种方式中，网络运营者可以用**简单网络管理协议**（SNMP）查询／设置设备**管理信息库**（MIB）对象中的数据。有些 MIB 是设备与厂商专用的，另一些 MIB（例如路由器上因 IP 数据报首部出错而丢弃的 IP 数据报数，或主机收到的 UDP 报文段数）则与设备无关，提供了抽象与通用性。网络运营者最常用这种方式查询与监视运行状态及设备统计，然后用 CLI 主动控制／配置设备。需要强调的是：这两种方式都是**逐设备**管理的。下文 5.7.2 节将讨论自 20 世纪 80 年代末就在使用的 SNMP 与 MIB。互联网架构委员会 2002 年召开的一次网络管理研讨会 [RFC 3535] 既指出了 SNMP/MIB 方式在设备监视方面的价值，也指出了它的不足，特别是在设备配置与大规模网络管理方面。这就促成了最新的网络管理方式——使用 NETCONF 与 YANG。
- **NETCONF/YANG**。NETCONF/YANG 方式对网络管理采取更抽象、网络范围、整体化的视角，更强调配置管理，包括规定正确性约束，并对多台被控设备提供原子性的管理操作。YANG [RFC 6020] 是一种数据建模语言，用于对配置数据与运行数据建模。NETCONF 协议 [RFC 6241] 用于与远程设备之间／之间传递与 YANG 兼容的动作与数据。

## 5.7.2　简单网络管理协议（SNMP）与管理信息库（MIB）

**简单网络管理协议**版本 3（SNMPv3）[RFC 3410] 是一个应用层协议，用于在管理服务器与代表该管理服务器执行的代理之间传递网络管理控制与信息报文。SNMP 最常见的用法是请求-响应模式：SNMP 管理服务器向 SNMP 代理发送请求，代理接收请求、执行某些动作，并回送应答。通常，请求用于查询（获取）或修改（设置）与被管设备关联的 MIB 对象值。SNMP 的第二种常见用法是代理向管理服务器发送一条非请求报文，称为 **trap**（陷阱）报文。trap 报文用于把导致 MIB 对象值发生变化的异常情况（例如某链路接口通了或断了）告知管理服务器。

MIB 对象用一种称为 **SMI**（Structure of Management Information，管理信息结构）的数据描述语言来规定 [RFC 2578; RFC 2579; RFC 2580]。这是网络管理框架中名字颇为古怪的一个组件，其名称丝毫不能提示它的功能。使用形式化的定义语言，是为了确保网络管理数据的语法与语义定义良好且无歧义。相关的 MIB 对象被汇集为 **MIB 模块**。截至 2024 年末，已有 400 多个与 MIB 相关的 RFC，厂商专用的（私有）MIB 模块数量则多得多。

SNMPv3 定义了七种报文类型，统称为**协议数据单元**（PDU），见表 5.2 及下文说明。

<p class="tbl-cap">表 5.2　SNMPv3 的 PDU 类型</p>

| **SNMPv3 PDU 类型** | **发送方-接收方** | **描述** |
| --- | --- | --- |
| GetRequest | manager→agent | 获取一个或多个 MIB 对象实例的值 |
| GetNextRequest | manager→agent | 获取列表或表中下一个 MIB 对象实例的值 |
| GetBulkRequest | manager→agent | 获取一大块数据中的值，例如大表中的值 |
| InformRequest | manager→manager | 把接收方无法访问的 MIB 值告知远程管理实体 |
| SetRequest | manager→agent | 设置一个或多个 MIB 对象实例的值 |
| Response | agent→manager 或 manager→manager | 响应 GetRequest、GetNextRequest、GetBulkRequest、SetRequest 或 InformRequest PDU 而生成 |
| SNMPv2-Trap | agent→manager | 把异常事件告知管理者 |

- GetRequest、GetNextRequest 与 GetBulkRequest 三种 PDU 都由管理服务器发给代理，用于请求代理所在被管设备上一个或多个 MIB 对象的值。被请求取值的 MIB 对象在 PDU 的**变量绑定**部分指定。这三种 PDU 在数据请求的粒度上不同：GetRequest 可以请求任意一组 MIB 值；多个 GetNextRequest 可用于遍历一个列表或表中的 MIB 对象；GetBulkRequest 允许返回一大块数据，避免发送多个 GetRequest 或 GetNextRequest 报文所带来的开销。这三种情况下，代理都回送一个 Response PDU，其中包含对象标识符及其关联值。
- SetRequest PDU 由管理服务器用来设置被管设备中一个或多个 MIB 对象的值。代理回送一个错误状态为 "noError" 的 Response PDU，以确认该值确实已被设置。
- InformRequest PDU 由管理服务器用来把接收服务器无法访问的 MIB 信息告知另一台管理服务器。
- Response PDU 通常由被管设备发给管理服务器，作为对该服务器请求报文的响应，返回所请求的信息。
- SNMPv3 PDU 的最后一种是 **trap** 报文。trap 报文是异步生成的，也就是说，它们不是为响应收到的请求而生成，而是为响应需要告知管理服务器的事件而生成。RFC 3418 定义了一些众所周知的 trap 类型，包括设备的冷启动或热启动、链路通断、邻居丢失，以及鉴别失败事件。管理服务器收到 trap 请求后不要求作出响应。

鉴于 SNMP 的请求-响应特性，这里值得指出：虽然 SNMP PDU 可以通过许多不同的运输协议承载，但它通常装在 UDP 数据报的载荷中。确实，RFC 3417 指出 UDP 是"首选的运输映射"。然而，由于 UDP 是不可靠的运输协议，请求或其响应并不能保证到达预期目的地。有意思的是，SNMP 标准并未规定任何特定的重传过程，甚至没有规定是否要做重传，只要求管理服务器"在重传的频率与持续时间方面需要负责任地行事"。这自然让人想知道：一个"负责任"的协议到底该怎么做！

SNMP 已经历三个版本。SNMPv3 的设计者说："SNMPv3 可以看作在 SNMPv2 之上增加了安全与管理能力的版本" [RFC 3410]。SNMPv3 相对 SNMPv2 确实有变化，但变化最明显之处莫过于管理与安全方面。安全在 SNMPv3 中的核心作用尤其重要，因为缺乏足够的安全性曾导致 SNMP 主要被用于监视而非控制（例如 SetRequest 在 SNMPv1 中极少被使用）。我们再次看到：安全——第 8 章将详细讨论的主题——是一个至关重要的关切，但同样是一个其重要性或许被认识得稍晚、然后才被"追加"上去的关切。

### 管理信息库（MIB）

前面我们学到：在 SNMP/MIB 方式的网络管理中，被管设备的运行状态数据（以及某种程度上它的配置数据）被表示为对象，这些对象汇集为该设备的 **MIB**。一个 MIB 对象可以是一个计数器，例如路由器上因 IP 数据报首部出错而丢弃的 IP 数据报数，或以太网接口卡上的载波侦听错误数；可以是描述性信息，例如 DNS 服务器上运行的软件版本；可以是状态信息，例如某台设备是否正常工作；也可以是协议特定信息，例如到某个目的地的选路路径。相关的 MIB 对象被汇集为 MIB 模块。在各种 IETF RFC 中定义了 400 多个 MIB 模块；设备与厂商专用的 MIB 还要多得多。[RFC 4293] 规定了定义用于管理 IP 及其相关 ICMP 实现的管理对象（包括 `ipSystemStatsInDelivers`）的 MIB 模块；[RFC 4022] 规定了 TCP 的 MIB 模块；[RFC 4113] 规定了 UDP 的 MIB 模块。

虽然与 MIB 相关的 RFC 读起来相当枯燥乏味，但看一个 MIB 对象的例子仍然是有教益的（就像吃蔬菜，"对你有好处"）。[RFC 4293] 中的 `ipSystemStatsInDelivers` 对象类型定义了一个 32 位只读计数器，用来记录在被管设备上收到并成功交付给上层协议的 IP 数据报数。在下例中，`Counter32` 是 SMI 定义的基本数据类型之一。

## 5.7.3　网络配置协议（NETCONF）与 YANG

NETCONF 协议运行在管理服务器与被管网络设备之间，提供以下报文能力：(i) 获取、设置与修改被管设备上的配置数据；(ii) 查询被管设备上的运行数据与统计；(iii) 订阅被管设备产生的通知。管理服务器通过向被管设备发送配置（以结构化 XML 文档规定）并激活该配置，来主动控制被管设备。NETCONF 采用远程过程调用（RPC）范式，协议报文同样以 XML 编码，并通过管理服务器与被管设备之间的安全、面向连接的会话（例如 TCP 之上第 8 章将讨论的 TLS）交换。

图 5.21 展示了一个 NETCONF 会话的例子。首先，管理服务器与被管设备建立安全连接。（用 NETCONF 的行话说，管理服务器实际被称为"客户端"，被管设备被称为"服务器"，因为是管理服务器向被管设备发起连接。但为与图 5.20 中沿用更久的网络管理服务器／客户端术语保持一致，这里我们忽略这一点。）安全连接建立后，管理服务器与被管设备交换 `<hello>` 报文，声明各自的"能力"——即补充 [RFC 6241] 中 NETCONF 基本规范之外的 NETCONF 功能。管理服务器与被管设备之间的交互采取远程过程调用的形式，使用 `<rpc>` 与 `<rpc-response>` 报文。这些报文用于获取、设置、查询与修改设备配置、运行数据与统计，以及订阅设备通知。设备通知本身则用 NETCONF `<notification>` 报文由被管设备主动发送给管理服务器。会话用 `<session-close>` 报文关闭。

### YANG

YANG 是用于精确规定 NETCONF 所用网络管理数据的结构、语法与语义的数据建模语言，其作用与 SNMP 中用 SMI 规定 MIB 大体相同。所有 YANG 定义都包含在模块中，并且可以由一个 YANG 模块生成描述某台设备及其能力的 XML 文档。

YANG 具备一小组内建数据类型（如 SMI 那样），还允许数据建模者表达一个合法 NETCONF 配置必须满足的约束——这在帮助确保 NETCONF 配置满足指定的正确性与一致性约束方面是强有力的辅助手段。YANG 也用于规定 NETCONF 通知。

对 YANG 更充分的讨论超出本书范围。更多信息请参阅出色的专著 [Claise 2019]。
