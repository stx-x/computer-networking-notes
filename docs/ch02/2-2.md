# 2.2　Web 与 HTTP

直到 20 世纪 90 年代初，因特网主要由研究者、学者和大学生使用：登录远程主机、在本地主机与远程主机之间传送文件、收发新闻、收发电子邮件。虽然这些应用当时（以及现在）极其有用，但因特网在学术与研究圈之外基本无人知晓。然后在 90 年代初，一个全新的重量级应用登场了——万维网 [Berners-Lee 1994]。Web 是第一个抓住普通公众眼球的因特网应用，它极大地改变了人们在工作中和工作之外互动的方式，把因特网从"众多数据网络之一"提升为实质上"唯一的数据网络"。

也许最吸引用户的是 Web 的**按需**特性：用户想要什么就能得到什么，想什么时候要就什么时候要。这与传统的广播电视不同——后者强迫用户在内容提供者播出时去收听收看。除了按需可得，Web 还有许多人们喜爱和珍视的迷人特性：任何人都极易通过 Web 发布信息——人人都能以极低成本成为出版者；超链接和搜索引擎帮助我们在信息的海洋中航行；照片和视频刺激我们的感官；表单、JavaScript、视频以及许多其他手段让我们能与页面和站点交互；而 Web 及其协议还成为生成式 AI、YouTube、基于 Web 的电子邮件（如 Gmail）以及大多数移动因特网应用（包括 Instagram 和 Google 地图）的平台。

## 2.2.1　HTTP 概述

超文本传输协议（HTTP）定义于 [RFC 1945]、[RFC 7230]、[RFC 7540] 和 [RFC 9114]。今天绝大多数应用都运行在 HTTP 之上，包括网页浏览、视频流、社交媒体，以及客户端与邮件服务器之间的电子邮件；智能手机应用通常也通过 HTTP 与服务器通信。

HTTP 由两个程序实现：一个客户程序和一个服务器程序。它们运行在不同的端系统上，通过交换 HTTP 报文彼此"交谈"。HTTP 定义了这些报文的结构，以及客户与服务器如何交换报文。在详细解释 HTTP 之前，先复习一些 Web 术语。

一个 **Web 页面**（也叫文档）由若干**对象**（object）组成。对象就是一个文件——例如 HTML 文件、JPEG 图像、JavaScript 文件、CSS 样式表文件或视频片段——它可由单个 URL 寻址。多数 Web 页面由一个**基础 HTML 文件**和若干被引用的对象组成。例如，若一个 Web 页面包含 HTML 文本和五幅 JPEG 图像，则该页面共有六个对象：基础 HTML 文件加五幅图像。基础 HTML 文件通过各对象的 URL 引用页面中的其他对象。每个 URL 有两个组成部分：存放该对象的服务器主机名，以及该对象的路径名。例如 URL

http://www.someSchool.edu/someDepartment/picture.gif

中，`www.someSchool.edu` 是主机名，`/someDepartment/picture.gif` 是路径名。由于 Web 浏览器（如 Chrome、Edge）实现 HTTP 的客户端，在 Web 语境中我们把"浏览器"与"客户"两个词交替使用。Web 服务器实现 HTTP 的服务器端，存放 Web 对象，每个对象可由一个 URL 寻址。流行的 Web 服务器包括 Apache、Nginx 和微软的 Internet Information Server。

HTTP 定义了 Web 客户如何向 Web 服务器请求网页、服务器如何把网页传送给客户。客户与服务器之间的交互细节稍后讨论，其总体思想如图 2.6 所示：当用户请求一个 Web 页面（例如点击一个超链接）时，浏览器向服务器发送对该页面中各对象的 HTTP 请求报文；服务器收到请求后，用包含这些对象的 HTTP 响应报文来响应。

<Figure src="ch02/fig2-06.webp" caption="图 2.6　HTTP 的请求-响应行为" />

视 HTTP 版本不同，它可以使用 TCP 或 UDP 作为底层运输协议，使用 UDP 是相对较新的发展。我们先假定 TCP 是底层运输协议来讨论 HTTP，2.2.7 节再讨论运行在 UDP 之上的 HTTP。

HTTP 客户首先与服务器发起一条 TCP 连接。连接建立后，浏览器与服务器进程通过各自的套接字接口访问 TCP。如 2.1 节所述，在客户端，套接字接口是客户进程与 TCP 连接之间的"门"；在服务器端，它是服务器进程与 TCP 连接之间的"门"。客户向其套接字接口发送 HTTP 请求报文、从其套接字接口接收 HTTP 响应报文；类似地，HTTP 服务器从其套接字接口接收请求报文、向其套接字接口发送响应报文。客户一旦把报文送入其套接字接口，该报文就不再由客户掌控，而是"交到了"TCP 手中。回忆 2.1 节：TCP 向 HTTP 提供可靠数据传输服务。这意味着客户进程发出的每个 HTTP 请求报文最终都会完好地到达服务器；类似地，服务器进程发出的每个 HTTP 响应报文最终都会完好地到达客户。这里可以看到分层体系结构的一大优点——HTTP 无需操心数据丢失，也无需操心 TCP 如何从网络中的数据丢失或乱序中恢复；那是 TCP 及协议栈低层协议的职责。

需要强调的是：服务器向客户发送所请求的文件时，并不保存关于客户的任何状态信息。如果某个客户在几秒钟内两次请求同一个对象，服务器不会回答"我刚才已经把它发给你了"，而是重新发送该对象——因为它早已把先前做过的事忘得一干二净。由于 HTTP 服务器不维护关于客户的任何信息，HTTP 被称为**无状态协议**（stateless protocol）。还要指出，Web 采用 2.1 节所述的客户-服务器应用体系结构：Web 服务器始终在线、具有固定 IP 地址，为可能数以百万计的不同浏览器提供服务。

HTTP 已经历多个版本。最初的 HTTP/1.0 可追溯到 90 年代初 [RFC 1945]；此后 HTTP/1.1 [RFC 7320] 与 HTTP/2 [RFC 7540] 得到广泛部署。HTTP/1.0、HTTP/1.1 和 HTTP/2 都运行在 TCP 之上；较近的 HTTP/3 已标准化 [RFC 9114] 并正在获得越来越多的采用，它运行在 UDP 之上，将在 2.2.7 节讨论。

## 2.2.2　非持续连接与持续连接

在许多因特网应用中，客户与服务器在较长时期内通信，客户发出一系列请求，服务器对每个请求作出响应。视应用及其使用方式而定，这一系列请求可以是背靠背的、按固定间隔周期性的，或间歇性的。当这种客户-服务器交互在 TCP 上进行时，应用开发者必须做一个重要决定：每个请求/响应对是否应通过一条单独的 TCP 连接发送，还是所有请求及其响应都通过同一条 TCP 连接发送？前一种做法称为使用**非持续连接**（non-persistent connection），后一种称为**持续连接**（persistent connection）。为深入理解这一设计问题，我们在一个具体应用——HTTP——的语境中考察持续连接的优缺点，HTTP 两种连接都可以使用。

### 使用非持续连接的 HTTP

以非持续连接为例，走一遍从服务器向客户传送一个 Web 页面的步骤。假设该页面由一个基础 HTML 文件和 10 幅 JPEG 图像组成，这 11 个对象都存放在同一台服务器上；并假设基础 HTML 文件的 URL 为 `http://www.someSchool.edu/someDepartment/home.index`。过程如下：

1. HTTP 客户进程向服务器 `www.someSchool.edu` 的 80 端口（HTTP 的默认端口号）发起一条 TCP 连接。与该 TCP 连接相关联，客户端会有一个套接字，服务器端也会有一个套接字。
1. HTTP 客户通过其套接字向服务器发送一个 HTTP 请求报文，其中包含路径名 `/someDepartment/home.index`。
1. HTTP 服务器进程通过其套接字收到请求报文，从存储器（RAM 或磁盘）中取出对象 `/someDepartment/home.index`，把它封装进一个 HTTP 响应报文，再通过其套接字把响应报文发给客户。
1. HTTP 服务器进程告诉 TCP 关闭该 TCP 连接。（但 TCP 要等到确知客户已完好收到响应报文之后才真正终止连接。）
1. HTTP 客户收到响应报文，TCP 连接终止。该报文表明所封装的对象是一个 HTML 文件；客户从响应报文中提取该文件，检查 HTML 文件，找到对 10 幅 JPEG 对象的引用。
1. 对每个被引用的 JPEG 对象，重复上述前四步。

浏览器收到 Web 页面后，就把它显示给用户。不同浏览器对同一网页的**解释**（即向用户显示的方式）可能有所不同；HTTP 与"客户如何解释网页"无关，HTTP 规范（[RFC 1945]、[RFC 7540]）只定义客户 HTTP 程序与服务器 HTTP 程序之间的通信协议。

上述步骤说明了**非持续连接**的使用：服务器发出对象后就关闭 TCP 连接，该连接不为其他对象继续保留。注意，每条非持续 TCP 连接恰好传送一个请求报文和一个响应报文。因此在本例中，用户请求该网页时会生成 11 条 TCP 连接。

在继续之前，做一个粗略估算：从客户请求基础 HTML 文件到客户收到整个文件，经过多少时间？为此定义**往返时间**（RTT），即一个小分组从客户传到服务器再返回客户所需的时间。RTT 包括分组传播时延、中间路由器与交换机中的排队时延以及分组处理时延（这些时延见 1.4 节）。

现在考虑用户点击一个超链接时会发生什么。如图 2.7 所示，浏览器要在自己与 Web 服务器之间发起一条 TCP 连接，这涉及一次"三次握手"：客户向服务器发送一个小 TCP 报文段，服务器确认并回送一个小 TCP 报文段，最后客户再向服务器确认。三次握手的前两部分占用一个 RTT。完成握手的前两部分后，客户把 HTTP 请求报文与三次握手的第三部分（确认）一起送入 TCP 连接；请求报文到达服务器后，服务器把 HTML 文件送入 TCP 连接。这个 HTTP 请求/响应又占用一个 RTT。因此，粗略地说，总响应时间是**两个 RTT 加上服务器传输 HTML 文件的时间**。

### 使用持续连接的 HTTP

非持续连接有一些缺点。第一，必须为每个请求的对象建立并维护一条全新的连接；对每条这样的连接，客户端和服务器都要分配 TCP 缓冲区、保存 TCP 变量。这会给 Web 服务器带来沉重负担——它可能同时为数百个不同客户提供服务。第二，如刚才所述，每个对象都要承受两个 RTT 的交付时延：一个 RTT 用于建立 TCP 连接，一个 RTT 用于请求并接收对象。

在使用**持续连接**时（HTTP/1.1 与 HTTP/2 即如此），服务器在发出响应后让 TCP 连接保持打开，同一客户与服务器之间后续的请求和响应可以通过同一条连接发送。特别地，整个 Web 页面（上例中的基础 HTML 文件加 10 幅图像）可以通过一条持续 TCP 连接发送；而且，存放在同一服务器上的多个 Web 页面也可以通过一条持续 TCP 连接从服务器发给同一客户。这些对象请求可以用"流水线"方式发出，即背靠背地发出而不必等待未决请求的应答。通常，HTTP 服务器在一段时间（可配置的超时间隔）未使用某条连接时就关闭它。当服务器收到这些背靠背的请求时，就把对象背靠背地发回。

## 2.2.3　HTTP 报文格式

HTTP 规范 [RFC 1945; RFC 7230; RFC 7540; RFC 9114] 包含 HTTP 报文格式的定义。HTTP 报文有两类：请求报文与响应报文。

### HTTP 请求报文

下面是一个典型的 HTTP 请求报文：

```text
GET /somedir/page.html HTTP/1.1
Host: www.someschool.edu
Connection: close
User-agent: Mozilla/5.0
Accept-language: fr
```

仔细看看这个简单的请求报文，可以得到很多信息。首先，报文是用普通 ASCII 文本写的，所以一个识字的人就能读懂。其次，报文由五行组成，每行后面跟一个回车换行；最后一行之后还有一个额外的回车换行。虽然这个请求报文只有五行，但请求报文可以有很多行，也可以只有一行。HTTP 请求报文的第一行称为**请求行**（request line），其后的各行称为**首部行**（header line）。请求行有三个字段：**方法**字段、**URL** 字段和 **HTTP 版本**字段。方法字段可以取若干不同的值，包括 GET、POST、HEAD、PUT 和 DELETE；绝大多数 HTTP 请求报文使用 GET 方法。当浏览器请求一个对象时使用 GET 方法，所请求的对象由 URL 字段标识；本例中浏览器请求的对象是 `/somedir/page.html`。版本字段不言自明：本例中浏览器实现的是 HTTP/1.1。

再看例子中的首部行。`Host: www.someschool.edu` 指明对象所在的主机。你也许认为这个首部行是多余的，因为已经有一条指向该主机的 TCP 连接了；但正如 2.2.5 节将会看到的，**Web 代理缓存**需要 host 首部行提供的信息。通过包含 `Connection: close` 首部行，浏览器告诉服务器它不想使用持续连接，希望服务器在发出所请求的对象后关闭连接。`User-agent:` 首部行指明用户代理，即向服务器发出请求的浏览器类型；本例中用户代理是 Mozilla/5.0，即 Firefox 浏览器。这个首部行很有用，因为服务器实际上可以针对不同类型的用户代理发送同一对象的不同版本（各版本由同一个 URL 寻址）。最后，`Accept-language:` 首部表示：如果服务器上有该对象的法语版本，用户希望收到法语版；否则服务器应发送其默认版本。`Accept-language:` 只是 HTTP 提供的众多**内容协商**首部之一。

看过例子之后，再看请求报文的通用格式，如图 2.8 所示。通用格式与我们刚才的例子非常接近。不过你也许注意到，在首部行（以及额外的回车换行）之后还有一个"实体主体"（entity body）。使用 GET 方法时实体主体为空，而使用 POST 方法时会用到它。当用户填写表单时（例如向搜索引擎提交搜索词），HTTP 客户常用 POST 方法：使用 POST 报文时，用户仍在向服务器请求一个 Web 页面，但该页面的具体内容取决于用户在表单字段中输入的内容。若方法字段的值为 POST，则实体主体中包含用户输入到表单字段中的内容。

必须指出，由表单生成的请求并不一定非要用 POST 方法；相反，HTML 表单常常使用 GET 方法，并把输入数据（表单字段内容）包含在所请求的 URL 中。例如，若一个表单使用 GET 方法、有两个字段，两个字段的输入分别是 monkeys 和 bananas，则 URL 将具有 `www.somesite.com/animalsearch?monkeys&bananas` 这样的结构。日常上网时，你大概见过这类带参数的 URL。

HEAD 方法与 GET 方法类似：服务器收到 HEAD 请求时，回送一个 HTTP 报文，但**不**返回所请求的对象。应用开发者常用 HEAD 方法进行调试。PUT 方法常与 Web 发布工具配合使用，允许用户把对象上传到某个 Web 服务器上的指定路径（目录）；需要向 Web 服务器上传对象的应用也会使用 PUT。DELETE 方法允许用户或应用删除 Web 服务器上的某个对象。

### HTTP 响应报文

下面是一个典型的 HTTP 响应报文，它可以是对刚才讨论的那个请求报文的响应：

```text
HTTP/1.1 200 OK
Connection: close
Date: Mon, 21 Oct 2024 18:58:21 GMT
Server: Apache/2.2.3 (CentOS)
Last-Modified: Sun, 20 Oct 2024 13:20:46 GMT
Content-Length: 6821
Content-Type: text/html

(data data data data data ...)
```

仔细看看这个响应报文。它有三个部分：一个初始的**状态行**、六个**首部行**，然后是**实体主体**。实体主体是报文的"肉"——它包含所请求的对象本身（用 `data data data ...` 表示）。状态行有三个字段：协议版本字段、**状态码**，以及相应的**状态短语**。本例中状态行表明服务器使用的是 HTTP/1.1，且一切正常（即服务器已找到并正在发送所请求的对象）。

## 2.2.3（续）　状态码与真实报文

再看响应报文的首部行。服务器用 `Connection: close` 首部行告诉客户：发出报文后它将关闭 TCP 连接。`Date:` 首部行指明 HTTP 响应由服务器创建并发送的时间与日期——注意这不是对象被创建或最后修改的时间，而是服务器从其文件系统中取出对象、插入响应报文并发送的时刻。`Server:` 首部行表明该报文由 Apache Web 服务器生成，它类似于请求报文中的 `User-agent:` 首部。`Last-Modified:` 首部行指明对象被创建或最后修改的时间与日期；这个首部对本地客户与网络缓存服务器（也称代理服务器）中的对象缓存都至关重要，稍后将详述。`Content-Length:` 首部行指明所发送对象的字节数。`Content-Type:` 首部行指明实体主体中的对象是 HTML 文本。（对象类型的正式标识由 `Content-Type:` 首部给出，而不是由文件扩展名给出。）

响应报文的通用格式如图 2.9 所示，与我们刚才的例子吻合。关于状态码及其短语再说几句：状态码与相应短语指示请求的结果。一些常见状态码及短语包括：

- **200 OK**：请求成功，信息在响应中返回。
- **301 Moved Permanently**：所请求的对象已被永久移动，新 URL 在响应报文的 `Location:` 首部中给出，客户软件会自动去取新 URL。
- **400 Bad Request**：这是一个通用错误码，表示服务器无法理解该请求。
- **404 Not Found**：所请求的文档在本服务器上不存在。
- **505 HTTP Version Not Supported**：服务器不支持所请求的 HTTP 协议版本。

想看看自己计算机发出的真实 HTTP 请求报文以及 Web 服务器返回的响应吗？这很容易，建议你试一试！在计算机的命令行提示符下输入：

```text
curl -v http://gaia.cs.umass.edu/kurose_ross/index.php
```

上面的 `curl` 命令会向 gaia.cs.umass.edu 的 Web 服务器发送一个 HTTP GET 请求，以获取 HTML 内容 `/kurose_ross/index.php`，即本书作者的主页。详细模式（`-v`）会把 HTTP GET 请求报文与所收到响应的文本内容显示出来。当然，若想看格式化显示后的响应是什么样子，只需把上面的 URL 输入你喜欢的浏览器。

本节讨论了 HTTP 请求与响应报文中可以使用的若干首部行。HTTP 规范定义的首部行还有很多很多，浏览器、Web 服务器和网络缓存服务器都可以插入。我们只覆盖了全部首部行中的一小部分；下面还会再讲几个，2.2.5 节讨论网络 Web 缓存时再讲一小部分。

浏览器如何决定在请求报文中包含哪些首部行？Web 服务器又如何决定在响应报文中包含哪些首部行？浏览器会根据自身类型与版本、用户配置，以及当前是否已缓存了该对象（可能是过时的版本）来生成首部行。Web 服务器的行为类似：不同的产品、版本和配置都会影响响应报文中包含哪些首部行。

## 2.2.4　用户与服务器的交互：Cookie

前面提到 HTTP 服务器是无状态的。这简化了服务器设计，使工程师能够开发出可处理数千条并发 TCP 连接的高性能 Web 服务器。然而，网站往往需要识别用户——或者因为服务器想限制用户访问，或者因为它想根据用户身份提供内容。为此，HTTP 使用了 **Cookie**。Cookie 定义于 [RFC 6265]，允许站点跟踪用户。今天大多数大型商业网站都使用 Cookie。

如图 2.10 所示，Cookie 技术有四个组成部分：(1) HTTP 响应报文中的一行 `Set-cookie:` 首部；(2) HTTP 请求报文中的一行 `Cookie:` 首部；(3) 保存在用户端系统上、由用户浏览器管理的 Cookie 文件；(4) 网站的后端数据库。

结合图 2.10 走一个例子。假设 Susan 一直在家用 PC 上用 Chrome 上网，她第一次访问 Amazon.com（假定她过去访问过 eBay）。当请求到达 Amazon 的 Web 服务器时，服务器生成一个唯一识别号，并在其后端数据库中创建一条以该识别号为索引的记录。随后，Amazon 的 Web 服务器向 Susan 的浏览器回送响应，其中包含一行 `Set-cookie:` 首部，带有该识别号，例如：

```text
Set-cookie: 1678
```

Susan 的浏览器收到该 HTTP 响应报文后，看到 `Set-cookie:` 首部，就在它管理的专用 Cookie 文件中追加一行，其中包括服务器的主机名和 `Set-cookie:` 首部中的识别号。注意，由于 Susan 过去访问过 eBay，Cookie 文件中已经有 eBay 的记录。随着 Susan 继续浏览 Amazon 站点，她每次请求一个网页，浏览器都会查阅 Cookie 文件，取出她在这个站点上的识别号，并在 HTTP 请求中放入包含该识别号的 `Cookie:` 首部行：

```text
Cookie: 1678
```

这样，Amazon 服务器就能跟踪 Susan 在 Amazon 站点上的活动。虽然 Amazon 网站未必知道 Susan 的姓名，但它确切知道用户 1678 访问了哪些页面、以什么顺序、在什么时间！Amazon 用 Cookie 提供购物车服务——它可以维护 Susan 打算购买的所有商品的清单，以便她在会话结束时一次性付款。

如果 Susan 一周后再次访问 Amazon，她的浏览器会继续在请求报文中放入 `Cookie: 1678`。Amazon 还会根据她过去访问过的页面向她推荐商品。如果 Susan 在 Amazon 注册，提供了全名、电子邮件地址、邮寄地址和信用卡信息，Amazon 就可以把这些信息加入其数据库，从而把 Susan 的姓名与她的识别号（以及她过去在该站点访问过的所有页面！）关联起来。Amazon 等电子商务网站就是这样提供"一键购物"的——Susan 在后续访问中选购商品时，无需重新输入姓名、卡号或地址。

由此可见，Cookie 可以用来识别用户。用户第一次访问某个站点时，可以提供用户标识（可能是姓名）；在随后的会话中，浏览器把 Cookie 首部传给服务器，从而向服务器表明用户身份。因此，Cookie 可以在无状态的 HTTP 之上构建一个**用户会话层**。例如，当用户登录基于 Web 的电子邮件应用时，浏览器把 Cookie 信息发送给服务器，使服务器能在该用户与应用的整个会话期间识别他。

虽然 Cookie 常常简化用户的网上购物体验，但它们也有争议，因为可以视为对隐私的侵犯。如我们刚才所见，结合 Cookie 与用户提供的账户信息，网站可以了解用户的许多情况，并可能把这些信息卖给第三方。

## 2.2.5　浏览器缓存

图 2.7 已经表明：从浏览器首次向 Web 服务器请求一个对象，到浏览器收到该对象，最小时延是 2 个 RTT——一个 RTT 用于在浏览器与服务器之间建立 TCP 连接，另一个 RTT 用于发送 HTTP 请求并接收 HTTP 响应。稍后会看到，最新版本的 HTTP（HTTP/3）经过优化，在许多情况下只需一个 RTT 就能请求一个网页。但我们能不能把这一时延降到比一个 RTT 还小？零时延岂不是很妙？这听起来似乎违背物理定律，但借助**浏览器缓存**确实可以做到——这是所有现代浏览器都实现、并在 Web 中广泛使用的技术。据一项估计，75% 的 Web 请求收到的 HTTP 响应带有我们下面要研究的那类显式浏览器缓存指令 [Web almanac 2021]。

借助浏览器缓存，Web 浏览器把最近收到的 Web 对象内容保存在本地**浏览器缓存**中。当用户请求某个 Web 对象时，浏览器先检查该对象是否已存于本地浏览器缓存；若是，就可以立即显示该对象，而无需向 Web 服务器发出新请求（从而避免随后的请求/响应时延）——因为浏览器此前已从该服务器请求并收到过该对象。

虽然浏览器缓存可以缩短用户感知的响应时间、减少因特网上承载的 HTTP 流量（这些优点将在章末习题中探讨），但它也带来一个新的重要挑战：浏览器如何知道 Web 服务器中当前存放的对象，是否在客户端缓存之后被修改过？某些类型的 Web 对象（如图像、JavaScript 文件和 CSS 文件）很少变化，另一些对象（如文本）则可能频繁变化。浏览器如何知道自己缓存的内容是最新的还是过时的？所幸 HTTP 协议在 GET 报文和响应报文中都提供了字段，帮助服务器与浏览器管理浏览器缓存 [RFC 7232]：

- **Cache-Control。** HTTP 响应报文中的 `Cache-Control` 字段让服务器规定 HTTP 响应中的内容应如何缓存。`Cache-Control: no-store` 指令告诉浏览器不要在本地缓存/存储该内容，此时浏览器必须总是重新向服务器请求内容。另一种做法是，服务器可以明确告知浏览器某对象可在缓存中保留多长时间：例如 `Cache-Control: max-age=3600` 指令告诉浏览器该内容可缓存 3600 秒，之后必须重新向服务器请求。[RFC 7232] 还定义了许多其他 `Cache-Control` 指令。
- **If-Modified-Since。** HTTP 还在客户端到服务器的报文中提供一种机制，即所谓的**条件 GET**（conditional GET），以方便缓存。条件 GET 就是普通的 HTTP GET 报文，只是额外包含一行 `If-Modified-Since:` 首部。使用条件 GET 时，客户显式请求一个对象，但同时告知服务器：它的浏览器缓存中已有该对象，以及该对象是何时被加入缓存的。HTTP 服务器若发现该对象在这段时间内已改变，就回送完整对象；否则只告诉浏览器其（浏览器缓存中的）副本仍是最新的，而不再重发该对象。

为说明条件 GET 如何运作，走一个例子。假设浏览器此前请求过某个对象，比如 `kiwi.jpg`，把它存入了缓存，并记录了它被加入缓存的时间。当用户后来再次请求该对象时，浏览器无法确定这份缓存副本是否仍然有效——原因可能是服务器从未提供缓存控制信息，或服务器先前给出的 `max-age` 已过期，或服务器指示浏览器缓存该对象但同时要求每次都与服务器核对新鲜度。此时，浏览器向服务器发送一个条件 GET：

```text
GET /fruit/kiwi.jpg HTTP/1.1
Host: www.exotiquecuisine.com
If-modified-since: Fri, 13 Sep 2024 09:23:24
```

`If-modified-since:` 首部行的值表明，浏览器缓存中的该对象是 2024 年 9 月 13 日 9:23:24 收到的。这个条件 GET 是在告诉服务器：只有当该对象在指定日期之后被修改过时，才发送它。假设该对象自 2024 年 9 月 13 日 09:23:24 以来未被修改，则 Web 服务器回送：

```text
HTTP/1.1 304 Not Modified
Date: Fri, 8 Nov 2024 12:07:29
Server: Apache/2.4.62 (Unix)
(empty entity body)
```

我们看到，此时 Web 服务器仍然发送一个响应报文，但报文中不包含所请求的对象。状态行中的 `304 Not Modified` 告诉浏览器：其缓存中的该对象副本仍是最新的，因此可以使用缓存副本。若把所请求的对象也包含进来，只会浪费带宽、增加用户感知的响应时间，尤其当对象很大时。

## 2.2.6　HTTP/2

HTTP/2 [RFC 7540] 于 2015 年标准化，是自 1997 年标准化的 HTTP/1.1 以来 HTTP 的第一个新版本。标准化之后，HTTP/2 迅速普及：2024 年，排名前 1000 万的网站中约 35% 支持 HTTP/2 [W3Techs]。多数浏览器——包括 Chrome、Edge、Safari、Opera 和 Firefox——也支持 HTTP/2。近年来由于 2.2.7 节将讨论的 HTTP/3 的出现，其使用率有所下降。

HTTP/2 的主要目标是：通过在单条 TCP 连接上实现请求与响应的**多路复用**来降低感知时延，提供请求优先级与服务器推送，并对 HTTP 首部字段进行高效压缩。HTTP/2 **不**改变 HTTP 的方法、状态码、URL 或首部字段，它改变的是数据在客户与服务器之间格式化与传输的方式。

为理解 HTTP/2 的必要性，回忆 HTTP/1.1 使用持续 TCP 连接，使一个网页可以通过单条 TCP 连接从服务器发往客户。每个网页只用一条 TCP 连接，可以减少服务器端的套接字数量，并使每个传输的网页获得公平的网络带宽份额（见下文）。但浏览器开发者很快发现，在单条 TCP 连接上发送网页中的所有对象存在**队头阻塞**（Head of Line, HOL blocking）问题。

为理解 HOL 阻塞，考虑一个网页：顶部是一个大视频片段，下面有许多小对象；再假设服务器与客户之间的路径上有一条中低速瓶颈链路（例如低速无线链路）。使用单条 TCP 连接时，视频片段要花很长时间才能通过瓶颈链路，而小对象则在它后面排队等待——也就是说，队首的视频片段阻塞了后面的小对象。HTTP/1.1 浏览器通常通过打开多条并行 TCP 连接来绕过这个问题，使同一网页中的对象并行发往浏览器；这样小对象可以更快到达并在浏览器中呈现，从而降低用户感知的时延。

第 3 章将详细讨论的 TCP 拥塞控制，也为浏览器使用多条并行 TCP 连接而非单条持续连接提供了意外的激励。粗略地说，TCP 拥塞控制力求让共享某条瓶颈链路的每条 TCP 连接获得该链路可用带宽的均等份额；因此若有 $n$ 条 TCP 连接经过某瓶颈链路，每条连接大致获得 $\frac{1}{n}$ 的带宽。通过打开多条并行 TCP 连接来传送单个网页，浏览器就能"作弊"抢占更大份额的链路带宽。许多 HTTP/1.1 浏览器最多打开六条并行 TCP 连接，既是为了绕开 HOL 阻塞，也是为了获得更多带宽。

HTTP/2 的主要目标之一，就是消除（至少减少）为传送单个网页而使用的并行 TCP 连接。这不仅减少了服务器上需要打开和维护的套接字数量，还让 TCP 拥塞控制得以按设计意图运作。但只用一条 TCP 连接传送网页，HTTP/2 就需要精心设计的机制来避免 HOL 阻塞。

### HTTP/2 的成帧

HTTP/2 解决 HOL 阻塞的办法，是把每条报文拆成小的**帧**（frame），并在同一条 TCP 连接上交错发送请求与响应报文。为理解这一点，再仔细考虑前面那个例子：网页由一个视频片段和 8 个较小对象组成，于是任何想看到该网页的浏览器都会向服务器发出 9 个并发请求；对这 9 个请求，服务器需要在同一条 TCP 连接上向浏览器发送 9 个相互竞争的 HTTP 响应报文。为简单起见，假设所有帧长度固定，视频片段由 1000 帧组成，每个较小对象由 2 帧组成。采用帧交错后，发送完视频片段的第 1 帧，就发送每个小对象的第 1 帧；再发送视频片段的第 2 帧，然后发送每个小对象的第 2 帧。这样，总共发送 18 帧之后，所有较小对象就都发完了。若不使用交错，则要等发送 1016 帧之后才会发送这些小对象。可见 HTTP/2 的成帧机制能显著降低用户感知的时延。

把一条 HTTP 报文拆成独立的帧、交错发送、再在对端重新组装——这是 HTTP/2 **最重要的单项增强**。成帧由 HTTP/2 协议的**成帧子层**（framing sub-layer）完成。当服务器要发送一个 HTTP 响应时，该响应由成帧子层处理，被拆分成帧：响应的首部字段成为一帧，报文主体被拆成一帧或多帧。随后，成帧子层把该响应的帧与其他响应的帧交错，通过这条单一的持续 TCP 连接发送。帧到达客户后，先在成帧子层重新组装成原来的响应报文，再由浏览器照常处理。类似地，客户的 HTTP 请求也被拆成帧并交错发送。

除了把每条 HTTP 报文拆成独立的帧，成帧子层还对帧进行**二进制编码**。二进制协议解析效率更高，帧略小，且更不易出错。

### 响应优先级与服务器推送

**报文优先级**（message prioritization）让开发者定制请求的相对优先级，以更好地优化应用性能。如前所述，成帧子层把报文组织成发往同一请求方的并行数据流。当客户向服务器发送并发请求时，可以给每条报文赋予 1 到 256 之间的权重来为所请求的响应排定优先级，数值越大优先级越高。服务器据此可以优先发送优先级最高的响应的帧。此外，客户还可以通过指定某条报文所依赖的另一条报文的 ID，说明报文之间的依赖关系。

HTTP/2 的另一个特性是服务器可以针对单个客户请求发送多个响应。也就是说，除了对原始请求的响应之外，服务器还可以向客户**推送**额外对象，而客户无需逐个请求。这是可行的，因为 HTML 基础页面已经指明了完整渲染该网页所需的对象。因此，服务器不必等待客户对这些对象的 HTTP 请求，而可以分析 HTML 页面、识别所需对象，并在收到显式请求之前就把它们发给客户。**服务器推送**（server push）消除了等待请求所带来的额外时延。

## 2.2.7　HTTP/3 与 QUIC

我们刚刚了解了 HTTP 协议的演进：从 HTTP/1.0 到 HTTP/1.1，再到 HTTP/2。这三个协议虽有显著差异，却有一个重要的共同特征——它们都运行在 TCP 之上。但这并不意味着 HTTP 将永远运行在 TCP 上！2022 年在 RFC 9114 中标准化的 HTTP/3 已席卷因特网界：它在 Web（包括电子邮件、音视频流和社交媒体）中正迅速获得市场份额，并已成为许多流行浏览器与智能手机应用的默认 HTTP 版本。引人注目的是，HTTP/3 **不**运行在 TCP 上，而是运行在 UDP 上！你也许会问：UDP 是一种没有可靠数据传输、因而无法保证 HTTP 报文交付的"光板"运输协议，这怎么可能？下面就来揭开这个颇为迷人的谜底。

### QUIC 运输协议

HTTP/3 运行在 **QUIC**（Quick UDP Internet Connections）运输协议之上。因此在描述 HTTP/3 之前，需要先讨论 2021 年在 RFC 9000 中标准化的 QUIC。

你现在也许在想："等等！作者不是一再告诉我们因特网恰好有两个运输协议——UDP 和 TCP 吗？现在又说还有第三个叫 QUIC 的运输协议？那因特网到底有两个还是三个运输协议？"

让我们澄清一下。严格说来，因特网仍然只有两个运输协议：TCP 和 UDP。事实上，QUIC 并不是运输层协议，而是**应用层中的一个子层**，它使用 UDP 在因特网上收发分组，如图 2.11 所示——这正是其名字中"UDP"的由来（Quick UDP Internet Connections）。

然而，尽管严格说来 QUIC 不是运输层协议，从应用开发者的角度看它却是。事实上，网络应用开发者可以像创建 TCP、UDP 套接字那样创建 **QUIC 套接字**来编写应用（见 2.6 节）。当应用建立一个 QUIC 套接字时，QUIC 子层会创建一个 UDP 套接字；随后应用就可以向 QUIC 套接字发送报文、从中接收报文，而无需关心 QUIC 的内部机制。总之，虽然实际上 QUIC 是应用层的一个子层，但从应用开发者的角度看，它是一个新的运输层协议。

### 为什么需要一个"新的运输协议"

QUIC 是一个可供许多应用使用的通用协议，但它主要的设计目标是提升 Web 的性能。来看看性能提升的空间在哪里。

在很久以前（大约到 2005 年为止），多数 Web 事务直接运行在未加密的 TCP 之上。但多年来，加密与鉴别已成为多数 Web 事务（包括网页浏览、Web 搜索和基于 Web 的电子邮件）的默认要求。这类安全服务通常通过 TLS 提供给 Web 应用（见 2.3 节的"安全聚焦"专栏，以及第 8 章的详述）。因此，多数现代 Web 事务实际使用的是"TCP + TLS"的组合：先用三次握手建立 TCP 连接，再用 TLS 握手协商密钥——这至少要花两个 RTT 才能发出第一个 HTTP 请求。

QUIC 的第一个改进是把传输握手与加密握手合并：QUIC 在建立连接的同时完成 TLS 1.3 的密钥协商，因此通常只需**一个 RTT** 就能开始发送应用数据；若客户此前与该服务器通信过并保存了会话凭证，还可以实现 **0-RTT**——在第一个报文中就携带应用数据。

第二个、也是更根本的改进，是消除 TCP 层面的队头阻塞。在 TCP 上，所有 HTTP 请求共享同一个字节流：只要有一个 TCP 报文段丢失，后续所有数据（哪怕属于完全无关的请求）都必须等待重传，这就是 2.2.6 节所说 HOL 阻塞的根源，而 HTTP/2 的成帧只能缓解、无法根治（因为帧仍在同一条 TCP 字节流里）。QUIC 则在同一连接内提供多条独立的**流**（stream）：每条流有自己的可靠、按序交付语义，某条流上的丢包只阻塞该流，其他流照常交付。

此外，QUIC 还提供：

- **面向连接且安全**：连接由连接 ID 标识，所有 QUIC 分组都加密；
- **每流可靠传输**：确认与重传机制与 TCP 类似；
- **拥塞控制**：基于 TCP NewReno 的拥塞控制，对应用透明；
- **连接迁移**：由于连接由连接 ID 而非 IP 地址与端口标识，当用户从 WiFi 切换到蜂窝网、IP 地址改变时，连接仍然保持——这对移动用户尤为重要。

最后，QUIC 在用户空间实现，可以随应用一起更新，而不必等待操作系统内核升级——这正是它能在短短几年内被广泛部署的重要原因。第 3 章的 3.8 节还将从运输层的角度再次讨论 QUIC。
