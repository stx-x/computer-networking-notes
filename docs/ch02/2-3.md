# 2.3　因特网中的电子邮件

电子邮件自因特网诞生之初就存在。在因特网尚在襁褓之时，它是最流行的应用 [Segaller 1998]；多年来它变得更加精巧、强大，至今仍是因特网最重要、使用最广泛的应用之一。

本节考察因特网电子邮件核心的应用层协议。不过在深入讨论这些协议之前，先从高层看一看因特网邮件系统及其关键组件。

图 2.12 给出因特网邮件系统的高层视图，它有三个主要组件：**用户代理**（user agent）、**邮件服务器**（mail server）和**简单邮件传输协议**（SMTP）。下面以发送方 Alice 给接收方 Bob 发一封邮件为例，逐一说明。

**用户代理**让用户阅读、回复、转发、保存和撰写邮件。电子邮件用户代理的例子包括 Microsoft Outlook、Apple Mail、基于 Web 的 Gmail、智能手机上的 Gmail 应用等。如今许多用户通过 Gmail、Yahoo! Mail 这类基于 HTTP 的用户代理，向自己的邮件服务器发信、从邮件服务器收信。当 Alice 写完邮件后，她的用户代理把邮件发送到她的邮件服务器，邮件被放入该服务器的**发送队列**。当 Bob 想读邮件时，他的用户代理从自己邮件服务器中的邮箱里取出邮件。

**邮件服务器**构成电子邮件基础设施的核心。每个接收者（如 Bob）都在某台邮件服务器上有一个**邮箱**（mailbox），该邮箱管理和保存发来的邮件。一封典型邮件从发送方的用户代理出发，先到发送方的邮件服务器，再到接收方的邮件服务器，最后投递进接收方的邮箱。当 Bob 想访问自己邮箱中的邮件时，存放其邮箱的邮件服务器先对 Bob 进行鉴别（用用户名和口令）。Alice 的邮件服务器还必须处理 Bob 的邮件服务器发生故障的情形：如果 Alice 的服务器无法把邮件投递到 Bob 的服务器，它就把邮件保存在消息队列中，稍后再尝试传送；重试通常每 30 分钟左右一次，若数天后仍不成功，服务器就删除该邮件，并向发送方（Alice）回一封电子邮件告知。

**SMTP** 是因特网电子邮件的主要应用层协议。它使用 TCP 的可靠数据传输服务，把邮件从发送方的邮件服务器传送到接收方的邮件服务器。与多数应用层协议一样，SMTP 有客户端与服务器端：客户端运行在发送方的邮件服务器上，服务器端运行在接收方的邮件服务器上；每台邮件服务器上都同时运行 SMTP 的客户端与服务器端。当一台邮件服务器向其他邮件服务器发信时，它充当 SMTP 客户；当它从其他邮件服务器收信时，它充当 SMTP 服务器。

## 2.3.1　SMTP

SMTP 定义于 RFC 5321，是因特网电子邮件的核心。如上所述，SMTP 把邮件从发送方的邮件服务器传送到接收方的邮件服务器。SMTP 比 HTTP 古老得多（最初的 SMTP RFC 可追溯到 1982 年，而 SMTP 的存在还更早）。尽管 SMTP 有许多优良品质——它在因特网中的普遍使用就是明证——但它毕竟是一项遗留技术，带有某些陈旧的特征。例如，它把所有邮件报文的**主体**（不只是首部）限制为简单的 7 比特 ASCII。这一限制在 80 年代初是合理的：当时传输能力稀缺，没人用电子邮件发送大附件或大的图像、音频、视频文件。但在今天这个多媒体时代，7 比特 ASCII 的限制就有点麻烦了——它要求二进制多媒体数据在通过 SMTP 发送之前先编码成 ASCII，并在 SMTP 传输之后再把相应的 ASCII 消息解码回二进制。回忆 2.2 节：HTTP 并不要求多媒体数据在传输前进行 ASCII 编码。

为说明 SMTP 的基本操作，走一遍常见场景。假设 Alice 要给 Bob 发一条简单的 ASCII 消息。

1. Alice 启动她的邮件用户代理，给出 Bob 的电子邮件地址（例如 bob\@someschool.edu），撰写邮件，并指示用户代理发送。
1. Alice 的用户代理把邮件发送到她的邮件服务器，邮件被放入消息队列。
1. 运行在 Alice 邮件服务器上的 SMTP 客户端看到队列中的邮件，向运行在 Bob 邮件服务器上的 SMTP 服务器打开一条 TCP 连接。
1. 经过一些初始的 SMTP 握手之后，SMTP 客户端把 Alice 的邮件送入该 TCP 连接。
1. 在 Bob 的邮件服务器上，SMTP 服务器端收到该邮件，随后 Bob 的邮件服务器把邮件放入 Bob 的邮箱。
1. Bob 在方便时启动他的用户代理读取该邮件。

这一场景总结于图 2.13。需要注意的是：SMTP 通常**不**使用中间邮件服务器来转发邮件，即使两台邮件服务器位于地球两端也是如此。如果 Alice 的服务器在香港、Bob 的服务器在圣路易斯，那么 TCP 连接就是香港与圣路易斯之间的一条直接连接。

<AsideCard title="SMTP 与 HTTP 的对比">

二者都是用于传送文件的协议，有不少可类比之处，也有重要差别。两者都使用 TCP 的持续连接；都采用"请求-响应"式的 ASCII 文本命令/应答交互。关键差别在于：HTTP 是**拉**（pull）协议——用户用 HTTP 从服务器**拉取**文件，TCP 连接由想获取文件的一方发起；而 SMTP 是**推**（push）协议——发送方的邮件服务器把文件**推**给接收方的邮件服务器，TCP 连接由想发送文件的一方发起。

</AsideCard>

## 2.3.2　邮件报文格式

当 Alice 给 Bob 写一封电子邮件时，她使用的用户代理可能要求她填写若干首部行，例如收件人地址、主题等。这些首部行与邮件主体一起构成**邮件报文**。邮件报文本身与 SMTP 是分开的：SMTP 负责**传送**报文，而报文**格式**由 RFC 5322 等规范定义。

一个典型的邮件报文如下（首部与主体之间以一个空行分隔）：

```text
From: alice@crepes.fr
To: bob@hamburger.edu
Subject: Searching for the meaning of life.

（这里是邮件主体……）
```

首部行之后必须有一个空行，然后是邮件主体（ASCII 文本）。值得注意的是，邮件报文的首部行与 SMTP 命令/应答是两回事：SMTP 的 `MAIL FROM`、`RCPT TO` 等命令用于在服务器之间建立传输会话，而邮件报文首部中的 `From:`、`To:` 只是给收件人看的"信纸抬头"，二者不必一致（这也正是伪造发件人如此容易的原因之一）。

## 2.3.3　邮件访问协议

一旦 SMTP 把邮件投递到接收方的邮件服务器，该邮件就被放入接收方的邮箱。此后，接收方如何从服务器上的邮箱取信？这里涉及另一组协议。

历史上，用户通过直接在邮件服务器上登录（例如用 Telnet）来读信，但这很不方便。于是发展出两类**邮件访问协议**：

- **POP3**（Post Office Protocol version 3，RFC 1939）：一种简单协议，客户与服务器建立 TCP 连接后进行"鉴别、事务、更新"三阶段交互，把邮件从服务器**下载**到本地并（通常）删除服务器副本。POP3 是有状态的（在一个会话内），但跨会话不保存状态。
- **IMAP**（Internet Mail Access Protocol，RFC 3501）：功能更强，允许用户在服务器上维护文件夹层次，把邮件在服务器上移动、标记为已读、搜索等；用户在客户端所做的操作会反映到服务器上，因而适合在多个设备上访问同一邮箱。
- **基于 Web 的电子邮件**（如 Gmail、Yahoo! Mail）：用户代理就是浏览器，浏览器通过 HTTP 与邮件服务器通信，邮件服务器再通过 SMTP（发信）和 IMAP/POP3 或私有接口（收信）与邮件系统交互。今天这是最常见的邮件访问方式。

<Figure src="ch02/fig2-14.webp" caption="图 2.14　电子邮件协议及其通信实体" />

<AsideCard title="安全聚焦 · 电子邮件的安全">

原始的 SMTP、POP3 和 IMAP 都以明文传输，包括口令。因此在无线链路或共享链路上，邮件内容与口令都可能被嗅探。今天，这些协议通常运行在 TLS 之上（即 SMTPS、POP3S、IMAPS），或者通过 HTTPS 访问基于 Web 的邮件。此外，邮件还面临垃圾邮件（spam）、钓鱼（phishing）和伪造发件人等问题，相应的防御手段（如 SPF、DKIM、DMARC）依赖域名与密码学机制，详见第 8 章。

</AsideCard>
