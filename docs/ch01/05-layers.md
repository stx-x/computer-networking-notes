# 1.5　协议层次及其服务模型

从上面的讨论可以明显看出，因特网是一个极其复杂的系统：众多的应用与协议、各种类型的端系统、分组交换机，以及各种类型的链路级媒体。面对如此巨大的复杂性，我们还有希望把网络体系结构——至少是我们关于网络体系结构的讨论——组织起来吗？幸运的是，两个问题的答案都是"有"。

## 1.5.1　分层体系结构

在着手梳理关于因特网体系结构的思路之前，先看一个人类类比。其实我们日常生活中无时无刻不在处理复杂系统。设想有人请你描述航空系统：面对售票员、行李托运、登机口人员、飞行员、飞机、空中交通管制以及全球性的飞机航线系统，你该如何找出描述这个复杂系统的结构？

一种办法是描述你乘飞机旅行时所经历（或别人为你所做）的一系列动作：买票、托运行李、到登机口、登机；飞机起飞并按航线飞往目的地；飞机降落后，你在登机口下机、取回行李；如果旅途不愉快，你就向售票员投诉航班（徒劳无功）。这一场景如图 1.22 所示。

<Figure src="ch01/fig1-22.webp" caption="图 1.22　乘飞机旅行：动作序列" />

这里已经能看出与计算机网络的一些类比：你被航空公司从起点运到终点；在因特网中，分组被从源主机运到目的主机。但这还不是我们想要的类比。我们要在图 1.22 中找出某种**结构**。观察图 1.22 可以发现：两端都有**售票**功能；对已购票的旅客还有**行李**功能；对已购票且已托运行李的旅客还有**登机口**功能；对已通过登机口的旅客（即已购票、已托运行李、已通过登机口），还有**起飞与降落**功能；而在飞行途中，还有**航线**功能。这提示我们可以按**水平**方式来看待图 1.22 中的功能，如图 1.23 所示。

<Figure src="ch01/fig1-23.webp" caption="图 1.23　航空功能的水平分层" />

图 1.23 把航空功能划分为若干**层次**，为讨论航空旅行提供了一个框架。注意，每一层与其下面各层一起实现某种功能、某种服务：在售票层及其以下各层，完成"从值机柜台到值机柜台"的人员运送；在行李层及其以下各层，完成"从行李托运到行李提取"的人员与行李运送（注意，行李层只向已购票的人提供这一服务）；在登机口层，完成"从出发登机口到到达登机口"的人员与行李运送；在起飞/降落层，完成"从跑道到跑道"的人员及其行李运送。每一层通过以下两种方式提供其服务：(1) 在该层内执行某些动作（例如在登机口层，让人上下飞机）；(2) 使用紧邻其下那一层的服务（例如在登机口层，使用起飞/降落层"从跑道到跑道"的旅客运送服务）。

分层体系结构使我们能够讨论一个庞大而复杂系统中界定明确的特定部分。这种简化本身就有相当的价值：它提供了**模块化**，使改变某一层所提供服务的**实现**变得容易得多。只要该层向上一层提供相同的服务、并使用下一层相同的服务，那么当某一层的实现发生变化时，系统其余部分保持不变。（注意，改变服务的实现与改变服务本身是完全不同的两回事！）例如，如果登机口的功能改变了（比如改成按身高上下飞机），航空系统的其余部分仍保持不变，因为登机口层仍然提供相同的功能（让人上下飞机），只是改变之后用不同的方式来实现该功能。对于不断更新的大型复杂系统而言，"能够改变某一服务的实现而不影响系统其他组件"正是分层的又一重要优点。

### 协议分层

关于航空公司的类比就说到这里，现在把注意力转向网络协议。为了给网络协议的设计提供结构，网络设计者把协议——以及实现这些协议的网络硬件和软件——按**层次**组织。每个协议属于某一层，正如图 1.23 中航空体系结构的每个功能属于某一层。我们同样关心某一层向上一层提供的服务，即所谓该层的**服务模型**。与航空例子一样，每一层通过以下两种方式提供其服务：(1) 在该层内执行某些动作；(2) 使用紧邻其下那一层的服务。例如，第 $n$ 层提供的服务可以包括从网络一端到另一端可靠地交付报文，这可以通过使用第 $n - 1$ 层不可靠的端到端报文交付服务、并增加第 $n$ 层检测与重传丢失报文的功能来实现。

协议层可以用软件、硬件或二者结合来实现。应用层协议（如 HTTP 和 SMTP）几乎总是在端系统中用软件实现，运输层协议也是如此。由于物理层和数据链路层负责处理特定链路上的通信，它们通常在与某条链路相关的**网络接口卡**（例如以太网卡或 WiFi 接口卡）中实现。网络层则常常是软硬件的混合实现。还要注意，正如分层航空体系结构中的功能分布在构成该系统的各个机场和飞行控制中心一样，第 $n$ 层的协议也分布在构成网络的端系统、分组交换机和其他组件之中——也就是说，这些网络组件中往往各有一份第 $n$ 层协议的实现。

协议分层具有概念上和结构上的优点 [RFC 3439]：如前所见，分层为讨论系统组件提供了有条理的方式，模块化使系统组件的更新更容易。不过要指出，有些研究者和网络工程师强烈反对分层 [Wakeman 1992]。分层的一个潜在缺点是，某一层可能重复低层的功能，例如许多协议栈既提供逐链路的差错恢复、又提供端到端的差错恢复。另一个潜在缺点是，某一层的功能可能需要只存在于另一层的信息（例如时间戳值），这违背了层间分离的目标。

把各层的协议合在一起，称为**协议栈**（protocol stack）。因特网协议栈由五层组成：物理层、链路层、网络层、运输层和应用层，如图 1.24 所示。如果你翻一翻本书目录，会发现我们大体上就是按因特网协议栈的各层来组织全书的，并采用**自顶向下**的方法：先讲应用层，然后逐层向下。

### 应用层

应用层是网络应用及其应用层协议所在之处。因特网的应用层包含许多协议，例如 HTTP 协议（提供 Web 文档的请求与传送）和 SMTP（提供电子邮件的传送）。我们还将看到，某些网络功能——例如把 www.ietf.org 这类便于人记忆的因特网端系统名字转换为 32 比特网络地址——也要借助一个特定的应用层协议来完成，即**域名系统**（DNS）。第 2 章将会看到，创建并部署我们自己的新应用层协议是非常容易的。

应用层协议分布在多个端系统上：一个端系统中的应用使用该协议与另一个端系统中的应用交换信息分组。我们把应用层的这种信息分组称为**报文**（message）。

### 运输层

因特网的运输层在应用端点之间传送应用层报文。因特网中有两个运输协议——TCP 和 UDP，二者都可以传送应用层报文。TCP 向其应用提供**面向连接**的服务，包括把应用层报文有保证地交付到目的地，以及**流量控制**（即发送方与接收方速度匹配）。TCP 还把长报文划分为较短的报文段，并提供**拥塞控制**机制，使源端在网络拥塞时抑制其发送速率。UDP 协议向其应用提供**无连接**服务，这是一种"极简"服务，不提供可靠性、不提供流量控制、也不提供拥塞控制。本书把运输层分组称为**报文段**（segment）。

### 网络层

因特网的网络层负责把称为**数据报**（datagram）的网络层分组从一台主机移动到另一台主机。源主机中的因特网运输层协议（TCP 或 UDP）把一个运输层报文段和一个目的地址交给网络层，就像你把一封写有目的地址的信交给邮政服务一样；网络层则提供把该报文段交付给目的主机运输层的服务。

因特网的网络层包含著名的 IP 协议，它定义了数据报中的字段，以及端系统与路由器如何作用于这些字段。IP 协议只有一个，所有具有网络层的因特网组件都必须运行 IP 协议。因特网的网络层还包含**路由协议**，用于确定数据报在源与目的之间所走的路径。因特网有许多路由协议：如 1.3 节所述，因特网是网络的网络，在一个网络内部，网络管理员可以运行任何想要的路由协议。尽管网络层既包含 IP 协议又包含众多路由协议，它常被简称为 **IP 层**，这反映出 IP 是把因特网黏合在一起的"胶水"。

### 链路层

因特网的网络层让数据报经源与目的之间的一系列路由器路由。要把一个分组从路由上的一个节点（主机或路由器）移动到下一个节点，网络层要依赖链路层的服务：具体地说，在每个节点，网络层把数据报下交给链路层，链路层把数据报交付给路由上的下一个节点；在下一个节点，链路层再把数据报上交给网络层。

链路层提供的服务取决于链路上所采用的具体链路层协议。例如，有些链路层协议提供从发送节点经一条链路到接收节点的可靠交付。注意，这种可靠交付服务不同于 TCP 的可靠交付服务——后者提供的是一台端系统到另一台端系统的可靠交付。链路层协议的例子包括以太网、WiFi 以及电缆接入网的 DOCSIS 协议。由于数据报从源到目的通常要经过若干条链路，一个数据报在其路径的不同链路上可能由不同的链路层协议处理——例如在某条链路上由 WiFi 处理，在下一条链路上由以太网处理。网络层将从各个不同的链路层协议获得不同的服务。本书把链路层分组称为**帧**（frame）。

### 物理层

链路层的任务是把整个帧从一个网络元素移动到相邻的网络元素，而物理层的任务则是把帧中的一个个**比特**从一个节点移动到下一个节点。这一层的协议同样依赖于链路，并进一步依赖于链路的实际传输媒体（例如双绞铜线、单模光纤）。例如，以太网有许多物理层协议：一个用于双绞铜线，一个用于同轴电缆，一个用于光纤，等等。每种情况下，比特跨越链路的方式各不相同。

## 1.5.2　封装

图 1.25 展示了数据在发送端系统协议栈中下行的物理路径，在中间链路层交换机和路由器的协议栈中上下往返，然后在接收端系统的协议栈中上行。如本书后文将要讨论的，路由器与链路层交换机都是分组交换机。与端系统类似，路由器和链路层交换机也把其网络硬件和软件按层组织。但路由器和链路层交换机并不实现协议栈中的所有层，它们通常只实现下面几层：如图 1.25 所示，链路层交换机实现第 1、2 层，路由器实现第 1 至第 3 层。这意味着，例如因特网路由器能够实现 IP 协议（一个第 3 层协议），而链路层交换机不能。后文将会看到，链路层交换机虽然不认识 IP 地址，却能识别第 2 层地址，例如以太网地址。注意，主机实现了全部五层——这与"因特网体系结构把大量复杂性放在网络边缘"的观点是一致的。

图 1.25 还说明了**封装**（encapsulation）这一重要概念。在发送主机，一个应用层报文（图 1.25 中的 M）被交给运输层。最简单的情形下，运输层取出该报文，附加上将被接收端运输层使用的附加信息（即所谓的运输层首部信息，图 1.25 中的 $H_{t}$）。应用层报文与运输层首部信息一起构成**运输层报文段**，于是运输层报文段**封装**了应用层报文。附加的信息可能包括让接收端运输层把报文交付给正确应用所需的信息，以及让接收端判断报文中比特在途中是否被改变的差错检测比特。

随后运输层把报文段交给网络层，网络层添加网络层首部信息（图 1.25 中的 $H_{n}$），例如源端系统与目的端系统的地址，从而生成**网络层数据报**；数据报再被交给链路层，链路层（当然！）会添加自己的链路层首部信息，生成**链路层帧**。于是我们看到，在每一层，分组都有两类字段：**首部字段**与**载荷字段**，而载荷通常就是来自上一层的分组。

这里有一个有用的类比：通过公共邮政服务把一个公司内部备忘录从一个分公司寄到另一个分公司。假设 Alice 在某个分公司，想给另一个分公司的 Bob 寄一份备忘录。备忘录相当于**应用层报文**。Alice 把备忘录装进一个**公司内部信封**，在信封正面写上 Bob 的姓名和部门。内部信封相当于**运输层报文段**——它包含首部信息（Bob 的姓名和部门编号），并封装了应用层报文（备忘录）。当发送方分公司的收发室收到这个内部信封时，它把内部信封再装进另一个适合通过公共邮政服务寄送的**邮政信封**，并在邮政信封上写明发送方与接收方分公司的邮政地址。这里，邮政信封相当于**数据报**——它封装了运输层报文段（内部信封），而后者又封装了原始报文（备忘录）。邮政服务把邮政信封投递到接收方分公司的收发室，在那里开始**解封装**过程：收发室取出内部备忘录并转交给 Bob；最后，Bob 打开信封取出备忘录。

封装过程可能比上面描述的更复杂。例如，一个长报文可能被划分为多个运输层报文段（而每个报文段本身又可能被划分为多个网络层数据报）；在接收端，这样的报文段必须由其各个数据报重新装配而成。
