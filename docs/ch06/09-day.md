# 6.7　回顾：一次 Web 页面请求的一生

本章讲完了链路层，前面的章节讲了网络层、运输层与应用层，我们沿协议栈的旅程到此完整了！本书开篇（1.1 节）我们写道"本书的大部分内容都涉及计算机网络协议"，前五章已经充分证明了这一点！在进入本书后半部分的专题章节之前，我们想以一种综合、整体的视角来总结这段沿协议栈下行的旅程，看看迄今学过的这些协议如何协同工作。采取这种"全局图景"视角的一个办法，是找出满足哪怕最简单的一个请求——下载一个 Web 页面——所涉及的许多（真的很多！）协议。图 6.34 说明了我们的场景：一名学生 Bob 把笔记本电脑连接到学校的以太网交换机，并下载一个 Web 页面（比如 `www.google.com` 的主页）。如我们现在所知，为满足这个看似简单的请求，"引擎盖下面"发生了许多事情。本章末的一个 Wireshark 实验会更详细地考察包含类似场景中若干分组的跟踪文件。

## 6.7.1　起步：DHCP、UDP、IP 与以太网

假设 Bob 启动笔记本电脑，然后把它接到一根连到学校以太网交换机的以太网电缆上，交换机又连到学校的路由器，如图 6.34 所示。学校路由器连接到一个 ISP，本例中是 `comcast.net`。在这个例子中，`comcast.net` 为学校提供 DNS 服务，因此 DNS 服务器位于 Comcast 网络中而不是学校网络中。我们假设 DHCP 服务器运行在路由器中，情况常常如此。

Bob 第一次把笔记本接入网络时，没有 IP 地址就什么也做不了（例如下载网页）。因此 Bob 的笔记本所做的第一个与网络有关的动作，就是运行 DHCP 协议，从本地 DHCP 服务器获得一个 IP 地址以及其他信息：

1. Bob 笔记本上的操作系统创建一个 DHCP 请求报文（4.3.3 节），并把它放入一个 UDP 报文段（3.3 节），目的端口 67（DHCP 服务器）、源端口 68（DHCP 客户端）。该 UDP 报文段随后被放入一个 IP 数据报（4.3.1 节），IP 目的地址为广播地址 `255.255.255.255`，源 IP 地址为 `0.0.0.0`（因为 Bob 的笔记本还没有 IP 地址）。
1. 含有 DHCP 请求报文的 IP 数据报随后被放入一个以太网帧（6.4.2 节）。该以太网帧的目的 MAC 地址为 `FF:FF:FF:FF:FF:FF`，以便该帧被广播到连接在交换机上的所有设备（希望其中包括一台 DHCP 服务器）；帧的源 MAC 地址是 Bob 笔记本的地址 `00:16:D3:23:68:8A`。
1. 含有 DHCP 请求的广播以太网帧是 Bob 笔记本发给以太网交换机的第一个帧。交换机把这个入帧广播到所有出端口，包括连到路由器的那个端口。
1. 路由器在其 MAC 地址为 `00:22:6B:45:1F:1B` 的接口上收到含有 DHCP 请求的广播以太网帧，并从以太网帧中取出 IP 数据报。该数据报的广播 IP 目的地址表明这个 IP 数据报应由本节点的上层协议处理，于是数据报的载荷（一个 UDP 报文段）被多路分用（3.2 节）上交 UDP，DHCP 请求报文再从 UDP 报文段中取出。DHCP 服务器现在拿到了 DHCP 请求报文。
1. 假设路由器中运行的 DHCP 服务器能在 CIDR（4.3.3 节）块 `68.85.2.0/24` 中分配 IP 地址。在这个例子中，学校里使用的所有 IP 地址因此都在 Comcast 的地址块内。假设 DHCP 服务器把地址 `68.85.2.101` 分配给 Bob 的笔记本。DHCP 服务器创建一个 DHCP ACK 报文（4.3.3 节），其中含有这个 IP 地址、DNS 服务器的 IP 地址（`68.87.71.226`）、默认网关路由器的 IP 地址（`68.85.2.1`）以及子网块 `68.85.2.0/24`（等价地，"网络掩码"）。该 DHCP 报文被放入一个 UDP 报文段，报文段被放入一个 IP 数据报，数据报被放入一个以太网帧。该以太网帧的源 MAC 地址是路由器面向学校网络的接口地址（`00:22:6B:45:1F:1B`），目的 MAC 地址是 Bob 的笔记本（`00:16:D3:23:68:8A`）。
1. 含有 DHCP ACK 的以太网帧由路由器（单播）发送给交换机。由于交换机是自学习的（6.4.3 节），且此前收到过来自 Bob 笔记本的以太网帧（含有 DHCP 请求），交换机知道应当把目的地址为 `00:16:D3:23:68:8A` 的帧只转发到通往 Bob 笔记本的那个输出端口。
1. Bob 的笔记本收到含有 DHCP ACK 的以太网帧，从以太网帧中取出 IP 数据报，从 IP 数据报中取出 UDP 报文段，再从 UDP 报文段中取出 DHCP ACK 报文。Bob 的 DHCP 客户端随后记录自己的 IP 地址及其 DNS 服务器的 IP 地址，并把默认网关地址装入自己的 IP 转发表（4.1 节）。Bob 的笔记本将把所有目的地址在其子网 `68.85.2.0/24` 之外的数据报发送给默认网关。至此，Bob 的笔记本已初始化好网络组件，可以开始处理 Web 页面获取了。（注意：第 4 章给出的四步 DHCP 中，实际上只有最后两步是必需的。）

## 6.7.2　仍在起步：DNS 与 ARP

当 Bob 在浏览器中输入 `www.google.com` 的 URL 时，他就启动了一长串最终会让浏览器显示 Google 主页的事件。Bob 的浏览器首先创建一个 TCP 套接字（2.7 节），用来把 HTTP 请求（2.2 节）发送给 `www.google.com`。为创建该套接字，Bob 的笔记本需要知道 `www.google.com` 的 IP 地址。我们在 2.5 节学到，DNS 协议用来提供这种"名字到 IP 地址"的翻译服务。

1. 于是 Bob 笔记本上的操作系统创建一个 DNS 查询报文（2.5.3 节），把字符串 "www.google.com" 放在 DNS 报文的问题段中。这个 DNS 报文随后被放入一个 UDP 报文段，目的端口 53（DNS 服务器）。UDP 报文段再被放入一个 IP 数据报，IP 目的地址为 `68.87.71.226`（第 5 步 DHCP ACK 中返回的 DNS 服务器地址），源 IP 地址为 `68.85.2.101`。
1. Bob 的笔记本随后把含有 DNS 查询报文的数据报放入一个以太网帧。该帧将被（在链路层上）发送给 Bob 学校网络中的网关路由器。然而，尽管 Bob 的笔记本通过上面第 5 步的 DHCP ACK 报文知道了学校网关路由器的 IP 地址 `68.85.2.1`，它并不知道网关路由器的 MAC 地址。为获得网关路由器的 MAC 地址，Bob 的笔记本需要使用 ARP 协议（6.4.1 节）。
1. Bob 的笔记本创建一个 ARP 查询报文，目标 IP 地址为 `68.85.2.1`（默认网关），把该 ARP 报文放入一个目的地址为广播地址 `FF:FF:FF:FF:FF:FF` 的以太网帧，并把该以太网帧发送给交换机，交换机把帧交付给所有连接的设备，包括网关路由器。
1. 网关路由器在面向学校网络的接口上收到含有 ARP 查询报文的帧，发现 ARP 报文中目标 IP 地址 `68.85.2.1` 与其接口的 IP 地址匹配。于是网关路由器准备一个 ARP 应答，指出其 MAC 地址 `00:22:6B:45:1F:1B` 对应 IP 地址 `68.85.2.1`。它把 ARP 应答报文放入一个以太网帧，目的地址为 `00:16:D3:23:68:8A`（Bob 的笔记本），并把帧发送给交换机，交换机把帧交付给 Bob 的笔记本。
1. Bob 的笔记本收到含有 ARP 应答报文的帧，从 ARP 应答报文中取出网关路由器的 MAC 地址 `00:22:6B:45:1F:1B`。
1. Bob 的笔记本现在（终于！）可以把含有 DNS 查询的以太网帧寻址到网关路由器的 MAC 地址。注意这个帧中的 IP 数据报的 IP 目的地址是 `68.87.71.226`（DNS 服务器），而帧的目的地址是 `00:22:6B:45:1F:1B`（网关路由器）。Bob 的笔记本把这个帧发送给交换机，交换机把帧交付给网关路由器。

## 6.7.3　仍在起步：域内选路到 DNS 服务器

1. 网关路由器收到帧并取出含有 DNS 查询的 IP 数据报。路由器查找该数据报的目的地址 `68.87.71.226`，并从其转发表确定该数据报应发往图 6.34 中 Comcast 网络最左侧的路由器。该 IP 数据报被放入一个适合连接学校路由器与最左侧 Comcast 路由器那条链路的链路层帧，并在这条链路上发送出去。
1. Comcast 网络最左侧的路由器收到帧，取出 IP 数据报，检查数据报的目的地址 `68.87.71.226`，并从其转发表确定把数据报朝 DNS 服务器转发的出接口。该转发表已由 Comcast 的域内协议（如 RIP、OSPF 或 IS-IS，5.3 节）以及因特网的域间协议 BGP（5.4 节）填充。
1. 最终，含有 DNS 查询的 IP 数据报到达 DNS 服务器。DNS 服务器取出 DNS 查询报文，在其 DNS 数据库（2.5 节）中查找名字 `www.google.com`，找到含有 `www.google.com` 的 IP 地址 `64.233.169.105` 的 DNS 资源记录（假设该记录当前缓存在 DNS 服务器中；回忆这些缓存数据源自 google.com 的权威 DNS 服务器，2.5.2 节）。DNS 服务器构造一个含有该"主机名到 IP 地址"映射的 DNS 应答报文，把 DNS 应答报文放入一个 UDP 报文段，再把报文段放入一个寻址到 Bob 笔记本 `68.85.2.101` 的 IP 数据报。该数据报将经 Comcast 网络转发回学校路由器，再从那里经以太网交换机送到 Bob 的笔记本。
1. Bob 的笔记本从 DNS 报文中取出服务器 `www.google.com` 的 IP 地址。经过大量工作，Bob 的笔记本终于准备好联系 `www.google.com` 服务器了！

## 6.7.4　Web 客户端-服务器交互：TCP 与 HTTP

1. 现在 Bob 的笔记本有了 `www.google.com` 的 IP 地址，它可以创建 TCP 套接字（2.7 节），用来把 HTTP GET 报文（2.2.3 节）发送给 `www.google.com`。当 Bob 创建 TCP 套接字时，Bob 笔记本中的 TCP 必须先与 `www.google.com` 中的 TCP 执行三次握手（3.5.6 节）。于是 Bob 的笔记本首先创建一个目的端口为 80（HTTP）的 TCP SYN 报文段，把该 TCP 报文段放入一个目的 IP 地址为 `64.233.169.105`（`www.google.com`）的 IP 数据报，把数据报放入一个目的 MAC 地址为 `00:22:6B:45:1F:1B`（网关路由器）的帧，并把帧发送给交换机。
1. 学校网络、Comcast 网络与 Google 网络中的路由器使用各自路由器中的转发表，把含有 TCP SYN 的数据报朝 `www.google.com` 转发，如上面第 14–16 步所述。回忆决定分组在 Comcast 与 Google 网络之间域间链路上转发的路由器转发表项，是由 BGP 协议（第 5 章）确定的。
1. 最终，含有 TCP SYN 的数据报到达 `www.google.com`。TCP SYN 报文从数据报中取出，并被多路分用到与端口 80 关联的欢迎套接字。为 Google HTTP 服务器与 Bob 笔记本之间的 TCP 连接创建一个连接套接字（2.6 节）。生成一个 TCP SYNACK（3.5.6 节）报文段，放入一个寻址到 Bob 笔记本的数据报，最后放入一个适合连接 `www.google.com` 与其第一跳路由器那条链路的链路层帧。
1. 含有 TCP SYNACK 报文段的数据报经 Google、Comcast 与学校网络转发，最终到达 Bob 笔记本中的以太网控制器。数据报在操作系统内被多路分用到第 18 步创建的 TCP 套接字，该套接字进入连接已建立状态。
1. Bob 笔记本上的套接字现在（终于！）可以向 `www.google.com` 发送字节了，于是 Bob 的浏览器创建含有待取 URL 的 HTTP GET 报文（2.2.3 节）。HTTP GET 报文随后被写入套接字，GET 报文成为某个 TCP 报文段的载荷。该 TCP 报文段被放入数据报，并按上面第 18–20 步发送并交付到 `www.google.com`。
1. `www.google.com` 上的 HTTP 服务器从 TCP 套接字读取 HTTP GET 报文，创建一个 HTTP 响应报文（2.2 节），把所请求的网页内容放入 HTTP 响应报文的主体，并把该报文写入 TCP 套接字。
1. 含有 HTTP 应答报文的数据报经 Google、Comcast 与学校网络转发，到达 Bob 的笔记本。Bob 的浏览器程序从套接字读取 HTTP 响应，从 HTTP 响应主体中取出网页的 HTML，最后（终于！）显示出这个网页！

上面这个场景涵盖了大量网络知识！如果你理解了上述例子的大部分或全部，那么自你第一次读 1.1 节以来也已经走了很远——那时我们写道"本书的大部分内容都涉及计算机网络协议"，而你也许还在纳闷协议到底是什么！上面这个例子虽然详尽，却省略了若干可能出现的其他协议（例如学校网关路由器中运行的 NAT、接入学校网络的无线接入、用于接入学校网络或加密报文段／数据报的安全协议、网络管理协议），以及一些在公共因特网中会遇到的考虑（Web 缓存、DNS 层次结构）。本书后半部分将涵盖其中若干主题以及更多内容。

最后要指出，上面这个例子是对本书前半部分学过的许多协议所做的综合、整体、同时也非常"螺母与螺栓"式的考察。这个例子更侧重"如何"而不是"为何"。若想对网络协议设计获得更宽广、更具反思性的视角，不妨重读 4.5 节的"因特网的体系结构原则"及其中的参考文献。
