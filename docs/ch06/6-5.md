# 6.5　链路虚拟化：把网络当作链路层

本章讨论链路层协议，而本章已近尾声，不妨回顾一下我们对"链路"一词的理解是如何演进的。本章开头把链路看作连接两台通信主机的物理导线。在研究多路访问协议时我们看到，多台主机可以由一条共享导线连接，而这条连接主机的"导线"可以是射频频谱或其他介质；这使我们更抽象地把链路看作**信道**，而不是导线。在研究以太网局域网（图 6.15）时我们看到，互联介质实际上可以是一个相当复杂的交换式基础设施。然而在整个演进过程中，主机自身始终认为互联介质只是连接两台或多台主机的**一条链路层信道**。例如我们看到，一台以太网主机可以完全不知道自己是经由一段短的局域网段（图 6.17）、一个地理上分散的交换式局域网（图 6.15）还是一个 VLAN（图 6.26）与其他局域网主机相连的。

在两台主机之间用拨号调制解调器连接的情况下，连接两台主机的链路实际上是电话网——一个逻辑上独立的全球电信网络，有自己的交换机、链路以及用于数据传输与信令的协议栈。然而从因特网链路层的角度看，经电话网的拨号连接被看作一条简单的"导线"。在这个意义上，因特网**虚拟化**了电话网，把电话网看作一种链路层技术，在两台因特网主机之间提供链路层连通性。你可能还记得第 2 章讨论覆盖网络时说过：覆盖网络同样把因特网看作在覆盖节点之间提供连通性的手段，试图以因特网覆盖电话网的同样方式覆盖因特网。

本节介绍两种技术：两台设备之间的**虚拟链路**在逻辑上表现得像一条物理链路，但实际上是由底层一个复杂的互联设备网络实现的。6.5.2 节将讨论前面提到的 VXLAN 技术；而 6.5.1 节先考察**多协议标签交换**（MPLS）。与电路交换的电话网不同，MPLS 本身就是一种分组交换的**虚电路**网络，有自己的分组格式与转发行为。因此从教学角度看，讨论 MPLS 既可归入网络层的学习，也可归入链路层的学习。不过从因特网的角度看，我们可以把 MPLS 像电话网和交换式以太网那样，看作一种用来互联 IP 设备的**链路层技术**。我们对 MPLS 的处理只能简短，因为这些网络足以（也确实已经）写成整本书。细节请参阅 [Davie 2000]。这里主要关注 MPLS 服务器如何与 IP 设备互联，同时也会稍微深入底层技术。

## 6.5.1　多协议标签交换（MPLS）

MPLS 源于 20 世纪 90 年代中后期若干产业界的努力，其目标是提高 IP 路由器的转发速度，办法是采纳虚电路网络世界的一个关键概念：**固定长度标签**。目标并不是要用基于固定长度标签和虚电路的转发基础设施取代基于目的地址的 IP 数据报转发基础设施，而是要**增强**它——有选择地给数据报打标签，并让路由器在可能时基于固定长度标签（而不是目的 IP 地址）转发数据报。重要的是，这些技术与 IP 携手工作，使用 IP 编址与选路。IETF 把这些努力统一为 MPLS 协议 [RFC 3031, RFC 3032]，实际上是把 VC 技术融入了路由式数据报网络。

先来考察由支持 MPLS 的路由器处理的链路层帧的格式。图 6.28 显示，在支持 MPLS 的设备之间传输的链路层帧，在二层（如以太网）首部与三层（即 IP）首部之间加入了一个小的 **MPLS 首部**。RFC 3032 规定了这类链路上 MPLS 首部的格式；其他 RFC 也为 ATM 与帧中继网络定义了相应首部。MPLS 首部中的字段包括**标签**、3 个保留供实验使用的比特、一个 **S 比特**（用于指示一串"堆叠"MPLS 首部的结束，这是这里不涉及的高级话题）以及一个**生存期**字段。

<Figure src="ch06/fig6-28.webp" caption="图 6.28　MPLS 首部：位于链路层与网络层首部之间" />

从图 6.28 可以立刻看出，MPLS 增强帧只能在**都**支持 MPLS 的路由器之间发送（因为一台不支持 MPLS 的路由器在本该找到 IP 首部的地方发现 MPLS 首部时，会相当困惑！）。支持 MPLS 的路由器常被称为**标签交换路由器**（label-switched router），因为它转发 MPLS 帧时，在转发表中查找 MPLS 标签，然后立即把数据报交给合适的输出接口。因此，支持 MPLS 的路由器不必取出目的 IP 地址、在转发表中做最长前缀匹配查找。但路由器如何知道它的邻居确实支持 MPLS？路由器又如何知道该把哪个标签与给定的 IP 目的地关联？要回答这些问题，需要看一组支持 MPLS 的路由器之间的交互。

在图 6.29 的例子中，路由器 R1 到 R4 支持 MPLS，R5 与 R6 是标准 IP 路由器。R1 已向 R2 与 R3 通告：它（R1）能路由到目的地 A，且收到的带 MPLS 标签 6 的帧将被转发到目的地 A。路由器 R3 已向路由器 R4 通告：它能路由到目的地 A 与 D，且分别带 MPLS 标签 10 与 12 的入帧将被交换到那些目的地。路由器 R2 也已向路由器 R4 通告：它（R2）能到达目的地 A，且收到的带 MPLS 标签 8 的帧将被交换到 A。注意路由器 R4 现在处于一个有意思的位置：它有两条到达 A 的 MPLS 路径——经接口 0 出境标签为 10，经接口 1 标签为 8。图 6.29 描绘的总体图景是：IP 设备 R5、R6、A 与 D 通过一个 MPLS 基础设施（支持 MPLS 的路由器 R1–R4）互联在一起，其方式很像交换式局域网或 ATM 网络可以互联 IP 设备。并且与交换式局域网或 ATM 网络一样，支持 MPLS 的路由器 R1–R4 在这样做时从不碰分组的 IP 首部。

<Figure src="ch06/fig6-29.webp" caption="图 6.29　MPLS 增强转发" />

上面的讨论没有说明在支持 MPLS 的路由器之间分发标签所用的具体协议，因为这一信令的细节远超出本书范围。不过要指出，IETF 的 MPLS 工作组已在 [RFC 3468] 中规定，RSVP 协议的一个扩展 RSVP-TE [RFC 3209] 将作为其 MPLS 信令工作的重点。我们也没有讨论 MPLS 实际如何计算支持 MPLS 的路由器之间的分组路径，以及它如何收集链路状态信息（例如 MPLS 未预留的链路带宽量）用于这些路径计算。现有的链路状态路由算法（如 OSPF）已被扩展，可把这些信息泛洪给支持 MPLS 的路由器。有意思的是，实际的路径计算算法并未标准化，目前是厂商专有的。

至此我们对 MPLS 的讨论重点一直是：MPLS 基于标签进行交换，无需考虑分组的 IP 地址。然而 MPLS 的真正优势、也是当前人们对 MPLS 感兴趣的原因，并不在于交换速度可能提高，而在于 MPLS 所带来的新的**流量管理**能力。如上所述，R4 有两条到 A 的 MPLS 路径。如果转发在 IP 层基于 IP 地址进行，我们第 5 章学过的 IP 路由协议只会指定一条到 A 的最小代价路径。因此，MPLS 提供了沿标准 IP 路由协议不可能实现的路由转发分组的能力。这是使用 MPLS 进行**流量工程**（traffic engineering）的一种简单形式 [RFC 3346; RFC 3272; RFC 2702; Xiao 2000]：网络运营者可以推翻正常的 IP 选路，把前往某个目的地的部分流量强制走一条路径，把前往同一目的地的其他流量强制走另一条路径（无论是出于策略、性能还是其他原因）。

MPLS 还可用于许多其他目的。它可以用来对 MPLS 转发路径做快速恢复，例如在链路故障时把流量改道到预先计算好的故障切换路径上 [Kar 2000; Huang 2002; RFC 3469]。最后要指出，MPLS 可以、也确实被用来实现所谓的**虚拟专用网**（VPN）：ISP 在为客户实现 VPN 时，用其支持 MPLS 的网络把客户的各个网络连接起来。MPLS 可以把客户 VPN 所用的资源与编址，与其他穿越该 ISP 网络的用户隔离开；细节见 [DeClercq 2002]。我们将在 8.7.1 节更详细地讨论 VPN。

以上对 MPLS 的讨论很简短，建议读者参阅 [Davie 2000] 及上面的参考文献。要指出的是，MPLS 在软件定义网络（第 5 章）发展之前就已崭露头角，而 MPLS 的许多流量工程能力也可以通过 SDN 以及第 4 章学过的广义转发范式实现。MPLS 与 SDN 会继续共存，还是更新的技术（如 SDN）最终取代 MPLS，只有未来才能告诉我们。

## 6.5.2　VXLAN：IP 之上的以太网

我们在 6.4.4 节研究的 802.1Q VLAN 有两个重要局限：受 802.1Q VLAN 标签中 12 比特 VLAN 标识符字段所限，VLAN 数量不能超过 4 096 个；而且 VLAN 必须包含在单一的全交换式以太网端到端局域网基础设施之内。能不能构建更大的虚拟局域网，或者把分布在全球的二层设备连接成一个虚拟局域网？这两个问题的答案都是"能！"，用的是一种称为**虚拟可扩展局域网**（Virtual extensible Local-Area Network，VXLAN）的途径 [RFC 7348]。

图 6.30 展示了一个简单情形：两个物理上分离的以太网局域网——一个在加利福尼亚州桑尼维尔，一个在印度班加罗尔——被合并成单一的逻辑 VXLAN，使得从桑尼维尔以太网段中某台主机发出、目的 MAC 地址为班加罗尔以太网中某台主机的以太网帧，会在班加罗尔的那台主机上被收到！这是通过创建一条**链路层隧道**实现的：隧道一端在桑尼维尔局域网上的某台设备，另一端在班加罗尔局域网上的某台设备。进入桑尼维尔局域网一侧隧道的以太网帧，会从班加罗尔局域网一侧的隧道出来。VXLAN 隧道把一段以太网（更一般地说，一个二层的子网）**延伸**跨过三层网络的边界。你可能还记得第 4 章用隧道把一个 IPv6 网络经中间的 IPv4 网络连接到另一个 IPv6 网络；有了 VXLAN，我们又看到一个例子：整个网络（这里是隧道端点之间的 IP 网络）被虚拟化成单一的逻辑链路。第 7 章还会看到隧道在蜂窝网络中被广泛使用。确实，隧道出现在许许多多网络场景中 [Zave 2024]。

**VXLAN 隧道端点**（VTEP）在 VXLAN 中起关键作用。VTEP 是一台普通的物理交换机或路由器，或数据中心中的虚拟化交换机或路由器，被配置为实现 VXLAN。在图 6.30 中，位于桑尼维尔的 Host A 发送一个以太网帧，其 MAC 目的地址是位于班加罗尔的 Host B。VTEP x 物理上连在桑尼维尔局域网上，它收到该帧并注意到其目的地是 Host B——它知道 B 在隧道的另一端。VTEP x 随后把整个以太网帧连同一些额外的 VXLAN 首部信息放入一个标准 UDP 数据报的载荷中。这些首部信息包括 24 比特的 **VXLAN 网络标识符**（VNI），它使每个扩展局域网可以标识 1 600 万个 VXLAN。VXLAN 所能提供的巨量虚拟局域网，在数据中心场景中特别有价值。

<Figure src="ch06/fig6-30.webp" caption="图 6.30　包含桑尼维尔与班加罗尔网段的 VXLAN" />

随后，含有原始以太网帧与首部信息的 UDP 数据报被放入一个 IP 数据报，该 IP 数据报被寻址到实现 VXLAN 隧道另一端的 VTEP y。x 与 y 之间的 IP 网络随后把这个 IP 数据报交付给 y，就像它正常交付任何数据报一样，对其内容一无所知。VTEP y 收到数据报，注意到其中含有一个装着 VXLAN 以太网帧的 UDP 报文段，于是取出该以太网帧并在班加罗尔以太网上发送。源 MAC 地址为 A、目的 MAC 地址为 B 的原始以太网帧随后就在 Host B 处被收到。

如果你能想明白图 6.30 所示这种相当不寻常的分层——把以太网数据报封装在 UDP 报文段里、再把 UDP 报文段封装在 IP 数据报里——那么你就真正掌握了**隧道**的概念，也掌握了**链路虚拟化**的概念，以及"整个网络充当单条虚拟链路"这一观念！

在这段关于 VXLAN 的简短讨论中，我们跳过了一些重要问题。例如，VTEP x 如何知道 Host B 位于隧道的另一端？UDP 数据报中究竟包含哪些 VXLAN 首部信息？需要大量 VXLAN 的各种用例是什么？关于 VXLAN 细节及其用途的良好资料有 [Arista VXLAN 2017; Cisco VXLAN 2014; Juniper VXLAN 2024; RFC 7348]。
