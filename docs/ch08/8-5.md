# 8.5　保护电子邮件

前面几节考察了网络安全中的一些根本问题，包括对称密钥与公钥密码学、端点鉴别、密钥分发、报文完整性与数字签名。现在来看这些工具如何被用于为因特网提供安全性。

有意思的是，在因特网协议栈最上面四层中的任何一层都可以提供安全服务。当为某个应用层协议提供安全性时，使用该协议的应用就能享有一项或多项安全服务，例如机密性、鉴别或完整性。当为某个运输层协议提供安全性时，所有使用该运输协议的应用都能享有该运输协议的安全服务。当在网络层以主机到主机的方式提供安全性时，所有运输层报文段（因而是所有应用层数据）都能享有网络层的安全服务。当以链路为单位提供安全性时，该链路上传输的所有帧中的数据都能获得该链路的安全服务。

8.5 至 8.8 节将考察安全工具如何被用于应用层、运输层、网络层与链路层。与本书的整体结构一致，我们从协议栈顶部开始，讨论应用层的安全性。我们的做法是以电子邮件这一具体应用作为应用层安全的案例研究，然后沿协议栈向下，考察 TLS 协议（在运输层提供安全性）、IPsec（在网络层提供安全性），以及 IEEE 802.11 无线局域网的安全性。

你也许会问：因特网为什么要在不止一层提供安全功能？只在网络层提供安全功能不就够了吗？对此有两个回答。第一，尽管网络层的安全性可以通过加密数据报中的所有数据（即所有运输层报文段）并鉴别所有源 IP 地址来提供"全面覆盖"，但它无法提供**用户级**的安全性。例如，一家商务网站不能依靠 IP 层的安全性来鉴别在其站点购物的顾客。因此，既需要低层的全面覆盖，也需要更高层的安全功能。第二，在协议栈较高层部署新的因特网服务（包括安全服务）通常更容易。一个经典例子是 **PGP**（Pretty Good Privacy），它提供安全的电子邮件（本节稍后讨论）。PGP 只需要客户端与服务器端的应用代码，是最早在因特网上被广泛使用的安全技术之一。

## 8.5.1　安全电子邮件

下面用 8.2 至 8.3 节的密码学原理来构建一个安全的电子邮件系统。我们以增量方式设计这个高层方案，每一步引入新的安全服务。设计时请记住 8.1 节引入的那个香艳例子——Alice 与 Bob 的恋情。设想 Alice 想给 Bob 发一封电子邮件，而 Trudy 想插一手。

在埋头为 Alice 与 Bob 设计安全电子邮件系统之前，先想想他们最希望有哪些安全特性。首先是**机密性**。如 8.1 节所述，Alice 与 Bob 都不希望 Trudy 读到 Alice 的邮件。他们其次希望安全邮件系统具备**发送方鉴别**。特别是当 Bob 收到"我不再爱你了。我再也不想见到你。曾经属于你的，Alice"这样一条报文时，他自然会想确认这条报文来自 Alice 而不是 Trudy。这对恋人还会喜欢的一个特性是**报文完整性**，即确信 Alice 发出的报文在发往 Bob 的途中没有被修改。最后，邮件系统应当提供**接收方鉴别**，即 Alice 想确认自己确实是把信发给了 Bob，而不是某个冒充 Bob 的人（例如 Trudy）。

先来解决最要紧的机密性问题。提供机密性最直接的办法，是 Alice 用对称密钥技术（如 DES 或 AES）加密报文，Bob 收到后解密。如 8.2 节所述，若对称密钥足够长，且只有 Alice 与 Bob 持有该密钥，那么其他人（包括 Trudy）要读懂这条报文就极其困难。这个办法虽然直接，却有一个根本困难——8.2 节讨论过的对称密钥分发问题：如何只让 Alice 与 Bob 持有密钥副本。于是我们自然会考虑另一种办法——公钥密码学（例如用 RSA）。在公钥方案中，Bob 把自己的公钥公开（例如放在公钥服务器上或自己的个人主页上），Alice 用 Bob 的公钥加密报文，再把密文发到 Bob 的邮箱地址；Bob 收到后用私钥解密即可。假定 Alice 确知那把公钥就是 Bob 的公钥，这个办法就是提供所需机密性的极佳手段。但有一个问题：公钥加密效率相对较低，对长报文尤其如此。

为克服效率问题，我们利用**会话密钥**（session key，见 8.2.2 节）。具体来说，Alice ①选择一个随机的对称会话密钥 $K_{S}$，②用该对称密钥加密报文 $m$，③用 Bob 的公钥 $K_{B}^{+}$ 加密该对称密钥，④把加密后的报文与加密后的对称密钥拼接成一个"包裹"，⑤把包裹发到 Bob 的邮箱地址。这些步骤见图 8.19。（在本图及后续各图中，带圈的"+"表示拼接，带圈的"−"表示拆解。）Bob 收到包裹后，①用自己的私钥 $K_{B}^{-}$ 得到对称密钥 $K_{S}$，②用对称密钥 $K_{S}$ 解密报文 $m$。

既然设计出了提供机密性的安全邮件系统，下面再设计一个提供发送方鉴别与报文完整性的系统。暂时假设 Alice 与 Bob 不再关心机密性（他们想把感情昭告天下！），只关心发送方鉴别与报文完整性。为此，我们使用 8.3 节讲的数字签名与报文摘要。具体来说，Alice ①对报文 $m$ 施加散列函数 $H$（例如 MD5）得到报文摘要，②用自己的私钥 $K_{A}^{-}$ 对散列结果签名，生成数字签名，③把原始（未加密的）报文与签名拼接成一个包裹，④把包裹发到 Bob 的邮箱地址。Bob 收到包裹后，①把 Alice 的公钥 $K_{A}^{+}$ 作用于经签名的报文摘要，②把该运算结果与自己对该报文计算的散列 $H$ 相比较。这些步骤见图 8.20。如 8.3 节所述，若两个结果相同，Bob 就能相当确信报文来自 Alice 且未被改动。

图 8.21 给出的安全邮件设计，对大多数邮件用户的大多数场合大概都能提供令人满意的安全性。但还有一个重要问题有待解决：该设计要求 Alice 取得 Bob 的公钥，也要求 Bob 取得 Alice 的公钥，而这些公钥的分发并非易事。例如，Trudy 可以冒充 Bob，把自己的公钥说成是 Bob 的公钥交给 Alice，从而收到本该发给 Bob 的报文。如 8.3 节所学，安全分发公钥的一种流行做法是用 CA 认证公钥。

## 8.5.2　PGP

**PGP**（Pretty Good Privacy）由 Phil Zimmermann 于 1991 年编写，是电子邮件加密方案的一个很好的例子。PGP 的设计本质上与图 8.21 所示的设计相同。视版本不同，PGP 软件用 MD5 或 SHA 计算报文摘要，用 CAST、三重 DES 或 IDEA 做对称密钥加密，用 RSA 做公钥加密。

安装 PGP 时，软件会为用户创建一对公钥。公钥可以发布在用户网站上，也可以放入公钥服务器；私钥则由口令保护，用户每次访问私钥都必须输入口令。PGP 让用户选择对报文做数字签名、加密报文，或者既签名又加密。图 8.22 显示了一条 PGP 签名报文，它出现在 MIME 首部之后。报文中的编码数据是 $K_{A}^{-}(H(m))$，即经数字签名的报文摘要。如上所述，Bob 要验证报文完整性，必须能够取得 Alice 的公钥。

<Figure src="ch08/fig8-22.webp" caption="图 8.22　一条 PGP 签名报文" />

图 8.23 显示了一条 PGP 机密报文，它也出现在 MIME 首部之后。当然，明文报文并不包含在这条机密邮件中。当发送方（例如 Alice）既要机密性又要完整性时，PGP 会把图 8.23 那样的报文嵌在图 8.22 那样的报文之中。

PGP 也提供公钥认证机制，但其机制与更常见的 CA 很不一样。PGP 公钥由**信任网**（web of trust）认证：Alice 自己只要相信某个"密钥/用户名"配对确实匹配，就可以认证该配对。此外，PGP 还允许 Alice 声明她信任另一位用户去为更多密钥的真实性作保。有些 PGP 用户通过举办**密钥签名会**（key-signing party）互相签署对方的密钥：用户们实地聚在一起，交换公钥，并用各自的私钥签署对方的密钥以完成认证。

**OpenPGP** [OpenPGP 2025] 是 Zimmermann 原版 PGP 的开放后继者，用公钥和/或对称加密技术为电子邮件与数据文件提供数据机密性、数字签名与报文完整性。OpenPGP 由 [RFC 9580] 规定。

::: info 注

这里值得留意 PGP 与 CA 体系的哲学差异。CA 体系是**层次式**的：你信任少数几个根 CA，根 CA 签发的证书再由下级 CA 转签，信任沿树向下传递。信任网是**网状**的：没有根，每个人自己决定信任谁，信任沿"我认识的人"这张图横向扩散。前者适合大规模、匿名的商业交易（你不认识 Amazon，但可以信任给它签证书的那家 CA）；后者适合小圈子、面对面的社群（你不需要第三方告诉你"这把密钥属于你的朋友"，因为你昨天刚跟他换过密钥）。两种模型各有各的失效模式：CA 体系一旦某个根 CA 被攻破或被胁迫，影响面是全局的；信任网则难以扩展，且"谁都可以认证谁"意味着认证本身的信息量很低。

:::
