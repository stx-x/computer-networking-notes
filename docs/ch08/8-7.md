# 8.7　网络层安全：IPsec 与虚拟专用网

IP 安全协议更常被称为 **IPsec**，它在网络层提供安全性。IPsec 为任意两个网络层实体（包括主机与路由器）之间的 IP 数据报提供安全性。下面很快会讲到，许多机构（公司、政府部门、非营利组织等等）用 IPsec 在公共因特网之上构建**虚拟专用网**（VPN）。

在深入 IPsec 的细节之前，先退一步想想"在网络层提供机密性"意味着什么。当一对网络实体之间（例如两台路由器之间、两台主机之间，或路由器与主机之间）具备网络层机密性时，发送实体对它发往接收实体的所有数据报的载荷都加密。被加密的载荷可以是 TCP 报文段、UDP 报文段、ICMP 报文等等。若这样的网络层服务到位，则从一个实体发往另一实体的所有数据——包括电子邮件、网页、TCP 握手报文以及管理报文（如 ICMP 与 SNMP）——都会对任何嗅探网络的第三方隐藏。正因如此，网络层安全被认为提供"**全面覆盖**"。

除机密性外，网络层安全协议还可能提供其他安全服务。例如它可以提供源鉴别，使接收实体能够验证受保护数据报的来源；可以提供数据完整性，使接收实体能够检查数据报在传输途中是否被改动；还可以提供**防重放攻击**，使 Bob 能够检测出攻击者可能插入的任何重复数据报。下面很快会看到，IPsec 确实为所有这些安全服务都提供了机制，即机密性、源鉴别、数据完整性与防重放攻击。

## 8.7.1　IPsec 与虚拟专用网（VPN）

横跨多个地理区域的机构，往往希望拥有自己的 IP 网络，以便其主机与服务器之间能安全、保密地互发数据。为实现这一目标，机构可以真正部署一个完全独立于公共因特网的物理网络（包括路由器、链路与 DNS 基础设施）。这种专属于某机构的独立网络称为**专用网**（private network）。毫不奇怪，专用网可能非常昂贵，因为机构需要自行采购、安装并维护物理网络基础设施。

如今许多机构不再部署和维护专用网，而是在现有的公共因特网之上构建 **VPN**。使用 VPN 时，机构的跨办公室流量走公共因特网，而不是走物理上独立的网络；但为提供机密性，这些跨办公室流量在进入公共因特网之前先被加密。图 8.27 给出一个简单的 VPN 例子。这里机构由总部、分支机构以及通常从酒店房间接入因特网的出差销售人员组成（图中只画了一位销售人员）。在这个 VPN 中，总部内部两台主机互发 IP 数据报时，或分支机构内部两台主机想通信时，用的都是普通的原味 IPv4（即不带 IPsec 服务）；但当机构的两台主机之间的通信路径要穿过公共因特网时，流量在进入因特网之前先被加密。

<Figure src="ch08/fig8-27.webp" caption="图 8.27　虚拟专用网（VPN）" />

为体会 VPN 如何工作，结合图 8.27 走一个简单例子。当总部的一台主机向住在酒店的销售人员发送 IP 数据报时，总部的网关路由器把这个普通 IPv4 数据报转换成 IPsec 数据报，再把该 IPsec 数据报转发进因特网。这个 IPsec 数据报实际上带有一个传统的 IPv4 首部，因此公共因特网中的路由器会像处理普通 IPv4 数据报那样处理它——对它们来说，这就是一个完全普通的数据报。但如图 8.27 所示，IPsec 数据报的载荷中包含一个 IPsec 首部（用于 IPsec 处理），而且 IPsec 数据报的载荷是加密的。当该 IPsec 数据报到达销售人员的笔记本电脑时，笔记本的操作系统解密载荷（并提供其他安全服务，例如验证数据完整性），再把解密后的载荷交给上层协议（例如 TCP 或 UDP）。

以上只是机构如何利用 IPsec 构建 VPN 的高层概述。为了不被细节淹没，我们略去了许多重要内容。下面细看。

## 8.7.2　AH 与 ESP 协议

IPsec 是个相当复杂的"动物"——它由十几个 RFC 定义。其中两个重要的 RFC 是 RFC 4301（描述整体 IP 安全体系结构）与 RFC 6071（提供 IPsec 协议族概述）。与本书一贯的做法一样，我们的目标不是复述干枯晦涩的 RFC，而是以更具操作性与教学性的方式来描述这些协议。

IPsec 协议族中有两个主要协议：**鉴别首部**（AH，Authentication Header）协议与**封装安全载荷**（ESP，Encapsulation Security Payload）协议。当源 IPsec 实体（通常是主机或路由器）向目的实体（也是主机或路由器）发送安全数据报时，用的是 AH 协议或 ESP 协议之一。AH 协议提供源鉴别与数据完整性，但不提供机密性；ESP 协议提供源鉴别、数据完整性与机密性。由于机密性对 VPN 及其他 IPsec 应用往往至关重要，ESP 协议的使用远比 AH 协议广泛。为进一步揭开 IPsec 的神秘面纱、避开其大部分复杂性，下面只讨论 ESP 协议。想了解 AH 协议的读者可自行查阅 RFC 与其他在线资料。

## 8.7.3　安全关联

IPsec 数据报在一对网络实体之间发送，例如两台主机之间、两台路由器之间，或主机与路由器之间。在从源实体向目的实体发送 IPsec 数据报之前，源与目的实体先建立一个网络层逻辑连接，这个逻辑连接称为**安全关联**（SA，security association）。SA 是**单工**逻辑连接，即从源到目的单向。若两个实体想互发安全数据报，则需要建立两个 SA（即两条逻辑连接），每个方向一条。

再来看图 8.27 中的机构 VPN。该机构由总部、分支机构以及 $n$ 位出差销售人员组成。为便于举例，假设总部与分支机构之间、总部与各销售人员之间都有双向 IPsec 流量。这个 VPN 中共有多少个 SA？回答这个问题要注意：总部网关路由器与分支机构网关路由器之间有 2 个 SA（每个方向一个）；对每位销售人员的笔记本电脑，总部网关路由器与该笔记本之间有 2 个 SA（同样是每个方向一个）。因此总共有 $2(n + 2)$ 个 SA。但要记住，网关路由器或笔记本电脑发进因特网的流量并非全部受 IPsec 保护。例如总部的一台主机可能想访问公共因特网上的 Web 服务器（如 Amazon 或 Google）。因此网关路由器（以及那些笔记本）会向因特网发出普通的 IPv4 数据报与受保护的 IPsec 数据报两种。

<Figure src="ch08/fig8-28.webp" caption="图 8.28　从 R1 到 R2 的安全关联（SA）" />

现在来看看 SA"内部"。为使讨论具体可感，我们以图 8.28 中从路由器 R1 到路由器 R2 的一个 SA 为背景（可以把 R1 看成图 8.27 的总部网关路由器，R2 看成分支机构网关路由器）。路由器 R1 维护关于该 SA 的状态信息，其中包括：

- 该 SA 的 32 比特标识符，称为**安全参数索引**（SPI，Security Parameter Index）；
- 该 SA 的源接口（这里是 200.168.1.100）与目的接口（这里是 193.68.2.23）；
- 要使用的加密类型（例如带 CBC 的 3DES）；
- 加密密钥；
- 完整性检验类型（例如带 MD5 的 HMAC）；
- 鉴别密钥。

每当路由器 R1 需要为该 SA 构造一个要转发的 IPsec 数据报时，它就访问这些状态信息，以确定应如何鉴别与加密该数据报。同样，路由器 R2 也为该 SA 维护相同的状态信息，并用它来鉴别与解密从该 SA 到来的任何 IPsec 数据报。

一个 IPsec 实体（路由器或主机）常常为许多 SA 维护状态信息。例如图 8.27 中带 $n$ 位销售人员的 VPN 例子里，总部网关路由器为 $2(n + 2)$ 个 SA 维护状态信息。IPsec 实体把所有 SA 的状态信息存放在**安全关联数据库**（SAD）中，SAD 是该实体操作系统内核里的一个数据结构。

## 8.7.4　IPsec 数据报

讲完 SA，就可以描述实际的 IPsec 数据报了。IPsec 有两种分组形式：一种用于所谓的**隧道模式**（tunnel mode），另一种用于所谓的**运输模式**（transport mode）。隧道模式更适合 VPN，部署也比运输模式广泛。为进一步揭开 IPsec 的神秘面纱、避开其大部分复杂性，下面只讨论隧道模式。一旦牢牢掌握了隧道模式，运输模式应当不难自行学会。

IPsec 数据报的分组格式见图 8.29。你也许觉得分组格式枯燥乏味，但很快会看到，IPsec 数据报的样子与味道都像一道流行的得州-墨西哥菜！结合图 8.28 来看 IPsec 的各个字段。假设路由器 R1 收到主机 172.16.1.17（总部网络中）发来的一个普通 IPv4 数据报，其目的是主机 172.16.2.48（分支机构网络中）。R1 用下面这套"菜谱"把这个"原始 IPv4 数据报"转换成 IPsec 数据报：

- 在原始 IPv4 数据报（**包括原始首部字段**！）后面附加一个"ESP 尾部"字段；
- 用 SA 指定的算法与密钥加密所得结果；
- 在这个加密后的量前面附加一个称为"ESP 首部"的字段；所得包裹称为"enchilada"（墨西哥卷）；
- 用 SA 指定的算法与密钥，对整条 enchilada 计算一个鉴别 MAC；
- 把该 MAC 附加到 enchilada 后面，构成载荷；
- 最后，创建一个全新的 IP 首部（包含全部经典 IPv4 首部字段，通常共 20 字节），附加在载荷之前。

<Figure src="ch08/fig8-29.webp" caption="图 8.29　IPsec 数据报格式" />

注意，所得的 IPsec 数据报是一个地道的 IPv4 数据报：传统 IPv4 首部字段之后跟着载荷。但在这里，载荷包含一个 ESP 首部、原始 IP 数据报、一个 ESP 尾部以及一个 ESP 鉴别字段（其中原始数据报与 ESP 尾部被加密）。原始 IP 数据报的源 IP 地址是 172.16.1.17、目的 IP 地址是 172.16.2.48。由于 IPsec 数据报包含原始 IP 数据报，这两个地址就（加密后）成为 IPsec 分组载荷的一部分。那么新 IP 首部（即 IPsec 数据报最左边的首部）中的源、目的 IP 地址又是什么呢？如你所料，它们被设为隧道两端的源、目的路由器接口，即 200.168.1.100 与 193.68.2.23。另外，这个新 IPv4 首部中的协议号不是 TCP、UDP 或 SMTP 的协议号，而是 50，表示这是一个使用 ESP 协议的 IPsec 数据报。

R1 把 IPsec 数据报发进公共因特网后，它会经过许多路由器才到达 R2。这些路由器都会把它当作普通数据报处理——它们完全不知道这个数据报载着经 IPsec 加密的数据。对这些公共因特网路由器来说，由于外层首部中的目的 IP 地址是 R2，该数据报的最终目的地就是 R2。

走完一个 IPsec 数据报的构造实例，下面细看这条 enchilada 的配料。在图 8.29 中可以看到，ESP 尾部由三个字段组成：填充、填充长度与下一个首部。回想块密码要求被加密的报文长度是块长的整数倍。填充（由无意义的字节组成）用于在附加到原始数据报之后（连同填充长度与下一个首部字段），使所得的"报文"恰为整数个块。填充长度字段告诉接收实体插入了多少填充（因而需要去掉多少）。下一个首部指明载荷数据字段中所含数据的类型（例如 UDP）。载荷数据（通常是原始 IP 数据报）与 ESP 尾部被拼接起来，然后加密。

在这个加密单元前面附加的是 ESP 首部，它以明文发送，由两个字段组成：SPI 与序号字段。SPI 告诉接收实体该数据报属于哪个 SA；接收实体随即可以用 SPI 检索自己的 SAD，确定相应的鉴别/解密算法与密钥。序号字段用于防重放攻击。

发送实体还会附加一个鉴别 MAC。如前所述，发送实体对整条 enchilada（由 ESP 首部、原始 IP 数据报与 ESP 尾部组成，其中数据报与尾部是加密的）计算 MAC。回想计算 MAC 时，发送方在 enchilada 之后附加一个秘密 MAC 密钥，再对结果计算定长散列。

当 R2 收到该 IPsec 数据报时，R2 发现数据报的目的 IP 地址就是自己，于是处理它。由于（最左侧 IP 首部中的）协议字段是 50，R2 知道应对该数据报施加 IPsec ESP 处理。第一步，R2 探入 enchilada，用 SPI 确定该数据报属于哪个 SA。第二步，计算 enchilada 的 MAC，并验证它与 ESP MAC 字段中的值一致；若一致，它就知道这条 enchilada 来自 R1 且未被篡改。第三步，检查序号字段以确认该数据报是新鲜的（不是重放的数据报）。第四步，用与该 SA 关联的解密算法与密钥解密那个加密单元。第五步，去掉填充，取出原始的普通 IP 数据报。最后第六步，把原始数据报转发进分支机构网络，送往其最终目的地。唉，这套菜谱真够复杂的吧？不过从来没人说过做一条 enchilada 再把它拆开是件容易事！

还有一个重要的微妙之处需要处理，核心是这个问题：当 R1 收到总部网络中某台主机发来的一个（未受保护的）数据报，而该数据报的目的 IP 地址在总部之外时，R1 怎么知道是否应把它转换成 IPsec 数据报？若要经 IPsec 处理，R1 又怎么知道该用（其 SAD 中众多 SA 里的）哪个 SA 来构造 IPsec 数据报？这个问题这样解决：除 SAD 外，IPsec 实体还维护另一个称为**安全策略数据库**（SPD，Security Policy Database）的数据结构。SPD 指明哪些类型的数据报（按源 IP 地址、目的 IP 地址与协议类型区分）应经 IPsec 处理，以及对这些应经 IPsec 处理的数据报该用哪个 SA。某种意义上，SPD 中的信息指明对到来的数据报"做什么"，SAD 中的信息指明"怎么做"。

### IPsec 服务小结

那么 IPsec 究竟提供哪些服务？从攻击者 Trudy 的视角来考察这些服务——假设 Trudy 是坐在图 8.28 中 R1 与 R2 之间某处的中间人，并且始终假设 Trudy 不知道该 SA 使用的鉴别密钥与加密密钥。Trudy 能做什么、不能做什么？第一，Trudy 看不到原始数据报。事实上，不仅原始数据报中的数据对她隐藏，连协议号、源 IP 地址与目的 IP 地址也一并隐藏。对于在该 SA 上发送的数据报，Trudy 只知道它源自 200.168.1.100、目的为 193.68.2.23；她不知道它载的是 TCP、UDP 还是 ICMP 数据，也不知道它载的是 HTTP、SMTP 还是别的应用数据。可见这里的机密性比 TLS 走得远得多。第二，假设 Trudy 试图通过翻转某些比特来篡改该 SA 中的数据报。这个被篡改的数据报到达 R2 时会通不过（用 MAC 做的）完整性检验，Trudy 的恶毒企图再次落空。第三，假设 Trudy 试图冒充 R1，构造一个源为 200.168.1.100、目的为 193.68.2.23 的 IPsec 数据报。她的攻击同样徒劳，因为这个数据报在 R2 处仍将通不过完整性检验。最后，由于 IPsec 包含序号，Trudy 也无法成功实施重放攻击。总之，如本节开头所声称的，IPsec 在**任何一对经网络层处理分组的设备之间**提供机密性、源鉴别、数据完整性与防重放攻击。

## 8.7.5　IKE：IPsec 中的密钥管理

当一个 VPN 只有少量端点时（例如图 8.28 中只有两台路由器），网络管理员可以手工把 SA 信息（加密/鉴别算法与密钥、以及 SPI）录入各端点的 SAD。对于可能有数百甚至数千台 IPsec 路由器与主机的大型 VPN，这种"手工密钥"显然不切实际。大型、地理上分散的部署需要自动创建 SA 的机制。IPsec 用**因特网密钥交换**（IKE）协议完成这件事，该协议由 RFC 5996 规定。

IKE 与 TLS 的握手（见 8.6 节）有些相似。每个 IPsec 实体都有一份证书，其中包含该实体的公钥。与 TLS 一样，IKE 协议让两个实体交换证书、协商鉴别与加密算法，并安全地交换用于在 IPsec SA 中创建会话密钥的密钥材料。与 TLS 不同的是，IKE 用**两个阶段**来完成这些任务。

下面结合图 8.28 中两台路由器 R1 与 R2 来考察这两个阶段。第一阶段由 R1 与 R2 之间两轮"报文对"交换组成：

- 在第一轮报文交换中，双方用 Diffie-Hellman（见本章习题）在两台路由器之间创建一个**双向 IKE SA**。为把大家彻底绕晕，这个双向 IKE SA 与 8.7.3、8.7.4 节讨论的 IPsec SA 完全是两回事。IKE SA 为两台路由器之间提供一条经鉴别并加密的信道。在这第一轮报文对交换中，为 IKE SA 建立了加密与鉴别密钥，同时也建立了一个主秘密，供第二阶段计算 IPsec SA 密钥时使用。注意在这一步中并未使用 RSA 公私钥——特别是 R1 与 R2 都没有通过用私钥签署报文来暴露自己的身份。
- 在第二轮报文交换中，双方通过签署报文向对方暴露自己的身份。但由于报文是在受保护的 IKE SA 信道上发送的，身份并不会暴露给被动的嗅探者。同样在这一阶段，双方协商 IPsec SA 将采用的 IPsec 加密与鉴别算法。

在 IKE 第二阶段，双方各建立一个方向的 SA。第二阶段结束时，双方的这两个 SA 都已建立好加密与鉴别会话密钥。此后双方就可以按 8.7.3、8.7.4 节所述，用这些 SA 发送受保护的数据报。IKE 采用两个阶段的主要动机是计算开销——由于第二阶段不涉及任何公钥密码学，IKE 能以相对很小的计算开销在两个 IPsec 实体之间生成大量 SA。
