早在 1.6 节，我们描述过几类较为常见且危害较大的因特网攻击，包括恶意软件攻击、拒绝服务、嗅探、源伪装，以及报文的修改与删除。此后我们学到了大量关于计算机网络的知识，但还没有考察如何保护网络免遭这些攻击。如今，带着新获得的计算机网络与因特网协议专长，我们深入研习安全通信——特别是计算机网络如何防御那些坏家伙。

先介绍 Alice 与 Bob：两人想通信，并且希望"安全地"通信。既然这是一本网络教材，我们应当说明：Alice 与 Bob 可以是两台想安全交换路由表的路由器，可以是两个想建立安全运输连接的客户端与服务器，也可以是两个想交换安全电子邮件的应用——这些都是本章后面要考察的案例。Alice 与 Bob 是安全界众所周知的固定角色，也许因为他们的名字比"想与实体 B 安全通信的实体 A"更有趣。爱情、战时通信与商业交易是人们常引用的安全通信的人类需求；相比后两者，我们更喜欢第一个，于是乐于用 Alice 与 Bob 作为发送方与接收方，并想象他们处于第一种场景。

我们说 Alice 与 Bob 想"安全地"通信，但这究竟意味着什么？我们将会看到，安全（就像爱情）是件多姿多彩的事，也就是说，安全有许多侧面。当然，Alice 与 Bob 希望他们通信的内容对窃听者保密；他们大概也希望确保自己在与对方通信时，对方确实是对方，而且如果通信被窃听者篡改，这种篡改能被检测出来。本章第一部分讲支撑加密通信、鉴别通信对方以及保证报文完整性的基础密码学技术。

本章第二部分考察如何用基础密码学原理构造安全的网络协议。我们再次采取自顶向下的方法，考察（上面四个）每一层中的安全协议，从应用层开始：如何保护电子邮件、如何保护 TCP 连接、如何在网络层提供"全覆盖"安全，以及如何保护无线局域网。本章第三部分讨论**运行安全**（operational security），即保护组织网络免遭攻击；我们将仔细考察防火墙与入侵检测系统如何增强组织网络的安全性。

## 8.1　什么是网络安全？

我们从那对恋人 Alice 与 Bob 说起——他们想"安全地"通信。这究竟意味着什么？当然，Alice 希望只有 Bob 能看懂她发出的报文，即使他们是在不安全的介质上通信、入侵者（Trudy，那个入侵者）可以截获 Alice 发给 Bob 的任何东西。Bob 也希望确认他从 Alice 收到的报文确实是 Alice 发的，而 Alice 希望确认与她通信的人确实是 Bob。Alice 与 Bob 还希望确保他们报文的内容在传输中没有被改动。他们还希望能通信得起来（即没有人剥夺他们访问通信所需资源的权利）。基于这些考虑，可以识别出安全通信的以下理想性质。

- **机密性**（confidentiality）。只有发送方与预期接收方能看懂所传报文的内容。由于窃听者可能截获报文，这必然要求报文以某种方式**加密**，使截获的报文无法被截获者看懂。机密性这一侧面大概是"安全通信"一词最常被理解的含义。我们将在 8.2 节研究加密与解密数据的密码学技术。
- **报文完整性**（message integrity）。Alice 与 Bob 希望确保其通信内容在传输中未被改动，无论是恶意改动还是意外改动。对我们在可靠运输与数据链路协议中遇到的校验和技术加以扩展，就可以提供这种报文完整性。我们将在 8.3 节研究报文完整性。
- **端点鉴别**（end-point authentication）。发送方与接收方都应能确认通信对方的身份——确认对方确实是其所声称的那个人或那个东西。面对面的人际交流靠视觉识别轻易解决了这个问题；而当通信实体在彼此看不见的介质上交换报文时，鉴别就不那么简单了。当用户想访问自己的收件箱时，邮件服务器如何核实该用户就是他自称的那个人？我们将在 8.4 节研究端点鉴别。
- **运行安全**（operational security）。今天几乎所有组织（公司、大学等）的网络都连接到公共因特网，因此这些网络都可能被攻陷。攻击者可能试图向网络中的主机植入蠕虫、获取企业机密、测绘内部网络配置，并发起 DoS 攻击。我们将在 8.9 节看到，防火墙与入侵检测系统这类运行设备被用来对抗针对组织网络的攻击：防火墙位于组织网络与公共网络之间，控制进出该网络的分组访问；入侵检测系统执行"深度分组检查"，就可疑活动向网络管理员告警。

明确了网络安全的含义，接下来考虑入侵者究竟能接触到哪些信息、能采取哪些动作。图 8.1 说明了这个场景。发送方 Alice 想向接收方 Bob 发送数据。为在满足机密性、端点鉴别与报文完整性要求的前提下安全地交换数据，Alice 与 Bob 将交换控制报文与数据报文（很像 TCP 发送方与接收方交换控制报文段与数据报文段）。这些报文的全部或一部分通常会被加密。如 1.6 节所述，入侵者可能进行

- **窃听**——在信道上嗅探并记录控制报文与数据报文；
- **修改、插入或删除**报文或报文内容。

我们将会看到，除非采取适当的对抗措施，这些能力使入侵者能够发动各种各样的安全攻击：窥探通信（可能窃取口令与数据）、冒充另一实体、劫持正在进行的会话、通过压垮系统资源来拒绝向合法网络用户提供服务，等等。这类脆弱性的汇总见 CERT 协调中心 [CERT 2025]。

<Figure src="ch08/fig8-01.webp" caption="图 8.1　发送方、接收方与入侵者（Alice、Bob 与 Trudy）" />

既然因特网中确实存在真实的威胁，那么我们需要安全通信的"Alice 与 Bob"在因特网中的对应物是什么？当然，Bob 与 Alice 可以是两个端系统上的人类用户——例如真实的 Alice 与真实的 Bob 确实想交换安全电子邮件；他们也可能是电子商务交易的参与者，例如真实的 Bob 想在网上购物时把信用卡号安全地传给某台 Web 服务器，真实的 Alice 想与她的银行在线交互。需要安全通信的各方也可能本身就是网络基础设施的一部分。回忆域名系统（DNS，2.4 节）或交换路由信息的路由守护程序（第 5 章）都需要两方之间的安全通信；网络管理应用（第 5 章考察的话题）也是如此。一个能主动干扰 DNS 查询（2.4 节）、路由计算（5.3、5.4 节）或网络管理功能（5.5、5.7 节）的入侵者，能在因特网中造成严重破坏。

至此我们确立了框架、几个最重要的定义以及网络安全的必要性，接下来深入密码学。密码学在提供机密性方面的用途不言自明；但我们很快就会看到，它对提供端点鉴别与报文完整性也至关重要——这使密码学成为网络安全的基石。

## 8.2　密码学原理

密码学的历史至少可追溯到尤利乌斯·凯撒，但现代密码学技术（包括因特网中使用的许多技术）基于过去 30 年的进展。Kahn 的《破译者》[Kahn 1967] 与 Singh 的《密码故事：从古埃及到量子密码学的保密科学》[Singh 1999] 对密码学的漫长历史作了引人入胜的梳理。完整讨论密码学本身需要一整本书 [Kaufman 2002; Ferguson 2010; Bishop 2018]，因此这里只触及密码学的本质方面，特别是它在因特网中的实践。还要指出，虽然本节聚焦密码学在机密性方面的用途，但很快会看到密码学技术不可分割地织入了鉴别、报文完整性与不可否认性等等之中。

密码学技术使发送方能伪装数据，使入侵者无法从截获的数据中获得任何信息；接收方当然必须能从伪装后的数据恢复原始数据。图 8.2 说明了其中一些重要术语。

<Figure src="ch08/fig8-02.webp" caption="图 8.2　密码学组件" />

假设 Alice 想给 Bob 发报文。Alice 的报文在其原始形态（例如"Bob, I love you. Alice"）称为**明文**（plaintext）或 **cleartext**。Alice 用**加密算法**加密她的明文报文，使加密后的报文——称为**密文**（ciphertext）——对任何入侵者都显得不可理解。有意思的是，在许多现代密码系统（包括因特网中使用的那些）里，加密技术本身是**公开**的——已发表、已标准化、人人可得（例如 [RFC 1321; RFC 3447; RFC 2420; NIST 2001, 2025]），连潜在的入侵者也能拿到！显然，如果人人都知道编码数据的方法，那就必须有某种**秘密信息**来阻止入侵者解密所传数据——这就是**密钥**的用武之地。

图 8.2 中，Alice 提供一个密钥 $K_{A}$（一串数字或字符）作为加密算法的输入。加密算法以密钥与明文报文 $m$ 为输入，输出密文。记号 $K_{A}(m)$ 表示明文报文 $m$ 的密文形式（用密钥 $K_{A}$ 加密）。使用密钥 $K_{A}$ 的具体加密算法从上下文即可看出。类似地，Bob 向解密算法提供密钥 $K_{B}$，解密算法以密文与 Bob 的密钥为输入，输出原始明文。也就是说，若 Bob 收到加密报文 $K_{A}(m)$，他通过计算 $K_{B}(K_{A}(m)) = m$ 来解密。在**对称密钥**系统中，Alice 与 Bob 的密钥相同且保密。在**公钥**系统中使用一对密钥：其中一个密钥 Bob 与 Alice 都知道（事实上全世界都知道），另一个密钥只有 Bob 或只有 Alice 知道（而不是两人都知道）。下面两小节更详细地考察对称密钥系统与公钥系统。

### 8.2.1　对称密钥密码学

所有密码算法都涉及用一物替代另一物——例如取一段明文，计算并替换为相应的密文，从而造出加密报文。在研究现代基于密钥的密码系统之前，先用一个非常古老、非常简单的对称密钥算法"热热身"：据传出自尤利乌斯·凯撒的**凯撒密码**（cipher 即加密数据的方法）。

对英文文本，凯撒密码把明文中每个字母替换为字母表中其后第 $k$ 个字母（允许回绕，即 z 之后是 a）。例如若 $k = 3$，则明文中的 a 在密文中变成 d，b 变成 e，依此类推。这里 $k$ 的值就是密钥。例如明文"bob, i love you. Alice"变成密文"ere, l oryh brx. dolfh"。密文确实看起来像乱码，但如果你知道用的是凯撒密码，破译它并不需要多久——因为只有 25 个可能的密钥值。

凯撒密码的一种改进是**单表替换密码**（monoalphabetic cipher），它同样用一个字母替换另一个字母；但与按规则模式（例如所有字母都偏移 $k$）替换不同，任何字母都可以替换任何其他字母，只要每个字母有唯一的替换字母、反之亦然。图 8.3 中的替换规则给出了编码明文的一种可能规则。

<Figure src="ch08/fig8-03.webp" caption="图 8.3　一种单表替换密码" />

明文"bob, i love you. Alice"变成"nkn, s gktc wky. Mgsbc."。于是，与凯撒密码一样，这看起来像乱码。单表替换密码似乎也比凯撒密码更好：可能的字母配对有 $26 !$（约 $10^{26}$）种，而不是 25 种。暴力尝试全部 $10^{26}$ 种配对所需的计算量太大，不可能成为破解加密算法、解出报文的可行途径。然而，通过对明文语言作统计分析——例如知道字母 e 与 t 在典型英文文本中出现最频繁（分别占字母出现次数的 13% 与 9%），并知道某些特定的两字母、三字母组合经常一起出现（如 "in"、"it"、"the"、"ion"、"ing" 等）——就比较容易破译这种密码。如果入侵者对报文可能的内容有所了解，破译就更容易。例如，若入侵者 Trudy 是 Bob 的妻子，怀疑 Bob 与 Alice 有婚外情，她可能猜到文中会出现"bob"与"alice"这两个名字。如果 Trudy 确知这两个名字出现在密文中，并且手里有上面那条示例密文，她就能立刻确定 26 个字母配对中的 7 个，使暴力法需要检查的可能性减少 $10^{9}$ 倍。确实，如果 Trudy 怀疑 Bob 有婚外情，她很可能还期望在报文中找到其他一些"关键"词。

在考虑 Trudy 破解 Bob 与 Alice 加密方案的难易程度时，可以根据入侵者掌握的信息区分三种不同情形：

- **唯密文攻击**（ciphertext-only attack）。有些情况下，入侵者只能接触到截获的密文，对明文内容没有确定信息。我们已经看到统计分析如何有助于对加密方案实施唯密文攻击。
- **已知明文攻击**（known-plaintext attack）。上面看到，如果 Trudy 以某种方式确知"bob"与"alice"出现在密文报文中，她就能确定字母 a、l、i、c、e、b、o 的（明文，密文）配对。Trudy 也可能运气好，记录下全部密文传输，然后在某张纸上发现了 Bob 自己写下的其中某次传输的解密版本。当入侵者知道某些（明文，密文）配对时，我们称这是对加密方案的**已知明文攻击**。
- **选择明文攻击**（chosen-plaintext attack）。在选择明文攻击中，入侵者能够选择明文报文并取得其相应的密文形式。对迄今见过的简单加密算法，如果 Trudy 能让 Alice 发送"The quick brown fox jumps over the lazy dog"这条报文，她就能完全破解该加密方案。我们很快就会看到，对更精巧的加密技术，选择明文攻击并不一定意味着加密技术能被破解。

五百年前，人们发明了改进单表替换加密的技术，称为**多表替换加密**（polyalphabetic encryption）。其思想是使用多个单表替换密码，用某个特定的单表替换密码来编码明文报文中某个特定位置上的字母。于是同一个字母出现在明文报文的不同位置时，可能被编码成不同结果。图 8.4 给出一个多表替换加密方案的例子：它有两行凯撒密码（$k = 5$ 与 $k = 19$）。我们可以选择以重复模式 $C_{1}, C_{2}, C_{2}, C_{1}, C_{2}$ 使用这两个凯撒密码 $C_{1}$ 与 $C_{2}$——即明文的第一个字母用 $C_{1}$ 编码，第二、三个用 $C_{2}$，第四个用 $C_{1}$，第五个用 $C_{2}$，然后模式重复，第六个字母用 $C_{1}$、第七个用 $C_{2}$，依此类推。于是明文"bob, i love you."被加密为"ghu, n etox dhz."。注意明文中第一个 b 用 $C_{1}$ 加密，而第二个 b 用 $C_{2}$ 加密。这个例子中，加密与解密的"密钥"是关于两个凯撒密钥（$k_{1} = 5$、$k_{2} = 19$）以及模式 $C_{1}, C_{2}, C_{2}, C_{1}, C_{2}$ 的知识。

#### 块密码

现在进入现代，考察今天对称密钥加密是如何做的。我们聚焦**块密码**（block cipher），它用于许多安全的因特网协议，包括 PGP（安全电子邮件）、TLS（保护 TCP 连接）与 IPsec（保护网络层传输）。

在块密码中，待加密的报文按 $k$ 比特一块处理。例如若 $k = 64$，报文被切成 64 比特的块，每块独立加密。为编码一个块，密码用一一映射把 $k$ 比特明文块映射为 $k$ 比特密文块。看一个例子：假设 $k = 3$，块密码把 3 比特输入（明文）映射为 3 比特输出（密文），表 8.1 给出一种可能的映射。注意这是一一映射，即每个输入都有不同的输出。这个块密码把报文切成 3 比特的块，并按上表映射加密每一块。你应当验证报文 `010 110 001 111` 被加密为 `101 000 111 001`。

<p class="tbl-cap">表 8.1　一个具体的 3 比特块密码</p>

| **输入** | **输出** | **输入** | **输出** |
| --- | --- | --- | --- |
| 000 | 110 | 100 | 011 |
| 001 | 111 | 101 | 010 |
| 010 | 101 | 110 | 000 |
| 011 | 100 | 111 | 001 |

继续这个 3 比特块的例子。注意表 8.1 中的映射只是众多可能映射之一。共有多少种可能的映射？回答这个问题要注意：一个映射无非是对所有可能输入的一个**置换**。共有 $2^{3} = 8$ 个可能输入（列在输入栏下），这 8 个输入可以按 $8 ! = 40 320$ 种不同方式置换。既然每种置换都指定一个映射，就有 40 320 种可能映射。我们可以把每种映射看成一个**密钥**——如果 Alice 与 Bob 都知道该映射（密钥），他们就能加密和解密彼此发送的报文。

对这个密码的暴力攻击，就是尝试用所有映射来解密密文。由于只有 40 320 个映射（$k = 3$ 时），这在台式 PC 上很快就能完成。为挫败暴力攻击，块密码通常使用大得多的块，例如 $k = 64$ 比特甚至更大。注意一般 $k$ 比特块密码的可能映射数为 $2^{k} !$，即使 $k$ 取中等大小（如 64），这个数也是天文数字。

<Figure src="ch08/fig8-05.webp" caption="图 8.5　一个块密码的例子" />

虽然如上面所述、$k$ 取中等大小时全表块密码可以产生健壮的对称密钥加密方案，但它们不幸难以实现。对 $k = 64$ 且给定映射，Alice 与 Bob 需要维护一张有 $2^{64}$ 个输入值的表，这是不可能完成的任务。而且，若 Alice 与 Bob 要更换密钥，他们各自还得重新生成该表。因此，提供所有输入输出之间预定映射的**全表**块密码（如上面例子）根本不可行。

因此，块密码通常使用**模拟随机置换表**的函数。图 8.5 给出 $k = 64$ 比特时这样一个函数的例子（改编自 [Kaufman 2002]）。该函数先把 64 比特块分成 8 块，每块 8 比特；每个 8 比特块经一张 8 比特到 8 比特的表处理（规模可管理），例如第一块由记为 $T_{1}$ 的表处理。接着把 8 个输出块重新组装成一个 64 比特块，然后把该块中 64 个比特的位置打乱（置换），产生 64 比特输出。这个输出再被反馈为 64 比特输入，开始下一轮；经过 $n$ 轮这样的循环后，函数给出 64 比特密文块。**轮**（round）的作用是让每个输入比特影响大多数（如果不是全部）最终输出比特。（若只做一轮，某个输入比特只影响 64 个输出比特中的 8 个。）这个块密码算法的密钥就是那八张置换表（假定打乱函数是公开的）。

今天有多种流行的块密码，包括 DES（数据加密标准）、3DES 与 AES（高级加密标准）。这些标准都使用类似图 8.5 的函数而非预定表（尽管更复杂、且各自不同）。这些算法也都使用一串比特作为密钥：例如 DES 使用 64 比特块与 56 比特密钥；AES 使用 128 比特块，可用 128、192 与 256 比特长的密钥。算法的密钥决定算法内部具体的"迷你表"映射与置换。对这些密码的暴力攻击就是遍历所有密钥、用每个密钥执行解密算法。注意密钥长度为 $n$ 时有 $2^{n}$ 个可能密钥。NIST [NIST 2001] 估计，一台能在一秒内破解 56 比特 DES（即一秒内试完 $2^{56}$ 个密钥）的机器，破解 128 比特 AES 密钥大约需要 149 万亿年。

#### 密码块链接

在计算机网络应用中，我们通常需要加密长报文或长数据流。若按上面所述简单地应用块密码——把报文切成 $k$ 比特块并独立加密每块——会出现一个微妙而重要的问题。要看清这一点，注意两个或更多明文块可能完全相同，例如两个或更多块的明文都可能是 "HTTP 1.1"。对这些相同的块，块密码当然会产生相同的密文。攻击者看到相同的密文块时可能猜出明文，甚至可能通过识别相同密文块、利用对底层协议结构的知识来解密整个报文 [Kaufman 2002]。

为解决这个问题，我们可以在密文中混入一些随机性，使相同的明文块产生不同的密文块。设 $m(i)$ 表示第 $i$ 个明文块，$c(i)$ 表示第 $i$ 个密文块，$a \oplus b$ 表示两个比特串 $a$ 与 $b$ 的**异或**（XOR）。（回忆 $0 \oplus 0 = 1 \oplus 1 = 0$，$0 \oplus 1 = 1 \oplus 0 = 1$，两个比特串的异或按位进行。例如 `10101010` $\oplus$ `11110000` = `01011010`。）再记密钥为 $S$ 的块密码加密算法为 $K_{S}$。基本思想如下：发送方为第 $i$ 块生成一个随机 $k$ 比特数 $r(i)$，并计算

$$
c(i) = K_{S}(m(i) \oplus r(i))
$$

注意每一块都重新选一个 $k$ 比特随机数。发送方随后发送 $c(1), r(1), c(2), r(2), c(3), r(3)$ 等等。由于接收方收到 $c(i)$ 与 $r(i)$，它可以通过计算 $m(i) = K_{S}(c(i)) \oplus r(i)$ 恢复每个明文块。要特别注意：虽然 $r(i)$ 以明文发送、因而可被 Trudy 嗅探，但她无法得到明文 $m(i)$，因为她不知道密钥 $K_{S}$。还注意若两个明文块 $m(i)$ 与 $m(j)$ 相同，对应密文块 $c(i)$ 与 $c(j)$ 会不同（只要随机数 $r(i)$ 与 $r(j)$ 不同，而这以极高概率成立）。

举例来说，考虑表 8.1 中的 3 比特块密码。假设明文为 `010 010 010`。若 Alice 不引入随机性直接加密，得到的密文是 `101 101 101`。若 Trudy 嗅探到这个密文，由于三个密文块都相同，她可以正确推断三个明文块都相同。现在假设 Alice 生成随机块 $r(1) =$ `001`、$r(2) =$ `111`、$r(3) =$ `100`，并用上述技术生成密文 $c(1) =$ `100`、$c(2) =$ `010`、$c(3) =$ `000`。注意尽管明文块相同，三个密文块却不同。Alice 随后发送 $c(1), r(1), c(2), r(2)$ 等等。你应当验证 Bob 能用共享密钥 $K_{S}$ 得到原始明文。

细心的读者会注意到，引入随机性解决了一个问题却带来了另一个问题：Alice 必须发送两倍的比特数。确实，对每个密文比特，她现在还必须发送一个随机比特，使所需带宽翻倍。为了"既要有蛋糕又要吃掉蛋糕"，块密码通常使用一种称为**密码块链接**（Cipher Block Chaining，CBC）的技术。其基本思想是：只随第一条报文发送一个随机值，随后让发送方与接收方用已算出的密文块代替后续的随机数。具体地说，CBC 的工作方式如下：

1. 加密报文（或数据流）之前，发送方生成一个随机 $k$ 比特串，称为**初始向量**（Initialization Vector，IV），记为 $c(0)$。发送方以明文把 IV 发给接收方。
1. 对第一块，发送方计算 $m(1) \oplus c(0)$，即第一块明文与 IV 的异或；然后把结果送入块密码算法，得到相应密文块，即 $c(1) = K_{S}(m(1) \oplus c(0))$。发送方把加密块 $c(1)$ 发给接收方。
1. 对第 $i$ 块，发送方由 $c(i) = K_{S}(m(i) \oplus c(i - 1))$ 生成第 $i$ 个密文块。

下面考察这种做法的一些后果。第一，接收方仍能恢复原始报文：收到 $c(i)$ 后，它用 $K_{S}$ 解密得到 $s(i) = m(i) \oplus c(i - 1)$；由于接收方也知道 $c(i - 1)$，它随后由 $m(i) = s(i) \oplus c(i - 1)$ 得到明文块。第二，即使两个明文块相同，对应密文（几乎总是）不同。第三，虽然发送方以明文发送 IV，入侵者仍无法解密密文块，因为入侵者不知道密钥 $S$。最后，发送方只多送一个块（IV），对由数百块组成的长报文而言，带宽增加的幅度可以忽略。

举例来说，现在为表 8.1 中的 3 比特块密码确定明文 `010 010 010`、$c(0) =$ `IV` $=$ `001` 时的密文。发送方先用 IV 计算 $c(1) = K_{S}(m(1) \oplus c(0)) =$ `100`；然后计算 $c(2) = K_{S}(m(2) \oplus c(1)) = K_{S}()$`010` $\oplus$ `100`$=$ `000`，以及 $c(3) = K_{S}(m(3) \oplus c(2)) = K_{S}()$`010` $\oplus$ `000`$=$ `101`。读者应当验证：知道 IV 与 $K_{S}$ 的接收方能恢复原始明文。

CBC 在设计安全网络协议时有一个重要后果：我们必须在协议中提供把 IV 从发送方分发到接收方的机制。本章后面会看到几个协议是如何做到这一点的。

### 8.2.2　公钥密码学

两千多年来（从凯撒密码时代直到 20 世纪 70 年代），加密通信要求通信双方共享一个秘密——用于加密与解密的对称密钥。这种途径的一个困难是：双方必须以某种方式就共享密钥达成一致，而要做到这一点本身就需要安全通信。也许双方可以先见面、当面商定密钥（例如凯撒的两名百夫长可以在罗马浴场碰面），此后便可用加密通信。但在网络世界里，通信双方可能永远不见面，除了通过网络之外可能永远不交谈。

两方能否在没有预先共享秘密密钥的情况下进行加密通信？1976 年，Diffie 与 Hellman [Diffie 1976] 演示了一个算法（现在称为 **Diffie-Hellman 密钥交换**）正是做这件事——一种截然不同、精妙优雅的安全通信途径，它促成了今天公钥密码系统的发展。我们很快就会看到，公钥密码系统还有若干美妙性质，使其不仅可用于加密，还可用于鉴别与数字签名。有意思的是，后来发现与 [Diffie 1976] 和 [RSA 1978] 类似的思想，早在 20 世纪 70 年代初就由英国通信电子安全组的研究者在一系列秘密报告中独立提出 [Ellis 1987]。正如常有的事，伟大的思想会在许多地方独立萌发；幸运的是，公钥的进展不仅发生在私下，也发生在公众视野之中。

公钥密码学的使用在概念上相当简单。假设 Alice 想与 Bob 通信。如图 8.6 所示，Bob 与 Alice 并不共享单一秘密密钥（如对称密钥系统那样），而是由 Bob（Alice 报文的接收者）持有两个密钥——一个全世界（包括入侵者 Trudy）都可获得的**公钥**，和一个只有 Bob 知道的**私钥**。我们用 $K_{B}^{+}$ 与 $K_{B}^{-}$ 分别表示 Bob 的公钥与私钥。为与 Bob 通信，Alice 先取得 Bob 的公钥，然后用 Bob 的公钥与一个已知（例如标准化的）加密算法加密她要发给 Bob 的报文 $m$，即 Alice 计算 $K_{B}^{+}(m)$。Bob 收到 Alice 的加密报文后，用他的私钥与一个已知（例如标准化的）解密算法解密，即 Bob 计算 $K_{B}^{-}(K_{B}^{+}(m))$。下面会看到，存在这样的加解密算法与公私钥选取技术，使得 $K_{B}^{-}(K_{B}^{+}(m)) = m$；也就是说，对报文 $m$ 施加 Bob 的公钥 $K_{B}^{+}$（得到 $K_{B}^{+}(m)$），再对 $m$ 的加密版本施加 Bob 的私钥 $K_{B}^{-}$（即计算 $K_{B}^{-}(K_{B}^{+}(m))$），会还原出 $m$。这是个非凡的结果！这样，Alice 就能用 Bob 公开可得的密钥给 Bob 发送秘密报文，而双方都不必分发任何秘密密钥！很快会看到，我们还可以把公钥与私钥的加密次序对调而得到同样非凡的结果——即 $K_{B}^{+}(K_{B}^{-}(m)) = K_{B}^{-}(K_{B}^{+}(m)) = m$。

<Figure src="ch08/fig8-06.webp" caption="图 8.6　公钥密码学" />

虽然公钥密码学很有吸引力，但一个担忧立刻浮现：既然 Bob 的加密密钥是公开的，任何人都能给 Bob 发送加密报文，包括 Alice，也包括某个冒充 Alice 的人。在单一共享秘密密钥的情形下，发送方知道秘密密钥这一事实本身就向接收方隐含地标识了发送方；而在公钥密码学中不再如此，因为任何人都能用 Bob 公开可得的密钥给 Bob 发送加密报文。这时就需要**数字签名**（8.3 节研究的话题）来把发送方与报文绑定起来。

#### RSA

虽然可能有许多算法应对这些关切，但 **RSA** 算法（以其创始人 Ron Rivest、Adi Shamir 与 Leonard Adleman 命名）几乎已成为公钥密码学的同义词。先看 RSA 如何工作，再考察它为何有效。

RSA 大量使用模 $n$ 算术运算。先简要回顾模算术：$x \bmod n$ 就是 $x$ 除以 $n$ 的余数，例如 $19 \bmod 5 = 4$。在模算术中照常做加、乘与幂运算，但每次运算的结果都替换为除以 $n$ 后留下的整数余数。模算术中的加法与乘法可由以下几条有用事实简化：

$(a \bmod n) + (b \bmod n) \bmod n = (a + b) \bmod n$
  
  $(a \bmod n) - (b \bmod n) \bmod n = (a - b) \bmod n$
  
  $(a \bmod n) \times (b \bmod n) \bmod n = (a \times b) \bmod n$

由第三条事实可得 $(a \bmod n)^{d} \bmod n = a^{d} \bmod n$，这个恒等式我们很快会用到。

现在假设 Alice 想给 Bob 发送一条 RSA 加密报文，如图 8.6 所示。讨论 RSA 时始终要记住：报文无非是一个比特图案，而每个比特图案都能被唯一地表示为一个整数（连同比特图案的长度）。例如，若报文是比特图案 `1001`，它可表示为十进制整数 9。因此用 RSA 加密报文，等价于加密代表该报文的那个唯一整数。

RSA 有两个相互关联的组成部分：

- 公钥与私钥的选取；
- 加密与解密算法。

为生成 RSA 公私钥，Bob 执行以下步骤：

1. 选两个大素数 $p$ 与 $q$。$p$ 与 $q$ 该多大？值越大，RSA 越难被破解，但编解码耗时也越长。RSA 实验室建议 $p$ 与 $q$ 的乘积在 1 024 比特量级。如何寻找大素数见 [Prime 2025]。
1. 计算 $n = p q$ 与 $z = (p - 1)(q - 1)$。
1. 选一个小于 $n$ 的数 $e$，使它与 $z$ 没有（除 1 以外的）公因子（此时称 $e$ 与 $z$ **互素**）。用字母 $e$ 是因为该值将用于加密。
1. 找一个数 $d$，使 $e d - 1$ 恰好能被 $z$ 整除（即无余数）。用字母 $d$ 是因为该值将用于解密。换言之，给定 $e$，我们选 $d$ 使

$$
e d \bmod z = 1
$$

1. Bob 向全世界公开的公钥 $K_{B}^{+}$ 是数对 $(n, e)$；他的私钥 $K_{B}^{-}$ 是数对 $(n, d)$。

Alice 的加密与 Bob 的解密如下进行：

- 假设 Alice 想给 Bob 发送由整数 $m$ 表示的比特图案（$m < n$）。为编码，Alice 计算 $m$ 的 $e$ 次幂，再求 $m^{e}$ 除以 $n$ 的整数余数。换句话说，Alice 明文报文 $m$ 的加密值 $c$ 为

$$
c = m^{e} \bmod n
$$

- 与该密文 $c$ 对应的比特图案被发送给 Bob。
- 为解密收到的密文 $c$，Bob 计算

$$
m = c^{d} \bmod n
$$

这需要用到他的私钥 $(n, d)$。

作为 RSA 的一个简单例子，假设 Bob 选 $p = 5$、$q = 7$（诚然，这些值太小，远不安全），则 $n = 35$、$z = 24$。Bob 选 $e = 5$，因为 5 与 24 没有公因子。最后 Bob 选 $d = 29$，因为 $5 \times 29 - 1$（即 $e d - 1$）恰好能被 24 整除。Bob 公开 $n = 35$ 与 $e = 5$ 两个值，并保密 $d = 29$。看到这两个公开值后，假设 Alice 想给 Bob 发送字母 l、o、v、e。把每个字母解释为 1 到 26 之间的数（a 为 1，z 为 26），Alice 与 Bob 分别执行表 8.2 与表 8.3 所示的加密与解密。注意这个例子中我们把四个字母各当作一条独立报文；更现实的例子是把四个字母转成 8 比特 ASCII 表示，再加密所得 32 比特图案对应的整数（这样的现实例子产生的数太长，无法印在教材里！）。

#### 会话密钥

这里要指出，RSA 所需的幂运算相当耗时。因此实践中 RSA 常与对称密钥密码学结合使用。例如，若 Alice 想给 Bob 发送大量加密数据，她可以这样做：首先 Alice 选一个用于编码数据本身的密钥，称为**会话密钥**（session key），记为 $K_{S}$。Alice 必须把会话密钥告知 Bob，因为这是他们将用对称密钥密码（如 DES 或 AES）共享的对称密钥。Alice 用 Bob 的公钥加密会话密钥，即计算 $c = K_{S}^{e} \bmod n$。Bob 收到 RSA 加密的会话密钥 $c$ 并解密，得到会话密钥 $K_{S}$。Bob 现在知道了 Alice 将用于其加密数据传输的会话密钥。

#### RSA 为何有效？

RSA 的加解密看起来相当神奇。为什么先施加加密算法、再施加解密算法就能恢复原始报文？为理解 RSA 为何有效，再次记 $n = p q$，其中 $p$ 与 $q$ 是 RSA 算法所用的大素数。回忆在 RSA 加密下，报文（由整数唯一表示）$m$ 用模 $n$ 算术求 $e$ 次幂，即 $c = m^{e} \bmod n$。解密则用模 $n$ 算术把这个值求 $d$ 次幂。因此加密一步再解密一步的结果是 $(m^{e} \bmod n)^{d} \bmod n$。来看看关于这个量能说什么。如前面所述，模算术有一个重要性质：对任意 $a$、$n$、$d$，有 $(a \bmod n)^{d} \bmod n = a^{d} \bmod n$。于是取 $a = m^{e}$ 代入该性质，得

$$
(m^{e} \bmod n)^{d} \bmod n = m^{e d} \bmod n
$$

因此剩下的就是证明 $m^{e d} \bmod n = m$。虽然我们想为 RSA 去掉一些"魔法"，但要确立这一点，还得用一个相当神奇的数论结果：若 $p$ 与 $q$ 为素数、$n = p q$、$z = (p - 1)(q - 1)$，则 $x^{y} \bmod n$ 与 $x^{y \bmod z} \bmod n$ 相同 [Kaufman 2002]。把该结果用于 $x = m$、$y = e d$，得

$$
m^{e d} \bmod n = m^{e d \bmod z} \bmod n
$$

但记住我们选取 $e$ 与 $d$ 时使 $e d \bmod z = 1$。于是

$$
m^{e d} \bmod n = m^{1} \bmod n = m
$$

这正是我们要的结果！先求 $e$ 次幂（加密）再求 $d$ 次幂（解密），就得到原始值 $m$。更美妙的是：若先求 $d$ 次幂再求 $e$ 次幂——即把加密与解密的次序颠倒，先执行解密操作再施加加密操作——同样得到原始值 $m$。这个美妙结果直接来自模算术：

$$
m^{d e} \bmod n = m^{e d} \bmod n = (m^{e} \bmod n)^{d} \bmod n = m
$$

近年来，**椭圆曲线密码学**（ECC）已成为公钥密码学中 RSA 的替代方案，两者的优缺点见 [Gupta 2002; VMware 2025]。RSA 的安全性依赖于：目前没有已知算法能把公开值 $n$ 快速分解为素数 $p$ 与 $q$。若某人知道了 $p$ 与 $q$，那么给定公开值 $e$，他就能轻易算出秘密密钥 $d$。另一方面，是否存在快速分解算法尚不可知；在这个意义上，RSA 的安全性并无保证。ECC 的安全性依赖于求解一个同样困难的问题。随着量子计算的最新进展以及已发表的量子计算机快速分解算法，人们担心 RSA 可能无法永远安全 [MIT TR 2019; RSA 2024]。虽然这些算法的实际实现看来仍遥遥无期，但对后量子时代现代密码学的担忧已相当严肃，以至于美国国家标准与技术研究院公开征集、评估并提出了三项抗量子公钥密码算法标准草案 [NIST 2025]。

#### 用公钥密码学协商共享密钥

后面几节会看到，公钥密码学不仅可用来提供加密服务，还可用来提供报文完整性、数字签名与鉴别。它还能为两个此前从未交互、因而无法事先选定共享秘密的通信实体派生一个对称密钥（共享秘密）。这在客户端-服务器应用中很有用——客户端与服务器想用共享对称密钥加密它们的交互。

做到这一点的方法称为 **Diffie-Hellman（DH）密钥协商协议**，以其发明者 Whitfield Diffie 与 Martin Hellman 命名。我们将在 8.6 节看到，DH 是用于保护因特网运输层通信的**运输层安全**（TLS）协议的核心组件。

DH 协议使用一个大素数 $p$ 与另一个小于 $p$ 的大数 $g$。Bob 或 Alice 选定 $p$ 与 $g$ 并公开其值，使双方（以及任何攻击者！）都知道。随后 Alice 与 Bob 各自独立选择私密值 $S_{A}$ 与 $S_{B}$。建议 $p$、$S_{A}$ 与 $S_{B}$ 的长度为 2 048 比特或更多。Alice 通过把 $g$ 求 $S_{A}$ 次幂再取模 $p$ 来计算她的公钥 $K_{A}^{+}$：

$$
K_{A}^{+} = g^{S_{A}} \bmod p
$$

Bob 类似地计算他自己的公钥 $K_{B}^{+}$：

$$
K_{B}^{+} = g^{S_{B}} \bmod p
$$

DH 的安全性依赖于：给定 $K_{A}^{+}$、$g$ 与 $p$，要确定上式中 $S_{A}$ 的值极其困难（确定 $S_{B}$ 同理）。确实，确定 $S_{A}$ 与 $S_{B}$ 的难度，与把 RSA 中的公开值 $n$ 分解为 RSA 素数 $p$ 与 $q$ 的难度相当。

现在看 Alice 与 Bob 如何在不显式交换共享秘密的情况下计算出共同的共享秘密。Alice 取人人皆知的 Bob 公钥 $K_{B}^{+}$，把它求她的秘密密钥 $S_{A}$ 次幂再取模 $p$：

$$
\text{Alice 算出的共享秘密} = (K_{B}^{+})^{S_{A}} \bmod p
$$

Bob 类似地计算：

$$
\text{Bob 算出的共享秘密} = (K_{A}^{+})^{S_{B}} \bmod p
$$

下面验证 Bob 与 Alice 确实算出同一个共享秘密——这里只需一点模算术的技巧。Alice 算出的共享密钥是 $(K_{B}^{+})^{S_{A}} \bmod p = (g^{S_{B}} \bmod p)^{S_{A}} \bmod p$，其中用了 $K_{B}^{+}$ 的定义。而按模算术规则，$(g^{S_{B}} \bmod p)^{S_{A}} \bmod p = g^{S_{B} S_{A}} \bmod p = g^{S_{A} S_{B}} \bmod p$。类似地，Bob 算出的共享密钥是 $(K_{A}^{+})^{S_{B}} \bmod p = (g^{S_{A}} \bmod p)^{S_{B}} \bmod p = g^{S_{A} S_{B}} \bmod p$，与 Alice 算出的共享密钥完全相同！

## 8.3　报文完整性与数字签名

上一节看到加密如何为两个通信实体提供机密性。本节转向另一个同等重要的密码学主题——**报文完整性**（message integrity，又称**报文鉴别**）。围绕报文完整性，本节还会讨论两个相关主题：**数字签名**（digital signature）与**端点鉴别**（end-point authentication）。

仍然用 Alice 与 Bob 来定义报文完整性问题。假设 Bob 收到一条报文（可能是密文，也可能是明文），并且相信这条报文是 Alice 发的。要鉴别这条报文，Bob 需要验证两件事：

1. 报文确实源自 Alice；
1. 报文在发往 Bob 的途中没有被篡改。

8.4 至 8.7 节会看到，报文完整性问题在几乎所有安全网络协议中都是关键关切。

举一个具体例子。考虑一个用链路状态路由算法（如 OSPF）确定每对路由器之间路由的计算机网络（见第 5 章）。在链路状态算法中，每台路由器都要向网络中所有其他路由器广播一条链路状态报文，其中包含其直连邻居的列表以及到这些邻居的直接代价。一旦收到所有其他路由器的链路状态报文，路由器就能构造出完整的网络拓扑图、运行最小代价路由算法、配置自己的转发表。针对路由算法的一种相对容易的攻击，就是 Trudy 分发带有错误链路状态信息的伪造链路状态报文。于是就有了报文完整性的需求——当路由器 B 收到路由器 A 的链路状态报文时，B 应当验证这条报文确实是 A 生成的，并且途中没有人改动过它。

本节介绍一种被许多安全网络协议采用的流行报文完整性技术。但在那之前，需要先讲密码学中另一个重要主题——**密码散列函数**。

### 8.3.1　密码散列函数

如图 8.7 所示，散列函数以 $m$ 为输入，计算出一个固定长度的串 $H(m)$，称为**散列**（hash）。第 3 章的因特网检验和与第 6 章的 CRC 都满足这个定义。而**密码散列函数**还要求具备如下附加性质：

- 要找到两条不同的报文 $x$ 与 $y$ 使得 $H(x) = H(y)$，在计算上是不可行的。

通俗地说，这条性质意味着：入侵者若想把一条受散列函数保护的报文替换成另一条报文，在计算上是不可行的。也就是说，若 $(m, H(m))$ 是发送方创建的报文及其散列，则入侵者无法伪造出另一条内容不同、散列值却与原文相同的报文 $y$。

下面来说明，像因特网检验和这样简单的检验和为什么不能充当密码散列函数。这里不做 1 的补码运算（因特网检验和的做法），而是把每个字符看成一个字节、每次按 4 字节一组相加来计算检验和。假设 Bob 欠 Alice 100.99 美元，于是给 Alice 发一张借条，文本为"IOU100.99BOB"。这些字符的 ASCII 表示（十六进制）是 49, 4F, 55, 31, 30, 30, 2E, 39, 39, 42, 4F, 42。

图 8.8 上半部分显示，这条报文的 4 字节检验和是 `B2 C1 D2 AC`。图的下半部分是一条略有不同（对 Bob 来说贵得多）的报文。"IOU100.99BOB"与"IOU900.19BOB"的检验和完全相同。可见这个简单检验和算法违反了上面那条要求：给定原始数据，很容易找出另一组具有相同检验和的数据。显然，出于安全目的，我们需要比检验和强大得多的散列函数。

<Figure src="ch08/fig8-08.webp" caption="图 8.8　初始报文与伪造报文的检验和相同！" />

<Figure src="ch08/fig8-07.webp" caption="图 8.7　散列函数" />

Ron Rivest 的 **MD5** 散列算法 [RFC 1321] 至今仍被广泛使用。它以四步过程计算出 128 比特的散列：填充（补一个 1 再补足够的 0，使报文长度满足特定条件）、追加（在填充前的报文长度之后追加其 64 比特表示）、初始化累加器，以及最后一个循环步骤——把报文的 16 字块分四轮处理（"捣碎"）。MD5 的描述（含一份 C 源码实现）见 [RFC 1321]。

今天在用的另一大散列算法是**安全散列算法**（SHA-1）[FIPS 1995]。该算法基于与 MD4 [RFC 1320]（MD5 的前身）相似的设计原理。SHA-1 是美国联邦标准，联邦应用中需要密码散列算法时必须使用它。它产生 160 比特的**报文摘要**（message digest）。更长的输出长度使 SHA-1 更为安全。

### 8.3.2　报文鉴别码

现在回到报文完整性问题。既然理解了散列函数，先来试一种最直接的做法：

1. Alice 创建报文 $m$，计算散列 $H(m)$（例如用 SHA-1）。
1. Alice 把 $H(m)$ 附在报文 $m$ 之后，构成扩展报文 $(m, H(m))$，发给 Bob。
1. Bob 收到扩展报文 $(m, h)$，计算 $H(m)$。若 $H(m) = h$，Bob 就认为一切正常。

这个做法显然有漏洞。Trudy 可以伪造一条报文 $m '$，在其中自称是 Alice，计算 $H(m ')$，然后把 $(m ', H(m '))$ 发给 Bob。Bob 收到后第 3 步检验全部通过，于是丝毫不会怀疑其中有诈。

要做报文完整性，除了密码散列函数，Alice 与 Bob 还需要一个共享秘密 $s$。这个共享秘密不过是一串比特，称为**鉴别密钥**（authentication key）。利用这个共享秘密，报文完整性可以这样做：

1. Alice 创建报文 $m$，把 $s$ 与 $m$ 拼接成 $s + m$，计算散列 $H(s + m)$（例如用 SHA-1）。$H(s + m)$ 称为**报文鉴别码**（message authentication code，MAC）。
1. Alice 把 MAC 附在报文 $m$ 之后，构成扩展报文 $(m, H(s + m))$，发给 Bob。
1. Bob 收到扩展报文 $(m, h)$，知道 $s$，于是计算 MAC $H(s + m)$。若 $H(s + m) = h$，Bob 就认为一切正常。

该过程汇总于图 8.9。读者应注意：这里的 MAC 指"报文鉴别码"，与链路层协议中的 MAC（介质访问控制）不是一回事！

<Figure src="ch08/fig8-09.webp" caption="图 8.9　报文鉴别码（MAC）" />

MAC 的一个好处是它不需要加密算法。事实上，在许多应用中（包括前面讲的链路状态路由算法），通信实体只关心报文完整性，并不关心报文机密性。用 MAC，实体之间就能相互鉴别所发报文，而不必把复杂的加密算法揉进完整性处理过程中。

如你所料，多年来提出过若干 MAC 标准。今天最流行的是 **HMAC**，它既可以配 MD5 也可以配 SHA-1 使用。HMAC 实际上把数据与鉴别密钥一起过两遍散列函数 [Kaufman 2002; RFC 2104]。

这里还留着一个重要问题：如何把共享鉴别密钥分发给各通信实体？例如在链路状态路由算法中，我们得以某种方式把秘密鉴别密钥分发给自治系统内的每台路由器（注意所有路由器可以共用同一个鉴别密钥）。网络管理员当然可以亲自逐台走访路由器来完成这件事。或者，如果这位管理员比较懒，而每台路由器都有自己的公钥，他也可以把鉴别密钥用某台路由器的公钥加密后，通过网络发给该路由器。

### 8.3.3　数字签名

想想你上周在纸上签了多少次名：支票、信用卡签购单、法律文件、信件。你的签名证明是你（而非别人）确认并/或同意了文件内容。在数字世界里，人们常常需要标明文档的所有者或创建者，或者表示自己同意文档内容。**数字签名**就是在数字世界中实现这些目标的密码学技术。

与手写签名一样，数字签名应当以**可验证**且**不可伪造**的方式进行。也就是说，必须能够证明某个人签过的文档确实由该人签署（签名可验证），并且只有该人可能签署过该文档（签名不可伪造）。

现在来考虑如何设计数字签名方案。注意，Bob 签署报文时，必须在报文上附加某种**只属于他**的东西。Bob 可以考虑附上一个 MAC，其中的 MAC 由"把只有他才知道的密钥附在报文之后、再取散列"得到。但 Alice 要验证签名，也必须持有同一把密钥的副本——那样这把密钥就不再是 Bob 独有的了。可见 MAC 在这里办不到这件事。

回想公钥密码学：Bob 既有公钥也有私钥，两把密钥都只属于 Bob。因此公钥密码学是提供数字签名的绝佳候选。下面来看具体怎么做。

假设 Bob 想对文档 $m$ 做数字签名。可以把该文档看成 Bob 将要签署并发送的一个文件或一条报文。如图 8.10 所示，Bob 只需用自己的私钥 $K_{B}^{-}$ 计算 $K_{B}^{-}(m)$。乍看之下，Bob 用私钥（8.2 节中它是用来解密"用其公钥加密过的报文"的）来签文档似乎很奇怪。但请回想：加密与解密不过是数学运算（在 RSA 中就是对 $e$ 或 $d$ 求幂，见 8.2 节），而 Bob 的目的并不是打乱或遮蔽文档内容，而是以可验证、不可伪造的方式签署文档。Bob 对该文档的数字签名就是 $K_{B}^{-}(m)$。

<Figure src="ch08/fig8-10.webp" caption="图 8.10　为文档创建数字签名" />

数字签名 $K_{B}^{-}(m)$ 是否满足可验证、不可伪造这两条要求？假设 Alice 手里有 $m$ 与 $K_{B}^{-}(m)$。她想在法庭上（她很好讼）证明 Bob 确实签过这份文档，且只有他可能签过。Alice 取 Bob 的公钥 $K_{B}^{+}$，作用于与该文档 $m$ 相关联的数字签名 $K_{B}^{-}(m)$，即计算 $K_{B}^{+}(K_{B}^{-}(m))$——于是，一阵戏剧性的忙乱之后，她得到了 $m$，与原始文档完全一致！接着 Alice 论证只有 Bob 可能签过这份文档，理由如下：

- 签署该报文的人必定在计算签名 $K_{B}^{-}(m)$ 时用了私钥 $K_{B}^{-}$，使得 $K_{B}^{+}(K_{B}^{-}(m)) = m$。
- 唯一可能知道私钥 $K_{B}^{-}$ 的人就是 Bob。回想 8.2 节关于 RSA 的讨论：知道公钥 $K_{B}^{+}$ 对获知私钥 $K_{B}^{-}$ 毫无帮助。因此唯一可能知道 $K_{B}^{-}$ 的人，就是当初生成这对密钥 $(K_{B}^{-}, K_{B}^{+})$ 的人——Bob。（注意，这里假设 Bob 没有把 $K_{B}^{-}$ 交给任何人，也没有人从 Bob 那里偷走 $K_{B}^{-}$。）

同样重要的是：若原始文档 $m$ 被改动成 $m '$，则 Bob 为 $m$ 创建的签名对 $m '$ 不再有效，因为 $K_{B}^{+}(K_{B}^{-}(m))$ 不等于 $m '$。可见数字签名同时提供了报文完整性——接收方既能验证报文未被改动，也能验证报文的来源。

<Figure src="ch08/fig8-11.webp" caption="图 8.11　发送一条经数字签名的报文" />

用加密来签署数据有一个顾虑：加密与解密的计算代价很高。考虑到这些开销，对整条报文做完整的加密/解密来签名未免小题大做。更高效的做法是把散列函数引入数字签名。回想 8.3.2 节：散列算法以任意长度的报文 $m$ 为输入，计算出该报文的定长"指纹" $H(m)$。利用散列函数，Bob 签署的是报文的散列而不是报文本身，即计算 $K_{B}^{-}(H(m))$。由于 $H(m)$ 通常远小于原始报文 $m$，创建数字签名所需的计算量大幅降低。

在 Bob 给 Alice 发报文的语境下，图 8.11 汇总了创建数字签名的操作流程：Bob 把原始长报文过一遍散列函数，再用私钥对所得散列做数字签名；随后把原始报文（明文）连同经数字签名的报文摘要（以下称**数字签名**）一起发给 Alice。图 8.12 汇总了验证签名的操作流程：Alice 把发送方的公钥作用于签名，得到一个散列结果；同时把散列函数作用于明文报文，得到第二个散列结果。若两个散列相同，Alice 就能确信报文的完整性与作者身份。

<Figure src="ch08/fig8-12.webp" caption="图 8.12　验证一条经签名的报文" />

在往下走之前，简要比较一下数字签名与 MAC——二者有相似之处，也有重要的细微差别。两者都从一条报文（或文档）出发。要由报文生成 MAC，我们把鉴别密钥附在报文之后，再对结果取散列；注意生成 MAC 不涉及公钥加密，也不涉及对称密钥加密。要生成数字签名，我们先取报文的散列，再用私钥（借助公钥密码学）加密该报文摘要。因此数字签名是一种"更重"的技术，因为其底层需要一套带认证机构的**公钥基础设施**（PKI，见下文）。8.5 节会看到，流行的安全电子邮件系统 PGP 用数字签名提供报文完整性；而已经看到 OSPF 用 MAC 提供报文完整性；8.6、8.7 节还会看到 MAC 也被用于流行的运输层与网络层安全协议。

#### 公钥认证

数字签名的一个重要应用是**公钥认证**（public key certification），即证明某把公钥属于某个特定实体。公钥认证被用于许多流行的安全网络协议，包括 IPsec 与 TLS。

为理解这个问题，考虑经典的"披萨恶作剧"的因特网商务版。Alice 做披萨外卖生意，接受因特网订单。披萨爱好者 Bob 给 Alice 发一条明文报文，其中包含他的家庭住址与想要的披萨种类；报文里还附有一个数字签名（即对原明文报文散列的签名），向 Alice 证明他才是报文的真实来源。为验证签名，Alice 取得 Bob 的公钥（也许从公钥服务器或从该电子邮件中取得），检验数字签名。这样她就确信下单的是 Bob，而不是某个恶作剧的少年。

这一切听起来都不错，直到聪明的 Trudy 出场。如图 8.13 所示，Trudy 正在搞恶作剧。她给 Alice 发一条报文，自称是 Bob，给出 Bob 的家庭住址，并订一份披萨。报文里她还附上了自己的（Trudy 的）公钥——而 Alice 自然以为那是 Bob 的公钥。Trudy 还附了一个用她自己（Trudy 的）私钥创建的签名。收到报文后，Alice 把 Trudy 的公钥（以为是 Bob 的）作用于数字签名，于是断定这条明文报文确实出自 Bob。等外卖员把一份加意大利辣肠和凤尾鱼的披萨送到 Bob 家时，Bob 会非常惊讶！

<Figure src="ch08/fig8-13.webp" caption="图 8.13　Trudy 用公钥密码学冒充 Bob" />

从这个例子可以看出：要让公钥密码学真正有用，你必须能够验证自己拿到的确实是想要通信的那个实体（人、路由器、浏览器等等）的公钥。例如 Alice 想用公钥密码学与 Bob 通信时，她需要验证"号称是 Bob 的那把公钥"确实是 Bob 的。

把公钥与特定实体绑定，通常由**认证机构**（CA，Certification Authority）完成，其职责是核实身份并签发证书。CA 有两项职能：

1. CA 核实某实体（人、路由器等等）确实是它所声称的那个实体。认证过程没有强制规定的程序。与 CA 打交道时，你必须信任该 CA 执行了足够严格的身份证核。例如，如果 Trudy 能走进"一夜暴富 CA"（Fly-by-Night CA），直接说一句"我是 Alice"就拿到了与 Alice 身份关联的证书，那就不该太相信这家 CA 认证的公钥。另一方面，人们也许（也许不！）更愿意相信属于联邦或州政府项目的 CA。你对某把公钥所关联身份的信任程度，只能达到你对那家 CA 及其身份核实技术的信任程度。信任之网何其纠缠！
1. CA 核实实体身份后，签发一份**证书**（certificate），把该实体的公钥与其身份绑定。证书包含公钥以及关于公钥所有者全局唯一的标识信息（例如人名或 IP 地址）。证书由 CA 做数字签名。这些步骤见图 8.14。

<Figure src="ch08/fig8-14.webp" caption="图 8.14　Bob 的公钥由 CA 认证" />

现在看看证书如何对付 Trudy 这类订披萨的恶作剧者以及其他不受欢迎的人。Bob 下单时同时发送由 CA 签名的证书。Alice 用 CA 的公钥检验 Bob 证书的有效性，并从中提取 Bob 的公钥。

国际电信联盟（ITU）与 IETF 都制定了 CA 标准。ITU X.509 [ITU 2005a] 规定了一种鉴别服务以及证书的具体语法。[RFC 1422] 描述了用于安全因特网电子邮件的基于 CA 的密钥管理，它与 X.509 兼容，但在建立密钥管理体系的程序与约定方面超出了 X.509。表 8.4 描述了证书中的一些重要字段。

## 8.4　端点鉴别

**端点鉴别**（end-point authentication）是一个实体在计算机网络上向另一个实体证明自己身份的过程，例如用户向电子邮件服务器证明自己的身份。作为人类，我们相互鉴别的方式很多：见面时辨认对方的脸，打电话时辨认对方的声音，过海关时由海关官员对照护照上的照片来鉴别我们。

本节考虑当双方通过网络通信时，一方如何鉴别另一方。这里聚焦于鉴别一个"活着的"对端，即在通信真正发生的那个时刻鉴别它。一个具体例子是用户向电子邮件服务器证明自己的身份。这与"证明过去某一时刻收到的报文确实来自所声称的发送方"是微妙不同的问题，后者是 8.3 节的内容。

在网上做鉴别时，通信双方不能依赖生物特征信息，例如长相或声纹。事实上，后面的案例研究将看到，需要相互鉴别的往往是路由器、客户/服务器进程这类网络元素。此时鉴别只能完全基于鉴别协议中交换的报文与数据。通常，鉴别协议会在双方运行其他协议（例如可靠数据传输协议、路由信息交换协议或电子邮件协议）之前运行：鉴别协议先让双方都满意地确认对方身份，之后双方才开始干正事。

与第 3 章开发可靠数据传输（rdt）协议时一样，这里也逐一开发鉴别协议的各个版本（称为 **ap**，authentication protocol），并在推进过程中逐个戳穿其中的漏洞。（如果你喜欢这种逐步演进的设计，可能也会喜欢 [Bryant 1988]——它讲述了一群开放网络鉴别系统设计者之间的虚构故事，以及他们如何发现其中许多微妙问题。）

下面假设 Alice 需要向 Bob 证明自己的身份。

#### 鉴别协议 ap1.0

也许能想到的最简单的鉴别协议，就是 Alice 直接给 Bob 发一条报文说自己是 Alice。该协议如图 8.15 所示。漏洞很明显——Bob 根本无法确认发来"我是 Alice"这条报文的人确实是 Alice。例如，入侵者 Trudy 完全可以发一条这样的报文。

<Figure src="ch08/fig8-15.webp" caption="图 8.15　协议 ap1.0 及一种失败情形" />

#### 鉴别协议 ap2.0

如果 Alice 有一个众所周知的、她总是从那里通信的网络地址（例如 IP 地址），Bob 就可以通过检验承载鉴别报文的 IP 数据报中的源地址是否等于 Alice 那个众所周知的地址，来试图鉴别 Alice。若相符，Alice 就通过鉴别。这也许能挡住非常不懂网络的入侵者，但挡不住认真读这本书的学生，更挡不住许多别的人！

从我们对网络层与链路层的学习可知，伪造源地址并不难（例如，若能接触操作系统源码并构建自己的操作系统内核——Linux 等若干自由可得的操作系统就是这种情况——就可以构造一个 IP 数据报，把任意 IP 源地址（例如 Alice 那个众所周知的 IP 地址）填进去，再通过链路层协议把该数据报发给第一跳路由器）。此后，这个源地址错误的数据报就会被忠实地转发给 Bob。这种做法（图 8.16）是 **IP 欺骗**（IP spoofing）的一种形式。如果 Trudy 的第一跳路由器配置成只转发源地址为 Trudy 自己 IP 地址的数据报 [RFC 2827]，IP 欺骗就可以避免。但这一能力并未普遍部署或强制执行。因此 Bob 若假定 Trudy 的网络管理员（可能就是 Trudy 本人）已把她的第一跳路由器配置成只转发地址正确的数据报，那就太天真了。

<Figure src="ch08/fig8-16.webp" caption="图 8.16　协议 ap2.0 及一种失败情形" />

#### 鉴别协议 ap3.0

鉴别的一种经典做法是使用秘密口令。口令是鉴别方与被鉴别方之间的共享秘密。Gmail、Facebook、telnet、FTP 以及许多其他服务都用口令鉴别。于是在协议 ap3.0 中，Alice 把自己的秘密口令发给 Bob，如图 8.17 所示。

由于口令使用如此广泛，我们或许会以为 ap3.0 相当安全。若这么想就错了！这里的漏洞很清楚：如果 Trudy 窃听 Alice 的通信，她就能获知 Alice 的口令。

<Figure src="ch08/fig8-17.webp" caption="图 8.17　协议 ap3.0 及一种失败情形" />

别以为这不太可能——你 Telnet 到另一台机器登录时，登录口令就是以未加密形式发给 Telnet 服务器的。与 Telnet 客户或服务器处于同一局域网的人，有可能嗅探（读取并存储）该局域网上传输的所有分组，从而窃取登录口令。事实上，这是窃取口令的一种众所周知的手法（例如见 [Jimenez 1997]）。这种威胁显然非常真实，因此 ap3.0 显然不行。

#### 鉴别协议 ap3.1

修 ap3.0 的下一个想法自然是把口令加密。加密口令后，就能防止 Trudy 获知 Alice 的口令。假设 Alice 与 Bob 共享一把对称秘密密钥 $K_{A, B}$，则 Alice 可以加密口令，把"我是 Alice"这条身份报文与加密后的口令一起发给 Bob。Bob 解密口令，若口令正确就鉴别 Alice 通过。Bob 之所以放心，是因为 Alice 不仅知道口令，还知道加密口令所需的共享秘密密钥。把这个协议称为 ap3.1。

ap3.1 确实能防止 Trudy 获知 Alice 的口令，但这里的密码学并没有解决鉴别问题。Bob 会遭受**回放攻击**（playback attack）：Trudy 只需窃听 Alice 的通信，录下口令的加密版本，再把该加密版本重放给 Bob，就能冒充 Alice。ap3.1 中加密口令的用法，与图 8.17 中协议 ap3.0 的情形并没有本质区别。

#### 鉴别协议 ap4.0

图 8.17 的失败情形源于：Bob 无法区分"Alice 的初次鉴别"与"之后对 Alice 初次鉴别的重放"。也就是说，Bob 分不清 Alice 是不是**活着的**（即此刻是否真的在连接的另一端），还是他收到的报文只是对先前某次 Alice 鉴别的录音回放。非常（非常）细心的读者会想起，TCP 三次握手协议也需要解决同一个问题——TCP 连接的服务器端不愿接受一个 SYN 段，如果该 SYN 段是更早某次连接的 SYN 段的旧副本（重传）。TCP 服务器端如何判断客户是否真的活着？它选择一个很久没有用过的初始序号，把该序号发给客户，然后等客户回送一个包含该序号的 ACK 段。我们可以在鉴别中采用同样的思路。

**一次性随机数**（nonce）是协议在其整个生命周期内只使用一次的数。也就是说，协议一旦用过某个 nonce，就再也不会使用该数。ap4.0 协议这样使用 nonce：

1. Alice 向 Bob 发送报文"我是 Alice"。
1. Bob 选择一个 nonce $R$，发给 Alice。
1. Alice 用 Alice 与 Bob 的共享对称秘密密钥 $K_{A, B}$ 加密该 nonce，把加密后的 nonce $K_{A, B}(R)$ 回送给 Bob。与协议 ap3.1 一样，正是"Alice 知道 $K_{A, B}$ 并用它加密了某个值"这一事实，让 Bob 知道收到的报文是 Alice 生成的。nonce 则用于确保 Alice 是活着的。
1. Bob 解密收到的报文。若解密出的 nonce 等于他发给 Alice 的 nonce，则 Alice 通过鉴别。

<Figure src="ch08/fig8-18.webp" caption="图 8.18　协议 ap4.0 及一种失败情形" />

协议 ap4.0 如图 8.18 所示。通过使用这个"一生只用一次"的值 $R$，再检验回送的 $K_{A, B}(R)$，Bob 就能确信 Alice 既是她所声称的那个人（因为她知道加密 $R$ 所需的秘密密钥值），又是活着的（因为她加密了 Bob 刚刚生成的 nonce $R$）。

用 nonce 加对称密钥密码学构成了 ap4.0 的基础。一个自然的问题是：能否用 nonce 加公钥密码学（而非对称密钥密码学）来解决鉴别问题？这个问题留到本章末的习题中探讨。

## 8.5　保护电子邮件

前面几节考察了网络安全中的一些根本问题，包括对称密钥与公钥密码学、端点鉴别、密钥分发、报文完整性与数字签名。现在来看这些工具如何被用于为因特网提供安全性。

有意思的是，在因特网协议栈最上面四层中的任何一层都可以提供安全服务。当为某个应用层协议提供安全性时，使用该协议的应用就能享有一项或多项安全服务，例如机密性、鉴别或完整性。当为某个运输层协议提供安全性时，所有使用该运输协议的应用都能享有该运输协议的安全服务。当在网络层以主机到主机的方式提供安全性时，所有运输层报文段（因而是所有应用层数据）都能享有网络层的安全服务。当以链路为单位提供安全性时，该链路上传输的所有帧中的数据都能获得该链路的安全服务。

8.5 至 8.8 节将考察安全工具如何被用于应用层、运输层、网络层与链路层。与本书的整体结构一致，我们从协议栈顶部开始，讨论应用层的安全性。我们的做法是以电子邮件这一具体应用作为应用层安全的案例研究，然后沿协议栈向下，考察 TLS 协议（在运输层提供安全性）、IPsec（在网络层提供安全性），以及 IEEE 802.11 无线局域网的安全性。

你也许会问：因特网为什么要在不止一层提供安全功能？只在网络层提供安全功能不就够了吗？对此有两个回答。第一，尽管网络层的安全性可以通过加密数据报中的所有数据（即所有运输层报文段）并鉴别所有源 IP 地址来提供"全面覆盖"，但它无法提供**用户级**的安全性。例如，一家商务网站不能依靠 IP 层的安全性来鉴别在其站点购物的顾客。因此，既需要低层的全面覆盖，也需要更高层的安全功能。第二，在协议栈较高层部署新的因特网服务（包括安全服务）通常更容易。一个经典例子是 **PGP**（Pretty Good Privacy），它提供安全的电子邮件（本节稍后讨论）。PGP 只需要客户端与服务器端的应用代码，是最早在因特网上被广泛使用的安全技术之一。

### 8.5.1　安全电子邮件

下面用 8.2 至 8.3 节的密码学原理来构建一个安全的电子邮件系统。我们以增量方式设计这个高层方案，每一步引入新的安全服务。设计时请记住 8.1 节引入的那个香艳例子——Alice 与 Bob 的恋情。设想 Alice 想给 Bob 发一封电子邮件，而 Trudy 想插一手。

在埋头为 Alice 与 Bob 设计安全电子邮件系统之前，先想想他们最希望有哪些安全特性。首先是**机密性**。如 8.1 节所述，Alice 与 Bob 都不希望 Trudy 读到 Alice 的邮件。他们其次希望安全邮件系统具备**发送方鉴别**。特别是当 Bob 收到"我不再爱你了。我再也不想见到你。曾经属于你的，Alice"这样一条报文时，他自然会想确认这条报文来自 Alice 而不是 Trudy。这对恋人还会喜欢的一个特性是**报文完整性**，即确信 Alice 发出的报文在发往 Bob 的途中没有被修改。最后，邮件系统应当提供**接收方鉴别**，即 Alice 想确认自己确实是把信发给了 Bob，而不是某个冒充 Bob 的人（例如 Trudy）。

先来解决最要紧的机密性问题。提供机密性最直接的办法，是 Alice 用对称密钥技术（如 DES 或 AES）加密报文，Bob 收到后解密。如 8.2 节所述，若对称密钥足够长，且只有 Alice 与 Bob 持有该密钥，那么其他人（包括 Trudy）要读懂这条报文就极其困难。这个办法虽然直接，却有一个根本困难——8.2 节讨论过的对称密钥分发问题：如何只让 Alice 与 Bob 持有密钥副本。于是我们自然会考虑另一种办法——公钥密码学（例如用 RSA）。在公钥方案中，Bob 把自己的公钥公开（例如放在公钥服务器上或自己的个人主页上），Alice 用 Bob 的公钥加密报文，再把密文发到 Bob 的邮箱地址；Bob 收到后用私钥解密即可。假定 Alice 确知那把公钥就是 Bob 的公钥，这个办法就是提供所需机密性的极佳手段。但有一个问题：公钥加密效率相对较低，对长报文尤其如此。

为克服效率问题，我们利用**会话密钥**（session key，见 8.2.2 节）。具体来说，Alice ①选择一个随机的对称会话密钥 $K_{S}$，②用该对称密钥加密报文 $m$，③用 Bob 的公钥 $K_{B}^{+}$ 加密该对称密钥，④把加密后的报文与加密后的对称密钥拼接成一个"包裹"，⑤把包裹发到 Bob 的邮箱地址。这些步骤见图 8.19。（在本图及后续各图中，带圈的"+"表示拼接，带圈的"−"表示拆解。）Bob 收到包裹后，①用自己的私钥 $K_{B}^{-}$ 得到对称密钥 $K_{S}$，②用对称密钥 $K_{S}$ 解密报文 $m$。

<Figure src="ch08/fig8-19.webp" caption="图 8.19　Alice 用对称会话密钥 K_{S} 给 Bob 发送机密邮件" />

图 8.21 给出的安全邮件设计，对大多数邮件用户的大多数场合大概都能提供令人满意的安全性。但还有一个重要问题有待解决：该设计要求 Alice 取得 Bob 的公钥，也要求 Bob 取得 Alice 的公钥，而这些公钥的分发并非易事。例如，Trudy 可以冒充 Bob，把自己的公钥说成是 Bob 的公钥交给 Alice，从而收到本该发给 Bob 的报文。如 8.3 节所学，安全分发公钥的一种流行做法是用 CA 认证公钥。

### 8.5.2　PGP

**PGP**（Pretty Good Privacy）由 Phil Zimmermann 于 1991 年编写，是电子邮件加密方案的一个很好的例子。PGP 的设计本质上与图 8.21 所示的设计相同。视版本不同，PGP 软件用 MD5 或 SHA 计算报文摘要，用 CAST、三重 DES 或 IDEA 做对称密钥加密，用 RSA 做公钥加密。

安装 PGP 时，软件会为用户创建一对公钥。公钥可以发布在用户网站上，也可以放入公钥服务器；私钥则由口令保护，用户每次访问私钥都必须输入口令。PGP 让用户选择对报文做数字签名、加密报文，或者既签名又加密。图 8.22 显示了一条 PGP 签名报文，它出现在 MIME 首部之后。报文中的编码数据是 $K_{A}^{-}(H(m))$，即经数字签名的报文摘要。如上所述，Bob 要验证报文完整性，必须能够取得 Alice 的公钥。

<Figure src="ch08/fig8-22.webp" caption="图 8.22　一条 PGP 签名报文" />

图 8.23 显示了一条 PGP 机密报文，它也出现在 MIME 首部之后。当然，明文报文并不包含在这条机密邮件中。当发送方（例如 Alice）既要机密性又要完整性时，PGP 会把图 8.23 那样的报文嵌在图 8.22 那样的报文之中。

<Figure src="ch08/fig8-23.webp" caption="图 8.23　一条 PGP 机密报文" />

PGP 也提供公钥认证机制，但其机制与更常见的 CA 很不一样。PGP 公钥由**信任网**（web of trust）认证：Alice 自己只要相信某个"密钥/用户名"配对确实匹配，就可以认证该配对。此外，PGP 还允许 Alice 声明她信任另一位用户去为更多密钥的真实性作保。有些 PGP 用户通过举办**密钥签名会**（key-signing party）互相签署对方的密钥：用户们实地聚在一起，交换公钥，并用各自的私钥签署对方的密钥以完成认证。

**OpenPGP** [OpenPGP 2025] 是 Zimmermann 原版 PGP 的开放后继者，用公钥和/或对称加密技术为电子邮件与数据文件提供数据机密性、数字签名与报文完整性。OpenPGP 由 [RFC 9580] 规定。

::: info 注

这里值得留意 PGP 与 CA 体系的哲学差异。CA 体系是**层次式**的：你信任少数几个根 CA，根 CA 签发的证书再由下级 CA 转签，信任沿树向下传递。信任网是**网状**的：没有根，每个人自己决定信任谁，信任沿"我认识的人"这张图横向扩散。前者适合大规模、匿名的商业交易（你不认识 Amazon，但可以信任给它签证书的那家 CA）；后者适合小圈子、面对面的社群（你不需要第三方告诉你"这把密钥属于你的朋友"，因为你昨天刚跟他换过密钥）。两种模型各有各的失效模式：CA 体系一旦某个根 CA 被攻破或被胁迫，影响面是全局的；信任网则难以扩展，且"谁都可以认证谁"意味着认证本身的信息量很低。

:::

## 8.6　保护 TCP 与 HTTP 连接：TLS

上一节看到密码学技术如何为某个具体应用（即电子邮件）提供机密性、数据完整性与端点鉴别。本节沿协议栈下降一层，考察密码学如何为 TCP 与 HTTP 增强安全性，包括机密性、数据完整性与端点鉴别。提供这些安全服务的协议称为**运输层安全**（TLS，Transport Layer Security）协议。

回想 2.2.6 节：严格说来，TLS 是一个**应用层**协议，在使用 TLS 的客户进程与服务器进程之间提供安全服务。历史上，TLS 实现在 TCP 之上，为 TCP 提供的底层进程到进程服务加上安全性。2.2.6 节也已看到，如今 TLS 还作为 QUIC 协议的一部分运行在 UDP 之上，而 QUIC 为 HTTP/3 提供运输服务。

TLS 源于更早的**安全套接字层**（SSL）协议，后者是为 Netscape 开发并发布的。事实上，规定 TLS 1.0 的 RFC 2246 就指出"本协议与 SSL 3.0 的差别并不显著"。顺便一提，保护 TCP 的基本思想早于 Netscape 的工作（例如见 [Woo 1994]）。

TLS 的部署极其广泛：所有流行的 Web 浏览器与 Web 服务器都支持 TLS，HTTP/3 默认使用 TLS，Gmail 以及几乎所有因特网商务站点（包括 Amazon、eBay 与淘宝）都使用 TLS。每年有数千亿美元的交易在 TLS 之上完成。事实上，如果你曾在因特网上用信用卡买过任何东西，你的浏览器与该服务器之间为这笔交易进行的通信几乎肯定走了 TLS。（当 URL 以"https:"而不是"http:"开头时，就可以识别出你的浏览器正在使用 TLS。）TLS 的当前版本是 TLS 1.3，由 RFC 8446 规定。相比早期版本，TLS 1.3 引入了更快的初始握手（见 2.2.6 节），并删除了较旧、较不安全的密码算法与过程。

为理解 TLS 的必要性，走一遍一个典型的因特网商务场景。Bob 在浏览网页时来到售卖香水的"Alice 公司"站点。站点显示一个表单，Bob 应在其中填写想要的香水种类与数量、自己的地址以及支付卡号。Bob 填好这些信息，点击"提交"，期待通过普通邮政收到所购香水，也期待在下期支付卡账单上看到这笔扣款。这一切听起来都不错，但若没有采取任何安全措施，Bob 可能会遇上几件意外。

- 若不使用机密性（加密），入侵者可以截获 Bob 的订单，获取他的支付卡信息，然后用 Bob 的钱去买东西。
- 若不使用数据完整性，入侵者可以修改 Bob 的订单，让他买下十倍于本意的香水。
- 最后，若不使用服务器鉴别，一个服务器可以显示"Alice 公司"那个著名徽标，而实际上该站点由冒充"Alice 公司"的 Trudy 维护。收到 Bob 的订单后，Trudy 可以卷款跑路，也可以通过收集 Bob 的姓名、地址与信用卡号来实施身份盗窃。

TLS 通过为运行在其上的应用提供机密性、数据完整性、服务器鉴别与客户鉴别，解决了这些问题。

### 8.6.1　全景

先从 TLS 的一个简化版本讲起，以便对 TLS 的"为什么"与"怎么做"形成全景式理解。我们把这个简化版 TLS 称为"准 TLS"（almost-TLS）。讲完准 TLS，下一小节再讲真正的 TLS，补上细节。准 TLS（以及 TLS）分为三个阶段：**握手**、**密钥导出**与**数据传输**。下面以客户（Bob）与服务器（Alice）之间的一次通信会话为例描述这三个阶段，其中 Alice 拥有一对公私钥以及一份把她的身份与公钥绑定的证书。这里以保护 TCP 连接为背景描述 TLS，但请记住 TLS 也被用在 QUIC 中，为 UDP 之上的进程到进程通信提供安全性。

<Figure src="ch08/fig8-24.webp" caption="图 8.24　准 TLS 握手，从建立 TCP 连接开始" />

#### 握手

在握手阶段，Bob 需要 (a) 与 Alice 建立 TCP 连接，(b) 验证 Alice 确实是 Alice，(c) 把一个主秘密（master secret）发给 Alice，供双方生成该 TLS 会话所需的所有对称密钥。这三个步骤见图 8.24。注意 TCP 连接建立后，Bob 向 Alice 发送一条 hello 报文；Alice 随后回送她的证书，其中包含她的公钥。如 8.3 节所述，由于证书由 CA 认证过，Bob 能确信证书中的公钥属于 Alice。接着 Bob 生成一个主秘密（MS，只用于本次 TLS 会话），用 Alice 的公钥加密 MS 得到加密主秘密（EMS），并把 EMS 发给 Alice。Alice 用私钥解密 EMS 得到 MS。此阶段结束后，Bob 与 Alice（且只有他们）知道本次 TLS 会话的主秘密。

#### 密钥导出

原则上，现在双方共享的 MS 可以直接用作后续所有加密与完整性检验的对称会话密钥。但一般认为更安全的做法是让 Alice 与 Bob 各自使用不同的密码学密钥，并且加密与完整性检验也使用不同的密钥。因此，双方都用 MS 生成四把密钥：

- $E_{B}$ = 从 Bob 发往 Alice 的数据的加密密钥；
- $M_{B}$ = 从 Bob 发往 Alice 的数据的 HMAC 密钥，其中 HMAC [RFC 2104] 是 8.3.2 节遇到的标准化散列报文鉴别码；
- $E_{A}$ = 从 Alice 发往 Bob 的数据的加密密钥；
- $M_{A}$ = 从 Alice 发往 Bob 的数据的 HMAC 密钥。

Alice 与 Bob 各自从 MS 生成这四把密钥，最简单的做法就是把 MS 切成四段。（但真正的 TLS 稍复杂些，下面会看到。）密钥导出阶段结束时，双方都拥有全部四把密钥。两把加密密钥用于加密数据，两把 HMAC 密钥用于验证数据完整性。

#### 数据传输

既然 Alice 与 Bob 共享同样的四把会话密钥（$E_{B}$、$M_{B}$、$E_{A}$、$M_{A}$），他们就可以在 TCP 连接上开始互发受保护的数据了。由于 TCP 是字节流协议，一个自然的做法是让 TLS 边加密应用数据、边把加密数据交给 TCP。但若真这么做，完整性检验所需的 HMAC 该放在哪里？我们当然不愿等到 TCP 会话结束时才去验证 Bob 在整个会话中发出的所有数据的完整性！为解决这个问题，TLS 把数据流切成**记录**（record），为每条记录附加一个 HMAC 用于完整性检验，然后加密"记录 + HMAC"。为生成 HMAC，Bob 把记录数据与密钥 $M_{B}$ 一起输入散列函数（如 8.3 节所述）。为加密"记录 + HMAC"这个包，Bob 使用自己的会话加密密钥 $E_{B}$。加密后的包随即交给 TCP，通过因特网传输。

这个做法虽然已经走了很远，但在为整个报文流提供数据完整性方面仍不是无懈可击的。特别是，假设 Trudy 是一个**中间人**（woman-in-the-middle），有能力在 Alice 与 Bob 之间往来的 TCP 报文段流中插入、删除与替换报文段。例如，Trudy 可以截获 Bob 发出的两个报文段，颠倒它们的顺序，调整 TCP 序号（TCP 序号是不加密的），然后把这两个顺序颠倒的报文段发给 Alice。假设每个 TCP 报文段恰好封装一条记录，来看看 Alice 会如何处理这两个报文段。

1. Alice 中的 TCP 会认为一切正常，把这两条记录交给 TLS 子层。
1. Alice 中的 TLS 会解密这两条记录。
1. Alice 中的 TLS 会用每条记录中的 HMAC 验证这两条记录的数据完整性。
1. 随后 TLS 会把这两条记录解密后的字节流交给应用层；但由于记录被颠倒了，Alice 收到的完整字节流顺序并不正确！

建议读者自己走一遍 Trudy 删除报文段或重放报文段时的类似情形。

这个问题的解决办法，你大概已经猜到了——使用序号。TLS 的做法是：Bob 维护一个序号计数器，从 0 开始，每发送一条 TLS 记录就加一。Bob 并不把序号真正放进记录里，而是在计算 HMAC 时把序号纳入 HMAC 的计算。于是 HMAC 成了"数据 + HMAC 密钥 $M_{B}$ + 当前序号"的散列。Alice 跟踪 Bob 的序号，从而可以在 HMAC 计算中纳入相应序号来验证某条记录的数据完整性。这种 TLS 序号的使用，使 Trudy 无法实施重排或重放报文段之类的中间人攻击。（想想为什么？）

### 8.6.2　更完整的图景：TLS 1.3

上一小节讲了准 TLS 协议，对 TLS 的"为什么"与"怎么做"有了基本理解。有了这个基础，现在可以再深入一些，考察真实 TLS 协议的要点。建议读者在阅读这段 TLS 协议描述的同时，完成教材网站上的 Wireshark TLS 实验。

TLS 协议从 1.0 演进到 1.1、1.2，再到如今的 1.3 [RFC 8446]，经历了若干变化。有些变化源于在早期版本中发现的安全缺陷，或为了落实新出现的安全最佳实践；另一些变化是为了提升 TLS 性能，特别是尽量减少建立 TLS 连接所需的 RTT 数——这个主题我们在第 2 章研究 HTTP 协议演进时已经遇到过。尽管有这些变化，TLS 的目标始终如一：为通过 TLS 通信的客户与服务器进程提供机密性、数据完整性与鉴别。而且正如我们将看到的，TLS 实现这些目标所用的，正是本章前面学过的基础密码学安全技术。

#### TLS 1.3 握手

TLS 1.3 握手的目标是：让客户与服务器安全地就可用来提供机密性、数据完整性与鉴别的**密码套件**（cipher suite）达成一致；完成鉴别；并就一个新的共享主秘密（称为**临时密钥**，ephemeral key）达成一致。这个临时密钥随后用于导出 TLS 保护会话后续阶段使用的其他共享密钥。常见的 TLS 1.3 握手包含以下步骤：

- **Client Hello**。在 Client Hello 报文中，客户指明 TLS 版本号（1.3）、三种密码套件之一及其参数，以及一个用于防重放攻击的 nonce。密码套件由几部分组成：(i) 用于生成主秘密的密钥交换技术，以及握手之后用于从主秘密导出其他密钥的 SHA 散列算法；(ii) 数据传输期间使用的**带关联数据的认证加密**（AEAD）算法。AEAD 不分别使用加密算法与报文完整性算法，而是用单个算法同时为传输的数据提供机密性与完整性，其加密使用 AES 或 ChaCha20。生成主秘密时，各种情形下都使用 Diffie-Hellman（DH）密钥协商的某个变体（见 8.2.2 节）。
- **Server Hello, Finished**。TLS 1.3 服务器说完"hello"紧接着就说"goodbye"。Server Hello 报文包含服务器证书、选定的密码套件以及一个服务器生成的 nonce。由于 Client Hello 报文已包含 DH 密钥协商所需的客户（公开）值，服务器生成自己的 DH 公私值，再由客户的公开值与自己的 DH 私值生成共享主秘密；它把自己的 DH 公开值放进 Server Hello 报文发给客户。
- **Client Finished**。客户验证签名与证书，并由自己的 DH 密钥协商私值与收到的服务器 DH 公开值生成自己那一份主秘密。Finished 报文包含对 Client Hello 与 Server Hello 报文的签名散列，用以验证这些报文已被收到且未被篡改。Finished 报文本身则用从主秘密导出的密钥加密并签名。

一旦 Client Finished 报文发出，客户就可以立即向服务器发送应用报文（例如一条 HTTP GET 报文），这些报文及其应答从此受 TLS 保护。如图 8.26 所示，TLS 1.3 只需要**一个** RTT——相比早期版本所需的两个或更多 RTT 是一大改进。

当 TLS 1.3 运行在 TCP 之上时，必须先建立 TCP 连接，然后才能进行 TLS 握手。因此，在 TCP 上运行 TLS 1.3 时，客户要等**两个** RTT 才能开始发送数据（例如最初的 HTTP 请求报文）。相比之下，使用 QUIC 时，TLS 1.3 并不运行在 QUIC 之上，而是被**集成进** QUIC：在 QUIC 中，TLS 1.3 的 Client Hello 报文是 QUIC 连接建立报文的一部分，而后者通过 UDP 发送。因此在 QUIC 下，客户只需等**一个** RTT 就能开始向服务器发送数据。若客户与服务器此前曾通信并在当时就商定了未来 TLS 连接要用的参数，QUIC 下甚至可以做到**零** RTT（即客户可以立即开始发送受 TLS 保护的数据）。

<Figure src="ch08/fig8-26.webp" caption="图 8.26　TLS 1.3 握手" />

你也许会问：TLS 握手为什么需要 nonce？难道序号不足以防止报文段重放攻击吗？答案是：序号确实够用，但仅有序号并不能防止"**连接重放攻击**"。考虑下面这种连接重放攻击：假设 Trudy 嗅探了 Alice 与 Bob 之间的所有报文；第二天，Trudy 冒充 Bob，把 Bob 前一天发给 Alice 的报文序列原样重发一遍。若 Alice 不使用 nonce，她就会回送与前一天完全相同的报文序列。由于她收到的每条报文都能通过完整性检验，Alice 不会察觉任何异常。若 Alice 是一台电子商务服务器，她会以为 Bob 又下了一单（买的还是完全相同的东西）。反之，若协议中包含 nonce，Alice 会为每个 TCP 会话发出不同的 nonce，从而使两天的加密密钥不同。于是当 Alice 收到 Trudy 重放的 TLS 记录时，这些记录无法通过完整性检验，那笔虚假的电子商务交易也就不会成功。总之，TLS 用 nonce 防范"连接重放攻击"，用序号防范进行中的会话内单个分组的重放。

TLS 1.3 中包含握手报文及后续应用层数据的记录，格式与图 8.25 所示的准 TLS 记录相同，只是由于 AEAD 算法已为传输数据同时提供机密性与完整性，不再需要显式的 HMAC 字段。

#### 连接关闭

到某个时刻，Bob 或 Alice 会想结束 TLS 会话。一种做法是让 Bob 直接终止底层的 TCP 连接——即向 Alice 发送一个 TCP FIN 报文段——来结束 TLS 会话。但这种天真的设计为**截断攻击**（truncation attack）埋下了伏笔：Trudy 再次插入到进行中的 TLS 会话中间，用一个 TCP FIN 提前结束会话。若 Trudy 这么做，Alice 会以为自己收到了 Bob 的全部数据，而实际上只收到了一部分。解决办法是在类型字段中指明该记录是否用于终止 TLS 会话。有了这个字段，若 Alice 在收到 TLS 关闭记录之前先收到 TCP FIN，她就知道其中有诈。

以上完成了对 TLS 的介绍。可以看到，它用到了 8.2 与 8.3 节讨论的许多密码学原理。想更深入研究 TLS 的读者，可以读 Rescorla 关于 SSL/TLS 的奠基性著作 [Rescorla 2001]，以及关于 TLS 1.3 的较新资料 [Cloudflare TLS 2018; Cloudflare TLS 2025]。

## 8.7　网络层安全：IPsec 与虚拟专用网

IP 安全协议更常被称为 **IPsec**，它在网络层提供安全性。IPsec 为任意两个网络层实体（包括主机与路由器）之间的 IP 数据报提供安全性。下面很快会讲到，许多机构（公司、政府部门、非营利组织等等）用 IPsec 在公共因特网之上构建**虚拟专用网**（VPN）。

在深入 IPsec 的细节之前，先退一步想想"在网络层提供机密性"意味着什么。当一对网络实体之间（例如两台路由器之间、两台主机之间，或路由器与主机之间）具备网络层机密性时，发送实体对它发往接收实体的所有数据报的载荷都加密。被加密的载荷可以是 TCP 报文段、UDP 报文段、ICMP 报文等等。若这样的网络层服务到位，则从一个实体发往另一实体的所有数据——包括电子邮件、网页、TCP 握手报文以及管理报文（如 ICMP 与 SNMP）——都会对任何嗅探网络的第三方隐藏。正因如此，网络层安全被认为提供"**全面覆盖**"。

除机密性外，网络层安全协议还可能提供其他安全服务。例如它可以提供源鉴别，使接收实体能够验证受保护数据报的来源；可以提供数据完整性，使接收实体能够检查数据报在传输途中是否被改动；还可以提供**防重放攻击**，使 Bob 能够检测出攻击者可能插入的任何重复数据报。下面很快会看到，IPsec 确实为所有这些安全服务都提供了机制，即机密性、源鉴别、数据完整性与防重放攻击。

### 8.7.1　IPsec 与虚拟专用网（VPN）

横跨多个地理区域的机构，往往希望拥有自己的 IP 网络，以便其主机与服务器之间能安全、保密地互发数据。为实现这一目标，机构可以真正部署一个完全独立于公共因特网的物理网络（包括路由器、链路与 DNS 基础设施）。这种专属于某机构的独立网络称为**专用网**（private network）。毫不奇怪，专用网可能非常昂贵，因为机构需要自行采购、安装并维护物理网络基础设施。

如今许多机构不再部署和维护专用网，而是在现有的公共因特网之上构建 **VPN**。使用 VPN 时，机构的跨办公室流量走公共因特网，而不是走物理上独立的网络；但为提供机密性，这些跨办公室流量在进入公共因特网之前先被加密。图 8.27 给出一个简单的 VPN 例子。这里机构由总部、分支机构以及通常从酒店房间接入因特网的出差销售人员组成（图中只画了一位销售人员）。在这个 VPN 中，总部内部两台主机互发 IP 数据报时，或分支机构内部两台主机想通信时，用的都是普通的原味 IPv4（即不带 IPsec 服务）；但当机构的两台主机之间的通信路径要穿过公共因特网时，流量在进入因特网之前先被加密。

<Figure src="ch08/fig8-27.webp" caption="图 8.27　虚拟专用网（VPN）" />

为体会 VPN 如何工作，结合图 8.27 走一个简单例子。当总部的一台主机向住在酒店的销售人员发送 IP 数据报时，总部的网关路由器把这个普通 IPv4 数据报转换成 IPsec 数据报，再把该 IPsec 数据报转发进因特网。这个 IPsec 数据报实际上带有一个传统的 IPv4 首部，因此公共因特网中的路由器会像处理普通 IPv4 数据报那样处理它——对它们来说，这就是一个完全普通的数据报。但如图 8.27 所示，IPsec 数据报的载荷中包含一个 IPsec 首部（用于 IPsec 处理），而且 IPsec 数据报的载荷是加密的。当该 IPsec 数据报到达销售人员的笔记本电脑时，笔记本的操作系统解密载荷（并提供其他安全服务，例如验证数据完整性），再把解密后的载荷交给上层协议（例如 TCP 或 UDP）。

以上只是机构如何利用 IPsec 构建 VPN 的高层概述。为了不被细节淹没，我们略去了许多重要内容。下面细看。

### 8.7.2　AH 与 ESP 协议

IPsec 是个相当复杂的"动物"——它由十几个 RFC 定义。其中两个重要的 RFC 是 RFC 4301（描述整体 IP 安全体系结构）与 RFC 6071（提供 IPsec 协议族概述）。与本书一贯的做法一样，我们的目标不是复述干枯晦涩的 RFC，而是以更具操作性与教学性的方式来描述这些协议。

IPsec 协议族中有两个主要协议：**鉴别首部**（AH，Authentication Header）协议与**封装安全载荷**（ESP，Encapsulation Security Payload）协议。当源 IPsec 实体（通常是主机或路由器）向目的实体（也是主机或路由器）发送安全数据报时，用的是 AH 协议或 ESP 协议之一。AH 协议提供源鉴别与数据完整性，但不提供机密性；ESP 协议提供源鉴别、数据完整性与机密性。由于机密性对 VPN 及其他 IPsec 应用往往至关重要，ESP 协议的使用远比 AH 协议广泛。为进一步揭开 IPsec 的神秘面纱、避开其大部分复杂性，下面只讨论 ESP 协议。想了解 AH 协议的读者可自行查阅 RFC 与其他在线资料。

### 8.7.3　安全关联

IPsec 数据报在一对网络实体之间发送，例如两台主机之间、两台路由器之间，或主机与路由器之间。在从源实体向目的实体发送 IPsec 数据报之前，源与目的实体先建立一个网络层逻辑连接，这个逻辑连接称为**安全关联**（SA，security association）。SA 是**单工**逻辑连接，即从源到目的单向。若两个实体想互发安全数据报，则需要建立两个 SA（即两条逻辑连接），每个方向一条。

再来看图 8.27 中的机构 VPN。该机构由总部、分支机构以及 $n$ 位出差销售人员组成。为便于举例，假设总部与分支机构之间、总部与各销售人员之间都有双向 IPsec 流量。这个 VPN 中共有多少个 SA？回答这个问题要注意：总部网关路由器与分支机构网关路由器之间有 2 个 SA（每个方向一个）；对每位销售人员的笔记本电脑，总部网关路由器与该笔记本之间有 2 个 SA（同样是每个方向一个）。因此总共有 $2(n + 2)$ 个 SA。但要记住，网关路由器或笔记本电脑发进因特网的流量并非全部受 IPsec 保护。例如总部的一台主机可能想访问公共因特网上的 Web 服务器（如 Amazon 或 Google）。因此网关路由器（以及那些笔记本）会向因特网发出普通的 IPv4 数据报与受保护的 IPsec 数据报两种。

<Figure src="ch08/fig8-28.webp" caption="图 8.28　从 R1 到 R2 的安全关联（SA）" />

现在来看看 SA"内部"。为使讨论具体可感，我们以图 8.28 中从路由器 R1 到路由器 R2 的一个 SA 为背景（可以把 R1 看成图 8.27 的总部网关路由器，R2 看成分支机构网关路由器）。路由器 R1 维护关于该 SA 的状态信息，其中包括：

- 该 SA 的 32 比特标识符，称为**安全参数索引**（SPI，Security Parameter Index）；
- 该 SA 的源接口（这里是 200.168.1.100）与目的接口（这里是 193.68.2.23）；
- 要使用的加密类型（例如带 CBC 的 3DES）；
- 加密密钥；
- 完整性检验类型（例如带 MD5 的 HMAC）；
- 鉴别密钥。

每当路由器 R1 需要为该 SA 构造一个要转发的 IPsec 数据报时，它就访问这些状态信息，以确定应如何鉴别与加密该数据报。同样，路由器 R2 也为该 SA 维护相同的状态信息，并用它来鉴别与解密从该 SA 到来的任何 IPsec 数据报。

一个 IPsec 实体（路由器或主机）常常为许多 SA 维护状态信息。例如图 8.27 中带 $n$ 位销售人员的 VPN 例子里，总部网关路由器为 $2(n + 2)$ 个 SA 维护状态信息。IPsec 实体把所有 SA 的状态信息存放在**安全关联数据库**（SAD）中，SAD 是该实体操作系统内核里的一个数据结构。

### 8.7.4　IPsec 数据报

讲完 SA，就可以描述实际的 IPsec 数据报了。IPsec 有两种分组形式：一种用于所谓的**隧道模式**（tunnel mode），另一种用于所谓的**运输模式**（transport mode）。隧道模式更适合 VPN，部署也比运输模式广泛。为进一步揭开 IPsec 的神秘面纱、避开其大部分复杂性，下面只讨论隧道模式。一旦牢牢掌握了隧道模式，运输模式应当不难自行学会。

IPsec 数据报的分组格式见图 8.29。你也许觉得分组格式枯燥乏味，但很快会看到，IPsec 数据报的样子与味道都像一道流行的得州-墨西哥菜！结合图 8.28 来看 IPsec 的各个字段。假设路由器 R1 收到主机 172.16.1.17（总部网络中）发来的一个普通 IPv4 数据报，其目的是主机 172.16.2.48（分支机构网络中）。R1 用下面这套"菜谱"把这个"原始 IPv4 数据报"转换成 IPsec 数据报：

- 在原始 IPv4 数据报（**包括原始首部字段**！）后面附加一个"ESP 尾部"字段；
- 用 SA 指定的算法与密钥加密所得结果；
- 在这个加密后的量前面附加一个称为"ESP 首部"的字段；所得包裹称为"enchilada"（墨西哥卷）；
- 用 SA 指定的算法与密钥，对整条 enchilada 计算一个鉴别 MAC；
- 把该 MAC 附加到 enchilada 后面，构成载荷；
- 最后，创建一个全新的 IP 首部（包含全部经典 IPv4 首部字段，通常共 20 字节），附加在载荷之前。

<Figure src="ch08/fig8-29.webp" caption="图 8.29　IPsec 数据报格式" />

注意，所得的 IPsec 数据报是一个地道的 IPv4 数据报：传统 IPv4 首部字段之后跟着载荷。但在这里，载荷包含一个 ESP 首部、原始 IP 数据报、一个 ESP 尾部以及一个 ESP 鉴别字段（其中原始数据报与 ESP 尾部被加密）。原始 IP 数据报的源 IP 地址是 172.16.1.17、目的 IP 地址是 172.16.2.48。由于 IPsec 数据报包含原始 IP 数据报，这两个地址就（加密后）成为 IPsec 分组载荷的一部分。那么新 IP 首部（即 IPsec 数据报最左边的首部）中的源、目的 IP 地址又是什么呢？如你所料，它们被设为隧道两端的源、目的路由器接口，即 200.168.1.100 与 193.68.2.23。另外，这个新 IPv4 首部中的协议号不是 TCP、UDP 或 SMTP 的协议号，而是 50，表示这是一个使用 ESP 协议的 IPsec 数据报。

R1 把 IPsec 数据报发进公共因特网后，它会经过许多路由器才到达 R2。这些路由器都会把它当作普通数据报处理——它们完全不知道这个数据报载着经 IPsec 加密的数据。对这些公共因特网路由器来说，由于外层首部中的目的 IP 地址是 R2，该数据报的最终目的地就是 R2。

走完一个 IPsec 数据报的构造实例，下面细看这条 enchilada 的配料。在图 8.29 中可以看到，ESP 尾部由三个字段组成：填充、填充长度与下一个首部。回想块密码要求被加密的报文长度是块长的整数倍。填充（由无意义的字节组成）用于在附加到原始数据报之后（连同填充长度与下一个首部字段），使所得的"报文"恰为整数个块。填充长度字段告诉接收实体插入了多少填充（因而需要去掉多少）。下一个首部指明载荷数据字段中所含数据的类型（例如 UDP）。载荷数据（通常是原始 IP 数据报）与 ESP 尾部被拼接起来，然后加密。

在这个加密单元前面附加的是 ESP 首部，它以明文发送，由两个字段组成：SPI 与序号字段。SPI 告诉接收实体该数据报属于哪个 SA；接收实体随即可以用 SPI 检索自己的 SAD，确定相应的鉴别/解密算法与密钥。序号字段用于防重放攻击。

发送实体还会附加一个鉴别 MAC。如前所述，发送实体对整条 enchilada（由 ESP 首部、原始 IP 数据报与 ESP 尾部组成，其中数据报与尾部是加密的）计算 MAC。回想计算 MAC 时，发送方在 enchilada 之后附加一个秘密 MAC 密钥，再对结果计算定长散列。

当 R2 收到该 IPsec 数据报时，R2 发现数据报的目的 IP 地址就是自己，于是处理它。由于（最左侧 IP 首部中的）协议字段是 50，R2 知道应对该数据报施加 IPsec ESP 处理。第一步，R2 探入 enchilada，用 SPI 确定该数据报属于哪个 SA。第二步，计算 enchilada 的 MAC，并验证它与 ESP MAC 字段中的值一致；若一致，它就知道这条 enchilada 来自 R1 且未被篡改。第三步，检查序号字段以确认该数据报是新鲜的（不是重放的数据报）。第四步，用与该 SA 关联的解密算法与密钥解密那个加密单元。第五步，去掉填充，取出原始的普通 IP 数据报。最后第六步，把原始数据报转发进分支机构网络，送往其最终目的地。唉，这套菜谱真够复杂的吧？不过从来没人说过做一条 enchilada 再把它拆开是件容易事！

还有一个重要的微妙之处需要处理，核心是这个问题：当 R1 收到总部网络中某台主机发来的一个（未受保护的）数据报，而该数据报的目的 IP 地址在总部之外时，R1 怎么知道是否应把它转换成 IPsec 数据报？若要经 IPsec 处理，R1 又怎么知道该用（其 SAD 中众多 SA 里的）哪个 SA 来构造 IPsec 数据报？这个问题这样解决：除 SAD 外，IPsec 实体还维护另一个称为**安全策略数据库**（SPD，Security Policy Database）的数据结构。SPD 指明哪些类型的数据报（按源 IP 地址、目的 IP 地址与协议类型区分）应经 IPsec 处理，以及对这些应经 IPsec 处理的数据报该用哪个 SA。某种意义上，SPD 中的信息指明对到来的数据报"做什么"，SAD 中的信息指明"怎么做"。

#### IPsec 服务小结

那么 IPsec 究竟提供哪些服务？从攻击者 Trudy 的视角来考察这些服务——假设 Trudy 是坐在图 8.28 中 R1 与 R2 之间某处的中间人，并且始终假设 Trudy 不知道该 SA 使用的鉴别密钥与加密密钥。Trudy 能做什么、不能做什么？第一，Trudy 看不到原始数据报。事实上，不仅原始数据报中的数据对她隐藏，连协议号、源 IP 地址与目的 IP 地址也一并隐藏。对于在该 SA 上发送的数据报，Trudy 只知道它源自 200.168.1.100、目的为 193.68.2.23；她不知道它载的是 TCP、UDP 还是 ICMP 数据，也不知道它载的是 HTTP、SMTP 还是别的应用数据。可见这里的机密性比 TLS 走得远得多。第二，假设 Trudy 试图通过翻转某些比特来篡改该 SA 中的数据报。这个被篡改的数据报到达 R2 时会通不过（用 MAC 做的）完整性检验，Trudy 的恶毒企图再次落空。第三，假设 Trudy 试图冒充 R1，构造一个源为 200.168.1.100、目的为 193.68.2.23 的 IPsec 数据报。她的攻击同样徒劳，因为这个数据报在 R2 处仍将通不过完整性检验。最后，由于 IPsec 包含序号，Trudy 也无法成功实施重放攻击。总之，如本节开头所声称的，IPsec 在**任何一对经网络层处理分组的设备之间**提供机密性、源鉴别、数据完整性与防重放攻击。

### 8.7.5　IKE：IPsec 中的密钥管理

当一个 VPN 只有少量端点时（例如图 8.28 中只有两台路由器），网络管理员可以手工把 SA 信息（加密/鉴别算法与密钥、以及 SPI）录入各端点的 SAD。对于可能有数百甚至数千台 IPsec 路由器与主机的大型 VPN，这种"手工密钥"显然不切实际。大型、地理上分散的部署需要自动创建 SA 的机制。IPsec 用**因特网密钥交换**（IKE）协议完成这件事，该协议由 RFC 5996 规定。

IKE 与 TLS 的握手（见 8.6 节）有些相似。每个 IPsec 实体都有一份证书，其中包含该实体的公钥。与 TLS 一样，IKE 协议让两个实体交换证书、协商鉴别与加密算法，并安全地交换用于在 IPsec SA 中创建会话密钥的密钥材料。与 TLS 不同的是，IKE 用**两个阶段**来完成这些任务。

下面结合图 8.28 中两台路由器 R1 与 R2 来考察这两个阶段。第一阶段由 R1 与 R2 之间两轮"报文对"交换组成：

- 在第一轮报文交换中，双方用 Diffie-Hellman（见本章习题）在两台路由器之间创建一个**双向 IKE SA**。为把大家彻底绕晕，这个双向 IKE SA 与 8.7.3、8.7.4 节讨论的 IPsec SA 完全是两回事。IKE SA 为两台路由器之间提供一条经鉴别并加密的信道。在这第一轮报文对交换中，为 IKE SA 建立了加密与鉴别密钥，同时也建立了一个主秘密，供第二阶段计算 IPsec SA 密钥时使用。注意在这一步中并未使用 RSA 公私钥——特别是 R1 与 R2 都没有通过用私钥签署报文来暴露自己的身份。
- 在第二轮报文交换中，双方通过签署报文向对方暴露自己的身份。但由于报文是在受保护的 IKE SA 信道上发送的，身份并不会暴露给被动的嗅探者。同样在这一阶段，双方协商 IPsec SA 将采用的 IPsec 加密与鉴别算法。

在 IKE 第二阶段，双方各建立一个方向的 SA。第二阶段结束时，双方的这两个 SA 都已建立好加密与鉴别会话密钥。此后双方就可以按 8.7.3、8.7.4 节所述，用这些 SA 发送受保护的数据报。IKE 采用两个阶段的主要动机是计算开销——由于第二阶段不涉及任何公钥密码学，IKE 能以相对很小的计算开销在两个 IPsec 实体之间生成大量 SA。

## 8.8　保护无线局域网与 4G/5G 蜂窝网

安全性在无线网络中尤为要紧：攻击者只需把一个接收设备放在发送方传输范围内的任何位置，就能嗅探帧。这在 802.11 无线局域网与 4G/5G 蜂窝网中都是如此。在这两种场景中，我们都会看到本章前面学过的基础安全技术被大量使用，包括用 nonce 做鉴别、用密码散列保证报文完整性、导出共享对称密钥以加密用户会话数据，以及广泛使用 AES 加密标准。我们还会看到——这与有线因特网的情形一样——无线安全协议一直在不断演进，因为研究人员与黑客不断发现现有安全协议的弱点与缺陷。

本节简要介绍 802.11（WiFi）与 4G/5G 场景下的无线安全。更深入的讨论可参阅那本极好读的 802.11 安全专著 [Wright 2015]、[Sauter 2021] 中对 WiFi 与 4G/5G 安全的出色论述，以及综述 [Zou 2016]。

### 8.8.1　802.11 无线局域网中的鉴别与密钥协商

讨论 802.11 安全，先指出我们期望 802.11 网络处理的两个关键安全问题（[Zou 2016] 中列举了很多）：

- **双向鉴别**。在允许移动设备完全接入某个接入点并向远程主机发送数据报之前，网络通常要先鉴别该设备——核实接入网络的移动设备的身份，并检查该设备的接入权限。同样，移动设备也想鉴别自己接入的网络，以确保自己加入的确实是它想接入的那个网络。这种双向的鉴别称为**双向鉴别**（mutual authentication）。
- **加密**。由于 802.11 帧在可被潜在坏人嗅探与操纵的无线信道上交换，加密移动设备与 AP 之间承载用户级数据的链路层帧就很重要。实践中使用对称密钥加密，因为加密与解密必须高速完成。移动设备与 AP 需要导出要用的对称加解密密钥。

WiFi 鉴别的具体做法取决于网络场景。在"个人"场景（例如家庭、咖啡馆或小型办公室）中，想加入 WiFi 网络的客户设备直接与 AP 鉴别。在"企业"场景中，设备与一台集中式鉴别服务器鉴别，该服务器通常提供对企业 LAN/WLAN 网络以及其他企业资源与服务的访问。企业场景中，AP 只充当客户设备与鉴别服务器之间的透传设备。下面分别看这两种场景下的 WiFi 鉴别。

#### WiFi 个人场景中的鉴别：WPA3-Personal

<Figure src="ch08/fig8-30.webp" caption="图 8.30　WPA3-Personal 安全性" />

图 8.30 展示了到来的设备与将鉴别它的 AP 之间的交互。为呈现客户设备加入 WiFi 网络所经历步骤的全貌，图中也画出了 7.3.4 节讲过的信标与 WLAN 关联过程。个人 WiFi 场景下鉴别所用的技术标准称为 **Wi-Fi 保护接入 3—个人版**（WPA3-Personal）。WPA3 [WiFi Alliance 2019, WiFi Alliance 2024] 是 WiFi 联盟制定的安全认证项目。自 2018 年起，想要获得 WiFi 联盟"WiFi 认证"标识的 WiFi 设备必须实现 WPA3。

WPA3-Personal 在 AP 与想加入 WiFi 网络的客户设备之间使用基于口令的鉴别。你大概已经体验过：接入该 WiFi 网络的所有设备使用同一个口令。而且你可能见过这样的口令就贴在咖啡馆墙上、人人都看得见——这意味着这种网络只能防住那些不知道口令的坏人！WPA3 所用的具体鉴别协议称为**对等实体同时鉴别**（SAE，Simultaneous Authentication of Equals）[WiFi Alliance 2024; Kumar 2024]。

WPA3-Personal 鉴别在客户设备收到 AP 的信标报文之后开始，该信标中含有一个字段，让客户知道支持 WPA3-Personal。图 8.30 所示的 SAE 鉴别协议使用四步 **Dragonfly 密钥交换**协议 [RFC 7664]：

1. **客户提交**（Client commit）。客户用口令（在 SAE 术语中称"共享秘密"）生成一个新值 element1，该值在密码学上是安全的，即无法从 element1 的值反推出口令。客户还创建一个随机值作为 nonce。客户把这些值及其他内容放在一条 SAE commit 报文中发给 AP。
1. **AP 提交**（AP commit）。AP 收到客户的 commit 报文。由于知道共享秘密，AP 能够判定生成 element1 的客户也知道共享秘密。到目前为止一切正常！接着 AP 创建 element2 与一个作为 nonce 的随机值，把这些值及其他内容放在一条 SAE commit 报文中发给客户。
1. **客户确认**（Client confirm）。客户设备同样能够判定发出 element2 的 AP 也知道共享秘密。为避免重放攻击，客户把"共享秘密与前面 SAE 各步所交换值（特别是 nonce）"的散列放在一条 SAE confirm 报文中发给 AP。
1. **AP 确认**（AP confirm）。AP 检查收到的散列，确认客户确实把正确的值散列在了一起；随后把自己对"共享秘密与前面 SAE 各步所交换值"的散列发给客户。

走完这四步 SAE 协议，客户设备与 AP 已相互鉴别，即双方都确认对方知道共享秘密，而共享秘密本身从未在网络上传输过。接着双方基于共享秘密与 SAE 协议中交换的随机值生成**成对主密钥**（PMK，pairwise master key）。由于每个加入网络的客户在 SAE 协议中生成的随机值都不同，每个客户生成的 PMK 也不同。还要注意，客户设备每次加入网络都会生成新的 PMK；正因如此，PMK 有时被称为"动态"密钥。

在关联请求/响应阶段（7.3.4 节讨论过）之后，PMK 将用于设备与 AP 之间的第二次握手，以生成在 WiFi 信道上交换的帧的链路层加密密钥。该过程见 [IEEE 802.11 2020]。

#### WiFi 企业场景中的鉴别：802.1x 与 WPA3-Enterprise

图 8.31 展示了到来的客户设备与将鉴别它的鉴别服务器之间的交互。IEEE 802.1X 标准 [IEEE 802.1x 2010] 定义了设备经由企业鉴别服务器做鉴别时的鉴别过程。在 802.1X 框架内，使用**可扩展鉴别协议**（EAP）提供鉴别。WPA3-Enterprise 认证直接采用 IEEE 802.1X 标准。

正如"可扩展"一词所暗示的，EAP 容纳了许多不同的鉴别"方法"，而 IEEE 802.1X 标准并不规定该用其中哪一种。标准化的 EAP 方法有 40 多种。其中一种在学术环境中常见的方法称为 **EAP-TTLS**（EAP-Tunneled Transport Layer Security，隧道化运输层安全）[RFC 5281]，图 8.31 所示即为该方法。

在描述 EAP-TTLS 的各步骤之前，先看全景。在到来的客户设备与 AP 之间完成最初的信标与 WLAN 关联（见 7.3.4 节）之后，鉴别本身发生在客户与鉴别服务器之间，AP 只充当透传设备。EAP-TTLS 严重依赖一条在客户与鉴别服务器之间建立的 TLS 隧道（8.6 节学过）来保护最内层的 EAP-TTLS 步骤。走完这些步骤后，TLS 隧道被拆除，PMK 用于客户设备与 AP 之间的第二次握手，以生成 WiFi 信道上交换帧的链路层加密密钥——与 WPA3-Personal 一样。

<Figure src="ch08/fig8-31.webp" caption="图 8.31　使用 EAP-TTLS 的 WPA3-Enterprise / 802.1x 安全性" />

下面细看图 8.31 中 EAP-TTLS 的步骤：

- 在步骤 1–3 中，客户设备告知 AP，它想用 EAP 做鉴别并加入网络。若 AP 配置为允许这样做，它就回应客户，并要求（且收到）一个占位身份；客户只会在保护 EAP-TTLS 与鉴别服务器之间报文的加密 TLS 隧道内部才暴露自己的真实身份。
- 在步骤 4 中，AP 用下面要讲的 RADIUS 协议，把客户加入 WiFi 网络的请求转给鉴别服务器。
- 回想 TLS 隧道建立的结果：客户已通过服务器的公钥证书鉴别了服务器，且双方已就共享秘密达成一致。但客户尚未被服务器鉴别；这一鉴别在步骤 5–8 中完成。这里鉴别服务器要求并收到客户设备的真实身份以及客户的共享秘密。一旦客户身份与口令得到验证，服务器拆除 TLS 隧道，通知 AP 该客户已通过鉴别，并向 AP 提供一个 PMK，以便 AP 与客户（客户也会导出同一个 PMK）建立 WiFi 信道的加密密钥。

#### 802.11 安全报文协议

<Figure src="ch08/fig8-32.webp" caption="图 8.32　EAP 是端到端协议。EAP 报文在移动设备与接入点之间经无线链路用 EAPoL 封装，在接入点与鉴别服务器之间经 UDP/IP 用 RADIUS 封装" />

图 8.32 展示了实现上述 802.11 安全框架所用的协议。**可扩展鉴别协议**（EAP）[RFC 3748] 定义了移动设备与鉴别服务器之间以简单请求/响应模式交互时所用的端到端报文格式。如图 8.32 所示，EAP 报文用 **EAPoL**（EAP over LAN）封装，通过 802.11 无线链路发送；这些 EAP 报文在接入点被解封装，再用 RADIUS 协议重新封装，通过 UDP/IP 发往鉴别服务器。RADIUS 服务器与协议 [RFC 2865] 虽非必需，却是事实上的标准组件。最近标准化的 DIAMETER 协议 [RFC 3588] 预计将来会取代 RADIUS。

### 8.8.2　5G 蜂窝网中的鉴别与密钥协商

本节描述 5G 网络中的双向鉴别与密钥生成机制。这里遇到的许多做法与刚学过的 802.11 网络平行，显著的例外是：在蜂窝网中，移动设备可能接在自己归属网络（即它签约的蜂窝运营商网络）上，也可能在拜访网络上漫游。后一种情况下，拜访网络与归属网络需要在鉴别移动设备、生成加密密钥时交互。在往下读之前，你也许想重读 7.3.3 与 7.5 节，重新熟悉 5G 网络体系结构。

5G 场景中双向鉴别与密钥生成的目标与 802.11 场景相同。为加密无线信道上传输的帧的内容，移动设备与基站需要导出一个共享对称加密密钥。此外，移动设备接入的网络需要鉴别该设备的身份并检查其接入权限；同样，移动设备也想鉴别自己接入的网络。网络需要鉴别移动设备也许显而易见，但反方向的鉴别需求就不那么清楚了。然而确实有文献记载，坏人运营 rogue 蜂窝基站，诱使毫无戒心的移动设备接入该恶意网络，从而使设备暴露于多种攻击之下 [Li 2017]。因此，与 802.11 WLAN 一样，移动设备在接入蜂窝网络时应当格外谨慎！

图 8.33（改编自 [3GPP TS 33.501] 中的图 6.1.2-1 与 6.1.3.1-1）展示了 5G 鉴别的场景与过程，它发生在到来的用户设备想加入 5G 网络时。在往下读之前，你也许想重读 7.4.3 节关于 5G 用户身份与注册的内容，特别是回顾图 7.42。学过 WPA3-Enterprise 鉴别之后，我们可以立刻注意到 5G 与 WPA3-Enterprise 鉴别在结构上有若干相似之处：

- 鉴别发生在设备与鉴别服务器之间。5G 基站与拜访网络中的 5G 核心网主要充当透传设备，就像 AP 以及设备与 Wi-Fi 鉴别服务器之间的网络充当透传一样。
- 两种场景都用 EAP 协议在设备与鉴别服务器之间承载鉴别报文。5G 中使用的一种 EAP 协议是 EAP-AKA'（Extensible Authentication Protocol—Authentication and Key Agreement Prime），图 8.33 用的就是它。
- 5G 与 WiFi 鉴别都利用了设备与鉴别服务器之间预先共享的秘密。在 5G 中，该共享秘密存在于设备的 SIM 卡上，以及设备归属（而非拜访）网络中的鉴别服务器上。
- WPA3-Enterprise 与 5G EAP-AKA' 都用 TLS 来安全传输鉴别报文。

<Figure src="ch08/fig8-33.webp" caption="图 8.33　使用 EAP-AKA' 的 5G 鉴别" />

Wi-Fi 与 5G 的一个差别当然是：Wi-Fi 中没有"归属网络"这个概念。这个差别至关重要。注意，5G 的鉴别决定由设备**归属**网络中的鉴别服务器（AUSF）做出，而不是由拜访网络做出。这是因为设备的身份与密码学信息只存放在两个地方：设备的 SIM 卡与归属网络。与 4G 鉴别（拜访网络扮演更重要的角色）相比，这是一项重大变化。这一变化反映出一种信念：只应信任归属网络来显式使用、存储与管理设备共享秘密密钥这类敏感信息。

下面细看 5G 鉴别的步骤：

1. 在步骤 1 中，设备向它想加入的网络之 5G 核心网中的**接入与移动性管理功能**（AMF）发送一条注册请求报文。设备在其中包含其**国际移动用户身份**（IMSI），它标识设备的归属网络以及设备在该网络中的身份。5G 核心网 AMF 的一个逻辑组件——**安全锚功能**（SEAF）——因此有足够信息定位设备归属网络 5G 核心网中的**鉴别服务器功能**（AUSF）；当设备漫游时，归属网络与正在加入的网络并不相同。SEAF 先建立一条 TLS 隧道（见 8.6 节），使 SEAF 与鉴别服务器之间的所有报文本身都得到鉴别与加密。
1. 在步骤 2 中，AUSF 联系设备归属网络中的**统一数据管理功能**（UDM）。第 7 章学过，UDM 存有归属网络各签约用户的 IMSI、加密密钥与服务授权信息。UDM 生成四样重要信息，存放在一个**鉴别向量**（AV）中返回给 AUSF：
  - 一个随机 nonce 值。
  - 一个**鉴别令牌**，这是 UDM 计算出的一个值，设备用它来验证所收到的鉴别信息确实来自其归属鉴别服务器、且是新鲜的（即不是重放）。令牌值包含一个序号，以及一个由设备秘密密钥导出的密钥（恰好只有设备与其鉴别服务器知道）。令牌由 UDM 用设备的秘密密钥签名。
  - **XRES** 是"期望响应"——鉴别服务器知道设备在收到随机 nonce 后会计算出的那个值。XRES 由 UDM 用 nonce 与设备共享秘密密钥生成。由于设备与其鉴别服务器都知道共享秘密密钥与 nonce 值（而且大概世界上只有这两个实体知道这些信息！），它们会为 XRES 计算出相同的值。这个 XRES 值将在下面的步骤 5 中使用。
  - 一个由鉴别过程导出的密钥，供拜访网络与 UE 稍后导出其他密钥（例如加密其通信所需的密钥）时使用。
1. 在步骤 3 中，归属网络中的鉴别服务器把随机 nonce 值与鉴别令牌发给拜访网络中的 SEAF，SEAF 再把这两样信息透明地转发给客户设备。
1. 设备收到 nonce 与鉴别令牌。凭借 nonce 与 SIM 卡上的共享秘密，设备判定该鉴别令牌确实由其归属网络中的鉴别服务器生成，且不是重放。接着设备按步骤 2 中 UDM 所用的同一过程，自行计算期望响应值。但愿客户设备算出的值 XRES~C~ 与 UDM 先前算出、现存于鉴别服务器中的 XRES 相同。设备把 XRES~C~ 放在一条 EAP 报文中发给 SEAF，SEAF 再把它转给鉴别服务器。接下来就是见分晓的时刻——鉴别决定！
1. 鉴别服务器把收到的 XRES~C~ 与先前算出的 XRES 相比较。若两者相同，鉴别服务器就鉴别该客户设备通过，并通知拜访网络与归属 UDM 该设备已通过鉴别。

鉴别服务器还会生成一个对称**锚密钥**（anchor key）并发给拜访网络。这个一次性密钥是用设备与鉴别服务器之间的共享秘密计算出来的，因此设备自己也能算出相同的锚密钥值。锚密钥将由设备、基站与拜访网络中的 5G 核心网功能用来计算设备会话期间所需的其他密钥（例如加密密钥）。因此在许多方面，锚密钥类似于 Wi-Fi 鉴别中的成对主密钥。

以上讨论聚焦于 5G 设备鉴别的主要步骤。还有一些参数与条件性协议步骤未在图中画出，细节见 3GPP 规范 [3GPP TS 33.501] 与 [RFC 5448]。除基本鉴别外，拜访网络还需要知道来访设备可以使用哪些服务（例如语音通话、带宽或数据用量上限、服务质量策略）。见 [3GPP TS 29.512 2022]。

本节只简要概述了 5G 网络中的双向鉴别与密钥协商。如所见，它们大量使用了本章前面学过的安全技术。上面引用的文献以及 [Cable Labs 2019] 对这些主题提供了更深入的细节。

把 WPA3-Personal、WPA3-Enterprise 与 5G 三者并排看，会发现一条清晰的设计谱系。WPA3-Personal 是**对等式**的：双方共知一个口令，用 Dragonfly 交换在不泄露口令的前提下证明"我也知道"，最终导出一个每客户端各不相同的 PMK。WPA3-Enterprise 引入**三方**：客户、AP（透传）、鉴别服务器，鉴别在 TLS 隧道内完成，PMK 由服务器交给 AP。5G 再把鉴别服务器搬到**归属网络**，中间又多了一层拜访网络与 SEAT/AUSF 的转接，理由是归属网络才是唯一有权处置长期密钥的地方。三者共同的技术骨架始终是：nonce 防重放、散列/签名保完整、DH 或共享秘密导出会话密钥、AES 加密数据。

## 8.9　运行安全：防火墙与入侵检测系统

本章通篇看到，因特网并不是个很安全的地方——坏人就在外面，制造着各种混乱。考虑到因特网的敌意本性，现在来考察一个组织的网络以及管理它的网络管理员。从网络管理员的视角看，世界干净利落地分成两个阵营：好人（属于本组织网络、应当能够相对不受约束地访问组织网络内资源的人）与坏人（其余所有人，他们对网络资源的访问必须仔细审查）。在许多组织中——从中世纪的城堡到现代企业办公楼——都有一个唯一的进出点，进出组织的所有人都在那里接受安全检查。在城堡里，这是在吊桥一端的城门处；在企业大楼里，这是保安台。在计算机网络中，进出网络的流量在那里被安全检查、记录、丢弃或转发，执行这些操作的是防火墙、入侵检测系统（IDS）与入侵防御系统（IPS）这类运行设备。

### 8.9.1　防火墙

**防火墙**（firewall）是硬件与软件的结合，它把组织的内部网络与外部因特网隔离开，允许某些分组通过、阻挡另一些分组。防火墙让网络管理员能够通过管理进出这些资源的流量，来控制外部世界与被管理网络内资源之间的访问。防火墙有三个目标：

- **所有从外到内、以及从内到外的流量都必须经过防火墙**。图 8.34 展示了一个端端正正坐在被管理网络与因特网其余部分边界上的防火墙。虽然大型组织可能使用多级防火墙或分布式防火墙 [Skoudis 2006]，但把防火墙放在网络单一接入点处（如图 8.34 所示）更便于管理与执行安全访问策略。
- **只有本地安全策略所定义的授权流量才允许通过**。既然进出机构网络的所有流量都经过防火墙，防火墙就能把访问限制在授权流量上。
- **防火墙本身对渗透免疫**。防火墙本身也是连在网络上的设备；若设计或安装不当，它可能被攻破，此时它只提供一种虚假的安全感（这比根本没有防火墙还糟！）。

Palo Alto Networks、Cisco 与 Check Point 是当今领先的防火墙厂商中的几家。此外，如第 4、5 章所述，如今防火墙常实现在路由器中，并通过 SDN 远程控制。

<Figure src="ch08/fig8-34.webp" caption="图 8.34　防火墙位于被管理网络与外部世界之间" />

防火墙可分为三类：传统分组过滤器、状态过滤器与应用网关。下面依次讨论。

#### 传统分组过滤器

如图 8.34 所示，组织通常有一台网关路由器，把内部网络连到其 ISP（从而连到更大的公共因特网）。进出内部网络的所有流量都经过这台路由器，分组过滤就发生在这里。**分组过滤器**（packet filter）逐个孤立地检查每个数据报，依据管理员设定的规则判断该数据报应被允许通过还是应被丢弃。过滤决策通常基于：

- IP 源地址或目的地址；
- IP 数据报字段中的协议类型：TCP、UDP、ICMP、OSPF 等等；
- TCP 或 UDP 的源端口与目的端口；
- TCP 标志比特：SYN、ACK 等等；
- ICMP 报文类型；
- 对离开网络与进入网络的数据报采用不同规则；
- 对不同路由器接口采用不同规则。

网络管理员依据组织策略配置防火墙。策略既可能考虑用户生产力与带宽占用，也可能考虑组织的安全关切。表 8.5 列出了组织可能有的若干策略，以及如何用分组过滤器实现它们。例如，若组织不希望有任何进入的 TCP 连接，只允许发往其公共 Web 服务器的连接，它可以阻挡所有进入的 TCP SYN 报文段，但目的端口为 80、目的 IP 地址对应 Web 服务器的 TCP SYN 报文段除外。若组织不希望其用户用因特网电台应用霸占接入带宽，它可以阻挡所有非关键 UDP 流量（因特网电台常用 UDP 传输）。若组织不希望内部网络被外人测绘（traceroute），它可以阻挡所有离开本组织网络的 ICMP TTL 超时报文。

<p class="tbl-cap">表 8.5　组织网络 130.207/16（Web 服务器为 130.207.244.203）的策略及相应的过滤规则</p>

| **策略** | **防火墙设置** |
| --- | --- |
| 不允许对外 Web 访问 | 丢弃所有发往任意 IP 地址、端口 80 的外出分组 |
| 除本组织公共 Web 服务器外，不允许进入的 TCP 连接 | 丢弃所有进入的 TCP SYN 分组，但发往 130.207.244.203、端口 80 的除外 |
| 防止网络电台耗尽可用带宽 | 丢弃所有进入的 UDP 分组——DNS 分组除外 |
| 防止本网络被用于 smurf DoS 攻击 | 丢弃所有发往"广播"地址（例如 130.207.255.255）的 ICMP ping 分组 |
| 防止本网络被 traceroute | 丢弃所有外出的 ICMP TTL 超时流量 |

过滤还可以基于地址与端口号的组合。例如，一台过滤路由器可以转发所有 Telnet 数据报（端口号为 23 的那些），但发往或来自某个特定 IP 地址列表的除外。这条策略允许与允许列表中的主机建立 Telnet 连接。遗憾的是，基于外部地址的策略无法防范源地址被伪造的数据报。

过滤还可以基于 TCP ACK 比特是否置位。如果组织想让内部客户连接外部服务器，却想阻止外部客户连接内部服务器，这个技巧非常有用。回想 3.5 节：每条 TCP 连接的第一个报文段其 ACK 比特置 0，而该连接中所有其他报文段的 ACK 比特置 1。因此，若组织想阻止外部客户向内部服务器发起连接，只需过滤掉所有 ACK 比特置 0 的进入报文段。这条策略会杀死所有源自外部的 TCP 连接，却允许源自内部的连接。

防火墙规则在路由器中以**访问控制列表**（ACL）实现，每个路由器接口各有自己的列表。表 8.6 给出组织 222.22/16 的一张访问控制列表，它用于把路由器连到组织外部 ISP 的那个接口。规则自上而下应用于通过该接口的每个数据报。前两条规则合起来允许内部用户浏览网页：第一条允许任何目的端口为 80 的 TCP 分组离开本组织网络；第二条允许任何源端口为 80 且 ACK 比特置位的 TCP 分组进入本组织网络。注意，若某个外部源试图与内部主机建立 TCP 连接，该连接将被阻断，即使源端口或目的端口是 80 也一样。后两条规则合起来允许 DNS 分组进出本组织网络。总之，这张相当严格的访问控制列表阻挡了除"由组织内部发起的 Web 流量"与"DNS 流量"之外的所有流量。[SEI Best Practices 2017] 讨论了防火墙处网络边界防护的最佳实践。

#### 状态分组过滤器

在传统分组过滤器中，过滤决策是对每个分组孤立做出的。**状态过滤器**（stateful filter）则真正跟踪 TCP 连接，并利用这些知识做出过滤决策。

为理解状态过滤器，重新审视表 8.6 中的访问控制列表。表 8.6 的访问控制列表虽然相当严格，却仍然允许任何从外部到来、ACK = 1 且源端口为 80 的分组通过过滤器。攻击者可以利用这类分组，用畸形分组撞垮内部系统、实施拒绝服务攻击或测绘内部网络。天真的解决办法是把 TCP ACK 分组也一并阻断，但那样会阻止组织内部用户浏览网页。

状态过滤器通过在一张**连接表**（connection table）中跟踪所有进行中的 TCP 连接来解决这个问题。这是可行的，因为防火墙能通过观察三次握手（SYN、SYNACK 与 ACK）察觉一条新连接的开端；也能在看到某条连接的 FIN 分组时察觉其结束。防火墙还可以（保守地）假定：若在比如 60 秒内没有看到该连接上的任何活动，则该连接已结束。表 8.7 给出一张防火墙连接表的例子，它表明当前有三条进行中的 TCP 连接，且都源自组织内部。此外，状态过滤器在访问控制列表中新增了一列"检查连接"，如表 8.8 所示。注意表 8.8 与表 8.6 的访问控制列表完全相同，只是现在它指明对其中两条规则应当检查连接。

下面走几个例子，看连接表与扩展后的访问控制列表如何配合工作。假设攻击者试图把畸形分组送进组织网络：他发送一个 TCP 源端口为 80 且 ACK 标志置位的数据报，其源端口号为 12543、源 IP 地址为 150.23.23.155。该分组到达防火墙时，防火墙检查表 8.8 的访问控制列表，其中指明在允许该分组进入组织网络之前还必须检查连接表。防火墙于是检查连接表，发现该分组不属于任何进行中的 TCP 连接，于是拒绝该分组。第二个例子：假设某个内部用户想浏览一个外部网站。由于该用户首先发送一个 TCP SYN 报文段，该用户的 TCP 连接就被记入连接表。当 Web 服务器回送分组（ACK 比特必然置位）时，防火墙检查连接表，发现有一条相应的连接正在进行中，于是让这些分组通过，从而不干扰内部用户的网页浏览活动。

#### 应用网关

在上述例子中可以看到，分组级过滤让组织能够基于 IP 与 TCP/UDP 首部内容（包括 IP 地址、端口号与确认比特）做粗粒度过滤。但如果组织想只对一组受限的内部**用户**（而不是 IP 地址）提供 SSH 服务呢？如果组织想要求这些特权用户先鉴别自己，才允许其向外部世界建立 SSH 会话呢？这类任务超出了传统过滤器与状态过滤器的能力。确实，关于内部用户身份的信息属于应用层数据，并不包含在 IP/TCP/UDP 首部中。

要获得更细粒度的安全，防火墙必须把分组过滤器与应用网关结合起来。**应用网关**（application gateway）越过 IP/TCP/UDP 首部，依据应用数据做策略决策。应用网关是一台特定于应用的服务器，所有应用数据（入向与出向）都必须经过它。多台应用网关可以运行在同一台主机上，但每台网关都是独立服务器，各有自己的进程。

为体会应用网关，我们来设计一个只允许一组受限内部用户向外部 SSH、并阻止所有外部客户向内部 SSH 的防火墙。这样的策略可以通过组合一台（位于路由器中的）分组过滤器与一台 SSH 应用网关来实现，如图 8.35 所示。路由器的过滤器配置为阻断除源自应用网关 IP 地址之外的所有 SSH 连接。这样的过滤配置迫使所有出向 SSH 连接都经过应用网关。现在考虑某个想向外部世界 SSH 的内部用户：他必须先与应用网关建立一条 Telnet 会话。网关中一个监听到来 SSH 会话的应用提示用户输入用户 ID 与口令；用户提供这些信息后，应用网关检查该用户是否有权向外部世界 SSH。若没有，网关就终止该内部用户到网关的 SSH 连接；若有，网关 (1) 提示用户输入他想连接的外部主机的主机名，(2) 在网关与该外部主机之间建立一条 SSH 会话，(3) 把从该用户到来的所有数据转发给外部主机，并把从外部主机到来的所有数据转发给该用户。因此，SSH 应用网关不仅执行用户授权，还同时充当 SSH 服务器与 SSH 客户端，在用户与远程 SSH 服务器之间转发信息。注意过滤器会允许步骤 (2)，因为那条 SSH 连接是网关向外部世界发起的。

<Figure src="ch08/fig8-35.webp" caption="图 8.35　由应用网关与过滤器组成的防火墙" />

<AsideCard title="案例：匿名与隐私">

假设你想访问一个争议性网站（例如某个政治活动站点），并且 (1) 不想向该网站暴露自己的 IP 地址，(2) 不想让你的本地 ISP（可能是家庭或办公室 ISP）知道你正在访问该站点，(3) 不想让本地 ISP 看到你与该站点交换的数据。若你采用不经任何加密、直接连接该网站的传统做法，这三条全都做不到。即使你使用 TLS，前两条也做不到：你发出的每个数据报都把源 IP 地址呈给了该网站；而你发出的每个分组的目的地址都很容易被本地 ISP 嗅探到。

要获得隐私与匿名，你可以改用"可信代理服务器 + TLS"的组合，如图 8.36 所示。做法是先与可信代理建立一条 TLS 连接，然后把对目标站点某页面的 HTTP 请求送进这条 TLS 连接。代理收到 TLS 加密的 HTTP 请求后解密，把明文 HTTP 请求转发给该网站；网站回应给代理，代理再把回应通过 TLS 转发给你。由于网站只看到代理的 IP 地址、看不到你客户端的地址，你确实获得了对该网站的匿名访问；又由于你与代理之间的所有流量都是加密的，本地 ISP 无法通过记录你访问的站点或录制你交换的数据来侵犯你的隐私。如今许多公司（例如 proxify.com）提供这类代理服务。

当然，在这个方案中你的代理知道一切：它知道你的 IP 地址与你所浏览站点的 IP 地址，也能看到你与该网站之间交换的全部明文流量。因此这种方案的好坏只取决于代理的可信程度。更稳健的做法（TOR 匿名与隐私服务采用）是让你的流量经过一串**不串通**的代理服务器 [TOR 2020]。具体来说，TOR 允许独立个人向其代理池贡献代理。当用户用 TOR 连接某服务器时，TOR（从其代理池中）随机选出一条由三个代理组成的链，让客户与服务器之间的所有流量都走这条链。这样，只要这些代理不串通，就没人知道你的 IP 地址与该目标网站之间发生过通信。此外，虽然最后一个代理与服务器之间传的是明文，但最后一个代理并不知道是哪个 IP 地址在收发这些明文。

<Figure src="ch08/fig8-36.webp" caption="图 8.36　用代理提供匿名与隐私" />

</AsideCard>

应用网关也并非没有缺点。第一，每个应用都需要一台不同的应用网关。第二，要付出性能代价，因为所有数据都要经网关转发——当多个用户或多个应用共用同一台网关机器时，这尤其成问题。最后，客户端软件必须知道在用户发出请求时如何联系网关，也必须知道如何告诉应用网关去连接哪台外部服务器。

### 8.9.2　入侵检测系统

刚才看到，分组过滤器（传统的与状态的）在决定让哪些分组通过防火墙时，检查的是 IP、TCP、UDP 与 ICMP 首部字段。然而要检测许多类型的攻击，我们需要做**深度分组检查**（deep packet inspection），即越过首部字段，深入到分组承载的实际应用数据中去看。如 8.9.1 节所见，应用网关常常做深度分组检查，但应用网关只对某个特定应用做这件事。

显然，这里还有另一类设备的用武之地——它不仅检查经过它的所有分组的首部（像分组过滤器那样），还做深度分组检查（这一点与分组过滤器不同）。当这样的设备观察到可疑的分组或可疑的分组序列时，它可以阻止这些分组进入组织网络；或者，由于该活动只是"被认定为可疑"，它可以让分组通过，但向网络管理员发送告警，管理员随后可以细看这些流量并采取适当行动。观察到潜在恶意流量时产生告警的设备称为**入侵检测系统**（IDS）；过滤掉可疑流量的设备称为**入侵防御系统**（IPS）。本节把 IDS 与 IPS 放在一起研究，因为这些系统最有趣的技术之处在于它们**如何**检测可疑流量（而不是它们究竟发告警还是丢分组）。以下把 IDS 系统与 IPS 系统统称为 IDS 系统。

IDS 可用于检测范围很广的攻击，包括网络测绘（例如来自 nmap 的）、端口扫描、TCP 栈扫描、DoS 带宽洪泛攻击、蠕虫与病毒、操作系统漏洞攻击以及应用漏洞攻击。（网络攻击综述见 1.6 节。）如今有数千个组织使用 IDS 系统。这些已部署系统中有许多是专有产品，由 Palo Alto Networks、Check Point 以及其他安全与路由/交换机设备厂商销售；但也有许多是公有领域系统，例如极受欢迎的 Snort IDS（下面很快讨论）。

一个组织可以在其网络中部署一个或多个 IDS 传感器。图 8.37 展示了一个部署了三个 IDS 传感器的组织。部署多个传感器时，它们通常协同工作，把可疑流量活动的信息送给一台中央 IDS 处理器，由后者汇总并整合信息，在认为适当时向网络管理员发出告警。图 8.37 中，该组织把网络划成两个区域：一个**高安全区**，由分组过滤器与应用网关保护，并由 IDS 传感器监控；一个安全性较低的区域——称为**非军事区**（DMZ，demilitarized zone）——只由分组过滤器保护，但也由 IDS 传感器监控。注意 DMZ 中包括需要与外部世界通信的组织服务器，例如其公共 Web 服务器与权威 DNS 服务器。

<Figure src="ch08/fig8-37.webp" caption="图 8.37　某组织部署的过滤器、应用网关与 IDS 传感器" />

此时你也许在想：为什么要多个 IDS 传感器？为什么不在图 8.37 中分组过滤器后面（甚至与分组过滤器集成在一起）只放一个 IDS 传感器？下面很快会看到，IDS 不仅要做深度分组检查，还必须把每个经过的分组与数万条"特征"（signature）相比较；这可能意味着相当大的处理量，尤其当组织从因特网收到 Gbit/s 级流量时。把 IDS 传感器放在更下游，每个传感器只看到组织流量的一部分，就更容易跟上。不过，如今已有高性能的 IDS 与 IPS 系统，许多组织实际上只在其接入路由器附近放一个传感器就够了。

IDS 系统大体上分为**基于特征的**（signature-based）与**基于异常的**（anomaly-based）两类。基于特征的 IDS 维护一个庞大的攻击特征数据库，每条特征是一组关于某种入侵活动的规则。一条特征可能只是关于单个分组的一串特征描述（例如源与目的端口号、协议类型、分组载荷中某个特定比特串），也可能涉及一系列分组。这些特征通常由研究已知攻击的资深网络安全工程师编写；组织的网络管理员可以定制这些特征，或把自己的特征加入数据库。

在运行上，基于特征的 IDS 嗅探经过它的每个分组，把每个嗅探到的分组与其数据库中的特征相比较。若某个分组（或某组分组）与数据库中的某条特征匹配，IDS 就产生一条告警。告警可以通过电子邮件发给网络管理员，可以送给网络管理系统，也可以简单记录下来供日后检查。

基于特征的 IDS 系统虽然部署广泛，却有若干局限。最重要的是，它们要求事先掌握该攻击才能生成准确的特征。换言之，基于特征的 IDS 对尚未被记录下来的新攻击完全视而不见。另一个缺点是：即使匹配了某条特征，该活动也未必真是攻击，于是产生误报。最后，由于每个分组都必须与一个庞大的特征集合相比较，IDS 可能被处理量压垮，实际上反而漏掉许多恶意分组。

基于异常的 IDS 在观察正常运行的流量时建立一份流量画像，然后寻找统计上异常的报文流，例如 ICMP 分组占比高得离谱，或端口扫描与 ping 扫描突然指数增长。基于异常的 IDS 系统的妙处在于，它们不依赖关于已有攻击的先验知识——也就是说，它们有可能检测出新的、未被记录的攻击。另一方面，区分正常流量与统计上异常的流量是个极其困难的问题。迄今为止，多数 IDS 部署仍以基于特征为主，尽管有些也包含一些基于异常的功能。

#### Snort

Snort 是一个公有领域的开源 IDS，已有数十万套部署 [Snort 2012; Koziol 2003]。它可运行在 Linux、UNIX 与 Windows 平台上，使用通用嗅探接口 libpcap（Wireshark 与许多其他分组嗅探器也用它）。它能轻松处理 100 Mbit/s 的流量；对于 Gbit/s 级速率的安装，可能需要多个 Snort 传感器。

为体会 Snort，来看一条 Snort 特征的例子：

```text
alert icmp $EXTERNAL_NET any -> $HOME_NET any
(msg:"ICMP PING NMAP"; dsize: 0; itype: 8;)
```

任何从外部（`$EXTERNAL_NET`）进入组织网络（`$HOME_NET`）、类型为 8（ICMP ping）且载荷为空（`dsize = 0`）的 ICMP 分组都会匹配这条特征。由于 nmap（见 1.6 节）生成的 ping 分组正是这些特征，这条特征就是用来检测 nmap ping 扫描的。当某个分组匹配这条特征时，Snort 产生一条包含消息"ICMP PING NMAP"的告警。

Snort 最令人印象深刻之处，也许是维护其特征数据库的庞大用户与安全专家社区。通常在新攻击出现后几小时内，Snort 社区就会写出并发布一条攻击特征，随后被全世界数十万套 Snort 部署下载。此外，利用 Snort 特征语法，网络管理员可以通过修改现有特征或创建全新特征，把特征裁剪成适合本组织需要的样式。

## 8.10　小结

本章考察了我们的秘密恋人 Bob 与 Alice 可以用来安全通信的各种机制。我们看到，Bob 与 Alice 关心**机密性**（只有他们两人能理解所传报文的内容）、**端点鉴别**（他们确信自己在与对方说话）与**报文完整性**（他们确信报文在途中未被改动）。当然，安全通信的需求并不限于秘密恋人。事实上，8.5 至 8.8 节表明，安全性可以用在网络体系结构的各个层次上，以抵御手头握有大量可能攻击手段的坏人。

本章前半部分给出了安全通信背后的各种原理。8.2 节讨论了加解密数据的密码学技术，包括对称密钥密码学与公钥密码学，并以 DES 与 RSA 作为当今网络所用两大类密码学技术的具体案例加以考察。

8.3 节考察了提供报文完整性的两种途径：报文鉴别码（MAC）与数字签名。这两种途径有许多相似之处：都用密码散列函数，都能让我们验证报文的来源以及报文本身的完整性。一个重要差别是 MAC 不依赖加密，而数字签名需要一套公钥基础设施。这两种技术在实践中的应用都很广泛，8.5 至 8.8 节已经看到。此外，数字签名被用来创建数字证书，而数字证书对验证公钥的有效性至关重要。8.4 节考察了端点鉴别，并引入 nonce 来防范重放攻击。

8.5 至 8.8 节考察了若干在实践中被广泛使用的安全网络协议。我们看到，对称密钥密码学是 PGP、TLS、IPsec 与无线安全的核心；公钥密码学对 PGP 与 TLS 都至关重要；PGP 用数字签名提供报文完整性，而 TLS 与 IPsec 用 MAC。我们还探讨了无线网络的安全性，包括 WiFi 网络与 4G/5G 蜂窝网络。既然已经理解了密码学的基本原理，又研究了这些原理实际如何被使用，你现在就有能力设计自己的安全网络协议了！

有了 8.2 至 8.8 节的技术，Bob 与 Alice 就能安全通信了。但机密性只是网络安全图景的一小部分。如 8.9 节所学，网络安全的焦点正日益转向保护网络基础设施，以抵御坏人的潜在猛攻。因此本章后半部分讨论了防火墙与 IDS 系统，它们检查进出组织网络的分组。

| RSA 加解密 | $c = m^{e} \bmod n$ | $m = c^{d} \bmod n$，$n = p q$ |

| MAC 定义 | $H(s + m)$ | $s$ 为鉴别密钥 |
| 数字签名 | $K_{B}^{-}(H(m))$ | 先取散列再签，省算力 |
| TLS 会话密钥 | 4 把 | $E_{B}, M_{B}, E_{A}, M_{A}$ |
| TLS 1.3 握手 | 1 个 RTT | QUIC 下可为 0 |
| IPsec 协议号 | 50（ESP）/ 51（AH） | 外层 IPv4 首部字段 |
