运输层位于应用层与网络层之间，是分层网络体系结构中承上启下的核心一环。它的关键职责，是**直接为运行在不同主机上的应用进程提供通信服务**。本章沿用的教学思路是：在"运输层原理"与"这些原理在现有协议中的实现"之间来回切换；一如既往，重点放在因特网协议上，尤其是 TCP 与 UDP 这两个运输层协议。

我们首先讨论运输层与网络层之间的关系，为考察运输层的第一个关键功能作铺垫——把网络层提供的**主机到主机**交付服务，扩展为运行在端系统上的**进程到进程**交付服务。这一功能将在因特网的无连接运输协议 UDP 中得到具体体现。

随后我们回到原理，直面计算机网络中最基本的问题之一：两个实体如何在可能丢失和损坏数据的介质上**可靠地**通信？我们将沿着由简到繁（也越来越接近真实）的场景，逐步搭建起运输协议解决该问题所用的整套技术，然后再看这些原理如何体现在因特网的面向连接运输协议 TCP 之中。

接下来是第二个根本性问题：如何控制运输层实体的发送速率，以避免网络内部出现拥塞，或在拥塞发生后从中恢复。我们会分析拥塞的成因与代价，介绍常用的拥塞控制技术；在建立起对拥塞控制问题的扎实理解之后，再考察 TCP 各种"变体"所采用的不同拥塞控制方案。

## 3.1　引言与运输层服务

前两章已经零散地提到过运输层的作用及其提供的服务，这里先做一个快速回顾。

运输层协议为运行在不同主机上的应用进程之间提供**逻辑通信**（logical communication）。所谓"逻辑"，是指从应用程序的角度看，仿佛运行这些进程的主机是直接相连的；而实际上，两台主机可能位于地球的两端，中间经过大量路由器和各种类型的链路。应用进程利用运输层提供的逻辑通信互相发送报文，而不必操心承载这些报文的物理基础设施的细节。图 3.1 给出了逻辑通信的示意。

<Figure src="ch03/fig3-01.webp" caption="图 3.1　运输层为运行在不同主机上的应用进程提供逻辑通信，而不是物理通信。" />

如图 3.1 所示，运输层协议实现在**端系统**中，而不在网络路由器中。在发送端，运输层把从发送方应用进程收到的应用层报文转换成运输层分组，用因特网的术语说就是**报文段**（segment）。具体做法（见 1.5.2 节）是：把应用报文（必要时）划分成较小的块，并为每一块加上运输层首部，从而生成运输层报文段。随后，运输层把报文段交给发送端系统的网络层；在网络层，报文段被封装进一个网络层分组（即数据报），再发往目的地。

需要强调的是：**网络路由器只处理数据报的网络层字段**，也就是说，它们既不检查、也不识别封装在数据报中的运输层报文段的字段。在接收端，网络层从数据报中取出运输层报文段，上交运输层；运输层处理该报文段，使报文段中的数据可供接收方应用使用。

网络应用可以使用不止一种运输层协议。例如，因特网就有两个：TCP 和 UDP。它们各自向调用它的应用提供一组不同的运输层服务。

### 3.1.1　运输层与网络层的关系

回忆一下，在协议栈中运输层紧挨在网络层之上。运输层协议为运行在不同主机上的**进程**之间提供逻辑通信，而网络层协议为**主机**之间提供逻辑通信。这一区别很细微，却很重要。我们借助一个家庭类比来体会它。

考虑两户人家，一户在东海岸，一户在西海岸，每家有十几个孩子，两家孩子是表亲。孩子们热衷于互相写信——每个孩子每周给每个表亲写一封信，每封信都装进单独的信封，由传统的邮政服务投递。于是，每户每周要向另一户寄出 144 封信。（要是他们用电子邮件，能省下一大笔钱！）每户人家都有一个孩子负责收发信件：西海岸家是 Ann，东海岸家是 Bill。每周 Ann 走访她所有的兄弟姐妹，把信收齐后交给邮递员，邮递员每天上门一次。西海岸家收到来信时，也由 Ann 负责把信分发给兄弟姐妹。Bill 在东海岸干着同样的活。

在这个例子里，**邮政服务**在两户人家之间提供逻辑通信——它把邮件从一家搬到另一家，而不是从一个人送到另一个人。另一方面，**Ann 和 Bill** 在表亲之间提供逻辑通信——他们从兄弟姐妹那里收信，也把信送到兄弟姐妹手中。请注意，在表亲们看来，Ann 和 Bill **就是**邮政服务，尽管 Ann 和 Bill 只是整个端到端投递过程中的一部分（端系统那一部分）。这个家庭类比恰好可以用来解释运输层与网络层的关系：

<p class="tbl-cap">表 3.1　家庭类比：运输层与网络层的分工</p>

| **概念** | **家庭类比** |
| --- | --- |
| 应用报文 | 信封里的信件 |
| 进程 | 表亲 |
| 主机（亦称端系统） | 两户人家 |
| 运输层协议 | Ann 和 Bill |
| 网络层协议 | 邮政服务（含邮递员） |

继续这个类比。注意 Ann 和 Bill 的所有工作都在各自家里完成；他们不参与中间邮件处理中心的分拣工作，也不参与把邮件从一个中心运到另一个中心。类似地，运输层协议只存在于端系统中。在一个端系统内部，运输协议把报文从应用进程搬到网络边缘（即网络层），反之亦然；但它对报文在网络核心中如何被搬运没有任何发言权。事实上，正如图 3.1 所示，中间路由器对运输层可能加到应用报文上的任何信息，既不处理也不识别。

再往下讲这个家庭故事。假设 Ann 和 Bill 去度假了，由另一对表亲——比如 Susan 和 Harvey——临时顶替，负责家庭内部的收信与分发。不幸的是，Susan 和 Harvey 干活的方式与 Ann 和 Bill 并不完全相同：他们年纪小，取信送信的频率更低，偶尔还会把信弄丢（有时信被家里的狗啃了）。因此，Susan 和 Harvey 提供的服务集合（即**服务模型**）与 Ann 和 Bill 不同。与此类似，一个计算机网络可能提供多种运输协议，每种协议向应用提供不同的服务模型。

Ann 和 Bill 所能提供的服务，显然受制于邮政服务所能提供的服务。例如，如果邮政服务并不保证两户之间投递时间不超过某个上界（比如三天），那么 Ann 和 Bill 就无论如何也无法保证任意一对表亲之间的最大时延。同样地，运输协议能提供哪些服务，往往受制于底层网络层协议的服务模型。如果网络层协议无法为在主机之间传送的运输层报文段提供时延或带宽保证，那么运输层协议也无法为在进程之间传送的应用报文提供时延或带宽保证。

不过，即使底层网络协议在网络层并不提供相应服务，运输协议仍然可以提供某些服务。例如，本章将会看到，即便底层网络协议是不可靠的——会丢失、出错或重复分组——运输协议依然可以向应用提供可靠数据传输服务。再如（第 8 章讨论网络安全时会展开），即使网络层无法保证运输层报文段的机密性，运输协议也可以用加密来保证应用报文不被入侵者读取。

### 3.1.2　因特网运输层概述

因特网向应用层提供两个截然不同的运输层协议。一个是 UDP（User Datagram Protocol，用户数据报协议），向调用它的应用提供**不可靠的、无连接**的服务；另一个是 TCP（Transmission Control Protocol，传输控制协议），提供**可靠的、面向连接**的服务。开发网络应用时，应用开发者必须在这两个运输协议中选定一个；正如 2.6 节所见，开发者在创建套接字时就要在 UDP 与 TCP 之间作出选择。

为简化术语，本书把运输层分组统称为**报文段**（segment）。需要说明的是，因特网文献（例如各种 RFC）对 TCP 的运输层分组也称报文段，但对 UDP 的分组常称**数据报**（datagram）；然而同一批文献又把网络层分组也叫数据报！对于一本入门教材而言，我们认为把 TCP 和 UDP 的分组都称为报文段、而把"数据报"一词留给网络层分组，更不容易造成混淆。

在简要介绍 UDP 和 TCP 之前，先就因特网的网络层说几句。（网络层的细节见第 4、5 章。）因特网的网络层协议有一个名字——IP，即网际协议（Internet Protocol）。IP 在主机之间提供逻辑通信，其服务模型是**尽力而为的交付服务**（best-effort delivery service）。这意味着 IP 会"尽最大努力"在通信的主机之间交付报文段，但不作任何保证：它不保证报文段一定送达，不保证按序送达，也不保证报文段中数据的完整性。因此，IP 被称为**不可靠服务**。另外，每台主机至少有一个网络层地址，即所谓的 IP 地址。IP 编址将在第 4 章详述；本章只需记住每台主机都有一个 IP 地址即可。

了解了 IP 的服务模型，现在可以概括 UDP 与 TCP 各自提供的服务模型了。UDP 和 TCP 最根本的职责，是把 IP 在两个端系统之间的交付服务，扩展为运行在这两个端系统上的两个进程之间的交付服务。把主机到主机的交付扩展为进程到进程的交付，称为**运输层的多路复用与多路分解**（multiplexing and demultiplexing），下一节将专门讨论。此外，UDP 与 TCP 都通过在报文段首部中加入差错检测字段来提供完整性检查。**进程到进程的数据交付**与**差错检查**这两项最基本的运输层服务，恰恰是 UDP 提供的全部服务！也就是说，与 IP 一样，UDP 是不可靠服务——它不保证一个进程发送的数据完好无损（甚至不保证能够到达）目的地进程。UDP 将在 3.3 节详述。

TCP 则向应用提供若干额外的服务。首要的是**可靠数据传输**：TCP 借助流量控制、序号、确认和定时器（本章将逐一展开的技术），确保数据从发送进程正确、有序地交付给接收进程。这样，TCP 就把 IP 在端系统之间的不可靠服务，转变成了进程之间的可靠数据传输服务。TCP 还提供**拥塞控制**。拥塞控制与其说是提供给调用它的应用的一种服务，不如说是为整个因特网、为公共利益提供的一种服务：它通过调节 TCP 连接发送端向网络注入流量的速率来实现这一点。相比之下，UDP 流量是不受调节的——使用 UDP 运输的应用想以多快速率发送、想发多久，就可以发多久。

一个既提供可靠数据传输、又提供拥塞控制的协议必然是复杂的。我们需要好几节的篇幅来讨论可靠数据传输与拥塞控制的原理，还需要额外的篇幅来讨论 TCP 协议本身，这些内容分布在 3.4 至 3.7 节。本章采取的办法是在基本原理与 TCP 协议之间交替推进：先在最一般的情形下讨论可靠数据传输，再讨论 TCP 具体如何实现可靠数据传输；先在最一般的情形下讨论拥塞控制，再讨论 TCP 的各种版本如何实施拥塞控制。不过在进入这些精彩内容之前，还是先看看运输层的多路复用与多路分解。

## 3.2　多路复用与多路分解

本节讨论运输层的**多路复用**与**多路分解**，也就是把网络层提供的**主机到主机**交付服务，扩展为运行在主机上的应用之间的**进程到进程**交付服务。为使讨论具体，我们仍放在因特网的语境中展开；但需要强调，任何计算机网络都需要多路复用/多路分解服务。

在目的主机上，运输层从紧邻其下的网络层接收报文段，并负责把这些报文段中的数据交付给主机中正确的应用进程。看一个例子：假设你坐在电脑前，一边下载网页，一边开着一个 Zoom 会话和两个 ssh 会话。那么你共有四个网络应用进程在运行——两个 ssh 进程、一个 Zoom 进程、一个 HTTP 进程。当电脑中的运输层从下层网络层收到数据时，它必须把收到的数据交给这四个进程中的一个。下面看看这是如何做到的。

首先回忆 2.6 节：一个进程（作为某个网络应用的一部分）可以拥有一个或多个**套接字**（socket）。套接字是数据从网络进入进程、以及从进程流向网络的"门"。因此，如图 3.2 所示，接收主机中的运输层实际上并不直接把数据交给进程，而是交给一个作为中介的套接字。由于在任一时刻接收主机中可能有多个套接字，每个套接字都必须有唯一的标识符。标识符的格式取决于该套接字是 UDP 还是 TCP 套接字，稍后讨论。

<Figure src="ch03/fig3-02.webp" caption="图 3.2　运输层的多路复用与多路分解" />

现在考虑接收主机如何把一个到达的运输层报文段导向正确的套接字。每个运输层报文段中都有若干字段用于此目的。在接收端，运输层检查这些字段，确定接收套接字，然后把报文段导向该套接字。把运输层报文段中的数据交付给正确套接字的工作，称为**多路分解**（demultiplexing）；而在源主机上从不同套接字收集数据块、为每个数据块封装首部信息（这些信息随后将用于多路分解）以生成报文段、再把报文段交给网络层的工作，称为**多路复用**（multiplexing）。

注意，图 3.2 中间那台主机中的运输层，必须把从下层网络层到达的报文段分解给上面的进程 P1 或 P2——做法是把到达报文段的数据导向相应进程的套接字。同时，该主机的运输层还必须从这些套接字收集外出数据，形成运输层报文段，再下交给网络层。虽然我们是在因特网运输协议的语境中引入复用与分解的，但应当认识到：只要某一层（运输层或其他层）上的单个协议被上一层中的多个协议所使用，就存在复用与分解的问题。

为了说明多路分解工作，回想上一节的家庭类比。每个孩子由他/她的名字来标识。当 Bill 从邮递员那里收到一批邮件时，他通过查看信件是写给谁的来执行"多路分解"，然后亲手把邮件分发给兄弟姐妹。而 Ann 从兄弟姐妹那里收集信件、把收齐的邮件交给邮递员时，执行的则是"多路复用"。

理解了运输层复用与分解的作用，下面看看主机中实际是怎么做的。由上面的讨论可知，运输层多路复用需要：(1) 套接字有唯一标识符；(2) 每个报文段有特殊字段来指明该报文段所要交付的套接字。这两个特殊字段如图 3.3 所示，即**源端口号字段**和**目的端口号字段**。（UDP 和 TCP 报文段还有其他字段，将在本章后续各节讨论。）

<Figure src="ch03/fig3-03.webp" caption="图 3.3　运输层报文段中的源端口号与目的端口号字段" />

每个端口号是一个 16 位数，取值范围 0～65535。其中 0～1023 的端口号称为**周知端口号**（well-known port number），受到限制使用，即保留给周知的应用协议，如 HTTP（使用端口号 80）和 FTP（使用端口号 21）。周知端口号的列表见 RFC 1700，并在 http://www.iana.org 上更新 [RFC 3232]。当我们开发一个新应用（例如 2.6 节开发的那个简单应用）时，必须为其分配一个端口号。

至此，运输层如何实现多路分解服务应当已经清楚了：主机中的每个套接字都可以分配一个端口号；当报文段到达主机时，运输层检查报文段中的目的端口号，把报文段导向相应的套接字，报文段的数据便经由该套接字进入与之相连的进程。正如我们将看到的，UDP 基本上就是这么做的；但 TCP 的复用/分解则要微妙一些。

### 用 UDP 进行无连接的多路复用与多路分解

回忆 2.6.1 节：主机中运行的 Python 程序可以用下面这行代码创建一个 UDP 套接字：

```text
clientSocket = socket(AF_INET, SOCK_DGRAM)
```

以这种方式创建 UDP 套接字时，运输层会自动为该套接字分配一个端口号，具体是分配 1024～65535 范围内、当前未被本主机中其他 UDP 端口占用的一个端口号。另一种做法是在创建套接字之后再加一行代码，通过套接字的 `bind()` 方法把一个特定端口号（例如 19157）与该 UDP 套接字关联起来：

```text
clientSocket.bind(('', 19157))
```

如果写这段代码的应用开发者实现的是某个"周知协议"的服务器端，那么他必须分配相应的周知端口号。通常情况下，应用的客户端让运输层自动（且透明地）分配端口号，而服务器端则分配一个特定的端口号。

有了分配给 UDP 套接字的端口号，就可以精确描述 UDP 的复用/分解了。假设主机 A 中一个 UDP 端口为 19157 的进程，要向主机 B 中 UDP 端口为 46428 的进程发送一块应用数据。主机 A 的运输层创建一个运输层报文段，其中包含应用数据、源端口号 19157、目的端口号 46428，以及另外两个值（后面会讨论，此处无关紧要）。随后运输层把该报文段交给网络层；网络层把报文段封装进一个 IP 数据报，尽最大努力把该报文段交付给接收主机。如果报文段到达接收主机 B，B 的运输层检查报文段中的目的端口号 46428，把该报文段交付给端口 46428 所标识的套接字。注意，主机 B 可能同时运行多个进程，每个进程都有自己的 UDP 套接字和相应端口号；当 UDP 报文段从网络到达时，主机 B 通过检查报文段的目的端口号，把每个报文段导向（分解到）相应的套接字。

需要强调的是，**一个 UDP 套接字由二元组（目的 IP 地址，目的端口号）完全标识**。因此，如果两个 UDP 报文段具有不同的源 IP 地址和/或不同的源端口号，但具有相同的目的 IP 地址和相同的目的端口号，那么这两个报文段将通过同一个目的套接字被导向同一个目的进程。

你也许在想：那源端口号有什么用？如图 3.4 所示，在 A 到 B 的报文段中，源端口号充当"回信地址"的一部分——当 B 要向 A 回发报文段时，B 到 A 报文段中的目的端口号就取自 A 到 B 报文段中的源端口值。（完整的回信地址是 A 的 IP 地址加上源端口号。）例如，回想 2.7 节研究的 UDP 服务器程序：在 UDPServer.py 中，服务器用 `recvfrom()` 方法从收到的客户端报文段中提取客户端（源）端口号，然后向客户端发送一个新报文段，并把提取出的源端口号作为新报文段中的目的端口号。

### 用 TCP 进行面向连接的多路复用与多路分解

要理解 TCP 的多路分解，必须仔细考察 TCP 套接字与 TCP 连接建立过程。TCP 套接字与 UDP 套接字的一个微妙区别是：**TCP 套接字由四元组（源 IP 地址，源端口号，目的 IP 地址，目的端口号）来标识**。因此，当一个 TCP 报文段从网络到达主机时，主机用全部四个值来把该报文段导向（分解到）相应的套接字。特别地，与 UDP 不同，具有不同源 IP 地址或不同源端口号的两个到达 TCP 报文段（携带初始连接建立请求的报文段除外），将被导向两个不同的套接字，即使它们的目的 IP 地址和目的端口号相同。

为了获得更深入的理解，重新考虑 2.6.2 节的 TCP 客户端-服务器编程示例：

- TCP 服务器应用有一个"欢迎套接字"（welcoming socket），在端口号 12000 上等待来自 TCP 客户端的连接建立请求（见图 2.24）。
- TCP 客户端创建一个套接字，并发送一个连接建立请求报文段：

```text
clientSocket = socket(AF_INET, SOCK_STREAM)
clientSocket.connect((serverName, 12000))
```

- 连接建立请求不过是一个目的端口号为 12000、并在 TCP 首部中置了特殊的连接建立位的 TCP 报文段（3.5 节讨论）。该报文段还包含客户端选择的源端口号。
- 当运行服务器进程的计算机的操作系统收到这个目的端口为 12000 的连接请求报文段时，它定位到正在端口号 12000 上等待接受连接的服务器进程。服务器进程随即创建一个新套接字：

```text
connectionSocket, addr = serverSocket.accept()
```

- 同时，服务器端的运输层记下连接请求报文段中的四个值：(1) 报文段中的源端口号，(2) 源主机的 IP 地址，(3) 报文段中的目的端口号，(4) 本机自己的 IP 地址。新创建的连接套接字就由这四个值来标识；此后所有源端口、源 IP 地址、目的端口、目的 IP 地址与这四个值相匹配的到达报文段，都将被分解到这个套接字。TCP 连接至此建立，客户端与服务器可以互发数据了。

服务器主机可以同时支撑许多 TCP 连接套接字，每个套接字连接到一个进程，并各自由自己的四元组标识。当一个 TCP 报文段到达主机时，四个字段（源 IP 地址、源端口、目的 IP 地址、目的端口）全部用于把报文段导向（分解到）相应的套接字。

<Figure src="ch03/fig3-05.webp" caption="图 3.5　两个客户端使用相同的目的端口号（80）与同一个 Web 服务器应用通信" />

图 3.5 给出了一个具体情形：主机 C 向服务器 B 发起两个 HTTP 会话，主机 A 向 B 发起一个 HTTP 会话。主机 A、C 与服务器 B 各有自己唯一的 IP 地址，分别为 A、C、B。主机 C 为它的两个 HTTP 连接分配了两个不同的源端口号（26145 和 7532）。由于主机 A 独立于 C 选择源端口号，它也可能为自己的 HTTP 连接分配源端口 26145。但这并不成问题——服务器 B 仍能正确分解这两个源端口号相同的连接，因为这两个连接的源 IP 地址不同。

<AsideCard title="安全聚焦 · 端口扫描">

我们已经看到，服务器进程会在某个打开的端口上耐心等待远程客户端的联系。有些端口保留给周知应用（如 Web、FTP、DNS、SMTP 服务器），另一些端口则被流行应用按惯例使用（例如 Microsoft Windows SQL 服务器在 UDP 端口 1434 上监听请求）。因此，一旦确定主机上某个端口是打开的，我们就有可能把这个端口映射到主机上运行的某个具体应用。这对系统管理员非常有用，他们常常想知道自己网络中的主机上跑着哪些网络应用。但攻击者在"踩点"时，同样想知道目标主机上哪些端口是打开的。如果发现某台主机正在运行带有已知安全漏洞的应用（例如监听 1434 端口的 SQL 服务器曾存在缓冲区溢出漏洞，可让远程用户在易受攻击的主机上执行任意代码，Slammer 蠕虫就利用了该漏洞 [Kristoff 2023]），那么这台主机就很容易被攻陷。

确定哪些应用在哪些端口上监听，是件相当容易的事。事实上，有不少公有领域的程序——称为**端口扫描器**（port scanner）——专门做这件事。其中最常用的也许是 nmap，可从 http://nmap.org 免费获得，且包含在大多数 Linux 发行版中。对 TCP，nmap 依次扫描各端口，寻找正在接受 TCP 连接的端口；对 UDP，nmap 同样依次扫描各端口，寻找对发出的 UDP 报文段作出响应的 UDP 端口。两种情况下，nmap 都会返回一份端口列表，标明各端口是打开、关闭还是不可达。运行 nmap 的主机可以尝试扫描因特网上的任何目标主机。

### Web 服务器与 TCP

在结束本节之前，再就 Web 服务器如何使用端口号说几句是有益的。考虑一台在端口 80 上运行 Web 服务器（例如 Apache）的主机。当客户端（例如浏览器）向服务器发送报文段时，所有报文段的目的端口都是 80；特别是，初始的连接建立报文段和携带 HTTP 请求消息的报文段，目的端口都是 80。正如刚才所述，服务器利用源 IP 地址和源端口号来区分来自不同客户端的报文段。

图 3.5 中的 Web 服务器为每个连接派生一个新进程。如图所示，每个进程都有自己的连接套接字，HTTP 请求经由它到达、HTTP 响应经由它发出。不过要说明的是，连接套接字与进程之间并不总是一一对应的。事实上，当今高性能的 Web 服务器往往只使用一个进程，而为每个新的客户端连接创建一个新线程和一个新的连接套接字。（线程可以看作轻量级的子进程。）如果你做过第 2 章的第一个编程作业，你写的 Web 服务器正是这样做的。对这类服务器而言，在任一时刻都可能有多个连接套接字（标识符各不相同）连接到同一个进程。

如果客户端与服务器使用持久 HTTP，那么在持久连接的整个持续期间，客户端与服务器都通过同一个服务器套接字交换 HTTP 消息。反之，如果使用非持久 HTTP，则每对请求/响应都要创建并关闭一个新的 TCP 连接，因而每对请求/响应都要创建、随后关闭一个新的套接字。这种频繁创建和关闭套接字会严重影响繁忙 Web 服务器的性能（尽管可以用一些操作系统技巧来缓解）。对持久与非持久 HTTP 所涉及的操作系统问题感兴趣的读者，可参阅 [Nielsen 1997; Nahum 2002]。

讨论了运输层的多路复用与多路分解，接下来考察因特网的运输协议之一：UDP。下一节将会看到，UDP 除了复用/分解服务之外，几乎没有给网络层协议增加什么别的东西。

## 3.3　无连接运输：UDP

本节仔细考察 UDP：它如何工作、能做些什么。建议读者回头参考 2.1 节（UDP 服务模型概述）与 2.6.1 节（用 UDP 进行套接字编程）。

为了引出 UDP 的讨论，不妨设想你要设计一个"极简"的运输协议：还能比"什么都不做"更简单吗？最朴素的想法是：发送端把应用进程交来的报文直接交给网络层，接收端把从网络层到达的报文直接交给应用进程。但正如上一节所学，我们总得比"什么都不做"多做一点——运输层至少要提供多路复用/多路分解服务，才能把数据在网络层与正确的应用层进程之间传递。

UDP（定义于 [RFC 768]）几乎就是一个运输协议所能做到的"最少限度"：除了多路复用/多路分解功能和一点点差错检查之外，它没有给 IP 增加任何东西。事实上，如果应用开发者选择 UDP 而不是 TCP，那么应用几乎就是在直接与 IP 打交道。UDP 从应用进程取出报文，附上用于复用/分解的源端口号与目的端口号字段，再加两个小字段，然后把生成的报文段交给网络层；网络层把该运输层报文段封装进一个 IP 数据报，尽最大努力把它交付给接收主机。若报文段到达接收主机，UDP 用目的端口号把报文段中的数据交付给正确的应用进程。

请注意：使用 UDP 时，发送方与接收方的运输层实体在传送报文段之前**没有握手过程**。正因如此，UDP 被称为是**无连接**的。

DNS 就是一个通常使用 UDP 的应用层协议的例子。主机中的 DNS 应用要发起查询时，构造一条 DNS 查询报文并交给 UDP。UDP 不与目的端系统中运行的 UDP 实体做任何握手，只在主机侧给报文加上首部字段，把生成的报文段交给网络层；网络层把 UDP 报文段封装进数据报，发往名字服务器。随后，发起查询的主机上的 DNS 应用等待查询的应答。如果没有收到应答（可能是因为底层网络丢失了查询或应答），它可能会重发查询、把查询发给另一台名字服务器，或者告知调用它的应用无法得到应答。

读到这里你可能会问：既然 TCP 提供可靠数据传输而 UDP 不提供，为什么应用开发者还会选择在 UDP 之上构建应用？难道 TCP 不总是更好的选择吗？答案是否定的。对某些应用而言，UDP 更合适，理由如下。

::: tip 要点

应用开发者选择 UDP 而非 TCP，通常是出于以下四个理由之一：

1. **对发送什么数据、何时发送，有更精细的应用层控制。** 使用 UDP 时，应用进程一旦把数据交给 UDP，UDP 就立即把它封装成报文段并马上交给网络层。而 TCP 有拥塞控制机制：当源与目的主机之间的某条链路出现严重拥塞时，TCP 会抑制运输层发送方；而且无论可靠交付需要多长时间，TCP 都会不断重传一个报文段，直到收到目的端的确认。实时应用往往要求一个最低发送速率，不愿报文段传输被过度延迟，并且能够容忍少量数据丢失——TCP 的服务模型与这类需求并不匹配。这类应用可以改用 UDP，并在应用自身中实现 UDP 那套"极简"报文段交付服务之外的任何附加功能。
1. **无需建立连接。** TCP 在开始传输数据之前要进行三次握手；UDP 则不做任何正式的准备就直接发送。因此 UDP 不会引入建立连接的额外时延。这大概就是 DNS 通常运行在 UDP 而非 TCP 之上的主要原因——若 DNS 跑在 TCP 上，会慢得多。2.2 节讲到，HTTP/1 与 HTTP/2 使用 TCP 而非 UDP，因为对于含文本的网页来说可靠性至关重要；但正如 2.2 节所讨论的，HTTP 中 TCP 连接建立的时延是下载 Web 文档时延的重要组成部分。事实上，HTTP/3 使用的是 QUIC 协议（Quick UDP Internet Connection，[RFC 9000; RFC 9002]），它以 UDP 作为底层运输协议，并在 UDP 之上于应用层实现可靠性。3.8 节将进一步考察 QUIC。
1. **无连接状态。** TCP 在端系统中维护连接状态，包括接收缓冲区与发送缓冲区、拥塞控制参数、序号与确认号参数等。3.5 节将会看到，实现 TCP 的可靠数据传输服务与拥塞控制正需要这些状态信息。UDP 则不维护连接状态，也不跟踪这些参数。因此，一个专门服务于某应用的服务器，在应用运行于 UDP 之上时通常能支撑多得多的活跃客户端。
1. **分组首部开销小。** TCP 每个报文段有 20 字节的首部开销，而 UDP 只有 8 字节。

:::

图 3.6 列出了常用的因特网应用及其所使用的运输协议。如我们所料，电子邮件、远程终端访问和文件传输运行在 TCP 之上——这些应用都需要 TCP 的可靠数据传输服务。第 2 章讲过，早期版本的 HTTP 运行在 TCP 之上，而较新的 HTTP 版本运行在 UDP 之上，在应用层自行提供差错控制与拥塞控制（以及其他服务）。不过，仍有许多重要应用运行在 UDP 而非 TCP 之上。例如，UDP 被用于承载网络管理数据（SNMP，见 5.7 节）。在这种场合 UDP 比 TCP 更可取，因为网络管理应用常常必须在网络处于受压状态时运行——而那恰恰是难以实现可靠、带拥塞控制的数据传输的时候。此外，如前所述，DNS 通常运行在 UDP 之上，从而避免 TCP 的连接建立时延；当然 DNS 也可以运行在 TCP 之上。

如图 3.6 所示，如今 UDP 与 TCP 有时都会被多媒体应用使用，例如因特网电话、实时视频会议、存储音频与视频的流式播放。这里只提一点：所有这些应用都能容忍少量分组丢失，因此可靠数据传输对应用的成功并非绝对关键。此外，像因特网电话和视频会议这类实时应用，对 TCP 的拥塞控制反应很差。基于这些原因，多媒体应用的开发者可能选择让应用运行在 UDP 而非 TCP 之上。当分组丢失率较低时，加上一些机构出于安全考虑封锁 UDP 流量（见第 8 章），TCP 在流媒体传输方面正变得越来越有吸引力。

尽管如今很常见，但在 UDP 之上运行多媒体应用仍需谨慎。如前所述，UDP 没有拥塞控制；而拥塞控制是防止网络陷入"几乎做不了有用功"的拥塞状态所必需的。如果所有人都开始以高比特率播放视频而不做任何拥塞控制，路由器处就会发生大量分组溢出，以致极少数 UDP 分组能够成功穿越源到目的的路径；更有甚者，不受控制的 UDP 发送方所引发的高丢失率，会使 TCP 发送方（如我们将会看到的，它们在拥塞面前会降低发送速率）大幅降低其速率。因此，UDP 缺少拥塞控制可能导致 UDP 收发方之间的高丢失率，并把 TCP 会话"挤出"网络。许多研究者提出了新的机制，强制包括 UDP 在内的所有源端执行自适应拥塞控制 [Mahdavi 1997; Floyd 2000; Kohler 2006; RFC 4340]。

在讨论 UDP 报文段结构之前，还要说明一点：应用使用 UDP 时，也是**可以**获得可靠数据传输的——只要把可靠性构建在应用自身之中（例如加入确认与重传机制，也就是下一节将要研究的那类机制）。前面提到，QUIC 协议就是在 UDP 之上、在应用层实现可靠性的。把可靠性直接构建在应用中，可以让应用"鱼与熊掌兼得"：应用进程能够可靠通信，却不必受制于 TCP 拥塞控制机制所施加的发送速率约束。

UDP 报文段结构如图 3.7 所示，由 RFC 768 定义。应用数据占据 UDP 报文段的**数据字段**。例如对 DNS 来说，数据字段包含一条查询报文或一条响应报文；对流式音频应用来说，音频采样填满数据字段。UDP 首部只有四个字段，每个字段两个字节。

如上一节所述，端口号使目的主机能够把应用数据交给目的端系统中正确的进程（即完成多路分解功能）。**长度字段**指明 UDP 报文段（首部加数据）的字节数。之所以需要显式的长度值，是因为数据字段的长度在不同 UDP 报文段之间可能不同。**校验和**由接收主机用来检验报文段在传输中是否引入了差错。（严格说来，校验和还要对 IP 首部中的若干字段一并计算，而不只是 UDP 报文段；这里略去这一细节，以便看清主干。）校验和的计算见下文；差错检测的基本原理见 6.2 节。

### 3.3.2　UDP 校验和

UDP 校验和提供差错检测：它用来判断 UDP 报文段从源到目的传输过程中，段内的比特是否发生了改变（例如由于链路噪声，或由于在路由器中缓存期间出错）。

在发送端，UDP 对报文段中所有 16 比特字求和，求和过程中遇到的任何溢出都**回卷**（wraparound），然后对结果取**反码**（1s complement），把该结果放入 UDP 报文段的校验和字段。下面给出一个简单的计算示例；高效实现的细节见 RFC 1071，在真实数据上的性能见 [Stone 1998; Stone 2000]。

假设有三个 16 比特字：

```text
0110011001100000
0101010101010101
1000111100001100
```

前两个 16 比特字之和为：

```text
0110011001100000
0101010101010101
────────────────
1011101110110101
```

再把第三个字加到上面的和上：

```text
  1011101110110101
+ 1000111100001100
──────────────────
1 0100101011000001
  0100101011000010
```

注意最后这次加法产生了溢出（最高位进位 1），该进位被回卷——即把 1 加到最低位，得到 0100101011000010。取反码就是把所有的 0 变成 1、所有的 1 变成 0，于是和 0100101011000010 的反码为 1011010100111101，这就是校验和。

在接收端，把包括校验和在内的四个 16 比特字全部相加。如果分组中没有引入差错，那么接收端的和显然应为 1111111111111111。只要其中有一位是 0，我们就知道分组中引入了差错。

你也许会问：许多链路层协议（包括流行的以太网协议）本身就提供差错检测，UDP 为什么还要提供校验和？原因在于，无法保证源与目的之间的**所有**链路都提供差错检测——其中某条链路可能使用了不提供差错检测的链路层协议。而且，即使报文段在链路上被正确传输，它在路由器内存中缓存时也可能引入比特差错。既然逐链路的可靠性和内存中的差错检测都不被保证，那么若端到端的数据传输服务要提供差错检测，UDP 就必须在运输层以**端到端**的方式提供差错检测。这正是系统设计中著名的**端到端原则**（end-end principle）的一个例子 [Saltzer 1984]：由于某些功能（此处是差错检测）必须在端到端的基础上实现，"与在高层提供这些功能的代价相比，放在低层实现的功能可能是冗余的，或者价值不大"。

由于 IP 被设计为可以运行在几乎任何链路层协议之上，运输层提供差错检查作为一种安全措施是有用的。不过，UDP 虽然提供差错检查，却**不做**任何差错恢复：某些 UDP 实现只是丢弃受损的报文段，另一些则把受损报文段连同警告一起交给应用。

UDP 的讨论到此结束。我们很快会看到，TCP 为其应用提供可靠数据传输，以及 UDP 所不提供的其他服务；自然，TCP 也比 UDP 复杂得多。不过在讨论 TCP 之前，先退一步考察可靠数据传输的基本原理，会很有帮助。

## 3.4　可靠数据传输原理

本节在一般意义上讨论可靠数据传输问题。这样安排是恰当的，因为可靠数据传输的实现问题不仅出现在运输层，也出现在链路层和应用层。因此，这个一般性问题对整个网络领域都具有核心重要性——如果要在整个网络领域列一份"十大根本问题"清单，它完全有资格排在首位。下一节将会看到，TCP 用到了我们即将描述的许多原理。

图 3.8 给出了研究可靠数据传输的框架。向上层实体提供的服务抽象是一条**可靠信道**：通过它传输的数据不会出现比特差错（不会从 0 翻转为 1 或反之），也不会丢失，并且全部按发送顺序交付。这正是 TCP 向调用它的因特网应用所提供的服务模型。

实现这一服务抽象是可靠数据传输协议的责任。这项任务之所以困难，是因为可靠数据传输协议**下面**的那一层可能是不可靠的。例如，TCP 就是一个建立在不可靠的（IP）端到端网络层之上的可靠数据传输协议。更一般地说，两个可靠通信端点之下的那一层，可能是一条单一物理链路（如链路层数据传输协议的情形），也可能是一个全球互联网络（如运输层协议的情形）。但就我们的目的而言，可以简单地把这个下层看作一条**不可靠的点对点信道**。

<Figure src="ch03/fig3-08.webp" caption="图 3.8　可靠数据传输：服务模型与服务实现" />

本节将逐步构造可靠数据传输协议的发送方与接收方，所考虑的下层信道模型越来越复杂。例如，我们会考察：当下层信道会损坏比特或丢失整个分组时，需要哪些协议机制。贯穿本节的一个假设是：分组按发送顺序交付，只是可能有一些分组丢失；也就是说，下层信道**不会重排**分组。

图 3.8(b) 给出了数据传输协议的接口。发送侧由上层调用 `rdt_send()` 来触发，参数是要交付给接收侧上层的数据。（这里 `rdt` 代表可靠数据传输协议，`_send` 表示调用的是 rdt 的发送侧。开发任何协议的第一步都是取个好名字！）在接收侧，当分组从信道的接收端到达时，会调用 `rdt_rcv()`。当 rdt 协议要向上一层交付数据时，就调用 `deliver_data()`。下文使用"分组"这一术语而不是运输层的"报文段"：本节建立的理论适用于一般计算机网络，而不限于因特网运输层，用通用的"分组"一词更为恰当。

本节只考虑**单向**数据传输，即数据从发送侧传向接收侧。可靠的双向（即全双工）数据传输在概念上并不更难，但解释起来要繁琐得多。虽然只考虑单向数据传输，但要注意：协议的发送侧与接收侧仍然需要在**两个方向**上传输分组，如图 3.8 所示。很快会看到，除了交换承载数据的分组之外，rdt 的收发双方还需要来回交换控制分组。rdt 的收发两侧都通过调用 `udt_send()` 向对方发送分组（`udt` 代表不可靠数据传输）。

### 3.4.1　构造可靠数据传输协议

下面我们依次走过一系列协议，一个比一个复杂，最终得到一个完美的、可靠的数据传输协议。

#### 完全可靠信道上的可靠数据传输：rdt1.0

先考虑最简单的情形：下层信道完全可靠。此时协议本身（称为 rdt1.0）平淡无奇。rdt1.0 发送方与接收方的有限状态机（FSM）定义如图 3.9 所示：图 3.9(a) 的 FSM 定义发送方的操作，图 3.9(b) 的 FSM 定义接收方的操作。要注意，发送方和接收方各有独立的 FSM。图 3.9 中的两个 FSM 都只有一个状态。

FSM 中的箭头表示协议从一个状态到另一个状态的**变迁**。（图 3.9 中每个 FSM 只有一个状态，因此变迁必然是从该状态回到自身；稍后会看到更复杂的状态图。）引起变迁的**事件**标在标注该变迁的水平线之上，事件发生时所采取的**动作**标在水平线之下。当某事件发生而不采取任何动作，或没有事件发生而采取动作时，我们分别在水平线下方或上方使用符号 Λ，显式表示"无动作"或"无事件"。FSM 的**初始状态**用虚线箭头表示。图 3.9 的 FSM 虽只有一个状态，但稍后看到的 FSM 会有多个状态，因此标明每个 FSM 的初始状态很重要。

<Figure src="ch03/fig3-09.webp" caption="图 3.9　rdt1.0——用于完全可靠信道的协议" />

rdt 的发送侧通过 `rdt_send(data)` 事件从上层接收数据，通过动作 `make_pkt(data)` 创建一个包含该数据的分组，然后把分组送入信道。在实际系统中，`rdt_send(data)` 事件来自上层应用的一次过程调用（例如调用 `rdt_send()`）。

在接收侧，rdt 通过 `rdt_rcv(packet)` 事件从下层信道接收分组，通过动作 `extract(packet, data)` 从分组中取出数据，再通过动作 `deliver_data(data)` 把数据上交上层。在实际系统中，`rdt_rcv(packet)` 事件来自下层协议的一次过程调用（例如调用 `rdt_rcv()`）。

在这个简单协议中，数据单元与分组没有区别。而且所有分组都从发送方流向接收方；在完全可靠的信道上，什么都不会出错，接收方无需向发送方提供任何反馈。注意我们还假定了接收方能够以发送方发送数据的同样速度接收数据，因此接收方也无需请求发送方放慢速度。

#### 具有比特差错信道上的可靠数据传输：rdt2.0

更接近真实的下层信道模型是：分组中的比特可能受损。这类比特差错通常发生在分组的传输、传播或缓存过程中，源于网络的物理部件。此刻我们仍假设所有发送的分组都能按序收到（尽管其比特可能已损坏）。

在为此类信道设计协议之前，先想想人在这种情况下会怎么做。设想你在电话里口述一条很长的消息：典型情形是，接收方在每一句被听到、听懂并记下之后说一声"好"。如果听到的是含混不清的一句，就会请你重说那一句。这个"口述协议"同时使用了**肯定确认**（"好"）与**否定确认**（"请重说"）。这些控制消息让接收方得以告知发送方：哪些内容已正确收到，哪些内容收到时有误因而需要重说。在计算机网络中，基于这种重传机制的可靠数据传输协议称为 **ARQ**（Automatic Repeat reQuest，自动重传请求）协议。

从根本上说，ARQ 协议要处理比特差错，还需要三项额外的协议能力：

::: tip 要点

1. **差错检测。** 首先需要一种机制，使接收方能够检测出比特差错何时发生。上一节讲过，UDP 正是用因特网校验和字段来实现这一目的。第 6 章将更详细地讨论差错检测与纠正技术；眼下只需知道，这类技术要求发送方向接收方发送一些额外的比特（超出原始数据比特之外），这些比特将被收集到 rdt2.0 数据分组的**分组校验和字段**中。
1. **接收方反馈。** 由于发送方与接收方通常运行在不同的端系统上，可能相隔数千公里，发送方要了解接收方那里的"情况"（此处即分组是否被正确接收），唯一的办法就是让接收方显式地向发送方提供反馈。口述场景中的肯定确认（ACK）与否定确认（NAK）就是这种反馈的例子。我们的 rdt2.0 协议同样会从接收方向发送方回送 ACK 与 NAK 分组。原则上这些分组只需一个比特长：例如值 0 表示 NAK，值 1 表示 ACK。
1. **重传。** 接收方收到出错的分组后，由发送方重传该分组。

:::

图 3.10 给出了 rdt2.0 的 FSM 表示——一个采用差错检测、肯定确认与否定确认的数据传输协议。

<Figure src="ch03/fig3-10.webp" caption="图 3.10　rdt2.0——用于具有比特差错信道的协议" />

rdt2.0 的发送侧有两个状态。在最左边的状态中，发送侧协议等待上层交下数据。当 `rdt_send(data)` 事件发生时，发送方创建一个包含待发数据及分组校验和的分组（`sndpkt`，校验和的计算见 3.3.2 节 UDP 报文段的情形），然后通过 `udt_send(sndpkt)` 操作把该分组发出。在最右边的状态中，发送侧协议等待来自接收方的 ACK 或 NAK 分组。如果收到 ACK 分组（图 3.10 中的记号 `rdt_rcv(rcvpkt) && isACK(rcvpkt)` 对应此事件），发送方就知道最近发送的分组已被正确接收，于是协议回到等待上层数据的状态。如果收到 NAK，协议重传最后一个分组，并继续等待接收方针对该重传分组回送的 ACK 或 NAK。

需要强调的是：当发送方处于"等待 ACK 或 NAK"状态时，它**不能**从上层获取更多数据，即 `rdt_send()` 事件不可能发生；只有等到发送方收到 ACK 并离开该状态之后，才可能发生。因此，在确信接收方已正确收到当前分组之前，发送方不会发送新的数据。由于这一行为，像 rdt2.0 这样的协议被称为**停等**（stop-and-wait）协议。

rdt2.0 的接收侧 FSM 仍然只有一个状态。分组到达时，接收方根据收到的分组是否受损，回送 ACK 或 NAK。图 3.10 中的记号 `rdt_rcv(rcvpkt) && corrupt(rcvpkt)` 对应"收到分组且发现其出错"这一事件。

rdt2.0 看上去似乎能工作，但不幸的是它有一个致命缺陷：我们**没有考虑 ACK 或 NAK 分组本身也可能受损**！（在往下读之前，不妨先想想这个问题该如何解决。）这个看似轻微的疏漏，后果却并不轻微。最起码，我们需要给 ACK/NAK 分组加上校验和比特，以检测这类差错。更难的问题是：协议应当如何从 ACK 或 NAK 的差错中恢复？困难在于，一旦 ACK 或 NAK 受损，发送方就无从知道接收方是否已正确收到最近发送的那份数据。

处理受损 ACK 或 NAK，有三种可能做法：

- **第一种可能**，想想人在口述场景中会怎么做。如果说话人没听清对方回的"好"或"请重说"，他多半会问一句"你说什么？"（这就给协议引入了一种新的发送方到接收方分组）。接收方随后重说一遍应答。可要是说话人的"你说什么？"也受损了呢？接收方无从判断那句含混的话是口述内容的一部分，还是要求重说上一次应答，于是多半也会回一句"你说什么？"——然后这句回应当然也可能受损。显然，这条路越走越难。
- **第二种可能**，增加足够的校验和比特，使发送方不仅能检测、而且能**恢复**比特差错。对于只损坏分组而不丢失分组的信道，这能解决眼前的问题。
- **第三种做法**，发送方在收到含混不清的 ACK 或 NAK 分组时，干脆重传当前数据分组。然而这种做法会在发送方到接收方的信道中引入**重复分组**。重复分组的根本困难在于：接收方不知道自己上次发出的 ACK 或 NAK 是否被发送方正确收到，因此它无法先验地判断到达的分组是携带新数据，还是一次重传！

对这个新问题有一个简单解法（几乎所有现有数据传输协议，包括 TCP，都采用了它）：在数据分组中增加一个新字段，让发送方把自己的数据分组**编号**，即把序号放入该字段。这样接收方只需检查序号，就能判断收到的分组是否为重传。对于停等协议这种简单情形，**1 个比特的序号**就够了：它足以让接收方分辨发送方是在重发前一个分组（收到分组的序号与最近收到的分组相同），还是在发新分组（序号改变，按模 2 运算"向前"推进）。由于当前假设信道不丢分组，ACK 与 NAK 分组本身无需指明它们在确认哪个分组的序号——发送方知道，收到的 ACK 或 NAK（无论是否受损）都是针对它最近发送的那个数据分组产生的。

图 3.11 与图 3.12 给出了 rdt2.1 的 FSM 描述，这是我们对 rdt2.0 的修正版本。rdt2.1 的发送方与接收方 FSM 的状态数都翻了一倍。这是因为协议状态现在必须反映：当前正在发送（发送方）或正在等待（接收方）的分组，其序号应当是 0 还是 1。注意，在"发送/等待序号为 0 的分组"的那些状态中所做的动作，与"发送/等待序号为 1 的分组"的状态互为镜像，唯一差别在于对序号的处理。

<Figure src="ch03/fig3-12.webp" caption="图 3.12　rdt2.1 接收方" />

rdt2.1 同时使用肯定确认与否定确认。当收到一个失序分组时，接收方为它已收到的分组发送一个肯定确认；当收到受损分组时，接收方发送否定确认。

其实，如果我们不发送 NAK，而是为**最近一次正确收到的分组**发送 ACK，也能达到与 NAK 相同的效果：收到对同一分组的两个 ACK（即**重复 ACK**）的发送方就知道，接收方没有正确收到那个被重复确认的分组**之后**的那个分组。这种不含 NAK 的、用于比特差错信道的可靠数据传输协议就是 **rdt2.2**，如图 3.13 与图 3.14 所示。rdt2.1 与 rdt2.2 之间有一处微妙变化：接收方现在必须在 ACK 消息中带上它所确认的分组的序号（在接收方 FSM 中，通过在 `make_pkt()` 里加入 `ACK, 0` 或 `ACK, 1` 参数来实现）；而发送方现在必须检查所收到的 ACK 消息确认的是哪个序号的分组（在发送方 FSM 中，通过在 `isACK()` 里加入参数 0 或 1 来实现）。

#### 具有比特差错的丢包信道上的可靠数据传输：rdt3.0

现在假设下层信道除了会损坏比特，还会**丢失分组**——这在当今的计算机网络（包括因特网）中并不罕见。协议此时必须解决两个新问题：如何**检测**分组丢失，以及分组丢失后**怎么办**。使用校验和、序号、ACK 分组与重传——这些在 rdt2.2 中已经发展出来的技术——可以回答后一个问题；而处理前一个问题则需要引入一种新的协议机制。

处理分组丢失有许多可能的做法（本章末的习题还将探讨若干种）。这里我们把检测丢包和从中恢复的担子交给发送方。假设发送方发出一个数据分组，而该分组、或接收方对该分组的 ACK 丢失了。无论哪种情况，发送方都收不到来自接收方的任何回应。只要发送方愿意等待足够长的时间，确信分组已经丢失，它就可以简单地重传该数据分组。你应当说服自己：这个协议确实可行。

但发送方必须等多久，才能确信"某个东西"已经丢失？显然，发送方至少要等一个往返时延（可能包括在中间路由器中的排队缓存）加上接收方处理一个分组所需的时间。在许多网络中，这个最坏情况下的最大时延极难估计，更不用说确知了。而且，协议最好能尽快从丢包中恢复；等待最坏时延可能意味着要等很久才开始差错恢复。因此实践中采用的做法是：发送方审慎地选择一个时间值，使得"分组很可能（虽不能保证）已经丢失"。若在此时间内没有收到 ACK，就重传该分组。注意，如果某个分组经历了特别大的时延，发送方也可能在数据分组与其 ACK 都未丢失的情况下重传——这就在发送方到接收方的信道中引入了重复数据分组的可能。所幸 rdt2.2 已具备足够的功能（即序号）来处理重复分组。

从发送方的角度看，重传是一剂万灵药：它不知道是数据分组丢了、ACK 丢了，还是分组或 ACK 只是被过度延迟了。所有情况下动作都一样——重传。实现基于时间的重传机制需要一个**倒计时定时器**，它能在给定时间到期后中断发送方。因此发送方需要能够：(1) 每发送一个分组（无论是首次发送还是重传）就启动定时器；(2) 响应定时器中断（采取适当动作）；(3) 停止定时器。

图 3.15 给出了 rdt3.0 的发送方 FSM。该协议能在会损坏或丢失分组的信道上可靠地传输数据；接收方 FSM 留给读者在习题中给出。图 3.16 展示了协议在无分组丢失或延迟时的运行情况，以及它如何处理数据分组丢失。

至此，我们已经集齐了数据传输协议的关键要素。校验和、序号、定时器，以及肯定确认与否定确认分组，每一项都在协议的运行中扮演着关键而必要的角色。现在，我们拥有了一个可以工作的可靠数据传输协议！

### 3.4.2　流水线可靠数据传输协议

rdt3.0 在功能上是正确的，但恐怕没有人会对它的性能感到满意，尤其是在当今的高速网络中。rdt3.0 性能问题的症结在于它是一个**停等**协议。

为了体会停等行为的性能影响，考虑一个理想化的场景：两台主机，一台在美国西海岸，另一台在东海岸，如图 3.17 所示。这两个端系统之间的光速往返传播时延 RTT 约为 30 毫秒。假设它们之间由一条传输速率 $R = 1$ Gbps（$10^{9}$ 比特/秒）的信道相连，分组长度 $L = 1000$ 字节（$8000$ 比特，含首部字段与数据）。那么把该分组真正注入 1 Gbps 链路所需的时间为

$$
d_{\text{trans}} = \frac{L}{R} = \frac{8000 \text{比特}}{10^{9} \text{比特/秒}} = 8 \text{微秒}
$$

图 3.18(a) 表明，在停等协议下，若发送方在 $t = 0$ 时刻开始发送该分组，则在 $t = \frac{L}{R} = 8$ 微秒时最后一个比特进入发送侧的链路。随后分组开始它横跨全国的 15 毫秒旅程，其最后一个比特在 $t = \frac{L}{R} + \frac{\text{RTT}}{2} = 15.008$ 毫秒时到达接收方。为简单起见，假定 ACK 分组极小（可忽略其传输时间），且接收方一收到数据分组的最后一个比特就能立即回送 ACK，则 ACK 在 $t = \frac{L}{R} + \text{RTT} = 30.008$ 毫秒时回到发送方。此时发送方才可以发送下一条消息。也就是说，在这 30.008 毫秒中，发送方真正在发送的时间只有 0.008 毫秒。

若把发送方（或信道）的**利用率**定义为发送方真正忙于向信道注入比特的时间所占的比例，则图 3.18(a) 的分析表明，停等协议的发送方利用率 $U_{\text{sender}}$ 低得可怜：

$$
U_{\text{sender}} = \frac{\frac{L}{R}}{\text{RTT} + \frac{L}{R}} = \frac{0.008}{30.008} = 0.00027
$$

<Figure src="ch03/fig3-17.webp" caption="图 3.17　停等协议与流水线协议的对比" />

也就是说，发送方只有万分之 2.7 的时间在忙！换个角度看，发送方在 30.008 毫秒内只能发出 1000 字节，有效吞吐量仅 267 kbps——尽管链路的容量是 1 Gbps！想象一下那位刚花大价钱买来千兆链路、却只得到 267 kbps 吞吐量的网络管理员会有多郁闷。这是"网络协议可能限制底层网络硬件能力"的一个生动例子。此外，我们还忽略了收发两端的低层协议处理时间，以及发送方与接收方之间任何中间路由器上会发生的处理和排队时延；把这些因素计入，只会进一步增大时延、进一步凸显性能之糟。

<Figure src="ch03/fig3-18.webp" caption="图 3.18　停等发送与流水线发送" />

这个性能问题的解法很简单：不要以停等方式运行，而是允许发送方连续发送多个分组而无需等待确认，如图 3.17(b) 所示。图 3.18(b) 表明，如果允许发送方在等待确认之前先发送三个分组，则发送方利用率基本上提高到三倍。由于发送方到接收方之间大量在途分组可以形象地看作"填满了一条管道"，这种技术称为**流水线**（pipelining）。流水线对可靠数据传输协议带来以下后果：

- **序号范围必须扩大。** 因为每个在途分组（不计重传）都必须有唯一序号，而在途的、未确认的分组可能有很多个。
- **协议的收发两侧可能必须缓存多个分组。** 至少，发送方必须缓存已发送但尚未确认的分组；如下文所述，接收方也可能需要缓存正确收到的分组。
- **所需序号范围与缓存需求，取决于数据传输协议如何应对丢失、损坏和过度延迟的分组。** 流水线差错恢复有两种基本方法：**回退 N 步**（Go-Back-N）与**选择重传**（selective repeat）。

### 3.4.3　回退 N 步（GBN）

在**回退 N 步**（GBN）协议中，发送方被允许发送多个分组（只要有数据）而无需等待确认，但在流水线中未确认的分组数不得超过某个最大允许值 $N$。本节较详细地描述 GBN 协议。

图 3.19 给出了 GBN 协议中发送方看到的序号范围。若把 `base` 定义为最早的未确认分组的序号，把 `nextseqnum` 定义为最小的未使用序号（即下一个待发分组的序号），则序号范围可划分为四个区间：

- $[0, \text{base} - 1]$：已发送且已确认的分组；
- $[\text{base}, \text{nextseqnum} - 1]$：已发送但尚未确认的分组；
- $[\text{nextseqnum}, \text{base} + N - 1]$：若有数据从上层到达，可立即发送的分组所使用的序号；
- 大于等于 $\text{base} + N$ 的序号：在流水线中当前的某个未确认分组（具体说，序号为 `base` 的分组）被确认之前，不能使用。

<Figure src="ch03/fig3-19.webp" caption="图 3.19　GBN 中发送方看到的序号" />

如图 3.19 所示，已发送但未确认分组的可用序号范围，可以看作序号空间上一个长度为 $N$ 的**窗口**。随着协议运行，这个窗口在序号空间上向前滑动；因此 $N$ 常被称为**窗口长度**，GBN 协议本身也被称为**滑动窗口协议**。你也许会问：为什么一开始就要把未确认的在途分组数限制为 $N$？为什么不许无限多？3.5 节将会看到，**流量控制**是对发送方施加限制的一个原因；3.7 节研究 TCP 拥塞控制时，还会看到另一个原因。

实际中，分组的序号放在分组首部中一个固定长度的字段里。若序号字段有 $k$ 个比特，则序号范围是 $[0, 2^{k} - 1]$。由于序号范围有限，所有涉及序号的运算都必须按**模 $2^{k}$** 进行（即序号空间可看作一个大小为 $2^{k}$ 的环，序号 $2^{k} - 1$ 之后紧接着就是序号 0）。回忆一下，rdt3.0 用 1 比特序号，序号范围为 $[0, 1]$。本章末有几道习题探讨序号范围有限所带来的后果。3.5 节将会看到，TCP 有一个 32 比特的序号字段，而 TCP 的序号计的是字节流中的**字节**，不是分组。

图 3.20 与图 3.21 给出了一个基于 ACK、不含 NAK 的 GBN 协议收发两侧的**扩展 FSM** 描述。之所以称为扩展 FSM，是因为我们为 `base` 和 `nextseqnum` 引入了变量（类似于程序设计语言中的变量），并增加了对这些变量的操作以及涉及这些变量的条件动作。可以看到，这种扩展 FSM 的规范已经开始有点像程序设计语言的规范了。[Bochman 1984] 对 FSM 技术的其他扩展、以及基于程序设计语言的其他协议描述技术，做了很好的综述。

GBN 发送方必须响应三类事件：

::: tip 要点

1. **上层调用。** 当上层调用 `rdt_send()` 时，发送方先检查窗口是否已满，即是否有 $N$ 个在途未确认的分组。若窗口未满，则创建一个分组并发送，同时适当地更新变量；若窗口已满，发送方只是把数据交还上层，以此隐含地表示窗口已满，上层大概只能稍后再试。在真实实现中，发送方更可能是把这份数据缓存起来（而不是立即发送），或者采用一种同步机制（例如信号量或标志），使得只有窗口未满时上层才能调用 `rdt_send()`。
1. **收到 ACK。** 在 GBN 协议中，对序号为 $n$ 的分组的确认将被视为**累积确认**（cumulative acknowledgment），表示序号直到并包括 $n$ 在内的所有分组都已在接收方被正确接收。稍后考察 GBN 接收方时会再回到这一点。
1. **超时事件。** 协议的名字"回退 N 步"源自发送方在分组丢失或过度延迟时的行为。与停等协议一样，仍用定时器从数据分组或 ACK 丢失中恢复。若发生超时，发送方重发所有已发送但尚未确认的分组。图 3.20 中的发送方只使用**一个**定时器，可以把它看作"最早发送但尚未确认的那个分组"的定时器：若收到一个 ACK 但仍有其他已发送未确认的分组，则重启定时器；若已无在途未确认分组，则停止定时器。

:::

<Figure src="ch03/fig3-20.webp" caption="图 3.20　GBN 发送方的扩展 FSM 描述" />

GBN 接收方的动作也很简单。若序号为 $n$ 的分组被正确接收且按序到达（即最近一次交付给上层的数据来自序号为 $n - 1$ 的分组），则接收方为分组 $n$ 发送 ACK，并把该分组的数据部分交付上层。其他所有情况下，接收方丢弃该分组，并为最近一次正确按序收到的分组重发 ACK。注意，由于分组是逐个交付上层的，若分组 $k$ 已被接收并交付，则所有序号小于 $k$ 的分组也一定已交付。因此，对 GBN 而言使用累积确认是自然而然的选择。

<Figure src="ch03/fig3-21.webp" caption="图 3.21　GBN 接收方的扩展 FSM 描述" />

在 GBN 协议中，接收方会丢弃那些虽被正确接收、但序号大于 `expectedseqnum` 的分组。例如，若 GBN 接收方正等待序号为 $n$ 的分组，而到达的是序号为 $n + 2$ 的分组，则图 3.21 中的 GBN 接收方会丢弃它——尽管该分组中的数据最终仍需要交付给接收方的上层。为什么不把 $n + 2$ 号分组中的数据缓存起来（但不确认），等序号 $n + 1$ 的分组正确收到之后，再确认并交付它呢？虽然接收方缓存会给 GBN 接收方增加复杂度、需要更多接收方内存，但把序号超出期望值的正确接收数据缓存起来，在实践中确实经常这么做。

图 3.22 展示了窗口长度为 4 个分组时 GBN 协议的运行过程。由于窗口长度的限制，发送方发出分组 0～3 之后，必须等到其中至少一个被确认才能继续。随着各个 ACK（例如 ACK0、ACK1）相继到达，窗口向前滑动，发送方可以发送一个新分组（分别为 pkt4、pkt5）。在接收方一侧，分组 2 丢失，因此分组 3、4、5 被发现失序而被丢弃。

<Figure src="ch03/fig3-22.webp" caption="图 3.22　GBN 的运行" />

在结束 GBN 的讨论之前，值得一提的是：该协议在协议栈中的实现，结构上很可能与图 3.20 的扩展 FSM 相似，也很可能采取若干过程（procedure）的形式，用以实现响应各类可能事件所需采取的动作。在这种**基于事件**的编程中，各个过程或由协议栈中的其他过程调用，或由中断触发。在发送方，这些事件是：(1) 上层实体调用 `rdt_send()`；(2) 定时器中断；(3) 分组到达时下层调用 `rdt_rcv()`。本章末的编程作业将给你机会，在一个模拟但逼真的网络环境中真正实现这些例程。

GBN 协议几乎包含了我们在 3.5 节研究 TCP 的可靠数据传输组件时会遇到的全部技术：序号的使用、累积确认、校验和，以及超时/重传操作。

### 3.4.4　选择重传（SR）

GBN 协议允许发送方把图 3.17 中的"管道"用分组填满，从而避免了我们在停等协议中看到的信道利用率问题。然而在某些情形下，GBN 本身也会遭遇性能问题。特别是当窗口长度与**带宽时延积**都很大时，流水线中可以有许多分组；于是单个分组的差错就可能导致 GBN 重传大量分组，而其中许多分组其实已被正确接收、只是失序而被缓存在接收方，属于不必要的重传。随着信道差错概率上升，流水线可能被这些不必要的重传填满。设想在我们的口述场景中，每当一个词听错了，就要把周围 1000 个词（例如窗口长度为 1000 个词）全部重说一遍——口述会被这些重复的词拖得极慢。

顾名思义，**选择重传**（SR）协议通过让发送方**只重传那些在接收方确实出错（丢失或损坏）的分组**，来避免不必要的重传。这种按需的、逐个分组的重传，要求接收方对正确收到的分组逐个确认。仍然使用长度为 $N$ 的窗口来限制流水线中在途未确认的分组数；但与 GBN 不同，发送方此时已经收到了窗口内某些分组的 ACK。图 3.23 给出了 SR 发送方看到的序号空间。

<Figure src="ch03/fig3-23.webp" caption="图 3.23　SR 发送方与接收方看到的序号空间" />

SR 接收方无论分组是否按序到达，都会对正确收到的分组予以确认。失序的分组被缓存，直到缺失的分组（即序号更小的分组）到达，此时可把一批分组按序交付上层。图 3.24 逐条列出了 SR 发送方采取的各种动作，图 3.25 逐条列出了 SR 接收方采取的各种动作。

<BoxCard caption="图 3.24　SR 发送方的事件与动作">

**1. 上层收到数据。** 当从上层收到数据时，SR 发送方检查该分组的下一个可用序号。若该序号落在发送方窗口内，则把数据封装成分组并发送；否则要么把它缓存起来，要么把它交还上层以便日后重传，这与 GBN 的做法相同。\
      **2. 超时。** 定时器再次用于防止丢失分组。不过，现在每个分组都必须有自己的逻辑定时器，因为超时后只重传一个分组。可以用一个硬件定时器来模拟多个逻辑定时器的运行 [Varghese 1997]。\
      **3. 收到 ACK。** 若收到 ACK，SR 发送方把该分组标记为已接收——前提是该分组在窗口内。若该分组的序号等于 `send_base`，则窗口基序号前移到具有最小序号的未确认分组处。若窗口移动了，并且窗口内有尚未发送、序号落在新窗口内的分组，则把这些分组发送出去。

</BoxCard>

<BoxCard caption="图 3.25　SR 接收方的事件与动作">

**1. 序号落在 $[\text{rcv\_base}, \text{rcv\_base} + N - 1]$ 内且被正确接收的分组。** 此时该分组落在接收方窗口内，接收方回送一个该序号的选择性 ACK 并缓存该分组。若该分组的序号等于 `rcv_base`，则该分组以及此前已缓存、且序号连续（从 `rcv_base` 开始）的一批分组一并交付上层。接收窗口随后向前移动，移动的分组数等于交付上层的分组数。举例来说，参见图 3.26：当收到序号为 `rcv_base` = 2 的分组时，分组 3、4、5 可以一并交付上层。\
      **2. 序号落在 $[\text{rcv\_base} - N, \text{rcv\_base} - 1]$ 内且被正确接收的分组。** 此时必须产生一个 ACK，尽管该分组是接收方此前已经确认过的。\
      **3. 其他情况。** 忽略该分组。

</BoxCard>

图 3.26 给出了存在分组丢失时 SR 运行的一个例子。注意，接收方最初缓存了分组 3、4、5，当分组 2 终于到达时，把它们与分组 2 一起交付上层。

需要强调的是，在图 3.25 的第 2 步中，接收方对序号低于当前窗口基序号、且此前已收到的分组**重新确认**（而不是忽略）。你应当说服自己：这种重新确认确实是必要的。例如，给定图 3.23 中收发双方的序号空间，如果从接收方传向发送方的 ACK 中丢失了对分组 `send_base` 的确认，发送方最终会重传分组 `send_base`——尽管（在我们看来，而不是在发送方看来！）接收方早已收到该分组。如果接收方不对这个分组予以确认，发送方的窗口就永远不会向前移动！这个例子揭示了 SR 协议（以及许多其他协议）的一个重要方面：发送方与接收方对"哪些已正确接收、哪些没有"的看法并不总是一致。对 SR 协议而言，这意味着发送窗口与接收窗口并不总是重合。

最后，让我们在结束可靠数据传输协议的讨论时，考察底层信道模型中剩下的一个假设。回忆一下，我们曾假设分组在发送方与接收方之间的信道中不会**乱序**。当收发双方由一条物理导线相连时，这通常是合理的假设；但当连接两者的"信道"是一个网络时，分组乱序就可能发生。乱序的一种表现是：序号或确认号为 $x$ 的分组的**旧副本**可能出现，尽管发送方窗口和接收方窗口都不包含 $x$。有了分组乱序，信道实质上可以看作在缓存分组，并在将来某个时刻自发地把它们释放出来。由于序号可能被重用，必须小心防范这类重复分组。实践中采取的做法是：确保在发送方"确信"此前发送的、序号为 $x$ 的任何分组都已不在网络中之前，不再重用序号 $x$。为此，假定一个分组在网络中"存活"的时间不会超过某个固定的最大时限。在面向高速网络的 TCP 扩展中，假定的最大分组生存期约为 3 分钟 [RFC 7323]。[Sunshine 1978] 描述了一种使用序号的方法，可以完全避免乱序问题。

## 3.5　面向连接的运输：TCP

掌握了可靠数据传输的基本原理之后，现在转向 TCP——因特网的运输层面向连接的可靠运输协议。本节将会看到，为了提供可靠数据传输，TCP 依赖上一节讨论的许多基本原理，包括差错检测、重传、累积确认、定时器，以及用于序号和确认号的首部字段。TCP 最初定义于 RFC 793，此后多年来又由若干 RFC 更新，包括 RFC 1122、RFC 2018、RFC 5681 和 RFC 7323；这些更新与原始的 RFC 793 规范已被汇总进新的 RFC [RFC 9293]，后者正式"废弃"了 RFC 793。

### 3.5.1　TCP 连接

TCP 被称为是**面向连接**的，因为在一个应用进程开始向另一个应用进程发送数据之前，两个进程必须先相互"握手"——即它们必须交换一些预备报文段，以确立后续数据传输所需的参数。作为 TCP 连接建立的一部分，连接双方都会初始化许多与该 TCP 连接相关的 TCP 状态变量（其中许多将在本节和 3.7 节讨论）。

TCP 的"连接"并不是电路交换网络中那种端到端的 TDM 或 FDM 电路，而是一种**逻辑**连接，其公共状态只存在于两个通信端系统的 TCP 之中。回忆一下，由于 TCP 协议只运行在端系统中、不运行在中间网络设备（路由器和链路层交换机）中，中间网络设备并不维护 TCP 连接状态。事实上，中间路由器对 TCP 连接完全无感：它们看到的是数据报，而不是连接。

TCP 连接提供**全双工**服务：若一台主机上的进程 A 与另一台主机上的进程 B 之间存在一条 TCP 连接，则应用层数据可以同时从 A 流向 B、从 B 流向 A。TCP 连接也总是**点对点**的，即连接在单个发送方与单个接收方之间。所谓的"多播"（multicasting，见本书在线补充材料）——在一次发送操作中把数据从一个发送方传给多个接收方——用 TCP 是做不到的。对 TCP 而言，两台主机正好，三台就太多了！

下面看看 TCP 连接是如何建立的。假设一台主机中运行的进程想要与另一台主机中的进程建立连接。回忆一下，发起连接的进程称为**客户进程**，另一个进程称为**服务器进程**。客户应用进程首先告知客户运输层：它想与服务器中的某个进程建立连接。如 2.6.2 节所述，Python 客户端程序通过发出如下命令来完成这一步：

```text
clientSocket.connect((serverName, serverPort))
```

其中 `serverName` 是服务器名，`serverPort` 标识服务器上的进程。随后，客户端的 TCP 开始与服务器端的 TCP 建立一条 TCP 连接。本节末尾将较详细地讨论连接建立过程；眼下只需知道：客户首先发送一个特殊的 TCP 报文段，服务器用第二个特殊报文段响应，最后客户再用第三个特殊报文段响应。前两个报文段不携带有效载荷（即不携带应用层数据），第三个报文段则可能携带有效载荷。由于两台主机之间共发送三个报文段，这个连接建立过程常被称为**三次握手**（three-way handshake）。

<AsideCard title="历史回眸 · Vinton Cerf、Robert Kahn 与 TCP/IP">

20 世纪 70 年代初，分组交换网络开始大量涌现，因特网的前身 ARPAnet 只是众多网络中的一个。这些网络各有自己的协议。两位研究者——Vinton Cerf 与 Robert Kahn——认识到把这些网络互连起来的重要性，发明了一种跨网络协议 TCP/IP，即传输控制协议/网际协议（Transmission Control Protocol/Internet Protocol）。虽然 Cerf 和 Kahn 起初把该协议视为单一实体，后来它被拆分为 TCP 与 IP 两部分，各自独立运行。1974 年 5 月，Cerf 和 Kahn 在 *IEEE Transactions on Communications Technology* 上发表了关于 TCP/IP 的论文 [Cerf 1974]。

TCP/IP 协议是当今因特网的命脉，而它被设计出来的时候，个人计算机、工作站、智能手机和平板电脑都还不存在，以太网、电缆、DSL、WiFi 等各种接入网技术尚未普及，Web、社交媒体和流媒体视频更是闻所未闻。Cerf 和 Kahn 预见到需要这样一种网络协议：一方面能为尚未定义的各类应用提供广泛支持，另一方面能让任意主机和链路层协议互操作。

2004 年，Cerf 和 Kahn 获得美国计算机学会（ACM）图灵奖——被誉为"计算领域的诺贝尔奖"——以表彰他们"在互连网络方面的开创性工作，包括因特网基础通信协议 TCP/IP 的设计与实现，以及在网络领域的卓越领导"。

</AsideCard>

一旦 TCP 连接建立起来，两个应用进程就可以互相发送数据。先看客户进程向服务器进程发送数据的情形。如 2.6 节所述，客户进程通过套接字（进程的"门"）传递数据流；数据一旦穿过这道门，就交到了客户端 TCP 的手中。如图 3.27 所示，TCP 把这些数据导向该连接的**发送缓冲区**（send buffer），它是三次握手期间预留的缓冲区之一。TCP 会不时地从发送缓冲区中取出一块块数据，交给网络层。有趣的是，最初的 TCP 规范 [RFC 793] 在"TCP 究竟应在何时真正发送缓冲区中的数据"这一点上非常随性，只说要"按自己的方便，把数据放在报文段中发送"。

一个报文段中能取出并放入的最大数据量，受**最大报文段长度**（maximum segment size, MSS）限制。MSS 的典型确定方法是：先确定本地发送主机所能发送的最大链路层帧长度（即所谓的**最大传输单元**，MTU），再据此设定 MSS，使得一个 TCP 报文段（封装进 IP 数据报后）加上 TCP/IP 首部长度（通常 40 字节）能装进一个链路层帧。以太网与 PPP 链路层协议的 MTU 都是 1500 字节，因此 MSS 的典型值为 1460 字节。也有人提出发现**路径 MTU**——从源到目的的所有链路上所能发送的最大链路层帧 [RFC 1191]——并据此设定 MSS 的方法。注意，MSS 指的是报文段中**应用层数据的最大量**，而不是包含首部的 TCP 报文段的最大长度。（这个术语容易混淆，但既然已经根深蒂固，我们也只好接受。）

TCP 为每一块客户数据配上 TCP 首部，从而形成 TCP 报文段。报文段被下交给网络层，在网络层各自封装进 IP 数据报，随后发入网络。在另一端，TCP 收到报文段后，把该报文段的数据放入该 TCP 连接的**接收缓冲区**（receive buffer），如图 3.27 所示；应用从该缓冲区读取数据流。连接的每一侧都有自己的发送缓冲区和接收缓冲区。

<Figure src="ch03/fig3-27.webp" caption="图 3.27　TCP 发送缓冲区与接收缓冲区" />

由此可见，一条 TCP 连接由一台主机中与某进程相连的一组缓冲区、变量和套接字连接，以及另一台主机中与另一进程相连的另一组缓冲区、变量和套接字连接共同构成。如前所述，主机之间的网络设备（路由器、交换机和转发器）中不会为该连接分配任何缓冲区或变量。

### 3.5.2　TCP 报文段结构

简要了解了 TCP 连接之后，来考察 TCP 报文段的结构。TCP 报文段由首部字段和一个数据字段组成，数据字段包含一块应用数据。如上所述，MSS 限制了报文段数据字段的最大长度。当 TCP 发送一个大文件（例如网页中的一幅图像）时，通常把文件切分成 MSS 大小的块（最后一块往往小于 MSS）。而交互式应用通常传输小于 MSS 的数据块；例如 Telnet 和 ssh 这类远程登录应用，TCP 报文段中的数据字段常常只有 1 个字节。由于 TCP 首部通常为 20 字节（比 UDP 首部多 12 字节），Telnet 和 ssh 发送的报文段长度可能只有 21 字节。

图 3.28 给出了 TCP 报文段的结构。与 UDP 一样，首部包含源端口号和目的端口号，用于与上层应用之间数据的多路复用/多路分解；也与 UDP 一样，首部包含校验和字段。此外，TCP 报文段首部还包含下列字段：

- **32 比特的序号字段**与**32 比特的确认号字段**，供 TCP 发送方与接收方实现可靠数据传输服务时使用，详见下文。
- **16 比特的接收窗口字段**，用于流量控制。稍后会看到，它用来指示接收方愿意接受的字节数。
- **4 比特的首部长度字段**，以 32 比特字为单位指明 TCP 首部的长度。由于存在选项字段，TCP 首部长度可变。（通常选项字段为空，因此典型 TCP 首部长度为 20 字节。）
- **选项字段**，长度可变，可选。当收发双方协商最大报文段长度（MSS），或在高速网络中使用窗口缩放因子时，会用到该字段；此外还定义了时间戳选项。详见 RFC 854 与 RFC 1323。
- **标志字段**，共 6 比特。ACK 比特用于指示确认号字段中的值有效，即该报文段包含对某个已成功接收的报文段的确认。RST、SYN 和 FIN 比特用于连接的建立与拆除，本节末尾将讨论。CWR 与 ECE 比特用于显式拥塞通知，见 3.7.2 节。置位 PSH 比特表示接收方应立即把数据交给上层。最后，URG 比特用于指示本报文段中存在被发送侧上层实体标记为"紧急"的数据，这些紧急数据的最后一个字节的位置由 16 比特的**紧急数据指针字段**指明；当存在紧急数据时，TCP 必须通知接收侧上层实体，并向其传递指向紧急数据末尾的指针。（实践中，PSH、URG 及紧急数据指针都未被使用，这里提及只是为了完整。）

<Figure src="ch03/fig3-28.webp" caption="图 3.28　TCP 报文段结构" />

作为教师的经验告诉我们，学生有时会觉得分组格式的讨论枯燥甚至有点无聊。若想以一种有趣而奇特的方式了解 TCP 首部字段——尤其如果你和我们一样热爱乐高积木——可参阅 [Pomeranz 2010]。

#### 序号与确认号

TCP 报文段首部中最重要的两个字段是序号字段和确认号字段，它们是 TCP 可靠数据传输服务的关键部分。不过在讨论如何用这两个字段提供可靠数据传输之前，先解释 TCP 究竟在这两个字段里放了什么。

TCP 把数据看作**无结构的、但有序的字节流**。TCP 对序号的使用正体现了这一观点：序号是建立在**传输的字节流**之上，而不是建立在**传输的报文段序列**之上。因此，一个报文段的序号就是该报文段数据字段中**第一个字节**的字节流编号。

看一个例子。假设主机 A 中的某个进程要通过一条 TCP 连接向主机 B 中的某个进程发送一个数据流。主机 A 的 TCP 会隐式地为数据流中的每个字节编号。假设该数据流是一个 500 000 字节的文件，MSS 为 1000 字节，且数据流的第一个字节编号为 0。如图 3.29 所示，TCP 由该数据流构造出 500 个报文段：第一个报文段的序号为 0，第二个为 1000，第三个为 2000，依此类推。每个序号都被填入相应 TCP 报文段首部的序号字段中。

<Figure src="ch03/fig3-29.webp" caption="图 3.29　把文件数据划分成 TCP 报文段" />

再来看确认号。它比序号要稍难一些。回忆一下，TCP 是全双工的，因此主机 A 在向 B 发送数据的同时，也可能在从 B 接收数据（同属一条 TCP 连接）。从 B 到达的每个报文段都带有 B 到 A 数据流的序号。**主机 A 填入其报文段的确认号，是主机 A 期望从主机 B 收到的下一个字节的序号**。多看几个例子有助于理解。

假设主机 A 已从 B 收到编号 0～535 的所有字节，并且即将向 B 发送一个报文段。此时主机 A 正在等待字节 536 以及 B 数据流中其后的所有字节，于是 A 在发往 B 的报文段的确认号字段中填入 536。

再看一例。假设主机 A 从 B 收到了一个包含字节 0～535 的报文段，又收到了另一个包含字节 900～1000 的报文段；由于某种原因，A 尚未收到字节 536～899。在这个例子中，A 仍在等待字节 536（及其后的字节），以便重建 B 的数据流。因此，A 发往 B 的下一个报文段将在确认号字段中填入 536。由于 TCP 只确认到数据流中第一个缺失字节之前的所有字节，因此说 TCP 提供**累积确认**。

上例还引出一个重要而微妙的问题：主机 A 在收到第二个报文段（字节 536～899）之前，就先收到了第三个报文段（字节 900～1000），即第三个报文段**失序**到达。微妙之处在于：主机在 TCP 连接中收到失序报文段时该怎么办？有趣的是，TCP 的 RFC 对此未作任何规定，而是把决定权留给实现 TCP 的程序员。基本上有两种选择：(1) 接收方立即丢弃失序报文段（如前所述，这可以简化接收方设计）；(2) 接收方保留失序字节，并等待缺失字节来填补空隙。显然，就网络带宽而言后一种选择更高效，实践中采用的也是这种做法。

在图 3.29 中，我们假定初始序号为 0。实际上，TCP 连接的两端都会**随机**选择一个初始序号。这样做是为了尽量减少一种可能：两台主机之间早先已终止的某条连接遗留在网络中的报文段，被误认为是这两台主机之间后来某条连接（恰好使用了与旧连接相同的端口号）中的有效报文段 [Sunshine 1978]。

#### Telnet：序号与确认号的一个案例

Telnet（定义于 RFC 854）是一种用于远程登录的流行应用层协议。它运行在 TCP 之上，被设计为可在任意一对主机之间工作。与第 2 章讨论的批量数据传输应用不同，Telnet 是一种交互式应用。这里讨论一个 Telnet 例子，因为它能很好地说明 TCP 的序号与确认号。需要指出，如今用户更愿意使用 SSH 协议而不是 Telnet，因为 Telnet 连接中发送的数据（包括口令！）未加密，使 Telnet 易受窃听攻击。

假设主机 A 向主机 B 发起一个 Telnet 会话。由于 A 发起会话，它被称为客户，B 被称为服务器。用户在客户端键入的每个字符都会被送到远程主机，远程主机则回送每个字符的一个副本，显示在 Telnet 用户的屏幕上。这种"回显"用于确保 Telnet 用户看到的字符已在远端被接收并处理。因此，从用户按键到字符显示在显示器上，每个字符都要在网络中往返两次。

现在假设用户键入了一个字母 'C'，然后端起咖啡喝了一口。我们来考察客户与服务器之间发送的 TCP 报文段。如图 3.30 所示，假设客户与服务器的初始序号分别为 42 和 79。回忆一下，报文段的序号就是其数据字段中第一个字节的序号，因此客户发送的第一个报文段序号为 42，服务器发送的第一个报文段序号为 79。再回忆一下，确认号是主机期望的下一个数据字节的序号。在 TCP 连接建立之后、尚未发送任何数据之前，客户在等待字节 79，服务器在等待字节 42。

如图 3.30 所示，共发送三个报文段。第一个报文段从客户发往服务器，数据字段中装着字母 'C' 的 1 字节 ASCII 表示；该报文段的序号字段为 42。又因为客户尚未从服务器收到任何数据，这个报文段的确认号字段为 79。

<Figure src="ch03/fig3-30.webp" caption="图 3.30　一个简单 Telnet 应用在 TCP 上的序号与确认号" />

第二个报文段从服务器发往客户，它有两个用途。其一，它确认服务器已收到的数据：通过在确认号字段填入 43，服务器告诉客户，它已成功收到直到字节 42 的全部内容，现在正等待字节 43 及其后的字节。其二，它回显字母 'C'，因此第二个报文段的数据字段中是 'C' 的 ASCII 表示。这个报文段的序号为 79，即该 TCP 连接服务器到客户数据流的初始序号，因为这是服务器发送的第一个数据字节。注意，对客户到服务器数据的确认，是搭载在承载服务器到客户数据的报文段中传送的；这种确认被称为**捎带**（piggybacked）在服务器到客户的数据报文段上。

第三个报文段从客户发往服务器，其唯一目的是确认它已从服务器收到的数据。（回忆一下，第二个报文段中包含了服务器到客户的字母 'C'。）该报文段的数据字段为空，即这个确认没有捎带任何客户到服务器的数据。它的确认号字段为 80，因为客户已收到直到序号 79 的字节流，现在正等待字节 80 及其后的字节。你也许会觉得奇怪：这个报文段不含数据，为什么还有序号？但由于 TCP 有序号字段，报文段总得有个序号。

### 3.5.3　往返时间估计与超时

与 3.4 节的 rdt 协议一样，TCP 使用超时/重传机制来从丢失的报文段中恢复。这在概念上很简单，但当我们在 TCP 这样的实际协议中实现超时/重传机制时，会出现许多微妙的问题。最明显的问题大概就是超时间隔该取多长。显然，超时应大于该连接的往返时间（RTT），即从报文段发出到它被确认所经历的时间；否则就会发送不必要的重传。但究竟要大多少？RTT 又该如何估计？是否应为每一个未确认的报文段都关联一个定时器？问题真不少！本节的讨论基于 [Jacobson 1988] 中关于 TCP 的工作，以及当前 IETF 关于 TCP 定时器管理的建议 [RFC 6298]。

#### 估计往返时间

先看 TCP 如何估计发送方与接收方之间的往返时间。做法如下：一个报文段的**样本 RTT**（SampleRTT）是该报文段从发出（即交给 IP）到收到其确认之间所经历的时间。多数 TCP 实现并不为每个发送的报文段都测量一个 SampleRTT，而是在任一时刻只测量一个 SampleRTT。也就是说，在任何时刻，只对某一个已发送但尚未确认的报文段估计 SampleRTT，因而大约每个 RTT 得到一个新的 SampleRTT 值。此外，TCP 从不为**重传**过的报文段计算 SampleRTT，只对**仅发送过一次**的报文段测量 SampleRTT [Karn 1987]。（章末有一道习题请你思考其中的原因。）

显然，由于路由器中的拥塞以及端系统负载的变化，SampleRTT 的值会随报文段不同而波动。由于这种波动，任何一个给定的 SampleRTT 值都可能是非典型的。为了估计一个典型的 RTT，自然要对 SampleRTT 值取某种平均。TCP 维护 SampleRTT 值的一个平均值，称为 EstimatedRTT。每得到一个的新 SampleRTT，TCP 就按下式更新 EstimatedRTT：

$$
\text{EstimatedRTT} = (1 - \alpha) \cdot \text{EstimatedRTT} + \alpha \cdot \text{SampleRTT} \tag{3.1}
$$

上式写成程序设计语言语句的形式——EstimatedRTT 的新值，是 EstimatedRTT 旧值与 SampleRTT 新值的加权组合。推荐的 $\alpha$ 取值为 0.125（即 $\frac{1}{8}$）[RFC 6298]，此时上式变为：

$$
\text{EstimatedRTT} = 0.875 \cdot \text{EstimatedRTT} + 0.125 \cdot \text{SampleRTT}
$$

注意，EstimatedRTT 是 SampleRTT 值的加权平均。正如章末一道习题所讨论的，这种加权平均给予**近期**样本的权重高于**旧**样本。这很自然，因为近期样本更好地反映了网络当前的拥塞状况。在统计学中，这样的平均值称为**指数加权移动平均**（EWMA）。EWMA 中之所以有"指数"二字，是因为随着更新不断进行，某个给定 SampleRTT 的权重按指数速度衰减。章末习题将请你推导 EstimatedRTT 中的指数项。

图 3.31 给出了 gaia.cs.umass.edu（位于马萨诸塞州阿默斯特）到 fantasia.eurecom.fr（位于法国南部）之间一条 TCP 连接在 $\alpha = \frac{1}{8}$ 时的 SampleRTT 值与 EstimatedRTT。可以看到，SampleRTT 的波动在 EstimatedRTT 的计算中被平滑掉了。

<Figure src="ch03/fig3-31.webp" caption="图 3.31　RTT 样本与 RTT 估计" />

除了 RTT 的估计值，RTT 的**变化程度**也是很有价值的度量。[RFC 6298] 把 RTT 偏差 DevRTT 定义为 SampleRTT 通常偏离 EstimatedRTT 多少的估计：

$$
\text{DevRTT} = (1 - \beta) \cdot \text{DevRTT} + \beta \cdot \lvert \text{SampleRTT} - \text{EstimatedRTT} \rvert \tag{3.2}
$$

注意，DevRTT 是 SampleRTT 与 EstimatedRTT 之差的 EWMA。若 SampleRTT 波动很小，DevRTT 就小；反之若波动很大，DevRTT 就大。$\beta$ 的推荐值为 0.25。

#### 设置与管理重传超时间隔

有了 EstimatedRTT 与 DevRTT，TCP 的超时间隔应取何值？显然，该间隔应大于或等于 EstimatedRTT，否则就会发送不必要的重传；但也不能比 EstimatedRTT 大太多，否则报文段丢失时 TCP 不能迅速重传，导致很大的数据传输时延。因此，理想的做法是把超时时间设为 EstimatedRTT 加上一定余量：SampleRTT 波动大时余量应大，波动小时余量应小。DevRTT 的值正该在此发挥作用。TCP 确定重传超时间隔的方法把这些考虑都纳入了：

$$
\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \cdot \text{DevRTT} \tag{3.3}
$$

<AsideCard title="实践中的原理 · TCP 的可靠数据传输">

TCP 通过使用肯定确认和定时器来提供可靠数据传输，做法与 3.4 节所研究的十分相似。TCP 对正确收到的数据予以确认，并在报文段或其确认被认为丢失或损坏时重传报文段。某些版本的 TCP 还有隐式的 NAK 机制——借助 TCP 的**快速重传**机制，收到对某报文段的三个重复 ACK，就相当于对**下一个**报文段的隐式 NAK，从而在超时之前触发该报文段的重传。TCP 用序号让接收方能够识别丢失或重复的报文段。与可靠数据传输协议 rdt3.0 一样，TCP 自身无法确知一个报文段或其 ACK 究竟是丢失、损坏还是被过度延迟；在发送方，TCP 的响应都一样：重传该报文段。

TCP 也使用流水线，允许发送方在任一时刻有多个已发送但尚未确认的报文段在途。前面已经看到，当报文段长度与往返时延之比很小时，流水线能大幅提高会话吞吐量。发送方可以拥有的在途未确认报文段的具体数目，由 TCP 的流量控制与拥塞控制机制决定；TCP 流量控制在本节末尾讨论，拥塞控制在 3.7 节讨论。眼下只需知道 TCP 发送方使用流水线。

推荐的初始 TimeoutInterval 值为 1 秒 [RFC 6298]。此外，一旦发生超时，TimeoutInterval 的值加倍，以避免对随后很快就会被确认的报文段过早超时。不过，一旦收到报文段并更新了 EstimatedRTT，TimeoutInterval 就又用上面的公式重新计算。

### 3.5.4　可靠数据传输

回忆一下，因特网的网络层服务（IP 服务）是不可靠的：IP 不保证数据报交付，不保证数据报按序交付，也不保证数据报中数据的完整性。在 IP 服务下，数据报可能溢出路由器缓冲区而永远到不了目的地，可能失序到达，其中的比特也可能损坏（0 变 1、1 变 0）。由于运输层报文段是由 IP 数据报承载着穿越网络的，运输层报文段同样会遭遇这些问题。

TCP 在 IP 不可靠的尽力而为服务之上，创建了可靠数据传输服务。TCP 的可靠数据传输服务确保：一个进程从 TCP 接收缓冲区读出的数据流是无损坏的、无间隙的、无重复的、且按序的；也就是说，该字节流与连接另一端端系统所发送的字节流完全一致。TCP 提供可靠数据传输的方式，涉及 3.4 节研究过的许多原理。

在先前发展可靠数据传输技术时，从概念上说最容易的假设是：为每个已发送但尚未确认的报文段关联一个定时器。这在理论上很好，但定时器管理可能需要相当大的开销。因此，推荐的 TCP 定时器管理规程 [RFC 6298] 只使用**一个**重传定时器，即使有多个已发送但尚未确认的报文段。本节描述的 TCP 协议遵循这一单定时器建议。

我们分两步、逐步深入地讨论 TCP 如何提供可靠数据传输：先给出一个高度简化的 TCP 发送方描述，它只用超时来从丢失的报文段中恢复；再给出更完整的描述，除超时之外还使用重复 ACK。以下讨论假定数据只在一个方向上传输，即从主机 A 发往主机 B，且 A 正在发送一个大文件。

图 3.32 给出了 TCP 发送方的一个高度简化的描述。可以看到，TCP 发送方中有三个与数据传输和重传有关的主要事件：从上层收到数据、定时器超时、收到 ACK。

发生第一个事件时，TCP 从应用收到数据，把数据封装进报文段，并把报文段交给 IP。注意，每个报文段都包含一个序号，即该报文段中第一个数据字节的字节流编号（见 3.5.2 节）。还要注意，如果定时器尚未因其他报文段而运行，TCP 在把报文段交给 IP 时启动定时器。（把定时器看作与最早的未确认报文段相关联，是有帮助的。）该定时器的超时间隔就是 TimeoutInterval，由 3.5.3 节所述的 EstimatedRTT 与 DevRTT 算出。

第二个主要事件是超时。TCP 通过重传引起超时的那个报文段来响应超时事件，然后重启定时器。

TCP 发送方必须处理的第三个主要事件，是收到来自接收方的确认报文段（更准确地说，是包含有效 ACK 字段值的报文段）。此事件发生时，TCP 把 ACK 值 $y$ 与其变量 SendBase 比较。TCP 状态变量 SendBase 是最早的未确认字节的序号（因此 SendBase − 1 就是已知被接收方正确按序收到的最后一个字节的序号）。如前所述，TCP 使用累积确认，因此 $y$ 确认了序号 $y$ 之前所有字节的接收。若 $y > \text{SendBase}$，则该 ACK 确认了一个或多个此前未确认的报文段；于是发送方更新其 SendBase 变量，并且如果当前还有尚未确认的报文段，就重启定时器。

<p class="tbl-cap">图 3.32　简化的 TCP 发送方</p>

```text
/* 假定发送方不受 TCP 流量控制或拥塞控制的约束，
   上层数据小于 MSS，且数据只在一个方向上传输 */

NextSeqNum = InitialSeqNumber
SendBase   = InitialSeqNumber

loop (forever) {
    switch(event)

        event: 从上层收到数据
            创建序号为 NextSeqNum 的 TCP 报文段
            if (定时器当前未运行)
                启动定时器
            把报文段交给 IP
            NextSeqNum = NextSeqNum + length(data)
            break;

        event: 定时器超时
            重传序号最小的尚未确认的报文段
            启动定时器
            break;

        event: 收到 ACK，其 ACK 字段值为 y
            if (y > SendBase) {
                SendBase = y
                if (当前还有尚未确认的报文段)
                    启动定时器
            }
            break;

} /* loop forever 结束 */
```

#### 几个有趣的场景

以上描述了 TCP 提供可靠数据传输的一个高度简化版本，但即便是这个高度简化的版本也有许多微妙之处。为体会该协议如何工作，下面走一遍几个简单场景。

图 3.33 描绘了第一个场景：主机 A 向主机 B 发送一个报文段，假设该报文段序号为 92、含 8 字节数据。发出后，主机 A 等待来自 B 的、确认号为 100 的报文段。虽然 A 的报文段被 B 收到，但 B 发往 A 的确认丢失了。此时发生超时事件，主机 A 重传同一个报文段。当然，当主机 B 收到这次重传时，它从序号看出该报文段包含的是已经收到的数据，于是 B 中的 TCP 丢弃重传报文段中的字节。

<Figure src="ch03/fig3-33.webp" caption="图 3.33　因确认丢失而重传" />

第二个场景如图 3.34 所示：主机 A 背靠背发送两个报文段，第一个序号 92、含 8 字节数据，第二个序号 100、含 20 字节数据。假设两个报文段都完好到达 B，B 分别为它们发送两个确认：第一个确认号为 100，第二个确认号为 120。现假设这两个确认在超时之前都未到达主机 A。超时事件发生时，主机 A 重发序号为 92 的第一个报文段，并重启定时器。只要第二个报文段的 ACK 在新的超时之前到达，第二个报文段就不会被重传。

#### 快速重传

超时触发重传的问题之一，是超时周期可能相对较长。当一个报文段丢失时，这个较长的超时周期迫使发送方延迟重发丢失的分组，从而增大端到端时延。所幸，发送方常常可以在超时事件发生之前，通过所谓的**重复 ACK** 推断出分组丢失。重复 ACK 是对某个报文段的再次确认，而发送方此前已经收到过对该报文段的确认。要理解发送方对重复 ACK 的响应，必须先弄清接收方究竟为什么发送重复 ACK。

当 TCP 接收方收到的报文段序号大于下一个期望的按序序号时，它就在数据流中检测到一个**间隙**，即有报文段缺失。这个间隙可能是网络中的报文段丢失或乱序造成的。由于 TCP 使用累积确认，一旦检测到间隙，TCP 接收方只是对它已收到的最后一个按序字节重新确认（即产生一个重复 ACK）。由于发送方使用流水线，收发双方之间可能有许多在途报文段；若其中一个在途报文段丢失，TCP 接收方很可能会产生许多背靠背的重复 ACK。因此，如果 TCP 发送方收到对同一数据的三个重复 ACK（即先收到该数据的一个原始 ACK，随后又收到对同一数据的三个额外 ACK），它就认为：被确认了四次的报文段**之后**的那个报文段已经丢失。（章末习题将讨论为什么发送方要等三个重复 ACK，而不是只等一个。）收到三个重复 ACK 时，TCP 发送方执行**快速重传**（fast retransmit）[RFC 5681]，在该报文段的定时器超时之前重传丢失的报文段。

#### 回退 N 步还是选择重传？

在结束对 TCP 差错恢复机制的讨论之前，考虑这样一个问题：TCP 是 GBN 协议还是 SR 协议？回忆一下，TCP 的确认是累积的，接收方不会对正确收到但失序的报文段逐个确认。因此，如图 3.32（另见图 3.19）所示，TCP 发送方只需维护已发送但未确认字节的最小序号（SendBase）以及下一个待发字节的序号（NextSeqNum）。从这个意义上说，TCP 很像 GBN 风格的协议。

但 TCP 与 GBN 之间也有一些显著差异。许多 TCP 实现会缓存正确收到但失序的报文段 [Stevens 1994]。再考虑这样一种情形：发送方发送报文段 1, 2, …, N，所有报文段都按序、无差错地到达接收方；进一步假设对报文段 $n$（$n < N$）的确认丢失了，而其余 $N - 1$ 个确认都在各自超时之前到达了发送方。在这个例子中，GBN 不仅要重传报文段 $n$，还要重传其后所有报文段 $n + 1, n + 2, …, N$；而 TCP 至多重传一个报文段，即报文段 $n$。更有甚者，如果对报文段 $n + 1$ 的确认在报文段 $n$ 超时之前到达，TCP 根本不会重传报文段 $n$。

对 TCP 的一项建议修改——所谓**选择确认**（selective acknowledgment）[RFC 2018]——允许 TCP 接收方确认失序的报文段……

选择性确认 [RFC 2018] 使 TCP 接收方能够对失序的报文段逐个确认，而不只是累积确认最后一个正确收到的按序报文段。当它与选择性重传——跳过那些已被接收方选择性确认过的报文段的重传——结合使用时，TCP 就与我们所讲的一般的 SR 协议颇为相似了。因此，TCP 的差错恢复机制最好归类为 GBN 与 SR 的**混合体**。

### 3.5.5　流量控制

回忆一下，TCP 连接两端的每台主机都为该连接预留了一个接收缓冲区。当 TCP 连接收到正确且按序的字节时，它就把数据放入接收缓冲区。相应的应用进程会从这个缓冲区读取数据，但不一定在数据到达的那一刻就读。事实上，接收方应用可能正忙于其他任务，甚至可能在数据到达很久之后才去读。如果应用读取数据相对较慢，发送方就很容易因发送过多、过快的数据而使该连接的接收缓冲区溢出。

TCP 为其应用提供**流量控制**（flow control）服务，以消除发送方使接收方缓冲区溢出的可能。因此，流量控制是一种**速度匹配**服务——把发送方发送的速率与接收方应用读取的速率匹配起来。如前所述，TCP 发送方也可能因 IP 网络内部的拥塞而受到抑制；这种形式的发送方控制称为**拥塞控制**，将在 3.6 与 3.7 节详细探讨。尽管流量控制与拥塞控制所采取的动作相似（都是抑制发送方），但其原因显然截然不同。不幸的是，许多作者把这两个术语混用，聪明的读者应当把它们区分开来。下面讨论 TCP 如何提供流量控制服务。为看清主干，本节通篇假定 TCP 实现采取"接收方丢弃失序报文段"的做法。

TCP 通过让发送方维护一个称为**接收窗口**（receive window）的变量来提供流量控制。通俗地说，接收窗口用来告诉发送方：接收方还有多少可用的缓冲区空间。由于 TCP 是全双工的，连接每一端的发送方都各自维护一个不同的接收窗口。我们结合文件传输来考察接收窗口。假设主机 A 通过一条 TCP 连接向主机 B 发送一个大文件。主机 B 为该连接分配一个接收缓冲区，记其大小为 RcvBuffer。主机 B 的应用进程不时从该缓冲区读取数据。定义以下变量：

- `LastByteRead`：B 的应用进程从缓冲区读出的数据流中最后一个字节的编号；
- `LastByteRcvd`：从网络到达并已放入 B 的接收缓冲区的数据流中最后一个字节的编号。

由于 TCP 不允许使分配的缓冲区溢出，必须满足

$$
\text{LastByteRcvd} - \text{LastByteRead} \le \text{RcvBuffer}
$$

接收窗口记为 rwnd，被设为缓冲区中的空闲空间量：

$$
\text{rwnd} = \text{RcvBuffer} - [\text{LastByteRcvd} - \text{LastByteRead}]
$$

由于空闲空间随时间变化，rwnd 是动态的。变量 rwnd 如图 3.36 所示。

<Figure src="ch03/fig3-36.webp" caption="图 3.36　接收窗口（rwnd）与接收缓冲区（RcvBuffer）" />

连接如何使用变量 rwnd 来提供流量控制服务呢？主机 B 通过把它当前的 rwnd 值放入发往 A 的每个报文段的接收窗口字段，来告诉主机 A 该连接缓冲区还有多少空闲空间。初始时，主机 B 置 rwnd = RcvBuffer。注意，要做到这一点，主机 B 必须跟踪若干与该连接相关的变量。

主机 A 则跟踪两个变量 LastByteSent 与 LastByteAcked，含义不言自明。注意这两个变量之差 LastByteSent − LastByteAcked，就是 A 已送入该连接但尚未被确认的数据量。只要让未确认数据量小于 rwnd 的值，主机 A 就能确保不会使主机 B 的接收缓冲区溢出。因此，在连接的整个生命周期内，主机 A 都要保证

$$
\text{LastByteSent} - \text{LastByteAcked} \le \text{rwnd}
$$

这个方案有一个小的技术问题。设想主机 B 的接收缓冲区已满，于是 rwnd = 0。在向主机 A 通告 rwnd = 0 之后，再假设 B 没有数据要发给 A。现在考虑会发生什么：随着 B 的应用进程清空缓冲区，TCP 并不会向主机 A 发送带有新 rwnd 值的新报文段——事实上，TCP 只有在有数据要发或有确认要发时才向主机 A 发送报文段。因此，主机 A 永远得不到"B 的接收缓冲区已有空闲空间"的通知，A 就被阻塞住、再也发不出数据了！为解决这个问题，TCP 规范要求：当 B 的接收窗口为 0 时，主机 A 仍继续发送只含 1 个数据字节的报文段。这些报文段会被接收方确认；最终缓冲区开始腾空，确认中就会包含非零的 rwnd 值。

在描述了 TCP 的流量控制服务之后，还要简要指出：UDP **不**提供流量控制，因此报文段可能因接收方缓冲区溢出而在接收方丢失。例如，考虑从主机 A 的某个进程向主机 B 的某个进程发送一系列 UDP 报文段：在典型的 UDP 实现中，UDP 会把这些报文段追加到一个有限大小的缓冲区中，该缓冲区"位于"相应套接字（即进程之门）之前。进程一次从缓冲区读取一整个报文段；如果进程读取的速度不够快，缓冲区就会溢出，报文段就会被丢弃。

### 3.5.6　TCP 连接管理

本小节仔细考察 TCP 连接如何建立与拆除。这个话题看似不那么令人兴奋，但却很重要，因为 TCP 连接建立会显著增加可感知的时延（例如上网浏览时）；此外，许多最常见的网络攻击——包括极为流行的 SYN 洪泛攻击（见后文专栏）——利用的正是 TCP 连接管理中的弱点。

先看 TCP 连接如何建立。假设一台主机（客户）中运行的进程想与另一台主机（服务器）中的进程建立连接。客户应用进程首先告知客户 TCP：它想与服务器中的某个进程建立连接。随后客户端的 TCP 按下列方式与服务器端的 TCP 建立 TCP 连接：

- **第 1 步。** 客户端的 TCP 首先向服务器端的 TCP 发送一个特殊的 TCP 报文段。该报文段不含应用层数据，但其首部中的一个标志位（见图 3.28）——SYN 比特——被置为 1。因此，这个特殊报文段被称为 **SYN 报文段**。此外，客户随机选择一个初始序号（client*isn），并把它放入该初始 TCP SYN 报文段的序号字段。该报文段被封装进一个 IP 数据报，发往服务器。如何恰当地随机化 client*isn 的选择，以避免某些安全攻击，一直是人们相当关注的问题 [RFC 4987]。
- **第 2 步。** 一旦包含 TCP SYN 报文段的 IP 数据报到达服务器主机（假定它确实到达了！），服务器就从数据报中取出该 TCP SYN 报文段，为该连接分配 TCP 缓冲区与变量，并向客户 TCP 发送一个**允许连接**报文段。（第 8 章将会看到，在完成三次握手第三步之前就分配这些缓冲区与变量，使 TCP 容易遭受一种称为 SYN 洪泛的拒绝服务攻击。）该允许连接报文段同样不含应用层数据，但其首部包含三条重要信息：第一，SYN 比特置为 1；第二，TCP 报文段首部的确认字段置为 client*isn + 1；第三，服务器选择自己的初始序号（server*isn），并把它放入 TCP 报文段首部的序号字段。这个允许连接报文段实际上是在说："我收到了你要求建立连接的 SYN 报文，你的初始序号是 client*isn。我同意建立这条连接，我的初始序号是 server*isn。"该报文段被称为 **SYNACK 报文段**。
- **第 3 步。** 收到 SYNACK 报文段后，客户也要为该连接分配缓冲区与变量。随后，客户主机再向服务器发送一个报文段；这最后一个报文段对服务器的允许连接报文段予以确认（客户把 server_isn + 1 放入 TCP 报文段首部的确认字段来完成这一确认）。由于连接已经建立，SYN 比特置为 0。三次握手的这第三个阶段可以在报文段载荷中携带客户到服务器的数据。

这三步完成之后，客户与服务器主机就可以互相发送包含数据的报文段了；此后所有报文段中的 SYN 比特都将置为 0。注意，为建立连接，两台主机之间共发送三个分组，如图 3.37 所示。因此，这个连接建立过程常被称为**三次握手**。TCP 三次握手的若干方面将在章末习题中探讨（为什么需要初始序号？为什么需要三次握手而不是两次握手？）。有趣的是，攀岩者与保护者（位于攀岩者下方、负责处理其安全绳的人）所用的通信协议也是三次握手，与 TCP 完全相同，以确保在攀岩者开始向上攀爬之前双方都已准备就绪。

<Figure src="ch03/fig3-37.webp" caption="图 3.37　TCP 三次握手：报文段交换" />

既然发起三次握手的 TCP 客户必须等到收到服务器的 SYNACK 消息，才能知道服务器已接受连接、连接状态已初始化，那么任何这类握手协议（例如第 8 章将研究的 TLS 协议，或第 2 章研究过、本章稍后还会再谈的 QUIC 协议）在连接建立时似乎都天然存在一个 RTT 的时延。不过，如果客户与服务器此前通信过，就可以使用一种称为"快速打开"（fast open）的技术，把握手时间降到零！也就是说，客户可以向此前通信过的面向连接服务器立即发送数据，而不必执行传统三次握手的前两步。

快速打开（有时也称为 **0-RTT 握手**）的关键思想是：在传统三次握手期间，客户可以请求服务器提供一个快速打开 cookie，该 cookie 编码了未来连接所需的全部连接信息。这个 cookie 由客户与服务器各自保存。下次客户想与这台服务器建立连接时，就在发给服务器的第一条消息中带上该快速打开 cookie 以及应用层数据。服务器检查该 cookie，认为可以接受，就接受连接、根据 cookie 建立连接参数，并对初始消息中的应用层数据作出响应，回送服务器的应用层响应数据——从而完全避免了"发送数据前要等一个 RTT"的三次握手时延。

需要强调的是，快速打开只是对客户的一种可能的优化；服务器可能出于策略原因不接受快速打开 cookie，例如服务器不再想与该客户通信，或想强制该客户重新进行身份认证（例如 TLS 握手的情形）。客户把 cookie 端到服务器面前，并不意味着服务器非得"吃"（接受）这块 cookie！当然，快速打开 cookie 必须以密码学安全的方式生成，所用技术将在第 8 章研究。TCP 快速打开见 RFC 7413；TLS（见第 8 章及 RFC 8446）与 QUIC 协议 [RFC 9000; RFC 9002] 也支持零 RTT 的快速打开。

天下没有不散的筵席，TCP 连接也是如此。参与一条 TCP 连接的两个进程中的任何一个都可以结束该连接。连接结束时，主机中的"资源"（即缓冲区与变量）被释放。举例来说，假设客户决定关闭连接，如图 3.38 所示。客户应用进程发出关闭命令，这使客户 TCP 向服务器进程发送一个特殊的 TCP 报文段，其首部中的标志位——FIN 比特（见图 3.28）——置为 1。服务器收到该报文段后，向客户回送一个确认报文段；随后服务器发送自己的关闭报文段，其 FIN 比特置为 1；最后，客户确认服务器的关闭报文段。至此，两台主机中的所有资源都被释放。

<Figure src="ch03/fig3-38.webp" caption="图 3.38　关闭一条 TCP 连接" />

在一条 TCP 连接的生命期内，每台主机中运行的 TCP 协议会在各种 TCP 状态之间转换。图 3.39 展示了客户端 TCP 通常经历的一系列 TCP 状态。客户端 TCP 从 CLOSED 状态开始。客户侧应用发起一条新的 TCP 连接（在第 2 章的 Python 示例中，就是创建一个 Socket 对象），这使客户端的 TCP 向服务器端的 TCP 发送一个 SYN 报文段。发出 SYN 报文段后，客户端 TCP 进入 SYN*SENT 状态。在 SYN*SENT 状态下，客户端 TCP 等待来自服务器 TCP 的、包含对客户前一个报文段的确认且 SYN 比特置 1 的报文段。收到这样的报文段后，客户端 TCP 进入 ESTABLISHED 状态。在 ESTABLISHED 状态下，TCP 客户可以发送和接收包含载荷（即应用产生的）数据的 TCP 报文段。

<Figure src="ch03/fig3-39.webp" caption="图 3.39　客户端 TCP 通常经历的一系列 TCP 状态" />

假设客户应用决定关闭连接（注意，服务器也可以选择关闭连接）。这使客户端 TCP 发送一个 FIN 比特置 1 的 TCP 报文段，并进入 FIN*WAIT*1 状态。在 FIN*WAIT*1 状态下，客户端 TCP 等待来自服务器的带确认的 TCP 报文段。收到该报文段后，客户端 TCP 进入 FIN*WAIT*2 状态。在 FIN*WAIT*2 状态下，客户等待服务器发来另一个 FIN 比特置 1 的报文段；收到后，客户端 TCP 确认服务器的报文段，并进入 TIME*WAIT 状态。TIME*WAIT 状态让 TCP 客户在最终确认丢失时能够重发它。在 TIME_WAIT 状态停留的时间取决于具体实现，典型值为 30 秒、1 分钟和 2 分钟。等待结束后，连接正式关闭，客户侧的所有资源（包括端口号）都被释放。

<Figure src="ch03/fig3-40.webp" caption="图 3.40　服务器端 TCP 通常经历的一系列 TCP 状态" />

图 3.40 展示了在假定客户发起连接拆除的情况下，服务器端 TCP 通常经历的一系列状态，其转换不言自明。在这两个状态转换图中，我们只展示了 TCP 连接通常如何建立与关闭，没有描述某些病态场景，例如连接双方同时想发起或关闭连接。若想了解这些问题以及其他 TCP 高级话题，建议参阅 Stevens 的综合性著作 [Stevens 1994]。

以上讨论假定客户与服务器都准备好通信，即服务器正在客户发送 SYN 报文段的那个端口上监听。那么，当一台主机收到的 TCP 报文段的端口号或源 IP 地址与该主机中任何现有套接字都不匹配时，会发生什么？例如，假设某主机收到一个目的端口为 80 的 TCP SYN 分组，但该主机并不在端口 80 上接受连接（即它没有在端口 80 上运行 Web 服务器）。此时，该主机会向源端发送一个特殊的**重置报文段**，其 RST 标志位（见 3.5.2 节）置为 1。因此，当一台主机发送重置报文段时，它是在告诉源端："我没有与该报文段对应的套接字，请不要重发该报文段。"当主机收到的 UDP 分组的目的端口号与任何现有 UDP 套接字都不匹配时，主机会发送一个特殊的 ICMP 数据报，详见第 5 章。

<AsideCard title="安全聚焦 · SYN 洪泛攻击">

在讨论 TCP 三次握手时我们已经看到，服务器在收到 SYN 后会分配并初始化连接变量与缓冲区，然后回送一个 SYNACK，并等待客户的 ACK 报文段。如果客户不发送 ACK 来完成三次握手的第三步，服务器最终（往往在一分钟甚至更久之后）会终止这个**半开连接**，并回收已分配的资源。

正是这套 TCP 连接管理协议，为一种经典的拒绝服务（DoS）攻击——**SYN 洪泛攻击**（SYN flood attack）——埋下了伏笔。在这种攻击中，攻击者发送大量 TCP SYN 报文段，却不完成握手的第三步。面对这铺天盖地的 SYN 报文段，服务器的连接资源被大量分配给半开连接（而且永远不会被使用！），从而被耗尽；合法客户于是得不到服务。这类 SYN 洪泛攻击是最早被记录的 DoS 攻击之一；30 年过去了，SYN 洪泛攻击仍占 DoS 攻击的 14% [Fastly 2024]。所幸，一种称为 **SYN cookie** 的有效防御手段 [RFC 4987] 如今已部署在大多数主流操作系统中。SYN cookie 的工作方式如下：

- 服务器收到 SYN 报文段时，无法判断它来自合法用户还是 SYN 洪泛攻击的一部分。因此，服务器不为这个 SYN 创建半开 TCP 连接，而是生成一个初始 TCP 序号，该序号是 SYN 报文段的源/目的 IP 地址与端口号、以及一个只有服务器知道的秘密数的复杂函数（散列函数）。这个精心构造的初始序号就是所谓的"cookie"。服务器随后向客户发送带有该特殊初始序号的 SYNACK 分组。重要的是，服务器**不**保存这个 cookie，也不保存与该 SYN 对应的任何状态信息。
- 合法客户会回送一个 ACK 报文段。服务器收到该 ACK 时，必须验证它确实对应此前发出的某个 SYN。可服务器对 SYN 报文段毫无记忆，这该如何做到？你可能已经猜到——靠 cookie。回忆一下，对于合法的 ACK，其确认字段的值等于 SYNACK 中的初始序号（此处即 cookie 值）加 1（见图 3.37）。于是服务器可以用 SYNACK 中的源/目的 IP 地址与端口号（它们与原始 SYN 中的相同）以及那个秘密数，再运行一遍同样的散列函数。如果函数结果加 1 恰好等于客户 ACK 中的确认（cookie）值，服务器就断定该 ACK 对应于此前的某个 SYN 报文段，因而有效；随后服务器创建一条完全打开的连接以及一个套接字。
- 反之，如果客户不回送 ACK 报文段，那么最初那个 SYN 对服务器毫无损害，因为服务器尚未针对这个伪造的 SYN 分配任何资源。

## 3.6　拥塞控制原理

前面几节既考察了在分组丢失情况下提供可靠数据传输服务的一般原理，也考察了 TCP 的具体机制。前面提到，实践中这类丢失通常源于网络拥塞时路由器缓冲区的溢出。因此，分组重传只是**治标**——处理网络拥塞的一个症状（某个运输层报文段的丢失），却没有**治本**——网络拥塞的根源在于太多源端试图以过高的速率发送数据。要治本，就需要有这样的机制：在网络拥塞时抑制发送方。

本节在一般意义上讨论拥塞控制问题，力求弄清：为什么拥塞是坏事？网络拥塞如何体现在上层应用所获得的性能上？有哪些办法可以避免拥塞或对拥塞作出反应？这种一般性研究是恰当的，因为与可靠数据传输一样，拥塞控制高居网络领域"十大根本问题"之列。下一节则详细研究 TCP 的拥塞控制算法。

### 3.6.1　拥塞的成因与代价

我们从三个越来越复杂的拥塞场景入手，开始对拥塞控制的一般性研究。在每个场景中，我们都考察拥塞究竟因何而起，以及拥塞的代价（就资源未被充分利用、端系统获得较差性能而言）。我们（暂时）不关注如何应对或避免拥塞，而只关注一个更简单的问题：当主机提高发送速率、网络变得拥塞时，究竟会发生什么。

#### 场景 1：两个发送方、一台无限缓冲的路由器

从最简单的拥塞场景开始：两台主机（A 与 B）各有一条连接，在源与目的之间共享一段单跳链路，如图 3.41 所示。

假设主机 A 中的应用以平均速率 $\lambda_{\text{in}}$ 字节/秒向连接中送入数据。这些数据是"原始"的，即每个数据单元只被送入套接字一次。底层运输层协议很简单：封装数据并发送，不做任何差错恢复（如重传）、流量控制或拥塞控制。忽略添加运输层与低层首部带来的额外开销，场景 1 中主机 A 向路由器提供的流量速率就是 $\lambda_{\text{in}}$ 字节/秒。主机 B 以类似方式工作，为简单起见假定它也以 $\lambda_{\text{in}}$ 字节/秒的速率发送。来自 A 和 B 的分组经过一台路由器，再通过一条容量为 $R$ 的共享出链路。路由器配有缓冲区，当分组到达速率超过出链路容量时用来暂存到达的分组。在场景 1 中，假定路由器拥有无限大的缓冲空间。

<Figure src="ch03/fig3-41.webp" caption="图 3.41　拥塞场景 1：两条连接共享一条无限缓冲的单跳链路" />

图 3.42 描绘了场景 1 下主机 A 这条连接的性能。左图给出每条连接的吞吐量（接收方每秒收到的字节数）随连接发送速率的变化。当发送速率在 0 与 $\frac{R}{2}$ 之间时，接收方吞吐量等于发送方发送速率——发送方发出的所有数据都以有限时延被接收方收到。然而当发送速率超过 $\frac{R}{2}$ 时，吞吐量只有 $\frac{R}{2}$。这个吞吐量上限是两条连接共享链路容量的结果：在稳态下，链路根本无法以超过 $\frac{R}{2}$ 的速率向接收方交付分组。无论 A、B 把发送速率设得多高，各自看到的吞吐量都不会超过 $\frac{R}{2}$。

<Figure src="ch03/fig3-42.webp" caption="图 3.42　拥塞场景 1：吞吐量和时延随主机发送速率的变化" />

每条连接达到 $\frac{R}{2}$ 的吞吐量，看上去似乎是件好事，因为链路在向目的地交付分组方面得到了充分利用。然而图 3.42 的右图揭示了在接近链路容量运行时会发生什么：当发送速率（从左侧）逼近 $\frac{R}{2}$ 时，平均时延越来越大；一旦发送速率超过 $\frac{R}{2}$，路由器中排队的平均分组数将无界增长，源到目的的平均时延趋于无穷（假定连接以这些发送速率运行无限长时间，且缓冲无限大）。因此，虽然从吞吐量角度看，以接近 $R$ 的总吞吐量运行是理想的，但从时延角度看却远非理想。即便在这个（极端）理想化的场景中，我们已经找到了**拥塞网络的一种代价——当分组到达速率接近链路容量时，将经历很大的排队时延**。

#### 场景 2：两个发送方、一台有限缓冲的路由器

现在把场景 1 稍作两处修改（见图 3.43）。第一，假定路由器缓冲区的容量有限。这一贴近现实的假设带来的后果是：当分组到达一个已满的缓冲区时将被丢弃。第二，假定每条连接都是可靠的：若承载运输层报文段的分组在路由器处被丢弃，发送方最终会重传它。由于分组可能被重传，我们在使用"发送速率"一词时必须更谨慎。具体地说，仍用 $\lambda_{\text{in}}$ 表示应用向套接字送入原始数据的速率；而运输层向网络发送报文段（含原始数据与重传数据）的速率记作 $\lambda '_{\text{in}}$，$\lambda '_{\text{in}}$ 有时称为向网络**提供的负载**（offered load）。

<Figure src="ch03/fig3-43.webp" caption="图 3.43　场景 2：两台主机（带重传）与一台有限缓冲的路由器" />

场景 2 下实现的性能，此时将强烈依赖于重传是如何进行的。先考虑一个不现实的极端：主机 A 能（神奇地！）判断路由器中是否有空闲缓冲区，因而只在有空闲缓冲时才发送分组。此时不会发生丢失，$\lambda_{\text{in}}$ 等于 $\lambda '_{\text{in}}$，连接吞吐量等于 $\lambda_{\text{in}}$。这一情形如图 3.44(a) 所示。从吞吐量角度看性能是理想的——发出的都被收到。注意在此情形下，主机的平均发送速率不可能超过 $\frac{R}{2}$，因为假定从不发生分组丢失。

<Figure src="ch03/fig3-44.webp" caption="图 3.44　有限缓冲下场景 2 的性能" />

再看稍为现实一些的情形：发送方只在确知某分组已丢失时才重传。（这一假设也有点勉强，但发送方确实可以把超时设得足够大，以致几乎可以确信未被确认的分组已经丢失。）此时性能大致如图 3.44(b) 所示。为理解其中缘由，考虑提供的负载 $\lambda '_{\text{in}}$（原始数据传输速率加重传）等于 $\frac{R}{2}$ 的情形：按图 3.44(b)，在此提供的负载下，数据交付给接收方应用的速率是 $\frac{R}{3}$。于是在所传输的 $0.5 R$ 单位数据中，平均有 $0.333 R$ 字节/秒是原始数据，$0.166 R$ 字节/秒是重传数据。这里我们看到了**拥塞网络的第二种代价——发送方必须重传，以补偿因缓冲区溢出而被丢弃（丢失）的分组**。

最后，考虑发送方可能过早超时、从而重传一个在队列中被延迟但尚未丢失的分组的情形。此时，原始数据分组与重传副本都可能到达接收方。当然，接收方只需要该分组的一份，会丢弃重传副本。在这种情况下，路由器转发原始分组重传副本所做的工作被浪费了，因为接收方早已收到该分组的原始副本；路由器本可以把链路传输能力用于发送别的分组。**这就是拥塞网络的第三种代价——面对大时延时，发送方不必要的重传会使路由器把链路带宽用于转发无用的分组副本**。若假定每个分组平均被路由器转发两次，图 3.44(c) 给出了吞吐量随提供的负载的变化；由于每个分组被转发两次，当提供的负载逼近 $\frac{R}{2}$ 时，吞吐量的渐近值为 $\frac{R}{4}$。

#### 场景 3：四个发送方、有限缓冲的路由器与多跳路径

在最后一个拥塞场景中，四台主机各自通过重叠的两跳路径发送分组，如图 3.45 所示。我们仍假定每台主机都用超时/重传机制实现可靠数据传输服务，所有主机的 $\lambda_{\text{in}}$ 相同，所有路由器链路的容量均为 $R$ 字节/秒。

考虑从主机 A 到主机 C、经过路由器 R1 和 R2 的连接。A–C 连接与 D–B 连接共享路由器 R1，与 B–D 连接共享路由器 R2。当 $\lambda_{\text{in}}$ 极小时，缓冲区溢出很少发生（与场景 1、2 一样），吞吐量约等于提供的负载。当 $\lambda_{\text{in}}$ 稍大时，相应吞吐量也更大，因为更多原始数据被送入网络并交付到目的地，而溢出仍然很少。因此，对较小的 $\lambda_{\text{in}}$，$\lambda_{\text{in}}$ 增大导致 $\lambda_{\text{out}}$ 增大。

考察了极低流量情形之后，再看 $\lambda_{\text{in}}$（因而 $\lambda '_{\text{in}}$）极大的情形。考虑路由器 R2：无论 $\lambda_{\text{in}}$ 取何值，A–C 流量到达 R2（经 R1 转发后到达 R2）的速率至多为 $R$，即 R1 到 R2 那条链路的容量。如果所有连接（包括 B–D 连接）的 $\lambda '_{\text{in}}$ 都极大，那么 B–D 流量到达 R2 的速率可能远大于 A–C 流量的到达速率。由于 A–C 与 B–D 流量必须在路由器 R2 处竞争有限的缓冲空间，随着 B–D 提供的负载越来越大，能够成功通过 R2（即未因缓冲区溢出而丢失）的 A–C 流量就越来越少。在极限情形下，当提供的负载趋于无穷时，R2 中刚空出的缓冲区立刻被 B–D 分组填满，A–C 连接在 R2 处的吞吐量趋于零；这又意味着，在重载极限下 A–C 的端到端吞吐量趋于零。这些考虑引出了图 3.46 所示的提供的负载与吞吐量之间的折衷关系。

<Figure src="ch03/fig3-45.webp" caption="图 3.45　四个发送方、有限缓冲的路由器与多跳路径" />

<Figure src="ch03/fig3-46.webp" caption="图 3.46　有限缓冲与多跳路径下场景 3 的性能" />

一旦考虑网络所做的无用功，吞吐量随提供的负载增加而最终下降的原因就一目了然了。在上述高流量场景中，只要分组在第二跳路由器处被丢弃，第一跳路由器把它转发给第二跳路由器所做的工作就"白费"了。如果第一台路由器干脆丢弃该分组并保持空闲，网络的处境也一样（更准确地说，也一样糟）。更要紧的是，第一台路由器为把该分组转发给第二台路由器而占用的传输能力，本可以更有价值地用于传输另一个分组。（例如，在选择要发送的分组时，路由器或许应当优先发送那些已经经过若干上游路由器的分组。）于是我们看到了**因拥塞而丢弃分组的又一种代价——当一个分组沿路径被丢弃时，各上游链路上为把它转发到丢弃点而消耗的传输能力都白费了**。

有了对拥塞代价的新认识——分组到达速率接近拥塞链路容量时排队时延增大（图 3.42）、因存在重传分组而使应用间吞吐量下降（图 3.44）、以及可能发生**拥塞崩溃**（图 3.46）——实施某种形式的拥塞控制显然是必要的。

在考察解决拥塞控制问题的方法之前，先退一步，看看这些协议试图解决的根本问题。图 3.47 展示了 $N$ 条运输层连接通过一条最大传输速率为 $R$ bps 的共享**瓶颈链路**。一条连接的瓶颈链路，是端到端路径上这样一条链路：若经过该链路的各发送方缓慢提高其发送速率，则该链路将是这些连接的端到端路径上最先出现拥塞丢失的链路。通常，我们只在链路处于拥塞状态时才称其为瓶颈链路。一个常见假设 [Cardwell 2017; Kleinrock 2018]——它在理论与实践上通常都成立 [Hu 2024]——是一条连接至多有一条瓶颈链路；源到目的路径不同的连接，其瓶颈链路也可能不同。

<Figure src="ch03/fig3-47.webp" caption="图 3.47　N 条连接共享一条容量为 R 的瓶颈链路" />

一条路径的瓶颈链路在拥塞控制中扮演重要角色。假设某瓶颈链路处于拥塞状态，即到达该链路的流量速率接近其容量 $R$。如果这 $N$ 条连接都提高发送速率，瓶颈链路也无法为这些连接提供任何额外吞吐量，因为该链路已经拥塞，在这种拥塞状态下始终忙于传输流量。因此，**通过该瓶颈链路的 $N$ 条连接所获得的总端到端吞吐量，将由瓶颈链路的传输速率 $R$ 决定**。而如果链路容量在这 $N$ 条连接之间被公平地共享（见 7.3.4 节），则每条连接的吞吐量为 $\frac{R}{N}$。

一个类比有助于直观理解。把图 3.47 中的 $N$ 条连接想象成 $N$ 根软管，它们接到一根共用的总软管上，总软管的最大出水流量为 $R$ 升/秒；总软管的出水量再平均分配给从它分出的、通向 $N$ 个目的地的 $N$ 根软管。凭经验可知，如果这 $N$ 条连接的输入速率之和超过 $R$ 升/秒，共用软管仍然无法输出超过其最大流量 $R$ 升/秒的水，因而任何端到端软管路径的流量都不会超过 $\frac{R}{N}$ 升/秒。

带着这一认识回到计算机网络：拥塞控制的目标应当是，**让图 3.47 中的 $N$ 条连接设定其运输层发送速率，使它们的总发送速率接近但不超过瓶颈链路的容量**。总发送速率低于这一理想值，会在发送方还有数据要发时使链路有时空闲；总发送速率高于这一理想值，则会遭受我们刚刚研究过的链路拥塞的全部负面后果。

于是立刻浮现出两个基本问题：

- 一条连接如何知道其源到目的路径上的某条链路发生了拥塞，即存在瓶颈链路？我们将在 7.6.2 节讨论这个问题。
- 各连接如何各自调节发送速率，使其总发送速率接近但不超过其路径上瓶颈链路的容量？我们将在 7.3 节看到 TCP 拥塞控制的不同"变体"如何回答这个问题。

### 3.6.2　端到端与网络辅助的拥塞控制

3.7 节将详细考察 TCP 具体的拥塞控制方法。这里先指出实践中采用的两大类拥塞控制方法，并讨论体现这些方法的具体网络体系结构与拥塞控制协议。

从最高层次看，可以按**网络层是否向运输层提供显式的拥塞控制协助**来区分不同的拥塞控制方法：

::: tip 要点

1. **端到端拥塞控制。** 在端到端方法中，网络层不为拥塞控制目的向运输层提供任何显式支持；甚至网络是否拥塞，也必须由端系统仅依据观察到的网络行为（例如分组丢失和时延）来推断。稍后 3.7.1 与 3.7.2 节将会看到，TCP 采取的正是这种端到端方法，因为 IP 层并不被要求向主机反馈网络拥塞信息。我们将考察 TCP 的若干不同"变体"：在某些变体中，报文段丢失（由超时或收到三个重复 ACK 指示）被当作网络拥塞的迹象，TCP 据此减小其窗口；另一些变体的 TCP 则用测得的往返时延和/或吞吐量来确定发送速率。
1. **网络辅助拥塞控制。** 在网络辅助方法中，路由器向发送方和/或接收方显式反馈网络的拥塞状态。这种反馈可以简单到用一个比特指示某条链路发生拥塞——早期 IBM SNA [Schwartz 1982]、DEC DECnet [Jain 1989; Ramakrishnan 1990] 以及 ATM [Black 1995] 网络体系结构采取的就是这种做法；也可以更精细，例如在 ATM 可用比特率（ABR）拥塞控制中，路由器把出链路上它能支持的最大主机发送速率告知发送方。如上所述，IP 与 TCP 的因特网默认版本采取端到端的拥塞控制方法；不过 3.7.3 节将会看到，近来 IP 与 TCP 也可以可选地实现网络辅助拥塞控制。

:::

对网络辅助拥塞控制，拥塞信息通常按图 3.48 所示的两种方式之一从网络反馈给发送方。一种是由网络路由器直接向发送方发送反馈，这种通知通常采取**阻流分组**（choke packet）的形式（实质上是在说"我拥塞了！"）。第二种、也是更常见的方式，是路由器在从发送方流向接收方的分组中标记/更新某个字段以指示拥塞；接收方收到被标记的分组后，再把拥塞指示通知发送方。后一种通知方式需要一个完整的往返时间。

## 3.7　TCP 拥塞控制

本节回到对 TCP 的研究。如 3.5 节所学，TCP 在不同主机上运行的两个进程之间提供可靠的运输服务；TCP 的另一个关键组成部分是它的**拥塞控制**机制。如上一节所述，我们称之为"经典"TCP 的版本——即 [RFC 2581; RFC 5681] 标准化的 TCP——使用端到端拥塞控制而非网络辅助拥塞控制，因为 IP 层不向端系统提供关于网络拥塞的显式反馈。3.7.1 节先深入讨论这个"经典"版本；3.7.2 节考察以不同于"经典"TCP 的方式使用端到端拥塞控制的若干较新变体；3.7.3 节研究利用网络层提供的显式拥塞指示的 TCP 版本；3.7.4 节讨论在共享拥塞链路的运输层流之间实现公平性的难题。

### 3.7.1　经典端到端 TCP 拥塞控制

TCP 采取的办法是：让每个发送方根据它所感知的网络拥塞程度，限制自己向连接中注入流量的速率。若 TCP 发送方感知到它与目的地之间的路径上拥塞较轻，就提高发送速率；若感知到路径上有拥塞，就降低发送速率。但这一办法引出三个问题：第一，TCP 发送方如何限制自己向连接中注入流量的速率？第二，TCP 发送方如何感知它与目的地之间的路径上存在拥塞？第三，发送方应当用什么算法，根据感知到的端到端拥塞来改变发送速率？

如今因特网中使用着许多不同的 TCP 拥塞控制"变体"。[Ware 2024] 报告了在排名前 1 万的 Web 站点上所观察到的十余种最广泛使用的 TCP 拥塞控制变体的使用情况。本节将学习其中四种算法——"经典"TCP、TCP Vegas、CUBIC TCP 与 BBR——如何以不同方式回答上述三个问题。

先从"经典"TCP 开始，考察 TCP 发送方如何限制自己向连接中注入流量的速率。3.5 节已经看到，TCP 连接的每一侧都由一个接收缓冲区、一个发送缓冲区和若干变量（LastByteRead、rwnd 等）组成。发送方运行的 TCP 拥塞控制机制还维护一个额外的变量——**拥塞窗口**（congestion window），记为 cwnd，它对 TCP 发送方向网络注入流量的速率构成约束。具体地说，发送方未确认的数据量不得超过 cwnd 与 rwnd 中的较小者，即

$$
\text{LastByteSent} - \text{LastByteAcked} \le \min \{\text{cwnd}, \text{rwnd} \}
$$

为聚焦于拥塞控制（而非流量控制），从现在起假定 TCP 接收缓冲区足够大，以致可以忽略接收窗口的约束；于是发送方未确认的数据量只受 cwnd 限制。我们还假定发送方总有数据要发，即拥塞窗口中的所有报文段都会被发送。

上面的约束限制了发送方未确认的数据量，因而间接限制了发送方的发送速率。为看清这一点，考虑一条丢失与分组传输时延均可忽略的连接：粗略地说，在每个 RTT 开始时，该约束允许发送方向连接中发送 cwnd 字节数据；到该 RTT 结束时，发送方收到这些数据的确认。因此发送方的发送速率约为 cwnd/RTT 字节/秒。**通过调节 cwnd 的值，发送方就能调节自己向连接中注入数据的速率。**

接下来看经典 TCP 发送方如何感知它与目的地之间的路径上存在拥塞。我们把 TCP 发送方的**丢包事件**定义为：发生超时，或收到来自接收方的三个重复 ACK。（回忆 3.5.4 节对图 3.32 中超时事件的讨论，以及随后加入的"收到三个重复 ACK 即快速重传"的修改。）当拥塞过度时，路径上某台（或多台）路由器的缓冲区溢出，导致一个（承载 TCP 报文段的）数据报被丢弃；被丢弃的数据报又导致发送方出现丢包事件——超时或收到三个重复 ACK——发送方据此认为发送方到接收方的路径上发生了拥塞。需要指出，经典 TCP 通过丢包事件推断拥塞，而其他可测量的事件（例如 RTT 的变化）在我们将要研究的其他 TCP 拥塞控制变体中也可作为拥塞指示。

考察了经典 TCP 如何检测拥塞之后，再看一个更乐观的情形：网络无拥塞，即没有丢包事件发生。此时，TCP 发送方会收到此前未确认报文段的确认。正如我们将看到的，经典 TCP 把这些确认的到达视为"一切正常"的迹象——送入网络的报文段正被成功交付到目的地——并利用确认来**增大**其拥塞窗口（从而增大传输速率）。注意，如果确认到达得较慢（例如端到端路径时延大，或包含低带宽链路），拥塞窗口就增长得较慢；反之若确认到达得快，拥塞窗口就增长得快。由于 TCP 用确认来**触发**（或"计时"）拥塞窗口的增大，因此说 TCP 是**自计时**（self-clocking）的。

有了通过调节 cwnd 控制发送速率的机制，关键问题依然是：单个 TCP 发送方应当如何确定自己该以多快速率发送？如果所有 TCP 发送方合起来发得太快，就会把网络搞拥塞，导致我们在图 3.46 中看到的那种拥塞崩溃。事实上，我们即将研究的经典 TCP 拥塞控制算法，正是针对早期 TCP 版本下观察到的因特网拥塞崩溃而提出的 [Jacobson 1988]。然而，如果 TCP 发送方过于谨慎、发得太慢，又会浪费网络带宽——也就是说，TCP 发送方本可以更高的速率发送而不致使网络拥塞。那么，TCP 发送方如何确定发送速率，才能既不使网络拥塞、又用尽全部可用带宽？TCP 发送方之间有显式的协调吗？还是存在一种分布式方法，使各发送方仅依据本地信息就能设定发送速率？经典 TCP 用以下指导原则回答这些问题：

::: tip 要点

1. **报文段丢失意味着拥塞，因此报文段丢失时 TCP 发送方应降低速率。** 回忆 3.5.4 节：超时事件，或收到对某报文段的四个确认（一个原始 ACK 加三个重复 ACK），被解释为对该报文段**之后**那个报文段的隐式"丢包事件"指示，从而触发对丢失报文段的重传。从拥塞控制的角度看，问题是：面对这一推断出的丢包事件，TCP 发送方应当如何减小其拥塞窗口，从而减小发送速率。
1. **被确认的报文段表明网络正在把发送方的报文段交付给接收方，因此当此前未确认的报文段的 ACK 到达时，发送方可以提高速率。** 确认的到达被视为"一切正常"的隐式指示——报文段正被成功地从发送方交付到接收方，网络因而没有拥塞，于是拥塞窗口可以增大。
1. **带宽探测。** 既然 ACK 表明源到目的路径无拥塞、丢包事件表明路径拥塞，TCP 调节传输速率的策略就是：随着 ACK 到达而提高速率，直到出现丢包事件为止，此时再降低速率。于是 TCP 发送方提高速率以探测"拥塞开始出现"的那个速率，从该速率后退，然后再开始探测，看看拥塞开始出现的速率是否已经变化。TCP 发送方的行为也许类似于这样一个孩子：他不断索要（并且得到）越来越多的好东西，直到终于被说"不行！"，于是退让一点，但很快又开始索要。注意，网络并不显式信令拥塞状态——ACK 与丢包事件充当隐式信号——而且每个 TCP 发送方只依据本地信息、与其他 TCP 发送方异步地行动。

:::

有了对 TCP 拥塞控制的这一概览，就可以深入考察这个著名的 TCP 拥塞控制算法的细节了。我们称之为"经典"TCP，它最早在 [Jacobson 1988] 中描述，并在 [RFC 5681] 中标准化。该算法有三个主要部分：(1) 慢启动；(2) 拥塞避免；(3) 快速恢复。慢启动与拥塞避免是 TCP 的必备部分，二者的区别在于如何根据收到的 ACK 增大 cwnd。稍后会看到，慢启动增大 cwnd 的速度比拥塞避免**更快**（尽管名字叫"慢"！）。快速恢复则是推荐而非必需的。

#### 慢启动

一条 TCP 连接开始时，cwnd 的值通常初始化为 1 个 MSS 这样的小值 [RFC 3390]，于是初始发送速率约为 MSS/RTT。例如，若 MSS = 500 字节、RTT = 200 毫秒，则初始发送速率只有约 20 kbps。由于 TCP 发送方可用的带宽可能远大于 MSS/RTT，它希望尽快找到可用带宽的量。因此在慢启动状态下，cwnd 从 1 个 MSS 开始，每当一个已发送的报文段首次被确认，就增加 1 个 MSS。

在图 3.49 的例子中，TCP 向网络发送第一个报文段并等待确认；该确认到达后，发送方把拥塞窗口增大 1 个 MSS，并发出两个最大长度的报文段；这两个报文段随后被确认，发送方又为每个被确认的报文段把拥塞窗口增大 1 个 MSS，使拥塞窗口达到 4 个 MSS；如此继续。这个过程使发送速率**每个 RTT 翻一番**。因此，TCP 的发送速率起步很慢，但在慢启动阶段以指数速度快速增长。

<Figure src="ch03/fig3-49.webp" caption="图 3.49　TCP 慢启动" />

但这种指数增长何时结束？慢启动对这个问题给出了几种答案。第一，如果出现由超时指示的丢包事件（即拥塞），TCP 发送方把 cwnd 置为 1，并重新开始慢启动过程；同时把第二个状态变量 ssthresh（"slow-start threshold"的简写，即慢启动阈值）置为 cwnd/2，也就是检测到拥塞时拥塞窗口值的一半。慢启动可能结束的第二种方式，直接与 ssthresh 的值相关：既然 ssthresh 是上次检测到拥塞时 cwnd 值的一半，那么当 cwnd 达到或超过 ssthresh 时还继续翻倍，或许就有点鲁莽了。因此，当 cwnd 等于 ssthresh 时，慢启动结束，TCP 转入**拥塞避免**模式；在拥塞避免模式下，TCP 会更谨慎地增大 cwnd。慢启动算法源自 [Jacobson 1988]；类似的方法也在 [Jain 1986] 中被独立提出。

#### 拥塞避免

进入拥塞避免状态时，cwnd 的值约为上次遇到拥塞时其值的一半——拥塞可能就在眼前！因此，TCP 不再每个 RTT 就把 cwnd 翻倍，而是采取更保守的做法：每个 RTT 只把 cwnd 增大 1 个 MSS [RFC 5681]。这可以通过几种方式实现，一种常见做法是：每当一个新 ACK 到达，TCP 发送方就把 cwnd 增大 MSS/cwnd 字节。例如，若 MSS 为 1460 字节、cwnd 为 14 600 字节，则一个 RTT 内会发送 10 个报文段；每个到达的 ACK（假定每段一个 ACK）使拥塞窗口增大 $\frac{1}{10}$ 个 MSS，于是当 10 个 ACK 全部收到时，拥塞窗口的值恰好增大了 1 个 MSS。

那么，在拥塞避免期间推断出丢包事件（由超时或收到三个重复 ACK）时会发生什么？若拥塞避免期间发生**超时**，TCP 的拥塞避免算法与慢启动情形相同：cwnd 置为 1 个 MSS，ssthresh 更新为丢包事件发生时 cwnd 值的一半。

若丢包是由**三个重复 ACK** 事件推断出来的，我们就知道网络仍在把一些报文段从发送方交付给接收方（重复 ACK 的到达表明了这一点）。因此，经典 TCP 对这类丢包事件的处理不像对超时指示的丢包那样剧烈：TCP 把 cwnd 减半（并为了"保险"再加上 3 个 MSS，以计入收到的三个重复 ACK），并把 ssthresh 置为收到三个重复 ACK 时 cwnd 值的一半。

若 TCP（可选地）实现**快速恢复**，它会以与拥塞避免略有不同的方式操纵 cwnd 的值，具体是：每收到一个针对缺失报文段的重复 ACK，就把 cwnd 增大 1 个 MSS。一旦有确认新数据的 ACK 到达，或发生超时，TCP 就分别返回慢启动阶段或拥塞避免阶段。本书较早的版本更详细地讨论了快速恢复，并给出了经典 TCP 的详细 FSM 描述；这些存档资料可参见出版社网站或作者网站（https://gaia.cs.umass.edu/kurose_ross）。

最早的 TCP 版本之一称为 **TCP Tahoe**，它在超时指示或三重复 ACK 指示的丢包事件之后，总是把拥塞窗口砍到 1 个 MSS 并进入慢启动阶段。下一代 TCP 拥塞控制 **TCP Reno** 引入的改动是：对三重复 ACK 指示的拥塞反应不那么剧烈，即把 cwnd 减半（再加 3）。

图 3.50 展示了 Reno 与 Tahoe 的拥塞窗口演化。图中阈值最初等于 8 个 MSS。在前八个传输轮次中，Tahoe 与 Reno 动作完全相同：拥塞窗口在慢启动期间指数式快速攀升，在第 4 个传输轮次达到阈值；随后拥塞窗口线性攀升，直到第 8 个传输轮次之后不久发生三重复 ACK 事件。注意该丢包事件发生时拥塞窗口为 12 个 MSS，ssthresh 随后被置为 $0.5 \times \text{cwnd} = 6$ 个 MSS。在 TCP Reno 下，拥塞窗口被置为 cwnd = 9 个 MSS，然后线性增长；在 TCP Tahoe 下，拥塞窗口被置为 1 个 MSS，指数增长直到达到 ssthresh 的值，此后线性增长。

#### TCP 拥塞控制：回顾

深入了解了慢启动、拥塞避免与快速恢复的细节之后，值得退一步看看全局。

<Figure src="ch03/fig3-51.webp" caption="图 3.51　加性增、乘性减（AIMD）拥塞控制" />

忽略连接开始时的初始慢启动阶段，并假定丢包由三重复 ACK 而非超时指示，则 TCP 的拥塞控制就是：每个 RTT 把 cwnd 线性（加性）增大 1 个 MSS，然后在三重复 ACK 事件时把 cwnd 减半（乘性减小）。因此，TCP 拥塞控制常被称为**加性增、乘性减**（additive-increase, multiplicative-decrease, AIMD）形式的拥塞控制。AIMD 拥塞控制产生了图 3.51 所示的"锯齿"行为，这也恰好印证了我们前面关于 TCP"探测"带宽的直觉——TCP 线性增大其拥塞窗口（从而增大传输速率），直到出现三重复 ACK 事件；随后把拥塞窗口减半，然后又线性增大，探测是否还有额外可用带宽。

TCP 的 AIMD 算法是基于对实际运行网络中拥塞控制的大量工程洞察与实验而发展出来的。相当惊人的是，在 TCP 被开发并部署十年之后，理论分析表明 TCP 的拥塞控制算法相当于一种**分布式异步优化算法**，它使若干重要的用户性能与网络性能同时得到优化 [Kelly 1998]！此后，一门丰富的拥塞控制理论发展了起来 [Srikant 2012]。

#### TCP Reno 吞吐量的宏观描述

鉴于 TCP Reno 的锯齿行为，自然要问：一条长期存活的 TCP Reno 连接的平均吞吐量（即平均速率）是多少？在这项分析中，我们忽略超时事件之后出现的慢启动阶段（这些阶段通常极短，因为发送方以指数速度快速越过该阶段）。在某个往返间隔内，TCP 发送数据的速率是拥塞窗口与当前 RTT 的函数：当窗口大小为 $w$ 字节、当前往返时间为 RTT 秒时，TCP 的传输速率约为 $\frac{w}{\text{RTT}}$。随后 TCP 通过每个 RTT 把 $w$ 增大 1 个 MSS 来探测额外带宽，直到发生丢包事件；记丢包事件发生时 $w$ 的值为 $W$。假定 RTT 与 $W$ 在连接持续期内近似不变，则 TCP 的传输速率在 $\frac{W}{2 \text{RTT}}$ 到 $\frac{W}{\text{RTT}}$ 之间变化。

这些假设导出一个高度简化的 TCP 稳态行为宏观模型：当速率增至 $\frac{W}{\text{RTT}}$ 时网络从该连接丢弃一个分组，速率随即减半，然后每过一个 RTT 增大 MSS/RTT，直到再次达到 $\frac{W}{\text{RTT}}$，如此周而复始。由于 TCP 的吞吐量（即速率）在这两个极值之间线性增长，有

$$
\text{连接的平均吞吐量} = 0.75 \cdot \frac{W}{\text{RTT}} \tag{3.4}
$$

用这个高度理想化的 TCP 稳态动力学模型，还可以推导出一个把连接的丢失率与其可用带宽联系起来的有趣表达式 [Mathis 1997]，其推导见章末习题。一个更精细、且经实证与测量数据相符的模型见 [Padhye 2000]。

### 3.7.2　近期的端到端 TCP 拥塞控制算法

过去 25 年间，许多新的端到端 TCP 拥塞控制算法被开发并部署。事实上，近期针对排名前 1 万的最热门网站 [Durumeric 2025] 所用拥塞控制算法的测量 [Ware 2024] 表明，上一节所研究的"经典"TCP 拥塞控制算法已在很大程度上被本节将要研究的新变体（特别是 BBR，以及此前的 TCP CUBIC）所取代。正如我们将看到的，其中一些新方法对经典 TCP"以丢包为拥塞指示"的做法只作了相对较小的改动，另一些则采取了根本不同的思路。

#### TCP CUBIC：对加性增的改进

面对 TCP Reno 加性增、乘性减的拥塞控制方法，人们自然会问：这是否是"探测略低于触发丢包阈值的发送速率"的最佳方式？把发送速率减半（甚至更糟，像 TCP Tahoe 那样减到每 RTT 一个分组），然后随时间缓慢增大，可能过于保守。如果发生丢包的拥塞链路状态没有多大变化，那么也许更好的做法是快速把发送速率提升到接近丢包前的速率，然后再谨慎地探测带宽。这一洞见正是 **TCP CUBIC** [Ha 2008; RFC 8312] 及其前身 BIC [Xu 2004] 的核心。

TCP CUBIC 与 TCP Reno 只有细微差别：拥塞窗口同样只在收到 ACK 时增大；CUBIC 只改动拥塞避免阶段，做法如下：

- 设 $W_{\text{max}}$ 为最近一次检测到丢包时 TCP 拥塞窗口的大小，$K$ 为 TCP CUBIC 的窗口大小（假定不再丢包）将再次达到 $W_{\text{max}}$ 的未来时刻。若干可调的 CUBIC 参数决定 $K$ 的值，即协议拥塞窗口将以多快的速度达到 $W_{\text{max}}$。
- CUBIC TCP 把拥塞窗口作为当前时间 $t$ 与 $K$ 之间距离的**立方**函数来增大。因此，当 $t$ 距 $K$ 较远时，拥塞窗口的增量远大于 $t$ 接近 $K$ 时的增量。也就是说，CUBIC 快速把 TCP 发送速率提升到接近丢包前的速率 $W_{\text{max}}$，只在接近 $W_{\text{max}}$ 时才谨慎地探测带宽。
- 当 $t$ 大于 $K$ 时，立方规则意味着：$t$ 仍接近 $K$ 时 CUBIC 的拥塞窗口增量很小（如果导致丢包的链路拥塞程度变化不大，这是好事），而随着 $t$ 超过 $K$，增量迅速变大（如果导致丢包的链路拥塞程度已明显变化，这使 CUBIC 能更快找到新的工作点）。

在这些规则下，图 3.52（改编自 [Huston 2017]）比较了 TCP Reno 与 TCP CUBIC 的理想化性能。可以看到慢启动阶段在 $t_{0}$ 结束；随后在 $t_{1}$、$t_{2}$、$t_{3}$ 处发生拥塞丢包时，CUBIC 更快地爬升到接近 $W_{\text{max}}$（从而获得比 TCP Reno 更高的总吞吐量）。从图中可以直观看到，TCP CUBIC 如何力图让流量尽可能长时间地保持在（发送方并不知晓的）拥塞阈值之下。注意在 $t_{3}$ 处，拥塞程度想必已明显下降，使 TCP Reno 与 TCP CUBIC 都能达到高于 $W_{\text{max}}$ 的发送速率。

<Figure src="ch03/fig3-52.webp" caption="图 3.52　TCP 拥塞避免的发送速率：TCP Reno 与 TCP CUBIC" />

TCP CUBIC 最初获得了广泛部署。2000 年前后对热门 Web 服务器的测量显示几乎全部运行经典 TCP [Padhye 2001]；而到 2014 年，对 5000 台最热门 Web 服务器的测量显示近 50% 运行某个版本的 TCP CUBIC [Yang 2014]。CUBIC 也曾是 Linux 操作系统中默认的 TCP 版本。然而到 2024 年，BBR 的使用量已显著超过 CUBIC，也超过了所有其他 TCP 拥塞控制变体的总和 [Ware 2024]！

#### TCP Vegas：基于时延的拥塞控制

经典 TCP、CUBIC 以及许多其他 TCP 变体，都基于"把由超时事件或三重复 ACK 事件推断出的报文段丢失作为拥塞指示"。**TCP Vegas** [Brakmo 1995] 是一种端到端拥塞控制方法，它利用测得的 RTT 时延来**主动**检测拥塞的开始，希望能在分组丢失发生之前就发现它。

在 TCP Vegas 中，发送方测量所有被确认分组的源到目的路径 RTT。设 $\text{RTT}_{\text{min}}$ 为发送方所测这些值中的最小值，它出现在路径无拥塞、分组经历的排队时延最小时。若 TCP Vegas 的拥塞窗口为 cwnd，则无拥塞时的吞吐速率应为 $\frac{\text{cwnd}}{\text{RTT}_{\text{min}}}$。TCP Vegas 背后的直觉是：如果发送方实测的吞吐量接近该值，那么 TCP 发送速率可以提高，因为（按定义、也按测量）路径尚未拥塞；反之，如果实测吞吐量明显低于无拥塞吞吐速率，则路径已拥塞，Vegas 的 TCP 发送方将降低发送速率。细节见 [Brakmo 1995]。

TCP Vegas 是最早利用实测 RTT 的因特网拥塞协议之一，此后许多协议也采用了基于时延的方法。对这些协议的综述、以及把时延作为拥塞信号的更广泛讨论，见 [Al-Saadi 2019]。

#### BBR：瓶颈带宽与往返传播时间

TCP Vegas 基于这样一种直觉运作：TCP 发送方应当"让管道恰好装满，但不要更满" [Kleinrock 2018]。"让管道装满"意味着，限制吞吐量的瓶颈链路应保持忙于传输、做有用功；"但不要更满"意味着，如果在管道装满的同时还让大量队列堆积起来，那什么也得不到（只会增大时延！）。**BBR**（Bottleneck Bandwidth and RTT，瓶颈带宽与往返时间）拥塞控制协议 [Cardwell 2017] 最初由 Google 开发，现已到第三版 [Cardwell 2024]，同样基于这一洞见。截至 2024 年，BBR 已成为部署最广泛的 TCP 拥塞控制变体 [Ware 2024]。

为理解 BBR，回忆 3.6.1 节与图 3.48 关于瓶颈链路的讨论，再次考虑 $N$ 条连接通过一条瓶颈链路的情形。现在考虑：当这些连接各自允许越来越多的未确认分组在发送方与接收方之间"在途"时，会发生什么。在途分组数 $n_{\text{inflight}}$ 与图 3.42、3.44、3.46 横轴上的 $\lambda '_{\text{in}}$ 值有微妙差别：

- 第一，$\lambda '_{\text{in}}$ 严格来说是一种**传输速率**的度量，而在途分组数是对在途分组**个数**的计数。注意 $n_{\text{inflight}}$ 还隐含地是分组在途时间（即 RTT）的函数。直观地说，如果目标是"让管道恰好装满"，就必须考虑一个事实：RTT 较长的管道能容纳的分组比 RTT 较短的管道更多。
- 第二，如果目标是"让管道恰好装满，但不要更满"，我们就希望让链路队列保持相对较短。需要缓冲来吸收瞬时到达速率的统计波动，但应避免持续存在的队列。
- 第三，应考虑链路传输容量对管道能容纳的在途分组数的影响。直观上，路径的链路容量越大，能容纳的在途分组就越多。事实上，"长而粗的管道"——具有大带宽链路和大 RTT，等价地说具有大**带宽时延积**的连接——的拥塞控制已被研究了几十年 [RFC 1072]。如下文所述，可以把带宽时延积看作连接（例如图 3.47 中的 $N$ 条连接）在不丢包情况下所能支撑的平均在途数据量的近似。

图 3.53 阐释了 BBR 背后的直觉。考虑当发送方增大 $n_{\text{inflight}}$ 时会发生什么。起初，连接的吞吐量也随之增大，而 RTT 保持不变——可以认为在途数据均匀分布在整个管道中，链路没有队列，RTT 只由传播时延构成。

当在途数据量达到连接的**带宽时延积**时，管道就"刚好装满"。继续增大在途流量，就会在瓶颈链路处形成在途数据的队列（其余部分在概念上仍均匀分布于整个管道中）。如图 3.53 下部所示，把 $n_{\text{inflight}}$ 增大到超过带宽时延积并不会提高吞吐量，因为（在这个近似模型中）瓶颈链路处已存在持续的队列，该链路因而始终繁忙。把 $n_{\text{inflight}}$ 增大到超过带宽时延积还会增大 RTT，原因是瓶颈链路处的排队时延增加了。

<Figure src="ch03/fig3-53.webp" caption="图 3.53　RTT 与吞吐量随在途数据量的变化" />

基于这些考虑，$n_{\text{inflight}}$ 等于带宽时延积的那个点可视为"理想"工作点——管道恰好装满，但不过满。以上洞见只基于平均速率，而实践中瓶颈队列处的流量到达速率会有统计波动。对瓶颈链路模型中时延与吞吐量的更正式的排队论处理（其结论与我们上面的平均情形分析基本一致），见 [Kleinrock 2018]。

BBR 的运行方式是：直接测量 RTT，估计带宽时延积，并据此设定 $n_{\text{inflight}}$ 的值。BBR 在两个时间尺度上运行。在较长的时间间隔上，BBR 减小 $n_{\text{inflight}}$ 以排空管道，看看是否存在更低的 RTT。在较短的时间间隔上，BBR 循环经历三个阶段：

- **加速**（Acceleration）：BBR 提高发送速率，增大 $n_{\text{inflight}}$，直到吞吐量达到平台（如图 3.53 所示），从而使可用的单流链路容量饱和。
- **巡航**（Cruising）：BBR 以网络正在交付数据的速率发送，这一点由收到的 ACK 反映出来。
- **减速**（Deceleration）：BBR 以低于网络交付数据的速率发送，减小 $n_{\text{inflight}}$、降低队列压力，并寻找更低的 RTT。

BBR 还有一个发送**节拍**（pacing）机制，确保不会背靠背地发出一大串报文段。BBRv3 运行的细节见 [Cardwell 2024]。早期版本 BBR 的一个隐忧是它与瓶颈链路上采用传统基于丢包方法的竞争 TCP 流（例如 TCP CUBIC 或 Reno）之间的**公平性**（见 7.3.4 节）[Ware 2019]，而 BBRv3 明确解决了这一隐忧。

### 3.7.3　网络辅助的显式拥塞通知

上一节讨论了"经典"TCP、CUBIC TCP、TCP Vegas 与 BBR 等若干端到端拥塞控制方法。这些方法之所以属于端到端方法，是因为它们利用 TCP 发送方对分组丢失、RTT 和实测吞吐量的观察来实施拥塞控制。

IP 与 TCP 的扩展 [RFC 3168] 已被提出、实现并部署，统称为**显式拥塞通知**（Explicit Congestion Notification, ECN），它允许网络向 TCP 发送方与接收方显式地指示拥塞。如图 3.54 所示，TCP 与 IP 都参与 ECN。

在网络层，IP 数据报首部服务类型字段（将在 4.3 节讨论）中的两个比特（共四种取值）用于 ECN。这两个比特有两种可能的设置：一种设置由路由器用来指示它（路由器）正经历拥塞，这个拥塞指示随被标记的 IP 数据报传到目的主机，再由目的主机告知发送主机，如图 3.54 所示。RFC 3168 并未定义路由器何时算拥塞，这一判断是由路由器厂商提供的配置选项、由网络运营者决定的。但其直觉是：可以在丢包真正发生之前就置位拥塞指示比特，向发送方发出拥塞开始的信号。ECN 比特的第二种设置由发送主机用来告知路由器：发送方与接收方都支持 ECN，因而能够对 ECN 指示的网络拥塞采取行动。

<Figure src="ch03/fig3-54.webp" caption="图 3.54　显式拥塞通知：网络辅助的拥塞控制" />

如图 3.54 所示，当接收主机中的 TCP 通过收到的数据报得到 ECN 拥塞指示时，接收主机的 TCP 通过在接收方到发送方的 TCP ACK 报文段中置位 ECE（Explicit Congestion Notification Echo，显式拥塞通知回显）比特（见图 3.28），把该拥塞指示告知发送主机。发送方 TCP 则对带有拥塞指示的 ACK 作出反应——像对待快速重传中的丢失报文段那样，把拥塞窗口减半——并在下一个发送方到接收方的 TCP 报文段首部中置位 CWR（Congestion Window Reduced，拥塞窗口已减小）比特。

除 TCP 之外，其他运输层协议也可以利用网络层信令的 ECN。数据报拥塞控制协议（DCCP）[RFC 4340] 提供一种低开销、带拥塞控制的类 UDP 不可靠服务，它就利用了 ECN。专为数据中心网络设计的 DCTCP（Data Center TCP）[Alizadeh 2010; RFC 8257] 与 DCQCN（Data Center Quantized Congestion Notification）[Zhu 2015] 也利用了 ECN。近期的因特网测量表明，超过 80% 的热门 Web 服务器、以及从这些服务器到其客户端的路径都支持 ECN 能力 [Lim 2022]。

### 3.7.4　公平性

考虑 $K$ 条 TCP 连接，各有不同的端到端路径，都采取基于丢包的 AIMD 拥塞控制，并且都通过一条传输速率为 $R$ bps 的瓶颈链路。（所谓瓶颈链路，是指对每条连接而言，其路径上其余链路都不拥塞，且传输能力相对瓶颈链路十分充裕。）假设每条连接都在传送一个大文件，且没有 UDP 流量经过该瓶颈链路。若每条连接的平均传输速率都约为 $\frac{R}{K}$，即每条连接获得链路容量的均等份额，则称该拥塞控制机制是**公平的**。

TCP 的 AIMD 算法公平吗？尤其是考虑到不同的 TCP 连接可能在不同时刻开始，因而在某一时刻窗口大小可能不同。[Chiu 1989] 对"TCP 拥塞控制为何会收敛到在竞争的各 TCP 连接之间均分瓶颈链路容量"给出了一个优雅而直观的解释。

考虑两条 TCP 连接共享一条传输速率为 $R$ 的单链路这一简单情形，如图 3.55 所示。假定两条连接具有相同的 MSS 和 RTT（因而若拥塞窗口相同，则吞吐量相同），都有大量数据要发送，且没有其他 TCP 连接或 UDP 数据报经过该共享链路；同时忽略 TCP 的慢启动阶段，假定这两条连接始终工作在拥塞避免（AIMD）模式。

<Figure src="ch03/fig3-55.webp" caption="图 3.55　两条 TCP 连接共享一条瓶颈链路" />

图 3.56 绘出了这两条 TCP 连接所实现的吞吐量。若 TCP 要在两条连接之间均分链路容量，则实现的吞吐量应落在从原点出发的 45 度箭头（链路容量的均等份额）上；理想情况下，两者吞吐量之和应等于 $R$。（当然，每条连接都得到均等但为零的份额，绝不是我们所希望的局面！）因此目标应是让实际达到的吞吐量落在图 3.56 中"均等容量份额线"与"满利用率线"交点附近。

<Figure src="ch03/fig3-56.webp" caption="图 3.56　TCP 连接 1 与连接 2 实现的吞吐量" />

假设在某时刻，两条连接的窗口大小使其吞吐量处于图 3.56 中的 A 点。由于两条连接共同消耗的链路容量小于 $R$，不会发生丢包，于是两条连接都因 TCP 的拥塞避免算法而每个 RTT 把窗口增大 1 个 MSS。因此，两条连接的总吞吐量从 A 点出发沿 45 度线（两者等量增加）前进。最终，两者共同消耗的链路容量将超过 $R$，于是迟早发生分组丢失。假设连接 1 和 2 在吞吐量处于 B 点时经历丢包，两条连接随即把窗口减半，于是实现的吞吐量落到 C 点——即从 B 点指向原点的那条向量的中点。由于 C 点处共同使用的容量小于 $R$，两条连接又从 C 点出发沿 45 度线提高吞吐量；最终再次发生丢包，比如在 D 点，两条连接又减半……你应当说服自己：两条连接所实现的容量最终会沿着均等容量份额线波动；也应当说服自己：无论它们处于二维空间的哪个位置，都会收敛到这种行为！尽管这一场景背后有若干理想化假设，它仍然直观地说明了 TCP 为何会导致连接之间均分容量。

在这个理想化场景中，我们假定只有 TCP 连接经过瓶颈链路、各连接 RTT 相同、且每个"主机-目的地"对只关联一条 TCP 连接。实践中这些条件通常并不成立，客户-服务器应用因而可能获得极不均等的链路容量份额。特别地，已有研究表明：当多条连接共享同一瓶颈时，RTT 较小的会话能在链路容量空出时更快地抢占（即更快地打开其拥塞窗口），从而获得比 RTT 较大的连接更高的吞吐量 [Lakshman 1997]。

#### 公平性与 UDP

我们刚刚看到 TCP 拥塞控制如何通过拥塞窗口机制调节应用的传输速率。许多多媒体应用（如因特网电话与视频会议）正因如此往往不运行在 TCP 之上——它们不希望自己的传输速率被抑制，即使网络非常拥塞。相反，这些应用更愿意运行在 UDP 之上，因为 UDP 没有内置拥塞控制。运行在 UDP 之上时，应用可以恒定速率把音频和视频注入网络，偶尔丢失一些分组，而不愿在拥塞时把速率降到"公平"水平以求不丢包。从 TCP 的角度看，运行在 UDP 之上的多媒体应用是不公平的——它们不与其他连接合作，也不适当地调整传输速率。由于 TCP 拥塞控制在拥塞（丢包）加剧时会降低传输速率，而 UDP 源不必如此，UDP 源就有可能把 TCP 流量挤出。为此，人们为因特网提出了若干拥塞控制机制，以防 UDP 流量把因特网的吞吐量拖到近乎停滞 [Floyd 1999; Floyd 2000; Kohler 2006; RFC 4340]。

#### 公平性与并行 TCP 连接

然而，即便我们能迫使 UDP 流量公平行事，公平性问题仍未彻底解决。这是因为没有什么能阻止一个基于 TCP 的应用使用多条并行连接。例如，Web 浏览器常常使用多条并行 TCP 连接来传输一个网页中的多个对象（并行连接的具体数目在多数浏览器中可配置）。当一个应用使用多条并行连接时，它就在拥塞链路中获得了更大份额的带宽。举例来说，考虑一条速率为 $R$ 的链路支撑着九个正在运行的客户-服务器应用，每个应用使用一条 TCP 连接。若新来一个应用也使用一条 TCP 连接，则每个应用获得大致相同的传输速率 $\frac{R}{10}$；但若这个新应用改用 11 条并行 TCP 连接，它就会获得超过 $\frac{R}{2}$ 的不公平份额。由于 Web 流量在因特网中如此普遍，并行连接并不罕见。

TCP 拥塞控制的讨论到此结束。恐怕没有别的因特网协议在研究文献和部署中受到过如此多的关注。想进一步学习 TCP 拥塞控制，[Peterson 2025] 是极好的资料。

## 3.8　运输层功能的演进

本章对具体因特网运输协议的讨论集中在 UDP 与 TCP——因特网运输层的两匹"老黄牛"。然而正如我们所见，四十年来使用这两个协议的经验已经识别出它们各自并不理想适用的情形，因此自这两个协议最初标准化以来，运输层功能的设计与实现一直在演进。3.5 与 3.7.2 节已经考察了 TCP 演进中的若干进展。

**数据报拥塞控制协议**（DCCP）[RFC 4340] 提供一种低开销、面向报文的、类 UDP 的不可靠服务，但带有一种由应用选择、且与 TCP 兼容的拥塞控制形式。DCCP 可选拥塞控制形式之一是**TCP 友好速率控制**（TCP-Friendly Rate Control, TFRC）协议 [RFC 5348]，它把 TCP 拥塞控制中的"锯齿"行为（见图 3.50）平滑掉，同时保持长期发送速率"相当"接近 TCP。由于发送速率比 TCP 更平滑，TFRC 很适合 IP 电话、流式媒体等多媒体应用。TFRC 是一种"基于方程"的协议：它把测得的丢包率作为某个方程的输入 [Padhye 2000]，该方程估计若一个 TCP 会话经历该丢包率时的吞吐量，再把该速率作为 TFRC 的目标发送速率。DCCP 设想用于流式媒体这类应用——它们能够利用数据交付的及时性与可靠性之间的折衷，但又希望对网络拥塞作出响应。若使用 DCCP 的应用需要可靠或半可靠的数据传输，那么这将在应用自身内部完成，很可能采用我们在 3.4 节研究过的机制。

除这些变化之外，过去十年运输层还经历了一场更为剧烈的变革——TCP 的可靠数据传输、流量控制、拥塞控制及其他服务，以**应用层模块**的形式迁移到了应用层，在 UDP 之上提供类 TCP 的服务。最能体现这一趋势的著名协议是 **QUIC**（Quick UDP Internet Connections）[RFC 9000; RFC 9002]，我们在 2.2 节讨论 HTTP/3 时已接触过它，下面将进一步考察。

今天，应用设计者仍可在操作系统实现的本地 TCP 与 UDP 服务之间选择；但现在有了第三种选择——应用设计者可以在应用层、基于 UDP 用 QUIC"自建"运输层服务。QUIC 早期版本的作者 [Langley 2017] 指出，在应用层实现运输层功能意味着可以按"应用更新的时间尺度"修改 QUIC，即特性迭代速度远快于 TCP 或 UDP 的更新速度。或者，正如 RFC 1263 颇为幽默地所言："能够在比标准委员会就'合适的开会时间'达成一致更短的时间内，设计并分发协议。"

下面仔细看看 QUIC。它也将作为我们运输层学习的一个漂亮收束，因为 QUIC 用到了本章研究过的可靠数据传输、拥塞控制和连接管理中的许多方法。在往下读之前，不妨回顾 2.2.7 节与图 2.11 中关于 QUIC 的讨论。QUIC 的一些主要特性包括：

::: tip 要点

1. **面向连接且安全。** 与 TCP 一样，QUIC 是两个端点之间面向连接的协议，这需要端点之间握手以建立 QUIC 连接状态，其中两项状态就是源连接 ID 与目的连接 ID。所有 QUIC 分组都加密；如图 3.57 所示，QUIC 把建立连接状态所需的握手与身份认证、加密所需的握手（传输层安全 TLS 的话题，将在第 8 章研究）合并在一起，从而比"先用多个 RTT 建立 TCP 连接、再在该 TCP 连接上建立 TLS 连接"的情形快得多地完成连接建立。
1. **流（stream）。** QUIC 允许若干不同的应用层"流"复用到一条 QUIC 连接上。流是两个 QUIC 端点之间可靠、按序、双向交付数据的抽象。每条连接有一个连接 ID，连接中的每个流有一个流 ID，这两个 ID 都包含在 QUIC 分组首部中（连同其他首部信息）。来自多个流的数据可以装在单个 QUIC 报文段中，由 UDP 承载。流控制传输协议（SCTP）[RFC 4960; RFC 3286] 是更早的一种可靠的、面向报文的协议，它开创了"若干应用层流复用到一条 SCTP 连接"的概念。
1. **可靠的、TCP 友好的、带拥塞控制的数据传输。** 如图 3.57 所示，QUIC 为每个 QUIC 流分别提供可靠数据传输。图 3.57(a) 展示 HTTP/1.1 在单条 TCP 连接上发送多个 HTTP 请求的情形：由于 TCP 提供可靠、按序的字节交付，这意味着多个 HTTP 请求必须在目的 HTTP 服务器处按序交付。因此，若某个 HTTP 请求的字节丢失，其余 HTTP 请求就无法交付，直到丢失的字节被重传并被 HTTP 服务器端的 TCP 正确收到——这就是我们在 2.2.5 节遇到的所谓**队头阻塞**（HOL blocking）问题。由于 QUIC 在每条流的基础上提供可靠按序交付，一个丢失的 UDP 报文段只影响其数据被装在该报文段中的那些流，其他流中的 HTTP 消息仍可继续被接收并交付给应用。QUIC 使用与 TCP 类似的确认机制提供可靠数据传输，见 [RFC 5681]。
1. **QUIC 的拥塞控制基于 TCP NewReno** [RFC 6582]，后者是对我们在 3.7.2 节研究过的 TCP Reno 协议的轻微修改。QUIC 关于丢包检测与拥塞控制的规范 [RFC 9002] 指出："熟悉 TCP 丢包检测与拥塞控制的读者，会发现这里的算法与众所周知的 TCP 算法并行不悖。"既然我们已在 3.7 节仔细研究过 TCP 的拥塞控制，读 QUIC 拥塞控制算法的规范细节时自会感到轻车熟路！

## 3.9　小结

本章从研究运输层协议能为网络应用提供哪些服务开始。一个极端是，运输层协议可以非常简单，只向应用提供"极简"服务，仅为通信进程提供多路复用/多路分解功能——因特网的 UDP 协议就是这类极简运输层协议的例子。另一个极端是，运输层协议可以向应用提供各种保证，例如可靠的数据交付、时延保证和带宽保证。不过，运输协议能提供哪些服务，往往受制于底层网络层协议的服务模型：如果网络层协议无法为运输层报文段提供时延或带宽保证，那么运输层协议也无法为进程之间发送的报文提供时延或带宽保证。

3.4 节我们看到，即使底层网络层不可靠，运输层协议仍能提供可靠数据传输。我们看到，提供可靠数据传输有许多微妙之处，但通过精心组合确认、定时器、重传和序号，这项任务是可以完成的。

尽管本章讨论了可靠数据传输，但应当记住：可靠数据传输可以由链路层、网络层、运输层或应用层协议来提供。协议栈上面四层中的任何一层，都可以实现确认、定时器、重传和序号，并向其上层提供可靠数据传输。事实上，多年来工程师和计算机科学家各自独立地设计并实现了提供可靠数据传输的链路层、网络层、运输层和应用层协议（尽管其中许多协议已悄然消失）。

3.5 节仔细考察了 TCP——因特网面向连接的可靠运输层协议。我们看到 TCP 很复杂，涉及连接管理、流量控制、往返时间估计以及可靠数据传输。事实上，TCP 比我们描述的还要复杂——我们有意没有讨论各种 TCP 补丁、修正和改进，它们在各种 TCP 版本中被广泛实现。然而，所有这些复杂性对网络应用都是隐藏的：若一台主机上的客户想可靠地向另一台主机上的服务器发送数据，它只需向服务器打开一个 TCP 套接字并把数据灌进去，客户-服务器应用对 TCP 的复杂性一无所知，乐得清闲。

3.6 节从广阔视角考察了拥塞控制，3.7 节展示了 TCP 如何实现拥塞控制。我们看到，拥塞控制对网络的健康运行至关重要：没有拥塞控制，网络很容易陷入僵局，端到端几乎传不了什么数据。3.7 节我们还看到，经典 TCP 实现了一种端到端拥塞控制机制——当判定 TCP 连接的路径无拥塞时，它加性地提高传输速率；当发生丢包时，它乘性地降低传输速率。这一机制还力求让经过拥塞链路的每条 TCP 连接获得链路带宽的均等份额。我们还研究了 TCP 拥塞控制的若干较新变体，它们试图比经典 TCP 更快地确定发送速率，或采用基于时延的方法、或利用来自网络的显式拥塞通知（而非基于丢包的方法）来确定发送速率。我们还较深入地考察了 TCP 连接建立与慢启动对时延的影响，观察到在许多重要场景中，连接建立与慢启动对端到端时延有显著贡献。我们要再次强调：尽管 TCP 拥塞控制多年来不断演进，它仍是一个研究热点，并很可能在未来若干年继续演进。作为本章的收尾，3.8 节研究了近年来的进展——用 QUIC 协议在应用层实现运输层的许多功能（可靠数据传输、拥塞控制、连接建立等）。

第 1 章我们说过，计算机网络可以划分为"网络边缘"与"网络核心"。网络边缘涵盖端系统中发生的一切。至此，应用层与运输层都已讲完，我们对网络边缘的讨论也就完整了。是时候探索网络核心了！这段旅程将从接下来两章对网络层的研究开始，并延续到第 6 章对链路层的研究。

| **公式** | **说明** |
| --- | --- |
| $U_{\text{sender}} = \frac{\frac{L}{R}}{\text{RTT} + \frac{L}{R}}$ | 停等协议的发送方利用率 |
| $\text{EstimatedRTT} = (1 - \alpha) \text{EstimatedRTT} + \alpha \text{SampleRTT}$ | RTT 的指数加权移动平均 |
| $\text{DevRTT} = (1 - \beta) \text{DevRTT} + \beta \lvert \text{SampleRTT} - \text{EstimatedRTT} \rvert$ | RTT 偏差 |
| $\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \text{DevRTT}$ | 重传超时间隔 |
| $\text{LastByteSent} - \text{LastByteAcked} \le \text{min}(\text{cwnd}, \text{rwnd})$ | 未确认数据量的上界 |
| $\text{rwnd} = \text{RcvBuffer} - [\text{LastByteRcvd} - \text{LastByteRead}]$ | 接收窗口 |
| $\text{发送速率} \approx \frac{\text{cwnd}}{\text{RTT}}$ | TCP 的平均发送速率 |
| $\text{平均吞吐量} = 0.75 \frac{W}{\text{RTT}}$ | TCP Reno 的宏观吞吐量 |
