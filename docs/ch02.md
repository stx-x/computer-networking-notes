网络应用是计算机网络存在的理由——如果我们想不出任何有用的应用，也就不需要网络基础设施和支撑它们的协议了。自因特网诞生以来，确实产生了许多有用而有趣的应用。这些应用一直是因特网成功的驱动力，被家庭、汽车、学校、政府和企业中的人们使用，使因特网成为他们日常活动中不可或缺的一部分。

因特网应用包括 20 世纪 70、80 年代流行起来的经典文本类应用：文本电子邮件、远程计算机访问、文件传输和新闻组；也包括 90 年代中期的杀手级应用——万维网，涵盖网页浏览、搜索和电子商务。进入新千年以来，新的、极具吸引力的应用不断涌现，包括 Zoom、FaceTime、Teams 这样的视频会议，YouTube 这样的用户生成视频，Netflix 这样的点播电影，以及《第二人生》《魔兽世界》这样的多人在线游戏。同一时期，还出现了新一代社交网络应用——TikTok、Facebook、Instagram、X 等——它们在因特网的路由器与通信链路之上构建起了人际网络。最近，随着智能手机的到来和 4G/5G 无线接入的普及，基于位置的移动应用大量涌现，包括流行的签到、交友和路况预测应用（如 Yelp、Tinder、Waze）、移动支付应用（如微信、Apple Pay）和消息应用（如微信、WhatsApp）。显然，新的精彩因特网应用从未放慢脚步。也许本书的某些读者，就会创造出下一代的杀手级因特网应用！

本章研究网络应用的概念与实现两个方面。我们先定义关键的应用层概念，包括应用所需的网络服务、客户与服务器、进程以及运输层接口；然后详细考察若干网络应用，包括 Web、电子邮件、DNS 和视频流；接着讨论基于 TCP 与 UDP 的网络应用开发，特别是套接字接口，并用 Python 走一遍几个简单的客户-服务器应用。本章末还提供了若干有趣味的套接字编程作业。

应用层是开始学习协议的绝佳起点：这是熟悉的地带，我们对依赖这些协议运行的许多应用并不陌生；它能让我们很好地体会"协议到底是怎么回事"，并让我们预先接触到那些在学习运输层、网络层和链路层协议时会再次遇到的问题。

## 2.1　网络应用的原理

假设你对一个新的网络应用有了想法。这个应用也许会极大地服务人类，也许会让你的教授高兴，也许会给你带来巨大财富，也许只是开发和使用起来很有趣。无论动机如何，现在来看看如何把这个想法变成真正的网络应用。

网络应用开发的核心，是编写运行在不同端系统上、通过网络彼此通信的程序。例如在 Web 应用中，有两个相互通信的不同程序：运行在用户主机（台式机、笔记本、平板、智能手机等）中的浏览器程序，以及运行在 Web 服务器主机中的 Web 服务器程序。又如 Netflix 这样的视频点播应用（见 2.5 节），有一个由 Netflix 提供的程序运行在用户的智能手机、平板、计算机或电视上，还有一个 Netflix 服务器程序运行在 Netflix 服务器主机上。服务器通常（但并非总是）放在数据中心里，如图 2.1 所示。

因此，开发新应用时，你需要编写运行在多个端系统上的软件。这些软件可以用 C、Java 或 Python 等语言编写。重要的是，你**不需要**编写运行在网络核心设备（如路由器或链路层交换机）上的软件——事实上，即使你想为这些核心设备编写应用软件，也做不到。如第 1 章所学（图 1.25），网络核心设备不在应用层工作，而是在较低层——具体说是网络层及以下——工作。这种基本设计，即把应用软件限制在端系统中（如图 2.1 所示），促进了大量网络应用的快速开发与部署。

### 2.1.1　网络应用体系结构

在深入编码之前，你应当为应用制定一个总体**体系结构**方案。请记住，应用的体系结构与网络体系结构（如第 1 章讨论的五层因特网体系结构）截然不同。从应用开发者的角度看，网络体系结构是固定的，它为应用提供一组特定的服务；而**应用体系结构**由应用开发者设计，规定应用如何在各个端系统上组织。在选择应用体系结构时，开发者通常会采用现代网络应用中两种主流范式之一：**客户-服务器**（client-server）体系结构或**对等**（peer-to-peer, P2P）体系结构。

在客户-服务器体系结构中，有一台始终在线的**服务器**主机，为许多其他称为**客户**的主机提供服务。经典例子是 Web 应用：一台始终在线的 Web 服务器为运行在客户主机上的浏览器提供服务。当 Web 服务器收到客户主机对某个对象的请求时，就通过向该客户主机发送所请求的对象来响应。注意，在客户-服务器体系结构中，客户之间并不直接通信——例如在 Web 应用中，两个浏览器不直接通信。客户-服务器体系的另一个特点是：服务器具有固定的、众所周知的地址，即 **IP 地址**（稍后讨论）。正因为服务器有固定且众所周知的地址、又始终在线，客户总能通过向服务器的 IP 地址发送分组来联系服务器。采用客户-服务器体系结构的知名应用包括 Web、电子邮件和视频流。客户-服务器体系结构如图 2.2(a) 所示。

在客户-服务器应用中，单台服务器主机往往跟不上所有客户的请求。例如，一个人气很旺的社交网站如果只有一台服务器处理全部请求，很快就会不堪重负。因此，常用一个容纳大量主机的**数据中心**来构成强大的**虚拟服务器**。最流行的因特网服务——如生成式 AI（聊天机器人、文生图/文生视频等）、搜索引擎（如 Google、Bing、百度）、因特网商务（如 Amazon、eBay、阿里巴巴）、基于 Web 的电子邮件（如 Gmail、Yahoo Mail）、社交媒体（如 TikTok、Facebook、Instagram、X、微信）——都运行在一个或多个数据中心里。如 1.3.3 节所述，谷歌在全球分布着 20 多个数据中心，共同承载搜索、YouTube、Gmail 等服务。一个数据中心可以有数十万台服务器，需要供电和维护；此外，服务提供商还必须为从数据中心发出的数据支付持续不断的互连与带宽费用。

在 P2P 体系结构中，对数据中心的专用服务器依赖极小（甚至没有），应用转而利用成对的、间歇连接的主机——称为**对等方**（peer）——之间的直接通信。对等方并非服务提供商所有，而是用户控制的台式机和笔记本电脑，其中大多数位于家庭、大学和办公室。由于对等方之间不经过专用服务器而直接通信，这种体系结构称为对等体系结构。一个流行的 P2P 应用例子是文件共享应用 BitTorrent。

<Figure src="ch02/fig2-02.webp" caption="图 2.2　（a）客户-服务器体系结构；（b）P2P 体系结构" />

P2P 体系结构最引人注目的特性之一是**自扩展性**：例如在 P2P 文件共享应用中，虽然每个对等方都因请求文件而产生工作负载，但每个对等方也通过向其他对等方分发文件而为系统增加服务能力。P2P 体系结构还具有成本效益，因为它们通常不需要大量的服务器基础设施和服务器带宽（这与配有数据中心的客户-服务器设计形成对照）。然而，由于其高度分散的结构，P2P 应用面临安全性、性能和可靠性方面的挑战。正因这些挑战，今天大多数应用采用客户-服务器体系结构。

### 2.1.2　进程通信

在构建网络应用之前，还需要基本理解运行在多个端系统中的程序如何彼此通信。用操作系统的术语说，真正通信的不是程序，而是**进程**（process）。进程可以看作运行在端系统内的程序。当进程运行在同一台端系统上时，它们可以通过**进程间通信**机制、按端系统操作系统规定的规则相互通信。但本书并不特别关心同一主机内进程如何通信，而关心运行在**不同主机**上（可能具有不同操作系统）的进程如何通信。

两个不同端系统上的进程，通过跨越计算机网络交换**报文**来相互通信。发送进程创建报文并送入网络；接收进程接收这些报文，并可能通过回送报文来响应。图 2.1 表明，相互通信的进程位于五层协议栈的**应用层**。

#### 客户进程与服务器进程

一个网络应用由成对的进程构成，它们通过网络互相发送报文。例如在 Web 应用中，客户浏览器进程与 Web 服务器进程交换报文。对每一对通信进程，我们通常把其中一个标为**客户**，另一个标为**服务器**。在 Web 中，浏览器是客户进程，Web 服务器是服务器进程。客户进程与服务器进程的定义如下：

::: info 定义

在一对进程之间的通信会话语境中，**发起**通信的进程（即在会话开始时主动联系另一个进程的进程）称为**客户**；**等待**被联系以开始会话的进程称为**服务器**。

:::

例如在 Web 中，浏览器进程主动联系 Web 服务器进程，因此浏览器进程是客户，Web 服务器进程是服务器。在不致混淆时，我们也使用"应用客户端与应用服务器端"的说法。本章末尾将走一遍网络应用客户端与服务器端的简单代码。

#### 进程与计算机网络的接口

如上所述，大多数应用由成对的通信进程构成，每对中的两个进程互相发送报文。从一个进程发往另一个进程的任何报文，都必须经过底层网络。进程通过一个称为**套接字**（socket）的软件接口向网络发送报文、从网络接收报文。

用一个类比来理解进程与套接字：进程类似于一栋房子，套接字类似于它的门。当一个进程要向另一台主机上的另一个进程发送报文时，它把报文推出自己的门（套接字）。发送进程假定门外有运输基础设施，会把报文运送到目的进程的门口。报文一旦到达目的主机，就穿过接收进程的门（套接字），接收进程随后对报文进行处理。

图 2.3 展示了通过因特网通信的两个进程之间的套接字通信（图中假定进程使用的运输协议是因特网的 TCP 协议）。如图所示，套接字是主机内应用层与运输层之间的接口；由于套接字是构建网络应用所使用的编程接口，它也被称为应用与网络之间的**应用编程接口**（API）。应用开发者可以控制套接字应用层一侧的一切，但对套接字运输层一侧几乎无能为力。开发者对运输层一侧仅有的控制是：(1) 选择运输协议；(2) 或许可以设定少数运输层参数，如最大缓冲区和最大报文段长度（第 3 章讨论）。一旦选定了运输协议（如果有选择余地），应用就建立在该协议提供的运输层服务之上。2.6 节将较详细地探讨套接字。

#### 进程的编址

要把邮件寄到某个特定目的地，目的地必须有地址。同样，一台主机上运行的进程要向另一台主机上运行的进程发送分组，接收进程也必须有地址。为标识接收进程，需要指明两项信息：(1) 主机的地址；(2) 指明目的主机中接收进程的标识符。

在因特网中，主机由其 **IP 地址**标识（第 4 章将详细讨论 IP 地址）。眼下只需知道，IP 地址是一个 32 比特的量，可以把它看作主机的唯一标识。除了知道报文所去主机的地址之外，发送进程还必须标识运行在该主机中的接收进程（更准确地说，接收套接字）。之所以需要这一信息，是因为一台主机通常可能运行着许多网络应用。**目的端口号**（port number）正是为此服务。流行的应用已被分配了特定的端口号：例如 Web 服务器由端口号 80 标识，邮件服务器进程（使用 SMTP 协议）由端口号 25 标识。所有因特网标准协议的周知端口号列表可在 www.iana.org 查到。第 3 章将详细讨论端口号。

### 2.1.3　可供应用使用的运输服务

回忆一下，套接字是应用进程与运输层协议之间的接口。发送侧的应用把报文推过套接字；在套接字的另一侧，运输层协议负责把报文送到接收进程的套接字。

包括因特网在内的许多网络，都提供不止一种运输层协议。开发应用时，你必须从可用的运输层协议中选择一个。如何选择？多半是先研究各运输层协议提供的服务，然后挑选服务与应用需求最匹配的那个。这种情形类似于在两座城市之间选择火车还是飞机：你必须二选一，而每种运输方式提供的服务不同（例如火车提供市中心的上下车，飞机则提供更短的旅行时间）。

运输层协议能为调用它的应用提供哪些服务？可以把可能的服务大致归为四个维度：**可靠数据传输**、**吞吐量**、**定时**和**安全性**。

#### 可靠数据传输

如第 1 章所述，分组在计算机网络中可能丢失——例如分组可能使路由器中的缓冲区溢出，或在某些比特受损后被主机或路由器丢弃。对许多应用——如电子邮件、文件传输、Web 文档传送和金融应用——数据丢失可能带来灾难性后果（就金融应用而言，对银行和客户都是如此！）。因此，为支持这些应用，必须做点什么来保证一端应用发出的数据正确、完整地交付给另一端应用。若某协议提供这种有保证的数据交付服务，就说它提供**可靠数据传输**。运输层协议可以潜在地向应用提供的一项重要服务，就是**进程到进程的可靠数据传输**：当运输协议提供此服务时，发送进程只需把数据交给套接字，就可以完全确信数据将无差错地到达接收进程。

当运输层协议不提供可靠数据传输时，发送进程发出的一些数据可能永远到不了接收进程。这对**容忍丢失的应用**（loss-tolerant application）也许可以接受，其中最典型的是会话式音频/视频这类能容忍一定数据丢失的多媒体应用。在这些多媒体应用中，丢失的数据可能造成音视频的轻微卡顿——不是致命损伤。

#### 吞吐量

第 1 章引入了**可用吞吐量**的概念：在两个进程沿某条网络路径通信的语境中，它是发送进程向接收进程交付比特的速率。由于其他会话会共享该网络路径上的带宽，且这些会话来来去去，可用吞吐量会随时间波动。由此引出运输层协议可以提供的另一项自然服务：**以某个指定速率保证可用吞吐量**。有了这种服务，应用可以请求 $r$ 比特/秒的保证吞吐量，运输协议则确保可用吞吐量始终不低于 $r$ 比特/秒。这种保证吞吐量服务会吸引许多应用：例如 IP 电话应用以 32 kbps 编码语音，它就需要以该速率把数据送入网络并交付给接收应用；如果运输协议无法提供这一吞吐量，应用就不得不以更低速率编码（并获得足以维持该较低编码速率的吞吐量），否则只能放弃——因为对这个 IP 电话应用来说，只得到所需吞吐量的一半，几乎没有用处。有吞吐量要求的应用称为**带宽敏感的应用**（bandwidth-sensitive application）。当前许多多媒体应用都是带宽敏感的，尽管有些多媒体应用会采用自适应编码技术，按当前可用吞吐量来编码数字化语音或视频。

带宽敏感的应用有特定的吞吐量要求，而**弹性应用**（elastic application）则能利用恰好可用的任何吞吐量——多也好、少也好。电子邮件、文件传输和 Web 传送都是弹性应用。当然，吞吐量越大越好。有句老话说：人不会嫌钱多、嫌身材瘦，也不会嫌吞吐量太大！

#### 定时

运输层协议还可以提供**定时**保证。与吞吐量保证一样，定时保证可以有多种形式。一个例子是保证发送方推入套接字的每个比特在不超过 100 毫秒后到达接收方套接字。这种服务会吸引交互式实时应用，如 IP 电话、视频会议、元宇宙和多人在线游戏——它们都需要对数据交付施加严格的定时约束才能有效工作，见 [Gauthier 1999; Ramjee 1994]。例如，IP 电话中的长时延往往导致对话中出现不自然的停顿；在多人在线游戏或虚拟交互元宇宙中，采取动作与看到环境（例如端到端连接另一端的另一位玩家）响应之间的长时延，会让应用显得不够真实。对非实时应用而言，时延总是越低越好，但对端到端时延没有严格约束。

#### 安全性

最后，运输协议可以为应用提供一种或多种**安全服务**。例如，运输协议可以在发送主机中加密发送进程传输的所有数据，并在接收主机中、把数据交付给接收进程之前解密。即使数据在收发进程之间被他人观察到，这种服务也能在两个进程之间提供机密性。除机密性之外，运输协议还可以提供其他安全服务，包括数据完整性和端点鉴别，这些将在第 8 章详述。

### 2.1.4　因特网提供的运输服务

至此，我们考察的是一般意义上计算机网络**可能**提供的运输服务。现在更具体一些，考察因特网提供的运输服务类型。因特网（更一般地说，TCP/IP 网络）向应用提供两个运输协议：UDP 与 TCP。当你（作为应用开发者）为因特网创建一个新的网络应用时，首先要做的决定之一就是使用 UDP 还是 TCP，因为这两个协议向调用它们的应用提供不同的服务集合。图 2.4 给出了一些典型应用的服务需求。

#### TCP 服务

TCP 服务模型包括**面向连接服务**与**可靠数据传输服务**。当一个应用以 TCP 作为其运输协议时，它就从 TCP 获得这两项服务。

- **面向连接服务。** 在应用层报文开始流动之前，TCP 让客户与服务器交换运输层控制信息。这个所谓的**握手**过程提醒客户与服务器，使它们为即将到来的大量分组做好准备。握手阶段之后，两个进程的套接字之间就存在一条 **TCP 连接**。这是一条**全双工**连接：两个进程可以在同一时刻通过该连接互相发送报文。当应用结束发送报文时，必须拆除该连接。第 3 章将详细讨论面向连接服务及其实现。
- **可靠数据传输服务。** 通信进程可以依靠 TCP，无差错、按正确顺序地交付所发送的全部数据。当应用的一端把字节流送入套接字时，它可以指望 TCP 把完全相同的字节流交付给接收套接字，不缺失、不重复。

TCP 还包含**拥塞控制**机制——这是一项为因特网整体利益而非为通信进程直接利益提供的服务。当发送方与接收方之间网络拥塞时，TCP 拥塞控制机制会抑制发送进程（客户或服务器）。第 3 章将会看到，TCP 拥塞控制还试图把每条 TCP 连接限制在其公平的带宽份额之内。

#### UDP 服务

UDP 是一种"极简"的轻量级运输协议，只提供最基本的服务。UDP 是**无连接**的，因此两个进程开始通信之前没有握手过程。UDP 提供**不可靠数据传输服务**：也就是说，当一个进程把报文送入 UDP 套接字时，UDP 并不保证该报文最终能到达接收进程；而且，确实到达接收进程的报文也可能是乱序到达的。

<AsideCard title="安全聚焦 · 为 TCP 提供安全保障">

TCP 和 UDP 都不提供任何加密——发送进程放入套接字的数据，就是经由网络到达目的进程的同一份数据。因此，如果发送进程把口令以**明文**（即未加密）形式放入套接字，这个明文口令就会经过发送方与接收方之间的所有链路，并可能在任一中间链路上被嗅探和发现。

由于隐私及其他安全问题对许多应用已变得至关重要，因特网界为 TCP 开发了一种增强机制，称为**传输层安全**（Transport Layer Security, TLS）[RFC 5246]。经 TLS 增强的 TCP 不仅完成传统 TCP 的一切功能，还提供关键的进程到进程安全服务，包括加密、数据完整性和端点鉴别。

我们要强调：TLS 并不是与 TCP、UDP 平级的**第三个**因特网运输协议，而是对 TCP 的一种增强，且增强是在**应用层**实现的。具体地说，如果某应用想使用 TLS 的服务，就需要在应用的客户端和服务器端都包含 TLS 代码（现成的、高度优化的库与类）。TLS 有自己的套接字 API，与传统的 TCP 套接字 API 相似。当应用使用 TLS 时，发送进程把明文数据交给 TLS 套接字；发送主机中的 TLS 随后加密数据，并把加密后的数据交给 TCP 套接字；加密数据经因特网到达接收进程的 TCP 套接字；接收套接字把加密数据交给 TLS 解密；最后，TLS 通过其 TLS 套接字把明文数据交给接收进程。第 8 章将较详细地讨论 TLS。

</AsideCard>

UDP 不包含拥塞控制机制，因此 UDP 的发送侧可以随心所欲的任何速率把数据注入其下一层（网络层）。（不过要注意，由于中间链路传输能力有限或由于拥塞，实际的端到端吞吐量可能低于该速率。）

#### 因特网运输协议未提供的服务

我们沿四个维度组织了运输协议服务：可靠数据传输、吞吐量、定时和安全性。TCP 和 UDP 提供了其中哪些？已经指出，TCP 提供可靠的端到端数据传输；也知道 TCP 可以在应用层用 TLS 轻松增强，以提供安全服务。但在我们对 TCP 与 UDP 的简要描述中，明显没有提到任何吞吐量或定时保证——这些服务是当今因特网运输协议**不**提供的。这是否意味着视频会议这类时间敏感的应用无法在当今因特网上运行？答案显然是否定的——因特网承载时间敏感的应用已有多年。这类应用往往运行得相当好，因为它们被设计成尽可能应对这种"无保证"的状况。不过，当时延过大或端到端吞吐量受限时，巧妙的设计也有其局限。总之，今天的因特网常常能为时间敏感的应用提供令人满意的服务，但无法提供任何定时或吞吐量保证。

图 2.5 列出了若干流行因特网应用所使用的运输协议。可以看到，电子邮件、远程终端访问、Web 和文件传输都使用 TCP。这些应用选择 TCP 主要是因为它提供可靠数据传输，保证所有数据最终都能到达目的地。由于视频会议应用（如 Zoom）通常能容忍一定丢失、但需要最低速率才有效，视频会议应用的开发者通常更愿意让应用运行在 UDP 之上，从而绕开 TCP 的拥塞控制机制和分组开销。但由于许多防火墙被配置为封锁（大多数类型的）UDP 流量，IP 电话应用常常被设计成在 UDP 通信失败时以 TCP 作为备份。

### 2.1.5　应用层协议

我们刚刚了解到，网络进程通过向套接字发送报文来相互通信。但这些报文是如何组织的？报文中各字段的含义是什么？进程何时发送报文？这些问题把我们带入**应用层协议**的领域。应用层协议定义运行在不同端系统上的应用进程如何互相传递报文。具体地说，应用层协议定义了：

- 所交换报文的**类型**，例如请求报文和响应报文；
- 各种报文类型的**语法**，例如报文中有哪些字段以及字段如何界定；
- 字段的**语义**，即字段中信息的含义；
- 确定一个进程**何时**、**如何**发送报文以及对报文作出响应的规则。

有些应用层协议在 RFC 中规定，因而属于公有领域。例如 Web 的应用层协议 HTTP（超文本传输协议 [RFC 7230]）就以 RFC 形式公开：如果浏览器开发者遵循 HTTP RFC 的规则，该浏览器就能从任何同样遵循 HTTP RFC 规则的 Web 服务器获取网页。另有许多应用层协议是专有的、有意不公开，例如 Zoom 使用的就是专有的应用层协议。

区分**网络应用**与**应用层协议**很重要：应用层协议只是网络应用的一个组成部分（尽管是非常重要的一个）。看几个例子。Web 是一个客户-服务器应用，允许用户按需从 Web 服务器获取文档；它由许多组件构成，包括文档格式标准（即 HTML）、Web 浏览器（如 Chrome、Edge）、Web 服务器（如 Apache、微软的服务器）以及一个应用层协议。Web 的应用层协议 HTTP 定义了浏览器与 Web 服务器之间交换报文的格式与次序。

### 2.1.6　本书涉及的网络应用

本书详细讨论几种流行的网络应用：Web（2.2 节）、电子邮件（2.3 节）、DNS（2.4 节）以及视频流与内容分发网（2.5 节）。此外，2.6 节讨论套接字编程，让你能亲手构建自己的网络应用。

## 2.2　Web 与 HTTP

直到 20 世纪 90 年代初，因特网主要由研究者、学者和大学生使用：登录远程主机、在本地主机与远程主机之间传送文件、收发新闻、收发电子邮件。虽然这些应用当时（以及现在）极其有用，但因特网在学术与研究圈之外基本无人知晓。然后在 90 年代初，一个全新的重量级应用登场了——万维网 [Berners-Lee 1994]。Web 是第一个抓住普通公众眼球的因特网应用，它极大地改变了人们在工作中和工作之外互动的方式，把因特网从"众多数据网络之一"提升为实质上"唯一的数据网络"。

也许最吸引用户的是 Web 的**按需**特性：用户想要什么就能得到什么，想什么时候要就什么时候要。这与传统的广播电视不同——后者强迫用户在内容提供者播出时去收听收看。除了按需可得，Web 还有许多人们喜爱和珍视的迷人特性：任何人都极易通过 Web 发布信息——人人都能以极低成本成为出版者；超链接和搜索引擎帮助我们在信息的海洋中航行；照片和视频刺激我们的感官；表单、JavaScript、视频以及许多其他手段让我们能与页面和站点交互；而 Web 及其协议还成为生成式 AI、YouTube、基于 Web 的电子邮件（如 Gmail）以及大多数移动因特网应用（包括 Instagram 和 Google 地图）的平台。

### 2.2.1　HTTP 概述

超文本传输协议（HTTP）定义于 [RFC 1945]、[RFC 7230]、[RFC 7540] 和 [RFC 9114]。今天绝大多数应用都运行在 HTTP 之上，包括网页浏览、视频流、社交媒体，以及客户端与邮件服务器之间的电子邮件；智能手机应用通常也通过 HTTP 与服务器通信。

HTTP 由两个程序实现：一个客户程序和一个服务器程序。它们运行在不同的端系统上，通过交换 HTTP 报文彼此"交谈"。HTTP 定义了这些报文的结构，以及客户与服务器如何交换报文。在详细解释 HTTP 之前，先复习一些 Web 术语。

一个 **Web 页面**（也叫文档）由若干**对象**（object）组成。对象就是一个文件——例如 HTML 文件、JPEG 图像、JavaScript 文件、CSS 样式表文件或视频片段——它可由单个 URL 寻址。多数 Web 页面由一个**基础 HTML 文件**和若干被引用的对象组成。例如，若一个 Web 页面包含 HTML 文本和五幅 JPEG 图像，则该页面共有六个对象：基础 HTML 文件加五幅图像。基础 HTML 文件通过各对象的 URL 引用页面中的其他对象。每个 URL 有两个组成部分：存放该对象的服务器主机名，以及该对象的路径名。例如 URL

http://www.someSchool.edu/someDepartment/picture.gif

中，`www.someSchool.edu` 是主机名，`/someDepartment/picture.gif` 是路径名。由于 Web 浏览器（如 Chrome、Edge）实现 HTTP 的客户端，在 Web 语境中我们把"浏览器"与"客户"两个词交替使用。Web 服务器实现 HTTP 的服务器端，存放 Web 对象，每个对象可由一个 URL 寻址。流行的 Web 服务器包括 Apache、Nginx 和微软的 Internet Information Server。

HTTP 定义了 Web 客户如何向 Web 服务器请求网页、服务器如何把网页传送给客户。客户与服务器之间的交互细节稍后讨论，其总体思想如图 2.6 所示：当用户请求一个 Web 页面（例如点击一个超链接）时，浏览器向服务器发送对该页面中各对象的 HTTP 请求报文；服务器收到请求后，用包含这些对象的 HTTP 响应报文来响应。

<Figure src="ch02/fig2-06.webp" caption="图 2.6　HTTP 的请求-响应行为" />

视 HTTP 版本不同，它可以使用 TCP 或 UDP 作为底层运输协议，使用 UDP 是相对较新的发展。我们先假定 TCP 是底层运输协议来讨论 HTTP，2.2.7 节再讨论运行在 UDP 之上的 HTTP。

HTTP 客户首先与服务器发起一条 TCP 连接。连接建立后，浏览器与服务器进程通过各自的套接字接口访问 TCP。如 2.1 节所述，在客户端，套接字接口是客户进程与 TCP 连接之间的"门"；在服务器端，它是服务器进程与 TCP 连接之间的"门"。客户向其套接字接口发送 HTTP 请求报文、从其套接字接口接收 HTTP 响应报文；类似地，HTTP 服务器从其套接字接口接收请求报文、向其套接字接口发送响应报文。客户一旦把报文送入其套接字接口，该报文就不再由客户掌控，而是"交到了"TCP 手中。回忆 2.1 节：TCP 向 HTTP 提供可靠数据传输服务。这意味着客户进程发出的每个 HTTP 请求报文最终都会完好地到达服务器；类似地，服务器进程发出的每个 HTTP 响应报文最终都会完好地到达客户。这里可以看到分层体系结构的一大优点——HTTP 无需操心数据丢失，也无需操心 TCP 如何从网络中的数据丢失或乱序中恢复；那是 TCP 及协议栈低层协议的职责。

需要强调的是：服务器向客户发送所请求的文件时，并不保存关于客户的任何状态信息。如果某个客户在几秒钟内两次请求同一个对象，服务器不会回答"我刚才已经把它发给你了"，而是重新发送该对象——因为它早已把先前做过的事忘得一干二净。由于 HTTP 服务器不维护关于客户的任何信息，HTTP 被称为**无状态协议**（stateless protocol）。还要指出，Web 采用 2.1 节所述的客户-服务器应用体系结构：Web 服务器始终在线、具有固定 IP 地址，为可能数以百万计的不同浏览器提供服务。

HTTP 已经历多个版本。最初的 HTTP/1.0 可追溯到 90 年代初 [RFC 1945]；此后 HTTP/1.1 [RFC 7320] 与 HTTP/2 [RFC 7540] 得到广泛部署。HTTP/1.0、HTTP/1.1 和 HTTP/2 都运行在 TCP 之上；较近的 HTTP/3 已标准化 [RFC 9114] 并正在获得越来越多的采用，它运行在 UDP 之上，将在 2.2.7 节讨论。

### 2.2.2　非持续连接与持续连接

在许多因特网应用中，客户与服务器在较长时期内通信，客户发出一系列请求，服务器对每个请求作出响应。视应用及其使用方式而定，这一系列请求可以是背靠背的、按固定间隔周期性的，或间歇性的。当这种客户-服务器交互在 TCP 上进行时，应用开发者必须做一个重要决定：每个请求/响应对是否应通过一条单独的 TCP 连接发送，还是所有请求及其响应都通过同一条 TCP 连接发送？前一种做法称为使用**非持续连接**（non-persistent connection），后一种称为**持续连接**（persistent connection）。为深入理解这一设计问题，我们在一个具体应用——HTTP——的语境中考察持续连接的优缺点，HTTP 两种连接都可以使用。

#### 使用非持续连接的 HTTP

以非持续连接为例，走一遍从服务器向客户传送一个 Web 页面的步骤。假设该页面由一个基础 HTML 文件和 10 幅 JPEG 图像组成，这 11 个对象都存放在同一台服务器上；并假设基础 HTML 文件的 URL 为 `http://www.someSchool.edu/someDepartment/home.index`。过程如下：

1. HTTP 客户进程向服务器 `www.someSchool.edu` 的 80 端口（HTTP 的默认端口号）发起一条 TCP 连接。与该 TCP 连接相关联，客户端会有一个套接字，服务器端也会有一个套接字。
1. HTTP 客户通过其套接字向服务器发送一个 HTTP 请求报文，其中包含路径名 `/someDepartment/home.index`。
1. HTTP 服务器进程通过其套接字收到请求报文，从存储器（RAM 或磁盘）中取出对象 `/someDepartment/home.index`，把它封装进一个 HTTP 响应报文，再通过其套接字把响应报文发给客户。
1. HTTP 服务器进程告诉 TCP 关闭该 TCP 连接。（但 TCP 要等到确知客户已完好收到响应报文之后才真正终止连接。）
1. HTTP 客户收到响应报文，TCP 连接终止。该报文表明所封装的对象是一个 HTML 文件；客户从响应报文中提取该文件，检查 HTML 文件，找到对 10 幅 JPEG 对象的引用。
1. 对每个被引用的 JPEG 对象，重复上述前四步。

浏览器收到 Web 页面后，就把它显示给用户。不同浏览器对同一网页的**解释**（即向用户显示的方式）可能有所不同；HTTP 与"客户如何解释网页"无关，HTTP 规范（[RFC 1945]、[RFC 7540]）只定义客户 HTTP 程序与服务器 HTTP 程序之间的通信协议。

上述步骤说明了**非持续连接**的使用：服务器发出对象后就关闭 TCP 连接，该连接不为其他对象继续保留。注意，每条非持续 TCP 连接恰好传送一个请求报文和一个响应报文。因此在本例中，用户请求该网页时会生成 11 条 TCP 连接。

在继续之前，做一个粗略估算：从客户请求基础 HTML 文件到客户收到整个文件，经过多少时间？为此定义**往返时间**（RTT），即一个小分组从客户传到服务器再返回客户所需的时间。RTT 包括分组传播时延、中间路由器与交换机中的排队时延以及分组处理时延（这些时延见 1.4 节）。

现在考虑用户点击一个超链接时会发生什么。如图 2.7 所示，浏览器要在自己与 Web 服务器之间发起一条 TCP 连接，这涉及一次"三次握手"：客户向服务器发送一个小 TCP 报文段，服务器确认并回送一个小 TCP 报文段，最后客户再向服务器确认。三次握手的前两部分占用一个 RTT。完成握手的前两部分后，客户把 HTTP 请求报文与三次握手的第三部分（确认）一起送入 TCP 连接；请求报文到达服务器后，服务器把 HTML 文件送入 TCP 连接。这个 HTTP 请求/响应又占用一个 RTT。因此，粗略地说，总响应时间是**两个 RTT 加上服务器传输 HTML 文件的时间**。

<Figure src="ch02/fig2-07.webp" caption="图 2.7　请求并接收一个 HTML 文件所需时间的粗略估算" />

#### 使用持续连接的 HTTP

非持续连接有一些缺点。第一，必须为每个请求的对象建立并维护一条全新的连接；对每条这样的连接，客户端和服务器都要分配 TCP 缓冲区、保存 TCP 变量。这会给 Web 服务器带来沉重负担——它可能同时为数百个不同客户提供服务。第二，如刚才所述，每个对象都要承受两个 RTT 的交付时延：一个 RTT 用于建立 TCP 连接，一个 RTT 用于请求并接收对象。

在使用**持续连接**时（HTTP/1.1 与 HTTP/2 即如此），服务器在发出响应后让 TCP 连接保持打开，同一客户与服务器之间后续的请求和响应可以通过同一条连接发送。特别地，整个 Web 页面（上例中的基础 HTML 文件加 10 幅图像）可以通过一条持续 TCP 连接发送；而且，存放在同一服务器上的多个 Web 页面也可以通过一条持续 TCP 连接从服务器发给同一客户。这些对象请求可以用"流水线"方式发出，即背靠背地发出而不必等待未决请求的应答。通常，HTTP 服务器在一段时间（可配置的超时间隔）未使用某条连接时就关闭它。当服务器收到这些背靠背的请求时，就把对象背靠背地发回。

### 2.2.3　HTTP 报文格式

HTTP 规范 [RFC 1945; RFC 7230; RFC 7540; RFC 9114] 包含 HTTP 报文格式的定义。HTTP 报文有两类：请求报文与响应报文。

#### HTTP 请求报文

下面是一个典型的 HTTP 请求报文：

```text
GET /somedir/page.html HTTP/1.1
Host: www.someschool.edu
Connection: close
User-agent: Mozilla/5.0
Accept-language: fr
```

仔细看看这个简单的请求报文，可以得到很多信息。首先，报文是用普通 ASCII 文本写的，所以一个识字的人就能读懂。其次，报文由五行组成，每行后面跟一个回车换行；最后一行之后还有一个额外的回车换行。虽然这个请求报文只有五行，但请求报文可以有很多行，也可以只有一行。HTTP 请求报文的第一行称为**请求行**（request line），其后的各行称为**首部行**（header line）。请求行有三个字段：**方法**字段、**URL** 字段和 **HTTP 版本**字段。方法字段可以取若干不同的值，包括 GET、POST、HEAD、PUT 和 DELETE；绝大多数 HTTP 请求报文使用 GET 方法。当浏览器请求一个对象时使用 GET 方法，所请求的对象由 URL 字段标识；本例中浏览器请求的对象是 `/somedir/page.html`。版本字段不言自明：本例中浏览器实现的是 HTTP/1.1。

再看例子中的首部行。`Host: www.someschool.edu` 指明对象所在的主机。你也许认为这个首部行是多余的，因为已经有一条指向该主机的 TCP 连接了；但正如 2.2.5 节将会看到的，**Web 代理缓存**需要 host 首部行提供的信息。通过包含 `Connection: close` 首部行，浏览器告诉服务器它不想使用持续连接，希望服务器在发出所请求的对象后关闭连接。`User-agent:` 首部行指明用户代理，即向服务器发出请求的浏览器类型；本例中用户代理是 Mozilla/5.0，即 Firefox 浏览器。这个首部行很有用，因为服务器实际上可以针对不同类型的用户代理发送同一对象的不同版本（各版本由同一个 URL 寻址）。最后，`Accept-language:` 首部表示：如果服务器上有该对象的法语版本，用户希望收到法语版；否则服务器应发送其默认版本。`Accept-language:` 只是 HTTP 提供的众多**内容协商**首部之一。

看过例子之后，再看请求报文的通用格式，如图 2.8 所示。通用格式与我们刚才的例子非常接近。不过你也许注意到，在首部行（以及额外的回车换行）之后还有一个"实体主体"（entity body）。使用 GET 方法时实体主体为空，而使用 POST 方法时会用到它。当用户填写表单时（例如向搜索引擎提交搜索词），HTTP 客户常用 POST 方法：使用 POST 报文时，用户仍在向服务器请求一个 Web 页面，但该页面的具体内容取决于用户在表单字段中输入的内容。若方法字段的值为 POST，则实体主体中包含用户输入到表单字段中的内容。

必须指出，由表单生成的请求并不一定非要用 POST 方法；相反，HTML 表单常常使用 GET 方法，并把输入数据（表单字段内容）包含在所请求的 URL 中。例如，若一个表单使用 GET 方法、有两个字段，两个字段的输入分别是 monkeys 和 bananas，则 URL 将具有 `www.somesite.com/animalsearch?monkeys&bananas` 这样的结构。日常上网时，你大概见过这类带参数的 URL。

HEAD 方法与 GET 方法类似：服务器收到 HEAD 请求时，回送一个 HTTP 报文，但**不**返回所请求的对象。应用开发者常用 HEAD 方法进行调试。PUT 方法常与 Web 发布工具配合使用，允许用户把对象上传到某个 Web 服务器上的指定路径（目录）；需要向 Web 服务器上传对象的应用也会使用 PUT。DELETE 方法允许用户或应用删除 Web 服务器上的某个对象。

#### HTTP 响应报文

下面是一个典型的 HTTP 响应报文，它可以是对刚才讨论的那个请求报文的响应：

```text
HTTP/1.1 200 OK
Connection: close
Date: Mon, 21 Oct 2024 18:58:21 GMT
Server: Apache/2.2.3 (CentOS)
Last-Modified: Sun, 20 Oct 2024 13:20:46 GMT
Content-Length: 6821
Content-Type: text/html

(data data data data data ...)
```

仔细看看这个响应报文。它有三个部分：一个初始的**状态行**、六个**首部行**，然后是**实体主体**。实体主体是报文的"肉"——它包含所请求的对象本身（用 `data data data ...` 表示）。状态行有三个字段：协议版本字段、**状态码**，以及相应的**状态短语**。本例中状态行表明服务器使用的是 HTTP/1.1，且一切正常（即服务器已找到并正在发送所请求的对象）。

### 2.2.3（续）　状态码与真实报文

再看响应报文的首部行。服务器用 `Connection: close` 首部行告诉客户：发出报文后它将关闭 TCP 连接。`Date:` 首部行指明 HTTP 响应由服务器创建并发送的时间与日期——注意这不是对象被创建或最后修改的时间，而是服务器从其文件系统中取出对象、插入响应报文并发送的时刻。`Server:` 首部行表明该报文由 Apache Web 服务器生成，它类似于请求报文中的 `User-agent:` 首部。`Last-Modified:` 首部行指明对象被创建或最后修改的时间与日期；这个首部对本地客户与网络缓存服务器（也称代理服务器）中的对象缓存都至关重要，稍后将详述。`Content-Length:` 首部行指明所发送对象的字节数。`Content-Type:` 首部行指明实体主体中的对象是 HTML 文本。（对象类型的正式标识由 `Content-Type:` 首部给出，而不是由文件扩展名给出。）

响应报文的通用格式如图 2.9 所示，与我们刚才的例子吻合。关于状态码及其短语再说几句：状态码与相应短语指示请求的结果。一些常见状态码及短语包括：

- **200 OK**：请求成功，信息在响应中返回。
- **301 Moved Permanently**：所请求的对象已被永久移动，新 URL 在响应报文的 `Location:` 首部中给出，客户软件会自动去取新 URL。
- **400 Bad Request**：这是一个通用错误码，表示服务器无法理解该请求。
- **404 Not Found**：所请求的文档在本服务器上不存在。
- **505 HTTP Version Not Supported**：服务器不支持所请求的 HTTP 协议版本。

想看看自己计算机发出的真实 HTTP 请求报文以及 Web 服务器返回的响应吗？这很容易，建议你试一试！在计算机的命令行提示符下输入：

```text
curl -v http://gaia.cs.umass.edu/kurose_ross/index.php
```

上面的 `curl` 命令会向 gaia.cs.umass.edu 的 Web 服务器发送一个 HTTP GET 请求，以获取 HTML 内容 `/kurose_ross/index.php`，即本书作者的主页。详细模式（`-v`）会把 HTTP GET 请求报文与所收到响应的文本内容显示出来。当然，若想看格式化显示后的响应是什么样子，只需把上面的 URL 输入你喜欢的浏览器。

本节讨论了 HTTP 请求与响应报文中可以使用的若干首部行。HTTP 规范定义的首部行还有很多很多，浏览器、Web 服务器和网络缓存服务器都可以插入。我们只覆盖了全部首部行中的一小部分；下面还会再讲几个，2.2.5 节讨论网络 Web 缓存时再讲一小部分。

浏览器如何决定在请求报文中包含哪些首部行？Web 服务器又如何决定在响应报文中包含哪些首部行？浏览器会根据自身类型与版本、用户配置，以及当前是否已缓存了该对象（可能是过时的版本）来生成首部行。Web 服务器的行为类似：不同的产品、版本和配置都会影响响应报文中包含哪些首部行。

### 2.2.4　用户与服务器的交互：Cookie

前面提到 HTTP 服务器是无状态的。这简化了服务器设计，使工程师能够开发出可处理数千条并发 TCP 连接的高性能 Web 服务器。然而，网站往往需要识别用户——或者因为服务器想限制用户访问，或者因为它想根据用户身份提供内容。为此，HTTP 使用了 **Cookie**。Cookie 定义于 [RFC 6265]，允许站点跟踪用户。今天大多数大型商业网站都使用 Cookie。

如图 2.10 所示，Cookie 技术有四个组成部分：(1) HTTP 响应报文中的一行 `Set-cookie:` 首部；(2) HTTP 请求报文中的一行 `Cookie:` 首部；(3) 保存在用户端系统上、由用户浏览器管理的 Cookie 文件；(4) 网站的后端数据库。

结合图 2.10 走一个例子。假设 Susan 一直在家用 PC 上用 Chrome 上网，她第一次访问 Amazon.com（假定她过去访问过 eBay）。当请求到达 Amazon 的 Web 服务器时，服务器生成一个唯一识别号，并在其后端数据库中创建一条以该识别号为索引的记录。随后，Amazon 的 Web 服务器向 Susan 的浏览器回送响应，其中包含一行 `Set-cookie:` 首部，带有该识别号，例如：

```text
Set-cookie: 1678
```

Susan 的浏览器收到该 HTTP 响应报文后，看到 `Set-cookie:` 首部，就在它管理的专用 Cookie 文件中追加一行，其中包括服务器的主机名和 `Set-cookie:` 首部中的识别号。注意，由于 Susan 过去访问过 eBay，Cookie 文件中已经有 eBay 的记录。随着 Susan 继续浏览 Amazon 站点，她每次请求一个网页，浏览器都会查阅 Cookie 文件，取出她在这个站点上的识别号，并在 HTTP 请求中放入包含该识别号的 `Cookie:` 首部行：

```text
Cookie: 1678
```

这样，Amazon 服务器就能跟踪 Susan 在 Amazon 站点上的活动。虽然 Amazon 网站未必知道 Susan 的姓名，但它确切知道用户 1678 访问了哪些页面、以什么顺序、在什么时间！Amazon 用 Cookie 提供购物车服务——它可以维护 Susan 打算购买的所有商品的清单，以便她在会话结束时一次性付款。

如果 Susan 一周后再次访问 Amazon，她的浏览器会继续在请求报文中放入 `Cookie: 1678`。Amazon 还会根据她过去访问过的页面向她推荐商品。如果 Susan 在 Amazon 注册，提供了全名、电子邮件地址、邮寄地址和信用卡信息，Amazon 就可以把这些信息加入其数据库，从而把 Susan 的姓名与她的识别号（以及她过去在该站点访问过的所有页面！）关联起来。Amazon 等电子商务网站就是这样提供"一键购物"的——Susan 在后续访问中选购商品时，无需重新输入姓名、卡号或地址。

由此可见，Cookie 可以用来识别用户。用户第一次访问某个站点时，可以提供用户标识（可能是姓名）；在随后的会话中，浏览器把 Cookie 首部传给服务器，从而向服务器表明用户身份。因此，Cookie 可以在无状态的 HTTP 之上构建一个**用户会话层**。例如，当用户登录基于 Web 的电子邮件应用时，浏览器把 Cookie 信息发送给服务器，使服务器能在该用户与应用的整个会话期间识别他。

虽然 Cookie 常常简化用户的网上购物体验，但它们也有争议，因为可以视为对隐私的侵犯。如我们刚才所见，结合 Cookie 与用户提供的账户信息，网站可以了解用户的许多情况，并可能把这些信息卖给第三方。

### 2.2.5　浏览器缓存

图 2.7 已经表明：从浏览器首次向 Web 服务器请求一个对象，到浏览器收到该对象，最小时延是 2 个 RTT——一个 RTT 用于在浏览器与服务器之间建立 TCP 连接，另一个 RTT 用于发送 HTTP 请求并接收 HTTP 响应。稍后会看到，最新版本的 HTTP（HTTP/3）经过优化，在许多情况下只需一个 RTT 就能请求一个网页。但我们能不能把这一时延降到比一个 RTT 还小？零时延岂不是很妙？这听起来似乎违背物理定律，但借助**浏览器缓存**确实可以做到——这是所有现代浏览器都实现、并在 Web 中广泛使用的技术。据一项估计，75% 的 Web 请求收到的 HTTP 响应带有我们下面要研究的那类显式浏览器缓存指令 [Web almanac 2021]。

借助浏览器缓存，Web 浏览器把最近收到的 Web 对象内容保存在本地**浏览器缓存**中。当用户请求某个 Web 对象时，浏览器先检查该对象是否已存于本地浏览器缓存；若是，就可以立即显示该对象，而无需向 Web 服务器发出新请求（从而避免随后的请求/响应时延）——因为浏览器此前已从该服务器请求并收到过该对象。

虽然浏览器缓存可以缩短用户感知的响应时间、减少因特网上承载的 HTTP 流量（这些优点将在章末习题中探讨），但它也带来一个新的重要挑战：浏览器如何知道 Web 服务器中当前存放的对象，是否在客户端缓存之后被修改过？某些类型的 Web 对象（如图像、JavaScript 文件和 CSS 文件）很少变化，另一些对象（如文本）则可能频繁变化。浏览器如何知道自己缓存的内容是最新的还是过时的？所幸 HTTP 协议在 GET 报文和响应报文中都提供了字段，帮助服务器与浏览器管理浏览器缓存 [RFC 7232]：

- **Cache-Control。** HTTP 响应报文中的 `Cache-Control` 字段让服务器规定 HTTP 响应中的内容应如何缓存。`Cache-Control: no-store` 指令告诉浏览器不要在本地缓存/存储该内容，此时浏览器必须总是重新向服务器请求内容。另一种做法是，服务器可以明确告知浏览器某对象可在缓存中保留多长时间：例如 `Cache-Control: max-age=3600` 指令告诉浏览器该内容可缓存 3600 秒，之后必须重新向服务器请求。[RFC 7232] 还定义了许多其他 `Cache-Control` 指令。
- **If-Modified-Since。** HTTP 还在客户端到服务器的报文中提供一种机制，即所谓的**条件 GET**（conditional GET），以方便缓存。条件 GET 就是普通的 HTTP GET 报文，只是额外包含一行 `If-Modified-Since:` 首部。使用条件 GET 时，客户显式请求一个对象，但同时告知服务器：它的浏览器缓存中已有该对象，以及该对象是何时被加入缓存的。HTTP 服务器若发现该对象在这段时间内已改变，就回送完整对象；否则只告诉浏览器其（浏览器缓存中的）副本仍是最新的，而不再重发该对象。

为说明条件 GET 如何运作，走一个例子。假设浏览器此前请求过某个对象，比如 `kiwi.jpg`，把它存入了缓存，并记录了它被加入缓存的时间。当用户后来再次请求该对象时，浏览器无法确定这份缓存副本是否仍然有效——原因可能是服务器从未提供缓存控制信息，或服务器先前给出的 `max-age` 已过期，或服务器指示浏览器缓存该对象但同时要求每次都与服务器核对新鲜度。此时，浏览器向服务器发送一个条件 GET：

```text
GET /fruit/kiwi.jpg HTTP/1.1
Host: www.exotiquecuisine.com
If-modified-since: Fri, 13 Sep 2024 09:23:24
```

`If-modified-since:` 首部行的值表明，浏览器缓存中的该对象是 2024 年 9 月 13 日 9:23:24 收到的。这个条件 GET 是在告诉服务器：只有当该对象在指定日期之后被修改过时，才发送它。假设该对象自 2024 年 9 月 13 日 09:23:24 以来未被修改，则 Web 服务器回送：

```text
HTTP/1.1 304 Not Modified
Date: Fri, 8 Nov 2024 12:07:29
Server: Apache/2.4.62 (Unix)
(empty entity body)
```

我们看到，此时 Web 服务器仍然发送一个响应报文，但报文中不包含所请求的对象。状态行中的 `304 Not Modified` 告诉浏览器：其缓存中的该对象副本仍是最新的，因此可以使用缓存副本。若把所请求的对象也包含进来，只会浪费带宽、增加用户感知的响应时间，尤其当对象很大时。

### 2.2.6　HTTP/2

HTTP/2 [RFC 7540] 于 2015 年标准化，是自 1997 年标准化的 HTTP/1.1 以来 HTTP 的第一个新版本。标准化之后，HTTP/2 迅速普及：2024 年，排名前 1000 万的网站中约 35% 支持 HTTP/2 [W3Techs]。多数浏览器——包括 Chrome、Edge、Safari、Opera 和 Firefox——也支持 HTTP/2。近年来由于 2.2.7 节将讨论的 HTTP/3 的出现，其使用率有所下降。

HTTP/2 的主要目标是：通过在单条 TCP 连接上实现请求与响应的**多路复用**来降低感知时延，提供请求优先级与服务器推送，并对 HTTP 首部字段进行高效压缩。HTTP/2 **不**改变 HTTP 的方法、状态码、URL 或首部字段，它改变的是数据在客户与服务器之间格式化与传输的方式。

为理解 HTTP/2 的必要性，回忆 HTTP/1.1 使用持续 TCP 连接，使一个网页可以通过单条 TCP 连接从服务器发往客户。每个网页只用一条 TCP 连接，可以减少服务器端的套接字数量，并使每个传输的网页获得公平的网络带宽份额（见下文）。但浏览器开发者很快发现，在单条 TCP 连接上发送网页中的所有对象存在**队头阻塞**（Head of Line, HOL blocking）问题。

为理解 HOL 阻塞，考虑一个网页：顶部是一个大视频片段，下面有许多小对象；再假设服务器与客户之间的路径上有一条中低速瓶颈链路（例如低速无线链路）。使用单条 TCP 连接时，视频片段要花很长时间才能通过瓶颈链路，而小对象则在它后面排队等待——也就是说，队首的视频片段阻塞了后面的小对象。HTTP/1.1 浏览器通常通过打开多条并行 TCP 连接来绕过这个问题，使同一网页中的对象并行发往浏览器；这样小对象可以更快到达并在浏览器中呈现，从而降低用户感知的时延。

第 3 章将详细讨论的 TCP 拥塞控制，也为浏览器使用多条并行 TCP 连接而非单条持续连接提供了意外的激励。粗略地说，TCP 拥塞控制力求让共享某条瓶颈链路的每条 TCP 连接获得该链路可用带宽的均等份额；因此若有 $n$ 条 TCP 连接经过某瓶颈链路，每条连接大致获得 $\frac{1}{n}$ 的带宽。通过打开多条并行 TCP 连接来传送单个网页，浏览器就能"作弊"抢占更大份额的链路带宽。许多 HTTP/1.1 浏览器最多打开六条并行 TCP 连接，既是为了绕开 HOL 阻塞，也是为了获得更多带宽。

HTTP/2 的主要目标之一，就是消除（至少减少）为传送单个网页而使用的并行 TCP 连接。这不仅减少了服务器上需要打开和维护的套接字数量，还让 TCP 拥塞控制得以按设计意图运作。但只用一条 TCP 连接传送网页，HTTP/2 就需要精心设计的机制来避免 HOL 阻塞。

#### HTTP/2 的成帧

HTTP/2 解决 HOL 阻塞的办法，是把每条报文拆成小的**帧**（frame），并在同一条 TCP 连接上交错发送请求与响应报文。为理解这一点，再仔细考虑前面那个例子：网页由一个视频片段和 8 个较小对象组成，于是任何想看到该网页的浏览器都会向服务器发出 9 个并发请求；对这 9 个请求，服务器需要在同一条 TCP 连接上向浏览器发送 9 个相互竞争的 HTTP 响应报文。为简单起见，假设所有帧长度固定，视频片段由 1000 帧组成，每个较小对象由 2 帧组成。采用帧交错后，发送完视频片段的第 1 帧，就发送每个小对象的第 1 帧；再发送视频片段的第 2 帧，然后发送每个小对象的第 2 帧。这样，总共发送 18 帧之后，所有较小对象就都发完了。若不使用交错，则要等发送 1016 帧之后才会发送这些小对象。可见 HTTP/2 的成帧机制能显著降低用户感知的时延。

把一条 HTTP 报文拆成独立的帧、交错发送、再在对端重新组装——这是 HTTP/2 **最重要的单项增强**。成帧由 HTTP/2 协议的**成帧子层**（framing sub-layer）完成。当服务器要发送一个 HTTP 响应时，该响应由成帧子层处理，被拆分成帧：响应的首部字段成为一帧，报文主体被拆成一帧或多帧。随后，成帧子层把该响应的帧与其他响应的帧交错，通过这条单一的持续 TCP 连接发送。帧到达客户后，先在成帧子层重新组装成原来的响应报文，再由浏览器照常处理。类似地，客户的 HTTP 请求也被拆成帧并交错发送。

除了把每条 HTTP 报文拆成独立的帧，成帧子层还对帧进行**二进制编码**。二进制协议解析效率更高，帧略小，且更不易出错。

#### 响应优先级与服务器推送

**报文优先级**（message prioritization）让开发者定制请求的相对优先级，以更好地优化应用性能。如前所述，成帧子层把报文组织成发往同一请求方的并行数据流。当客户向服务器发送并发请求时，可以给每条报文赋予 1 到 256 之间的权重来为所请求的响应排定优先级，数值越大优先级越高。服务器据此可以优先发送优先级最高的响应的帧。此外，客户还可以通过指定某条报文所依赖的另一条报文的 ID，说明报文之间的依赖关系。

HTTP/2 的另一个特性是服务器可以针对单个客户请求发送多个响应。也就是说，除了对原始请求的响应之外，服务器还可以向客户**推送**额外对象，而客户无需逐个请求。这是可行的，因为 HTML 基础页面已经指明了完整渲染该网页所需的对象。因此，服务器不必等待客户对这些对象的 HTTP 请求，而可以分析 HTML 页面、识别所需对象，并在收到显式请求之前就把它们发给客户。**服务器推送**（server push）消除了等待请求所带来的额外时延。

### 2.2.7　HTTP/3 与 QUIC

我们刚刚了解了 HTTP 协议的演进：从 HTTP/1.0 到 HTTP/1.1，再到 HTTP/2。这三个协议虽有显著差异，却有一个重要的共同特征——它们都运行在 TCP 之上。但这并不意味着 HTTP 将永远运行在 TCP 上！2022 年在 RFC 9114 中标准化的 HTTP/3 已席卷因特网界：它在 Web（包括电子邮件、音视频流和社交媒体）中正迅速获得市场份额，并已成为许多流行浏览器与智能手机应用的默认 HTTP 版本。引人注目的是，HTTP/3 **不**运行在 TCP 上，而是运行在 UDP 上！你也许会问：UDP 是一种没有可靠数据传输、因而无法保证 HTTP 报文交付的"光板"运输协议，这怎么可能？下面就来揭开这个颇为迷人的谜底。

#### QUIC 运输协议

HTTP/3 运行在 **QUIC**（Quick UDP Internet Connections）运输协议之上。因此在描述 HTTP/3 之前，需要先讨论 2021 年在 RFC 9000 中标准化的 QUIC。

你现在也许在想："等等！作者不是一再告诉我们因特网恰好有两个运输协议——UDP 和 TCP 吗？现在又说还有第三个叫 QUIC 的运输协议？那因特网到底有两个还是三个运输协议？"

让我们澄清一下。严格说来，因特网仍然只有两个运输协议：TCP 和 UDP。事实上，QUIC 并不是运输层协议，而是**应用层中的一个子层**，它使用 UDP 在因特网上收发分组，如图 2.11 所示——这正是其名字中"UDP"的由来（Quick UDP Internet Connections）。

然而，尽管严格说来 QUIC 不是运输层协议，从应用开发者的角度看它却是。事实上，网络应用开发者可以像创建 TCP、UDP 套接字那样创建 **QUIC 套接字**来编写应用（见 2.6 节）。当应用建立一个 QUIC 套接字时，QUIC 子层会创建一个 UDP 套接字；随后应用就可以向 QUIC 套接字发送报文、从中接收报文，而无需关心 QUIC 的内部机制。总之，虽然实际上 QUIC 是应用层的一个子层，但从应用开发者的角度看，它是一个新的运输层协议。

<Figure src="ch02/fig2-11.webp" caption="图 2.11　（a）传统的安全 HTTP 协议栈；（b）基于 QUIC 的安全 HTTP/3 协议栈" />

#### 为什么需要一个"新的运输协议"

QUIC 是一个可供许多应用使用的通用协议，但它主要的设计目标是提升 Web 的性能。来看看性能提升的空间在哪里。

在很久以前（大约到 2005 年为止），多数 Web 事务直接运行在未加密的 TCP 之上。但多年来，加密与鉴别已成为多数 Web 事务（包括网页浏览、Web 搜索和基于 Web 的电子邮件）的默认要求。这类安全服务通常通过 TLS 提供给 Web 应用（见 2.3 节的"安全聚焦"专栏，以及第 8 章的详述）。因此，多数现代 Web 事务实际使用的是"TCP + TLS"的组合：先用三次握手建立 TCP 连接，再用 TLS 握手协商密钥——这至少要花两个 RTT 才能发出第一个 HTTP 请求。

QUIC 的第一个改进是把传输握手与加密握手合并：QUIC 在建立连接的同时完成 TLS 1.3 的密钥协商，因此通常只需**一个 RTT** 就能开始发送应用数据；若客户此前与该服务器通信过并保存了会话凭证，还可以实现 **0-RTT**——在第一个报文中就携带应用数据。

第二个、也是更根本的改进，是消除 TCP 层面的队头阻塞。在 TCP 上，所有 HTTP 请求共享同一个字节流：只要有一个 TCP 报文段丢失，后续所有数据（哪怕属于完全无关的请求）都必须等待重传，这就是 2.2.6 节所说 HOL 阻塞的根源，而 HTTP/2 的成帧只能缓解、无法根治（因为帧仍在同一条 TCP 字节流里）。QUIC 则在同一连接内提供多条独立的**流**（stream）：每条流有自己的可靠、按序交付语义，某条流上的丢包只阻塞该流，其他流照常交付。

此外，QUIC 还提供：

- **面向连接且安全**：连接由连接 ID 标识，所有 QUIC 分组都加密；
- **每流可靠传输**：确认与重传机制与 TCP 类似；
- **拥塞控制**：基于 TCP NewReno 的拥塞控制，对应用透明；
- **连接迁移**：由于连接由连接 ID 而非 IP 地址与端口标识，当用户从 WiFi 切换到蜂窝网、IP 地址改变时，连接仍然保持——这对移动用户尤为重要。

最后，QUIC 在用户空间实现，可以随应用一起更新，而不必等待操作系统内核升级——这正是它能在短短几年内被广泛部署的重要原因。第 3 章的 3.8 节还将从运输层的角度再次讨论 QUIC。

## 2.3　因特网中的电子邮件

电子邮件自因特网诞生之初就存在。在因特网尚在襁褓之时，它是最流行的应用 [Segaller 1998]；多年来它变得更加精巧、强大，至今仍是因特网最重要、使用最广泛的应用之一。

本节考察因特网电子邮件核心的应用层协议。不过在深入讨论这些协议之前，先从高层看一看因特网邮件系统及其关键组件。

图 2.12 给出因特网邮件系统的高层视图，它有三个主要组件：**用户代理**（user agent）、**邮件服务器**（mail server）和**简单邮件传输协议**（SMTP）。下面以发送方 Alice 给接收方 Bob 发一封邮件为例，逐一说明。

**用户代理**让用户阅读、回复、转发、保存和撰写邮件。电子邮件用户代理的例子包括 Microsoft Outlook、Apple Mail、基于 Web 的 Gmail、智能手机上的 Gmail 应用等。如今许多用户通过 Gmail、Yahoo! Mail 这类基于 HTTP 的用户代理，向自己的邮件服务器发信、从邮件服务器收信。当 Alice 写完邮件后，她的用户代理把邮件发送到她的邮件服务器，邮件被放入该服务器的**发送队列**。当 Bob 想读邮件时，他的用户代理从自己邮件服务器中的邮箱里取出邮件。

**邮件服务器**构成电子邮件基础设施的核心。每个接收者（如 Bob）都在某台邮件服务器上有一个**邮箱**（mailbox），该邮箱管理和保存发来的邮件。一封典型邮件从发送方的用户代理出发，先到发送方的邮件服务器，再到接收方的邮件服务器，最后投递进接收方的邮箱。当 Bob 想访问自己邮箱中的邮件时，存放其邮箱的邮件服务器先对 Bob 进行鉴别（用用户名和口令）。Alice 的邮件服务器还必须处理 Bob 的邮件服务器发生故障的情形：如果 Alice 的服务器无法把邮件投递到 Bob 的服务器，它就把邮件保存在消息队列中，稍后再尝试传送；重试通常每 30 分钟左右一次，若数天后仍不成功，服务器就删除该邮件，并向发送方（Alice）回一封电子邮件告知。

**SMTP** 是因特网电子邮件的主要应用层协议。它使用 TCP 的可靠数据传输服务，把邮件从发送方的邮件服务器传送到接收方的邮件服务器。与多数应用层协议一样，SMTP 有客户端与服务器端：客户端运行在发送方的邮件服务器上，服务器端运行在接收方的邮件服务器上；每台邮件服务器上都同时运行 SMTP 的客户端与服务器端。当一台邮件服务器向其他邮件服务器发信时，它充当 SMTP 客户；当它从其他邮件服务器收信时，它充当 SMTP 服务器。

### 2.3.1　SMTP

SMTP 定义于 RFC 5321，是因特网电子邮件的核心。如上所述，SMTP 把邮件从发送方的邮件服务器传送到接收方的邮件服务器。SMTP 比 HTTP 古老得多（最初的 SMTP RFC 可追溯到 1982 年，而 SMTP 的存在还更早）。尽管 SMTP 有许多优良品质——它在因特网中的普遍使用就是明证——但它毕竟是一项遗留技术，带有某些陈旧的特征。例如，它把所有邮件报文的**主体**（不只是首部）限制为简单的 7 比特 ASCII。这一限制在 80 年代初是合理的：当时传输能力稀缺，没人用电子邮件发送大附件或大的图像、音频、视频文件。但在今天这个多媒体时代，7 比特 ASCII 的限制就有点麻烦了——它要求二进制多媒体数据在通过 SMTP 发送之前先编码成 ASCII，并在 SMTP 传输之后再把相应的 ASCII 消息解码回二进制。回忆 2.2 节：HTTP 并不要求多媒体数据在传输前进行 ASCII 编码。

为说明 SMTP 的基本操作，走一遍常见场景。假设 Alice 要给 Bob 发一条简单的 ASCII 消息。

1. Alice 启动她的邮件用户代理，给出 Bob 的电子邮件地址（例如 bob\@someschool.edu），撰写邮件，并指示用户代理发送。
1. Alice 的用户代理把邮件发送到她的邮件服务器，邮件被放入消息队列。
1. 运行在 Alice 邮件服务器上的 SMTP 客户端看到队列中的邮件，向运行在 Bob 邮件服务器上的 SMTP 服务器打开一条 TCP 连接。
1. 经过一些初始的 SMTP 握手之后，SMTP 客户端把 Alice 的邮件送入该 TCP 连接。
1. 在 Bob 的邮件服务器上，SMTP 服务器端收到该邮件，随后 Bob 的邮件服务器把邮件放入 Bob 的邮箱。
1. Bob 在方便时启动他的用户代理读取该邮件。

这一场景总结于图 2.13。需要注意的是：SMTP 通常**不**使用中间邮件服务器来转发邮件，即使两台邮件服务器位于地球两端也是如此。如果 Alice 的服务器在香港、Bob 的服务器在圣路易斯，那么 TCP 连接就是香港与圣路易斯之间的一条直接连接。

<Figure src="ch02/fig2-13.webp" caption="图 2.13　Alice 向 Bob 发送邮件" />

<AsideCard title="SMTP 与 HTTP 的对比">

二者都是用于传送文件的协议，有不少可类比之处，也有重要差别。两者都使用 TCP 的持续连接；都采用"请求-响应"式的 ASCII 文本命令/应答交互。关键差别在于：HTTP 是**拉**（pull）协议——用户用 HTTP 从服务器**拉取**文件，TCP 连接由想获取文件的一方发起；而 SMTP 是**推**（push）协议——发送方的邮件服务器把文件**推**给接收方的邮件服务器，TCP 连接由想发送文件的一方发起。

### 2.3.2　邮件报文格式

当 Alice 给 Bob 写一封电子邮件时，她使用的用户代理可能要求她填写若干首部行，例如收件人地址、主题等。这些首部行与邮件主体一起构成**邮件报文**。邮件报文本身与 SMTP 是分开的：SMTP 负责**传送**报文，而报文**格式**由 RFC 5322 等规范定义。

一个典型的邮件报文如下（首部与主体之间以一个空行分隔）：

```text
From: alice@crepes.fr
To: bob@hamburger.edu
Subject: Searching for the meaning of life.

（这里是邮件主体……）
```

首部行之后必须有一个空行，然后是邮件主体（ASCII 文本）。值得注意的是，邮件报文的首部行与 SMTP 命令/应答是两回事：SMTP 的 `MAIL FROM`、`RCPT TO` 等命令用于在服务器之间建立传输会话，而邮件报文首部中的 `From:`、`To:` 只是给收件人看的"信纸抬头"，二者不必一致（这也正是伪造发件人如此容易的原因之一）。

### 2.3.3　邮件访问协议

一旦 SMTP 把邮件投递到接收方的邮件服务器，该邮件就被放入接收方的邮箱。此后，接收方如何从服务器上的邮箱取信？这里涉及另一组协议。

历史上，用户通过直接在邮件服务器上登录（例如用 Telnet）来读信，但这很不方便。于是发展出两类**邮件访问协议**：

- **POP3**（Post Office Protocol version 3，RFC 1939）：一种简单协议，客户与服务器建立 TCP 连接后进行"鉴别、事务、更新"三阶段交互，把邮件从服务器**下载**到本地并（通常）删除服务器副本。POP3 是有状态的（在一个会话内），但跨会话不保存状态。
- **IMAP**（Internet Mail Access Protocol，RFC 3501）：功能更强，允许用户在服务器上维护文件夹层次，把邮件在服务器上移动、标记为已读、搜索等；用户在客户端所做的操作会反映到服务器上，因而适合在多个设备上访问同一邮箱。
- **基于 Web 的电子邮件**（如 Gmail、Yahoo! Mail）：用户代理就是浏览器，浏览器通过 HTTP 与邮件服务器通信，邮件服务器再通过 SMTP（发信）和 IMAP/POP3 或私有接口（收信）与邮件系统交互。今天这是最常见的邮件访问方式。

<Figure src="ch02/fig2-14.webp" caption="图 2.14　电子邮件协议及其通信实体" />

<AsideCard title="安全聚焦 · 电子邮件的安全">

原始的 SMTP、POP3 和 IMAP 都以明文传输，包括口令。因此在无线链路或共享链路上，邮件内容与口令都可能被嗅探。今天，这些协议通常运行在 TLS 之上（即 SMTPS、POP3S、IMAPS），或者通过 HTTPS 访问基于 Web 的邮件。此外，邮件还面临垃圾邮件（spam）、钓鱼（phishing）和伪造发件人等问题，相应的防御手段（如 SPF、DKIM、DMARC）依赖域名与密码学机制，详见第 8 章。

</AsideCard>

## 2.4　DNS：因特网的目录服务

对人类而言，识别主机有两种方式：用**主机名**（hostname），或用 **IP 地址**。主机名如 `www.facebook.com`、`gaia.cs.umass.edu`，便于人们记忆；而路由器处理的是固定长度的二进制 IP 地址。人们偏爱便于记忆的主机名，路由器偏爱便于处理的 IP 地址，二者之间的折衷就产生了一个需求：需要一种能把主机名转换为 IP 地址的目录服务。这正是**域名系统**（Domain Name System, DNS）的主要任务。

DNS 是：(1) 一个由分层的 DNS 服务器实现的分布式数据库；(2) 一个使主机能够查询该分布式数据库的应用层协议。DNS 通常由其他应用层协议使用，包括 HTTP、SMTP 和 FTP——例如，当浏览器请求 `www.someSchool.edu` 上的网页时，它需要先把该主机名转换为 IP 地址，这一过程由 DNS 完成。

### 2.4.1　DNS 提供的服务

DNS 除了进行主机名到 IP 地址的转换，还提供其他重要服务：

- **主机别名**（host aliasing）：有着复杂主机名的主机可以有一个或多个别名，DNS 可以被用来获取别名对应的规范主机名（canonical hostname）及其 IP 地址。
- **邮件服务器别名**（mail server aliasing）：电子邮件地址要求便于记忆，因此 MX 记录允许一个公司的邮件服务器使用简单别名（如 `yahoo.com`），而实际主机名可能复杂得多。
- **负载分配**（load distribution）：繁忙的站点会被复制到多台服务器上，每台服务器运行在不同的端系统上，各有不同的 IP 地址。DNS 数据库中同一规范主机名可以对应一个 IP 地址集合，DNS 在响应查询时循环这些地址，从而把负载分摊到多台服务器上。

DNS 的一个重要设计特征是：它被实现为**分布式**数据库，而不是集中式数据库。集中式设计（单一 DNS 服务器回答所有查询）会带来单点故障、通信容量、远距离时延和维护等严重问题。DNS 的分布式设计使其能够扩展到整个因特网。

### 2.4.2　DNS 工作机理概述

DNS 采用层次化的服务器结构，大致分为三类：

- **根 DNS 服务器**（root DNS server）：全球有 1000 多台根服务器实例，分布在多个地点（图 2.16），由 13 个不同组织管理。根服务器提供顶级域（TLD）服务器的 IP 地址。
- **顶级域 DNS 服务器**（TLD DNS server）：负责顶级域（如 `.com`、`.org`、`.net`、`.edu` 以及所有国家顶级域如 `.cn`、`.uk`、`.fr`）。TLD 服务器提供权威 DNS 服务器的 IP 地址。
- **权威 DNS 服务器**（authoritative DNS server）：每个有公开可访问主机（如 Web 服务器、邮件服务器）的组织都要提供权威 DNS 记录，这些记录把该组织中主机名映射为 IP 地址。一个组织可以选择自己实现权威 DNS 服务器，也可以付费把记录存放在某服务提供商的权威 DNS 服务器上。

此外还有**本地 DNS 服务器**（local DNS server）。严格说它不属于上述层次结构，但对 DNS 体系结构至关重要：每个 ISP（居民 ISP、公司、大学）都有一台本地 DNS 服务器（也叫默认名字服务器）。当主机发出 DNS 查询时，该查询被发往其本地 DNS 服务器，后者充当中介，把查询转发到层次结构中。

<Figure src="ch02/fig2-15.webp" caption="图 2.15　DNS 服务器层次结构的一部分" />

<Figure src="ch02/fig2-16.webp" caption="图 2.16　根服务器的数量与位置（2024 年）" />

图 2.17 说明了 DNS 解析的典型过程。假设主机 `cse.nyu.edu` 上的客户想确定 `gaia.cs.umass.edu` 的 IP 地址：

1. 客户向本地 DNS 服务器发送 DNS 查询报文，其中包含被转换的主机名 `gaia.cs.umass.edu`。
1. 本地 DNS 服务器把该报文转发给根 DNS 服务器。
1. 根 DNS 服务器注意到 `.edu` 前缀，向本地 DNS 服务器返回负责 `.edu` 的 TLD 服务器的 IP 地址列表。
1. 本地 DNS 服务器向这些 TLD 服务器之一重发查询报文。
1. TLD 服务器注意到 `umass.edu` 前缀，用负责 `umass.edu` 的权威 DNS 服务器的 IP 地址作为响应。
1. 本地 DNS 服务器向该权威 DNS 服务器重发查询报文。
1. 权威 DNS 服务器用 `gaia.cs.umass.edu` 的 IP 地址作为响应。
1. 本地 DNS 服务器把该 IP 地址回送给客户。

<Figure src="ch02/fig2-17.webp" caption="图 2.17　各 DNS 服务器之间的交互" />

从上述过程可见，客户与本地 DNS 服务器之间是**递归查询**（recursive query），而本地 DNS 服务器与根、TLD、权威服务器之间通常是**迭代查询**（iterative query）——被查询的服务器直接把下一个该问谁告诉本地 DNS 服务器，而不是替它去问。图 2.18 对比了这两种查询方式。

<Figure src="ch02/fig2-18.webp" caption="图 2.18　DNS 中的递归查询" />

DNS 广泛使用**缓存**（caching）。当某台 DNS 服务器收到一个 DNS 回答（包含主机名到 IP 地址的映射）时，它就把该映射缓存在本地存储器中。若再有对同一主机名的查询到达，该服务器可以直接提供所需的 IP 地址，即使它不是该主机名的权威服务器。由于主机名与 IP 地址之间的映射并非永久不变，DNS 服务器会在一段时间（通常两天）后丢弃缓存项。

### 2.4.3　DNS 记录和报文

实现 DNS 分布式数据库的所有 DNS 服务器共同存储**资源记录**（Resource Record, RR）。每个 DNS 回答报文包含一条或多条资源记录。资源记录是一个四元组：

(Name, Value, Type, TTL)

TTL 是该记录的生存时间，决定它何时应从缓存中删除。Name 和 Value 的含义取决于 Type：

- **Type = A**：Name 是主机名，Value 是该主机名的 IP 地址。A 记录提供标准的 DNS 映射。
- **Type = NS**：Name 是一个域（如 `foo.com`），Value 是知道如何获得该域中主机 IP 地址的权威 DNS 服务器的主机名。
- **Type = CNAME**：Value 是别名为 Name 的主机的**规范主机名**。CNAME 用于提供主机别名。
- **Type = MX**：Value 是别名为 Name 的邮件服务器的规范主机名。MX 记录允许邮件服务器使用简单别名。

若某台 DNS 服务器是某个主机名的权威服务器，则该服务器中会包含该主机名的 A 记录；若某服务器不是某主机名的权威服务器，它也可能缓存该主机名的 A 记录。

DNS 只有一种报文格式，查询报文与回答报文使用相同的格式，如图 2.19 所示。报文首部中的**标识符**字段用于匹配查询与回答；**标志**字段包含若干比特，其中"查询/回答"比特指示报文是查询还是回答，"权威"比特指示回答是否来自权威服务器，"希望递归"比特在客户希望服务器执行递归查询时置位。首部之后是四个长度可变的字段：**问题**部分包含正在被查询的名字与类型；**回答**部分包含对所查询名字的资源记录；**权威**部分包含其他权威服务器的记录；**附加信息**部分包含其他有帮助的记录（例如 MX 查询的附加部分常包含邮件服务器的 A 记录）。

<Figure src="ch02/fig2-19.webp" caption="图 2.19　DNS 报文格式" />

**向 DNS 数据库插入记录**：要把一个新域名（如 `networkutopia.com`）注册到 DNS 中，需要向某**注册登记机构**（registrar）注册。注册登记机构是一家商业实体，负责验证域名的唯一性，并把该域名输入 DNS 数据库。注册时需提供该域名的权威 DNS 服务器的主机名与 IP 地址，注册机构会把相应的 NS 与 A 记录放入 TLD 服务器。此后，任何人查询该域名时，TLD 服务器就会把查询者引向该域名的权威服务器。

## 2.5　视频流与内容分发网

本节讨论当今因特网上最流行、带宽消耗最大的一类应用：流式视频。先看因特网视频的几个关键特征，再讨论 HTTP 流式传输与 DASH，最后考察**内容分发网**（CDN）。

### 2.5.1　因特网视频

在流式视频系统中，视频被压缩并存储在服务器上，用户按需请求观看。视频是一幅幅图像（帧）以恒定速率（如每秒 24 或 30 帧）连续播放的结果，未经压缩的数字视频数据量极大，因此实际系统中视频都经过压缩。压缩后的比特率决定了视频质量与所需的网络带宽：从几百 kbps 的低清视频，到数 Mbps 的高清视频，再到十几 Mbps 以上的 4K 视频。

流式视频系统面临的一个核心挑战是**带宽的异质性**：不同用户接入速率差异巨大，且同一用户的可用带宽还会随时间波动。因此，视频系统需要能适应不同带宽的机制——这就引出了下面的 DASH。

### 2.5.2　HTTP 流式传输与 DASH

最简单的做法是让视频服务器通过 HTTP 传送整个视频文件，客户端边收边播。但这种方式有一个明显缺陷：所有客户端收到的是同一编码版本的视频，无法适应各自带宽。于是产生了 **DASH**（Dynamic Adaptive Streaming over HTTP，基于 HTTP 的动态自适应流）。

在 DASH 中，视频被编码为多个不同比特率的版本，每个版本又被切分为若干短小的**块**（chunk），每块时长通常为几秒。这些块存放在 HTTP 服务器上，每个块有一个 URL。客户端首先获取一个**告示文件**（manifest file），其中列出了各版本及其块的 URL。随后客户端周期性地测量可用带宽，并据此决定下一个要请求哪个版本的块：带宽充足时请求高比特率版本，带宽下降时切换到低比特率版本。这样，播放可以尽量不中断，同时在带宽允许时提供尽可能好的画质。

DASH 使得每个客户端可以自主地、动态地选择码率——这正是它被称为"自适应"的原因。今天几乎所有主流流媒体服务都采用 DASH 或与之类似的自适应流技术。

### 2.5.3　内容分发网

对一个流行的视频服务而言，若所有视频都存放在单一数据中心，会带来两个问题：其一，远离该数据中心的用户会经历很长的时延，且视频流量要穿越大量链路，可能造成拥塞；其二，同一视频内容会在网络上被反复传送多次，浪费带宽。

解决办法是**内容分发网**（Content Distribution Network, CDN）。CDN 的基本思想是：把内容副本存放在分布在多地的大量服务器上，使用户能从地理上或网络位置上较近的服务器获取内容。CDN 有两种主要的部署原则：

- **深入（enterprise）型**：CDN 在众多 ISP（尤其是接入 ISP）内部部署服务器集群，尽可能靠近用户。
- **邀请（ISP）型**：CDN 在少数关键位置（如 IXP 附近）部署较大的集群，通过高速链路连接。

CDN 的内容分发也有两种主要策略：

- **拉（pull）式**：CDN 服务器按需从源服务器拉取内容——当某用户首次请求某视频时，CDN 节点若没有该内容，就去源站取回并缓存。这种方式简单，适合长尾内容。
- **推（push）式**：内容提供方主动把热门内容推送到各 CDN 节点，通常在内容发布时或夜间进行。这种方式适合可预测的热门内容。

CDN 通常还利用 DNS 把用户请求重定向到"最合适"的 CDN 节点：当用户请求视频 URL 时，DNS 解析返回的可能是 CDN 的某个节点地址，而非源站地址（图 2.20）。"最合适"的判断依据包括地理距离、网络路径时延、节点负载等。

<Figure src="ch02/fig2-20.webp" caption="图 2.20　DNS 把用户请求重定向到 CDN 服务器" />

### 2.5.4　案例研究：Netflix 与 YouTube

**Netflix** 是当今最大的流媒体视频服务之一，其架构很有代表性。Netflix 自己并不拥有全球骨干网，而是：(1) 把视频内容存放在自己的服务器上，并把这些服务器部署在各地 ISP 的数据中心内（这些服务器称为 Open Connect 服务器）；(2) 使用亚马逊云（AWS）完成注册、计费、推荐、视频转码等后台功能。当用户请求某部影片时，Netflix 的软件（运行在 AWS 上）根据用户位置选择一个合适的 Open Connect 服务器，并把该服务器的地址告知客户端，客户端随后直接从该服务器以 DASH 方式拉取视频块。这样，视频流量绝大部分不经过公共因特网骨干，而是从就近的 ISP 内部服务器直接流向用户。

**YouTube**（以及国内的哔哩哔哩等）则采用另一种思路：它是世界上最大的用户生成内容（UGC）平台。YouTube 使用 Google 自己的全球私有网络和遍布各地的数据中心来分发视频，并大量使用 CDN 技术；其视频上传后需经过转码，生成多个码率版本以支持 DASH。由于内容量极其庞大且长尾特征明显，YouTube 更依赖按需拉取与缓存。

<Figure src="ch02/fig2-21.webp" caption="图 2.21　Netflix 视频流平台" />

::: tip 要点

流式视频系统的三个关键设计要素：**自适应码率**（DASH）以适应异构且波动的带宽；**内容分发网**（CDN）把内容推向网络边缘以降低时延与骨干带宽消耗；**DNS 重定向**把用户引导到最合适的服务器。三者共同构成了今天视频流的基础设施。

## 2.6　套接字编程：创建网络应用

前面各节考察了若干应用层协议，但都是"读"协议。本节换个角度：亲手**写**网络应用。我们将用 Python 编写几个简单的客户-服务器应用，从中体会应用开发者所面对的套接字接口。

在开始之前，回顾 2.1 节的几个基本概念：一个网络应用由一对通过套接字交换报文的进程构成；套接字是应用进程与运输层之间的接口，也是应用开发者所能控制的最底层"把手"。开发者可以选择使用 UDP 还是 TCP，这一选择决定了应用能获得哪些运输层服务，也决定了编写代码的方式。

### 2.6.1　UDP 套接字编程

使用 UDP 时，两个进程之间没有"连接"：发送进程把分组附上目的地址（IP 地址与端口号）后直接送入网络，接收进程从套接字中取出分组，并可从分组中得知源地址。

图 2.22 展示了一个简单的 UDP 客户-服务器应用。服务器进程先创建一个 UDP 套接字并绑定到某个端口（例如 12000），然后循环等待客户请求；客户进程创建 UDP 套接字后，直接向服务器的地址和端口发送报文，并等待应答。

<Figure src="ch02/fig2-22.webp" caption="图 2.22　使用 UDP 的客户-服务器应用" />

服务器端代码如下：

```text
# UDPServer.py
from socket import *

serverPort = 12000
serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))
print('The server is ready to receive')

while True:
    message, clientAddress = serverSocket.recvfrom(2048)
    modifiedMessage = message.decode().upper()
    serverSocket.sendto(modifiedMessage.encode(), clientAddress)
```

客户端代码如下：

```text
# UDPClient.py
from socket import *

serverName = 'hostname'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_DGRAM)
message = input('Input lowercase sentence:')
clientSocket.sendto(message.encode(), (serverName, serverPort))
modifiedMessage, serverAddress = clientSocket.recvfrom(2048)
print(modifiedMessage.decode())
clientSocket.close()
```

几点说明：`socket(AF_INET, SOCK_DGRAM)` 创建一个 UDP 套接字，`AF_INET` 表示使用 IPv4，`SOCK_DGRAM` 表示这是一个 UDP（数据报）套接字。`sendto()` 的第二个参数是目的地址二元组（主机名或 IP 地址，端口号）。`recvfrom()` 返回报文数据与源地址；注意服务器端从这个源地址中取得了客户的 IP 与端口，从而能够回送应答——这正是第 3 章将讨论的"源端口号充当回信地址"的作用。用 UDP 时，客户与服务器之间没有握手，因此若一个分组丢失，客户可能永远等不到应答。

### 2.6.2　TCP 套接字编程

使用 TCP 时，客户与服务器必须先建立连接，然后才能传输数据。TCP 提供的是**字节流**抽象：没有报文边界，应用看到的是一条连续的字节序列。

图 2.23 与图 2.24 说明了 TCP 客户-服务器应用的结构。注意一个关键区别：TCP 服务器有两个套接字——**欢迎套接字**（welcoming socket）在固定端口上等待连接请求，而 `accept()` 返回的是一个**新**套接字（连接套接字），专门用于与这个特定客户通信。这样，一个服务器进程就能同时服务多个客户。

<Figure src="ch02/fig2-23.webp" caption="图 2.23　TCPServer 进程有两个套接字" />

服务器端代码如下：

```text
# TCPServer.py
from socket import *

serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)
print('The server is ready to receive')

while True:
    connectionSocket, addr = serverSocket.accept()
    sentence = connectionSocket.recv(1024).decode()
    capitalizedSentence = sentence.upper()
    connectionSocket.send(capitalizedSentence.encode())
    connectionSocket.close()
```

客户端代码如下：

```text
# TCPClient.py
from socket import *

serverName = 'servername'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_STREAM)
clientSocket.connect((serverName, serverPort))
sentence = input('Input lowercase sentence:')
clientSocket.send(sentence.encode())
modifiedSentence = clientSocket.recv(1024)
print('From Server:', modifiedSentence.decode())
clientSocket.close()
```

注意 `SOCK_STREAM` 表示这是一个 TCP 套接字；`listen(1)` 的参数指明连接请求队列的最大长度；`connect()` 触发 TCP 三次握手。与 UDP 不同，TCP 客户不需要在每次发送时都附上目的地址——连接已经"记住"了对端。

<Figure src="ch02/fig2-24.webp" caption="图 2.24　使用 TCP 的客户-服务器应用" />

### 2.6.3　QUIC 套接字编程

如 2.2.7 节所述，QUIC 提供了一种"新的运输层"接口：开发者可以像创建 TCP、UDP 套接字那样创建 QUIC 套接字，而 QUIC 子层在内部创建一个 UDP 套接字来完成实际的分组收发。

从编程接口看，QUIC 与 TCP 的相似之处在于它同样提供可靠的、按序的**流**抽象；不同之处在于一条 QUIC 连接上可以有多条相互独立的流，且连接建立更快（通常一个 RTT，甚至 0-RTT）、默认加密。因此，编写 QUIC 应用时，开发者通常先建立一个连接，再在该连接上打开一条或多条流，在流上读写数据——这与 TCP 的"一条连接一条字节流"不同。

本节的三个例子展示了网络应用开发的基本套路：创建套接字、绑定/连接、收发数据、关闭。掌握了这套接口，你就已经可以编写自己的网络应用了。章末的套接字编程作业提供了进一步练习的机会。

## 2.7　小结

本章从应用层出发，开始自顶向下地考察计算机网络。我们首先建立了网络应用的基本原理：应用体系结构（客户-服务器与 P2P）、进程与套接字、可供应用使用的运输服务（可靠数据传输、吞吐量、定时、安全性），以及因特网实际提供的两种运输服务（TCP 与 UDP）。随后详细考察了四类重要应用：Web（HTTP）、电子邮件（SMTP、POP3、IMAP）、目录服务（DNS）和流式视频（DASH 与 CDN）。最后，通过套接字编程，我们看到了应用开发者眼中的运输层。

本章的几个要点值得反复回味：

::: tip 要点

1. **应用层协议只在端系统中实现。** 网络核心设备不运行应用层协议，这一设计把复杂性推向边缘，也使得新应用的部署无需改动网络核心——这正是因特网能够迅速催生大量新应用的根本原因。
1. **应用体系结构与网络体系结构是两回事。** 前者由开发者设计（客户-服务器、P2P），后者由协议栈规定（五层模型）。
1. **选择 TCP 还是 UDP，本质上是在选择服务模型。** TCP 提供可靠、有序、带拥塞控制的字节流；UDP 提供最小化的数据报服务，把控制权交给应用。实时应用往往偏好 UDP，可靠应用偏好 TCP，而 QUIC 则试图兼得二者。
1. **HTTP 是无状态的，Cookie 在无状态之上构建了状态。** 这一组合既保持了服务器的简单与可扩展，又满足了识别用户的需求，同时也带来了隐私争议。
1. **缓存是 Web 性能的关键。** 浏览器缓存与条件 GET（`If-Modified-Since`、`304 Not Modified`）使得大量请求无需真正传输对象。
1. **DNS 是分布式数据库的经典范例。** 层次化的服务器结构、递归与迭代查询、缓存机制，共同支撑了全球规模的名称解析。
1. **视频是当今因特网流量的主体。** DASH 解决带宽异构，CDN 解决时延与骨干带宽，二者共同构成现代流媒体的基础设施。
