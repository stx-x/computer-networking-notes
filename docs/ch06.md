前两章我们学到，网络层在任意两台网络主机之间提供通信服务。在这两台主机之间，数据报要经过一系列通信链路——有些是有线的，有些是无线的——从源主机出发，穿过一系列分组交换机（交换机和路由器），最后到达目的主机。当我们沿协议栈继续向下、从网络层走到链路层时，自然会产生这样的疑问：分组究竟如何跨过构成端到端通信路径的各条**单条链路**？网络层数据报如何被封装进链路层帧，以便在一条链路上传输？通信路径上不同的链路是否使用不同的链路层协议？广播链路上的传输冲突如何解决？链路层有编址吗——如果有，链路层编址与我们第 4 章学过的网络层编址如何配合？交换机与路由器究竟有什么不同？本章将回答这些以及其他重要问题。

讨论链路层时会看到，链路层信道有两大类，性质根本不同。第一类是**广播信道**（broadcast channel），它把多台主机连接在无线局域网、卫星网络以及混合光纤同轴电缆（HFC）接入网中。由于许多主机连在同一条广播通信信道上，就需要一种所谓的**介质访问协议**来协调帧的传输。有些情况下可以用一个中心控制器来协调传输，另一些情况下则由各主机自行协调。第二类是**点对点通信链路**（point-to-point communication link），例如由一条长途链路连接的两台路由器之间常见的那种，或者用户办公室的计算机与其附近的以太网交换机之间的那种。协调对点对点链路的访问要简单一些；本书网站上的参考资料详细讨论了点对点协议（PPP），它被用于从电话线上的拨号服务到光纤链路上的高速点对点帧传输等各种场合。

本章将探讨若干重要的链路层概念与技术：深入讨论差错检测与纠正（第 3 章曾简要提及）；考察多路访问网络与交换式局域网，包括以太网——它是迄今最普遍的有线局域网技术；还会看虚拟局域网与数据中心网络。WiFi（更一般地说是无线局域网）虽然也属于链路层话题，但我们把这些重要内容推迟到第 7 章。

## 6.1　链路层导论

先讲几个重要的术语。本章中，我们把任何运行链路层（即第 2 层）协议的设备都称为**节点**（node）。节点包括主机、路由器、交换机以及 WiFi 接入点（第 7 章讨论）。我们把沿通信路径连接相邻节点的通信信道称为**链路**（link）。一个数据报要从源主机传送到目的主机，就必须沿着端到端路径上的每一条链路被移动一次。以图 6.1 底部所示公司网络为例，考虑从一个无线主机向某台服务器发送数据报：这个数据报实际上要经过六条链路——发送主机与 WiFi 接入点之间的 WiFi 链路，接入点与一台链路层交换机之间的以太网链路，链路层交换机与路由器之间的链路，两台路由器之间的链路，路由器与一台链路层交换机之间的以太网链路，最后是交换机与服务器之间的以太网链路。在一条给定链路上，发送节点把数据报封装进一个**链路层帧**，并把该帧发送到链路中。

<Figure src="ch06/fig6-01.webp" caption="图 6.1　无线主机与服务器之间的六次链路层跳" />

为进一步理解链路层及其与网络层的关系，考虑一个运输类比。一位旅行社代理正在为一名游客规划从新泽西州普林斯顿到瑞士洛桑的行程。代理判定最方便的方式是：游客先乘豪华轿车从普林斯顿到肯尼迪机场，再从肯尼迪机场乘飞机到日内瓦机场，最后从日内瓦机场乘火车到洛桑火车站。一旦代理订好这三段行程，把游客从普林斯顿送到肯尼迪机场就是普林斯顿那家轿车公司的责任；把游客从肯尼迪机场送到日内瓦是航空公司的责任；把游客从日内瓦送到洛桑是瑞士铁路的责任。行程的这三段，每一段都是在两个"相邻"地点之间的"直达"运输。注意这三段运输由不同公司经营，使用完全不同的运输方式（轿车、飞机、火车）。尽管运输方式不同，它们都提供把旅客从一个地点送到相邻地点这一基本服务。在这个运输类比中，游客就是数据报，每一段运输就是一条链路，运输方式就是链路层协议，而旅行社代理就是路由协议。

### 6.1.1　链路层提供的服务

尽管任何链路层的基本服务都是把数据报沿一条通信链路从一个节点移动到相邻节点，但所提供服务的细节因链路层协议而异。链路层协议可能提供的服务包括：

- **成帧**（framing）。几乎所有链路层协议都在把网络层数据报经链路传输之前，把它封装进一个链路层帧。一个帧由一个**数据字段**（网络层数据报被放入其中）和若干**首部字段**组成。帧的结构由链路层协议规定。本章后半部分考察具体链路层协议时会看到几种不同的帧格式。
- **链路接入**（link access）。**介质访问控制**（MAC）协议规定帧如何被发送到链路上的规则。对于一端只有一个发送方、另一端只有一个接收方的点对点链路，MAC 协议很简单（甚至不存在）——链路空闲时发送方就可以发帧。更有意思的情形是多个节点共享同一条广播链路，即所谓的**多路访问问题**。这时 MAC 协议的作用是协调众多节点的帧传输。
- **可靠交付**（reliable delivery）。当链路层协议提供可靠交付服务时，它保证把每个网络层数据报无差错地送过该链路。回忆某些运输层协议（如 TCP）也提供可靠交付服务。与运输层的可靠交付类似，链路层的可靠交付也可以用确认与重传实现（见 3.4 节）。链路层可靠交付常用于误码率高的链路（如无线链路），其目标是在**本地**——在差错发生的链路上——纠正差错，而不是迫使运输层或应用层协议做端到端重传。不过对于低误码链路（包括光纤、同轴电缆以及许多双绞铜线链路），链路层可靠交付可以被视为不必要的开销。因此，许多有线链路层协议并不提供可靠交付服务。
- **差错检测与纠正**（error detection and correction）。接收节点中的链路层硬件可能把帧中某个本应传输为 1 的比特错误地判为 0，反之亦然。这类比特差错由信号衰减与电磁噪声引入。由于转发一个已有差错的数据报毫无意义，许多链路层协议提供检测这类比特差错的机制：发送节点在帧中包含**差错检测比特**，接收节点执行差错检查。回忆第 3、4 章：因特网的运输层与网络层也提供有限形式的差错检测——因特网校验和。链路层的差错检测通常更精巧，并且用硬件实现。**差错纠正**与差错检测类似，只是接收方不仅检测帧中是否发生了比特差错，还要确定差错在帧中的确切位置（然后纠正这些差错）。

### 6.1.2　链路层实现在哪里？

在深入细致地研究链路层之前，先以一个问题结束本节导论：链路层实现在哪里？主机的链路层是用硬件还是软件实现的？它实现在一块独立的卡或芯片上吗？它如何与主机其余的硬件和操作系统组件接口？

图 6.2 展示了一个典型的主机体系结构。以太网功能要么集成在主板芯片组中，要么通过一块低成本的专用以太网芯片实现。大体上说，链路层实现在一块称为**网络适配器**（network adapter）的芯片上，它有时也称为**网络接口控制器**（NIC）。网络适配器实现许多链路层服务，包括成帧、链路接入、差错检测等。因此，链路层控制器的大部分功能是用硬件实现的。例如，Intel 的 800 系列适配器 [Intel 2025] 实现了我们将在 6.4 节研究的以太网协议；Atheros Fastconnect 6800 子系统 [Qualcomm 2025] 的控制器实现了我们将在第 7 章研究的 802.11 协议。

<Figure src="ch06/fig6-02.webp" caption="图 6.2　网络适配器：它与其他主机组件以及与协议栈功能的关系" />

在发送侧，控制器取出由协议栈较高层创建并存储在主机内存中的数据报，把它封装进一个链路层帧（填好帧的各个字段），然后按链路接入协议把该帧发送到通信链路中。在接收侧，控制器接收整个帧并取出网络层数据报。如果链路层执行差错检测，那么是发送控制器在帧首部中设置差错检测比特，是接收控制器执行差错检测。

图 6.2 还显示：链路层的大部分虽然用硬件实现，但有一部分是用运行在主机 CPU 上的软件实现的。链路层的软件组件实现较高层的链路层功能，例如装配链路层编址信息、激活控制器硬件。在接收侧，链路层软件响应控制器中断（例如由于收到一个或多个帧），处理差错状况并把数据报上交网络层。因此，链路层是硬件与软件的结合——是协议栈中软件与硬件相遇的地方。

## 6.2　差错检测与纠正技术

上一节提到，比特级差错检测与纠正——检测并纠正从一个节点发往物理上相邻节点的链路层帧中比特的损坏——是链路层常提供的两项服务。第 3 章也看到，运输层同样常提供差错检测与纠正服务。本节考察几种最简单的、可用于检测（有时还能纠正）这类比特差错的技术。这个主题的理论与实现足以写成多本教材（例如 [Schwartz 1980] 或 [Bertsekas 1991]），因此这里的处理只能简短。我们的目标是建立对差错检测与纠正技术能力的直观感觉，并看看几种简单技术如何工作、如何在链路层实践中使用。

图 6.3 说明了研究的场景。在发送节点，要防止比特差错的数据 $D$ 被附加**差错检测与纠正比特** $\text{EDC}$。通常，受保护的数据不仅包括从网络层下交、要经链路传输的数据报，还包括链路层编址信息、序号以及链路帧首部中的其他字段。$D$ 与 $\text{EDC}$ 一起装在链路层帧中发送给接收节点。在接收节点，收到的是比特序列 $D '$ 与 $\text{EDC} '$。注意，由于传输途中的比特翻转，$D '$ 与 $\text{EDC} '$ 可能与原来的 $D$ 与 $\text{EDC}$ 不同。

<Figure src="ch06/fig6-03.webp" caption="图 6.3　差错检测与纠正场景" />

接收方的挑战是：在只收到 $D '$ 与 $\text{EDC} '$ 的情况下，判断 $D '$ 是否与原来的 $D$ 相同。图 6.3 中接收方判决的措辞很重要——我们问的是"**是否检测到差错**"，而不是"**是否发生了差错**"！差错检测与纠正技术使接收方有时（但并非总能）检测出发生了比特差错。即使使用了差错检测比特，仍可能存在**未检测到的比特差错**，即接收方可能并不知道收到的信息含有比特差错。其后果是，接收方可能把一个已损坏的数据报交给网络层，或者不知道帧首部中某个字段的内容已被损坏。因此我们希望选择一种使这类情形发生概率很小的差错检测方案。一般来说，更精巧的差错检测与纠正技术（即让未检测到的比特差错概率更小的技术）会带来更大的开销——需要更多计算，并要传输更多的差错检测与纠正比特。

下面考察三种检测传输数据差错的技术：奇偶校验（用以说明差错检测与纠正背后的基本思想）、校验和方法（更常用于运输层）以及循环冗余检测（更常用于适配器中的链路层）。

### 6.2.1　奇偶校验

也许最简单的差错检测形式是使用单个**奇偶校验位**。假设要发送的信息（图 6.4 中的 $D$）有 $d$ 个比特。在**偶校验**（even parity）方案中，发送方只需额外包含一个比特，并选择其值使得这 $d + 1$ 个比特（原信息加一个校验位）中 1 的总数为偶数。对于**奇校验**（odd parity）方案，则选择校验位的值使得 1 的个数为奇数。图 6.4 展示了一个偶校验方案，其中单个校验位存放在一个单独的字段中。

<Figure src="ch06/fig6-04.webp" caption="图 6.4　单比特偶校验" />

使用单个校验位时，接收方的操作也很简单：只需数一数收到的 $d + 1$ 个比特中 1 的个数。若采用偶校验方案却数出奇数个 1，接收方就知道至少发生了一个比特差错——更准确地说，它知道发生了奇数个比特差错。

但如果发生了**偶数个**比特差错呢？你应该说服自己：这会导致一个未检测到的差错。如果比特差错概率很小，并且可以假定差错在各比特之间独立发生，那么一个分组中出现多个比特差错的概率会极小，此时单个校验位也许就够了。然而测量表明，差错往往并非独立发生，而是成簇地以"突发"（burst）形式出现。在突发差错条件下，受单比特奇偶校验保护的帧中未检测出差错的概率可以接近 50% [Spragins 1991]。显然，需要一种更健壮的差错检测方案（幸运的是，实践中确实用了！）。不过在考察实践中使用的差错检测方案之前，先看单比特奇偶校验的一个简单推广，它会让我们对差错**纠正**技术有所领悟。

图 6.5 展示了单比特奇偶校验方案的二维推广。这里把 $D$ 中的 $d$ 个比特排成 $i$ 行 $j$ 列，为每一行和每一列各计算一个奇偶校验值。得到的 $i + j + 1$ 个校验位构成链路层帧的差错检测比特。

<Figure src="ch06/fig6-05.webp" caption="图 6.5　二维偶校验" />

现在假设原始 $d$ 个信息比特中发生了一个比特差错。在这个二维奇偶校验方案下，包含该翻转比特的那一列和那一行的校验都会出错。于是接收方不仅能检测出发生了单个比特差错，还能利用出错行与出错列的索引，**确切地指出**是哪个比特被损坏，并纠正该差错！图 6.5 给出了一个例子：位置 $(2, 2)$ 处值为 1 的比特被损坏、变成了 0——这个差错在接收方既可以被检测出，也可以被纠正。虽然我们的讨论聚焦于原始 $d$ 个信息比特，但校验位自身发生的单个差错同样可以被检测并纠正。二维奇偶校验还能检测（但**不能**纠正！）一个分组中任意两个差错的组合。二维奇偶校验方案的其他性质在本章末的习题中探讨。

接收方既检测又纠正差错的能力称为**前向纠错**（forward error correction，FEC）。这类技术常用于音频存储与播放设备，如音频 CD。在网络环境中，FEC 技术可以单独使用，也可以与类似于第 3 章考察的链路层 ARQ 技术结合使用。FEC 技术的价值在于可以减少所需的发送方重传次数。也许更重要的是，它们能在接收方立即纠正差错，从而不必等待"发送方收到 NAK 分组"所需的往返传播时延，也不必等待重传分组再传播回接收方——这对实时网络应用 [Rubenstein 1998] 或传播时延很长的链路（如深空链路）是一个可能很重要的优势。关于在差错控制协议中使用 FEC 的研究包括 [Biersack 1992; Nonnenmacher 1998; Byers 1998; Shacham 1990]。

### 6.2.2　校验和方法

在校验和技术中，图 6.4 中的 $d$ 个数据比特被当作 $k$ 比特整数的序列来处理。一种简单的校验和方法是把这些 $k$ 比特整数直接相加，用所得之和作为差错检测比特。**因特网校验和**就基于这种途径——数据字节被当作 16 比特整数相加，该和的**反码**（1s complement）构成报文段首部中携带的因特网校验和。如 3.3 节所述，接收方对收到的数据（包括校验和）求反码和，检查结果是否全为 1 比特；若有任何一位为 0，就表明有差错。RFC 1071 详细讨论了因特网校验和算法及其实现。在 TCP 与 UDP 协议中，因特网校验和是对所有字段（包括首部字段与数据字段）计算的；在 IP 中，校验和只对 IP 首部计算（因为 UDP 或 TCP 报文段有自己的校验和）。在另一些协议中，例如 XTP [Strayer 1992]，一个校验和对首部计算，另一个校验和对整个分组计算。

校验和方法所需的分组开销相对较小。例如 TCP 与 UDP 中的校验和只用了 16 比特。但与下面要讨论的、链路层常用的循环冗余检测相比，它们提供的差错保护相对较弱。这里一个自然的问题是：**为什么运输层用校验和，而链路层用循环冗余检测？**回忆运输层通常作为主机操作系统的一部分用**软件**实现。既然运输层的差错检测用软件实现，那么拥有一种简单快速的差错检测方案（如校验和）就很重要。另一方面，链路层的差错检测是在适配器的**专用硬件**中实现的，硬件可以快速执行更复杂的 CRC 运算。Feldmeier [Feldmeier 1995] 给出了加权校验码以及 CRC（见下文）和其他编码的快速软件实现技术。

### 6.2.3　循环冗余检测（CRC）

当今计算机网络中广泛使用的一种差错检测技术基于**循环冗余检测**（CRC）码。CRC 码也称为**多项式码**，因为可以把要发送的比特串看成一个多项式，其系数就是比特串中的 0、1 值，而对比特串的运算可以解释为多项式运算。

CRC 码的工作方式如下。考虑发送节点要发给接收节点的 $d$ 比特数据 $D$。发送方与接收方必须首先商定一个 $r + 1$ 比特的图案，称为**生成多项式**（generator），记为 $G$。我们要求 $G$ 的最高位（最左位）为 1。CRC 码的关键思想如图 6.6 所示。对给定数据 $D$，发送方选择 $r$ 个附加比特 $R$，把它们附加在 $D$ 之后，使得得到的 $d + r$ 比特图案（解释为一个二进制数）用**模 2 运算**恰好能被 $G$ 整除（即余数为零）。于是用 CRC 做差错检查的过程很简单：接收方把收到的 $d + r$ 个比特除以 $G$；若余数非零，接收方就知道发生了差错；否则就认为数据是正确的。

<Figure src="ch06/fig6-06.webp" caption="图 6.6　CRC" />

所有 CRC 计算都在**模 2 运算**下进行：加法不进位，减法不借位。这意味着加法与减法完全相同，且都等价于操作数的按位**异或**（XOR）。因此，例如

```text
1011 XOR 0101 = 1110
1001 XOR 1101 = 0100
```

同样也有

```text
1011 − 0101 = 1110
1001 − 1101 = 0100
```

乘除法与二进制算术相同，只是所需的加减都不进位、不借位。与普通二进制算术一样，乘以 $2^{k}$ 就是把比特图案左移 $k$ 位。因此，给定 $D$ 与 $R$，量 $D \cdot 2^{r} \text{XOR} R$ 就得到图 6.6 所示的 $d + r$ 比特图案。下文我们将使用图 6.6 中这个 $d + r$ 比特图案的代数刻画。

现在来看关键问题：发送方如何计算 $R$？回忆我们要找 $R$，使得存在某个 $n$ 满足

$$
D \cdot 2^{r} \text{XOR} R = n G
$$

也就是说，我们要选择 $R$，使 $G$ 能整除 $D \cdot 2^{r} \text{XOR} R$ 而无余数。若把 $R$ 异或（即模 2 相加，不进位）到上式两边，得到

$$
D \cdot 2^{r} = n G \text{XOR} R
$$

这个式子告诉我们：若用 $G$ 去除 $D \cdot 2^{r}$，余数恰好就是 $R$。换句话说，$R$ 可以这样计算：

$$
R = \text{remainder} \frac{D \cdot 2^{r}}{G}
$$

图 6.7 以 $D = 101110$、$d = 6$、$G = 1001$、$r = 3$ 为例说明了这个计算。此例中发送的 9 个比特是 `101 110 011`。你应当自己核对这些计算，并核对确实有 $D \cdot 2^{r} \text{XOR} R = 101011 \cdot G$。

<Figure src="ch06/fig6-07.webp" caption="图 6.7　一个 CRC 计算示例" />

国际标准已为 8、12、16 与 32 比特的生成多项式 $G$ 作出规定。CRC-32 这个 32 比特标准已被若干 IEEE 链路层协议采用，它使用的生成多项式为

```text
CRC-32
```

每种 CRC 标准都能检测长度小于 $r + 1$ 比特的突发差错（这意味着所有连续 $r$ 比特或更少的比特差错都会被检测出来）。此外，在适当假设下，长度大于 $r + 1$ 比特的突发被检测出的概率为 $1 - 0.5^{r}$。每种 CRC 标准还能检测任意奇数个比特差错。关于实现 CRC 校验的讨论见 [Williams 1993]。CRC 码乃至更强大的编码背后的理论超出本书范围；[Schwartz 1980] 对该主题作了出色的入门介绍。

## 6.3　多路访问链路与协议

本章导论中提到，网络链路有两类：点对点链路与广播链路。**点对点链路**由链路一端的单个发送方和另一端的单个接收方组成。许多链路层协议是为点对点链路设计的，点对点协议（PPP）与高级数据链路控制（HDLC）就是两个这样的协议。第二类链路是**广播链路**，它可以有多个发送节点与接收节点，全部连接到同一条共享的广播信道上。这里用"广播"一词，是因为当任何一个节点发送帧时，信道会广播该帧，其他每个节点都收到一份拷贝。以太网与无线局域网就是广播链路层技术的例子。本节先暂时离开具体的链路层协议，考察一个对链路层至关重要的问题：如何协调多个发送与接收节点对共享广播信道的访问——即**多路访问问题**。广播信道常用于局域网（LAN），即在地理上集中于一座建筑（或一个公司、大学校园）内的网络。因此本节末尾会看多路访问信道在局域网中如何使用。

<Figure src="ch06/fig6-08.webp" caption="图 6.8　多种多路访问信道" />

我们都熟悉"广播"这个概念——电视自发明以来一直在用。但传统电视是单向广播（一个固定节点向许多接收节点发送），而计算机网络广播信道上的节点既能发送也能接收。也许更贴切的人类类比是**鸡尾酒会**：许多人聚在一个大房间里（空气提供广播介质）交谈与倾听。第二个好类比是许多读者都熟悉的**课堂**：老师与学生同样共享同一条广播介质。这两种场景的核心问题都是：确定谁能在什么时候讲话（即向信道发送）。作为人类，我们已经演化出一套精巧的共享广播信道的"协议"：

"给每个人说话的机会。"\
    "别人没跟你说话之前别开口。"\
    "不要独占谈话。"\
    "有问题就举手。"\
    "别人讲话时不要打断。"\
    "别人讲话时别睡着。"

计算机网络同样有协议——即所谓的**多路访问协议**——各节点据此调节自己向共享广播信道的发送。如图 6.8 所示，多路访问协议在有线与无线接入网以及卫星网络等各种网络环境中都是必需的。虽然从技术上说每个节点是通过其适配器访问广播信道的，但本节我们把节点直接称为发送与接收设备。实践中，数百甚至数千个节点可以直接在一条广播信道上通信。

由于所有节点都能发送帧，两个以上节点可能同时发送帧。这时所有节点会同时收到多个帧，也就是说，所发送的帧在**所有**接收方处**冲突**（collide）。通常发生冲突时，没有任何接收节点能理解所传输的任何帧——某种意义上，冲突各帧的信号纠缠在一起、无法分开。于是冲突涉及的所有帧都丢失，广播信道在冲突期间被浪费。显然，如果许多节点频繁地想发送帧，就会有很多传输发生冲突，广播信道的大部分带宽将被浪费。

为确保多个节点活跃时广播信道仍能做有用功，必须以某种方式协调活跃节点的传输。这项协调工作是**多路访问协议**的职责。过去 50 年间，关于多路访问协议的论文数以千计、博士论文数以百计；对这一领域前 20 年工作的综述见 [Rom 1990]。此外，由于新型链路（尤其是新型无线链路）不断涌现，多路访问协议的活跃研究仍在继续。

多年来，已有数十种多路访问协议在各种链路层技术中实现。不过，几乎任何多路访问协议都可以归入三类之一：**信道划分协议**、**随机接入协议**与**轮流协议**。下面三小节分别讨论这三类。

在结束这个概述之前，先指出：理想情况下，速率为 $R$ bit/s 的广播信道的多路访问协议应具备以下良好特性：

1. 当只有一个节点有数据要发送时，该节点的吞吐量为 $R$ bit/s。
1. 当有 $M$ 个节点有数据要发送时，每个节点的吞吐量为 $\frac{R}{M}$ bit/s。这并不一定意味着这 $M$ 个节点在每一瞬间都有 $\frac{R}{M}$ 的速率，而是说在某个适当定义的时间区间内，每个节点的**平均**传输速率应为 $\frac{R}{M}$。
1. 协议是分散的，即没有作为网络单点故障的集中控制节点。
1. 协议简单，因而实现成本低。

### 6.3.1　信道划分协议

回忆 1.3 节的早期讨论：**时分多路复用**（TDM）与**频分多路复用**（FDM）是两种可用来在共享信道的所有节点之间划分广播信道带宽的技术。举例来说，假设信道支持 $N$ 个节点，信道传输速率为 $R$ bit/s。TDM 把时间划分为**时帧**，再把每个时帧划分为 $N$ 个**时隙**。（不要把 TDM 的时帧与链路层在发送与接收适配器之间交换的数据单元混淆，后者也称为"帧"。为减少混淆，本小节把链路层交换的数据单元称为**分组**。）每个时隙随后分配给 $N$ 个节点之一。每当某节点有分组要发送，它就在循环的 TDM 帧中自己分到的时隙内发送该分组的比特。通常时隙大小选得刚好能发送一个分组。图 6.9 展示了一个简单的四节点 TDM 例子。回到鸡尾酒会类比，TDM 规范的酒会会允许一位客人讲一段固定时长，然后让另一位客人讲同样长的时间，如此继续；等每个人都轮到一次后，这一模式重复。

<Figure src="ch06/fig6-09.webp" caption="图 6.9　四节点 TDM 与 FDM 示例" />

TDM 有吸引力，是因为它消除了冲突并且完全公平：每个节点在每个帧时间内获得专用的 $\frac{R}{N}$ bit/s 传输速率。然而它有两个主要缺点。第一，即使某节点是唯一有分组要发的节点，它的平均速率也被限制在 $\frac{R}{N}$ bit/s。第二，节点必须总是等待轮到自己发送——同样，即使它是唯一有帧要发的节点。想象那位唯一有话要说的酒会客人（再想象这是更罕见的情形：所有人都想听这个人说）。显然，对这场特定的酒会来说，TDM 会是个糟糕的多路访问协议选择。

TDM 在**时间**上共享广播信道，FDM 则把 $R$ bit/s 的信道划分为不同**频率**（每个带宽为 $\frac{R}{N}$），并把每个频率分配给 $N$ 个节点之一。于是 FDM 从单条较大的 $R$ bit/s 信道中造出 $N$ 条 $\frac{R}{N}$ bit/s 的较小信道。FDM 兼具 TDM 的优点与缺点：它避免冲突，在 $N$ 个节点间公平划分带宽；但它与 TDM 共有同一个主要缺点——即使某节点是唯一有分组要发的节点，其带宽也被限制在 $\frac{R}{N}$。TDM 与 FDM 技术广泛用于我们将在第 7 章研究的蜂窝、WiFi、蓝牙与卫星系统，两者也都用于电缆接入网，本章后面会看到。

第三种信道划分协议是**码分多址**（CDMA）。TDM 与 FDM 分别给节点分配时隙与频率，而 CDMA 给每个节点分配**不同的码**，每个节点用自己独有的码对要发送的数据比特编码。如果码选得仔细，CDMA 网络有一个美妙性质：不同节点可以同时发送，而各自的接收方（在知道发送方码的前提下）仍能正确收到某个发送方编码后的数据比特，尽管存在其他节点的干扰传输。CDMA 是 3G 蜂窝网络的基础技术，但在 4G 与 5G 网络中被其他技术取代。关于 CDMA 的讲解见本书早期版本的第 7 章。

### 6.3.2　随机接入协议

第二大类多路访问协议是**随机接入协议**。在随机接入协议中，发送节点总是以信道的全速率 $R$ bit/s 发送。当发生冲突时，卷入冲突的每个节点反复重传其帧（即分组），直到该帧无冲突地通过为止。但节点遇到冲突时不一定立刻重传，而是先等待一个**随机时延**再重传。卷入冲突的每个节点独立选择随机时延。由于时延是独立选择的，有可能某个节点选到的时延比其他冲突节点短得多，从而能把它的帧"偷偷"送进信道而不发生冲突。

文献中描述的随机接入协议即使没有几百种也有几十种 [Rom 1990; Bertsekas 1991]。本节介绍几种最著名的随机接入协议——ALOHA 协议 [Abramson 1970; Abramson 1985; Abramson 2009] 与**载波侦听多路访问**（CSMA）协议 [Kleinrock 1975b]。以太网 [Metcalfe 1976] 是一种流行且广泛部署的 CSMA 协议。第 7 章将讨论随机接入在 WiFi 的 CSMA/CA 协议中的使用。

#### 时隙 ALOHA

先从最简单的随机接入协议之一——**时隙 ALOHA**（slotted ALOHA）——开始。描述时隙 ALOHA 时作如下假设：

- 所有帧恰好由 $L$ 个比特组成。
- 时间被划分为大小为 $\frac{L}{R}$ 秒的时隙（即一个时隙等于传输一帧所需的时间）。
- 节点只在时隙起点开始发送帧。
- 节点是同步的，因此每个节点都知道时隙何时开始。
- 若一个时隙内有两个或更多帧冲突，则所有节点在该时隙结束前都能检测到冲突事件。

设 $p$ 是一个概率，即 0 到 1 之间的数。时隙 ALOHA 在每个节点中的运行很简单：

- 当节点有一个新帧要发送时，它等到下一个时隙开始，并在该时隙中发送整个帧。
- 若没有冲突，该节点就成功发送了帧，因而不必考虑重传（若有新帧，可以准备发送新帧）。
- 若有冲突，节点会在时隙结束前检测到冲突。此后它在每个后续时隙中以概率 $p$ 重传该帧，直到该帧无冲突地传输成功。

"以概率 $p$ 重传"是指节点实际上抛一枚有偏的硬币：正面表示"重传"，概率为 $p$；反面表示"跳过该时隙、下一时隙再抛"，概率为 $1 - p$。所有卷入冲突的节点独立抛各自的硬币。

时隙 ALOHA 似乎有许多优点。与信道划分不同，当某节点是唯一活跃节点（有帧要发送的节点称为**活跃**节点）时，时隙 ALOHA 允许它以全速率 $R$ 连续发送。时隙 ALOHA 也是高度分散的，因为每个节点自行检测冲突并独立决定何时重传。（不过时隙 ALOHA 要求各节点同步时隙；稍后会讨论不需要这种同步的非时隙 ALOHA 以及 CSMA 协议。）时隙 ALOHA 还是一个极其简单的协议。

只有一个活跃节点时，时隙 ALOHA 工作得很好；但有多个活跃节点时效率如何？这里有两个可能的效率问题。第一，如图 6.10 所示，有多个活跃节点时，总有一部分时隙会发生冲突，因而被"浪费"。第二，还有另一部分时隙会是空的，因为按概率发送策略，所有活跃节点都恰好没发。唯一"不被浪费"的时隙，是恰好有一个节点发送的时隙。恰好一个节点发送的时隙称为**成功时隙**。时隙多路访问协议的**效率**定义为：在大量活跃节点、每个节点总有大量帧要发送的情况下，成功时隙所占的长期比例。注意，如果不用任何形式的接入控制、每个节点在每次冲突后立即重传，效率将为零。时隙 ALOHA 显然把效率提高到了零以上，但提高了多少？

<Figure src="ch06/fig6-10.webp" caption="图 6.10　节点 1、2、3 在第一个时隙冲突。节点 2 最终在第四个时隙成功，节点 1 在第八个时隙成功，节点 3 在第九个时隙成功" />

下面给出时隙 ALOHA 最大效率的推导梗概。为使推导简单，把协议稍作修改，假设每个节点在每个时隙以概率 $p$ 尝试发送一帧（即假设每个节点总有帧要发，且无论新帧还是已冲突过的帧都以概率 $p$ 发送）。设有 $N$ 个节点，则某个给定时隙是成功时隙的概率，等于"一个节点发送、其余 $N - 1$ 个节点不发送"的概率。某个给定节点发送的概率为 $p$，其余节点不发送的概率为 $(1 - p)^{N - 1}$。因此某个给定节点成功的概率为 $p(1 - p)^{N - 1}$。由于共有 $N$ 个节点，$N$ 个节点中任一个成功的概率为

$$
N p(1 - p)^{N - 1}
$$

因此，有 $N$ 个活跃节点时，时隙 ALOHA 的效率为 $N p(1 - p)^{N - 1}$。要得到 $N$ 个活跃节点下的最大效率，需找出使该式最大的 $p^{*}$（推导思路见章末习题）。而要得到大量活跃节点下的最大效率，则取 $N p^{*}(1 - p^{*})^{N - 1}$ 在 $N$ 趋于无穷时的极限（同样见章末习题）。完成这些计算后会得到：协议的最大效率为

$$
\frac{1}{e} \approx 0.37
$$

也就是说，当大量节点有许多帧要发送时，（最好情况下）只有 37% 的时隙在做有用功。于是信道的有效传输速率不是 $R$ bit/s，而只有 $0.37 R$ bit/s！类似分析还表明，37% 的时隙是空的，26% 的时隙发生冲突。想象那位可怜的网络管理员，他买了一台 100 Mbit/s 的时隙 ALOHA 系统，期望能以比如 80 Mbit/s 的总速率在大量用户之间传输数据！虽然信道能够以 100 Mbit/s 的全速率发送某一帧，但长期看这条信道的成功吞吐量不到 37 Mbit/s。

#### ALOHA

时隙 ALOHA 协议要求所有节点把发送同步到时隙起点。最早的 ALOHA 协议 [Abramson 1970] 其实是一个非时隙的、完全分散的协议。在**纯 ALOHA** 中，当一个帧首次到达时（即网络层把一个数据报下交给发送节点），节点立即把该帧完整地发送到广播信道中。若发送的帧与一个或多个其他传输发生冲突，节点随后（在完整发送完其冲突帧之后）立即以概率 $p$ 重传该帧；否则节点等待一个帧传输时间，之后再以概率 $p$ 发送该帧，或以概率 $1 - p$ 再空闲等待一个帧时间。

为确定纯 ALOHA 的最大效率，我们聚焦于单个节点。作与时隙 ALOHA 分析相同的假设，并把帧传输时间取为时间单位。在任意给定时刻，某节点正在发送帧的概率为 $p$。假设该帧在时刻 $t_{0}$ 开始发送。如图 6.11 所示，要使该帧成功传输，在时间区间 $[t_{0} - 1, t_{0}]$ 内不能有其他节点开始发送——那样的传输会与该节点帧发送的开头部分重叠。所有其他节点都不在该区间内开始发送的概率为 $(1 - p)^{N - 1}$。类似地，在节点 $i$ 发送期间也不能有其他节点开始发送，因为那样的传输会与节点 $i$ 帧发送的后半部分重叠；所有其他节点都不在该区间内开始发送的概率同样是 $(1 - p)^{N - 1}$。因此某个给定节点成功传输的概率为 $p(1 - p)^{2(N - 1)}$。与时隙 ALOHA 一样取极限，我们发现纯 ALOHA 协议的最大效率仅为

$$
\frac{1}{2 e} \approx 0.18
$$

恰好是时隙 ALOHA 的一半。这就是为"完全分散的 ALOHA 协议"付出的代价。

#### 载波侦听多路访问（CSMA）

在时隙 ALOHA 与纯 ALOHA 中，节点决定是否发送时并不理会广播信道上其他节点的活动。特别地，节点开始发送时既不去听是否有别的节点恰好在发送，也不在别的节点开始干扰其传输时停止发送。用鸡尾酒会类比，ALOHA 协议很像一位粗鲁的客人，不管别人是否在说话都喋喋不休。作为人类，我们有"人际协议"，不仅能让我们举止更文明，还能减少彼此"对话冲突"的时间，从而增加交流的信息量。具体地说，礼貌的人类交谈有两条重要规则：

- **先听后说**。如果别人正在说话，就等他说完。在网络世界里这称为**载波侦听**（carrier sensing）——节点在发送前侦听信道。如果当前有别的节点正在向信道发送帧，节点就等到检测到一小段时间内没有传输，然后开始发送。
- **若有人同时开口，就停止说话**。在网络世界里这称为**冲突检测**（collision detection）——发送节点在发送的同时侦听信道。若检测到另一节点正在发送干扰帧，它就停止发送，等待一段随机时间后重复"先听后说、空闲即发"的循环。

这两条规则体现在**载波侦听多路访问**（CSMA）与**带冲突检测的载波侦听多路访问**（CSMA/CD）这一族协议中 [Kleinrock 1975b; Metcalfe 1976; Lam 1980; Rom 1990]。人们提出了 CSMA 与 CSMA/CD 的许多变体。这里考察其中一些最重要、最基本的特征。

Norm Abramson 是一位工学博士，酷爱冲浪，也对分组交换感兴趣。这两种兴趣的结合把他带到了夏威夷大学（1969 年）。夏威夷由许多多山的岛屿组成，安装和运营陆基网络很困难。不冲浪的时候，Abramson 就在琢磨如何设计一个用无线电做分组交换的网络。他设计的网络有一个中心主机和若干散布在夏威夷各岛上的从节点，使用两个信道、各占一个频段：下行信道把分组从中心主机广播给各从主机；上行信道把分组从从主机送往中心主机。除发送信息分组外，中心主机还在下行信道上为每个成功收到的来自从主机的分组发送确认。

由于从主机以分散方式发送分组，上行信道不可避免地会发生冲突。这一观察促使 Abramson 设计了本章所述的纯 ALOHA 协议。1970 年，在 ARPA 的持续资助下，Abramson 把他的 ALOHAnet 接入了 ARPAnet。ALOHAnet 的历史见 [Schwartz 2009]。Abramson 的工作之所以重要，不仅因为它是无线电分组网络的第一个实例，还因为它启发了 Bob Metcalfe——几年后，Metcalfe 修改 ALOHA 协议，创造了 CSMA/CD 协议与以太网局域网。

关于 CSMA，你可能首先会问：既然所有节点都做载波侦听，那冲突究竟为什么还会发生？毕竟节点一旦侦听到别的节点在发送就不会发送。这个问题最好用**时空图**（space-time diagram）来说明 [Molle 1987]。图 6.12 给出了连接在一条线性广播总线上四个节点（A、B、C、D）的时空图：横轴表示各节点在空间中的位置，纵轴表示时间。

在时刻 $t_{0}$，节点 B 侦听到信道空闲（当前没有别的节点在发送），于是开始发送，其比特沿广播介质向两个方向传播。图 6.12 中 B 的比特随时间向下传播，说明 B 的比特沿广播介质传播实际需要非零时间（尽管接近光速）。在时刻 $t_{1}$（$t_{1} > t_{0}$），节点 D 有帧要发。虽然 $t_{1}$ 时刻节点 B 正在发送，但 B 发出的比特尚未到达 D，因此 D 在 $t_{1}$ 时刻侦听到信道空闲。按 CSMA 协议，D 于是开始发送自己的帧。稍后，B 的传输在 D 处开始干扰 D 的传输。从图 6.12 可以明显看出，广播信道的**端到端传播时延**——信号从一个节点传播到另一个节点所需的时间——在决定其性能方面起关键作用。这个传播时延越长，做载波侦听的节点来不及侦听到另一节点已经开始传输的概率就越大。

<Figure src="ch06/fig6-12.webp" caption="图 6.12　两个 CSMA 节点发生冲突传输的时空图" />

#### 带冲突检测的载波侦听多路访问（CSMA/CD）

图 6.12 中的节点没有做冲突检测；尽管冲突已经发生，B 与 D 都继续完整地发送各自的帧。当节点执行冲突检测时，它一旦检测到冲突就停止发送。图 6.13 展示了与图 6.12 相同的场景，只是两个节点在检测到冲突后不久就各自中止了发送。显然，把冲突检测加入多路访问协议，可以避免完整发送一个已因与别的节点的帧相互干扰而损坏的无用帧，从而有助于提高协议性能。

<Figure src="ch06/fig6-13.webp" caption="图 6.13　带冲突检测的 CSMA" />

在分析 CSMA/CD 协议之前，先从一个连接在广播信道上的（节点中的）适配器的角度总结其运行：

1. 适配器从网络层取得一个数据报，准备好一个链路层帧，并把帧放入适配器缓冲区。
1. 若适配器侦听到信道空闲（即没有信号能量从信道进入适配器），它就开始发送该帧。反之，若侦听到信道忙，它就等到侦听不到信号能量时再开始发送该帧。
1. 在发送过程中，适配器监视是否有来自其他使用该广播信道的适配器的信号能量。
1. 若适配器完整发送完该帧而未检测到来自其他适配器的信号能量，则该帧发送完毕。反之，若在发送过程中检测到来自其他适配器的信号能量，它就中止发送（即停止发送其帧）。
1. 中止之后，适配器等待一段随机时间，然后回到第 2 步。

等待**随机**（而非固定）时间段的必要性应该很清楚——如果两个节点同时发送帧、然后又都等待相同的固定时间，它们就会永远冲突下去。但"随机退避时间"该从什么样的区间里取才好？如果区间大而冲突节点少，节点就很可能要等很久（信道一直空闲）才重复"先听后说、空闲即发"；反之，如果区间小而冲突节点多，选到的随机值很可能相近，发送节点又会再次冲突。我们想要的是：冲突节点少时区间短，冲突节点多时区间长。

以太网以及 DOCSIS 电缆网络多路访问协议 [DOCSIS 3.1 2014] 中使用的**二进制指数退避**（binary exponential backoff）算法优雅地解决了这个问题。具体地说，当一个帧已经历了 $n$ 次冲突时，节点从 ${0, 1, 2, \cdots, 2^{n} - 1}$ 中随机选取 $K$ 值。于是帧经历的冲突越多，$K$ 的取值区间就越大。对以太网而言，节点实际等待的时间是 $K \cdot 512$ 个比特时间（即 $K$ 乘以把 512 比特送入以太网所需的时间），而 $n$ 的最大值上限为 10。

看一个例子。假设某节点第一次尝试发送一帧，并在发送过程中检测到冲突。节点随后以 0.5 的概率选 $K = 0$，以 0.5 的概率选 $K = 1$。若选 $K = 0$，它立即开始侦听信道；若选 $K = 1$，它等待 512 个比特时间（例如 100 Mbit/s 以太网中为 5.12 微秒）后开始"先听后说、空闲即发"的循环。第二次冲突后，$K$ 从 ${0, 1, 2, 3}$ 中等概率选取；第三次冲突后，从 ${0, 1, 2, 3, 4, 5, 6, 7}$ 中等概率选取；10 次或更多次冲突后，从 ${0, 1, 2, \cdots, 1023}$ 中等概率选取。可见 $K$ 的取值集合大小随冲突次数指数增长，因此该算法称为**二进制指数退避**。

还要指出：节点每次准备发送一个新帧时都重新运行 CSMA/CD 算法，不考虑最近可能发生过的冲突。因此，一个新帧的节点有可能在其他若干节点正处于指数退避状态时立刻"溜进"一次成功发送。

#### CSMA/CD 的效率

当只有一个节点有帧要发送时，节点可以按信道全速率发送（例如以太网的典型速率为 10 Mbit/s、100 Mbit/s 或 1 Gbit/s）。但若许多节点都有帧要发送，信道的有效传输速率可能低得多。我们把 CSMA/CD 的**效率**定义为：在大量活跃节点、每个节点都有大量帧要发送的情况下，帧在信道上无冲突传输所占的长期时间比例。为给出以太网效率的闭式近似，记 $d_{\text{prop}}$ 为信号能量在任意两个适配器之间传播所需的最大时间，$d_{\text{trans}}$ 为发送一个最大长度帧所需的时间（10 Mbit/s 以太网中约为 1.2 毫秒）。CSMA/CD 效率的推导超出本书范围（见 [Lam 1980] 与 [Bertsekas 1991]），这里只给出如下近似：

$$
\text{效率} = \frac{1}{1 + 5 \frac{d_{\text{prop}}}{d_{\text{trans}}}}
$$

由该式可见，当 $d_{\text{prop}}$ 趋于 0 时效率趋于 1。这与我们的直觉一致：若传播时延为零，冲突节点会立即中止而不会浪费信道。同样，当 $d_{\text{trans}}$ 变得很大时效率也趋于 1；这也符合直觉——一帧一旦抓住信道就会占用很长时间，因而信道大部分时间都在做有用功。

### 6.3.3　轮流协议

回忆多路访问协议的两个理想性质：(1) 只有一个活跃节点时，该活跃节点的吞吐量为 $R$ bit/s；(2) 有 $M$ 个活跃节点时，每个活跃节点的吞吐量接近 $\frac{R}{M}$ bit/s。ALOHA 与 CSMA 协议具备第一个性质，但不具备第二个。这促使研究者创造了另一类协议——**轮流协议**。与随机接入协议一样，轮流协议有几十种，每种又有许多变体。这里讨论其中两种较重要的协议。

第一种是**轮询协议**（polling protocol）。轮询协议要求指定其中一个节点为**控制节点**。控制节点以轮转方式轮询每个节点：它先向节点 1 发消息，说节点 1 可以发送最多某个最大数量的帧；节点 1 发送若干帧后，控制节点告诉节点 2 可以发送最多该数量的帧（控制节点可以通过观察信道上没有信号来判断某节点已发完）。如此循环，控制节点以循环方式轮询每个节点。

轮询协议消除了困扰随机接入协议的冲突与空时隙，从而使轮询能达到高得多的效率。但它也有几个缺点。第一个缺点是引入了**轮询时延**——通知某节点它可以发送所需的时间。例如，若只有一个活跃节点，该节点的发送速率会低于 $R$ bit/s，因为每当这个活跃节点发完其最大数量的帧，控制节点都必须依次轮询所有不活跃节点。第二个缺点可能更严重：如果控制节点故障，整个信道就无法工作。我们将在 7.5.1 节研究的蓝牙协议就是轮询协议的一个例子。

第二种轮流协议是**令牌传递协议**（token-passing protocol）。这种协议没有控制节点，而是让一个称为**令牌**（token）的小型专用帧按某种固定顺序在各节点之间传递。例如，节点 1 总是把令牌传给节点 2，节点 2 总是传给节点 3，节点 $N$ 总是传给节点 1。节点收到令牌时，只有当它有帧要发送才持有令牌；否则立即把令牌转发给下一个节点。如果收到令牌时确实有帧要发，它就发送最多某个最大数量的帧，然后把令牌转发给下一个节点。令牌传递是分散的、高效的，但也有问题：例如某个节点故障可能使整个信道瘫痪；又如某节点不小心没有释放令牌，就必须启用某种恢复过程把令牌重新投入循环。多年来已开发出许多令牌传递协议，包括光纤分布式数据接口（FDDI）[Jain 1994] 与 IEEE 802.5 令牌环协议 [IEEE 802.5 2012]，每一种都必须处理这些问题以及其他棘手问题。

### 6.3.4　DOCSIS：电缆因特网接入的链路层协议

前三小节我们学习了三大类多路访问协议：信道划分协议、随机接入协议与轮流协议。电缆接入网在这里是一个绝好的案例研究，因为我们会发现电缆接入网同时体现了这三类多路访问协议的各个方面！

回忆 1.2.1 节：电缆接入网通常把数千个住宅电缆调制解调器连接到电缆网络头端的**电缆调制解调器端接系统**（CMTS）。**电缆数据服务接口规范**（DOCSIS）[DOCSIS 3.1 2014; Hamzeh 2015] 规定了电缆数据网络体系结构及其协议。DOCSIS 用 FDM 把下行（CMTS 到调制解调器）与上行（调制解调器到 CMTS）网段划分为多个频率信道：每个下行信道宽 24 MHz 到 192 MHz，每信道最大吞吐量约 1.6 Gbit/s；每个上行信道宽度从 6.4 MHz 到 96 MHz，上行最大吞吐量约 1 Gbit/s。每条上行与下行信道都是广播信道。CMTS 在下行信道上发送的帧会被所有接收该信道的电缆调制解调器收到；不过由于只有一台 CMTS 向下行信道发送，不存在多路访问问题。上行方向则更有意思、技术上更具挑战，因为多个电缆调制解调器共享同一条通往 CMTS 的上行信道（频率），因而可能发生冲突。

<Figure src="ch06/fig6-14.webp" caption="图 6.14　CMTS 与电缆调制解调器之间的上行与下行信道" />

如图 6.14 所示，每条上行信道被划分为若干时间区间（类似 TDM），每个区间包含一串**微时隙**（mini-slot），电缆调制解调器可在其中向 CMTS 发送。CMTS 明确**授予**各个电缆调制解调器在特定微时隙中发送的许可。CMTS 通过在下行信道上发送一种称为 **MAP 报文**的控制报文来完成这一点，该报文规定哪个（有数据要发的）电缆调制解调器可以在控制报文所指定的时间区间内的哪个微时隙中发送。由于微时隙被显式分配给电缆调制解调器，CMTS 可以确保一个微时隙内没有冲突的传输。

但 CMTS 起初怎么知道哪些电缆调制解调器有数据要发？办法是让电缆调制解调器在一组专门用于此目的的区间微时隙中向 CMTS 发送**微时隙请求帧**，如图 6.14 所示。这些微时隙请求帧以随机接入方式发送，因而可能彼此冲突。电缆调制解调器既不能侦听上行信道是否忙，也不能检测冲突；取而代之的是，如果它在下一个下行控制报文中没有收到对所求分配的响应，就推断自己的微时隙请求帧发生了冲突。推断出冲突后，电缆调制解调器用二进制指数退避把微时隙请求帧的重传推迟到将来的时隙。当上行信道流量很小时，电缆调制解调器甚至可以在名义上分配给微时隙请求帧的时隙中发送数据帧（从而免去等待微时隙分配）。

因此，电缆接入网是"多路访问协议实战"的绝佳范例——FDM、TDM、随机接入与集中分配的时隙，全都出现在同一个网络里！

## 6.4　交换式局域网

<Figure src="ch06/fig6-15.webp" caption="图 6.15　由四台交换机连接起来的机构网络" />

上一节讨论了广播网络与多路访问协议，接下来把注意力转向**交换式局域网**。图 6.15 展示了一个交换式局域网，它用四台交换机把三个系、若干服务器和一台路由器连接起来。由于这些交换机工作在链路层，它们交换的是**链路层帧**（而不是网络层数据报），不认识网络层地址，也不用 OSPF 之类的路由算法来确定穿越二层交换机网络的路径。它们不用 IP 地址，而是很快会看到，它们用**链路层地址**在交换机网络中转发链路层帧。我们研究交换式局域网，先从链路层编址开始（6.4.1 节），然后考察大名鼎鼎的以太网协议（6.4.2 节），再看链路层交换机如何工作（6.4.3 节），最后看这些交换机通常如何被用来构建大规模局域网（6.4.4 节）。

### 6.4.1　链路层编址与 ARP

主机和路由器都有链路层地址。回想第 4 章学过主机和路由器也有网络层地址，你也许会觉得这很奇怪：我们到底为什么要在网络层和链路层**都**有地址？本节除了描述链路层地址的语法与功能，还希望说明这两层地址为什么有用、事实上为什么不可或缺。本节还会讨论**地址解析协议**（ARP），它提供了把 IP 地址翻译成链路层地址的机制。

#### MAC 地址

严格说来，拥有链路层地址的并不是主机和路由器，而是它们的**适配器**（即网络接口）。因此，一台有多个网络接口的主机或路由器会有多个链路层地址与之关联，正如它也会关联多个 IP 地址一样。不过要注意，链路层交换机连接主机和路由器的那些接口并没有关联的链路层地址。这是因为链路层交换机的职责是在主机与路由器之间承载数据报；交换机完成这项工作是**透明**的，即主机或路由器不必显式地把帧地址写成中间那台交换机。图 6.16 说明了这一点。链路层地址有各种叫法：局域网地址、物理地址或 **MAC 地址**。由于 MAC 地址似乎是最流行的说法，下文我们把链路层地址称为 MAC 地址。对大多数局域网（包括以太网与 802.11 无线局域网），MAC 地址长 6 字节，共有 $2^{48}$ 个可能的 MAC 地址。如图 6.16 所示，这 6 个字节通常用十六进制表示，每个字节写成一对十六进制数字。虽然 MAC 地址当初设计为永久的，但现在已可以通过软件修改适配器的 MAC 地址。不过本节余下部分仍假定适配器的 MAC 地址是固定的。

<Figure src="ch06/fig6-16.webp" caption="图 6.16　连到局域网的每个接口都有一个唯一的 MAC 地址" />

MAC 地址的一个有趣性质是：没有两个适配器具有相同的地址。考虑到适配器由许多国家的许多公司制造，这似乎令人惊讶。在台湾制造适配器的公司如何确保自己用的地址与比利时某公司不同？答案是 IEEE 管理着 MAC 地址空间。具体地说，当一家公司想制造适配器时，它花一点象征性的费用购买一块由 $2^{24}$ 个地址组成的地址空间。IEEE 通过固定 MAC 地址的前 24 比特来分配这块 $2^{24}$ 的地址，并让该公司为每个适配器在后 24 比特上创造唯一组合。

适配器的 MAC 地址是**扁平**结构（相对于层次结构），无论适配器到哪里都不改变。带以太网接口的笔记本电脑，无论计算机到哪里都始终具有相同的 MAC 地址；带 802.11 接口的智能手机，无论手机到哪里都始终具有相同的 MAC 地址。回想相比之下，IP 地址具有层次结构（即一个网络部分加一个主机部分），主机移动（即改变所连接的网络）时其 IP 地址需要改变。适配器的 MAC 地址类似于人的**社会保障号**——它也是扁平编址结构，无论人到哪里都不变；IP 地址则类似于人的**邮政地址**——它是层次的，人一搬家就必须改变。正如一个人会发现同时拥有邮政地址和社会保障号很有用，主机与路由器接口同时拥有网络层地址和 MAC 地址也是有用的。

当一个适配器想向某个目的适配器发送帧时，发送适配器把目的适配器的 MAC 地址插入帧中，然后把帧发送到局域网中。很快会看到，交换机会偶尔把收到的帧广播到它的所有接口上；第 7 章会看到 802.11 也广播帧。因此，一个适配器可能收到并非发给它的帧。所以适配器收到帧时会检查帧中的目的 MAC 地址是否与自己的 MAC 地址匹配：若匹配，适配器取出封装的数据报并上交协议栈；若不匹配，适配器丢弃该帧，不上交网络层数据报。这样，只有当帧是发给它的时候，目的方才被打断。

不过，有时发送适配器确实想让局域网上的所有其他适配器都接收并处理它要发送的帧。这时发送适配器在帧的目的地址字段中填入一个特殊的 **MAC 广播地址**。对使用 6 字节地址的局域网（如以太网与 802.11），广播地址是 48 个连续的 1（即十六进制的 `FF-FF-FF-FF-FF-FF`）。

<AsideCard title="原理与实践 · 保持各层独立">

主机与路由器接口除了网络层地址之外还要有 MAC 地址，有几个原因。第一，局域网是为任意网络层协议设计的，而不只是为 IP 和因特网。如果适配器被分配 IP 地址而不是"中立"的 MAC 地址，那么适配器就不容易支持其他网络层协议（例如 IPX 或 DECnet）。第二，如果适配器改用网络层地址而不是 MAC 地址，那么网络层地址就必须存放在适配器的 RAM 中，并且每次适配器被移动（或上电）时都要重新配置。另一种选择是完全不在适配器中使用地址，让每个适配器把它收到的每个帧的数据（通常是 IP 数据报）都上交协议栈，由网络层去检查网络层地址是否匹配。这种选择的一个问题是：主机将被局域网上发送的**每一个**帧打断，包括那些目的地是同一广播局域网中其他主机的帧。总之，要使各层成为网络体系结构中大体独立的构建块，不同层就需要有各自的编址方案。至此我们已见过三类地址：应用层的主机名、网络层的 IP 地址、链路层的 MAC 地址。

</AsideCard>

#### 地址解析协议（ARP）

由于既有网络层地址（例如因特网 IP 地址）又有链路层地址（即 MAC 地址），就需要在两者之间进行翻译。对因特网而言，这是**地址解析协议**（ARP）[RFC 826] 的职责。

为理解为什么需要 ARP 这样的协议，考虑图 6.17 所示的网络。在这个简单例子中，每台主机和路由器只有一个 IP 地址和一个 MAC 地址。照例，IP 地址用点分十进制表示，MAC 地址用十六进制表示。为便于讨论，本节假定交换机广播所有帧，即每当交换机在一个接口上收到帧，就把它从所有其他接口转发出去。下一节将给出交换机工作方式的更准确说明。

<Figure src="ch06/fig6-17.webp" caption="图 6.17　局域网上的每个接口都有一个 IP 地址和一个 MAC 地址" />

现在假设 IP 地址为 `222.222.222.220` 的主机想向主机 `222.222.222.222` 发送一个 IP 数据报。在这个例子中，源与目的在 4.3.3 节编址意义上属于同一子网。要发送数据报，源不仅要给它的适配器 IP 数据报，还要给出目的地 `222.222.222.222` 的 MAC 地址；发送适配器随后构造一个包含目的 MAC 地址的链路层帧，并把帧发送到局域网中。

本节要回答的重要问题是：发送主机如何确定 IP 地址为 `222.222.222.222` 的目的主机的 MAC 地址？你可能已经猜到，它使用 ARP。发送主机中的 ARP 模块以同一局域网上的任意 IP 地址为输入，返回相应的 MAC 地址。在手头的例子里，发送主机 `222.222.222.220` 把 IP 地址 `222.222.222.222` 交给它的 ARP 模块，ARP 模块返回相应的 MAC 地址 `49-BD-D2-C7-56-2A`。

可见 ARP 把 IP 地址解析为 MAC 地址。在许多方面它类似于 DNS（2.5 节研究过），后者把主机名解析为 IP 地址。但这两个解析器有一个重要区别：DNS 为因特网中**任何地方**的主机解析主机名，而 ARP 只为**同一子网**上的主机和路由器接口解析 IP 地址。如果加利福尼亚的某个节点试图用 ARP 解析密西西比州某节点的 IP 地址，ARP 会返回一个错误。

说明了 ARP 做什么，接下来看它如何工作。每台主机和路由器在内存中都有一张 **ARP 表**，其中包含 IP 地址到 MAC 地址的映射。图 6.18 给出主机 `222.222.222.220` 中 ARP 表可能的样子。ARP 表还包含一个**生存期**（TTL）值，表明每个映射何时从表中删除。注意，表里不一定有子网上每台主机和路由器的表项：有些可能从未被加入表中，有些可能已经过期。表项典型的过期时间是自放入 ARP 表起的 20 分钟。

<Figure src="ch06/fig6-18.webp" caption="图 6.18　222.222.222.220 中一张可能的 ARP 表" />

现在假设主机 `222.222.222.220` 想发送一个以该子网上另一台主机或路由器为 IP 目的地的数据报。发送主机需要在给定 IP 地址的情况下取得目的地的 MAC 地址。如果发送方的 ARP 表中已有目的节点的表项，这件事很容易。但如果 ARP 表当前没有目的地的表项呢？特别地，假设 `222.222.222.220` 想向 `222.222.222.222` 发送数据报。这时发送方用 ARP 协议来解析地址。首先，发送方构造一个称为 **ARP 分组**的特殊分组。ARP 分组有几个字段，包括发送方与接收方的 IP 地址和 MAC 地址。ARP 查询分组与响应分组格式相同。ARP 查询分组的用途是向子网上所有其他主机和路由器查询"被解析的那个 IP 地址对应哪个 MAC 地址"。

回到我们的例子，`222.222.222.220` 把一个 ARP 查询分组交给适配器，并指示适配器把该分组发送到 MAC 广播地址，即 `FF-FF-FF-FF-FF-FF`。适配器把 ARP 分组封装进链路层帧，用广播地址作为帧的目的地址，并把帧发送到子网中。回想我们关于社会保障号／邮政地址的类比，ARP 查询相当于一个人在某公司（比如 AnyCorp）拥挤的隔间办公室里大喊："邮政地址是加利福尼亚帕洛阿尔托 AnyCorp 112 房间 13 号隔间的那个人，社会保障号是多少？"包含 ARP 查询的帧被子网上所有其他适配器收到，并且（由于是广播地址）每个适配器都把帧中的 ARP 分组上交自己的 ARP 模块。每个 ARP 模块检查自己的 IP 地址是否与 ARP 分组中的目的 IP 地址匹配；匹配的那一个向查询主机回送一个包含所需映射的 ARP 响应分组。查询主机 `222.222.222.220` 随后就可以更新自己的 ARP 表，并发送它的 IP 数据报——封装在一个链路层帧中，该帧的目的 MAC 地址就是刚才响应 ARP 查询的那台主机或路由器的地址。

关于 ARP 协议，有几点值得注意。第一，ARP **查询**报文是在广播帧中发送的，而 ARP **响应**报文是在标准帧中发送的（继续往下读之前，你应当想一想为什么会这样）。第二，ARP 是**即插即用**的：ARP 表自动建立，不需要系统管理员配置；而且如果某台主机从子网上断开，它的表项最终会从子网上其他 ARP 表中删除。

学生常问：ARP 是链路层协议还是网络层协议？如我们所见，ARP 分组封装在链路层帧中，因此在体系结构上位于链路层之上。但 ARP 分组含有链路层地址字段，因此可以说它是链路层协议；它又含有网络层地址，因此也可以说是网络层协议。归根到底，ARP 最好被看作一个横跨链路层与网络层边界的协议——它并不整齐地落入我们在第 1 章学过的简单分层协议栈。现实世界中的协议就是这般复杂！

#### 向子网之外发送数据报

现在应该清楚主机向同一子网上另一台主机发送数据报时 ARP 如何工作了。但接下来看更复杂的情形：子网上的一台主机想向子网**之外**（即跨过一台路由器到另一个子网）的主机发送网络层数据报。我们结合图 6.19 来讨论这个问题，该图展示了一个由路由器互联的两个子网组成的简单网络。

<Figure src="ch06/fig6-19.webp" caption="图 6.19　由一台路由器互联的两个子网" />

关于图 6.19 有几点值得注意。每台主机恰好有一个 IP 地址和一个适配器。但如第 4 章所述，路由器为其每个接口都有一个 IP 地址；每个路由器接口还各有一个（路由器中的）ARP 模块和一个适配器。由于图 6.19 中的路由器有两个接口，它有两个 IP 地址、两个 ARP 模块和两个适配器。当然，网络中每个适配器都有自己的 MAC 地址。

还要注意，子网 1 的网络地址是 `111.111.111/24`，子网 2 的网络地址是 `222.222.222/24`。因此，连接到子网 1 的所有接口地址形如 `111.111.111.xxx`，连接到子网 2 的所有接口地址形如 `222.222.222.xxx`。

现在考察子网 1 上的一台主机如何向子网 2 上的一台主机发送数据报。具体地，假设主机 `111.111.111.111` 想向主机 `222.222.222.222` 发送一个 IP 数据报。发送主机照例把数据报交给它的适配器，但发送主机还必须向适配器指明一个合适的**目的 MAC 地址**。适配器该用哪个 MAC 地址？人们可能忍不住猜：合适的 MAC 地址是主机 `222.222.222.222` 那个适配器的地址，即 `49-BD-D2-C7-56-2A`。但这个猜测是**错的**！如果发送适配器使用那个 MAC 地址，那么子网 1 上没有任何适配器会把该 IP 数据报上交网络层，因为帧的目的地址不匹配子网 1 上任何适配器的 MAC 地址。这个数据报只会直接"死掉"、上数据报天堂。

仔细看图 6.19 就会发现，要让数据报从 `111.111.111.111` 到达子网 2 上的主机，必须先把数据报发给路由器接口 `111.111.111.110`，它是通往最终目的地路径上的**第一跳路由器**的 IP 地址。因此，帧合适的目的 MAC 地址是路由器接口 `111.111.111.110` 那个适配器的地址，即 `E6-E9-00-17-BB-4B`。发送主机如何获得 `111.111.111.110` 的 MAC 地址？当然还是用 ARP！一旦发送适配器拿到这个 MAC 地址，它就构造一个帧（其中含有目的地为 `222.222.222.222` 的数据报）并把帧发送到子网 1。子网 1 上的路由器适配器看到链路层帧是发给自己的，于是把帧交给路由器的网络层。好极了——IP 数据报已成功从源主机移动到路由器！但事情还没完，我们还得把数据报从路由器送到目的地。路由器现在必须确定应该从哪个接口转发该数据报。如第 4 章所述，这是通过查询路由器中的转发表完成的。转发表告诉路由器：该数据报应经路由器接口 `222.222.222.220` 转发。这个接口随后把数据报交给它的适配器，适配器把数据报封装进一个新帧并把帧发送到子网 2。这一次，帧的目的 MAC 地址确实是最终目的地的 MAC 地址。路由器如何获得这个目的 MAC 地址？当然还是从 ARP！

以太网的 ARP 定义在 RFC 826 中。RFC 1180 这份 TCP/IP 教程对 ARP 作了很好的介绍。我们将在章末习题中更详细地探讨 ARP。

### 6.4.2　以太网

以太网几乎已经占领了有线局域网市场。20 世纪 80 年代与 90 年代初，以太网面临来自其他局域网技术（包括令牌环、FDDI 与 ATM）的诸多挑战，其中一些技术在几年里确实抢到了一部分局域网市场。但自 20 世纪 70 年代中期发明以来，以太网不断发展壮大，并一直保持主导地位。今天，以太网是迄今最普遍的有线局域网技术，而且在可预见的未来很可能仍将如此。可以说，以太网之于局域网，正如因特网之于全球网络。

以太网成功的原因很多。第一，以太网是第一个广泛部署的高速局域网。由于部署得早，网络管理员对以太网非常熟悉——它的奇妙之处与种种怪癖——因而不愿在别的局域网技术出现时转投过去。第二，令牌环、FDDI 与 ATM 都比以太网更复杂、更昂贵，这进一步抑制了网络管理员转投的意愿。第三，转投另一种局域网技术（如 FDDI 或 ATM）最有说服力的理由，通常是新技术更高的数据速率；然而以太网总能反击，推出速率相当或更高的版本。20 世纪 90 年代初问世的交换式以太网进一步提高了其有效数据速率。最后，由于以太网如此流行，以太网硬件（特别是适配器与交换机）已成为大宗商品，价格便宜得惊人。

最初的以太网局域网由 Bob Metcalfe 与 David Boggs 在 20 世纪 70 年代中期发明。最初的以太网用同轴电缆总线互联节点；以太网的**总线拓扑**一直延续到 80 年代、进入 90 年代中期。总线拓扑的以太网是一个广播局域网——所有发送的帧都会到达总线上连接的每个适配器并被其处理。回忆 6.3.2 节我们讨论过以太网采用二进制指数退避的 CSMA/CD 多路访问协议。

到 20 世纪 90 年代末，多数公司和大学已把局域网换成了采用**基于集线器的星形拓扑**的以太网。在这种安装方式中，主机（和路由器）用双绞铜线直接连到一台**集线器**（hub）。集线器是一种物理层设备，作用于单个比特而不是帧。当一个表示 0 或 1 的比特从某个接口到达时，集线器只是重新生成该比特、增强其能量强度，并把它发送到所有其他接口。因此，基于集线器星形拓扑的以太网也是一个广播局域网——每当集线器从某个接口收到一个比特，它就向所有其他接口发送一份拷贝。特别地，如果集线器同时从两个不同接口收到帧，就会发生冲突，产生这些帧的节点必须重传。

21 世纪初，以太网又经历了一次重大演进。以太网安装仍采用星形拓扑，但中心的集线器被**交换机**取代。本章后面将深入考察交换式以太网。这里只需指出：交换机不仅"无冲突"，而且是名副其实的**存储转发分组交换机**；但与一直工作到第 3 层的路由器不同，交换机只工作到第 2 层。

#### 以太网帧结构

通过考察以太网帧（图 6.20）可以了解以太网的许多方面。为给这段关于以太网帧的讨论一个具体语境，考虑从一台主机向另一台主机发送 IP 数据报，两台主机在同一个以太网局域网中（例如图 6.17 中的以太网局域网）。（虽然我们这里以太网帧的载荷是 IP 数据报，但要指出以太网帧也可以承载其他网络层分组。）设发送适配器 A 的 MAC 地址为 `AA-AA-AA-AA-AA-AA`，接收适配器 B 的 MAC 地址为 `BB-BB-BB-BB-BB-BB`。发送适配器把 IP 数据报封装进以太网帧，并把帧交给物理层；接收适配器从物理层收到帧，取出 IP 数据报，并把它交给网络层。在这个语境下，来看图 6.20 所示以太网帧的六个字段。

<Figure src="ch06/fig6-20.webp" caption="图 6.20　以太网帧结构" />

- **数据字段（46–1 500 字节）**。该字段承载 IP 数据报。以太网的**最大传输单元**（MTU）是 1 500 字节，这意味着若 IP 数据报超过 1 500 字节，主机就必须按 4.3.2 节所述对数据报分片。数据字段的最小长度是 46 字节，这意味着若 IP 数据报不足 46 字节，数据字段就必须"填充"（stuffing）到 46 字节。使用填充时，交给网络层的数据既包含填充也包含 IP 数据报；网络层用 IP 数据报首部中的长度字段去掉填充。
- **目的地址（6 字节）**。该字段包含目的适配器的 MAC 地址 `BB-BB-BB-BB-BB-BB`。当适配器 B 收到一个目的地址为 `BB-BB-BB-BB-BB-BB` 或 MAC 广播地址的以太网帧时，它把该帧数据字段的内容交给网络层；若收到目的地址为其他任何 MAC 地址的帧，它就丢弃该帧。
- **源地址（6 字节）**。该字段包含把帧发送到局域网上的那个适配器的 MAC 地址，本例中为 `AA-AA-AA-AA-AA-AA`。
- **类型字段（2 字节）**。类型字段使以太网能多路复用网络层协议。要理解这一点，需记住主机除 IP 之外还可以使用其他网络层协议；事实上，一台给定主机可能为不同应用支持多个网络层协议。因此，当以太网帧到达适配器 B 时，适配器 B 需要知道应把数据字段的内容交给（即多路分用给）哪个网络层协议。IP 及其他网络层协议（例如 Novell IPX 或 AppleTalk）各有自己标准化的类型号。此外，ARP 协议（上一节讨论过）有自己的类型号；若到达的帧包含 ARP 分组（即类型字段为十六进制 `0806`），ARP 分组就会被多路分用上交 ARP 协议。注意，类型字段类似于网络层数据报中的协议字段以及运输层报文段中的端口号字段——这些字段都起到把一层的协议"粘"到上一层协议的作用。
- **循环冗余检测（CRC）（4 字节）**。如 6.2.3 节所述，CRC 字段的用途是让接收适配器 B 检测帧中的比特差错。
- **前同步码（8 字节）**。以太网帧以一个 8 字节的**前同步码**（preamble）字段开始。前同步码的前 7 个字节每个都是 `10101010`，最后一个字节是 `10101011`。前 7 个字节用于"唤醒"接收适配器，并把它们的时钟同步到发送方时钟。为什么时钟会不同步？要记住，适配器 A 的目标是以 10 Mbit/s、100 Mbit/s 或 1 Gbit/s（取决于以太网类型）发送帧；但由于没有什么是绝对完美的，适配器 A 不会恰好以目标速率发送，总会有某种偏离目标速率的漂移，而局域网上其他适配器事先并不知道这种漂移。接收适配器只要锁定前同步码前 7 个字节中的比特，就能锁定适配器 A 的时钟。前同步码第 8 个字节的最后 2 个比特（最先出现的两个连续 1）提醒适配器 B："重要的东西"就要来了。

所有以太网技术都向网络层提供**无连接**服务。也就是说，当适配器 A 想向适配器 B 发送数据报时，适配器 A 把数据报封装进以太网帧并把帧发送到局域网中，而不先与适配器 B 握手。这种二层无连接服务类似于 IP 的三层数据报服务与 UDP 的四层无连接服务。

以太网技术向网络层提供**不可靠**服务。具体地说，当适配器 B 从适配器 A 收到帧时，它对帧做 CRC 校验，但帧通过 CRC 校验时不发送确认，帧未通过 CRC 校验时也不发送否定确认；帧未通过 CRC 校验时，适配器 B 只是丢弃该帧。因此适配器 A 根本不知道它发送的帧是否到达适配器 B、是否通过了 CRC 校验。这种（链路层）可靠传输的缺失有助于使以太网简单廉价，但也意味着交给网络层的数据报流中可能出现空缺。

如果因为以太网帧被丢弃而出现空缺，主机 B 上的应用也会看到空缺吗？如第 3 章所学，这取决于应用用的是 UDP 还是 TCP。若应用使用 UDP，主机 B 上的应用确实会看到数据空缺；若应用使用 TCP，主机 B 中的 TCP 不会确认被丢弃帧中所含的数据，从而使主机 A 中的 TCP 重传。注意，TCP 重传数据时，这些数据最终会回到当初丢弃它的那个以太网适配器。因此在这个意义上，以太网确实重传了数据——尽管以太网并不知道自己发送的是一个带全新数据的全新数据报，还是一个含有至少已发送过一次的数据的数据报。

#### 以太网技术

上面的讨论中我们把以太网当作单一协议标准来谈。但事实上以太网有许多不同"口味"，其缩写令人眼花缭乱：10BASE-T、10BASE-2、100BASE-T、1000BASE-LX、10GBASE-T、40GBASE-T 等等。这些以及许多其他以太网技术多年来由 IEEE 802.3 CSMA/CD（以太网）工作组标准化 [IEEE 802.3 2020]。这些缩写看似令人困惑，其实很有规律：缩写的第一部分指标准的速度——10、100、1000 或 10G，分别表示 10 兆比特（每秒）、100 兆比特、千兆、10 吉比特与 40 吉比特以太网；"BASE" 指**基带**以太网，即物理介质只承载以太网流量，几乎所有 802.3 标准都是基带以太网；缩写的最后一部分指物理介质本身——以太网既是链路层规范也是物理层规范，可运行在同轴电缆、铜线、光纤等多种物理介质上，通常 "T" 指双绞铜线。

历史上，以太网最初被设想为一段同轴电缆。早期的 10BASE-2 与 10BASE-5 标准规定在两种同轴电缆上运行 10 Mbit/s 以太网，每种长度限制为 500 米；更长的距离可以通过**中继器**（repeater）实现——一种在输入端接收信号、在输出端重新生成信号的物理层设备。同轴电缆非常契合我们把以太网看作广播介质的观点——一个接口发送的所有帧都会被其他接口收到，以太网的 CSMA/CD 协议正好解决多路访问问题。节点只要接到电缆上，瞧，我们就有了一个局域网！

多年来以太网经历了一系列演进，今天的以太网与最初使用同轴电缆的总线拓扑设计已大不相同。今天大多数安装中，节点通过铜线或光纤构成的点对点段连接到交换机，如图 6.15–6.17 所示。

到 2000 年代中期，千兆以太网的各种标准已经就位——顾名思义，它以每秒 1 吉比特传输比特。早期 10 Mbit/s 与 100 Mbit/s 的以太网 MAC 协议与帧格式被保留下来，但为双绞铜线（1000BASE-T）、光纤（1000BASE-SX、1000BASE-LX、1000BASE-LX10、1000BASE-BX10）与铜缆（1000BASE-CX）定义了更高速的物理层。允许的以太网距离从几十米（双绞线）到某些光纤物理层的几十公里不等。图 6.21 展示了这些不同标准与共同的以太网 MAC 协议及帧格式。千兆以太网今天仍在使用，而为 10、40、100、200 与 400 Gbit/s 的更高速度以太网标准也已制定。

<Figure src="ch06/fig6-21.webp" caption="图 6.21　100 Gbit/s 以太网标准：共同的链路层，不同的物理层" />

最后用一个也许一直困扰你的问题来结束以太网技术的讨论。在总线拓扑与基于集线器的星形拓扑时代，以太网显然是（6.3 节所定义的）广播链路，节点同时发送时会发生帧冲突；为处理这些冲突，以太网标准包含了 CSMA/CD 协议，它对覆盖较小地理范围的有线广播局域网特别有效。但如果今天以太网的主流用法是基于交换机的星形拓扑、使用存储转发分组交换，那么还需要以太网 MAC 协议吗？我们很快会看到，交换机会协调其传输，任何时候都不会向同一接口转发一个以上的帧；此外现代交换机是**全双工**的，交换机和节点可以同时互相发送帧而不受干扰。换句话说，在基于交换机的以太网局域网中不存在冲突，因而也就不需要 MAC 协议！

如我们所见，今天的以太网与 40 多年前 Metcalfe 和 Boggs 构想的最初以太网已大不相同——速率提高了三个数量级，以太网帧运行在多种介质上，交换式以太网占据主导，如今甚至常常不需要 MAC 协议！这一切还算是以太网吗？答案当然是"按定义，是的"。不过有意思的是，在所有这些变化中，确实有一个近 50 年不变的恒量——以太网的**帧格式** [Metcalfe 2025]。也许这才是以太网标准中唯一真正永恒的核心。

### 6.4.3　链路层交换机

到此为止，我们一直有意含糊地谈交换机究竟做什么、如何工作。交换机的职责是接收到达的链路层帧并把它们转发到出链路上；本小节详细研究这一转发功能。我们会看到，交换机本身对子网中的主机和路由器是**透明**的——主机／路由器把帧寻址到另一台主机／路由器（而不是寻址到交换机），然后把帧高高兴兴地发送到局域网中，完全不知道会有交换机接收并转发该帧。帧到达交换机某个输出接口的速率可能暂时超过该接口的链路容量。为解决这个问题，交换机输出接口设有缓冲区，很像路由器输出接口为数据报设有缓冲区。下面更仔细地看交换机如何工作。

#### 转发与过滤

**过滤**（filtering）是交换机确定一个帧应当被转发到某个接口还是应当被丢弃的功能。**转发**（forwarding）是交换机确定一个帧应被导向哪些接口、然后把帧移到那些接口的功能。交换机的过滤与转发通过**交换机表**完成。交换机表包含局域网上**部分**（而不一定是全部）主机和路由器的表项。交换机表中的一个表项包含：(1) 一个 MAC 地址；(2) 通向该 MAC 地址的交换机接口；(3) 该表项被放入表中的时间。图 6.15 中最上方那台交换机的交换机表例子如图 6.22 所示。这段关于帧转发的描述听起来也许类似于第 4 章关于数据报转发的讨论。确实，在 4.4 节关于广义转发的讨论中我们学到，许多现代分组交换机可以配置为基于二层目的 MAC 地址转发（即作为二层交换机工作），或基于三层 IP 目的地址转发（即作为三层路由器工作）。不过我们仍要强调一个重要区别：交换机基于 MAC 地址而非 IP 地址转发分组。我们还会看到，传统（即非 SDN 语境下的）交换机表的构建方式与路由器转发表**非常**不同。

<Figure src="ch06/fig6-22.webp" caption="图 6.22　图 6.15 中最上方交换机的交换机表的一部分" />

要理解交换机过滤与转发如何工作，假设一个目的地址为 `DD-DD-DD-DD-DD-DD` 的帧从接口 $x$ 到达交换机。交换机用 MAC 地址 `DD-DD-DD-DD-DD-DD` 索引其表。有三种可能的情况：

- 表中**没有** `DD-DD-DD-DD-DD-DD` 的表项。这时交换机把该帧的拷贝转发到除接口 $x$ 之外所有接口之前的输出缓冲区。换句话说，若目的地址没有表项，交换机就**广播**该帧。
- 表中有表项，把 `DD-DD-DD-DD-DD-DD` 与接口 $x$ 关联。这时该帧来自包含适配器 `DD-DD-DD-DD-DD-DD` 的那段局域网。既然没有必要把帧转发到任何其他接口，交换机就执行**过滤**功能，丢弃该帧。
- 表中有表项，把 `DD-DD-DD-DD-DD-DD` 与接口 $y \ne x$ 关联。这时该帧需要被转发到连接在接口 $y$ 上的那段局域网。交换机执行**转发**功能，把帧放入接口 $y$ 之前的输出缓冲区。

用图 6.15 中最上方那台交换机及其图 6.22 的交换机表走一遍这些规则。假设一个目的地址为 `62-FE-F7-11-89-A3` 的帧从接口 1 到达交换机。交换机查表，看到该目的地就在接口 1 所连的那段局域网（即电气工程系）上。这意味着该帧早已在包含目的地的这段局域网上广播过了，因此交换机**过滤**（即丢弃）该帧。现在假设一个目的地址相同的帧从接口 2 到达。交换机再次查表，看到该目的地在接口 1 的方向上，于是把帧转发到接口 1 之前的输出缓冲区。从这个例子应当清楚：只要交换机表完整且准确，交换机就会朝着目的地转发帧而无需任何广播。

在这个意义上，交换机比集线器"更聪明"。但这张交换机表最初是如何配置的？有链路层版本的网络层路由协议吗？还是必须由一位忙得不可开交的管理员手工配置交换机表？

#### 自学习

交换机有一个美妙的性质（对已经忙不过来的网络管理员尤其如此）：它的表是自动、动态、自主地建立的——不需要网络管理员或配置协议的任何干预。换句话说，交换机是**自学习**（self-learning）的。这一能力这样实现：

1. 交换机表初始为空。
1. 对每个接口上收到的每个入帧，交换机在表中存入 (1) 该帧源地址字段中的 MAC 地址，(2) 帧到达的那个接口，(3) 当前时间。这样，交换机就在表中记录了发送方所驻留的那段局域网。如果局域网中每台主机最终都发送过帧，那么每台主机最终都会被记录到表中。
1. 若在某段时间（**老化时间**，aging time）之后没有收到以某个地址为源地址的帧，交换机就把该地址从表中删除。这样，如果一台 PC 被另一台 PC（带不同适配器）替换，原 PC 的 MAC 地址最终会从交换机表中清除。

用图 6.15 中最上方那台交换机及其图 6.22 的交换机表走一遍自学习性质。假设 9:39 有一个源地址为 `01-12-23-34-45-56` 的帧从接口 2 到达，并假设该地址不在交换机表中；于是交换机向表中加入一个新表项，如图 6.23 所示。

继续这个例子，假设该交换机的老化时间是 60 分钟，而 9:32 到 10:32 之间没有以 `62-FE-F7-11-89-A3` 为源地址的帧到达交换机。那么在 10:32，交换机就把该地址从表中删除。

<Figure src="ch06/fig6-23.webp" caption="图 6.23　交换机学习地址为 01-12-23-34-45-56 的适配器的位置" />

交换机是**即插即用**设备，因为它们不需要网络管理员或用户的任何干预。想安装交换机的网络管理员只需把各段局域网连到交换机接口上，不必在安装时或在某台主机从某段局域网移除时配置交换机表。交换机还是**全双工**的，即任何交换机接口都可以同时发送和接收。

#### 链路层交换的性质

描述了链路层交换机的基本运行之后，来考虑它们的特性与性质。可以识别出用交换机（而不是总线或基于集线器的星形拓扑这类广播链路）的若干优点：

- **消除冲突**。在由交换机（且不含集线器）构成的局域网中，没有因冲突而浪费的带宽！交换机缓存帧，任何时候都不会在一段链路上发送一个以上的帧。与路由器一样，交换机的最大总吞吐量是所有交换机接口速率之和。因此，交换机相对广播链路局域网带来显著的性能提升。
- **异构链路**。由于交换机把一条链路与另一条链路隔离开，局域网中不同链路可以运行在不同速率上、使用不同介质。例如，图 6.15 中最上方那台交换机可能有三条 1 Gbit/s 的 1000BASE-T 铜缆链路、两条 100 Mbit/s 的 100BASE-FX 光纤链路和一条 100BASE-T 铜缆链路。因此，交换机非常适合把旧设备与新设备混用。
- **管理**。除了提供更强的安全性（见"安全聚焦"专栏），交换机还简化了网络管理。例如，若某个适配器发生故障并不断发送以太网帧（称为**喋喋不休的适配器**，jabbering adapter），交换机可以检测到该问题并在内部断开这个故障适配器。有了这个特性，网络管理员不必半夜起床开车回单位去排除故障。同样，电缆被切断只会断开使用该电缆连接到交换机的那台主机。在同轴电缆时代，许多网络管理员花数小时"沿线巡查"（更准确地说，"在地板上爬行"）以找出导致整个网络瘫痪的电缆断点。交换机还收集带宽使用、冲突率与流量类型的统计信息，并把这些信息提供给网络管理员；这些信息可用于调试与纠错，以及规划局域网未来的演进。研究者正在原型部署中探索为以太网局域网增加更多管理功能 [Casado 2007; Koponen 2011]。

<AsideCard title="安全聚焦 · 嗅探交换式局域网：交换机投毒">

当一台主机连接到交换机时，它通常只收到发给它的帧。例如考虑图 6.17 中的交换式局域网：当主机 A 向主机 B 发送帧、且交换机表中有主机 B 的表项时，交换机只会把该帧转发给主机 B。如果主机 C 恰好在运行嗅探器，主机 C 就无法嗅探这个 A 到 B 的帧。因此在交换式局域网环境中（与 802.11 局域网或基于集线器的以太网局域网这类广播链路环境不同），攻击者更难嗅探帧。不过，由于交换机会广播目的地址不在交换机表中的帧，C 处的嗅探器仍能嗅探到一些并非发给 C 的帧；此外嗅探器还能嗅探所有目的地址为广播地址 `FF-FF-FF-FF-FF-FF` 的以太网广播帧。一种针对交换机的著名攻击叫**交换机投毒**（switch poisoning）：向交换机发送大量携带许多伪造源 MAC 地址的分组，从而用伪造表项填满交换机表，使合法主机的 MAC 地址无处可存。这会导致交换机广播大多数帧，随后被嗅探器捕获 [Skoudis 2006]。由于这种攻击即使对老练的攻击者也相当复杂，交换机受嗅探的危害显著小于集线器和无线局域网。

</AsideCard>

#### 交换机与路由器

如第 4 章所学，路由器是使用网络层地址转发分组的存储转发分组交换机。交换机虽然也是存储转发分组交换机，但与路由器有本质区别：它使用 MAC 地址转发分组。路由器是三层分组交换机，交换机是二层分组交换机。不过回忆 4.4 节学过，使用"匹配加动作"操作的现代交换机既能基于帧的目的 MAC 地址转发二层帧，也能基于数据报的目的 IP 地址转发三层数据报。确实，我们看到使用 OpenFlow 标准的交换机可以基于 11 个不同的帧、数据报与运输层首部字段中的任意一个执行广义分组转发。

尽管交换机与路由器有本质区别，网络管理员在安装互联设备时常常必须在两者之间选择。例如对图 6.15 的网络，网络管理员完全可以用一台路由器（而不是交换机）来连接各系局域网、服务器和因特网网关路由器。确实，路由器可以在不产生冲突的情况下实现系间通信。既然交换机和路由器都是互联设备的候选，两种途径各有什么优缺点？

先看交换机的优缺点。如上所述，交换机是即插即用的，这一性质深受全世界忙不过来的网络管理员喜爱。交换机的过滤与转发速率也可以相当高——如图 6.24 所示，交换机只需处理到第 2 层的帧，而路由器必须处理到第 3 层的数据报。另一方面，为防止广播帧循环，交换式网络的活动拓扑被限制为一棵**生成树**（spanning tree）。此外，大型交换式网络需要在主机和路由器中维护大型 ARP 表，并会产生大量 ARP 流量与处理开销。再者，交换机易受**广播风暴**（broadcast storm）影响——若某台主机失控、发送无休止的以太网广播帧流，交换机将转发所有这些帧，导致整个网络崩溃。

<Figure src="ch06/fig6-24.webp" caption="图 6.24　交换机、路由器与主机中的分组处理" />

再看路由器的优缺点。由于网络编址通常是层次的（而不像 MAC 编址那样扁平），即使网络存在冗余路径，分组通常也不会在路由器之间循环。（当然，路由器表配置错误时分组可能循环；但如第 4 章所学，IP 使用一个特殊的数据报首部字段来限制循环。）因此分组不受生成树限制，可以使用源与目的之间的最佳路径。正因为路由器没有生成树限制，才使因特网得以建立在丰富拓扑之上，例如欧洲与北美之间存在多条活动链路。路由器的另一个特性是它们对二层广播风暴提供防火墙式保护。不过路由器最显著的缺点也许是它们不是即插即用的——路由器以及连接其上的主机都需要配置 IP 地址。此外，路由器每分组的处理时间通常比交换机更长，因为它们必须处理到第 3 层字段。最后，"router" 这个词有两种读法（"rootor" 或 "rowter"），人们为正确读音浪费了大量时间争论 [Perlman 1999]。

既然交换机和路由器各有优缺点（汇总于表 6.1），那么一个机构网络（例如大学校园网或公司园区网）何时该用交换机、何时该用路由器？通常，由几百台主机组成的小型网络只有几段局域网。对这些小网络来说交换机就够了，因为它们能本地化流量、提高总吞吐量，而且不需要配置任何 IP 地址。但由数千台主机组成的大型网络通常会在网内（除交换机之外）使用路由器：路由器提供更健壮的流量隔离、控制广播风暴，并在网络主机之间使用更"智能"的路由。

|  | **集线器** | **路由器** | **交换机** |
| --- | --- | --- | --- |
| 流量隔离 | 否 | 是 | 是 |

### 6.4.4　虚拟局域网（VLAN）

前面讨论图 6.15 时我们指出，现代机构局域网常按层次配置：每个工作组（系）有自己的交换式局域网，再通过交换机层次连接到其他组的交换式局域网。这种配置在理想世界里运行良好，但现实世界往往远非理想。图 6.15 的配置可以识别出三个缺点：

- **缺乏流量隔离**。虽然这种层次结构把组内流量本地化到一台交换机内，但广播流量（例如携带 ARP 与 DHCP 报文的帧，或目的地尚未被自学习交换机学到的帧）仍必须穿越整个机构网络。限制这类广播流量的范围会改善局域网性能。也许更重要的是，出于安全／隐私考虑也可能希望限制局域网广播流量。例如，若一个组包含公司高管团队，另一个组包含心怀不满、正在运行 Wireshark 嗅探器的员工，网络管理员很可能希望高管的流量根本不要到达员工主机。这类隔离可以通过把图 6.15 的中心交换机换成路由器来提供；很快会看到，这种隔离也可以用交换式（二层）方案实现。
- **交换机利用效率低**。如果机构不是三个组而是十个组，就需要十台一级交换机。如果每个组都很小（比如不到 10 人），那么一台 96 端口的交换机大概就足以容纳所有人，但这台单一交换机无法提供流量隔离。
- **用户管理**。如果某员工在组之间调动，就必须改变物理布线，把他接到图 6.15 中另一台交换机上。属于两个组的员工会让问题更难办。

幸运的是，这些困难都可以由支持**虚拟局域网**（VLAN）的交换机来处理。顾名思义，支持 VLAN 的交换机允许在单一物理局域网基础设施上定义多个虚拟局域网。一个 VLAN 内的主机彼此通信，就好像它们（且只有它们）连接在这台交换机上一样。在**基于端口的 VLAN** 中，交换机的端口（接口）由网络管理员划分为若干组，每组构成一个 VLAN，每个 VLAN 中的端口形成一个**广播域**（即来自一个端口的广播流量只能到达该组内的其他端口）。图 6.25 展示了一台有 16 个端口的单一交换机：端口 2 到 8 属于 EE VLAN，端口 9 到 15 属于 CS VLAN（端口 1 与 16 未分配）。这个 VLAN 解决了上面提到的所有困难——EE 与 CS 的 VLAN 帧彼此隔离，图 6.15 中的两台交换机被一台单一交换机取代，而如果端口 8 上的用户转到计算机科学系，网络运营者只需重新配置 VLAN 软件，使端口 8 现在关联到 CS VLAN。很容易想象 VLAN 交换机是如何配置和运行的——网络管理员用交换机管理软件声明某个端口属于某个给定 VLAN（未声明的端口属于默认 VLAN），交换机内部维护一张端口到 VLAN 映射的表，交换机硬件只在属于同一 VLAN 的端口之间交付帧。

<Figure src="ch06/fig6-25.webp" caption="图 6.25　配置了两个 VLAN 的单台交换机" />

但把两个 VLAN 完全隔离开，又引入了一个新困难！EE 系的流量如何送到 CS 系？一种处理方式是把一个 VLAN 交换机端口（例如图 6.25 中的端口 1）连到一台外部路由器，并把这个端口配置为同时属于 EE 与 CS 两个 VLAN。这样，尽管 EE 与 CS 系共享同一台物理交换机，逻辑配置看起来就像两个系各有一台交换机、通过一台路由器相连。从 EE 到 CS 的 IP 数据报会先经 EE VLAN 到达路由器，再由路由器经 CS VLAN 转发回 CS 主机。幸运的是，交换机厂商把 VLAN 交换机与路由器做在同一个设备里，使这种配置对网络管理员来说很容易，无需单独的外部路由器。章末有一道习题更详细地探讨这个场景。

再回到图 6.15，现在假设不是单独设一个计算机工程系，而是有些 EE 和 CS 的教师被安排到另一座楼里，他们（当然！）需要网络接入，而且（当然！）希望属于自己系的 VLAN。图 6.26 展示了第二台 8 端口交换机，其端口已按需定义为属于 EE 或 CS VLAN。但这两台交换机应当如何互联？一个简单的办法是在每台交换机上定义一个属于 CS VLAN 的端口（EE VLAN 同理），并把这些端口互连，如图 6.26(a) 所示。然而这种方案不可扩展：$N$ 个 VLAN 就需要在每台交换机上占用 $N$ 个端口，仅仅用于互联这两台交换机。

一种更具可扩展性的 VLAN 交换机互联方式称为 **VLAN 干线**（VLAN trunking）。在图 6.26(b) 所示的干线方式中，每台交换机上的一个特殊端口（左交换机端口 16、右交换机端口 1）被配置为**干线端口**（trunk port），用于互联两台 VLAN 交换机。干线端口属于所有 VLAN，发往任何 VLAN 的帧都经干线链路转发到另一台交换机。但这就引出了另一个问题：交换机如何知道到达干线端口的帧属于哪个 VLAN？IEEE 为跨越 VLAN 干线的帧定义了一种扩展以太网帧格式 **802.1Q**。如图 6.27 所示，802.1Q 帧由标准以太网帧加上插入首部的 4 字节 **VLAN 标签**构成，该标签携带帧所属 VLAN 的标识。VLAN 标签由 VLAN 干线发送侧的交换机加入帧中，由干线接收侧的交换机解析并移除。VLAN 标签本身由 2 字节的**标签协议标识符**（TPID）字段（固定十六进制值 `81-00`）、2 字节的**标签控制信息**字段（其中含 12 比特的 VLAN 标识符字段）以及 3 比特的**优先级**字段（用意类似于 IP 数据报的 TOS 字段）组成。

<Figure src="ch06/fig6-26.webp" caption="图 6.26　用两个 VLAN 连接两台 VLAN 交换机：(a) 两根电缆；(b) 干线方式" />

<Figure src="ch06/fig6-27.webp" caption="图 6.27　原始以太网帧（上）与带 802.1Q 标签的以太网 VLAN 帧（下）" />

以上讨论只简要涉及 VLAN，并且聚焦于基于端口的 VLAN。还应提到，VLAN 还可以用其他几种方式定义。在**基于 MAC 的 VLAN** 中，网络管理员规定每个 VLAN 所属的 MAC 地址集合；每当设备接入某个端口，该端口就根据设备的 MAC 地址被接入相应的 VLAN。VLAN 也可以基于网络层协议（例如 IPv4、IPv6 或 AppleTalk）以及其他准则来定义，详见 802.1Q 标准 [IEEE 802.1q 2005]。VLAN 还可以跨 IP 路由器扩展，从而把若干"局域网孤岛"连接起来，形成可覆盖全球的单一 VLAN [Yu 2011]。确实，我们将在 6.5.2 节讨论的 VXLAN（虚拟可扩展局域网）技术，允许创建覆盖比 VLAN 更大地理范围的虚拟局域网。

## 6.5　链路虚拟化：把网络当作链路层

本章讨论链路层协议，而本章已近尾声，不妨回顾一下我们对"链路"一词的理解是如何演进的。本章开头把链路看作连接两台通信主机的物理导线。在研究多路访问协议时我们看到，多台主机可以由一条共享导线连接，而这条连接主机的"导线"可以是射频频谱或其他介质；这使我们更抽象地把链路看作**信道**，而不是导线。在研究以太网局域网（图 6.15）时我们看到，互联介质实际上可以是一个相当复杂的交换式基础设施。然而在整个演进过程中，主机自身始终认为互联介质只是连接两台或多台主机的**一条链路层信道**。例如我们看到，一台以太网主机可以完全不知道自己是经由一段短的局域网段（图 6.17）、一个地理上分散的交换式局域网（图 6.15）还是一个 VLAN（图 6.26）与其他局域网主机相连的。

在两台主机之间用拨号调制解调器连接的情况下，连接两台主机的链路实际上是电话网——一个逻辑上独立的全球电信网络，有自己的交换机、链路以及用于数据传输与信令的协议栈。然而从因特网链路层的角度看，经电话网的拨号连接被看作一条简单的"导线"。在这个意义上，因特网**虚拟化**了电话网，把电话网看作一种链路层技术，在两台因特网主机之间提供链路层连通性。你可能还记得第 2 章讨论覆盖网络时说过：覆盖网络同样把因特网看作在覆盖节点之间提供连通性的手段，试图以因特网覆盖电话网的同样方式覆盖因特网。

本节介绍两种技术：两台设备之间的**虚拟链路**在逻辑上表现得像一条物理链路，但实际上是由底层一个复杂的互联设备网络实现的。6.5.2 节将讨论前面提到的 VXLAN 技术；而 6.5.1 节先考察**多协议标签交换**（MPLS）。与电路交换的电话网不同，MPLS 本身就是一种分组交换的**虚电路**网络，有自己的分组格式与转发行为。因此从教学角度看，讨论 MPLS 既可归入网络层的学习，也可归入链路层的学习。不过从因特网的角度看，我们可以把 MPLS 像电话网和交换式以太网那样，看作一种用来互联 IP 设备的**链路层技术**。我们对 MPLS 的处理只能简短，因为这些网络足以（也确实已经）写成整本书。细节请参阅 [Davie 2000]。这里主要关注 MPLS 服务器如何与 IP 设备互联，同时也会稍微深入底层技术。

### 6.5.1　多协议标签交换（MPLS）

MPLS 源于 20 世纪 90 年代中后期若干产业界的努力，其目标是提高 IP 路由器的转发速度，办法是采纳虚电路网络世界的一个关键概念：**固定长度标签**。目标并不是要用基于固定长度标签和虚电路的转发基础设施取代基于目的地址的 IP 数据报转发基础设施，而是要**增强**它——有选择地给数据报打标签，并让路由器在可能时基于固定长度标签（而不是目的 IP 地址）转发数据报。重要的是，这些技术与 IP 携手工作，使用 IP 编址与选路。IETF 把这些努力统一为 MPLS 协议 [RFC 3031, RFC 3032]，实际上是把 VC 技术融入了路由式数据报网络。

先来考察由支持 MPLS 的路由器处理的链路层帧的格式。图 6.28 显示，在支持 MPLS 的设备之间传输的链路层帧，在二层（如以太网）首部与三层（即 IP）首部之间加入了一个小的 **MPLS 首部**。RFC 3032 规定了这类链路上 MPLS 首部的格式；其他 RFC 也为 ATM 与帧中继网络定义了相应首部。MPLS 首部中的字段包括**标签**、3 个保留供实验使用的比特、一个 **S 比特**（用于指示一串"堆叠"MPLS 首部的结束，这是这里不涉及的高级话题）以及一个**生存期**字段。

<Figure src="ch06/fig6-28.webp" caption="图 6.28　MPLS 首部：位于链路层与网络层首部之间" />

从图 6.28 可以立刻看出，MPLS 增强帧只能在**都**支持 MPLS 的路由器之间发送（因为一台不支持 MPLS 的路由器在本该找到 IP 首部的地方发现 MPLS 首部时，会相当困惑！）。支持 MPLS 的路由器常被称为**标签交换路由器**（label-switched router），因为它转发 MPLS 帧时，在转发表中查找 MPLS 标签，然后立即把数据报交给合适的输出接口。因此，支持 MPLS 的路由器不必取出目的 IP 地址、在转发表中做最长前缀匹配查找。但路由器如何知道它的邻居确实支持 MPLS？路由器又如何知道该把哪个标签与给定的 IP 目的地关联？要回答这些问题，需要看一组支持 MPLS 的路由器之间的交互。

在图 6.29 的例子中，路由器 R1 到 R4 支持 MPLS，R5 与 R6 是标准 IP 路由器。R1 已向 R2 与 R3 通告：它（R1）能路由到目的地 A，且收到的带 MPLS 标签 6 的帧将被转发到目的地 A。路由器 R3 已向路由器 R4 通告：它能路由到目的地 A 与 D，且分别带 MPLS 标签 10 与 12 的入帧将被交换到那些目的地。路由器 R2 也已向路由器 R4 通告：它（R2）能到达目的地 A，且收到的带 MPLS 标签 8 的帧将被交换到 A。注意路由器 R4 现在处于一个有意思的位置：它有两条到达 A 的 MPLS 路径——经接口 0 出境标签为 10，经接口 1 标签为 8。图 6.29 描绘的总体图景是：IP 设备 R5、R6、A 与 D 通过一个 MPLS 基础设施（支持 MPLS 的路由器 R1–R4）互联在一起，其方式很像交换式局域网或 ATM 网络可以互联 IP 设备。并且与交换式局域网或 ATM 网络一样，支持 MPLS 的路由器 R1–R4 在这样做时从不碰分组的 IP 首部。

<Figure src="ch06/fig6-29.webp" caption="图 6.29　MPLS 增强转发" />

上面的讨论没有说明在支持 MPLS 的路由器之间分发标签所用的具体协议，因为这一信令的细节远超出本书范围。不过要指出，IETF 的 MPLS 工作组已在 [RFC 3468] 中规定，RSVP 协议的一个扩展 RSVP-TE [RFC 3209] 将作为其 MPLS 信令工作的重点。我们也没有讨论 MPLS 实际如何计算支持 MPLS 的路由器之间的分组路径，以及它如何收集链路状态信息（例如 MPLS 未预留的链路带宽量）用于这些路径计算。现有的链路状态路由算法（如 OSPF）已被扩展，可把这些信息泛洪给支持 MPLS 的路由器。有意思的是，实际的路径计算算法并未标准化，目前是厂商专有的。

至此我们对 MPLS 的讨论重点一直是：MPLS 基于标签进行交换，无需考虑分组的 IP 地址。然而 MPLS 的真正优势、也是当前人们对 MPLS 感兴趣的原因，并不在于交换速度可能提高，而在于 MPLS 所带来的新的**流量管理**能力。如上所述，R4 有两条到 A 的 MPLS 路径。如果转发在 IP 层基于 IP 地址进行，我们第 5 章学过的 IP 路由协议只会指定一条到 A 的最小代价路径。因此，MPLS 提供了沿标准 IP 路由协议不可能实现的路由转发分组的能力。这是使用 MPLS 进行**流量工程**（traffic engineering）的一种简单形式 [RFC 3346; RFC 3272; RFC 2702; Xiao 2000]：网络运营者可以推翻正常的 IP 选路，把前往某个目的地的部分流量强制走一条路径，把前往同一目的地的其他流量强制走另一条路径（无论是出于策略、性能还是其他原因）。

MPLS 还可用于许多其他目的。它可以用来对 MPLS 转发路径做快速恢复，例如在链路故障时把流量改道到预先计算好的故障切换路径上 [Kar 2000; Huang 2002; RFC 3469]。最后要指出，MPLS 可以、也确实被用来实现所谓的**虚拟专用网**（VPN）：ISP 在为客户实现 VPN 时，用其支持 MPLS 的网络把客户的各个网络连接起来。MPLS 可以把客户 VPN 所用的资源与编址，与其他穿越该 ISP 网络的用户隔离开；细节见 [DeClercq 2002]。我们将在 8.7.1 节更详细地讨论 VPN。

以上对 MPLS 的讨论很简短，建议读者参阅 [Davie 2000] 及上面的参考文献。要指出的是，MPLS 在软件定义网络（第 5 章）发展之前就已崭露头角，而 MPLS 的许多流量工程能力也可以通过 SDN 以及第 4 章学过的广义转发范式实现。MPLS 与 SDN 会继续共存，还是更新的技术（如 SDN）最终取代 MPLS，只有未来才能告诉我们。

### 6.5.2　VXLAN：IP 之上的以太网

我们在 6.4.4 节研究的 802.1Q VLAN 有两个重要局限：受 802.1Q VLAN 标签中 12 比特 VLAN 标识符字段所限，VLAN 数量不能超过 4 096 个；而且 VLAN 必须包含在单一的全交换式以太网端到端局域网基础设施之内。能不能构建更大的虚拟局域网，或者把分布在全球的二层设备连接成一个虚拟局域网？这两个问题的答案都是"能！"，用的是一种称为**虚拟可扩展局域网**（Virtual extensible Local-Area Network，VXLAN）的途径 [RFC 7348]。

图 6.30 展示了一个简单情形：两个物理上分离的以太网局域网——一个在加利福尼亚州桑尼维尔，一个在印度班加罗尔——被合并成单一的逻辑 VXLAN，使得从桑尼维尔以太网段中某台主机发出、目的 MAC 地址为班加罗尔以太网中某台主机的以太网帧，会在班加罗尔的那台主机上被收到！这是通过创建一条**链路层隧道**实现的：隧道一端在桑尼维尔局域网上的某台设备，另一端在班加罗尔局域网上的某台设备。进入桑尼维尔局域网一侧隧道的以太网帧，会从班加罗尔局域网一侧的隧道出来。VXLAN 隧道把一段以太网（更一般地说，一个二层的子网）**延伸**跨过三层网络的边界。你可能还记得第 4 章用隧道把一个 IPv6 网络经中间的 IPv4 网络连接到另一个 IPv6 网络；有了 VXLAN，我们又看到一个例子：整个网络（这里是隧道端点之间的 IP 网络）被虚拟化成单一的逻辑链路。第 7 章还会看到隧道在蜂窝网络中被广泛使用。确实，隧道出现在许许多多网络场景中 [Zave 2024]。

**VXLAN 隧道端点**（VTEP）在 VXLAN 中起关键作用。VTEP 是一台普通的物理交换机或路由器，或数据中心中的虚拟化交换机或路由器，被配置为实现 VXLAN。在图 6.30 中，位于桑尼维尔的 Host A 发送一个以太网帧，其 MAC 目的地址是位于班加罗尔的 Host B。VTEP x 物理上连在桑尼维尔局域网上，它收到该帧并注意到其目的地是 Host B——它知道 B 在隧道的另一端。VTEP x 随后把整个以太网帧连同一些额外的 VXLAN 首部信息放入一个标准 UDP 数据报的载荷中。这些首部信息包括 24 比特的 **VXLAN 网络标识符**（VNI），它使每个扩展局域网可以标识 1 600 万个 VXLAN。VXLAN 所能提供的巨量虚拟局域网，在数据中心场景中特别有价值。

<Figure src="ch06/fig6-30.webp" caption="图 6.30　包含桑尼维尔与班加罗尔网段的 VXLAN" />

随后，含有原始以太网帧与首部信息的 UDP 数据报被放入一个 IP 数据报，该 IP 数据报被寻址到实现 VXLAN 隧道另一端的 VTEP y。x 与 y 之间的 IP 网络随后把这个 IP 数据报交付给 y，就像它正常交付任何数据报一样，对其内容一无所知。VTEP y 收到数据报，注意到其中含有一个装着 VXLAN 以太网帧的 UDP 报文段，于是取出该以太网帧并在班加罗尔以太网上发送。源 MAC 地址为 A、目的 MAC 地址为 B 的原始以太网帧随后就在 Host B 处被收到。

如果你能想明白图 6.30 所示这种相当不寻常的分层——把以太网数据报封装在 UDP 报文段里、再把 UDP 报文段封装在 IP 数据报里——那么你就真正掌握了**隧道**的概念，也掌握了**链路虚拟化**的概念，以及"整个网络充当单条虚拟链路"这一观念！

在这段关于 VXLAN 的简短讨论中，我们跳过了一些重要问题。例如，VTEP x 如何知道 Host B 位于隧道的另一端？UDP 数据报中究竟包含哪些 VXLAN 首部信息？需要大量 VXLAN 的各种用例是什么？关于 VXLAN 细节及其用途的良好资料有 [Arista VXLAN 2017; Cisco VXLAN 2014; Juniper VXLAN 2024; RFC 7348]。

## 6.6　数据中心网络

Google、Microsoft、Amazon、阿里巴巴等因特网公司建设了大规模数据中心，每个数据中心容纳数万到数十万台主机。正如 1.2 节专栏简要讨论过的，数据中心不仅连接到因特网，其内部还包含复杂的计算机网络——**数据中心网络**——用来互联内部主机。本节简要介绍面向云应用的数据中心网络。

概括地说，数据中心有三个用途。第一，向用户提供网页、搜索结果、AI 聊天机器人、电子邮件或流媒体视频等内容。第二，作为大规模并行计算基础设施，承担特定的数据处理任务，例如搜索引擎的分布式索引计算。第三，向其他公司提供云计算。确实，当今计算的一大趋势就是公司使用 Amazon Web Services、Microsoft Azure、阿里云等云提供商来处理其几乎所有 IT 需求。

### 6.6.1　数据中心体系结构

数据中心的设计被当作公司机密小心保守，因为它们常常为领先的云计算公司提供关键竞争优势。2024 年，建设一个大型数据中心的成本可以从数亿美元到十亿美元以上。约 45% 的成本可归于主机本身（每 3–4 年需要更换）；25% 归于基础设施，包括变压器、不间断电源（UPS）系统、用于长时间断电的发电机以及冷却系统；15% 是电力消耗的电费；15% 用于网络，包括网络设备（交换机、路由器、负载均衡器）、外部链路与过境流量费用。（在这些百分比中，设备成本已摊销，以便对一次性采购和电费等持续性支出使用统一的成本度量。）虽然网络不是最大的成本项，但网络创新是降低总成本、最大化性能的关键 [Greenberg 2009a]。

数据中心里的"工蜂"是主机。数据中心中的主机称为**刀片**（blade），外形像比萨盒，一般是包含 CPU、内存与磁盘存储的通用主机。主机堆叠在**机架**（rack）中，每个机架通常有 20 到 40 块刀片。每个机架顶部有一台交换机，恰如其分地称为**机架顶部**（TOR）交换机，它把机架内主机彼此互联，并把它们与数据中心中的其他交换机互联。具体地说，机架中每台主机都有一个网络接口连到其 TOR 交换机，每台 TOR 交换机还有额外端口可以连到其他交换机。今天，主机通常以 40 Gbit/s 或 100 Gbit/s 以太网连接到其 TOR 交换机 [FB 2019; Greenberg 2015; Roy 2015; Singh 2015]。每台主机还被分配自己的数据中心内部 IP 地址。

数据中心网络支持两类流量：外部客户端与内部主机之间的流量，以及内部主机之间的流量。为处理外部客户端与内部主机之间的流，数据中心网络包含一台或多台**边界路由器**，把数据中心网络连接到公共因特网。因此，数据中心网络把各机架彼此互联，并把机架连接到边界路由器。图 6.31 展示了一个数据中心网络的例子。数据中心网络设计——设计把机架彼此互联、并把机架与边界路由器互联的互联网络与协议的艺术——近年来已成为计算机网络研究的一个重要分支（见本节参考文献）。

#### 负载均衡

一个云数据中心（例如 Google、Microsoft、Amazon、阿里巴巴运营的数据中心）同时提供许多应用，如搜索、电子邮件与视频应用。为支持来自外部客户端的请求，每个应用都关联一个对外可见的 IP 地址，客户端把请求发往该地址、并从该地址接收响应。在数据中心内部，外部请求首先被导向一台**负载均衡器**（load balancer），其职责是把请求分发给各主机，并根据各主机当前负载在主机之间平衡负载 [Patel 2013; Eisenbud 2016]。大型数据中心常常有多台负载均衡器，每台专门服务一组特定的云应用。这种负载均衡器有时被称为"四层交换机"，因为它依据分组中的目的端口号（第 4 层）以及目的 IP 地址做决策。收到对某个特定应用的请求后，负载均衡器把请求转发给处理该应用的某台主机（该主机随后可能调用其他主机的服务来协助处理该请求）。负载均衡器不仅在主机之间平衡工作负载，还提供类似 NAT 的功能：把对外的公共 IP 地址翻译成相应主机的内部 IP 地址，然后对返回客户端的反向分组再做翻译。这使客户端无法直接联系主机，具有隐藏内部网络结构、防止客户端与主机直接交互的安全好处。

#### 层次体系结构

对于一个只容纳几千台主机的小型数据中心，一个由一台边界路由器、一台负载均衡器和几十个机架组成、全部由一台以太网交换机互联的简单网络也许就够了。但要扩展到数万到数十万台主机，数据中心往往采用路由器与交换机的层次结构，例如图 6.31 所示的拓扑。在层次结构顶部，边界路由器连接到**接入路由器**（图 6.31 只画了两台，但可以有很多台）。每台接入路由器之下有三层交换机：每台接入路由器连接到一台**顶层交换机**，每台顶层交换机连接到多台**二层交换机**和一台负载均衡器；每台二层交换机又通过机架的 TOR 交换机（三层交换机）连接到多个机架。所有链路通常都用以太网作为链路层与物理层协议，铜缆与光纤混用。有了这样的层次设计，就有可能把数据中心扩展到数十万台主机。

由于持续为应用提供高可用性对云应用提供商至关重要，数据中心的设计中还包含冗余的网络设备与冗余链路（图 6.31 未画出）。例如，每台 TOR 交换机可以连接到两台二层交换机；每台接入路由器、顶层交换机与二层交换机都可以复制一份并整合进设计中 [Cisco 2012; Greenberg 2009b]。在图 6.31 的层次设计中可以看到，每台接入路由器之下的主机构成一个子网。为了把 ARP 广播流量本地化，这些子网每一个又被进一步划分为更小的 VLAN 子网，每个包含几百台主机 [Greenberg 2009a]。

尽管刚才描述的常规层次体系结构解决了规模问题，但它受限于**主机到主机容量**不足 [Greenberg 2009b]。为理解这一局限，再看图 6.31，假设每台主机以 10 Gbit/s 链路连到其 TOR 交换机，而交换机之间的链路是 100 Gbit/s 以太网链路。同一机架中的两台主机总能以完整的 10 Gbit/s 通信，只受主机网络接口控制器速率的限制。然而，如果数据中心网络中有许多同时进行的流，不同机架中两台主机之间的最大速率可能低得多。为看清这个问题，考虑一个由 40 对主机之间 40 条同时进行的流构成的流量模式：具体地，假设图 6.31 中机架 1 的 10 台主机各向机架 5 中一台对应主机发送一条流；类似地，机架 2 与 6 之间、机架 3 与 7 之间、机架 4 与 8 之间也各有 10 条同时进行的流。若每条流与其经过链路上的其他流均分链路容量，那么穿越 100 Gbit/s 的 A 到 B 链路（以及 100 Gbit/s 的 B 到 C 链路）的 40 条流每条只能得到 $100 \frac{\text{Gbit/s}}{40} = 2.5 \text{Gbit/s}$，显著低于 10 Gbit/s 的网络接口速率。对需要走到层次结构更高层的主机之间的流，问题更加尖锐。

这个问题有几种可能的解决方案：

- 一种方案是部署更高速率的交换机与路由器。但这会显著增加数据中心成本，因为高速端口交换机与路由器非常昂贵。
- 第二种方案（只要可能就采用）是把相关服务与数据尽量放在彼此靠近的位置（例如同一机架或邻近机架）[Roy 2015; Singh 2015]，以尽量减少经二层或一层交换机的机架间通信。但这有其极限，因为数据中心的一个关键要求是计算与服务放置的**灵活性** [Greenberg 2009b; Farrington 2010]。例如，一个大规模因特网搜索引擎可能运行在分布在多个机架上的数千台主机上，任意两台主机之间都有很大的带宽需求；类似地，某个云计算服务（如 Amazon Web Services 或 Microsoft Azure）可能希望把构成客户服务的多台虚拟机放在容量最大的物理主机上，而不论它们在数据中心中的位置。若这些物理主机分散在多个机架中，上述网络瓶颈就可能导致性能很差。
- 解决方案的最后一部分，是在 TOR 交换机（常称为**接入交换机**）与二层交换机（常称为**汇聚交换机**）之间、以及二层交换机与一层交换机（常称为**核心交换机**）之间提供更强的连通性。例如，如图 6.32 所示，每台 TOR 交换机可以连接到两台二层交换机，从而在机架之间提供多条链路不相交、交换机不相交的路径。图 6.32 中，第一台与第二台二层交换机之间有 4 条不同路径，合计在这两台二层交换机之间提供 400 Gbit/s 的总容量。提高层间连通度有两大好处：交换机之间的容量增大，可靠性也提高（因为路径多样）。在 Facebook 的数据中心 [FB 2019] 中，每台 TOR 连接到 16 台不同的二层交换机，每台二层交换机又连接到 16 台不同的一层交换机。

<Figure src="ch06/fig6-32.webp" caption="图 6.32　三层、高度互联的数据中心网络拓扑" />

数据中心网络中层间连通度提高的一个直接后果是：**多路径路由**在这些网络中成为一等公民。流默认就是多路径流。一种非常简单的多路径路由方案是**等代价多路径**（ECMP）[RFC 2992]，它在源与目的之间的交换机上执行随机化的下一跳选择。也有人提出了使用更细粒度负载均衡的高级方案 [Alizadeh 2014; Noormohammadpour 2018]。这些方案在**流**级别执行多路径路由，而另一些设计则在一条流内部把各个分组路由到多条路径上 [He 2015; Raiciu 2010]。

图 6.31 与 6.32 所示的三层层次结构，已演化为一种称为 **leaf-spine** 拓扑的两层数据中心互联结构 [Alizadeh 2013]，如图 6.33 所示。在 leaf-spine 拓扑中，接入交换机（称为**叶交换机**，leaf switch）连接到**每一台**核心交换机（称为**脊交换机**，spine switch）。leaf-spine 拓扑的互联容量可以通过升级叶与脊节点之间的链路速率来扩展，也可以通过水平增加更多脊节点来扩展。在 leaf-spine 拓扑中，数据中心内越过接入交换机的所有通信都恰好需要两跳交换机，而不像图 6.31 与 6.32 的拓扑那样跳数可变、可能更多。

<Figure src="ch06/fig6-33.webp" caption="图 6.33　叶交换机与脊交换机的互联" />

向 leaf-spine 拓扑的演进，反映了数据中心内服务器之间通信（所谓"东西向"流量）相对于服务器与数据中心之外端点之间通信（所谓"南北向"流量）的增长。此外，人们对在 SDN 控制下、在叶（或汇聚）交换机之间使用可重构的直接光互连也越来越感兴趣，从而绕过对脊交换机的需求 [Poutievski 2022]。

像图 6.32 与 6.33 所示这种多交换机分层（多级）互联网络称为 **Clos 网络**，得名于 Charles Clos——他在电话交换的背景下研究了这类网络 [Clos 1953]。此后，Clos 网络的丰富理论发展起来，并在数据中心网络与多处理器互联网络中获得了更多应用。对一些最大的数据中心运营者来说，互联网络中的交换机正用商用现成的"商用芯片"自行制造 [Greenberg 2009b; Roy 2015; Singh 2015; Poutievski 2022]，而不是从交换机厂商购买。

### 6.6.2　数据中心网络的发展趋势

数据中心网络正在迅速演进，其趋势由降低成本、虚拟化、物理限制、可管理性、可扩展性与定制化所驱动。

#### 集中的 SDN 控制与管理

由于数据中心由单一组织管理，若干最大的数据中心运营者（包括 Google、Microsoft 与 Facebook）拥抱类似 SDN 的逻辑集中式控制这一理念，也许是自然的。例如我们了解到 Google 的 Orion SDN 平台既用于控制和管理其数据中心网络，也用于管理连接这些数据中心的广域 B4 网络。它们的体系结构同样体现了数据平面（由相对简单的通用交换机组成）与基于软件的控制平面的清晰分离，正如 5.5 节所见。由于其数据中心的巨大规模，5.7 节所涉及的自动化配置与运行状态管理也至关重要 [Vahdat 2024]。

#### 虚拟化

虚拟化一直是云计算乃至更广义的数据中心网络增长的驱动力。**虚拟机**（VM）把运行应用的软件与物理硬件解耦，这种解耦还允许 VM 在物理服务器之间无缝迁移，而这些服务器可能位于不同机架上。标准以太网与 IP 协议在支持 VM 迁移、同时在服务器之间保持活动网络连接方面存在局限。由于所有数据中心网络都由单一管理权威管理，这个问题的一个优雅解决方案是把整个数据中心网络视为一个单一的、扁平的二层网络。回忆在典型以太网中，ARP 协议维护接口上 IP 地址与硬件（MAC）地址之间的绑定。为模拟"所有主机都连到一台交换机"的效果，ARP 机制被修改为使用类似 DNS 的查询系统而不是广播，并由一个目录维护"分配给某 VM 的 IP 地址"与"该 VM 当前连在数据中心网络中哪台物理交换机上"之间的映射。实现这一基本设计的可扩展方案已在 [Mysore 2009; Greenberg 2009b] 中提出，并已成功部署在现代数据中心中。

#### 物理限制

与广域因特网不同，数据中心网络所处的环境不仅容量极高（40 Gbit/s 与 100 Gbit/s 链路如今已司空见惯），而且时延极低（微秒级）。因此缓冲区很小，TCP 及其变体这类拥塞控制协议在数据中心里扩展性不佳。在数据中心，拥塞控制协议必须快速反应，并在极低丢包的区间内运行，因为丢包恢复与超时会导致极端低效。人们提出并部署了多种途径来解决这个问题，从数据中心专用的 TCP 变体 [Alizadeh 2010]，到在标准以太网上实现远程直接内存访问（RDMA）技术 [Zhu 2015; Moshref 2016; Guo 2016]。调度理论也被用来开发把流调度与速率控制解耦的机制，从而在保持链路高利用率的同时支持非常简单的拥塞控制协议 [Alizadeh 2013; Hong 2012]。

#### 硬件模块化与定制化

另一个主要趋势是采用基于集装箱的**模块化数据中心**（MDC）[YouTube 2009; Waldrop 2007]。在 MDC 中，工厂在一个标准 12 米集装箱内建好一个"迷你数据中心"，再把集装箱运到数据中心所在地。每个集装箱最多有几千台主机，堆叠在几十个机架中，紧密排列。在数据中心所在地，多个集装箱彼此互联，也与因特网互联。预制集装箱一旦部署到数据中心，往往难以维修。因此每个集装箱都被设计为**性能优雅降级**：随着组件（服务器与交换机）逐渐失效，集装箱继续运行但性能下降；当许多组件失效、性能降到阈值以下时，整个集装箱被移走并换上一个新的。

用集装箱搭建数据中心带来了新的网络挑战。在 MDC 中，有两类网络：每个集装箱**内部**的网络，以及连接各集装箱的**核心网络** [Guo 2009; Farrington 2010]。在每个集装箱内部，在最多几千台主机的规模上，有可能用廉价的商用千兆以太网交换机搭建一个全连通网络。然而核心网络的设计——互联数百到数千个集装箱，同时为典型工作负载提供集装箱之间高主机到主机带宽——仍然是一个挑战。

### 6.7.1　起步：DHCP、UDP、IP 与以太网

假设 Bob 启动笔记本电脑，然后把它接到一根连到学校以太网交换机的以太网电缆上，交换机又连到学校的路由器，如图 6.34 所示。学校路由器连接到一个 ISP，本例中是 `comcast.net`。在这个例子中，`comcast.net` 为学校提供 DNS 服务，因此 DNS 服务器位于 Comcast 网络中而不是学校网络中。我们假设 DHCP 服务器运行在路由器中，情况常常如此。

Bob 第一次把笔记本接入网络时，没有 IP 地址就什么也做不了（例如下载网页）。因此 Bob 的笔记本所做的第一个与网络有关的动作，就是运行 DHCP 协议，从本地 DHCP 服务器获得一个 IP 地址以及其他信息：

1. Bob 笔记本上的操作系统创建一个 DHCP 请求报文（4.3.3 节），并把它放入一个 UDP 报文段（3.3 节），目的端口 67（DHCP 服务器）、源端口 68（DHCP 客户端）。该 UDP 报文段随后被放入一个 IP 数据报（4.3.1 节），IP 目的地址为广播地址 `255.255.255.255`，源 IP 地址为 `0.0.0.0`（因为 Bob 的笔记本还没有 IP 地址）。
1. 含有 DHCP 请求报文的 IP 数据报随后被放入一个以太网帧（6.4.2 节）。该以太网帧的目的 MAC 地址为 `FF:FF:FF:FF:FF:FF`，以便该帧被广播到连接在交换机上的所有设备（希望其中包括一台 DHCP 服务器）；帧的源 MAC 地址是 Bob 笔记本的地址 `00:16:D3:23:68:8A`。
1. 含有 DHCP 请求的广播以太网帧是 Bob 笔记本发给以太网交换机的第一个帧。交换机把这个入帧广播到所有出端口，包括连到路由器的那个端口。
1. 路由器在其 MAC 地址为 `00:22:6B:45:1F:1B` 的接口上收到含有 DHCP 请求的广播以太网帧，并从以太网帧中取出 IP 数据报。该数据报的广播 IP 目的地址表明这个 IP 数据报应由本节点的上层协议处理，于是数据报的载荷（一个 UDP 报文段）被多路分用（3.2 节）上交 UDP，DHCP 请求报文再从 UDP 报文段中取出。DHCP 服务器现在拿到了 DHCP 请求报文。
1. 假设路由器中运行的 DHCP 服务器能在 CIDR（4.3.3 节）块 `68.85.2.0/24` 中分配 IP 地址。在这个例子中，学校里使用的所有 IP 地址因此都在 Comcast 的地址块内。假设 DHCP 服务器把地址 `68.85.2.101` 分配给 Bob 的笔记本。DHCP 服务器创建一个 DHCP ACK 报文（4.3.3 节），其中含有这个 IP 地址、DNS 服务器的 IP 地址（`68.87.71.226`）、默认网关路由器的 IP 地址（`68.85.2.1`）以及子网块 `68.85.2.0/24`（等价地，"网络掩码"）。该 DHCP 报文被放入一个 UDP 报文段，报文段被放入一个 IP 数据报，数据报被放入一个以太网帧。该以太网帧的源 MAC 地址是路由器面向学校网络的接口地址（`00:22:6B:45:1F:1B`），目的 MAC 地址是 Bob 的笔记本（`00:16:D3:23:68:8A`）。
1. 含有 DHCP ACK 的以太网帧由路由器（单播）发送给交换机。由于交换机是自学习的（6.4.3 节），且此前收到过来自 Bob 笔记本的以太网帧（含有 DHCP 请求），交换机知道应当把目的地址为 `00:16:D3:23:68:8A` 的帧只转发到通往 Bob 笔记本的那个输出端口。
1. Bob 的笔记本收到含有 DHCP ACK 的以太网帧，从以太网帧中取出 IP 数据报，从 IP 数据报中取出 UDP 报文段，再从 UDP 报文段中取出 DHCP ACK 报文。Bob 的 DHCP 客户端随后记录自己的 IP 地址及其 DNS 服务器的 IP 地址，并把默认网关地址装入自己的 IP 转发表（4.1 节）。Bob 的笔记本将把所有目的地址在其子网 `68.85.2.0/24` 之外的数据报发送给默认网关。至此，Bob 的笔记本已初始化好网络组件，可以开始处理 Web 页面获取了。（注意：第 4 章给出的四步 DHCP 中，实际上只有最后两步是必需的。）

### 6.7.2　仍在起步：DNS 与 ARP

当 Bob 在浏览器中输入 `www.google.com` 的 URL 时，他就启动了一长串最终会让浏览器显示 Google 主页的事件。Bob 的浏览器首先创建一个 TCP 套接字（2.7 节），用来把 HTTP 请求（2.2 节）发送给 `www.google.com`。为创建该套接字，Bob 的笔记本需要知道 `www.google.com` 的 IP 地址。我们在 2.5 节学到，DNS 协议用来提供这种"名字到 IP 地址"的翻译服务。

1. 于是 Bob 笔记本上的操作系统创建一个 DNS 查询报文（2.5.3 节），把字符串 "www.google.com" 放在 DNS 报文的问题段中。这个 DNS 报文随后被放入一个 UDP 报文段，目的端口 53（DNS 服务器）。UDP 报文段再被放入一个 IP 数据报，IP 目的地址为 `68.87.71.226`（第 5 步 DHCP ACK 中返回的 DNS 服务器地址），源 IP 地址为 `68.85.2.101`。
1. Bob 的笔记本随后把含有 DNS 查询报文的数据报放入一个以太网帧。该帧将被（在链路层上）发送给 Bob 学校网络中的网关路由器。然而，尽管 Bob 的笔记本通过上面第 5 步的 DHCP ACK 报文知道了学校网关路由器的 IP 地址 `68.85.2.1`，它并不知道网关路由器的 MAC 地址。为获得网关路由器的 MAC 地址，Bob 的笔记本需要使用 ARP 协议（6.4.1 节）。
1. Bob 的笔记本创建一个 ARP 查询报文，目标 IP 地址为 `68.85.2.1`（默认网关），把该 ARP 报文放入一个目的地址为广播地址 `FF:FF:FF:FF:FF:FF` 的以太网帧，并把该以太网帧发送给交换机，交换机把帧交付给所有连接的设备，包括网关路由器。
1. 网关路由器在面向学校网络的接口上收到含有 ARP 查询报文的帧，发现 ARP 报文中目标 IP 地址 `68.85.2.1` 与其接口的 IP 地址匹配。于是网关路由器准备一个 ARP 应答，指出其 MAC 地址 `00:22:6B:45:1F:1B` 对应 IP 地址 `68.85.2.1`。它把 ARP 应答报文放入一个以太网帧，目的地址为 `00:16:D3:23:68:8A`（Bob 的笔记本），并把帧发送给交换机，交换机把帧交付给 Bob 的笔记本。
1. Bob 的笔记本收到含有 ARP 应答报文的帧，从 ARP 应答报文中取出网关路由器的 MAC 地址 `00:22:6B:45:1F:1B`。
1. Bob 的笔记本现在（终于！）可以把含有 DNS 查询的以太网帧寻址到网关路由器的 MAC 地址。注意这个帧中的 IP 数据报的 IP 目的地址是 `68.87.71.226`（DNS 服务器），而帧的目的地址是 `00:22:6B:45:1F:1B`（网关路由器）。Bob 的笔记本把这个帧发送给交换机，交换机把帧交付给网关路由器。

### 6.7.3　仍在起步：域内选路到 DNS 服务器

1. 网关路由器收到帧并取出含有 DNS 查询的 IP 数据报。路由器查找该数据报的目的地址 `68.87.71.226`，并从其转发表确定该数据报应发往图 6.34 中 Comcast 网络最左侧的路由器。该 IP 数据报被放入一个适合连接学校路由器与最左侧 Comcast 路由器那条链路的链路层帧，并在这条链路上发送出去。
1. Comcast 网络最左侧的路由器收到帧，取出 IP 数据报，检查数据报的目的地址 `68.87.71.226`，并从其转发表确定把数据报朝 DNS 服务器转发的出接口。该转发表已由 Comcast 的域内协议（如 RIP、OSPF 或 IS-IS，5.3 节）以及因特网的域间协议 BGP（5.4 节）填充。
1. 最终，含有 DNS 查询的 IP 数据报到达 DNS 服务器。DNS 服务器取出 DNS 查询报文，在其 DNS 数据库（2.5 节）中查找名字 `www.google.com`，找到含有 `www.google.com` 的 IP 地址 `64.233.169.105` 的 DNS 资源记录（假设该记录当前缓存在 DNS 服务器中；回忆这些缓存数据源自 google.com 的权威 DNS 服务器，2.5.2 节）。DNS 服务器构造一个含有该"主机名到 IP 地址"映射的 DNS 应答报文，把 DNS 应答报文放入一个 UDP 报文段，再把报文段放入一个寻址到 Bob 笔记本 `68.85.2.101` 的 IP 数据报。该数据报将经 Comcast 网络转发回学校路由器，再从那里经以太网交换机送到 Bob 的笔记本。
1. Bob 的笔记本从 DNS 报文中取出服务器 `www.google.com` 的 IP 地址。经过大量工作，Bob 的笔记本终于准备好联系 `www.google.com` 服务器了！

### 6.7.4　Web 客户端-服务器交互：TCP 与 HTTP

1. 现在 Bob 的笔记本有了 `www.google.com` 的 IP 地址，它可以创建 TCP 套接字（2.7 节），用来把 HTTP GET 报文（2.2.3 节）发送给 `www.google.com`。当 Bob 创建 TCP 套接字时，Bob 笔记本中的 TCP 必须先与 `www.google.com` 中的 TCP 执行三次握手（3.5.6 节）。于是 Bob 的笔记本首先创建一个目的端口为 80（HTTP）的 TCP SYN 报文段，把该 TCP 报文段放入一个目的 IP 地址为 `64.233.169.105`（`www.google.com`）的 IP 数据报，把数据报放入一个目的 MAC 地址为 `00:22:6B:45:1F:1B`（网关路由器）的帧，并把帧发送给交换机。
1. 学校网络、Comcast 网络与 Google 网络中的路由器使用各自路由器中的转发表，把含有 TCP SYN 的数据报朝 `www.google.com` 转发，如上面第 14–16 步所述。回忆决定分组在 Comcast 与 Google 网络之间域间链路上转发的路由器转发表项，是由 BGP 协议（第 5 章）确定的。
1. 最终，含有 TCP SYN 的数据报到达 `www.google.com`。TCP SYN 报文从数据报中取出，并被多路分用到与端口 80 关联的欢迎套接字。为 Google HTTP 服务器与 Bob 笔记本之间的 TCP 连接创建一个连接套接字（2.6 节）。生成一个 TCP SYNACK（3.5.6 节）报文段，放入一个寻址到 Bob 笔记本的数据报，最后放入一个适合连接 `www.google.com` 与其第一跳路由器那条链路的链路层帧。
1. 含有 TCP SYNACK 报文段的数据报经 Google、Comcast 与学校网络转发，最终到达 Bob 笔记本中的以太网控制器。数据报在操作系统内被多路分用到第 18 步创建的 TCP 套接字，该套接字进入连接已建立状态。
1. Bob 笔记本上的套接字现在（终于！）可以向 `www.google.com` 发送字节了，于是 Bob 的浏览器创建含有待取 URL 的 HTTP GET 报文（2.2.3 节）。HTTP GET 报文随后被写入套接字，GET 报文成为某个 TCP 报文段的载荷。该 TCP 报文段被放入数据报，并按上面第 18–20 步发送并交付到 `www.google.com`。
1. `www.google.com` 上的 HTTP 服务器从 TCP 套接字读取 HTTP GET 报文，创建一个 HTTP 响应报文（2.2 节），把所请求的网页内容放入 HTTP 响应报文的主体，并把该报文写入 TCP 套接字。
1. 含有 HTTP 应答报文的数据报经 Google、Comcast 与学校网络转发，到达 Bob 的笔记本。Bob 的浏览器程序从套接字读取 HTTP 响应，从 HTTP 响应主体中取出网页的 HTML，最后（终于！）显示出这个网页！

上面这个场景涵盖了大量网络知识！如果你理解了上述例子的大部分或全部，那么自你第一次读 1.1 节以来也已经走了很远——那时我们写道"本书的大部分内容都涉及计算机网络协议"，而你也许还在纳闷协议到底是什么！上面这个例子虽然详尽，却省略了若干可能出现的其他协议（例如学校网关路由器中运行的 NAT、接入学校网络的无线接入、用于接入学校网络或加密报文段／数据报的安全协议、网络管理协议），以及一些在公共因特网中会遇到的考虑（Web 缓存、DNS 层次结构）。本书后半部分将涵盖其中若干主题以及更多内容。

最后要指出，上面这个例子是对本书前半部分学过的许多协议所做的综合、整体、同时也非常"螺母与螺栓"式的考察。这个例子更侧重"如何"而不是"为何"。若想对网络协议设计获得更宽广、更具反思性的视角，不妨重读 4.5 节的"因特网的体系结构原则"及其中的参考文献。

## 6.8　小结

本章考察了链路层——它的服务、其运行背后的原理，以及若干运用这些原理实现链路层服务的重要具体协议。

我们看到，链路层的基本服务是把网络层数据报从一个节点（主机、交换机、路由器、WiFi 接入点）移动到相邻节点。我们看到，所有链路层协议在把帧经链路发送给相邻节点之前，都把网络层数据报封装进一个链路层帧。然而除这一共同的成帧功能之外，我们还学到不同链路层协议提供的链路接入、交付与传输服务差别很大。这些差异部分源于链路层协议必须在其上运行的链路类型极为多样：简单的点对点链路只有一对在单根"导线"上通信的发送方与接收方；多路访问链路由许多发送方与接收方共享，因此多路访问信道的链路层协议要有一个（其多路访问协议）来协调链路接入。在 VXLAN 与 MPLS 的情形下，连接两个节点的"链路"实际上本身就可能是一个网络。某种意义上，"把一个网络看作一条链路"的想法并不奇怪：例如，把家里的调制解调器／计算机连接到远端调制解调器／路由器的电话链路，实际上就是一条穿越复杂精巧的电话网的路径。

在链路层通信背后的原理中，我们考察了差错检测与纠正技术、多路访问协议、链路层编址、虚拟化（VLAN），以及扩展交换式局域网与数据中心网络的构建。今天链路层的大部分关注点都在这些交换式网络上。在差错检测／纠正方面，我们考察了如何通过在帧首部增加额外比特来检测（有时还能纠正）帧经链路传输时可能发生的比特翻转差错；我们讨论了简单的奇偶校验与校验和方案，以及更健壮的循环冗余检测。随后我们转向多路访问协议，识别并研究了三类协调广播信道访问的途径：信道划分（TDM、FDM）、随机接入（ALOHA 协议族与 CSMA 协议族）以及轮流（轮询与令牌传递）。我们研究了电缆接入网，发现它同时使用了其中多种多路访问方法。我们看到，多个节点共享单一广播信道的一个后果，就是需要在链路层提供节点地址。我们学到链路层地址与网络层地址相当不同，并且在因特网的情形下用一种特殊协议（ARP，地址解析协议）在这两种编址形式之间翻译；我们还详细研究了取得巨大成功的以太网协议。接着我们考察了共享广播信道的节点如何构成局域网，以及多个局域网如何互联成更大的局域网——这一切都不需要网络层选路介入来互联这些本地节点。我们还学到如何在一套物理局域网基础设施上创建多个虚拟局域网。

我们以链路虚拟化为链路层学习的收尾，用 MPLS 与 VXLAN 作为案例。随后概述了当今大型数据中心网络的设计。最后，通过找出获取一个简单网页所需的众多协议，为本章（也确为前五章）画上句号。讲完链路层，我们沿协议栈下行的旅程就结束了！当然，物理层位于链路层之下，但物理层的细节大概最好留给另一门课（例如通信理论课，而不是计算机网络课）。不过本章与第 1 章（1.2 节对物理介质的讨论）已触及物理层的若干方面；下一章研究无线链路特性时还会再看物理层。

虽然沿协议栈下行的旅程结束了，我们对计算机网络的学习尚未到头。接下来两章讲无线网络与网络安全。这两个主题都不便归入任何单一层次——事实上，它们横跨许多层。因此理解这些主题（在某些网络教材中被称为高级主题）需要在协议栈所有层都有坚实基础——而我们对链路层的学习现在已把这一基础补全了！

| 512 比特时间 | 5.12 微秒 | 10 Mbit/s 以太网上的退避粒度 |
| 交换机老化时间 | 典型 60 分钟 | 无帧则删除表项 |
| CRC 突发检测 | $\le r$ 比特必检 | $> r + 1$ 比特：概率 $1 - 0.5^{r}$ |

par(first-line-indent: 0em, leading: 1.45em)

最后把本章出现的互联设备按"工作层次—转发依据"并列对照。"工作层次"决定了设备能看到哪些首部字段，也决定了它的转发依据与隔离能力——这也是"交换机与路由器有何不同"这类问题的标准答法。

| **互联设备** | **工作层次与转发依据** |
| --- | --- |
| 中继器 / 集线器 | 物理层，逐比特再生并转发到所有其他端口 |
| 链路层交换机 | 第 2 层，按目的 MAC 地址查交换机表转发 |
| 路由器 | 第 3 层，按目的 IP 地址做最长前缀匹配转发 |
| 负载均衡器（"四层交换机"） | 按目的端口号 + 目的 IP 地址做分发决策 |
| VLAN 交换机 | 第 2 层，按端口所属 VLAN 隔离广播域 |
