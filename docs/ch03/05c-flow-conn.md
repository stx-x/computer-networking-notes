选择性确认 [RFC 2018] 使 TCP 接收方能够对失序的报文段逐个确认，而不只是累积确认最后一个正确收到的按序报文段。当它与选择性重传——跳过那些已被接收方选择性确认过的报文段的重传——结合使用时，TCP 就与我们所讲的一般的 SR 协议颇为相似了。因此，TCP 的差错恢复机制最好归类为 GBN 与 SR 的**混合体**。

# 3.5.5　流量控制

回忆一下，TCP 连接两端的每台主机都为该连接预留了一个接收缓冲区。当 TCP 连接收到正确且按序的字节时，它就把数据放入接收缓冲区。相应的应用进程会从这个缓冲区读取数据，但不一定在数据到达的那一刻就读。事实上，接收方应用可能正忙于其他任务，甚至可能在数据到达很久之后才去读。如果应用读取数据相对较慢，发送方就很容易因发送过多、过快的数据而使该连接的接收缓冲区溢出。

TCP 为其应用提供**流量控制**（flow control）服务，以消除发送方使接收方缓冲区溢出的可能。因此，流量控制是一种**速度匹配**服务——把发送方发送的速率与接收方应用读取的速率匹配起来。如前所述，TCP 发送方也可能因 IP 网络内部的拥塞而受到抑制；这种形式的发送方控制称为**拥塞控制**，将在 3.6 与 3.7 节详细探讨。尽管流量控制与拥塞控制所采取的动作相似（都是抑制发送方），但其原因显然截然不同。不幸的是，许多作者把这两个术语混用，聪明的读者应当把它们区分开来。下面讨论 TCP 如何提供流量控制服务。为看清主干，本节通篇假定 TCP 实现采取"接收方丢弃失序报文段"的做法。

TCP 通过让发送方维护一个称为**接收窗口**（receive window）的变量来提供流量控制。通俗地说，接收窗口用来告诉发送方：接收方还有多少可用的缓冲区空间。由于 TCP 是全双工的，连接每一端的发送方都各自维护一个不同的接收窗口。我们结合文件传输来考察接收窗口。假设主机 A 通过一条 TCP 连接向主机 B 发送一个大文件。主机 B 为该连接分配一个接收缓冲区，记其大小为 RcvBuffer。主机 B 的应用进程不时从该缓冲区读取数据。定义以下变量：

- `LastByteRead`：B 的应用进程从缓冲区读出的数据流中最后一个字节的编号；
- `LastByteRcvd`：从网络到达并已放入 B 的接收缓冲区的数据流中最后一个字节的编号。

由于 TCP 不允许使分配的缓冲区溢出，必须满足

$$
\text{LastByteRcvd} - \text{LastByteRead} \le \text{RcvBuffer}
$$

接收窗口记为 rwnd，被设为缓冲区中的空闲空间量：

$$
\text{rwnd} = \text{RcvBuffer} - [\text{LastByteRcvd} - \text{LastByteRead}]
$$

由于空闲空间随时间变化，rwnd 是动态的。变量 rwnd 如图 3.36 所示。

<Figure src="ch03/fig3-36.webp" caption="图 3.36　接收窗口（rwnd）与接收缓冲区（RcvBuffer）" />

连接如何使用变量 rwnd 来提供流量控制服务呢？主机 B 通过把它当前的 rwnd 值放入发往 A 的每个报文段的接收窗口字段，来告诉主机 A 该连接缓冲区还有多少空闲空间。初始时，主机 B 置 rwnd = RcvBuffer。注意，要做到这一点，主机 B 必须跟踪若干与该连接相关的变量。

主机 A 则跟踪两个变量 LastByteSent 与 LastByteAcked，含义不言自明。注意这两个变量之差 LastByteSent − LastByteAcked，就是 A 已送入该连接但尚未被确认的数据量。只要让未确认数据量小于 rwnd 的值，主机 A 就能确保不会使主机 B 的接收缓冲区溢出。因此，在连接的整个生命周期内，主机 A 都要保证

$$
\text{LastByteSent} - \text{LastByteAcked} \le \text{rwnd}
$$

这个方案有一个小的技术问题。设想主机 B 的接收缓冲区已满，于是 rwnd = 0。在向主机 A 通告 rwnd = 0 之后，再假设 B 没有数据要发给 A。现在考虑会发生什么：随着 B 的应用进程清空缓冲区，TCP 并不会向主机 A 发送带有新 rwnd 值的新报文段——事实上，TCP 只有在有数据要发或有确认要发时才向主机 A 发送报文段。因此，主机 A 永远得不到"B 的接收缓冲区已有空闲空间"的通知，A 就被阻塞住、再也发不出数据了！为解决这个问题，TCP 规范要求：当 B 的接收窗口为 0 时，主机 A 仍继续发送只含 1 个数据字节的报文段。这些报文段会被接收方确认；最终缓冲区开始腾空，确认中就会包含非零的 rwnd 值。

在描述了 TCP 的流量控制服务之后，还要简要指出：UDP **不**提供流量控制，因此报文段可能因接收方缓冲区溢出而在接收方丢失。例如，考虑从主机 A 的某个进程向主机 B 的某个进程发送一系列 UDP 报文段：在典型的 UDP 实现中，UDP 会把这些报文段追加到一个有限大小的缓冲区中，该缓冲区"位于"相应套接字（即进程之门）之前。进程一次从缓冲区读取一整个报文段；如果进程读取的速度不够快，缓冲区就会溢出，报文段就会被丢弃。

# 3.5.6　TCP 连接管理

本小节仔细考察 TCP 连接如何建立与拆除。这个话题看似不那么令人兴奋，但却很重要，因为 TCP 连接建立会显著增加可感知的时延（例如上网浏览时）；此外，许多最常见的网络攻击——包括极为流行的 SYN 洪泛攻击（见后文专栏）——利用的正是 TCP 连接管理中的弱点。

先看 TCP 连接如何建立。假设一台主机（客户）中运行的进程想与另一台主机（服务器）中的进程建立连接。客户应用进程首先告知客户 TCP：它想与服务器中的某个进程建立连接。随后客户端的 TCP 按下列方式与服务器端的 TCP 建立 TCP 连接：

- **第 1 步。** 客户端的 TCP 首先向服务器端的 TCP 发送一个特殊的 TCP 报文段。该报文段不含应用层数据，但其首部中的一个标志位（见图 3.28）——SYN 比特——被置为 1。因此，这个特殊报文段被称为 **SYN 报文段**。此外，客户随机选择一个初始序号（client*isn），并把它放入该初始 TCP SYN 报文段的序号字段。该报文段被封装进一个 IP 数据报，发往服务器。如何恰当地随机化 client*isn 的选择，以避免某些安全攻击，一直是人们相当关注的问题 [RFC 4987]。
- **第 2 步。** 一旦包含 TCP SYN 报文段的 IP 数据报到达服务器主机（假定它确实到达了！），服务器就从数据报中取出该 TCP SYN 报文段，为该连接分配 TCP 缓冲区与变量，并向客户 TCP 发送一个**允许连接**报文段。（第 8 章将会看到，在完成三次握手第三步之前就分配这些缓冲区与变量，使 TCP 容易遭受一种称为 SYN 洪泛的拒绝服务攻击。）该允许连接报文段同样不含应用层数据，但其首部包含三条重要信息：第一，SYN 比特置为 1；第二，TCP 报文段首部的确认字段置为 client*isn + 1；第三，服务器选择自己的初始序号（server*isn），并把它放入 TCP 报文段首部的序号字段。这个允许连接报文段实际上是在说："我收到了你要求建立连接的 SYN 报文，你的初始序号是 client*isn。我同意建立这条连接，我的初始序号是 server*isn。"该报文段被称为 **SYNACK 报文段**。
- **第 3 步。** 收到 SYNACK 报文段后，客户也要为该连接分配缓冲区与变量。随后，客户主机再向服务器发送一个报文段；这最后一个报文段对服务器的允许连接报文段予以确认（客户把 server_isn + 1 放入 TCP 报文段首部的确认字段来完成这一确认）。由于连接已经建立，SYN 比特置为 0。三次握手的这第三个阶段可以在报文段载荷中携带客户到服务器的数据。

这三步完成之后，客户与服务器主机就可以互相发送包含数据的报文段了；此后所有报文段中的 SYN 比特都将置为 0。注意，为建立连接，两台主机之间共发送三个分组，如图 3.37 所示。因此，这个连接建立过程常被称为**三次握手**。TCP 三次握手的若干方面将在章末习题中探讨（为什么需要初始序号？为什么需要三次握手而不是两次握手？）。有趣的是，攀岩者与保护者（位于攀岩者下方、负责处理其安全绳的人）所用的通信协议也是三次握手，与 TCP 完全相同，以确保在攀岩者开始向上攀爬之前双方都已准备就绪。

<Figure src="ch03/fig3-37.webp" caption="图 3.37　TCP 三次握手：报文段交换" />

既然发起三次握手的 TCP 客户必须等到收到服务器的 SYNACK 消息，才能知道服务器已接受连接、连接状态已初始化，那么任何这类握手协议（例如第 8 章将研究的 TLS 协议，或第 2 章研究过、本章稍后还会再谈的 QUIC 协议）在连接建立时似乎都天然存在一个 RTT 的时延。不过，如果客户与服务器此前通信过，就可以使用一种称为"快速打开"（fast open）的技术，把握手时间降到零！也就是说，客户可以向此前通信过的面向连接服务器立即发送数据，而不必执行传统三次握手的前两步。

快速打开（有时也称为 **0-RTT 握手**）的关键思想是：在传统三次握手期间，客户可以请求服务器提供一个快速打开 cookie，该 cookie 编码了未来连接所需的全部连接信息。这个 cookie 由客户与服务器各自保存。下次客户想与这台服务器建立连接时，就在发给服务器的第一条消息中带上该快速打开 cookie 以及应用层数据。服务器检查该 cookie，认为可以接受，就接受连接、根据 cookie 建立连接参数，并对初始消息中的应用层数据作出响应，回送服务器的应用层响应数据——从而完全避免了"发送数据前要等一个 RTT"的三次握手时延。

需要强调的是，快速打开只是对客户的一种可能的优化；服务器可能出于策略原因不接受快速打开 cookie，例如服务器不再想与该客户通信，或想强制该客户重新进行身份认证（例如 TLS 握手的情形）。客户把 cookie 端到服务器面前，并不意味着服务器非得"吃"（接受）这块 cookie！当然，快速打开 cookie 必须以密码学安全的方式生成，所用技术将在第 8 章研究。TCP 快速打开见 RFC 7413；TLS（见第 8 章及 RFC 8446）与 QUIC 协议 [RFC 9000; RFC 9002] 也支持零 RTT 的快速打开。

天下没有不散的筵席，TCP 连接也是如此。参与一条 TCP 连接的两个进程中的任何一个都可以结束该连接。连接结束时，主机中的"资源"（即缓冲区与变量）被释放。举例来说，假设客户决定关闭连接，如图 3.38 所示。客户应用进程发出关闭命令，这使客户 TCP 向服务器进程发送一个特殊的 TCP 报文段，其首部中的标志位——FIN 比特（见图 3.28）——置为 1。服务器收到该报文段后，向客户回送一个确认报文段；随后服务器发送自己的关闭报文段，其 FIN 比特置为 1；最后，客户确认服务器的关闭报文段。至此，两台主机中的所有资源都被释放。

<Figure src="ch03/fig3-38.webp" caption="图 3.38　关闭一条 TCP 连接" />

在一条 TCP 连接的生命期内，每台主机中运行的 TCP 协议会在各种 TCP 状态之间转换。图 3.39 展示了客户端 TCP 通常经历的一系列 TCP 状态。客户端 TCP 从 CLOSED 状态开始。客户侧应用发起一条新的 TCP 连接（在第 2 章的 Python 示例中，就是创建一个 Socket 对象），这使客户端的 TCP 向服务器端的 TCP 发送一个 SYN 报文段。发出 SYN 报文段后，客户端 TCP 进入 SYN*SENT 状态。在 SYN*SENT 状态下，客户端 TCP 等待来自服务器 TCP 的、包含对客户前一个报文段的确认且 SYN 比特置 1 的报文段。收到这样的报文段后，客户端 TCP 进入 ESTABLISHED 状态。在 ESTABLISHED 状态下，TCP 客户可以发送和接收包含载荷（即应用产生的）数据的 TCP 报文段。

<Figure src="ch03/fig3-39.webp" caption="图 3.39　客户端 TCP 通常经历的一系列 TCP 状态" />

假设客户应用决定关闭连接（注意，服务器也可以选择关闭连接）。这使客户端 TCP 发送一个 FIN 比特置 1 的 TCP 报文段，并进入 FIN*WAIT*1 状态。在 FIN*WAIT*1 状态下，客户端 TCP 等待来自服务器的带确认的 TCP 报文段。收到该报文段后，客户端 TCP 进入 FIN*WAIT*2 状态。在 FIN*WAIT*2 状态下，客户等待服务器发来另一个 FIN 比特置 1 的报文段；收到后，客户端 TCP 确认服务器的报文段，并进入 TIME*WAIT 状态。TIME*WAIT 状态让 TCP 客户在最终确认丢失时能够重发它。在 TIME_WAIT 状态停留的时间取决于具体实现，典型值为 30 秒、1 分钟和 2 分钟。等待结束后，连接正式关闭，客户侧的所有资源（包括端口号）都被释放。

<Figure src="ch03/fig3-40.webp" caption="图 3.40　服务器端 TCP 通常经历的一系列 TCP 状态" />

图 3.40 展示了在假定客户发起连接拆除的情况下，服务器端 TCP 通常经历的一系列状态，其转换不言自明。在这两个状态转换图中，我们只展示了 TCP 连接通常如何建立与关闭，没有描述某些病态场景，例如连接双方同时想发起或关闭连接。若想了解这些问题以及其他 TCP 高级话题，建议参阅 Stevens 的综合性著作 [Stevens 1994]。

以上讨论假定客户与服务器都准备好通信，即服务器正在客户发送 SYN 报文段的那个端口上监听。那么，当一台主机收到的 TCP 报文段的端口号或源 IP 地址与该主机中任何现有套接字都不匹配时，会发生什么？例如，假设某主机收到一个目的端口为 80 的 TCP SYN 分组，但该主机并不在端口 80 上接受连接（即它没有在端口 80 上运行 Web 服务器）。此时，该主机会向源端发送一个特殊的**重置报文段**，其 RST 标志位（见 3.5.2 节）置为 1。因此，当一台主机发送重置报文段时，它是在告诉源端："我没有与该报文段对应的套接字，请不要重发该报文段。"当主机收到的 UDP 分组的目的端口号与任何现有 UDP 套接字都不匹配时，主机会发送一个特殊的 ICMP 数据报，详见第 5 章。

<AsideCard title="安全聚焦 · SYN 洪泛攻击">

在讨论 TCP 三次握手时我们已经看到，服务器在收到 SYN 后会分配并初始化连接变量与缓冲区，然后回送一个 SYNACK，并等待客户的 ACK 报文段。如果客户不发送 ACK 来完成三次握手的第三步，服务器最终（往往在一分钟甚至更久之后）会终止这个**半开连接**，并回收已分配的资源。

正是这套 TCP 连接管理协议，为一种经典的拒绝服务（DoS）攻击——**SYN 洪泛攻击**（SYN flood attack）——埋下了伏笔。在这种攻击中，攻击者发送大量 TCP SYN 报文段，却不完成握手的第三步。面对这铺天盖地的 SYN 报文段，服务器的连接资源被大量分配给半开连接（而且永远不会被使用！），从而被耗尽；合法客户于是得不到服务。这类 SYN 洪泛攻击是最早被记录的 DoS 攻击之一；30 年过去了，SYN 洪泛攻击仍占 DoS 攻击的 14% [Fastly 2024]。所幸，一种称为 **SYN cookie** 的有效防御手段 [RFC 4987] 如今已部署在大多数主流操作系统中。SYN cookie 的工作方式如下：

- 服务器收到 SYN 报文段时，无法判断它来自合法用户还是 SYN 洪泛攻击的一部分。因此，服务器不为这个 SYN 创建半开 TCP 连接，而是生成一个初始 TCP 序号，该序号是 SYN 报文段的源/目的 IP 地址与端口号、以及一个只有服务器知道的秘密数的复杂函数（散列函数）。这个精心构造的初始序号就是所谓的"cookie"。服务器随后向客户发送带有该特殊初始序号的 SYNACK 分组。重要的是，服务器**不**保存这个 cookie，也不保存与该 SYN 对应的任何状态信息。
  - 合法客户会回送一个 ACK 报文段。服务器收到该 ACK 时，必须验证它确实对应此前发出的某个 SYN。可服务器对 SYN 报文段毫无记忆，这该如何做到？你可能已经猜到——靠 cookie。回忆一下，对于合法的 ACK，其确认字段的值等于 SYNACK 中的初始序号（此处即 cookie 值）加 1（见图 3.37）。于是服务器可以用 SYNACK 中的源/目的 IP 地址与端口号（它们与原始 SYN 中的相同）以及那个秘密数，再运行一遍同样的散列函数。如果函数结果加 1 恰好等于客户 ACK 中的确认（cookie）值，服务器就断定该 ACK 对应于此前的某个 SYN 报文段，因而有效；随后服务器创建一条完全打开的连接以及一个套接字。
  - 反之，如果客户不回送 ACK 报文段，那么最初那个 SYN 对服务器毫无损害，因为服务器尚未针对这个伪造的 SYN 分配任何资源。
