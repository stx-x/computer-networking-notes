# 3.3　无连接运输：UDP

本节仔细考察 UDP：它如何工作、能做些什么。建议读者回头参考 2.1 节（UDP 服务模型概述）与 2.6.1 节（用 UDP 进行套接字编程）。

为了引出 UDP 的讨论，不妨设想你要设计一个"极简"的运输协议：还能比"什么都不做"更简单吗？最朴素的想法是：发送端把应用进程交来的报文直接交给网络层，接收端把从网络层到达的报文直接交给应用进程。但正如上一节所学，我们总得比"什么都不做"多做一点——运输层至少要提供多路复用/多路分解服务，才能把数据在网络层与正确的应用层进程之间传递。

UDP（定义于 [RFC 768]）几乎就是一个运输协议所能做到的"最少限度"：除了多路复用/多路分解功能和一点点差错检查之外，它没有给 IP 增加任何东西。事实上，如果应用开发者选择 UDP 而不是 TCP，那么应用几乎就是在直接与 IP 打交道。UDP 从应用进程取出报文，附上用于复用/分解的源端口号与目的端口号字段，再加两个小字段，然后把生成的报文段交给网络层；网络层把该运输层报文段封装进一个 IP 数据报，尽最大努力把它交付给接收主机。若报文段到达接收主机，UDP 用目的端口号把报文段中的数据交付给正确的应用进程。

请注意：使用 UDP 时，发送方与接收方的运输层实体在传送报文段之前**没有握手过程**。正因如此，UDP 被称为是**无连接**的。

DNS 就是一个通常使用 UDP 的应用层协议的例子。主机中的 DNS 应用要发起查询时，构造一条 DNS 查询报文并交给 UDP。UDP 不与目的端系统中运行的 UDP 实体做任何握手，只在主机侧给报文加上首部字段，把生成的报文段交给网络层；网络层把 UDP 报文段封装进数据报，发往名字服务器。随后，发起查询的主机上的 DNS 应用等待查询的应答。如果没有收到应答（可能是因为底层网络丢失了查询或应答），它可能会重发查询、把查询发给另一台名字服务器，或者告知调用它的应用无法得到应答。

读到这里你可能会问：既然 TCP 提供可靠数据传输而 UDP 不提供，为什么应用开发者还会选择在 UDP 之上构建应用？难道 TCP 不总是更好的选择吗？答案是否定的。对某些应用而言，UDP 更合适，理由如下。

::: tip 要点

应用开发者选择 UDP 而非 TCP，通常是出于以下四个理由之一：

1. **对发送什么数据、何时发送，有更精细的应用层控制。** 使用 UDP 时，应用进程一旦把数据交给 UDP，UDP 就立即把它封装成报文段并马上交给网络层。而 TCP 有拥塞控制机制：当源与目的主机之间的某条链路出现严重拥塞时，TCP 会抑制运输层发送方；而且无论可靠交付需要多长时间，TCP 都会不断重传一个报文段，直到收到目的端的确认。实时应用往往要求一个最低发送速率，不愿报文段传输被过度延迟，并且能够容忍少量数据丢失——TCP 的服务模型与这类需求并不匹配。这类应用可以改用 UDP，并在应用自身中实现 UDP 那套"极简"报文段交付服务之外的任何附加功能。
1. **无需建立连接。** TCP 在开始传输数据之前要进行三次握手；UDP 则不做任何正式的准备就直接发送。因此 UDP 不会引入建立连接的额外时延。这大概就是 DNS 通常运行在 UDP 而非 TCP 之上的主要原因——若 DNS 跑在 TCP 上，会慢得多。2.2 节讲到，HTTP/1 与 HTTP/2 使用 TCP 而非 UDP，因为对于含文本的网页来说可靠性至关重要；但正如 2.2 节所讨论的，HTTP 中 TCP 连接建立的时延是下载 Web 文档时延的重要组成部分。事实上，HTTP/3 使用的是 QUIC 协议（Quick UDP Internet Connection，[RFC 9000; RFC 9002]），它以 UDP 作为底层运输协议，并在 UDP 之上于应用层实现可靠性。3.8 节将进一步考察 QUIC。
1. **无连接状态。** TCP 在端系统中维护连接状态，包括接收缓冲区与发送缓冲区、拥塞控制参数、序号与确认号参数等。3.5 节将会看到，实现 TCP 的可靠数据传输服务与拥塞控制正需要这些状态信息。UDP 则不维护连接状态，也不跟踪这些参数。因此，一个专门服务于某应用的服务器，在应用运行于 UDP 之上时通常能支撑多得多的活跃客户端。
1. **分组首部开销小。** TCP 每个报文段有 20 字节的首部开销，而 UDP 只有 8 字节。

:::

如图 3.6 所示，如今 UDP 与 TCP 有时都会被多媒体应用使用，例如因特网电话、实时视频会议、存储音频与视频的流式播放。这里只提一点：所有这些应用都能容忍少量分组丢失，因此可靠数据传输对应用的成功并非绝对关键。此外，像因特网电话和视频会议这类实时应用，对 TCP 的拥塞控制反应很差。基于这些原因，多媒体应用的开发者可能选择让应用运行在 UDP 而非 TCP 之上。当分组丢失率较低时，加上一些机构出于安全考虑封锁 UDP 流量（见第 8 章），TCP 在流媒体传输方面正变得越来越有吸引力。

尽管如今很常见，但在 UDP 之上运行多媒体应用仍需谨慎。如前所述，UDP 没有拥塞控制；而拥塞控制是防止网络陷入"几乎做不了有用功"的拥塞状态所必需的。如果所有人都开始以高比特率播放视频而不做任何拥塞控制，路由器处就会发生大量分组溢出，以致极少数 UDP 分组能够成功穿越源到目的的路径；更有甚者，不受控制的 UDP 发送方所引发的高丢失率，会使 TCP 发送方（如我们将会看到的，它们在拥塞面前会降低发送速率）大幅降低其速率。因此，UDP 缺少拥塞控制可能导致 UDP 收发方之间的高丢失率，并把 TCP 会话"挤出"网络。许多研究者提出了新的机制，强制包括 UDP 在内的所有源端执行自适应拥塞控制 [Mahdavi 1997; Floyd 2000; Kohler 2006; RFC 4340]。

在讨论 UDP 报文段结构之前，还要说明一点：应用使用 UDP 时，也是**可以**获得可靠数据传输的——只要把可靠性构建在应用自身之中（例如加入确认与重传机制，也就是下一节将要研究的那类机制）。前面提到，QUIC 协议就是在 UDP 之上、在应用层实现可靠性的。把可靠性直接构建在应用中，可以让应用"鱼与熊掌兼得"：应用进程能够可靠通信，却不必受制于 TCP 拥塞控制机制所施加的发送速率约束。

## 3.3.1　UDP 报文段结构

UDP 报文段结构如图 3.7 所示，由 RFC 768 定义。应用数据占据 UDP 报文段的**数据字段**。例如对 DNS 来说，数据字段包含一条查询报文或一条响应报文；对流式音频应用来说，音频采样填满数据字段。UDP 首部只有四个字段，每个字段两个字节。

如上一节所述，端口号使目的主机能够把应用数据交给目的端系统中正确的进程（即完成多路分解功能）。**长度字段**指明 UDP 报文段（首部加数据）的字节数。之所以需要显式的长度值，是因为数据字段的长度在不同 UDP 报文段之间可能不同。**校验和**由接收主机用来检验报文段在传输中是否引入了差错。（严格说来，校验和还要对 IP 首部中的若干字段一并计算，而不只是 UDP 报文段；这里略去这一细节，以便看清主干。）校验和的计算见下文；差错检测的基本原理见 6.2 节。

## 3.3.2　UDP 校验和

UDP 校验和提供差错检测：它用来判断 UDP 报文段从源到目的传输过程中，段内的比特是否发生了改变（例如由于链路噪声，或由于在路由器中缓存期间出错）。

在发送端，UDP 对报文段中所有 16 比特字求和，求和过程中遇到的任何溢出都**回卷**（wraparound），然后对结果取**反码**（1s complement），把该结果放入 UDP 报文段的校验和字段。下面给出一个简单的计算示例；高效实现的细节见 RFC 1071，在真实数据上的性能见 [Stone 1998; Stone 2000]。

假设有三个 16 比特字：

```text
0110011001100000
0101010101010101
1000111100001100
```

前两个 16 比特字之和为：

```text
0110011001100000
0101010101010101
────────────────
1011101110110101
```

再把第三个字加到上面的和上：

```text
  1011101110110101
+ 1000111100001100
──────────────────
1 0100101011000001
  0100101011000010
```

注意最后这次加法产生了溢出（最高位进位 1），该进位被回卷——即把 1 加到最低位，得到 0100101011000010。取反码就是把所有的 0 变成 1、所有的 1 变成 0，于是和 0100101011000010 的反码为 1011010100111101，这就是校验和。

在接收端，把包括校验和在内的四个 16 比特字全部相加。如果分组中没有引入差错，那么接收端的和显然应为 1111111111111111。只要其中有一位是 0，我们就知道分组中引入了差错。

你也许会问：许多链路层协议（包括流行的以太网协议）本身就提供差错检测，UDP 为什么还要提供校验和？原因在于，无法保证源与目的之间的**所有**链路都提供差错检测——其中某条链路可能使用了不提供差错检测的链路层协议。而且，即使报文段在链路上被正确传输，它在路由器内存中缓存时也可能引入比特差错。既然逐链路的可靠性和内存中的差错检测都不被保证，那么若端到端的数据传输服务要提供差错检测，UDP 就必须在运输层以**端到端**的方式提供差错检测。这正是系统设计中著名的**端到端原则**（end-end principle）的一个例子 [Saltzer 1984]：由于某些功能（此处是差错检测）必须在端到端的基础上实现，"与在高层提供这些功能的代价相比，放在低层实现的功能可能是冗余的，或者价值不大"。

由于 IP 被设计为可以运行在几乎任何链路层协议之上，运输层提供差错检查作为一种安全措施是有用的。不过，UDP 虽然提供差错检查，却**不做**任何差错恢复：某些 UDP 实现只是丢弃受损的报文段，另一些则把受损报文段连同警告一起交给应用。

UDP 的讨论到此结束。我们很快会看到，TCP 为其应用提供可靠数据传输，以及 UDP 所不提供的其他服务；自然，TCP 也比 UDP 复杂得多。不过在讨论 TCP 之前，先退一步考察可靠数据传输的基本原理，会很有帮助。
