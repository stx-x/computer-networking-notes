# 3.8　运输层功能的演进

本章对具体因特网运输协议的讨论集中在 UDP 与 TCP——因特网运输层的两匹"老黄牛"。然而正如我们所见，四十年来使用这两个协议的经验已经识别出它们各自并不理想适用的情形，因此自这两个协议最初标准化以来，运输层功能的设计与实现一直在演进。3.5 与 3.7.2 节已经考察了 TCP 演进中的若干进展。

**数据报拥塞控制协议**（DCCP）[RFC 4340] 提供一种低开销、面向报文的、类 UDP 的不可靠服务，但带有一种由应用选择、且与 TCP 兼容的拥塞控制形式。DCCP 可选拥塞控制形式之一是**TCP 友好速率控制**（TCP-Friendly Rate Control, TFRC）协议 [RFC 5348]，它把 TCP 拥塞控制中的"锯齿"行为（见图 3.50）平滑掉，同时保持长期发送速率"相当"接近 TCP。由于发送速率比 TCP 更平滑，TFRC 很适合 IP 电话、流式媒体等多媒体应用。TFRC 是一种"基于方程"的协议：它把测得的丢包率作为某个方程的输入 [Padhye 2000]，该方程估计若一个 TCP 会话经历该丢包率时的吞吐量，再把该速率作为 TFRC 的目标发送速率。DCCP 设想用于流式媒体这类应用——它们能够利用数据交付的及时性与可靠性之间的折衷，但又希望对网络拥塞作出响应。若使用 DCCP 的应用需要可靠或半可靠的数据传输，那么这将在应用自身内部完成，很可能采用我们在 3.4 节研究过的机制。

除这些变化之外，过去十年运输层还经历了一场更为剧烈的变革——TCP 的可靠数据传输、流量控制、拥塞控制及其他服务，以**应用层模块**的形式迁移到了应用层，在 UDP 之上提供类 TCP 的服务。最能体现这一趋势的著名协议是 **QUIC**（Quick UDP Internet Connections）[RFC 9000; RFC 9002]，我们在 2.2 节讨论 HTTP/3 时已接触过它，下面将进一步考察。

今天，应用设计者仍可在操作系统实现的本地 TCP 与 UDP 服务之间选择；但现在有了第三种选择——应用设计者可以在应用层、基于 UDP 用 QUIC"自建"运输层服务。QUIC 早期版本的作者 [Langley 2017] 指出，在应用层实现运输层功能意味着可以按"应用更新的时间尺度"修改 QUIC，即特性迭代速度远快于 TCP 或 UDP 的更新速度。或者，正如 RFC 1263 颇为幽默地所言："能够在比标准委员会就'合适的开会时间'达成一致更短的时间内，设计并分发协议。"

下面仔细看看 QUIC。它也将作为我们运输层学习的一个漂亮收束，因为 QUIC 用到了本章研究过的可靠数据传输、拥塞控制和连接管理中的许多方法。在往下读之前，不妨回顾 2.2.7 节与图 2.11 中关于 QUIC 的讨论。QUIC 的一些主要特性包括：

::: tip 要点

1. **面向连接且安全。** 与 TCP 一样，QUIC 是两个端点之间面向连接的协议，这需要端点之间握手以建立 QUIC 连接状态，其中两项状态就是源连接 ID 与目的连接 ID。所有 QUIC 分组都加密；如图 3.57 所示，QUIC 把建立连接状态所需的握手与身份认证、加密所需的握手（传输层安全 TLS 的话题，将在第 8 章研究）合并在一起，从而比"先用多个 RTT 建立 TCP 连接、再在该 TCP 连接上建立 TLS 连接"的情形快得多地完成连接建立。
1. **流（stream）。** QUIC 允许若干不同的应用层"流"复用到一条 QUIC 连接上。流是两个 QUIC 端点之间可靠、按序、双向交付数据的抽象。每条连接有一个连接 ID，连接中的每个流有一个流 ID，这两个 ID 都包含在 QUIC 分组首部中（连同其他首部信息）。来自多个流的数据可以装在单个 QUIC 报文段中，由 UDP 承载。流控制传输协议（SCTP）[RFC 4960; RFC 3286] 是更早的一种可靠的、面向报文的协议，它开创了"若干应用层流复用到一条 SCTP 连接"的概念。
1. **可靠的、TCP 友好的、带拥塞控制的数据传输。** 如图 3.57 所示，QUIC 为每个 QUIC 流分别提供可靠数据传输。图 3.57(a) 展示 HTTP/1.1 在单条 TCP 连接上发送多个 HTTP 请求的情形：由于 TCP 提供可靠、按序的字节交付，这意味着多个 HTTP 请求必须在目的 HTTP 服务器处按序交付。因此，若某个 HTTP 请求的字节丢失，其余 HTTP 请求就无法交付，直到丢失的字节被重传并被 HTTP 服务器端的 TCP 正确收到——这就是我们在 2.2.5 节遇到的所谓**队头阻塞**（HOL blocking）问题。由于 QUIC 在每条流的基础上提供可靠按序交付，一个丢失的 UDP 报文段只影响其数据被装在该报文段中的那些流，其他流中的 HTTP 消息仍可继续被接收并交付给应用。QUIC 使用与 TCP 类似的确认机制提供可靠数据传输，见 [RFC 5681]。
1. **QUIC 的拥塞控制基于 TCP NewReno** [RFC 6582]，后者是对我们在 3.7.2 节研究过的 TCP Reno 协议的轻微修改。QUIC 关于丢包检测与拥塞控制的规范 [RFC 9002] 指出："熟悉 TCP 丢包检测与拥塞控制的读者，会发现这里的算法与众所周知的 TCP 算法并行不悖。"既然我们已在 3.7 节仔细研究过 TCP 的拥塞控制，读 QUIC 拥塞控制算法的规范细节时自会感到轻车熟路！

:::
