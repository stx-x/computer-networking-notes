# 3.5　面向连接的运输：TCP

掌握了可靠数据传输的基本原理之后，现在转向 TCP——因特网的运输层面向连接的可靠运输协议。本节将会看到，为了提供可靠数据传输，TCP 依赖上一节讨论的许多基本原理，包括差错检测、重传、累积确认、定时器，以及用于序号和确认号的首部字段。TCP 最初定义于 RFC 793，此后多年来又由若干 RFC 更新，包括 RFC 1122、RFC 2018、RFC 5681 和 RFC 7323；这些更新与原始的 RFC 793 规范已被汇总进新的 RFC [RFC 9293]，后者正式"废弃"了 RFC 793。

## 3.5.1　TCP 连接

TCP 被称为是**面向连接**的，因为在一个应用进程开始向另一个应用进程发送数据之前，两个进程必须先相互"握手"——即它们必须交换一些预备报文段，以确立后续数据传输所需的参数。作为 TCP 连接建立的一部分，连接双方都会初始化许多与该 TCP 连接相关的 TCP 状态变量（其中许多将在本节和 3.7 节讨论）。

TCP 的"连接"并不是电路交换网络中那种端到端的 TDM 或 FDM 电路，而是一种**逻辑**连接，其公共状态只存在于两个通信端系统的 TCP 之中。回忆一下，由于 TCP 协议只运行在端系统中、不运行在中间网络设备（路由器和链路层交换机）中，中间网络设备并不维护 TCP 连接状态。事实上，中间路由器对 TCP 连接完全无感：它们看到的是数据报，而不是连接。

TCP 连接提供**全双工**服务：若一台主机上的进程 A 与另一台主机上的进程 B 之间存在一条 TCP 连接，则应用层数据可以同时从 A 流向 B、从 B 流向 A。TCP 连接也总是**点对点**的，即连接在单个发送方与单个接收方之间。所谓的"多播"（multicasting，见本书在线补充材料）——在一次发送操作中把数据从一个发送方传给多个接收方——用 TCP 是做不到的。对 TCP 而言，两台主机正好，三台就太多了！

下面看看 TCP 连接是如何建立的。假设一台主机中运行的进程想要与另一台主机中的进程建立连接。回忆一下，发起连接的进程称为**客户进程**，另一个进程称为**服务器进程**。客户应用进程首先告知客户运输层：它想与服务器中的某个进程建立连接。如 2.6.2 节所述，Python 客户端程序通过发出如下命令来完成这一步：

```text
clientSocket.connect((serverName, serverPort))
```

其中 `serverName` 是服务器名，`serverPort` 标识服务器上的进程。随后，客户端的 TCP 开始与服务器端的 TCP 建立一条 TCP 连接。本节末尾将较详细地讨论连接建立过程；眼下只需知道：客户首先发送一个特殊的 TCP 报文段，服务器用第二个特殊报文段响应，最后客户再用第三个特殊报文段响应。前两个报文段不携带有效载荷（即不携带应用层数据），第三个报文段则可能携带有效载荷。由于两台主机之间共发送三个报文段，这个连接建立过程常被称为**三次握手**（three-way handshake）。

<AsideCard title="历史回眸 · Vinton Cerf、Robert Kahn 与 TCP/IP">

20 世纪 70 年代初，分组交换网络开始大量涌现，因特网的前身 ARPAnet 只是众多网络中的一个。这些网络各有自己的协议。两位研究者——Vinton Cerf 与 Robert Kahn——认识到把这些网络互连起来的重要性，发明了一种跨网络协议 TCP/IP，即传输控制协议/网际协议（Transmission Control Protocol/Internet Protocol）。虽然 Cerf 和 Kahn 起初把该协议视为单一实体，后来它被拆分为 TCP 与 IP 两部分，各自独立运行。1974 年 5 月，Cerf 和 Kahn 在 *IEEE Transactions on Communications Technology* 上发表了关于 TCP/IP 的论文 [Cerf 1974]。

TCP/IP 协议是当今因特网的命脉，而它被设计出来的时候，个人计算机、工作站、智能手机和平板电脑都还不存在，以太网、电缆、DSL、WiFi 等各种接入网技术尚未普及，Web、社交媒体和流媒体视频更是闻所未闻。Cerf 和 Kahn 预见到需要这样一种网络协议：一方面能为尚未定义的各类应用提供广泛支持，另一方面能让任意主机和链路层协议互操作。

2004 年，Cerf 和 Kahn 获得美国计算机学会（ACM）图灵奖——被誉为"计算领域的诺贝尔奖"——以表彰他们"在互连网络方面的开创性工作，包括因特网基础通信协议 TCP/IP 的设计与实现，以及在网络领域的卓越领导"。

</AsideCard>

一旦 TCP 连接建立起来，两个应用进程就可以互相发送数据。先看客户进程向服务器进程发送数据的情形。如 2.6 节所述，客户进程通过套接字（进程的"门"）传递数据流；数据一旦穿过这道门，就交到了客户端 TCP 的手中。如图 3.27 所示，TCP 把这些数据导向该连接的**发送缓冲区**（send buffer），它是三次握手期间预留的缓冲区之一。TCP 会不时地从发送缓冲区中取出一块块数据，交给网络层。有趣的是，最初的 TCP 规范 [RFC 793] 在"TCP 究竟应在何时真正发送缓冲区中的数据"这一点上非常随性，只说要"按自己的方便，把数据放在报文段中发送"。

一个报文段中能取出并放入的最大数据量，受**最大报文段长度**（maximum segment size, MSS）限制。MSS 的典型确定方法是：先确定本地发送主机所能发送的最大链路层帧长度（即所谓的**最大传输单元**，MTU），再据此设定 MSS，使得一个 TCP 报文段（封装进 IP 数据报后）加上 TCP/IP 首部长度（通常 40 字节）能装进一个链路层帧。以太网与 PPP 链路层协议的 MTU 都是 1500 字节，因此 MSS 的典型值为 1460 字节。也有人提出发现**路径 MTU**——从源到目的的所有链路上所能发送的最大链路层帧 [RFC 1191]——并据此设定 MSS 的方法。注意，MSS 指的是报文段中**应用层数据的最大量**，而不是包含首部的 TCP 报文段的最大长度。（这个术语容易混淆，但既然已经根深蒂固，我们也只好接受。）

TCP 为每一块客户数据配上 TCP 首部，从而形成 TCP 报文段。报文段被下交给网络层，在网络层各自封装进 IP 数据报，随后发入网络。在另一端，TCP 收到报文段后，把该报文段的数据放入该 TCP 连接的**接收缓冲区**（receive buffer），如图 3.27 所示；应用从该缓冲区读取数据流。连接的每一侧都有自己的发送缓冲区和接收缓冲区。

<Figure src="ch03/fig3-27.webp" caption="图 3.27　TCP 发送缓冲区与接收缓冲区" />

由此可见，一条 TCP 连接由一台主机中与某进程相连的一组缓冲区、变量和套接字连接，以及另一台主机中与另一进程相连的另一组缓冲区、变量和套接字连接共同构成。如前所述，主机之间的网络设备（路由器、交换机和转发器）中不会为该连接分配任何缓冲区或变量。

## 3.5.2　TCP 报文段结构

简要了解了 TCP 连接之后，来考察 TCP 报文段的结构。TCP 报文段由首部字段和一个数据字段组成，数据字段包含一块应用数据。如上所述，MSS 限制了报文段数据字段的最大长度。当 TCP 发送一个大文件（例如网页中的一幅图像）时，通常把文件切分成 MSS 大小的块（最后一块往往小于 MSS）。而交互式应用通常传输小于 MSS 的数据块；例如 Telnet 和 ssh 这类远程登录应用，TCP 报文段中的数据字段常常只有 1 个字节。由于 TCP 首部通常为 20 字节（比 UDP 首部多 12 字节），Telnet 和 ssh 发送的报文段长度可能只有 21 字节。

图 3.28 给出了 TCP 报文段的结构。与 UDP 一样，首部包含源端口号和目的端口号，用于与上层应用之间数据的多路复用/多路分解；也与 UDP 一样，首部包含校验和字段。此外，TCP 报文段首部还包含下列字段：

- **32 比特的序号字段**与**32 比特的确认号字段**，供 TCP 发送方与接收方实现可靠数据传输服务时使用，详见下文。
- **16 比特的接收窗口字段**，用于流量控制。稍后会看到，它用来指示接收方愿意接受的字节数。
- **4 比特的首部长度字段**，以 32 比特字为单位指明 TCP 首部的长度。由于存在选项字段，TCP 首部长度可变。（通常选项字段为空，因此典型 TCP 首部长度为 20 字节。）
- **选项字段**，长度可变，可选。当收发双方协商最大报文段长度（MSS），或在高速网络中使用窗口缩放因子时，会用到该字段；此外还定义了时间戳选项。详见 RFC 854 与 RFC 1323。
- **标志字段**，共 6 比特。ACK 比特用于指示确认号字段中的值有效，即该报文段包含对某个已成功接收的报文段的确认。RST、SYN 和 FIN 比特用于连接的建立与拆除，本节末尾将讨论。CWR 与 ECE 比特用于显式拥塞通知，见 3.7.2 节。置位 PSH 比特表示接收方应立即把数据交给上层。最后，URG 比特用于指示本报文段中存在被发送侧上层实体标记为"紧急"的数据，这些紧急数据的最后一个字节的位置由 16 比特的**紧急数据指针字段**指明；当存在紧急数据时，TCP 必须通知接收侧上层实体，并向其传递指向紧急数据末尾的指针。（实践中，PSH、URG 及紧急数据指针都未被使用，这里提及只是为了完整。）

<Figure src="ch03/fig3-28.webp" caption="图 3.28　TCP 报文段结构" />

作为教师的经验告诉我们，学生有时会觉得分组格式的讨论枯燥甚至有点无聊。若想以一种有趣而奇特的方式了解 TCP 首部字段——尤其如果你和我们一样热爱乐高积木——可参阅 [Pomeranz 2010]。

### 序号与确认号

TCP 报文段首部中最重要的两个字段是序号字段和确认号字段，它们是 TCP 可靠数据传输服务的关键部分。不过在讨论如何用这两个字段提供可靠数据传输之前，先解释 TCP 究竟在这两个字段里放了什么。

TCP 把数据看作**无结构的、但有序的字节流**。TCP 对序号的使用正体现了这一观点：序号是建立在**传输的字节流**之上，而不是建立在**传输的报文段序列**之上。因此，一个报文段的序号就是该报文段数据字段中**第一个字节**的字节流编号。

看一个例子。假设主机 A 中的某个进程要通过一条 TCP 连接向主机 B 中的某个进程发送一个数据流。主机 A 的 TCP 会隐式地为数据流中的每个字节编号。假设该数据流是一个 500 000 字节的文件，MSS 为 1000 字节，且数据流的第一个字节编号为 0。如图 3.29 所示，TCP 由该数据流构造出 500 个报文段：第一个报文段的序号为 0，第二个为 1000，第三个为 2000，依此类推。每个序号都被填入相应 TCP 报文段首部的序号字段中。

<Figure src="ch03/fig3-29.webp" caption="图 3.29　把文件数据划分成 TCP 报文段" />

再来看确认号。它比序号要稍难一些。回忆一下，TCP 是全双工的，因此主机 A 在向 B 发送数据的同时，也可能在从 B 接收数据（同属一条 TCP 连接）。从 B 到达的每个报文段都带有 B 到 A 数据流的序号。**主机 A 填入其报文段的确认号，是主机 A 期望从主机 B 收到的下一个字节的序号**。多看几个例子有助于理解。

假设主机 A 已从 B 收到编号 0～535 的所有字节，并且即将向 B 发送一个报文段。此时主机 A 正在等待字节 536 以及 B 数据流中其后的所有字节，于是 A 在发往 B 的报文段的确认号字段中填入 536。

再看一例。假设主机 A 从 B 收到了一个包含字节 0～535 的报文段，又收到了另一个包含字节 900～1000 的报文段；由于某种原因，A 尚未收到字节 536～899。在这个例子中，A 仍在等待字节 536（及其后的字节），以便重建 B 的数据流。因此，A 发往 B 的下一个报文段将在确认号字段中填入 536。由于 TCP 只确认到数据流中第一个缺失字节之前的所有字节，因此说 TCP 提供**累积确认**。

上例还引出一个重要而微妙的问题：主机 A 在收到第二个报文段（字节 536～899）之前，就先收到了第三个报文段（字节 900～1000），即第三个报文段**失序**到达。微妙之处在于：主机在 TCP 连接中收到失序报文段时该怎么办？有趣的是，TCP 的 RFC 对此未作任何规定，而是把决定权留给实现 TCP 的程序员。基本上有两种选择：(1) 接收方立即丢弃失序报文段（如前所述，这可以简化接收方设计）；(2) 接收方保留失序字节，并等待缺失字节来填补空隙。显然，就网络带宽而言后一种选择更高效，实践中采用的也是这种做法。

在图 3.29 中，我们假定初始序号为 0。实际上，TCP 连接的两端都会**随机**选择一个初始序号。这样做是为了尽量减少一种可能：两台主机之间早先已终止的某条连接遗留在网络中的报文段，被误认为是这两台主机之间后来某条连接（恰好使用了与旧连接相同的端口号）中的有效报文段 [Sunshine 1978]。

### Telnet：序号与确认号的一个案例

Telnet（定义于 RFC 854）是一种用于远程登录的流行应用层协议。它运行在 TCP 之上，被设计为可在任意一对主机之间工作。与第 2 章讨论的批量数据传输应用不同，Telnet 是一种交互式应用。这里讨论一个 Telnet 例子，因为它能很好地说明 TCP 的序号与确认号。需要指出，如今用户更愿意使用 SSH 协议而不是 Telnet，因为 Telnet 连接中发送的数据（包括口令！）未加密，使 Telnet 易受窃听攻击。

假设主机 A 向主机 B 发起一个 Telnet 会话。由于 A 发起会话，它被称为客户，B 被称为服务器。用户在客户端键入的每个字符都会被送到远程主机，远程主机则回送每个字符的一个副本，显示在 Telnet 用户的屏幕上。这种"回显"用于确保 Telnet 用户看到的字符已在远端被接收并处理。因此，从用户按键到字符显示在显示器上，每个字符都要在网络中往返两次。

现在假设用户键入了一个字母 'C'，然后端起咖啡喝了一口。我们来考察客户与服务器之间发送的 TCP 报文段。如图 3.30 所示，假设客户与服务器的初始序号分别为 42 和 79。回忆一下，报文段的序号就是其数据字段中第一个字节的序号，因此客户发送的第一个报文段序号为 42，服务器发送的第一个报文段序号为 79。再回忆一下，确认号是主机期望的下一个数据字节的序号。在 TCP 连接建立之后、尚未发送任何数据之前，客户在等待字节 79，服务器在等待字节 42。

如图 3.30 所示，共发送三个报文段。第一个报文段从客户发往服务器，数据字段中装着字母 'C' 的 1 字节 ASCII 表示；该报文段的序号字段为 42。又因为客户尚未从服务器收到任何数据，这个报文段的确认号字段为 79。

<Figure src="ch03/fig3-30.webp" caption="图 3.30　一个简单 Telnet 应用在 TCP 上的序号与确认号" />

第二个报文段从服务器发往客户，它有两个用途。其一，它确认服务器已收到的数据：通过在确认号字段填入 43，服务器告诉客户，它已成功收到直到字节 42 的全部内容，现在正等待字节 43 及其后的字节。其二，它回显字母 'C'，因此第二个报文段的数据字段中是 'C' 的 ASCII 表示。这个报文段的序号为 79，即该 TCP 连接服务器到客户数据流的初始序号，因为这是服务器发送的第一个数据字节。注意，对客户到服务器数据的确认，是搭载在承载服务器到客户数据的报文段中传送的；这种确认被称为**捎带**（piggybacked）在服务器到客户的数据报文段上。

第三个报文段从客户发往服务器，其唯一目的是确认它已从服务器收到的数据。（回忆一下，第二个报文段中包含了服务器到客户的字母 'C'。）该报文段的数据字段为空，即这个确认没有捎带任何客户到服务器的数据。它的确认号字段为 80，因为客户已收到直到序号 79 的字节流，现在正等待字节 80 及其后的字节。你也许会觉得奇怪：这个报文段不含数据，为什么还有序号？但由于 TCP 有序号字段，报文段总得有个序号。

## 3.5.3　往返时间估计与超时

与 3.4 节的 rdt 协议一样，TCP 使用超时/重传机制来从丢失的报文段中恢复。这在概念上很简单，但当我们在 TCP 这样的实际协议中实现超时/重传机制时，会出现许多微妙的问题。最明显的问题大概就是超时间隔该取多长。显然，超时应大于该连接的往返时间（RTT），即从报文段发出到它被确认所经历的时间；否则就会发送不必要的重传。但究竟要大多少？RTT 又该如何估计？是否应为每一个未确认的报文段都关联一个定时器？问题真不少！本节的讨论基于 [Jacobson 1988] 中关于 TCP 的工作，以及当前 IETF 关于 TCP 定时器管理的建议 [RFC 6298]。

### 估计往返时间

先看 TCP 如何估计发送方与接收方之间的往返时间。做法如下：一个报文段的**样本 RTT**（SampleRTT）是该报文段从发出（即交给 IP）到收到其确认之间所经历的时间。多数 TCP 实现并不为每个发送的报文段都测量一个 SampleRTT，而是在任一时刻只测量一个 SampleRTT。也就是说，在任何时刻，只对某一个已发送但尚未确认的报文段估计 SampleRTT，因而大约每个 RTT 得到一个新的 SampleRTT 值。此外，TCP 从不为**重传**过的报文段计算 SampleRTT，只对**仅发送过一次**的报文段测量 SampleRTT [Karn 1987]。（章末有一道习题请你思考其中的原因。）

显然，由于路由器中的拥塞以及端系统负载的变化，SampleRTT 的值会随报文段不同而波动。由于这种波动，任何一个给定的 SampleRTT 值都可能是非典型的。为了估计一个典型的 RTT，自然要对 SampleRTT 值取某种平均。TCP 维护 SampleRTT 值的一个平均值，称为 EstimatedRTT。每得到一个的新 SampleRTT，TCP 就按下式更新 EstimatedRTT：

$$
\text{EstimatedRTT} = (1 - \alpha) \cdot \text{EstimatedRTT} + \alpha \cdot \text{SampleRTT} \tag{3.1}
$$

上式写成程序设计语言语句的形式——EstimatedRTT 的新值，是 EstimatedRTT 旧值与 SampleRTT 新值的加权组合。推荐的 $\alpha$ 取值为 0.125（即 $\frac{1}{8}$）[RFC 6298]，此时上式变为：

$$
\text{EstimatedRTT} = 0.875 \cdot \text{EstimatedRTT} + 0.125 \cdot \text{SampleRTT}
$$

注意，EstimatedRTT 是 SampleRTT 值的加权平均。正如章末一道习题所讨论的，这种加权平均给予**近期**样本的权重高于**旧**样本。这很自然，因为近期样本更好地反映了网络当前的拥塞状况。在统计学中，这样的平均值称为**指数加权移动平均**（EWMA）。EWMA 中之所以有"指数"二字，是因为随着更新不断进行，某个给定 SampleRTT 的权重按指数速度衰减。章末习题将请你推导 EstimatedRTT 中的指数项。

图 3.31 给出了 gaia.cs.umass.edu（位于马萨诸塞州阿默斯特）到 fantasia.eurecom.fr（位于法国南部）之间一条 TCP 连接在 $\alpha = \frac{1}{8}$ 时的 SampleRTT 值与 EstimatedRTT。可以看到，SampleRTT 的波动在 EstimatedRTT 的计算中被平滑掉了。

<Figure src="ch03/fig3-31.webp" caption="图 3.31　RTT 样本与 RTT 估计" />

除了 RTT 的估计值，RTT 的**变化程度**也是很有价值的度量。[RFC 6298] 把 RTT 偏差 DevRTT 定义为 SampleRTT 通常偏离 EstimatedRTT 多少的估计：

$$
\text{DevRTT} = (1 - \beta) \cdot \text{DevRTT} + \beta \cdot \lvert \text{SampleRTT} - \text{EstimatedRTT} \rvert \tag{3.2}
$$

注意，DevRTT 是 SampleRTT 与 EstimatedRTT 之差的 EWMA。若 SampleRTT 波动很小，DevRTT 就小；反之若波动很大，DevRTT 就大。$\beta$ 的推荐值为 0.25。

### 设置与管理重传超时间隔

有了 EstimatedRTT 与 DevRTT，TCP 的超时间隔应取何值？显然，该间隔应大于或等于 EstimatedRTT，否则就会发送不必要的重传；但也不能比 EstimatedRTT 大太多，否则报文段丢失时 TCP 不能迅速重传，导致很大的数据传输时延。因此，理想的做法是把超时时间设为 EstimatedRTT 加上一定余量：SampleRTT 波动大时余量应大，波动小时余量应小。DevRTT 的值正该在此发挥作用。TCP 确定重传超时间隔的方法把这些考虑都纳入了：

$$
\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \cdot \text{DevRTT} \tag{3.3}
$$

<AsideCard title="实践中的原理 · TCP 的可靠数据传输">

TCP 通过使用肯定确认和定时器来提供可靠数据传输，做法与 3.4 节所研究的十分相似。TCP 对正确收到的数据予以确认，并在报文段或其确认被认为丢失或损坏时重传报文段。某些版本的 TCP 还有隐式的 NAK 机制——借助 TCP 的**快速重传**机制，收到对某报文段的三个重复 ACK，就相当于对**下一个**报文段的隐式 NAK，从而在超时之前触发该报文段的重传。TCP 用序号让接收方能够识别丢失或重复的报文段。与可靠数据传输协议 rdt3.0 一样，TCP 自身无法确知一个报文段或其 ACK 究竟是丢失、损坏还是被过度延迟；在发送方，TCP 的响应都一样：重传该报文段。

TCP 也使用流水线，允许发送方在任一时刻有多个已发送但尚未确认的报文段在途。前面已经看到，当报文段长度与往返时延之比很小时，流水线能大幅提高会话吞吐量。发送方可以拥有的在途未确认报文段的具体数目，由 TCP 的流量控制与拥塞控制机制决定；TCP 流量控制在本节末尾讨论，拥塞控制在 3.7 节讨论。眼下只需知道 TCP 发送方使用流水线。

推荐的初始 TimeoutInterval 值为 1 秒 [RFC 6298]。此外，一旦发生超时，TimeoutInterval 的值加倍，以避免对随后很快就会被确认的报文段过早超时。不过，一旦收到报文段并更新了 EstimatedRTT，TimeoutInterval 就又用上面的公式重新计算。

## 3.5.4　可靠数据传输

回忆一下，因特网的网络层服务（IP 服务）是不可靠的：IP 不保证数据报交付，不保证数据报按序交付，也不保证数据报中数据的完整性。在 IP 服务下，数据报可能溢出路由器缓冲区而永远到不了目的地，可能失序到达，其中的比特也可能损坏（0 变 1、1 变 0）。由于运输层报文段是由 IP 数据报承载着穿越网络的，运输层报文段同样会遭遇这些问题。

TCP 在 IP 不可靠的尽力而为服务之上，创建了可靠数据传输服务。TCP 的可靠数据传输服务确保：一个进程从 TCP 接收缓冲区读出的数据流是无损坏的、无间隙的、无重复的、且按序的；也就是说，该字节流与连接另一端端系统所发送的字节流完全一致。TCP 提供可靠数据传输的方式，涉及 3.4 节研究过的许多原理。

在先前发展可靠数据传输技术时，从概念上说最容易的假设是：为每个已发送但尚未确认的报文段关联一个定时器。这在理论上很好，但定时器管理可能需要相当大的开销。因此，推荐的 TCP 定时器管理规程 [RFC 6298] 只使用**一个**重传定时器，即使有多个已发送但尚未确认的报文段。本节描述的 TCP 协议遵循这一单定时器建议。

我们分两步、逐步深入地讨论 TCP 如何提供可靠数据传输：先给出一个高度简化的 TCP 发送方描述，它只用超时来从丢失的报文段中恢复；再给出更完整的描述，除超时之外还使用重复 ACK。以下讨论假定数据只在一个方向上传输，即从主机 A 发往主机 B，且 A 正在发送一个大文件。

图 3.32 给出了 TCP 发送方的一个高度简化的描述。可以看到，TCP 发送方中有三个与数据传输和重传有关的主要事件：从上层收到数据、定时器超时、收到 ACK。

发生第一个事件时，TCP 从应用收到数据，把数据封装进报文段，并把报文段交给 IP。注意，每个报文段都包含一个序号，即该报文段中第一个数据字节的字节流编号（见 3.5.2 节）。还要注意，如果定时器尚未因其他报文段而运行，TCP 在把报文段交给 IP 时启动定时器。（把定时器看作与最早的未确认报文段相关联，是有帮助的。）该定时器的超时间隔就是 TimeoutInterval，由 3.5.3 节所述的 EstimatedRTT 与 DevRTT 算出。

第二个主要事件是超时。TCP 通过重传引起超时的那个报文段来响应超时事件，然后重启定时器。

TCP 发送方必须处理的第三个主要事件，是收到来自接收方的确认报文段（更准确地说，是包含有效 ACK 字段值的报文段）。此事件发生时，TCP 把 ACK 值 $y$ 与其变量 SendBase 比较。TCP 状态变量 SendBase 是最早的未确认字节的序号（因此 SendBase − 1 就是已知被接收方正确按序收到的最后一个字节的序号）。如前所述，TCP 使用累积确认，因此 $y$ 确认了序号 $y$ 之前所有字节的接收。若 $y > \text{SendBase}$，则该 ACK 确认了一个或多个此前未确认的报文段；于是发送方更新其 SendBase 变量，并且如果当前还有尚未确认的报文段，就重启定时器。

<p class="tbl-cap">图 3.32　简化的 TCP 发送方</p>

```text
/* 假定发送方不受 TCP 流量控制或拥塞控制的约束，
   上层数据小于 MSS，且数据只在一个方向上传输 */

NextSeqNum = InitialSeqNumber
SendBase   = InitialSeqNumber

loop (forever) {
    switch(event)

        event: 从上层收到数据
            创建序号为 NextSeqNum 的 TCP 报文段
            if (定时器当前未运行)
                启动定时器
            把报文段交给 IP
            NextSeqNum = NextSeqNum + length(data)
            break;

        event: 定时器超时
            重传序号最小的尚未确认的报文段
            启动定时器
            break;

        event: 收到 ACK，其 ACK 字段值为 y
            if (y > SendBase) {
                SendBase = y
                if (当前还有尚未确认的报文段)
                    启动定时器
            }
            break;

} /* loop forever 结束 */
```

### 几个有趣的场景

以上描述了 TCP 提供可靠数据传输的一个高度简化版本，但即便是这个高度简化的版本也有许多微妙之处。为体会该协议如何工作，下面走一遍几个简单场景。

图 3.33 描绘了第一个场景：主机 A 向主机 B 发送一个报文段，假设该报文段序号为 92、含 8 字节数据。发出后，主机 A 等待来自 B 的、确认号为 100 的报文段。虽然 A 的报文段被 B 收到，但 B 发往 A 的确认丢失了。此时发生超时事件，主机 A 重传同一个报文段。当然，当主机 B 收到这次重传时，它从序号看出该报文段包含的是已经收到的数据，于是 B 中的 TCP 丢弃重传报文段中的字节。

<Figure src="ch03/fig3-33.webp" caption="图 3.33　因确认丢失而重传" />

第二个场景如图 3.34 所示：主机 A 背靠背发送两个报文段，第一个序号 92、含 8 字节数据，第二个序号 100、含 20 字节数据。假设两个报文段都完好到达 B，B 分别为它们发送两个确认：第一个确认号为 100，第二个确认号为 120。现假设这两个确认在超时之前都未到达主机 A。超时事件发生时，主机 A 重发序号为 92 的第一个报文段，并重启定时器。只要第二个报文段的 ACK 在新的超时之前到达，第二个报文段就不会被重传。

第三个、也是最后一个场景：假设主机 A 像上例那样发送两个报文段。第一个报文段的确认在网络中丢失，但就在超时事件之前，主机 A 收到了确认号为 120 的确认。于是主机 A 知道主机 B 已收到直到字节 119 的全部内容，因此不再重传这两个报文段中的任何一个。这一场景如图 3.35 所示。

### 快速重传

超时触发重传的问题之一，是超时周期可能相对较长。当一个报文段丢失时，这个较长的超时周期迫使发送方延迟重发丢失的分组，从而增大端到端时延。所幸，发送方常常可以在超时事件发生之前，通过所谓的**重复 ACK** 推断出分组丢失。重复 ACK 是对某个报文段的再次确认，而发送方此前已经收到过对该报文段的确认。要理解发送方对重复 ACK 的响应，必须先弄清接收方究竟为什么发送重复 ACK。

当 TCP 接收方收到的报文段序号大于下一个期望的按序序号时，它就在数据流中检测到一个**间隙**，即有报文段缺失。这个间隙可能是网络中的报文段丢失或乱序造成的。由于 TCP 使用累积确认，一旦检测到间隙，TCP 接收方只是对它已收到的最后一个按序字节重新确认（即产生一个重复 ACK）。由于发送方使用流水线，收发双方之间可能有许多在途报文段；若其中一个在途报文段丢失，TCP 接收方很可能会产生许多背靠背的重复 ACK。因此，如果 TCP 发送方收到对同一数据的三个重复 ACK（即先收到该数据的一个原始 ACK，随后又收到对同一数据的三个额外 ACK），它就认为：被确认了四次的报文段**之后**的那个报文段已经丢失。（章末习题将讨论为什么发送方要等三个重复 ACK，而不是只等一个。）收到三个重复 ACK 时，TCP 发送方执行**快速重传**（fast retransmit）[RFC 5681]，在该报文段的定时器超时之前重传丢失的报文段。

### 回退 N 步还是选择重传？

在结束对 TCP 差错恢复机制的讨论之前，考虑这样一个问题：TCP 是 GBN 协议还是 SR 协议？回忆一下，TCP 的确认是累积的，接收方不会对正确收到但失序的报文段逐个确认。因此，如图 3.32（另见图 3.19）所示，TCP 发送方只需维护已发送但未确认字节的最小序号（SendBase）以及下一个待发字节的序号（NextSeqNum）。从这个意义上说，TCP 很像 GBN 风格的协议。

但 TCP 与 GBN 之间也有一些显著差异。许多 TCP 实现会缓存正确收到但失序的报文段 [Stevens 1994]。再考虑这样一种情形：发送方发送报文段 1, 2, …, N，所有报文段都按序、无差错地到达接收方；进一步假设对报文段 $n$（$n < N$）的确认丢失了，而其余 $N - 1$ 个确认都在各自超时之前到达了发送方。在这个例子中，GBN 不仅要重传报文段 $n$，还要重传其后所有报文段 $n + 1, n + 2, …, N$；而 TCP 至多重传一个报文段，即报文段 $n$。更有甚者，如果对报文段 $n + 1$ 的确认在报文段 $n$ 超时之前到达，TCP 根本不会重传报文段 $n$。

对 TCP 的一项建议修改——所谓**选择确认**（selective acknowledgment）[RFC 2018]——允许 TCP 接收方确认失序的报文段……

选择性确认 [RFC 2018] 使 TCP 接收方能够对失序的报文段逐个确认，而不只是累积确认最后一个正确收到的按序报文段。当它与选择性重传——跳过那些已被接收方选择性确认过的报文段的重传——结合使用时，TCP 就与我们所讲的一般的 SR 协议颇为相似了。因此，TCP 的差错恢复机制最好归类为 GBN 与 SR 的**混合体**。

## 3.5.5　流量控制

回忆一下，TCP 连接两端的每台主机都为该连接预留了一个接收缓冲区。当 TCP 连接收到正确且按序的字节时，它就把数据放入接收缓冲区。相应的应用进程会从这个缓冲区读取数据，但不一定在数据到达的那一刻就读。事实上，接收方应用可能正忙于其他任务，甚至可能在数据到达很久之后才去读。如果应用读取数据相对较慢，发送方就很容易因发送过多、过快的数据而使该连接的接收缓冲区溢出。

TCP 为其应用提供**流量控制**（flow control）服务，以消除发送方使接收方缓冲区溢出的可能。因此，流量控制是一种**速度匹配**服务——把发送方发送的速率与接收方应用读取的速率匹配起来。如前所述，TCP 发送方也可能因 IP 网络内部的拥塞而受到抑制；这种形式的发送方控制称为**拥塞控制**，将在 3.6 与 3.7 节详细探讨。尽管流量控制与拥塞控制所采取的动作相似（都是抑制发送方），但其原因显然截然不同。不幸的是，许多作者把这两个术语混用，聪明的读者应当把它们区分开来。下面讨论 TCP 如何提供流量控制服务。为看清主干，本节通篇假定 TCP 实现采取"接收方丢弃失序报文段"的做法。

TCP 通过让发送方维护一个称为**接收窗口**（receive window）的变量来提供流量控制。通俗地说，接收窗口用来告诉发送方：接收方还有多少可用的缓冲区空间。由于 TCP 是全双工的，连接每一端的发送方都各自维护一个不同的接收窗口。我们结合文件传输来考察接收窗口。假设主机 A 通过一条 TCP 连接向主机 B 发送一个大文件。主机 B 为该连接分配一个接收缓冲区，记其大小为 RcvBuffer。主机 B 的应用进程不时从该缓冲区读取数据。定义以下变量：

- `LastByteRead`：B 的应用进程从缓冲区读出的数据流中最后一个字节的编号；
- `LastByteRcvd`：从网络到达并已放入 B 的接收缓冲区的数据流中最后一个字节的编号。

由于 TCP 不允许使分配的缓冲区溢出，必须满足

$$
\text{LastByteRcvd} - \text{LastByteRead} \le \text{RcvBuffer}
$$

接收窗口记为 rwnd，被设为缓冲区中的空闲空间量：

$$
\text{rwnd} = \text{RcvBuffer} - [\text{LastByteRcvd} - \text{LastByteRead}]
$$

由于空闲空间随时间变化，rwnd 是动态的。变量 rwnd 如图 3.36 所示。

<Figure src="ch03/fig3-36.webp" caption="图 3.36　接收窗口（rwnd）与接收缓冲区（RcvBuffer）" />

连接如何使用变量 rwnd 来提供流量控制服务呢？主机 B 通过把它当前的 rwnd 值放入发往 A 的每个报文段的接收窗口字段，来告诉主机 A 该连接缓冲区还有多少空闲空间。初始时，主机 B 置 rwnd = RcvBuffer。注意，要做到这一点，主机 B 必须跟踪若干与该连接相关的变量。

主机 A 则跟踪两个变量 LastByteSent 与 LastByteAcked，含义不言自明。注意这两个变量之差 LastByteSent − LastByteAcked，就是 A 已送入该连接但尚未被确认的数据量。只要让未确认数据量小于 rwnd 的值，主机 A 就能确保不会使主机 B 的接收缓冲区溢出。因此，在连接的整个生命周期内，主机 A 都要保证

$$
\text{LastByteSent} - \text{LastByteAcked} \le \text{rwnd}
$$

这个方案有一个小的技术问题。设想主机 B 的接收缓冲区已满，于是 rwnd = 0。在向主机 A 通告 rwnd = 0 之后，再假设 B 没有数据要发给 A。现在考虑会发生什么：随着 B 的应用进程清空缓冲区，TCP 并不会向主机 A 发送带有新 rwnd 值的新报文段——事实上，TCP 只有在有数据要发或有确认要发时才向主机 A 发送报文段。因此，主机 A 永远得不到"B 的接收缓冲区已有空闲空间"的通知，A 就被阻塞住、再也发不出数据了！为解决这个问题，TCP 规范要求：当 B 的接收窗口为 0 时，主机 A 仍继续发送只含 1 个数据字节的报文段。这些报文段会被接收方确认；最终缓冲区开始腾空，确认中就会包含非零的 rwnd 值。

在描述了 TCP 的流量控制服务之后，还要简要指出：UDP **不**提供流量控制，因此报文段可能因接收方缓冲区溢出而在接收方丢失。例如，考虑从主机 A 的某个进程向主机 B 的某个进程发送一系列 UDP 报文段：在典型的 UDP 实现中，UDP 会把这些报文段追加到一个有限大小的缓冲区中，该缓冲区"位于"相应套接字（即进程之门）之前。进程一次从缓冲区读取一整个报文段；如果进程读取的速度不够快，缓冲区就会溢出，报文段就会被丢弃。

## 3.5.6　TCP 连接管理

本小节仔细考察 TCP 连接如何建立与拆除。这个话题看似不那么令人兴奋，但却很重要，因为 TCP 连接建立会显著增加可感知的时延（例如上网浏览时）；此外，许多最常见的网络攻击——包括极为流行的 SYN 洪泛攻击（见后文专栏）——利用的正是 TCP 连接管理中的弱点。

先看 TCP 连接如何建立。假设一台主机（客户）中运行的进程想与另一台主机（服务器）中的进程建立连接。客户应用进程首先告知客户 TCP：它想与服务器中的某个进程建立连接。随后客户端的 TCP 按下列方式与服务器端的 TCP 建立 TCP 连接：

- **第 1 步。** 客户端的 TCP 首先向服务器端的 TCP 发送一个特殊的 TCP 报文段。该报文段不含应用层数据，但其首部中的一个标志位（见图 3.28）——SYN 比特——被置为 1。因此，这个特殊报文段被称为 **SYN 报文段**。此外，客户随机选择一个初始序号（client*isn），并把它放入该初始 TCP SYN 报文段的序号字段。该报文段被封装进一个 IP 数据报，发往服务器。如何恰当地随机化 client*isn 的选择，以避免某些安全攻击，一直是人们相当关注的问题 [RFC 4987]。
- **第 2 步。** 一旦包含 TCP SYN 报文段的 IP 数据报到达服务器主机（假定它确实到达了！），服务器就从数据报中取出该 TCP SYN 报文段，为该连接分配 TCP 缓冲区与变量，并向客户 TCP 发送一个**允许连接**报文段。（第 8 章将会看到，在完成三次握手第三步之前就分配这些缓冲区与变量，使 TCP 容易遭受一种称为 SYN 洪泛的拒绝服务攻击。）该允许连接报文段同样不含应用层数据，但其首部包含三条重要信息：第一，SYN 比特置为 1；第二，TCP 报文段首部的确认字段置为 client*isn + 1；第三，服务器选择自己的初始序号（server*isn），并把它放入 TCP 报文段首部的序号字段。这个允许连接报文段实际上是在说："我收到了你要求建立连接的 SYN 报文，你的初始序号是 client*isn。我同意建立这条连接，我的初始序号是 server*isn。"该报文段被称为 **SYNACK 报文段**。
- **第 3 步。** 收到 SYNACK 报文段后，客户也要为该连接分配缓冲区与变量。随后，客户主机再向服务器发送一个报文段；这最后一个报文段对服务器的允许连接报文段予以确认（客户把 server_isn + 1 放入 TCP 报文段首部的确认字段来完成这一确认）。由于连接已经建立，SYN 比特置为 0。三次握手的这第三个阶段可以在报文段载荷中携带客户到服务器的数据。

这三步完成之后，客户与服务器主机就可以互相发送包含数据的报文段了；此后所有报文段中的 SYN 比特都将置为 0。注意，为建立连接，两台主机之间共发送三个分组，如图 3.37 所示。因此，这个连接建立过程常被称为**三次握手**。TCP 三次握手的若干方面将在章末习题中探讨（为什么需要初始序号？为什么需要三次握手而不是两次握手？）。有趣的是，攀岩者与保护者（位于攀岩者下方、负责处理其安全绳的人）所用的通信协议也是三次握手，与 TCP 完全相同，以确保在攀岩者开始向上攀爬之前双方都已准备就绪。

<Figure src="ch03/fig3-37.webp" caption="图 3.37　TCP 三次握手：报文段交换" />

既然发起三次握手的 TCP 客户必须等到收到服务器的 SYNACK 消息，才能知道服务器已接受连接、连接状态已初始化，那么任何这类握手协议（例如第 8 章将研究的 TLS 协议，或第 2 章研究过、本章稍后还会再谈的 QUIC 协议）在连接建立时似乎都天然存在一个 RTT 的时延。不过，如果客户与服务器此前通信过，就可以使用一种称为"快速打开"（fast open）的技术，把握手时间降到零！也就是说，客户可以向此前通信过的面向连接服务器立即发送数据，而不必执行传统三次握手的前两步。

快速打开（有时也称为 **0-RTT 握手**）的关键思想是：在传统三次握手期间，客户可以请求服务器提供一个快速打开 cookie，该 cookie 编码了未来连接所需的全部连接信息。这个 cookie 由客户与服务器各自保存。下次客户想与这台服务器建立连接时，就在发给服务器的第一条消息中带上该快速打开 cookie 以及应用层数据。服务器检查该 cookie，认为可以接受，就接受连接、根据 cookie 建立连接参数，并对初始消息中的应用层数据作出响应，回送服务器的应用层响应数据——从而完全避免了"发送数据前要等一个 RTT"的三次握手时延。

需要强调的是，快速打开只是对客户的一种可能的优化；服务器可能出于策略原因不接受快速打开 cookie，例如服务器不再想与该客户通信，或想强制该客户重新进行身份认证（例如 TLS 握手的情形）。客户把 cookie 端到服务器面前，并不意味着服务器非得"吃"（接受）这块 cookie！当然，快速打开 cookie 必须以密码学安全的方式生成，所用技术将在第 8 章研究。TCP 快速打开见 RFC 7413；TLS（见第 8 章及 RFC 8446）与 QUIC 协议 [RFC 9000; RFC 9002] 也支持零 RTT 的快速打开。

天下没有不散的筵席，TCP 连接也是如此。参与一条 TCP 连接的两个进程中的任何一个都可以结束该连接。连接结束时，主机中的"资源"（即缓冲区与变量）被释放。举例来说，假设客户决定关闭连接，如图 3.38 所示。客户应用进程发出关闭命令，这使客户 TCP 向服务器进程发送一个特殊的 TCP 报文段，其首部中的标志位——FIN 比特（见图 3.28）——置为 1。服务器收到该报文段后，向客户回送一个确认报文段；随后服务器发送自己的关闭报文段，其 FIN 比特置为 1；最后，客户确认服务器的关闭报文段。至此，两台主机中的所有资源都被释放。

<Figure src="ch03/fig3-38.webp" caption="图 3.38　关闭一条 TCP 连接" />

在一条 TCP 连接的生命期内，每台主机中运行的 TCP 协议会在各种 TCP 状态之间转换。图 3.39 展示了客户端 TCP 通常经历的一系列 TCP 状态。客户端 TCP 从 CLOSED 状态开始。客户侧应用发起一条新的 TCP 连接（在第 2 章的 Python 示例中，就是创建一个 Socket 对象），这使客户端的 TCP 向服务器端的 TCP 发送一个 SYN 报文段。发出 SYN 报文段后，客户端 TCP 进入 SYN*SENT 状态。在 SYN*SENT 状态下，客户端 TCP 等待来自服务器 TCP 的、包含对客户前一个报文段的确认且 SYN 比特置 1 的报文段。收到这样的报文段后，客户端 TCP 进入 ESTABLISHED 状态。在 ESTABLISHED 状态下，TCP 客户可以发送和接收包含载荷（即应用产生的）数据的 TCP 报文段。

<Figure src="ch03/fig3-39.webp" caption="图 3.39　客户端 TCP 通常经历的一系列 TCP 状态" />

假设客户应用决定关闭连接（注意，服务器也可以选择关闭连接）。这使客户端 TCP 发送一个 FIN 比特置 1 的 TCP 报文段，并进入 FIN*WAIT*1 状态。在 FIN*WAIT*1 状态下，客户端 TCP 等待来自服务器的带确认的 TCP 报文段。收到该报文段后，客户端 TCP 进入 FIN*WAIT*2 状态。在 FIN*WAIT*2 状态下，客户等待服务器发来另一个 FIN 比特置 1 的报文段；收到后，客户端 TCP 确认服务器的报文段，并进入 TIME*WAIT 状态。TIME*WAIT 状态让 TCP 客户在最终确认丢失时能够重发它。在 TIME_WAIT 状态停留的时间取决于具体实现，典型值为 30 秒、1 分钟和 2 分钟。等待结束后，连接正式关闭，客户侧的所有资源（包括端口号）都被释放。

<Figure src="ch03/fig3-40.webp" caption="图 3.40　服务器端 TCP 通常经历的一系列 TCP 状态" />

图 3.40 展示了在假定客户发起连接拆除的情况下，服务器端 TCP 通常经历的一系列状态，其转换不言自明。在这两个状态转换图中，我们只展示了 TCP 连接通常如何建立与关闭，没有描述某些病态场景，例如连接双方同时想发起或关闭连接。若想了解这些问题以及其他 TCP 高级话题，建议参阅 Stevens 的综合性著作 [Stevens 1994]。

以上讨论假定客户与服务器都准备好通信，即服务器正在客户发送 SYN 报文段的那个端口上监听。那么，当一台主机收到的 TCP 报文段的端口号或源 IP 地址与该主机中任何现有套接字都不匹配时，会发生什么？例如，假设某主机收到一个目的端口为 80 的 TCP SYN 分组，但该主机并不在端口 80 上接受连接（即它没有在端口 80 上运行 Web 服务器）。此时，该主机会向源端发送一个特殊的**重置报文段**，其 RST 标志位（见 3.5.2 节）置为 1。因此，当一台主机发送重置报文段时，它是在告诉源端："我没有与该报文段对应的套接字，请不要重发该报文段。"当主机收到的 UDP 分组的目的端口号与任何现有 UDP 套接字都不匹配时，主机会发送一个特殊的 ICMP 数据报，详见第 5 章。

<AsideCard title="安全聚焦 · SYN 洪泛攻击">

在讨论 TCP 三次握手时我们已经看到，服务器在收到 SYN 后会分配并初始化连接变量与缓冲区，然后回送一个 SYNACK，并等待客户的 ACK 报文段。如果客户不发送 ACK 来完成三次握手的第三步，服务器最终（往往在一分钟甚至更久之后）会终止这个**半开连接**，并回收已分配的资源。

正是这套 TCP 连接管理协议，为一种经典的拒绝服务（DoS）攻击——**SYN 洪泛攻击**（SYN flood attack）——埋下了伏笔。在这种攻击中，攻击者发送大量 TCP SYN 报文段，却不完成握手的第三步。面对这铺天盖地的 SYN 报文段，服务器的连接资源被大量分配给半开连接（而且永远不会被使用！），从而被耗尽；合法客户于是得不到服务。这类 SYN 洪泛攻击是最早被记录的 DoS 攻击之一；30 年过去了，SYN 洪泛攻击仍占 DoS 攻击的 14% [Fastly 2024]。所幸，一种称为 **SYN cookie** 的有效防御手段 [RFC 4987] 如今已部署在大多数主流操作系统中。SYN cookie 的工作方式如下：

- 服务器收到 SYN 报文段时，无法判断它来自合法用户还是 SYN 洪泛攻击的一部分。因此，服务器不为这个 SYN 创建半开 TCP 连接，而是生成一个初始 TCP 序号，该序号是 SYN 报文段的源/目的 IP 地址与端口号、以及一个只有服务器知道的秘密数的复杂函数（散列函数）。这个精心构造的初始序号就是所谓的"cookie"。服务器随后向客户发送带有该特殊初始序号的 SYNACK 分组。重要的是，服务器**不**保存这个 cookie，也不保存与该 SYN 对应的任何状态信息。
- 合法客户会回送一个 ACK 报文段。服务器收到该 ACK 时，必须验证它确实对应此前发出的某个 SYN。可服务器对 SYN 报文段毫无记忆，这该如何做到？你可能已经猜到——靠 cookie。回忆一下，对于合法的 ACK，其确认字段的值等于 SYNACK 中的初始序号（此处即 cookie 值）加 1（见图 3.37）。于是服务器可以用 SYNACK 中的源/目的 IP 地址与端口号（它们与原始 SYN 中的相同）以及那个秘密数，再运行一遍同样的散列函数。如果函数结果加 1 恰好等于客户 ACK 中的确认（cookie）值，服务器就断定该 ACK 对应于此前的某个 SYN 报文段，因而有效；随后服务器创建一条完全打开的连接以及一个套接字。
- 反之，如果客户不回送 ACK 报文段，那么最初那个 SYN 对服务器毫无损害，因为服务器尚未针对这个伪造的 SYN 分配任何资源。
