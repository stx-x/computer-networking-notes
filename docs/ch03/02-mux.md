# 3.2　多路复用与多路分解

本节讨论运输层的**多路复用**与**多路分解**，也就是把网络层提供的**主机到主机**交付服务，扩展为运行在主机上的应用之间的**进程到进程**交付服务。为使讨论具体，我们仍放在因特网的语境中展开；但需要强调，任何计算机网络都需要多路复用/多路分解服务。

在目的主机上，运输层从紧邻其下的网络层接收报文段，并负责把这些报文段中的数据交付给主机中正确的应用进程。看一个例子：假设你坐在电脑前，一边下载网页，一边开着一个 Zoom 会话和两个 ssh 会话。那么你共有四个网络应用进程在运行——两个 ssh 进程、一个 Zoom 进程、一个 HTTP 进程。当电脑中的运输层从下层网络层收到数据时，它必须把收到的数据交给这四个进程中的一个。下面看看这是如何做到的。

首先回忆 2.6 节：一个进程（作为某个网络应用的一部分）可以拥有一个或多个**套接字**（socket）。套接字是数据从网络进入进程、以及从进程流向网络的"门"。因此，如图 3.2 所示，接收主机中的运输层实际上并不直接把数据交给进程，而是交给一个作为中介的套接字。由于在任一时刻接收主机中可能有多个套接字，每个套接字都必须有唯一的标识符。标识符的格式取决于该套接字是 UDP 还是 TCP 套接字，稍后讨论。

<Figure src="ch03/fig3-02.webp" caption="图 3.2　运输层的多路复用与多路分解" />

现在考虑接收主机如何把一个到达的运输层报文段导向正确的套接字。每个运输层报文段中都有若干字段用于此目的。在接收端，运输层检查这些字段，确定接收套接字，然后把报文段导向该套接字。把运输层报文段中的数据交付给正确套接字的工作，称为**多路分解**（demultiplexing）；而在源主机上从不同套接字收集数据块、为每个数据块封装首部信息（这些信息随后将用于多路分解）以生成报文段、再把报文段交给网络层的工作，称为**多路复用**（multiplexing）。

注意，图 3.2 中间那台主机中的运输层，必须把从下层网络层到达的报文段分解给上面的进程 P1 或 P2——做法是把到达报文段的数据导向相应进程的套接字。同时，该主机的运输层还必须从这些套接字收集外出数据，形成运输层报文段，再下交给网络层。虽然我们是在因特网运输协议的语境中引入复用与分解的，但应当认识到：只要某一层（运输层或其他层）上的单个协议被上一层中的多个协议所使用，就存在复用与分解的问题。

为了说明多路分解工作，回想上一节的家庭类比。每个孩子由他/她的名字来标识。当 Bill 从邮递员那里收到一批邮件时，他通过查看信件是写给谁的来执行"多路分解"，然后亲手把邮件分发给兄弟姐妹。而 Ann 从兄弟姐妹那里收集信件、把收齐的邮件交给邮递员时，执行的则是"多路复用"。

理解了运输层复用与分解的作用，下面看看主机中实际是怎么做的。由上面的讨论可知，运输层多路复用需要：(1) 套接字有唯一标识符；(2) 每个报文段有特殊字段来指明该报文段所要交付的套接字。这两个特殊字段如图 3.3 所示，即**源端口号字段**和**目的端口号字段**。（UDP 和 TCP 报文段还有其他字段，将在本章后续各节讨论。）

<Figure src="ch03/fig3-03.webp" caption="图 3.3　运输层报文段中的源端口号与目的端口号字段" />

每个端口号是一个 16 位数，取值范围 0～65535。其中 0～1023 的端口号称为**周知端口号**（well-known port number），受到限制使用，即保留给周知的应用协议，如 HTTP（使用端口号 80）和 FTP（使用端口号 21）。周知端口号的列表见 RFC 1700，并在 http://www.iana.org 上更新 [RFC 3232]。当我们开发一个新应用（例如 2.6 节开发的那个简单应用）时，必须为其分配一个端口号。

至此，运输层如何实现多路分解服务应当已经清楚了：主机中的每个套接字都可以分配一个端口号；当报文段到达主机时，运输层检查报文段中的目的端口号，把报文段导向相应的套接字，报文段的数据便经由该套接字进入与之相连的进程。正如我们将看到的，UDP 基本上就是这么做的；但 TCP 的复用/分解则要微妙一些。

## 用 UDP 进行无连接的多路复用与多路分解

回忆 2.6.1 节：主机中运行的 Python 程序可以用下面这行代码创建一个 UDP 套接字：

```text
clientSocket = socket(AF_INET, SOCK_DGRAM)
```

以这种方式创建 UDP 套接字时，运输层会自动为该套接字分配一个端口号，具体是分配 1024～65535 范围内、当前未被本主机中其他 UDP 端口占用的一个端口号。另一种做法是在创建套接字之后再加一行代码，通过套接字的 `bind()` 方法把一个特定端口号（例如 19157）与该 UDP 套接字关联起来：

```text
clientSocket.bind(('', 19157))
```

如果写这段代码的应用开发者实现的是某个"周知协议"的服务器端，那么他必须分配相应的周知端口号。通常情况下，应用的客户端让运输层自动（且透明地）分配端口号，而服务器端则分配一个特定的端口号。

有了分配给 UDP 套接字的端口号，就可以精确描述 UDP 的复用/分解了。假设主机 A 中一个 UDP 端口为 19157 的进程，要向主机 B 中 UDP 端口为 46428 的进程发送一块应用数据。主机 A 的运输层创建一个运输层报文段，其中包含应用数据、源端口号 19157、目的端口号 46428，以及另外两个值（后面会讨论，此处无关紧要）。随后运输层把该报文段交给网络层；网络层把报文段封装进一个 IP 数据报，尽最大努力把该报文段交付给接收主机。如果报文段到达接收主机 B，B 的运输层检查报文段中的目的端口号 46428，把该报文段交付给端口 46428 所标识的套接字。注意，主机 B 可能同时运行多个进程，每个进程都有自己的 UDP 套接字和相应端口号；当 UDP 报文段从网络到达时，主机 B 通过检查报文段的目的端口号，把每个报文段导向（分解到）相应的套接字。

需要强调的是，**一个 UDP 套接字由二元组（目的 IP 地址，目的端口号）完全标识**。因此，如果两个 UDP 报文段具有不同的源 IP 地址和/或不同的源端口号，但具有相同的目的 IP 地址和相同的目的端口号，那么这两个报文段将通过同一个目的套接字被导向同一个目的进程。

你也许在想：那源端口号有什么用？如图 3.4 所示，在 A 到 B 的报文段中，源端口号充当"回信地址"的一部分——当 B 要向 A 回发报文段时，B 到 A 报文段中的目的端口号就取自 A 到 B 报文段中的源端口值。（完整的回信地址是 A 的 IP 地址加上源端口号。）例如，回想 2.7 节研究的 UDP 服务器程序：在 UDPServer.py 中，服务器用 `recvfrom()` 方法从收到的客户端报文段中提取客户端（源）端口号，然后向客户端发送一个新报文段，并把提取出的源端口号作为新报文段中的目的端口号。

## 用 TCP 进行面向连接的多路复用与多路分解

要理解 TCP 的多路分解，必须仔细考察 TCP 套接字与 TCP 连接建立过程。TCP 套接字与 UDP 套接字的一个微妙区别是：**TCP 套接字由四元组（源 IP 地址，源端口号，目的 IP 地址，目的端口号）来标识**。因此，当一个 TCP 报文段从网络到达主机时，主机用全部四个值来把该报文段导向（分解到）相应的套接字。特别地，与 UDP 不同，具有不同源 IP 地址或不同源端口号的两个到达 TCP 报文段（携带初始连接建立请求的报文段除外），将被导向两个不同的套接字，即使它们的目的 IP 地址和目的端口号相同。

为了获得更深入的理解，重新考虑 2.6.2 节的 TCP 客户端-服务器编程示例：

- TCP 服务器应用有一个"欢迎套接字"（welcoming socket），在端口号 12000 上等待来自 TCP 客户端的连接建立请求（见图 2.24）。
- TCP 客户端创建一个套接字，并发送一个连接建立请求报文段：

```text
clientSocket = socket(AF_INET, SOCK_STREAM)
clientSocket.connect((serverName, 12000))
```

- 连接建立请求不过是一个目的端口号为 12000、并在 TCP 首部中置了特殊的连接建立位的 TCP 报文段（3.5 节讨论）。该报文段还包含客户端选择的源端口号。
- 当运行服务器进程的计算机的操作系统收到这个目的端口为 12000 的连接请求报文段时，它定位到正在端口号 12000 上等待接受连接的服务器进程。服务器进程随即创建一个新套接字：

```text
connectionSocket, addr = serverSocket.accept()
```

- 同时，服务器端的运输层记下连接请求报文段中的四个值：(1) 报文段中的源端口号，(2) 源主机的 IP 地址，(3) 报文段中的目的端口号，(4) 本机自己的 IP 地址。新创建的连接套接字就由这四个值来标识；此后所有源端口、源 IP 地址、目的端口、目的 IP 地址与这四个值相匹配的到达报文段，都将被分解到这个套接字。TCP 连接至此建立，客户端与服务器可以互发数据了。

服务器主机可以同时支撑许多 TCP 连接套接字，每个套接字连接到一个进程，并各自由自己的四元组标识。当一个 TCP 报文段到达主机时，四个字段（源 IP 地址、源端口、目的 IP 地址、目的端口）全部用于把报文段导向（分解到）相应的套接字。

<Figure src="ch03/fig3-05.webp" caption="图 3.5　两个客户端使用相同的目的端口号（80）与同一个 Web 服务器应用通信" />

图 3.5 给出了一个具体情形：主机 C 向服务器 B 发起两个 HTTP 会话，主机 A 向 B 发起一个 HTTP 会话。主机 A、C 与服务器 B 各有自己唯一的 IP 地址，分别为 A、C、B。主机 C 为它的两个 HTTP 连接分配了两个不同的源端口号（26145 和 7532）。由于主机 A 独立于 C 选择源端口号，它也可能为自己的 HTTP 连接分配源端口 26145。但这并不成问题——服务器 B 仍能正确分解这两个源端口号相同的连接，因为这两个连接的源 IP 地址不同。

<AsideCard title="安全聚焦 · 端口扫描">

我们已经看到，服务器进程会在某个打开的端口上耐心等待远程客户端的联系。有些端口保留给周知应用（如 Web、FTP、DNS、SMTP 服务器），另一些端口则被流行应用按惯例使用（例如 Microsoft Windows SQL 服务器在 UDP 端口 1434 上监听请求）。因此，一旦确定主机上某个端口是打开的，我们就有可能把这个端口映射到主机上运行的某个具体应用。这对系统管理员非常有用，他们常常想知道自己网络中的主机上跑着哪些网络应用。但攻击者在"踩点"时，同样想知道目标主机上哪些端口是打开的。如果发现某台主机正在运行带有已知安全漏洞的应用（例如监听 1434 端口的 SQL 服务器曾存在缓冲区溢出漏洞，可让远程用户在易受攻击的主机上执行任意代码，Slammer 蠕虫就利用了该漏洞 [Kristoff 2023]），那么这台主机就很容易被攻陷。

确定哪些应用在哪些端口上监听，是件相当容易的事。事实上，有不少公有领域的程序——称为**端口扫描器**（port scanner）——专门做这件事。其中最常用的也许是 nmap，可从 http://nmap.org 免费获得，且包含在大多数 Linux 发行版中。对 TCP，nmap 依次扫描各端口，寻找正在接受 TCP 连接的端口；对 UDP，nmap 同样依次扫描各端口，寻找对发出的 UDP 报文段作出响应的 UDP 端口。两种情况下，nmap 都会返回一份端口列表，标明各端口是打开、关闭还是不可达。运行 nmap 的主机可以尝试扫描因特网上的任何目标主机。

</AsideCard>

## Web 服务器与 TCP

在结束本节之前，再就 Web 服务器如何使用端口号说几句是有益的。考虑一台在端口 80 上运行 Web 服务器（例如 Apache）的主机。当客户端（例如浏览器）向服务器发送报文段时，所有报文段的目的端口都是 80；特别是，初始的连接建立报文段和携带 HTTP 请求消息的报文段，目的端口都是 80。正如刚才所述，服务器利用源 IP 地址和源端口号来区分来自不同客户端的报文段。

图 3.5 中的 Web 服务器为每个连接派生一个新进程。如图所示，每个进程都有自己的连接套接字，HTTP 请求经由它到达、HTTP 响应经由它发出。不过要说明的是，连接套接字与进程之间并不总是一一对应的。事实上，当今高性能的 Web 服务器往往只使用一个进程，而为每个新的客户端连接创建一个新线程和一个新的连接套接字。（线程可以看作轻量级的子进程。）如果你做过第 2 章的第一个编程作业，你写的 Web 服务器正是这样做的。对这类服务器而言，在任一时刻都可能有多个连接套接字（标识符各不相同）连接到同一个进程。

如果客户端与服务器使用持久 HTTP，那么在持久连接的整个持续期间，客户端与服务器都通过同一个服务器套接字交换 HTTP 消息。反之，如果使用非持久 HTTP，则每对请求/响应都要创建并关闭一个新的 TCP 连接，因而每对请求/响应都要创建、随后关闭一个新的套接字。这种频繁创建和关闭套接字会严重影响繁忙 Web 服务器的性能（尽管可以用一些操作系统技巧来缓解）。对持久与非持久 HTTP 所涉及的操作系统问题感兴趣的读者，可参阅 [Nielsen 1997; Nahum 2002]。

讨论了运输层的多路复用与多路分解，接下来考察因特网的运输协议之一：UDP。下一节将会看到，UDP 除了复用/分解服务之外，几乎没有给网络层协议增加什么别的东西。
