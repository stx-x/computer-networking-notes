# 3.5　面向连接的运输：TCP

掌握了可靠数据传输的基本原理之后，现在转向 TCP——因特网的运输层面向连接的可靠运输协议。本节将会看到，为了提供可靠数据传输，TCP 依赖上一节讨论的许多基本原理，包括差错检测、重传、累积确认、定时器，以及用于序号和确认号的首部字段。TCP 最初定义于 RFC 793，此后多年来又由若干 RFC 更新，包括 RFC 1122、RFC 2018、RFC 5681 和 RFC 7323；这些更新与原始的 RFC 793 规范已被汇总进新的 RFC [RFC 9293]，后者正式"废弃"了 RFC 793。

## 3.5.1　TCP 连接

TCP 被称为是**面向连接**的，因为在一个应用进程开始向另一个应用进程发送数据之前，两个进程必须先相互"握手"——即它们必须交换一些预备报文段，以确立后续数据传输所需的参数。作为 TCP 连接建立的一部分，连接双方都会初始化许多与该 TCP 连接相关的 TCP 状态变量（其中许多将在本节和 3.7 节讨论）。

TCP 的"连接"并不是电路交换网络中那种端到端的 TDM 或 FDM 电路，而是一种**逻辑**连接，其公共状态只存在于两个通信端系统的 TCP 之中。回忆一下，由于 TCP 协议只运行在端系统中、不运行在中间网络设备（路由器和链路层交换机）中，中间网络设备并不维护 TCP 连接状态。事实上，中间路由器对 TCP 连接完全无感：它们看到的是数据报，而不是连接。

TCP 连接提供**全双工**服务：若一台主机上的进程 A 与另一台主机上的进程 B 之间存在一条 TCP 连接，则应用层数据可以同时从 A 流向 B、从 B 流向 A。TCP 连接也总是**点对点**的，即连接在单个发送方与单个接收方之间。所谓的"多播"（multicasting，见本书在线补充材料）——在一次发送操作中把数据从一个发送方传给多个接收方——用 TCP 是做不到的。对 TCP 而言，两台主机正好，三台就太多了！

20 世纪 70 年代初，分组交换网络开始大量涌现，因特网的前身 ARPAnet 只是众多网络中的一个。这些网络各有自己的协议。两位研究者——Vinton Cerf 与 Robert Kahn——认识到把这些网络互连起来的重要性，发明了一种跨网络协议 TCP/IP，即传输控制协议/网际协议（Transmission Control Protocol/Internet Protocol）。虽然 Cerf 和 Kahn 起初把该协议视为单一实体，后来它被拆分为 TCP 与 IP 两部分，各自独立运行。1974 年 5 月，Cerf 和 Kahn 在 *IEEE Transactions on Communications Technology* 上发表了关于 TCP/IP 的论文 [Cerf 1974]。

TCP/IP 协议是当今因特网的命脉，而它被设计出来的时候，个人计算机、工作站、智能手机和平板电脑都还不存在，以太网、电缆、DSL、WiFi 等各种接入网技术尚未普及，Web、社交媒体和流媒体视频更是闻所未闻。Cerf 和 Kahn 预见到需要这样一种网络协议：一方面能为尚未定义的各类应用提供广泛支持，另一方面能让任意主机和链路层协议互操作。

2004 年，Cerf 和 Kahn 获得美国计算机学会（ACM）图灵奖——被誉为"计算领域的诺贝尔奖"——以表彰他们"在互连网络方面的开创性工作，包括因特网基础通信协议 TCP/IP 的设计与实现，以及在网络领域的卓越领导"。

</AsideCard>

一旦 TCP 连接建立起来，两个应用进程就可以互相发送数据。先看客户进程向服务器进程发送数据的情形。如 2.6 节所述，客户进程通过套接字（进程的"门"）传递数据流；数据一旦穿过这道门，就交到了客户端 TCP 的手中。如图 3.27 所示，TCP 把这些数据导向该连接的**发送缓冲区**（send buffer），它是三次握手期间预留的缓冲区之一。TCP 会不时地从发送缓冲区中取出一块块数据，交给网络层。有趣的是，最初的 TCP 规范 [RFC 793] 在"TCP 究竟应在何时真正发送缓冲区中的数据"这一点上非常随性，只说要"按自己的方便，把数据放在报文段中发送"。

一个报文段中能取出并放入的最大数据量，受**最大报文段长度**（maximum segment size, MSS）限制。MSS 的典型确定方法是：先确定本地发送主机所能发送的最大链路层帧长度（即所谓的**最大传输单元**，MTU），再据此设定 MSS，使得一个 TCP 报文段（封装进 IP 数据报后）加上 TCP/IP 首部长度（通常 40 字节）能装进一个链路层帧。以太网与 PPP 链路层协议的 MTU 都是 1500 字节，因此 MSS 的典型值为 1460 字节。也有人提出发现**路径 MTU**——从源到目的的所有链路上所能发送的最大链路层帧 [RFC 1191]——并据此设定 MSS 的方法。注意，MSS 指的是报文段中**应用层数据的最大量**，而不是包含首部的 TCP 报文段的最大长度。（这个术语容易混淆，但既然已经根深蒂固，我们也只好接受。）

TCP 为每一块客户数据配上 TCP 首部，从而形成 TCP 报文段。报文段被下交给网络层，在网络层各自封装进 IP 数据报，随后发入网络。在另一端，TCP 收到报文段后，把该报文段的数据放入该 TCP 连接的**接收缓冲区**（receive buffer），如图 3.27 所示；应用从该缓冲区读取数据流。连接的每一侧都有自己的发送缓冲区和接收缓冲区。

<Figure src="ch03/fig3-27.webp" caption="图 3.27　TCP 发送缓冲区与接收缓冲区" />

由此可见，一条 TCP 连接由一台主机中与某进程相连的一组缓冲区、变量和套接字连接，以及另一台主机中与另一进程相连的另一组缓冲区、变量和套接字连接共同构成。如前所述，主机之间的网络设备（路由器、交换机和转发器）中不会为该连接分配任何缓冲区或变量。

## 3.5.2　TCP 报文段结构

简要了解了 TCP 连接之后，来考察 TCP 报文段的结构。TCP 报文段由首部字段和一个数据字段组成，数据字段包含一块应用数据。如上所述，MSS 限制了报文段数据字段的最大长度。当 TCP 发送一个大文件（例如网页中的一幅图像）时，通常把文件切分成 MSS 大小的块（最后一块往往小于 MSS）。而交互式应用通常传输小于 MSS 的数据块；例如 Telnet 和 ssh 这类远程登录应用，TCP 报文段中的数据字段常常只有 1 个字节。由于 TCP 首部通常为 20 字节（比 UDP 首部多 12 字节），Telnet 和 ssh 发送的报文段长度可能只有 21 字节。

图 3.28 给出了 TCP 报文段的结构。与 UDP 一样，首部包含源端口号和目的端口号，用于与上层应用之间数据的多路复用/多路分解；也与 UDP 一样，首部包含校验和字段。此外，TCP 报文段首部还包含下列字段：

- **32 比特的序号字段**与**32 比特的确认号字段**，供 TCP 发送方与接收方实现可靠数据传输服务时使用，详见下文。
- **16 比特的接收窗口字段**，用于流量控制。稍后会看到，它用来指示接收方愿意接受的字节数。
- **4 比特的首部长度字段**，以 32 比特字为单位指明 TCP 首部的长度。由于存在选项字段，TCP 首部长度可变。（通常选项字段为空，因此典型 TCP 首部长度为 20 字节。）
- **选项字段**，长度可变，可选。当收发双方协商最大报文段长度（MSS），或在高速网络中使用窗口缩放因子时，会用到该字段；此外还定义了时间戳选项。详见 RFC 854 与 RFC 1323。
- **标志字段**，共 6 比特。ACK 比特用于指示确认号字段中的值有效，即该报文段包含对某个已成功接收的报文段的确认。RST、SYN 和 FIN 比特用于连接的建立与拆除，本节末尾将讨论。CWR 与 ECE 比特用于显式拥塞通知，见 3.7.2 节。置位 PSH 比特表示接收方应立即把数据交给上层。最后，URG 比特用于指示本报文段中存在被发送侧上层实体标记为"紧急"的数据，这些紧急数据的最后一个字节的位置由 16 比特的**紧急数据指针字段**指明；当存在紧急数据时，TCP 必须通知接收侧上层实体，并向其传递指向紧急数据末尾的指针。（实践中，PSH、URG 及紧急数据指针都未被使用，这里提及只是为了完整。）

<Figure src="ch03/fig3-28.webp" caption="图 3.28　TCP 报文段结构" />

作为教师的经验告诉我们，学生有时会觉得分组格式的讨论枯燥甚至有点无聊。若想以一种有趣而奇特的方式了解 TCP 首部字段——尤其如果你和我们一样热爱乐高积木——可参阅 [Pomeranz 2010]。

### 序号与确认号

TCP 报文段首部中最重要的两个字段是序号字段和确认号字段，它们是 TCP 可靠数据传输服务的关键部分。不过在讨论如何用这两个字段提供可靠数据传输之前，先解释 TCP 究竟在这两个字段里放了什么。

TCP 把数据看作**无结构的、但有序的字节流**。TCP 对序号的使用正体现了这一观点：序号是建立在**传输的字节流**之上，而不是建立在**传输的报文段序列**之上。因此，一个报文段的序号就是该报文段数据字段中**第一个字节**的字节流编号。

看一个例子。假设主机 A 中的某个进程要通过一条 TCP 连接向主机 B 中的某个进程发送一个数据流。主机 A 的 TCP 会隐式地为数据流中的每个字节编号。假设该数据流是一个 500 000 字节的文件，MSS 为 1000 字节，且数据流的第一个字节编号为 0。如图 3.29 所示，TCP 由该数据流构造出 500 个报文段：第一个报文段的序号为 0，第二个为 1000，第三个为 2000，依此类推。每个序号都被填入相应 TCP 报文段首部的序号字段中。

<Figure src="ch03/fig3-29.webp" caption="图 3.29　把文件数据划分成 TCP 报文段" />

再来看确认号。它比序号要稍难一些。回忆一下，TCP 是全双工的，因此主机 A 在向 B 发送数据的同时，也可能在从 B 接收数据（同属一条 TCP 连接）。从 B 到达的每个报文段都带有 B 到 A 数据流的序号。**主机 A 填入其报文段的确认号，是主机 A 期望从主机 B 收到的下一个字节的序号**。多看几个例子有助于理解。

假设主机 A 已从 B 收到编号 0～535 的所有字节，并且即将向 B 发送一个报文段。此时主机 A 正在等待字节 536 以及 B 数据流中其后的所有字节，于是 A 在发往 B 的报文段的确认号字段中填入 536。

再看一例。假设主机 A 从 B 收到了一个包含字节 0～535 的报文段，又收到了另一个包含字节 900～1000 的报文段；由于某种原因，A 尚未收到字节 536～899。在这个例子中，A 仍在等待字节 536（及其后的字节），以便重建 B 的数据流。因此，A 发往 B 的下一个报文段将在确认号字段中填入 536。由于 TCP 只确认到数据流中第一个缺失字节之前的所有字节，因此说 TCP 提供**累积确认**。

上例还引出一个重要而微妙的问题：主机 A 在收到第二个报文段（字节 536～899）之前，就先收到了第三个报文段（字节 900～1000），即第三个报文段**失序**到达。微妙之处在于：主机在 TCP 连接中收到失序报文段时该怎么办？有趣的是，TCP 的 RFC 对此未作任何规定，而是把决定权留给实现 TCP 的程序员。基本上有两种选择：(1) 接收方立即丢弃失序报文段（如前所述，这可以简化接收方设计）；(2) 接收方保留失序字节，并等待缺失字节来填补空隙。显然，就网络带宽而言后一种选择更高效，实践中采用的也是这种做法。

在图 3.29 中，我们假定初始序号为 0。实际上，TCP 连接的两端都会**随机**选择一个初始序号。这样做是为了尽量减少一种可能：两台主机之间早先已终止的某条连接遗留在网络中的报文段，被误认为是这两台主机之间后来某条连接（恰好使用了与旧连接相同的端口号）中的有效报文段 [Sunshine 1978]。

### Telnet：序号与确认号的一个案例

Telnet（定义于 RFC 854）是一种用于远程登录的流行应用层协议。它运行在 TCP 之上，被设计为可在任意一对主机之间工作。与第 2 章讨论的批量数据传输应用不同，Telnet 是一种交互式应用。这里讨论一个 Telnet 例子，因为它能很好地说明 TCP 的序号与确认号。需要指出，如今用户更愿意使用 SSH 协议而不是 Telnet，因为 Telnet 连接中发送的数据（包括口令！）未加密，使 Telnet 易受窃听攻击。

假设主机 A 向主机 B 发起一个 Telnet 会话。由于 A 发起会话，它被称为客户，B 被称为服务器。用户在客户端键入的每个字符都会被送到远程主机，远程主机则回送每个字符的一个副本，显示在 Telnet 用户的屏幕上。这种"回显"用于确保 Telnet 用户看到的字符已在远端被接收并处理。因此，从用户按键到字符显示在显示器上，每个字符都要在网络中往返两次。

现在假设用户键入了一个字母 'C'，然后端起咖啡喝了一口。我们来考察客户与服务器之间发送的 TCP 报文段。如图 3.30 所示，假设客户与服务器的初始序号分别为 42 和 79。回忆一下，报文段的序号就是其数据字段中第一个字节的序号，因此客户发送的第一个报文段序号为 42，服务器发送的第一个报文段序号为 79。再回忆一下，确认号是主机期望的下一个数据字节的序号。在 TCP 连接建立之后、尚未发送任何数据之前，客户在等待字节 79，服务器在等待字节 42。

如图 3.30 所示，共发送三个报文段。第一个报文段从客户发往服务器，数据字段中装着字母 'C' 的 1 字节 ASCII 表示；该报文段的序号字段为 42。又因为客户尚未从服务器收到任何数据，这个报文段的确认号字段为 79。

<Figure src="ch03/fig3-30.webp" caption="图 3.30　一个简单 Telnet 应用在 TCP 上的序号与确认号" />

第二个报文段从服务器发往客户，它有两个用途。其一，它确认服务器已收到的数据：通过在确认号字段填入 43，服务器告诉客户，它已成功收到直到字节 42 的全部内容，现在正等待字节 43 及其后的字节。其二，它回显字母 'C'，因此第二个报文段的数据字段中是 'C' 的 ASCII 表示。这个报文段的序号为 79，即该 TCP 连接服务器到客户数据流的初始序号，因为这是服务器发送的第一个数据字节。注意，对客户到服务器数据的确认，是搭载在承载服务器到客户数据的报文段中传送的；这种确认被称为**捎带**（piggybacked）在服务器到客户的数据报文段上。

第三个报文段从客户发往服务器，其唯一目的是确认它已从服务器收到的数据。（回忆一下，第二个报文段中包含了服务器到客户的字母 'C'。）该报文段的数据字段为空，即这个确认没有捎带任何客户到服务器的数据。它的确认号字段为 80，因为客户已收到直到序号 79 的字节流，现在正等待字节 80 及其后的字节。你也许会觉得奇怪：这个报文段不含数据，为什么还有序号？但由于 TCP 有序号字段，报文段总得有个序号。
