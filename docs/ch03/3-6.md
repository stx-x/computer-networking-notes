# 3.6　拥塞控制原理

前面几节既考察了在分组丢失情况下提供可靠数据传输服务的一般原理，也考察了 TCP 的具体机制。前面提到，实践中这类丢失通常源于网络拥塞时路由器缓冲区的溢出。因此，分组重传只是**治标**——处理网络拥塞的一个症状（某个运输层报文段的丢失），却没有**治本**——网络拥塞的根源在于太多源端试图以过高的速率发送数据。要治本，就需要有这样的机制：在网络拥塞时抑制发送方。

本节在一般意义上讨论拥塞控制问题，力求弄清：为什么拥塞是坏事？网络拥塞如何体现在上层应用所获得的性能上？有哪些办法可以避免拥塞或对拥塞作出反应？这种一般性研究是恰当的，因为与可靠数据传输一样，拥塞控制高居网络领域"十大根本问题"之列。下一节则详细研究 TCP 的拥塞控制算法。

## 3.6.1　拥塞的成因与代价

我们从三个越来越复杂的拥塞场景入手，开始对拥塞控制的一般性研究。在每个场景中，我们都考察拥塞究竟因何而起，以及拥塞的代价（就资源未被充分利用、端系统获得较差性能而言）。我们（暂时）不关注如何应对或避免拥塞，而只关注一个更简单的问题：当主机提高发送速率、网络变得拥塞时，究竟会发生什么。

### 场景 1：两个发送方、一台无限缓冲的路由器

从最简单的拥塞场景开始：两台主机（A 与 B）各有一条连接，在源与目的之间共享一段单跳链路，如图 3.41 所示。

假设主机 A 中的应用以平均速率 $\lambda_{\text{in}}$ 字节/秒向连接中送入数据。这些数据是"原始"的，即每个数据单元只被送入套接字一次。底层运输层协议很简单：封装数据并发送，不做任何差错恢复（如重传）、流量控制或拥塞控制。忽略添加运输层与低层首部带来的额外开销，场景 1 中主机 A 向路由器提供的流量速率就是 $\lambda_{\text{in}}$ 字节/秒。主机 B 以类似方式工作，为简单起见假定它也以 $\lambda_{\text{in}}$ 字节/秒的速率发送。来自 A 和 B 的分组经过一台路由器，再通过一条容量为 $R$ 的共享出链路。路由器配有缓冲区，当分组到达速率超过出链路容量时用来暂存到达的分组。在场景 1 中，假定路由器拥有无限大的缓冲空间。

<Figure src="ch03/fig3-41.webp" caption="图 3.41　拥塞场景 1：两条连接共享一条无限缓冲的单跳链路" />

图 3.42 描绘了场景 1 下主机 A 这条连接的性能。左图给出每条连接的吞吐量（接收方每秒收到的字节数）随连接发送速率的变化。当发送速率在 0 与 $\frac{R}{2}$ 之间时，接收方吞吐量等于发送方发送速率——发送方发出的所有数据都以有限时延被接收方收到。然而当发送速率超过 $\frac{R}{2}$ 时，吞吐量只有 $\frac{R}{2}$。这个吞吐量上限是两条连接共享链路容量的结果：在稳态下，链路根本无法以超过 $\frac{R}{2}$ 的速率向接收方交付分组。无论 A、B 把发送速率设得多高，各自看到的吞吐量都不会超过 $\frac{R}{2}$。

<Figure src="ch03/fig3-42.webp" caption="图 3.42　拥塞场景 1：吞吐量和时延随主机发送速率的变化" />

每条连接达到 $\frac{R}{2}$ 的吞吐量，看上去似乎是件好事，因为链路在向目的地交付分组方面得到了充分利用。然而图 3.42 的右图揭示了在接近链路容量运行时会发生什么：当发送速率（从左侧）逼近 $\frac{R}{2}$ 时，平均时延越来越大；一旦发送速率超过 $\frac{R}{2}$，路由器中排队的平均分组数将无界增长，源到目的的平均时延趋于无穷（假定连接以这些发送速率运行无限长时间，且缓冲无限大）。因此，虽然从吞吐量角度看，以接近 $R$ 的总吞吐量运行是理想的，但从时延角度看却远非理想。即便在这个（极端）理想化的场景中，我们已经找到了**拥塞网络的一种代价——当分组到达速率接近链路容量时，将经历很大的排队时延**。

### 场景 2：两个发送方、一台有限缓冲的路由器

现在把场景 1 稍作两处修改（见图 3.43）。第一，假定路由器缓冲区的容量有限。这一贴近现实的假设带来的后果是：当分组到达一个已满的缓冲区时将被丢弃。第二，假定每条连接都是可靠的：若承载运输层报文段的分组在路由器处被丢弃，发送方最终会重传它。由于分组可能被重传，我们在使用"发送速率"一词时必须更谨慎。具体地说，仍用 $\lambda_{\text{in}}$ 表示应用向套接字送入原始数据的速率；而运输层向网络发送报文段（含原始数据与重传数据）的速率记作 $\lambda '_{\text{in}}$，$\lambda '_{\text{in}}$ 有时称为向网络**提供的负载**（offered load）。

<Figure src="ch03/fig3-43.webp" caption="图 3.43　场景 2：两台主机（带重传）与一台有限缓冲的路由器" />

场景 2 下实现的性能，此时将强烈依赖于重传是如何进行的。先考虑一个不现实的极端：主机 A 能（神奇地！）判断路由器中是否有空闲缓冲区，因而只在有空闲缓冲时才发送分组。此时不会发生丢失，$\lambda_{\text{in}}$ 等于 $\lambda '_{\text{in}}$，连接吞吐量等于 $\lambda_{\text{in}}$。这一情形如图 3.44(a) 所示。从吞吐量角度看性能是理想的——发出的都被收到。注意在此情形下，主机的平均发送速率不可能超过 $\frac{R}{2}$，因为假定从不发生分组丢失。

<Figure src="ch03/fig3-44.webp" caption="图 3.44　有限缓冲下场景 2 的性能" />

再看稍为现实一些的情形：发送方只在确知某分组已丢失时才重传。（这一假设也有点勉强，但发送方确实可以把超时设得足够大，以致几乎可以确信未被确认的分组已经丢失。）此时性能大致如图 3.44(b) 所示。为理解其中缘由，考虑提供的负载 $\lambda '_{\text{in}}$（原始数据传输速率加重传）等于 $\frac{R}{2}$ 的情形：按图 3.44(b)，在此提供的负载下，数据交付给接收方应用的速率是 $\frac{R}{3}$。于是在所传输的 $0.5 R$ 单位数据中，平均有 $0.333 R$ 字节/秒是原始数据，$0.166 R$ 字节/秒是重传数据。这里我们看到了**拥塞网络的第二种代价——发送方必须重传，以补偿因缓冲区溢出而被丢弃（丢失）的分组**。

最后，考虑发送方可能过早超时、从而重传一个在队列中被延迟但尚未丢失的分组的情形。此时，原始数据分组与重传副本都可能到达接收方。当然，接收方只需要该分组的一份，会丢弃重传副本。在这种情况下，路由器转发原始分组重传副本所做的工作被浪费了，因为接收方早已收到该分组的原始副本；路由器本可以把链路传输能力用于发送别的分组。**这就是拥塞网络的第三种代价——面对大时延时，发送方不必要的重传会使路由器把链路带宽用于转发无用的分组副本**。若假定每个分组平均被路由器转发两次，图 3.44(c) 给出了吞吐量随提供的负载的变化；由于每个分组被转发两次，当提供的负载逼近 $\frac{R}{2}$ 时，吞吐量的渐近值为 $\frac{R}{4}$。

### 场景 3：四个发送方、有限缓冲的路由器与多跳路径

在最后一个拥塞场景中，四台主机各自通过重叠的两跳路径发送分组，如图 3.45 所示。我们仍假定每台主机都用超时/重传机制实现可靠数据传输服务，所有主机的 $\lambda_{\text{in}}$ 相同，所有路由器链路的容量均为 $R$ 字节/秒。

考虑从主机 A 到主机 C、经过路由器 R1 和 R2 的连接。A–C 连接与 D–B 连接共享路由器 R1，与 B–D 连接共享路由器 R2。当 $\lambda_{\text{in}}$ 极小时，缓冲区溢出很少发生（与场景 1、2 一样），吞吐量约等于提供的负载。当 $\lambda_{\text{in}}$ 稍大时，相应吞吐量也更大，因为更多原始数据被送入网络并交付到目的地，而溢出仍然很少。因此，对较小的 $\lambda_{\text{in}}$，$\lambda_{\text{in}}$ 增大导致 $\lambda_{\text{out}}$ 增大。

考察了极低流量情形之后，再看 $\lambda_{\text{in}}$（因而 $\lambda '_{\text{in}}$）极大的情形。考虑路由器 R2：无论 $\lambda_{\text{in}}$ 取何值，A–C 流量到达 R2（经 R1 转发后到达 R2）的速率至多为 $R$，即 R1 到 R2 那条链路的容量。如果所有连接（包括 B–D 连接）的 $\lambda '_{\text{in}}$ 都极大，那么 B–D 流量到达 R2 的速率可能远大于 A–C 流量的到达速率。由于 A–C 与 B–D 流量必须在路由器 R2 处竞争有限的缓冲空间，随着 B–D 提供的负载越来越大，能够成功通过 R2（即未因缓冲区溢出而丢失）的 A–C 流量就越来越少。在极限情形下，当提供的负载趋于无穷时，R2 中刚空出的缓冲区立刻被 B–D 分组填满，A–C 连接在 R2 处的吞吐量趋于零；这又意味着，在重载极限下 A–C 的端到端吞吐量趋于零。这些考虑引出了图 3.46 所示的提供的负载与吞吐量之间的折衷关系。

<Figure src="ch03/fig3-45.webp" caption="图 3.45　四个发送方、有限缓冲的路由器与多跳路径" />

<Figure src="ch03/fig3-46.webp" caption="图 3.46　有限缓冲与多跳路径下场景 3 的性能" />

一旦考虑网络所做的无用功，吞吐量随提供的负载增加而最终下降的原因就一目了然了。在上述高流量场景中，只要分组在第二跳路由器处被丢弃，第一跳路由器把它转发给第二跳路由器所做的工作就"白费"了。如果第一台路由器干脆丢弃该分组并保持空闲，网络的处境也一样（更准确地说，也一样糟）。更要紧的是，第一台路由器为把该分组转发给第二台路由器而占用的传输能力，本可以更有价值地用于传输另一个分组。（例如，在选择要发送的分组时，路由器或许应当优先发送那些已经经过若干上游路由器的分组。）于是我们看到了**因拥塞而丢弃分组的又一种代价——当一个分组沿路径被丢弃时，各上游链路上为把它转发到丢弃点而消耗的传输能力都白费了**。

有了对拥塞代价的新认识——分组到达速率接近拥塞链路容量时排队时延增大（图 3.42）、因存在重传分组而使应用间吞吐量下降（图 3.44）、以及可能发生**拥塞崩溃**（图 3.46）——实施某种形式的拥塞控制显然是必要的。

在考察解决拥塞控制问题的方法之前，先退一步，看看这些协议试图解决的根本问题。图 3.47 展示了 $N$ 条运输层连接通过一条最大传输速率为 $R$ bps 的共享**瓶颈链路**。一条连接的瓶颈链路，是端到端路径上这样一条链路：若经过该链路的各发送方缓慢提高其发送速率，则该链路将是这些连接的端到端路径上最先出现拥塞丢失的链路。通常，我们只在链路处于拥塞状态时才称其为瓶颈链路。一个常见假设 [Cardwell 2017; Kleinrock 2018]——它在理论与实践上通常都成立 [Hu 2024]——是一条连接至多有一条瓶颈链路；源到目的路径不同的连接，其瓶颈链路也可能不同。

<Figure src="ch03/fig3-47.webp" caption="图 3.47　N 条连接共享一条容量为 R 的瓶颈链路" />

一条路径的瓶颈链路在拥塞控制中扮演重要角色。假设某瓶颈链路处于拥塞状态，即到达该链路的流量速率接近其容量 $R$。如果这 $N$ 条连接都提高发送速率，瓶颈链路也无法为这些连接提供任何额外吞吐量，因为该链路已经拥塞，在这种拥塞状态下始终忙于传输流量。因此，**通过该瓶颈链路的 $N$ 条连接所获得的总端到端吞吐量，将由瓶颈链路的传输速率 $R$ 决定**。而如果链路容量在这 $N$ 条连接之间被公平地共享（见 7.3.4 节），则每条连接的吞吐量为 $\frac{R}{N}$。

一个类比有助于直观理解。把图 3.47 中的 $N$ 条连接想象成 $N$ 根软管，它们接到一根共用的总软管上，总软管的最大出水流量为 $R$ 升/秒；总软管的出水量再平均分配给从它分出的、通向 $N$ 个目的地的 $N$ 根软管。凭经验可知，如果这 $N$ 条连接的输入速率之和超过 $R$ 升/秒，共用软管仍然无法输出超过其最大流量 $R$ 升/秒的水，因而任何端到端软管路径的流量都不会超过 $\frac{R}{N}$ 升/秒。

带着这一认识回到计算机网络：拥塞控制的目标应当是，**让图 3.47 中的 $N$ 条连接设定其运输层发送速率，使它们的总发送速率接近但不超过瓶颈链路的容量**。总发送速率低于这一理想值，会在发送方还有数据要发时使链路有时空闲；总发送速率高于这一理想值，则会遭受我们刚刚研究过的链路拥塞的全部负面后果。

于是立刻浮现出两个基本问题：

- 一条连接如何知道其源到目的路径上的某条链路发生了拥塞，即存在瓶颈链路？我们将在 7.6.2 节讨论这个问题。
- 各连接如何各自调节发送速率，使其总发送速率接近但不超过其路径上瓶颈链路的容量？我们将在 7.3 节看到 TCP 拥塞控制的不同"变体"如何回答这个问题。

## 3.6.2　端到端与网络辅助的拥塞控制

3.7 节将详细考察 TCP 具体的拥塞控制方法。这里先指出实践中采用的两大类拥塞控制方法，并讨论体现这些方法的具体网络体系结构与拥塞控制协议。

从最高层次看，可以按**网络层是否向运输层提供显式的拥塞控制协助**来区分不同的拥塞控制方法：

::: tip 要点

1. **端到端拥塞控制。** 在端到端方法中，网络层不为拥塞控制目的向运输层提供任何显式支持；甚至网络是否拥塞，也必须由端系统仅依据观察到的网络行为（例如分组丢失和时延）来推断。稍后 3.7.1 与 3.7.2 节将会看到，TCP 采取的正是这种端到端方法，因为 IP 层并不被要求向主机反馈网络拥塞信息。我们将考察 TCP 的若干不同"变体"：在某些变体中，报文段丢失（由超时或收到三个重复 ACK 指示）被当作网络拥塞的迹象，TCP 据此减小其窗口；另一些变体的 TCP 则用测得的往返时延和/或吞吐量来确定发送速率。
1. **网络辅助拥塞控制。** 在网络辅助方法中，路由器向发送方和/或接收方显式反馈网络的拥塞状态。这种反馈可以简单到用一个比特指示某条链路发生拥塞——早期 IBM SNA [Schwartz 1982]、DEC DECnet [Jain 1989; Ramakrishnan 1990] 以及 ATM [Black 1995] 网络体系结构采取的就是这种做法；也可以更精细，例如在 ATM 可用比特率（ABR）拥塞控制中，路由器把出链路上它能支持的最大主机发送速率告知发送方。如上所述，IP 与 TCP 的因特网默认版本采取端到端的拥塞控制方法；不过 3.7.3 节将会看到，近来 IP 与 TCP 也可以可选地实现网络辅助拥塞控制。

:::

对网络辅助拥塞控制，拥塞信息通常按图 3.48 所示的两种方式之一从网络反馈给发送方。一种是由网络路由器直接向发送方发送反馈，这种通知通常采取**阻流分组**（choke packet）的形式（实质上是在说"我拥塞了！"）。第二种、也是更常见的方式，是路由器在从发送方流向接收方的分组中标记/更新某个字段以指示拥塞；接收方收到被标记的分组后，再把拥塞指示通知发送方。后一种通知方式需要一个完整的往返时间。

<Figure src="ch03/fig3-48.webp" caption="图 3.48　网络指示的拥塞信息的两种反馈途径" />
