# 3.5.3　往返时间估计与超时

与 3.4 节的 rdt 协议一样，TCP 使用超时/重传机制来从丢失的报文段中恢复。这在概念上很简单，但当我们在 TCP 这样的实际协议中实现超时/重传机制时，会出现许多微妙的问题。最明显的问题大概就是超时间隔该取多长。显然，超时应大于该连接的往返时间（RTT），即从报文段发出到它被确认所经历的时间；否则就会发送不必要的重传。但究竟要大多少？RTT 又该如何估计？是否应为每一个未确认的报文段都关联一个定时器？问题真不少！本节的讨论基于 [Jacobson 1988] 中关于 TCP 的工作，以及当前 IETF 关于 TCP 定时器管理的建议 [RFC 6298]。

## 估计往返时间

先看 TCP 如何估计发送方与接收方之间的往返时间。做法如下：一个报文段的**样本 RTT**（SampleRTT）是该报文段从发出（即交给 IP）到收到其确认之间所经历的时间。多数 TCP 实现并不为每个发送的报文段都测量一个 SampleRTT，而是在任一时刻只测量一个 SampleRTT。也就是说，在任何时刻，只对某一个已发送但尚未确认的报文段估计 SampleRTT，因而大约每个 RTT 得到一个新的 SampleRTT 值。此外，TCP 从不为**重传**过的报文段计算 SampleRTT，只对**仅发送过一次**的报文段测量 SampleRTT [Karn 1987]。（章末有一道习题请你思考其中的原因。）

显然，由于路由器中的拥塞以及端系统负载的变化，SampleRTT 的值会随报文段不同而波动。由于这种波动，任何一个给定的 SampleRTT 值都可能是非典型的。为了估计一个典型的 RTT，自然要对 SampleRTT 值取某种平均。TCP 维护 SampleRTT 值的一个平均值，称为 EstimatedRTT。每得到一个的新 SampleRTT，TCP 就按下式更新 EstimatedRTT：

$$
\text{EstimatedRTT} = (1 - \alpha) \cdot \text{EstimatedRTT} + \alpha \cdot \text{SampleRTT} \tag{3.1}
$$

上式写成程序设计语言语句的形式——EstimatedRTT 的新值，是 EstimatedRTT 旧值与 SampleRTT 新值的加权组合。推荐的 $\alpha$ 取值为 0.125（即 $\frac{1}{8}$）[RFC 6298]，此时上式变为：

$$
\text{EstimatedRTT} = 0.875 \cdot \text{EstimatedRTT} + 0.125 \cdot \text{SampleRTT}
$$

注意，EstimatedRTT 是 SampleRTT 值的加权平均。正如章末一道习题所讨论的，这种加权平均给予**近期**样本的权重高于**旧**样本。这很自然，因为近期样本更好地反映了网络当前的拥塞状况。在统计学中，这样的平均值称为**指数加权移动平均**（EWMA）。EWMA 中之所以有"指数"二字，是因为随着更新不断进行，某个给定 SampleRTT 的权重按指数速度衰减。章末习题将请你推导 EstimatedRTT 中的指数项。

图 3.31 给出了 gaia.cs.umass.edu（位于马萨诸塞州阿默斯特）到 fantasia.eurecom.fr（位于法国南部）之间一条 TCP 连接在 $\alpha = \frac{1}{8}$ 时的 SampleRTT 值与 EstimatedRTT。可以看到，SampleRTT 的波动在 EstimatedRTT 的计算中被平滑掉了。

<Figure src="ch03/fig3-31.webp" caption="图 3.31　RTT 样本与 RTT 估计" />

除了 RTT 的估计值，RTT 的**变化程度**也是很有价值的度量。[RFC 6298] 把 RTT 偏差 DevRTT 定义为 SampleRTT 通常偏离 EstimatedRTT 多少的估计：

$$
\text{DevRTT} = (1 - \beta) \cdot \text{DevRTT} + \beta \cdot \lvert \text{SampleRTT} - \text{EstimatedRTT} \rvert \tag{3.2}
$$

注意，DevRTT 是 SampleRTT 与 EstimatedRTT 之差的 EWMA。若 SampleRTT 波动很小，DevRTT 就小；反之若波动很大，DevRTT 就大。$\beta$ 的推荐值为 0.25。

## 设置与管理重传超时间隔

有了 EstimatedRTT 与 DevRTT，TCP 的超时间隔应取何值？显然，该间隔应大于或等于 EstimatedRTT，否则就会发送不必要的重传；但也不能比 EstimatedRTT 大太多，否则报文段丢失时 TCP 不能迅速重传，导致很大的数据传输时延。因此，理想的做法是把超时时间设为 EstimatedRTT 加上一定余量：SampleRTT 波动大时余量应大，波动小时余量应小。DevRTT 的值正该在此发挥作用。TCP 确定重传超时间隔的方法把这些考虑都纳入了：

$$
\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \cdot \text{DevRTT} \tag{3.3}
$$

<AsideCard title="实践中的原理 · TCP 的可靠数据传输">

TCP 通过使用肯定确认和定时器来提供可靠数据传输，做法与 3.4 节所研究的十分相似。TCP 对正确收到的数据予以确认，并在报文段或其确认被认为丢失或损坏时重传报文段。某些版本的 TCP 还有隐式的 NAK 机制——借助 TCP 的**快速重传**机制，收到对某报文段的三个重复 ACK，就相当于对**下一个**报文段的隐式 NAK，从而在超时之前触发该报文段的重传。TCP 用序号让接收方能够识别丢失或重复的报文段。与可靠数据传输协议 rdt3.0 一样，TCP 自身无法确知一个报文段或其 ACK 究竟是丢失、损坏还是被过度延迟；在发送方，TCP 的响应都一样：重传该报文段。

TCP 也使用流水线，允许发送方在任一时刻有多个已发送但尚未确认的报文段在途。前面已经看到，当报文段长度与往返时延之比很小时，流水线能大幅提高会话吞吐量。发送方可以拥有的在途未确认报文段的具体数目，由 TCP 的流量控制与拥塞控制机制决定；TCP 流量控制在本节末尾讨论，拥塞控制在 3.7 节讨论。眼下只需知道 TCP 发送方使用流水线。

推荐的初始 TimeoutInterval 值为 1 秒 [RFC 6298]。此外，一旦发生超时，TimeoutInterval 的值加倍，以避免对随后很快就会被确认的报文段过早超时。不过，一旦收到报文段并更新了 EstimatedRTT，TimeoutInterval 就又用上面的公式重新计算。

# 3.5.4　可靠数据传输

回忆一下，因特网的网络层服务（IP 服务）是不可靠的：IP 不保证数据报交付，不保证数据报按序交付，也不保证数据报中数据的完整性。在 IP 服务下，数据报可能溢出路由器缓冲区而永远到不了目的地，可能失序到达，其中的比特也可能损坏（0 变 1、1 变 0）。由于运输层报文段是由 IP 数据报承载着穿越网络的，运输层报文段同样会遭遇这些问题。

TCP 在 IP 不可靠的尽力而为服务之上，创建了可靠数据传输服务。TCP 的可靠数据传输服务确保：一个进程从 TCP 接收缓冲区读出的数据流是无损坏的、无间隙的、无重复的、且按序的；也就是说，该字节流与连接另一端端系统所发送的字节流完全一致。TCP 提供可靠数据传输的方式，涉及 3.4 节研究过的许多原理。

在先前发展可靠数据传输技术时，从概念上说最容易的假设是：为每个已发送但尚未确认的报文段关联一个定时器。这在理论上很好，但定时器管理可能需要相当大的开销。因此，推荐的 TCP 定时器管理规程 [RFC 6298] 只使用**一个**重传定时器，即使有多个已发送但尚未确认的报文段。本节描述的 TCP 协议遵循这一单定时器建议。

我们分两步、逐步深入地讨论 TCP 如何提供可靠数据传输：先给出一个高度简化的 TCP 发送方描述，它只用超时来从丢失的报文段中恢复；再给出更完整的描述，除超时之外还使用重复 ACK。以下讨论假定数据只在一个方向上传输，即从主机 A 发往主机 B，且 A 正在发送一个大文件。

图 3.32 给出了 TCP 发送方的一个高度简化的描述。可以看到，TCP 发送方中有三个与数据传输和重传有关的主要事件：从上层收到数据、定时器超时、收到 ACK。

发生第一个事件时，TCP 从应用收到数据，把数据封装进报文段，并把报文段交给 IP。注意，每个报文段都包含一个序号，即该报文段中第一个数据字节的字节流编号（见 3.5.2 节）。还要注意，如果定时器尚未因其他报文段而运行，TCP 在把报文段交给 IP 时启动定时器。（把定时器看作与最早的未确认报文段相关联，是有帮助的。）该定时器的超时间隔就是 TimeoutInterval，由 3.5.3 节所述的 EstimatedRTT 与 DevRTT 算出。

第二个主要事件是超时。TCP 通过重传引起超时的那个报文段来响应超时事件，然后重启定时器。

TCP 发送方必须处理的第三个主要事件，是收到来自接收方的确认报文段（更准确地说，是包含有效 ACK 字段值的报文段）。此事件发生时，TCP 把 ACK 值 $y$ 与其变量 SendBase 比较。TCP 状态变量 SendBase 是最早的未确认字节的序号（因此 SendBase − 1 就是已知被接收方正确按序收到的最后一个字节的序号）。如前所述，TCP 使用累积确认，因此 $y$ 确认了序号 $y$ 之前所有字节的接收。若 $y > \text{SendBase}$，则该 ACK 确认了一个或多个此前未确认的报文段；于是发送方更新其 SendBase 变量，并且如果当前还有尚未确认的报文段，就重启定时器。

## 几个有趣的场景

以上描述了 TCP 提供可靠数据传输的一个高度简化版本，但即便是这个高度简化的版本也有许多微妙之处。为体会该协议如何工作，下面走一遍几个简单场景。

图 3.33 描绘了第一个场景：主机 A 向主机 B 发送一个报文段，假设该报文段序号为 92、含 8 字节数据。发出后，主机 A 等待来自 B 的、确认号为 100 的报文段。虽然 A 的报文段被 B 收到，但 B 发往 A 的确认丢失了。此时发生超时事件，主机 A 重传同一个报文段。当然，当主机 B 收到这次重传时，它从序号看出该报文段包含的是已经收到的数据，于是 B 中的 TCP 丢弃重传报文段中的字节。

<Figure src="ch03/fig3-33.webp" caption="图 3.33　因确认丢失而重传" />

第二个场景如图 3.34 所示：主机 A 背靠背发送两个报文段，第一个序号 92、含 8 字节数据，第二个序号 100、含 20 字节数据。假设两个报文段都完好到达 B，B 分别为它们发送两个确认：第一个确认号为 100，第二个确认号为 120。现假设这两个确认在超时之前都未到达主机 A。超时事件发生时，主机 A 重发序号为 92 的第一个报文段，并重启定时器。只要第二个报文段的 ACK 在新的超时之前到达，第二个报文段就不会被重传。

<Figure src="ch03/fig3-34.webp" caption="图 3.34　报文段 100 未被重传" />

第三个、也是最后一个场景：假设主机 A 像上例那样发送两个报文段。第一个报文段的确认在网络中丢失，但就在超时事件之前，主机 A 收到了确认号为 120 的确认。于是主机 A 知道主机 B 已收到直到字节 119 的全部内容，因此不再重传这两个报文段中的任何一个。这一场景如图 3.35 所示。

## 快速重传

超时触发重传的问题之一，是超时周期可能相对较长。当一个报文段丢失时，这个较长的超时周期迫使发送方延迟重发丢失的分组，从而增大端到端时延。所幸，发送方常常可以在超时事件发生之前，通过所谓的**重复 ACK** 推断出分组丢失。重复 ACK 是对某个报文段的再次确认，而发送方此前已经收到过对该报文段的确认。要理解发送方对重复 ACK 的响应，必须先弄清接收方究竟为什么发送重复 ACK。

当 TCP 接收方收到的报文段序号大于下一个期望的按序序号时，它就在数据流中检测到一个**间隙**，即有报文段缺失。这个间隙可能是网络中的报文段丢失或乱序造成的。由于 TCP 使用累积确认，一旦检测到间隙，TCP 接收方只是对它已收到的最后一个按序字节重新确认（即产生一个重复 ACK）。由于发送方使用流水线，收发双方之间可能有许多在途报文段；若其中一个在途报文段丢失，TCP 接收方很可能会产生许多背靠背的重复 ACK。因此，如果 TCP 发送方收到对同一数据的三个重复 ACK（即先收到该数据的一个原始 ACK，随后又收到对同一数据的三个额外 ACK），它就认为：被确认了四次的报文段**之后**的那个报文段已经丢失。（章末习题将讨论为什么发送方要等三个重复 ACK，而不是只等一个。）收到三个重复 ACK 时，TCP 发送方执行**快速重传**（fast retransmit）[RFC 5681]，在该报文段的定时器超时之前重传丢失的报文段。

## 回退 N 步还是选择重传？

在结束对 TCP 差错恢复机制的讨论之前，考虑这样一个问题：TCP 是 GBN 协议还是 SR 协议？回忆一下，TCP 的确认是累积的，接收方不会对正确收到但失序的报文段逐个确认。因此，如图 3.32（另见图 3.19）所示，TCP 发送方只需维护已发送但未确认字节的最小序号（SendBase）以及下一个待发字节的序号（NextSeqNum）。从这个意义上说，TCP 很像 GBN 风格的协议。

但 TCP 与 GBN 之间也有一些显著差异。许多 TCP 实现会缓存正确收到但失序的报文段 [Stevens 1994]。再考虑这样一种情形：发送方发送报文段 1, 2, …, N，所有报文段都按序、无差错地到达接收方；进一步假设对报文段 $n$（$n < N$）的确认丢失了，而其余 $N - 1$ 个确认都在各自超时之前到达了发送方。在这个例子中，GBN 不仅要重传报文段 $n$，还要重传其后所有报文段 $n + 1, n + 2, …, N$；而 TCP 至多重传一个报文段，即报文段 $n$。更有甚者，如果对报文段 $n + 1$ 的确认在报文段 $n$ 超时之前到达，TCP 根本不会重传报文段 $n$。
